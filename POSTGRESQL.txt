TASK 0.1: Process Model Discovery [CON] [OP]
  - Start PostgreSQL and identify every running process by name and function
  - Trace: client connects → postmaster forks backend → authentication →
    query received → parsing → planning → execution → result returned

    WAL receiver, stats collector, logical replication launcher
  - Understand what happens when each process type is killed: which are
    critical (postmaster death = all connections lost, cluster down),
    which are resilient (backend death = one connection lost),
    which restart automatically (autovacuum workers)

TASK 0.2: Directory Structure Discovery [CON] [OP]
  - Navigate PGDATA and understand purpose of every subdirectory
  - Learn: base/ (database files, one directory per database OID),
    global/ (cluster-wide catalog tables), pg_wal/ (WAL segment files),
    pg_stat/ (statistics files), pg_stat_tmp/ (temporary statistics),
    pg_tblspc/ (tablespace symlinks), pg_logical/ (logical replication
    state), pg_xact/ (transaction commit status, formerly pg_clog),
    pg_subtrans/ (subtransaction status), pg_multixact/ (shared row lock
    status), pg_commit_ts/ (commit timestamps), pg_dynshmem/ (dynamic
    shared memory state), pg_notify/ (LISTEN/NOTIFY state), pg_serial/
    (serializable transaction state), pg_snapshots/ (exported snapshots),
    pg_twophase/ (prepared two-phase commit transactions)
  - Find a specific table file: pg_relation_filepath() → navigate to file →
    verify with hex viewer — identify 8KB page boundaries

TASK 0.3: Shared Memory Discovery [CON] [OP]
  - Identify shared memory segments: ipcs -m or /dev/shm entries
  - Understand: shared_buffers stores data pages (not queries, not plans)
  - Understand: OS page cache also stores data pages → double buffering
  - Install pg_buffercache extension → inspect which relations occupy
    buffer space → observe usage_count distribution
  - Learn what else lives in shared memory: lock tables, process array,
    WAL buffers, prepared transaction state, replication state

TASK 0.4: Configuration System Discovery [CON] [OP]
  - Locate postgresql.conf and understand include, include_dir, include_if_exists
  - Understand layering: postgresql.conf → postgresql.auto.conf → ALTER SYSTEM
  - Query pg_settings: name, setting, unit, category, context, vartype,
    source, sourcefile, sourceline, pending_restart
  - Learn context values: postmaster (requires restart), sighup (reload),
    user (per-session), superuser (superuser per-session), backend (set
    at connection start), internal (read-only)
  - Categorize key parameters by context: know which require restart vs reload

TASK 0.5: The Complete Architecture Diagram [CON]
  - Draw from memory: client connection → postmaster → backend pool →
    shared_buffers ↔ OS page cache ↔ disk → WAL buffer → WAL writer →
    pg_wal → archive command → archive destination
  - Include every process: bgwriter → dirty pages to disk, checkpointer →
    checkpoint execution, autovacuum launcher → worker spawning, WAL sender →
    standby, stats collector → pg_stat files
  - Annotate every arrow: data flow direction, protocol, shared memory vs IPC
  - Explain the complete path of a single INSERT from client to disk

COMMON FAILURES FOR MODULE 0:
────────────────────────────────────────────────────────────────

FAILURE 0.F1: PostgreSQL won't start after configuration change
  Symptom: systemctl start fails, pg_ctl start fails
  Diagnosis: check pg_settings for pending_restart entries, check
    postgresql.conf syntax (especially quotes, commas, semicolons)
  Recovery: revert configuration change, reload, identify problematic parameter

FAILURE 0.F2: "too many clients already" error
  Symptom: application can't connect, FATAL in logs
  Diagnosis: pg_stat_activity count vs max_connections, identify connection
    consumers (which users, which databases, which applications)
  Recovery: increase max_connections (if memory allows), terminate idle
    connections, implement connection pooling

FAILURE 0.F3: Out of memory condition
  Symptom: process terminated unexpectedly, OOM killer in dmesg
  Diagnosis: correlate PostgreSQL memory usage (shared_buffers + work_mem ×
    connections + maintenance_work_mem) with available RAM
  Recovery: reduce work_mem, reduce max_connections, add connection pooler,
    increase system RAM

FAILURE 0.F4: Disk full on PGDATA
  Symptom: transaction failures, "could not write to file" in logs
  Diagnosis: df -h on PGDATA partition, find largest files/relations
  Recovery: free space (delete old logs, old WAL, old temporary files),
    add storage, move pg_wal to separate partition

FAILURE 0.F5: Port already in use
  Symptom: "could not bind to address" at startup
  Diagnosis: ss -tlnp to find occupying process, check postmaster.pid
  Recovery: stop conflicting process (verify it's safe), change port,
    remove stale postmaster.pid (if previous process definitely dead)

PREREQUISITES: Module 0
PURPOSE: Deploy PostgreSQL that survives production. Every installation

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 1.1: Platform Installation Methods [OP]
  - Install from PGDG repository on Debian/Ubuntu: understand sources.list
    entry, GPG key verification, package contents (postgresql-17,
    postgresql-contrib-17, postgresql-client-17, libpq-dev)
  - Install from PGDG repository on RHEL/Rocky/Alma Linux: understand
    dnf module disable (system PostgreSQL), PGDG repo RPM, package names
    (postgresql17-server, postgresql17-contrib)
  - Understand pg_lsclusters (Debian tool) vs manual systemd unit management
  - Install multiple PostgreSQL versions on one machine: learn how
    packages isolate versions (different binaries, different data directories,
    different ports)

TASK 1.2: initdb — What Happens and Why [CON] [OP]
  - Understand initdb parameters: -D (data directory), --encoding (default
    encoding), --locale (default locale), --lc-collate, --lc-ctype,
    --wal-segsize (WAL segment size), --data-checksums, --auth (default
    authentication method), --auth-host, --auth-local
  - Understand what initdb creates: directory structure, postgresql.conf
    (with calculated defaults based on system resources), pg_hba.conf
    (with specified default auth), pg_ident.conf, template databases
    (template0, template1), system catalogs (populated from bootstrap
    catalog), pg_wal directory, pg_stat directory, postmaster.pid placeholder
  - Understand locale consequences: LC_COLLATE determines string comparison
    order (affects index ordering, ORDER BY, LIKE, = on text), LC_CTYPE
    determines character classification (upper/lower/digit). Locale comes
    from OS; must exist on OS. Changing locale after initdb requires REINDEX
    of all text indexes. SQL_ASCII is dangerous (no encoding validation,
    locale-dependent functions behave unexpectedly)
  - Understand data checksums: protects against silent data corruption from
    storage, RAM, filesystem. Overhead: ~2-3% CPU for checksum calculation.
    Can be enabled on existing cluster with pg_checksums --enable (requires
    full cluster shutdown)
  - Understand WAL segment size: default 16MB. Larger = fewer WAL switches
    (good for high-write), larger archive files (fewer files to manage).
    Smaller = more switches, smaller archive files. Cannot change after initdb

TASK 1.3: Production Filesystem Layout [DES] [OP]
  - Design mount strategy: separate filesystems for PGDATA, pg_wal, pg_log,
    WAL archive, backup staging, and tablespaces
  - PGDATA: XFS filesystem recommended. Mount options: noatime (don't update
    access time on read — significant performance for index scans), nodiratime
  - pg_wal: dedicated NVMe or fast SSD. Separate from PGDATA so WAL writes
    don't contend with data reads. If pg_wal fills, PGDATA still operational
    (writes blocked, reads still work). XFS recommended for good fsync
    performance
  - pg_log: separate mount (cheaper storage acceptable). If pg_log fills,
    prevent PostgreSQL from crashing due to log write failures
  - WAL archive: separate mount or remote (NFS, S3 via archive_command).
    Critical: archive destination failure should not block PostgreSQL
    (archive_command should be designed to fail gracefully)
  - Backup staging: local fast storage for pg_basebackup before offsite copy
  - Tablespaces: place hot tables on fast storage, cold/archive tables on
    cheaper storage
  - Calculate sizes: estimate data growth rate, add 30% headroom, design
    monitoring thresholds at 70% and 85%

TASK 1.4: Process Environment [OP]
  - PostgreSQL dedicated user: no login shell (/sbin/nologin or /bin/false),
    no sudo access, dedicated group (postgres). Why: minimized attack surface
  - ulimits: nofile (max open file descriptors per process — each connection
    opens files, each relation uses file descriptors, default 1024 is too low
    for any real deployment, 65536 recommended), nproc (max processes per user
    — must exceed max_connections + background processes + autovacuum workers
    + parallel workers), memlock (locked memory — required if huge_pages=on
    to allow shared_buffers allocation in huge pages)
  - systemd service: Type=notify (PostgreSQL uses systemd notification protocol),
    User=postgres, Group=postgres, Environment=PGDATA=/path/to/data,
    ExecStart=pg_ctl start, ExecStop=pg_ctl stop -m fast, ExecReload=pg_ctl
    reload, TimeoutSec, Restart=on-failure, RestartSec, KillMode=mixed,
    OOMScoreAdjust (set negative to reduce OOM killer probability but don't
    set too low or OOM killer will never target PostgreSQL even when it should)

TASK 1.5: Kernel Parameter Tuning [CON] [OP]
  - Shared memory: kernel.shmmax (maximum size of a single shared memory
    segment — must be > shared_buffers), kernel.shmall (total shared memory
    pages available system-wide — must be > shared_buffers/pagesize)
  - Semaphores: kernel.sem (four values: SEMMSL — max semaphores per array,
    SEMMNS — max semaphores system-wide, SEMOPM — max operations per semop
    call, SEMMNI — max semaphore arrays). PostgreSQL uses semaphores for
    inter-process locking. Defaults usually sufficient; tune if many instances
  - Memory overcommit: vm.overcommit_memory=2 (never overcommit — process
    won't get killed by OOM if memory is available at allocation time),
    vm.overcommit_ratio (percentage of RAM that can be committed —
    calculate: (RAM - OS overhead) / RAM × 100). With overcommit=2, you
    know exactly when PostgreSQL will hit memory limits (at startup)
    rather than at random time under load
  - Swappiness: vm.swappiness=1 (minimum swap, but not 0 on newer kernels
    where 0 means "never swap" which can cause OOM when memory pressure
    exists). PostgreSQL uses shared_buffers intentionally; swapping
    shared_buffers defeats the purpose and causes terrible performance
  - Huge pages: calculate required pages for shared_buffers
    (shared_buffers/huge_page_size + some overhead), configure
    vm.nr_hugepages. Transparent Huge Pages (THP): disable
    (/sys/kernel/mm/transparent_hugepage/enabled = never). PostgreSQL
    manages memory in 8KB pages; THP can cause unpredictable latency
    spikes during page compaction
  - Dirty page writeback: vm.dirty_ratio (percentage of RAM that can be
    dirty before forcing writeback — if too high, checkpoint storms),
    vm.dirty_background_ratio (percentage of RAM that triggers background
    writeback). These interact with PostgreSQL's own checkpoint mechanism.
    General guidance: set low enough that OS writeback doesn't amplify
    PostgreSQL's checkpoint writes

COMMON FAILURES FOR MODULE 1:
────────────────────────────────────────────────────────────────

FAILURE 1.F1: PostgreSQL Won't Start After Boot
  Symptoms: systemctl shows failed status, no postgres processes visible
  Root cause categories: filesystem mount not ready (systemd dependency
    missing), PGDATA ownership/permissions changed, stale postmaster.pid
    from crash, listen_addresses IP no longer available (network interface
    changed)
  Diagnosis: journalctl -u postgresql, check postmaster.pid existence and
    contents (PID match running process?), check PGDATA ownership and
    permissions, check listen_addresses validity
  Recovery: fix filesystem mount ordering (After= in systemd service),
    restore ownership (chown -R postgres:postgres PGDATA),
    remove stale postmaster.pid (only if process definitely dead),
    fix listen_addresses

FAILURE 1.F2: Permission Denied on Critical File
  Symptoms: "could not read file", "could not open file",
    "Permission denied" in PostgreSQL logs
  Root causes: PGDATA ownership changed (restore from backup as root,
    filesystem remounted with wrong options), SELinux context wrong,
    AppArmor profile blocking, directory permissions too permissive
    or too restrictive
  Diagnosis: ls -la on the file path mentioned in error, ls -laZ
    (SELinux context), audit2why (SELinux), aa-status (AppArmor)
  Recovery: chown -R postgres:postgres, restorecon -R (SELinux),
    adjust AppArmor profile, fix directory permissions

FAILURE 1.F3: Port Already In Use
  Symptoms: "could not bind to address", "Address already in use"
  Root causes: another PostgreSQL instance on same port, stale
    postmaster.pid from crash (socket still held by dead child? — no,
    but PID file prevents new start), another application bound to port
  Diagnosis: ss -tlnp | grep :5432 (or configured port), lsof -i :5432,
    check postmaster.pid for PID and verify process exists
  Recovery: stop conflicting process (verify it's safe), remove stale
    postmaster.pid (verify PID doesn't exist first), change port

FAILURE 1.F4: shared_buffers Allocation Failure
  Symptoms: "could not create shared memory segment" at startup,
    "Invalid argument", "Cannot allocate memory"
  Root causes: kernel.shmmax too small for shared_buffers, system RAM
    insufficient, huge_pages=on but vm.nr_hugepages too small for
    allocation, huge pages fragmented (try echo 3 > /proc/sys/vm/drop_caches
    then try again)
  Diagnosis: sysctl kernel.shmmax and kernel.shmall values,
    free -h (available memory), /proc/meminfo (HugePages_Total
    and HugePages_Free)
  Recovery: increase kernel.shmmax, reduce shared_buffers, allocate
    more huge pages, disable huge_pages if not needed

FAILURE 1.F5: Locale Not Available
  Symptoms: "invalid locale name" at initdb or startup
  Root causes: locale not installed on OS, OS upgrade removed locale
    or changed locale definition, container image missing locale support,
    locale-gen not run after adding locale
  Diagnosis: locale -a (list available locales), locale (current locale
    settings), check if specified locale in output
  Recovery: install locale (apt install language-pack-XX, dnf install
    glibc-langpack-XX), locale-gen, or re-initdb with available locale

FAILURE 1.F6: ulimit Too Low
  Symptoms: "too many open files" errors under load, "could not fork
    process: Resource temporarily unavailable"
  Root causes: nofile limit reached (many connections each open many files),
    nproc limit reached (connections + workers exceeds limit)
  Diagnosis: check ulimit -n and ulimit -u for postgres user,
    lsof -p <postmaster PID> | wc -l to see current open files,
    count PostgreSQL processes
  Recovery: increase ulimits in limits.conf, systemd service file
    (LimitNOFILE, LimitNPROC), restart PostgreSQL

RANDOM FAILURE SCENARIOS FOR MODULE 1:
────────────────────────────────────────────────────────────────

  - Delete postmaster.pid while PostgreSQL is running
  - Change PGDATA ownership to root while PostgreSQL is running
  - Fill /tmp partition (where Unix socket may live)
  - Remove execute permission from pg_wal directory
  - Set log_directory to non-existent path in postgresql.conf then reload
  - Change listen_addresses to unavailable IP then reload

TASK 2.1: Connection Methods and Troubleshooting [OP]
  - Connect via Unix socket (local, no host specified): fastest, most
    secure (no network), requires OS user matching PostgreSQL role or
    peer/ident auth. Unix socket location varies: /var/run/postgresql/
    (Debian), /tmp/ (RHEL default)
  - Connect via TCP/IP (host specified): works remotely, requires
    listen_addresses to include target IP, requires pg_hba.conf entry
  - Connect via URI: postgresql://user:password@host:port/database?options
  - Environment variables: PGHOST (overrides host), PGPORT (overrides port),
    PGUSER (overrides user), PGDATABASE (default database), PGPASSWORD
    (password — security risk, use .pgpass instead), PGPASSFILE (custom
    .pgpass location), PGSERVICE (service file definition)
  - .pgpass file: format (hostname:port:database:username:password), must
    be 0600 permissions, must be owned by user. Security: password stored
    in plaintext on filesystem — ensure filesystem encryption and proper
    ownership
  - .pg_service.conf: service definitions, connection aliases, parameter
    inheritance. Location: /etc/postgresql-common/ or ~/.pg_service.conf
  - Troubleshoot every "could not connect to server" scenario: wrong host
    (typo, DNS resolution), wrong port (default vs configured), firewall
    blocking (iptables, security group, network ACL), pg_hba.conf rejection
    (check entry order and CIDR mask), SSL mismatch (client requires SSL
    but server doesn't offer, or certificate verification fails), PostgreSQL
    service not running (pg_isready failure), Unix socket directory wrong
    or inaccessible

    RowShare, RowExclusive, ShareUpdateExclusive, Share, ShareRowExclusive,
    Exclusive, AccessExclusive), granted (true = lock held, false = waiting)
  - pg_stat_user_tables: seq_scan (sequential scans), seq_tup_read (rows
    read by seq scans), idx_scan (index scans), idx_tup_fetch (rows
    returned by index scans), n_tup_ins (rows inserted), n_tup_upd (rows
    updated — counts HOT updates too), n_tup_del (rows deleted), n_tup_hot_upd
    (HOT updates — subset of n_tup_upd), n_dead_tup (estimated dead rows
    — critical: high = need vacuum), n_live_tup (estimated live rows),
    last_vacuum (last manual vacuum), last_autovacuum (last autovacuum),
    last_analyze (last manual analyze), last_autoanalyze (last autoanalyze),
    vacuum_count (total manual vacuums), autovacuum_count (total autovacuums),
    analyze_count, autoanalyze_count
  - pg_stat_user_indexes: relid (table OID), indexrelid (index OID),
    idx_scan (number of index scans — 0 = unused index), idx_tup_read
    (index entries read), idx_tup_fetch (rows fetched from heap)
  - pg_statio_user_tables: heap_blks_read (blocks read from disk),
    heap_blks_hit (blocks found in shared_buffers), idx_blks_read,

  - pg_statio_user_indexes: idx_blks_read (disk reads for this index),
    idx_blks_hit (buffer hits for this index)
  - pg_stat_bgwriter: checkpoints_timed (scheduled checkpoints),

    means bgwriter/checkpointer isn't keeping up), buffers_alloc (total

TASK 2.5: Essential Diagnostic Queries [DIAG] [MON]
  Build a diagnostic query portfolio. Each query must be:
    - Understood (not just copy-pasted)
    - Saved and version-controlled
    - Retrievable within seconds when diagnosing an incident

  Portfolio contents:
    - Top 10 largest relations (table + index + toast combined)
    - Tables with dead tuple ratio > 20% (bloat indicator)
    - Tables never vacuumed (last_vacuum IS NULL AND last_autovacuum IS NULL)
    - Tables with statistics older than 7 days
    - Tables approaching transaction wraparound (age(relfrozenxid) > 1B)
    - Unused indexes (idx_scan = 0, excluding unique constraint indexes)
    - Duplicate indexes (same columns, same order, same predicates)
    - Invalid indexes (indisvalid = false)
    - Long-running queries (by duration, with blocking chain)
    - Idle-in-transaction sessions over threshold
    - Blocking chain (waiting PID → blocking PID → query both are executing)
    - Replication lag per standby (bytes and time)
    - Cache hit ratio per database (blks_hit / (blks_hit + blks_read))
    - Current autovacuum progress on large tables
    - Temporary file usage by database (temp_files, temp_bytes)
    - Sequences near exhaustion (> 80% of maxvalue)
    - Tables without primary keys

FAILURE 2.F1: "too many connections" / "remaining connection slots reserved"
  Symptoms: FATAL in logs, application cannot connect
  Diagnosis: pg_stat_activity count vs max_connections, connection count
    per database, per user, per application. Check superuser_reserved_connections.
    Check for connection leaks (idle connections with old backend_start).
  Recovery: terminate idle connections (pg_terminate_backend), increase
    max_connections (if memory allows), implement connection pooler
    immediately to prevent recurrence

FAILURE 2.F2: Authentication failure
  Symptoms: "FATAL: password authentication failed", "FATAL: no pg_hba.conf
    entry for host"
  Diagnosis: check pg_hba.conf entry order (first matching line applies),
    check CIDR mask (wrong mask = no match), check auth method (md5 vs
    scram-sha-256), check password validity (pg_shadow.rolvaliduntil),
    check user existence (pg_roles)
  Recovery: add correct pg_hba.conf entry before conflicting entry, reload
    PostgreSQL, verify with test connection

FAILURE 2.F3: Query hangs indefinitely
  Symptoms: pg_stat_activity shows query in 'active' state with
    wait_event_type = 'Lock'
  Diagnosis: join pg_locks WHERE NOT granted → find waiting PID → find
    blocking PID (granted lock on same relation/transaction) → check
    blocking PID's query in pg_stat_activity
  Recovery: terminate blocking transaction (if idle in transaction or
    unreasonable duration) or wait

FAILURE 2.F4: Connection accepted but query fails with "relation does not exist"
  Symptoms: relation exists (visible in \dt), but query can't find it
  Diagnosis: check search_path (SHOW search_path;), check schema of
    relation (\d+ tablename shows schema), check if relation is in
    search_path schemas
  Recovery: use schema-qualified name (schema.tablename) or adjust search_path

FAILURE 2.F5: psql script fails silently
  Symptoms: script runs, some statements don't execute, no errors
  Diagnosis: missing ON_ERROR_STOP setting. Check exit code of psql
    ($? in shell). Add \set ON_ERROR_STOP on at script start.
  Recovery: fix failing statements, re-run with ON_ERROR_STOP

MODULE 3: DATA STORAGE — PAGES, TUPLES, TOAST
================================================================================
PREREQUISITES: Module 2
PURPOSE: Understand physical disk representation. Bloat, vacuum behavior,
  and I/O performance all originate from page/tuple/TOAST structure.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 3.1: Page Layout Internals [CON] [OP]
  - Install pageinspect extension
  - Inspect page 0 of any table: SELECT * FROM page_header(get_raw_page('t',0));
  - Interpret every header field:
    lsn       — WAL LSN of last page modification (for crash recovery)
    checksum  — page checksum (0 if data checksums disabled at initdb)
    flags     — page flags: 0=normal, 1=PD_HAS_FREE_LINES, 2=PD_PAGE_FULL,
                4=PD_ALL_VISIBLE
    lower     — byte offset where item pointers end (grows upward)
    upper     — byte offset where tuple data starts (grows downward)
    special   — byte offset of special space (used by indexes, 0 for heap)
    pagesize  — always 8192 (8KB) for standard build
    version   — page layout version (4 for PostgreSQL 8.3+, unlikely to change)
    prune_xid — transaction ID that last pruned this page
  - Inspect all tuples on page:
    SELECT * FROM heap_page_items(get_raw_page('t', 0));
  - Interpret every tuple field:
    lp         — line pointer index (position on page)
    lp_off     — byte offset of tuple data from page start
    lp_flags   — 0=unused, 1=normal, 2=redirect (HOT), 3=dead
    lp_len     — length of tuple data in bytes
    t_xmin     — transaction ID that created this tuple version
    t_xmax     — transaction ID that deleted/updated this version (0=living)
    t_field3   — combined cmin/cmax (command ID within transaction)
    t_ctid     — current tuple ID (page, offset): points to self normally,
                 points to new version after UPDATE
    t_infomask2 — additional flags (number of attributes, HOT status)
    t_infomask  — visibility and status flags (HEAP_XMIN_COMMITTED,
                  HEAP_XMAX_COMMITTED, HEAP_HASNULL, etc.)
    t_hoff      — tuple header offset (where header ends and data begins)
    t_bits      — NULL bitmap (which attributes are NULL)
    t_oid       — object ID (only if table created WITH OIDS, deprecated)
    t_data      — actual column data (binary)

  - Draw the complete page layout from memory:
    ┌──────────────────────────────────────────┐ offset 0
    │ PageHeaderData (24 bytes)                │
    ├──────────────────────────────────────────┤
    │ ItemId (4 bytes each, grow downward)     │
    │ ItemId 1: offset=X, flags=Y, len=Z       │
    │ ItemId 2: ...                            │
    │ ...                                       │
    │            FREE SPACE                     │
    │              (middle)                     │
    │ ...                                       │
    │ Tuple data (variable, grow upward)        │
    │ Tuple 2 (at upper-1 offset)               │
    │ Tuple 1 (at upper-0 offset)               │
    ├──────────────────────────────────────────┤
    │ Special space (indexes only, 0 for heap) │ offset 8192
    └──────────────────────────────────────────┘

TASK 3.2: Tuple Lifecycle Through INSERT/UPDATE/DELETE [CON] [OP]
  - INSERT: observe new tuple with t_xmin = current XID, t_xmax = 0,
    t_ctid = (self page, self offset). infomask shows HEAP_XMAX_INVALID
  - UPDATE: observe old tuple's t_xmax set to updating XID, t_ctid changed
    to point to new tuple location. New tuple inserted with t_xmin =
    updating XID, t_xmax = 0. infomask on old tuple shows HEAP_UPDATED
    if this is part of update chain
  - DELETE: observe tuple's t_xmax set to deleting XID. t_ctid unchanged.
    Tuple not physically removed
  - After COMMIT: observe infomask bits change — HEAP_XMIN_COMMITTED or
    HEAP_XMAX_COMMITTED set by first reader that needs to check commit
    status (hint bit setting)
  - After VACUUM: dead tuples (t_xmax committed + older than all snapshots)
    are physically removed. Line pointers either recycled (marked unused)
    or become dead line pointers

TASK 3.3: HOT (Heap-Only Tuple) Updates [CON] [OP]
  - Create table with index. Update non-indexed column.
  - Observe via pageinspect: new tuple on same page, old tuple's t_ctid
    points to new tuple, lp_flags on old tuple becomes LP_REDIRECT (2)
    pointing to new tuple
  - Observe: NO new index entry created (HOT optimization). Index still
    points to old ctid, follows redirect to find new tuple
  - Update indexed column. Observe: NOT a HOT update. New tuple may go
    to different page. Index entry created for new ctid
  - Conditions for HOT: (1) no indexed column changed, (2) new tuple fits
    on same page (fillfactor determines available space)
  - HOT chain traversal: index → old ctid → redirect → new ctid. If
    multiple updates, chain follows through successive redirects
  - HOT pruning: when page is pruned (during normal operation or vacuum),
    dead intermediate tuples are removed, redirects updated

TASK 3.4: TOAST Discovery [CON] [OP]
  - Create table with TEXT column (default storage = EXTENDED)
  - Insert value exceeding ~2KB: observe it gets TOASTed
  - Find TOAST table: SELECT reltoastrelid::regclass FROM pg_class WHERE
    relname = 'your_table';
  - Inspect TOAST table structure: chunk_id (groups chunks for one value),
    chunk_seq (chunk order within value), chunk_data (actual bytes)
  - Understand TOAST strategies:
    PLAIN       — no TOAST, no compression. For types where storing inline
                  is critical (small types, fixed-length types)
    EXTENDED    — compress first (try to fit inline), then TOAST if still
                  too large (default for TEXT, BYTEA, JSONB, XML)
    EXTERNAL    — TOAST without compression. For values that are already
                  compressed (JPEG, PNG in bytea). Avoid double-compression
                  CPU waste
    MAIN        — compress first, only TOAST if absolutely necessary
  - Test: set column to EXTERNAL, insert large value, observe no compression
  - Test: set column to MAIN, insert value just over threshold, observe
    compression but still inline
  - Measure: pg_column_size() shows actual stored size on disk (including
    TOAST pointer size if TOASTed)
  - TOAST threshold: approximately 2KB (TOAST_TUPLE_THRESHOLD). Tuple
    must be small enough that at least 4 tuples fit in a page (8192/4=2048)

TASK 3.5: Free Space Map (FSM) and Visibility Map (VM) [CON] [OP]
  - Install pg_freespacemap extension
  - Query: SELECT * FROM pg_freespace('tablename'); — see free space per page
    (between lower and upper in that page)
  - Understand: FSM is a separate file (relfilenode_fsm) tracking approximate
    free space per page. VACUUM updates FSM after reclaiming dead tuple space.
    INSERT uses FSM to find pages with room (avoids scanning whole table)
  - Install pg_visibility extension
  - Query: SELECT * FROM pg_visibility_map('tablename', 0); — see visibility
    map for page 0
  - Understand: Visibility Map is a separate file (relfilenode_vm) with one
    bit per page. 1 = all tuples on this page are visible to all active
    transactions. VACUUM sets VM bits. UPDATE/DELETE clear VM bits (because
    they create tuples with uncommitted xmax)
  - Why VM matters for index-only scans: planner can skip heap access only
    if VM bit is 1 for every page containing needed tuples. If any VM bit
    is 0, must visit heap to check visibility

COMMON FAILURES FOR MODULE 3:
────────────────────────────────────────────────────────────────

FAILURE 3.F1: Page-Level Corruption
  Symptoms: "invalid page in block X of relation 'tablename'", "page
    verification failed, calculated checksum X but expected Y"
  Root causes: disk hardware returning corrupted data (bad blocks),
    filesystem bug (ext4 without barriers), RAM bit flip during write
    (non-ECC memory), LVM snapshot inconsistency, NFS silent corruption
  Diagnosis: pg_checksums --check (offline) or verify checksum error
    from log. Identify affected pages. Check dmesg for disk errors.
  Recovery: restore corrupted pages from backup (if PITR: point-in-time
    restore to before corruption). zero_damaged_pages=on as last resort
    (accept data loss on those pages). REINDEX if index page. If heap
    page: salvage what you can, restore corrupted rows from backup.

FAILURE 3.F2: TOAST Chunk Missing
  Symptoms: "missing chunk number X for toast value Y" when reading
    large value
  Root causes: TOAST table corruption, TOAST table rows deleted directly
    (someone did DELETE FROM pg_toast.pg_toast_XXXXX), CTID chain broken
  Diagnosis: query TOAST table for chunk_id with missing chunk, verify
    chunk_seq sequence has gaps
  Recovery: restore affected rows from backup. If the value is not
    critical, set column to NULL in affected rows. Prevent: never directly
    modify catalog or TOAST tables

FAILURE 3.F3: Bloat from Dead Tuples
  Symptoms: pg_stat_user_tables.n_dead_tup >> n_live_tup, table file
    size much larger than expected for row count, sequential scans slowing
  Root causes: heavy UPDATE/DELETE workload, vacuum not keeping up
    (cost settings too conservative, long transactions blocking vacuum,
    autovacuum disabled on table)
  Diagnosis: n_dead_tup/n_live_tup ratio, pgstattuple output (dead_tuple_percent,
    free_percent, dead_tuple_len), pg_stat_activity for blocking transactions
  Recovery: manual VACUUM (or VACUUM FULL for extreme cases), tune
    autovacuum for this table, partition table for faster vacuum

FAILURE 3.F4: FSM/VM Corruption
  Symptoms: FSM corruption → INSERT takes longer (scans for free page
    instead of using FSM). VM corruption → index-only scans unexpectedly
    hit heap (slower, but still correct results)
  Diagnosis: pg_freespacemap shows pages as full but pgstattuple shows
    free space, or vice versa. pg_visibility shows all-visible false but
    all tuples on page are frozen
  Recovery: VACUUM rebuilds both FSM and VM. No data loss.

FAILURE 3.F5: HOT Chain Too Long
  Symptoms: queries on frequently-updated tables slower than expected,
    pageinspect shows long chains of redirect line pointers
  Root causes: many HOT updates chained on same page without pruning,
    fillfactor too low (less space per page = more chain pages)
  Diagnosis: pageinspect on table pages, count redirect chain length
  Recovery: VACUUM or page prune shortens chains. Adjust fillfactor.

LAYER 2: CONNECTED (after Modules 4-5)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 3.X1: Dead Tuples → MVCC → Vacuum Chain
    - Complete trace: BEGIN → UPDATE → new tuple created (xmin=XID) →
      old tuple marked (xmax=XID) → COMMIT → vacuum scans page → sees
      old tuple with xmax committed → checks if any snapshot still needs
      this version → if no: marks line pointer unused, adds space to FSM,
      updates VM if page now all-visible → if yes: leaves tuple, waits
      for next vacuum pass
    - Understand: vacuum cannot reclaim a dead tuple if ANY active
      transaction's snapshot xmin <= the dead tuple's xmax

  CROSS-TOPIC TASK 3.X2: TOAST → Vacuum
    - TOAST tables accumulate dead tuples when large values are updated
    - Autovacuum processes TOAST tables as separate relations
    - Manual VACUUM on main table may not vacuum its TOAST table; must
      vacuum both or rely on autovacuum for TOAST
    - pg_stat_user_tables shows main table stats; TOAST table stats
      available via pg_stat_user_tables WHERE relname LIKE 'pg_toast%'

  CROSS-TOPIC TASK 3.X3: Fillfactor → Index → Write Performance
    - Fillfactor reserves space for HOT updates (UPDATE without index change)
    - Lower fillfactor = more page space reserved = HOT updates more likely
      to fit on same page = fewer index inserts = less index bloat
    - Trade-off: lower fillfactor = fewer rows per page = more pages =
      longer sequential scans = more buffer space needed
    - Optimal fillfactor depends on UPDATE frequency and whether updated
      columns are indexed

  COMBINED FAILURE 3.XF1: Bloat Spiral (dead tuples → vacuum blocked →
    query slowdown → more concurrent queries → vacuum more blocked)
    Scenario: moderate UPDATE load → dead tuples accumulate → autovacuum
      starts but gets throttled by cost_limit → long analytics query
      starts, holds snapshot → autovacuum can't clean dead tuples →
      table grows → queries scan more pages → queries take longer →
      more concurrent queries holding snapshots → dead tuples multiply
    Diagnosis: observe n_dead_tup trend (exponential growth), query
      latency trend (exponential growth), vacuum success rate (declining
      or zero), backend_xmin age for long queries
    Recovery: kill long query (breaks snapshot hold), temporarily increase
      autovacuum_vacuum_cost_limit, run manual VACUUM, analyze root cause
      of long query and tune or isolate

LAYER 3: DEEP (after Module 6)
────────────────────────────────────────────────────────────────

  TASK 3.D1: Page Internals Deep Dive [CON]
    - Page checksum algorithm: CRC-32C or FNV-1a (if compiled with
      --with-openssl). Checksum covers: page header (except lsn and
      checksum fields) + all data. Stored in page header, verified
      on every read if data_checksums=on
    - Page pruning: PostgreSQL prunes pages during normal operation
      (opportunistic pruning when accessing a page that has dead tuples).
      Removes dead HOT chains, updates redirects. Reduces vacuum work.
    - prune_xid header field: records last transaction that pruned this
      page. Helps determine when to prune again
    - PD_ALL_VISIBLE flag: set when all tuples on page are visible to all.
      This is the per-page equivalent of the visibility map bit. Must be
      consistent with VM or recovery will reset it

  TASK 3.D2: TOAST Internals [CON]
    - TOAST write path: value compressed (if EXTENDED/MAIN) → if
      compressed size <= 2KB, store inline → if still too large,
      split into ~2KB chunks → store chunk_id (assigned per TOASTed
      value), chunk_seq (0,1,2,...), chunk_data → store TOAST pointer
      in main table (chunk_id + toast table OID)
    - TOAST read path: read main tuple → detect TOAST pointer (varlena
      header indicates TOAST) → query TOAST table for all chunks with
      matching chunk_id ORDER BY chunk_seq → reassemble → decompress
      (if EXTENDED/MAIN and was compressed) → return
    - TOAST and UPDATE: if updated columns don't include TOASTed column,
      TOAST data is NOT duplicated (new tuple reuses same TOAST pointer).
      If TOASTed column IS updated, new TOAST data created (old TOAST
      data becomes dead, eventually vacuumed)

  TASK 3.D3: Storage Parameter Tuning [DES]
    - fillfactor: for tables, controls % of page filled on INSERT/COPY.
      (100% = full, 70% = 30% free space reserved for UPDATE). For
      indexes, fillfactor applies to leaf pages only during index build
    - toast_tuple_target: minimum tuple length before TOAST is considered
      (default ~2KB). Increase to allow larger inline values (faster
      access, but wider table pages)
    - autovacuum storage parameters per table: autovacuum_vacuum_threshold,
      autovacuum_vacuum_scale_factor, autovacuum_vacuum_cost_delay,
      autovacuum_vacuum_cost_limit, autovacuum_freeze_min_age,
      autovacuum_freeze_max_age, autovacuum_freeze_table_age,
      log_autovacuum_min_duration, toast.autovacuum_* (PG17+)

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 3:
    - FSM file corruption: wrong free space information. INSERT performance
      degrades (slower page selection). Recovery: VACUUM FULL rebuilds FSM
    - VM file corruption: incorrect visibility map. Index-only scans may
      incorrectly skip heap access → wrong query results! Recovery: VACUUM
      rebuilds VM. Very rare, usually accompanied by heap corruption
    - Tuple header corruption: infomask bits wrong → tuple visibility
      incorrect → queries return wrong results or miss rows. Recovery:
      restore from backup, pg_resetwal as last resort
    - TOAST compression corruption: decompression of TOASTed value fails.
      Recovery: restore row from backup, or accept NULL
    - Partial write corruption: power loss during page write → half-written
      page with incomplete tuple. Checksum catches this. Recovery: WAL
      replay during crash recovery replaces page, or restore from backup
    - Truncated relation file: file shorter than expected page count.
      Recovery: restore from backup
    - Wrong page size binary: PostgreSQL binary compiled with different
      BLCKSZ than existing data directory → cannot start. Recovery: use
      correct BLCKSZ binary or re-initdb

================================================================================
MODULE 4: MVCC & TRANSACTION ISOLATION
================================================================================
PREREQUISITES: Module 3
PURPOSE: MVCC is the heart of concurrency. Every isolation decision, vacuum
  urgency, and performance behavior under load ties back to MVCC.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 4.1: Transaction ID Fundamentals [CON]
  - XID is 32-bit unsigned (0 to 4,294,967,295). Three special values:
    0 = InvalidTransactionId (no transaction)
    1 = BootstrapTransactionId (initdb catalog setup)
    2 = FrozenTransactionId (frozen tuple, unconditionally visible)
    Regular XIDs start at 3, increment by 1 each transaction
  - Wraparound: at ~2 billion XIDs from current, comparison flips.
    PostgreSQL uses modulo-2^31 arithmetic for XID comparison:
    XID A is "in the past" of XID B if (int32)(A - B) < 0
    Thus the "horizon" is about 2.1 billion XIDs ahead and behind
  - Retrieving: SELECT txid_current() (or pg_current_xact_id())
    gives current transaction's XID. Each command that modifies data
    gets its own XID if not already assigned to a transaction

TASK 4.2: Transaction Snapshots [CON] [OP]
  - Snapshot structure:
    xmin: lowest XID among all active transactions at snapshot time.
          All XIDs < xmin are committed and visible
    xmax: first unassigned XID at snapshot time. All XIDs >= xmax
          are in the future and not visible
    xip_list: list of XIDs that are active (in progress) at snapshot time.
              These are neither committed nor aborted yet, so their tuples
              must be checked for commit status
  - When snapshots are taken:
    READ COMMITTED: new snapshot for each statement in the transaction
    REPEATABLE READ: single snapshot at first statement, reused for all
      subsequent statements
    SERIALIZABLE: single snapshot like REPEATABLE READ, plus predicate
      locking for conflict detection
  - Demonstrate snapshot behavior with two concurrent transactions:
    T1 starts → T2 starts → T2 inserts and commits → T1 SELECTs
    READ COMMITTED T1: sees T2's committed insert (new snapshot)
    REPEATABLE READ T1: does NOT see T2's commit (still uses old snapshot)

TASK 4.3: Visibility Check Algorithm [CON]
  - Full visibility test for a tuple:
    1. If tuple's xmin is current transaction (taken from snapshot
       composition info): visible if this is not a delete (xmax=0 or
       xmax=self and this is part of update chain)
    2. If xmin is committed (check CLOG) AND xmin < snapshot.xmax
       AND xmin not in snapshot.xip_list:
       a. If xmax is 0 or InvalidTransactionId: visible
       b. If xmax is current transaction: NOT visible (we deleted it)
       c. If xmax is committed: NOT visible if xmax committed before
          snapshot (xmax < xmax_threshold and not in xip_list)
       d. If xmax is aborted: visible (deleter rolled back)
    3. If xmin is aborted: NOT visible (creator rolled back)
    4. If xmin is in progress (in xip_list): NOT visible (not committed yet)
    5. If xmin is FrozenTransactionId: unconditionally visible (skip steps 1-4)
  - Hint bits optimization: HEAP_XMIN_COMMITTED and HEAP_XMAX_COMMITTED
    avoid consulting CLOG on repeated tuple accesses. Set by first reader
    that verifies commit status (called "hint bit setting" or "setting
    commit status bits")

TASK 4.4: Isolation Levels in Practice [CON] [OP]
  - READ COMMITTED:
    - Anomaly allowed: non-repeatable read (same query in same transaction
      returns different rows because another transaction committed changes)
    - Anomaly allowed: phantom read (same query returns new/different rows
      because another transaction inserted matching rows)
    - When to use: most OLTP workloads, where seeing committed data of
      other transactions is acceptable or desired
  - REPEATABLE READ:
    - Difference from standard SQL: PostgreSQL REPEATABLE READ prevents
      phantom reads (due to snapshot isolation). Standard SQL allows
      phantoms in REPEATABLE READ
    - Anomaly allowed: serialization anomaly/write skew (two concurrent
      transactions each read overlapping data and update based on what
      they read, producing a state that couldn't occur in any serial order)
    - When to use: reports that need consistent view of data, backup dumps
  - SERIALIZABLE:
    - Uses Serializable Snapshot Isolation (SSI), not traditional locking
    - Detects dangerous patterns (rw-dependency cycles) and aborts one
      transaction with serialization failure
    - When to use: financial transactions, any scenario where write skew
      would cause data integrity violation
    - Cost: higher abort rate, application must implement retry logic

TASK 4.5: Monitoring MVCC Health [OP] [DIAG]
  - pg_stat_activity.backend_xid: this session has an active transaction
    with a real XID. NULL means idle or only-read transaction (no XID
    assigned). Holding an XID is not itself harmful but indicates
    potential for holding locks
  - pg_stat_activity.backend_xmin: the oldest XID this session's snapshot
    can see. This is the CRITICAL field for vacuum blockage. If any
    session has old backend_xmin, vacuum cannot remove dead tuples with
    xmax newer than that value. Long-running SELECTs in REPEATABLE READ
    or SERIALIZABLE hold their snapshot's xmin
  - age(XID): SELECT age(backend_xmin) shows how old the held snapshot is.
    More than a few hours requires investigation
  - Long-running transaction detection: find PIDs with old xact_start or
    old backend_xmin. Understand difference: xact_start old but backend_xmin
    NULL = idle session with no transaction = harmless. xact_start old AND
    backend_xmin old = transaction holding back vacuum = dangerous

COMMON FAILURES FOR MODULE 4:
────────────────────────────────────────────────────────────────

FAILURE 4.F1: Long-Running Transaction Blocks Vacuum → Bloat
  Symptoms: n_dead_tup climbing on tables, last_autovacuum old despite
    autovacuum running, table file size growing, queries slowing
  Root cause: a session with old backend_xmin holds a snapshot from long ago.
    Common causes: forgotten psql session with BEGIN, application bug
    leaving transaction open, analytics query running for hours,
    pg_dump (takes snapshot for consistency), replication slot with
    hot_standby_feedback
  Diagnosis: SELECT pid, age(backend_xmin), query FROM pg_stat_activity
    WHERE backend_xmin IS NOT NULL ORDER BY age(backend_xmin) DESC;
    Identify the oldest snapshot holder. Check what they're doing.
  Recovery: terminate the blocking session (pg_terminate_backend(pid))
    if safe. Manual VACUUM on affected tables after blockage removed.
    Prevention: set idle_in_transaction_session_timeout,
    statement_timeout for long queries

FAILURE 4.F2: Transaction ID Wraparound Danger
  Symptoms: WARNING message in logs: "database 'X' must be vacuumed
    within N transactions". age(datfrozenxid) approaching 1.5-2 billion.
    For tables: age(relfrozenxid) > 1 billion
  Root cause: autovacuum disabled or too slow, freezing not happening.
    Common causes: autovacuum=off, autovacuum_freeze_max_age set too
    high, vacuum cost settings too conservative for write rate,
    vacuum blocked by long transactions
  Diagnosis: SELECT datname, age(datfrozenxid) FROM pg_database;
    For specific tables: SELECT relname, age(relfrozenxid) FROM
    pg_class WHERE relkind='r' ORDER BY age(relfrozenxid) DESC;
  Recovery: If still running: aggressively VACUUM FREEZE the oldest
    tables. May need to terminate blocking transactions first.
    If shutdown already occurred: start in single-user mode,
    VACUUM FREEZE pg_database and critical tables, restart normally.
    Prevention: aggressive autovacuum_freeze_max_age (100M-400M),
    monitor age() across all tables, regular VACUUM FREEZE during
    maintenance windows for append-only tables

FAILURE 4.F3: Serialization Failures Under Concurrent Load
  Symptoms: "ERROR: could not serialize access due to
    read/write dependencies among transactions" from application
  Root cause: SERIALIZABLE isolation level, concurrent transactions
    reading overlapping data and writing based on those reads
  Diagnosis: pg_stat_database.conflicts counter increase rate.
    Identify conflicting query patterns from application logs
  Recovery: Application must implement retry logic (repeat entire
    transaction on serialization failure). Reduce transaction scope
    (shorter transactions = fewer conflicts). Consider if REPEATABLE
    READ with explicit locking is sufficient

FAILURE 4.F4: Orphaned Prepared Transaction
  Symptoms: pg_prepared_xacts shows entries for hours/days.
    These hold locks and XIDs indefinitely
  Root cause: two-phase commit started (PREPARE TRANSACTION) but
    COMMIT PREPARED never called. Application or coordinator crashed
    after prepare but before commit
  Diagnosis: SELECT * FROM pg_prepared_xacts; check prepared timestamp
  Recovery: if coordinator is permanently gone: ROLLBACK PREPARED
    (data loss for that transaction) or COMMIT PREPARED (if certain
    it should be committed). Never leave prepared transactions
    orphaned; they block vacuum and hold locks

LAYER 2: CONNECTED (after Module 5)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 4.X1: MVCC → Vacuum → Bloat — Complete Relationship
    - Full chain: Transaction creates dead tuple (UPDATE/DELETE).
      Dead tuple has xmax = transaction XID. If xmax is older than
      ALL current snapshots' xmin, vacuum can reclaim it. Otherwise,
      dead tuple must stay until oldest snapshot moves forward.
    - Formula: A dead tuple is removable when (xmax < all backend_xmin
      values across cluster OR xmax is frozen)
    - Monitoring: Check oldest backend_xmin vs n_dead_tup creation rate.
      If oldest snapshot is 1 hour old and dead tuples created at
      1000/sec, 3.6M dead tuples cannot be cleaned = guaranteed bloat

  CROSS-TOPIC TASK 4.X2: MVCC → Indexes
    - Indexes also store ctid (page, offset). When tuple moves (UPDATE),
      index must be updated unless HOT
    - Dead index entries: index entries pointing to dead heap tuples.
      Vacuum removes these during index vacuum phase
    - Index bloat: if vacuum doesn't run, indexes also bloat with dead
      entries. Same snapshot-based reclaim rules apply
    - Many indexes = vacuum must scan them all = vacuum takes longer =
      more window for new dead tuples to accumulate

  CROSS-TOPIC TASK 4.X3: MVCC → Replication (Hot Standby Feedback)
    - On standby: queries run in read-only mode, hold snapshots
    - hot_standby_feedback = on: standby sends its oldest xmin to primary
    - Primary sees standby's xmin as a "virtual" snapshot holder
    - Vacuum on primary cannot remove dead tuples if standby query needs them
    - Trade-off: data consistency on standby vs bloat on primary
    - Recovery conflict: if vacuum on primary removes tuples that standby
      query needs (because hot_standby_feedback = off or lagged),
      standby query gets cancelled: "canceling statement due to
      conflict with recovery"

  COMBINED FAILURE 4.XF1: Standby Report → Hot Standby Feedback → Primary Bloat
    - Long report runs on standby (hours). hot_standby_feedback=on
    - Standby sends its xmin to primary. Primary's vacuum sees this as
      oldest snapshot holder
    - Primary accumulates dead tuples because vacuum cannot clean
    - Primary table bloats despite normal autovacuum operations
    - Diagnosis: On primary: check pg_stat_replication for
      backend_xmin from standby connections. Compare with pg_stat_activity
      backend_xmin. Identify standby as the blocker
    - Recovery: set max_standby_streaming_delay on standby, or terminate
      the long query on standby, or temporarily set hot_standby_feedback=off

LAYER 3: DEEP (after Module 9)
────────────────────────────────────────────────────────────────

  TASK 4.D1: Serializable Snapshot Isolation Internals [CON]
    - SSI tracks SIREAD locks (read dependencies). Not in pg_locks;
      maintained in RAM only for SERIALIZABLE transactions
    - Two types of dangerous structures:
      rw-dependency: T1 reads data, T2 writes to that data → T2 depends
        on T1 not having read stale data
      wr-dependency: T1 writes data, T2 reads that data → T2 depends
        on T1's write
    - When SSI detects a cycle of dependencies where at least two are
      rw-dependencies and the transactions are concurrent, it rolls back
      one transaction
    - Write skew example: two doctors checking on-call status. Both read
      "at least one doctor on call" (true, 2 doctors). Both update their
      own status to "off call". End result: 0 doctors on call. REPEATABLE
      READ allows this. SERIALIZABLE detects the conflicting reads → one
      transaction gets serialization error

  TASK 4.D2: XID Wraparound Mechanics [CON]
    - Frozen tuples: have xmin=2 (FrozenTransactionId). Any XID comparison
      sees FrozenTransactionId as "in the past" of all real XIDs. This
      means frozen tuples are always visible without XID arithmetic
    - Freeze process: VACUUM (or autovacuum) marks tuples with old enough
      xmin as frozen. Threshold: age(xmin) > vacuum_freeze_min_age
      (default 50M). Anti-wraparound vacuum triggers when
      age(relfrozenxid) > autovacuum_freeze_max_age (default 200M)
    - Anti-wraparound vacuum differences: skips index vacuum (to be
      faster), uses all available autovacuum workers, ignores
      autovacuum_vacuum_cost_limit (runs at full speed)
    - Why 2 billion, not 4 billion: comparison modulo 2^31 means XIDs
      more than 2^31 (2.1B) apart look "in the past" of each other.
      Safety margin: freeze well before 2B
    - Database shutdown at 2B: PostgreSQL refuses to start. Requires
      single-user mode to VACUUM FREEZE. If that fails: pg_resetwal
      -f resets XID counter but loses all data (effectively re-inits)

  TASK 4.D3: CLOG (Commit Log) and Transaction Status [CON]
    - pg_xact/ (formerly pg_clog): stores commit status for each
      transaction. 2 bits per XID: 00=in-progress, 01=committed,
      10=aborted, 11=subcommitted
    - CLOG lookup: when checking if xmin committed, PostgreSQL first
      checks hint bits (HEAP_XMIN_COMMITTED). If hint bit not set,
      reads CLOG. If committed, sets hint bit
    - CLOG aging: CLOG pages for old XIDs can be truncated once all
      transactions that could see those XIDs are gone (after freeze)
    - CLOG corruption: "could not access status of transaction" error.
      Recovery: restore CLOG files from backup, or pg_resetwal (data loss)

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 4:
    - Subtransaction overflow: too many subtransactions within one
      transaction (64KB limit per backend). pg_subtrans directory
      grows. Risk: performance degradation, backend crash
    - Multixact wraparound: similar to XID wraparound but for
      multixact IDs (shared row locks). Monitor age(relminmxid)
    - CLOG file deleted: transaction status unknown for range of
      XIDs. Database may refuse to start. Recovery from backup CLOG
    - Prepared transaction blocks vacuum for days: orphaned two-phase
      commit holds locks and XID. Must manually COMMIT or ROLLBACK
    - Deferrable unique constraint relies on MVCC snapshot: two
      concurrent inserts of same value, both see no conflict, both
      commit → duplicate in unique column. Solution: use SERIALIZABLE
      or explicit locking

================================================================================
MODULE 5: VACUUM & AUTOVACUUM
================================================================================
PREREQUISITES: Module 4
PURPOSE: VACUUM is PostgreSQL's garbage collector. Mastery of vacuum is
  the single most important operational skill for a PostgreSQL DBA.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 5.1: Manual VACUUM Operations [OP] [CON]
  - Plain VACUUM: scans table for dead tuples, reclaims space within pages,
    updates FSM and VM. Does NOT return space to OS (file size unchanged).
    Does NOT block reads/writes (ShareUpdateExclusiveLock). Can run
    concurrently with normal operations
  - VACUUM FULL: rewrites entire table to new file (no dead tuples, optimal
    layout, minimum size). Takes AccessExclusiveLock — blocks ALL access.
    Returns space to OS. Use only during maintenance windows or on tables
    that can be briefly locked. For large tables, pg_repack is preferred
  - VACUUM ANALYZE: vacuum + update statistics in one command. Useful after
    bulk deletes where both dead tuple cleanup and fresh statistics needed
  - VACUUM FREEZE: marks old tuples as frozen regardless of
    vacuum_freeze_min_age. Anti-wraparound tool
  - VACUUM (options): VACUUM (VERBOSE, ANALYZE, FREEZE, INDEX_CLEANUP on|off,
    TRUNCATE on|off, PARALLEL N, SKIP_LOCKED, PROCESS_TOAST on|off)
  - Understand when to use each variant and the operational impact

TASK 5.2: Autovacuum Configuration [DES] [OP]
  - Core parameters:
    autovacuum = on (governing switch)
    autovacuum_max_workers = 3 (default, increase for many tables)
    autovacuum_naptime = 60s (sleep between checking for tables needing vacuum)
    autovacuum_vacuum_threshold = 50 (base dead tuple count before vacuum)
    autovacuum_vacuum_scale_factor = 0.2 (fraction of table size added to
      threshold: threshold + scale_factor × n_live_tup)
    autovacuum_analyze_threshold = 50 (same for ANALYZE)
    autovacuum_analyze_scale_factor = 0.1
    autovacuum_vacuum_cost_limit = 200 (total vacuum cost limit across all
      workers — key performance parameter)
    autovacuum_vacuum_cost_delay = 2ms (sleep when cost limit exceeded)
    autovacuum_freeze_max_age = 200000000 (anti-wraparound trigger)
    autovacuum_multixact_freeze_max_age = 400000000
    autovacuum_work_mem = -1 (uses maintenance_work_mem; separate in PG17+)
  - Understand the trigger formula: vacuum triggers when
    n_dead_tup > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor
    × n_live_tup. For a 100M-row table with default (0.2): 50 + 20M = 20M
    dead tuples needed to trigger vacuum. That's 20% bloat before vacuum runs
  - Modern recommendation for large tables: set scale_factor very low
    (0.01 or 0.001) or use threshold-based approach with high threshold

TASK 5.3: Autovacuum Monitoring [MON] [DIAG]
  - pg_stat_user_tables: n_dead_tup (current estimate), n_live_tup, n_tup_del,
    n_tup_upd, last_autovacuum, last_autoanalyze, autovacuum_count
  - pg_stat_progress_vacuum: shows active vacuum operations with phases:
    initializing, scanning heap, vacuuming indexes, vacuuming heap,
    cleaning up indexes, truncating heap, performing final cleanup
  - pg_stat_activity: filter backend_type = 'autovacuum worker'.
    Check wait_event_type and wait_event to see if worker is blocked
  - Key metrics to monitor: dead tuple ratio (n_dead_tup/n_live_tup),
    age of last autovacuum (now() - last_autovacuum), wraparound age
    (age(relfrozenxid)), autovacuum worker count vs max_workers,
    tables with autovacuum_count = 0

TASK 5.4: Vacuum Blockage Detection and Resolution [DIAG] [REC]
  - Find PID blocking vacuum: pg_stat_activity with oldest backend_xmin
  - Find autovacuum worker waiting: pg_stat_activity with
    backend_type='autovacuum worker' and wait_event_type='Lock'
  - Understand what can block vacuum: long-running transactions
    (especially REPEATABLE READ or SERIALIZABLE), orphaned prepared
    transactions, stale replication slots with hot_standby_feedback,
    exclusive locks on the table (DDL running, REFRESH MATERIALIZED VIEW)
  - Recovery: terminate blocking transaction, drop orphaned prepared
    transaction, drop stale replication slot, wait for DDL to complete

COMMON FAILURES FOR MODULE 5:
────────────────────────────────────────────────────────────────

FAILURE 5.F1: Bloat Spiral
  Symptoms: Table size growing faster than expected from data growth,
    queries scanning more pages, I/O increasing, application latency
    rising week over week
  Root cause: dead tuple creation rate exceeds vacuum's removal rate.
    Common causes: autovacuum cost_limit too low (vacuum throttled),
    long transactions blocking vacuum, autovacuum disabled on specific
    tables, maintenance_work_mem too small causing many index passes
  Diagnosis: Compare n_dead_tup trend (should be steady or oscillating;
    if monotonically increasing = problem). Check autovacuum_count
    per table (should be incrementing). Check last_autovacuum (should
    be recent). pgstattuple to confirm actual bloat percentage
  Recovery: Short-term: manual VACUUM on bloated tables (or VACUUM
    FULL for critical bloat > 50% if downtime acceptable). Medium-term:
    increase autovacuum_vacuum_cost_limit, tune per-table autovacuum
    settings, increase maintenance_work_mem. Long-term: partition
    large tables, address write patterns generating excess dead tuples

FAILURE 5.F2: Autovacuum Never Runs
  Symptoms: last_autovacuum IS NULL for many tables, n_dead_tup
    accumulating, autovacuum_count = 0 for cluster
  Root cause: autovacuum = off in postgresql.conf, or
    autovacuum_max_workers = 0, or autovacuum = off on specific
    tables (ALTER TABLE ... SET (autovacuum_enabled = false))
  Diagnosis: SHOW autovacuum; check pg_stat_activity for autovacuum
    workers. Check pg_class.reloptions for per-table overrides
  Recovery: Set autovacuum = on globally or per-table. Manual VACUUM
    on all tables immediately

FAILURE 5.F3: Anti-Wraparound Vacuum Storm
  Symptoms: High I/O utilization, many autovacuum workers active,
    queries slowing, database approaching or passing
    autovacuum_freeze_max_age for many tables
  Root cause: Freezing deferred too long (autovacuum_freeze_max_age
    too high, or vacuum blocked/disabled). When threshold hit, all
    affected tables trigger aggressive anti-wraparound vacuum
    simultaneously
  Diagnosis: age(relfrozenxid) shows values near 200M.
    pg_stat_progress_vacuum shows many vacuums in progress.
    Checkpoint frequency increases due to vacuum's WAL generation
  Recovery: Let it complete (may take hours/days). Prevent recurrence:
    lower autovacuum_freeze_max_age (100M-150M), stagger vacuum windows
    per table with per-table freeze age settings, run manual VACUUM
    FREEZE on oldest tables during low-traffic periods to prevent
    all tables hitting threshold simultaneously

FAILURE 5.F4: VACUUM FULL During Peak Hours
  Symptoms: Table locked, all queries on that table pile up in
    pg_stat_activity with wait_event_type='Lock', wait_event='relation'
  Root cause: Someone ran VACUUM FULL or CLUSTER on a busy table
    without checking for AccessExclusiveLock impact
  Diagnosis: pg_stat_activity shows process with query containing
    VACUUM FULL or CLUSTER, holding AccessExclusiveLock
  Recovery: VACUUM FULL cannot be safely cancelled mid-operation.
    Must wait. Monitor pg_stat_progress_cluster for progress.
    Prevention: Never run VACUUM FULL without maintenance window
    approval. Use pg_repack for online table rebuild

FAILURE 5.F5: Vacuum Not Reclaiming Despite Running
  Symptoms: autovacuum_count incrementing, last_autovacuum current,
    but n_dead_tup not decreasing
  Root causes: (1) Long-running transaction(s) holding old snapshot.
    (2) Replication slot with hot_standby_feedback. (3) Orphaned
    prepared transaction. (4) maintenance_work_mem too small →
    vacuum makes many passes over indexes, each pass interrupted
    by cost_limit sleep, dead tuples created faster than removed
  Diagnosis: Check for old backend_xmin. Check pg_replication_slots
    with active_pid NULL but slot retained. Check pg_prepared_xacts.
    Check if n_dead_tup decreasing slowly (indicates vacuum working
    but throttled) vs not decreasing at all (indicates snapshot block)
  Recovery: Remove the blocker (terminate long transaction, drop slot,
    resolve prepared transaction). Tune cost settings for faster vacuum

LAYER 2: CONNECTED (after Modules 6-7)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 5.X1: Vacuum → WAL
    - Every vacuum operation writes WAL: heap modifications, index
      modifications, page truncation
    - Anti-wraparound vacuum generates more WAL than regular vacuum
      (freezing each tuple requires WAL record)
    - Vacuum's WAL generation contributes to max_wal_size consumption
    - During heavy vacuum, checkpoint frequency may increase →
      checkpoint I/O compounds with vacuum I/O
    - Strategy: increase max_wal_size to absorb vacuum's WAL burst
    - Monitoring: pg_stat_progress_vacuum shows phases; during index
      vacuum phase, WAL generation peaks

  CROSS-TOPIC TASK 5.X2: Vacuum → Indexes
    - Index vacuum phase: vacuum must find and remove all index entries
      pointing to dead heap tuples
    - Each index on the table must be scanned (full index scan per pass)
    - maintenance_work_mem stores array of dead tuple IDs. Larger =
      more dead TIDs per pass = fewer passes over each index. Small
      maintenance_work_mem on a table with 10 indexes = 10 full index
      scans × number of passes (could be 50+ passes)
    - vacuum_index_cleanup option: set OFF for insert-only tables
      (no dead index entries exist)
    - Index-only scan impact: vacuum updates VM which enables index-only
      scans. Stale VM = index-only scans revert to heap access

  CROSS-TOPIC TASK 5.X3: Vacuum → Partitioning
    - Vacuum runs per partition, not on parent table
    - Huge advantage: vacuum one partition at a time avoids hours-long
      vacuum on massive table
    - Partition elimination by age: detach old partitions → archive
      or drop → no vacuum needed
    - Partitioned table with 100 partitions: each partition gets
      vacuumed independently → 100 small vacuums instead of 1 huge one

  COMBINED FAILURE 5.XF1: High Write + Many Indexes + Conservative Cost Limit
    - Table: 500GB, 15 indexes, 10K UPDATEs/second
    - autovacuum_vacuum_scale_factor=0.2 → triggers at 20% dead tuples
      (100GB of dead space)
    - autovacuum_vacuum_cost_limit=200 → heavily throttled
    - Vacuum starts → processes few pages → hits cost limit → sleeps
      2ms → new dead tuples created during sleep → vacuum never catches up
    - maintenance_work_mem=64MB → needs 50+ passes over 15 indexes
    - Diagnosis: n_dead_tup consistently rising, autovacuum running
      (visible in pg_stat_progress_vacuum) but never completing,
      cost limit reached quickly
    - Recovery: increase autovacuum_vacuum_cost_limit to 2000+,
      increase maintenance_work_mem to 1GB+, set per-table
      autovacuum_vacuum_scale_factor=0.01 to trigger earlier,
      consider reducing index count

LAYER 3: DEEP (after Module 11)
────────────────────────────────────────────────────────────────

  TASK 5.D1: Vacuum Phase Internals [CON]
    Phase 1 — Scanning Heap: sequential scan of table, identifies dead
      tuples, stores their TIDs in maintenance_work_mem array. If
      maintenance_work_mem fills before scan completes → moves to index
      vacuum with partial TID list → returns to heap scan for more
    Phase 2 — Vacuuming Indexes: for each index, scan index pages
      looking for entries that match dead TIDs, remove them. This
      phase is repeated for each batch of TIDs (if maintenance_work_mem
      couldn't hold all TIDs from full heap scan)
    Phase 3 — Vacuuming Heap: re-scan heap pages containing dead tuples,
      physically remove dead tuples, compact page, update line pointers
    Phase 4 — Cleaning Up Indexes: vacuum had set dead index entries as
      "dead" in phase 2; now reclaim that space in indexes
    Phase 5 — Truncating Heap: if last pages are empty, truncate file
    Phase 6 — Performing Final Cleanup: update FSM, update VM, update
      statistics (if ANALYZE), truncate indexes if applicable

  TASK 5.D2: Vacuum Cost System Deep Dive [CON] [DES]
    - Cost parameters and their default values:
      vacuum_cost_page_hit = 1 (page found in shared_buffers)
      vacuum_cost_page_miss = 2 (page read from disk)
      vacuum_cost_page_dirty = 20 (page dirtied — written to)
    - Cost accumulation: scanner accumulates costs as it processes pages.
      When accumulated cost >= autovacuum_vacuum_cost_limit, scanner
      sleeps for autovacuum_vacuum_cost_delay milliseconds
    - Effective throughput calculation: if cost_limit = 200, and average
      cost per page = 10 (mix of hits/misses/dirty), vacuum processes
      20 pages, then sleeps 2ms. 20 pages/burst × (1000ms/2ms) = 10000
      pages/second = 80MB/s at 8KB pages
    - Tuning for modern storage (NVMe): set autovacuum_vacuum_cost_delay=0
      to disable throttling entirely. Or increase cost_limit to 2000+.
      Modern storage can handle vacuum I/O without impacting queries

  TASK 5.D3: Emergency Vacuum Procedures [REC]
    - Transaction wraparound shutdown:
      1. Start PostgreSQL in single-user mode
      2. VACUUM (FREEZE) on the most critical catalogs
      3. Restart normally
      4. VACUUM FREEZE all remaining tables
    - Table with >90% bloat:
      Option A: VACUUM FULL — fastest table reclaim, but blocks table.
        Schedule downtime, execute, monitor with pg_stat_progress_cluster
      Option B: pg_repack — creates new table, copies data, swaps. No
        long lock. Requires: free disk space for new table copy, primary
        key or unique index, no DDL during repack
      Option C: Partition swap — create new partition, move data with
        INSERT INTO new ... SELECT FROM old (batch), swap partition
        names, drop old. Zero downtime, complex orchestration
    - pg_repack operation details: creates shadow table with new layout,
      copies rows in batches, creates indexes, sets up trigger to capture
      concurrent changes, applies changes during swap lock window
      (very short AccessExclusiveLock), swaps filenode, drops old table

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 5:
    - Autovacuum worker stuck on corrupted page (keeps retrying, never
      progressing): diagnosis via pg_stat_progress_vacuum (stuck at
      same heap_blks_vacuumed), recovery via zero_damaged_pages on that
      page or restore from backup
    - maintenance_work_mem causing 50+ index passes on large table with
      many indexes: diagnosis via phase transitions in vacuum log (log
      messages for each index vacuum batch), recovery via increase
      maintenance_work_mem and/or reduce index count
    - Vacuum truncation blocked by standby query (AccessExclusiveLock
      for truncation conflicts with standby's AccessShareLock):
      diagnosis via pg_stat_activity on standby (query on truncated
      table), recovery via terminate standby query or skip truncation
      with VACUUM (TRUNCATE OFF)
    - pg_repack failure mid-operation leaving orphaned objects: diagnosis
      via pg_class for tables with names like 'repack_*', recovery via
      DROP TABLE on orphaned repack tables and triggers
    - Vacuum on pg_attribute or pg_statistic (catalog tables): special
      care needed. Catalog tables are small but critical. Vacuum on
      them takes AccessShareLock (not blocking). But VACUUM FULL is
      catastrophic (AEL, blocks entire cluster)
    - Per-table autovacuum overrides not working: check if
      toast.autovacuum_* also needs setting (TOAST table is separate
      relation with separate autovacuum triggers)

MODULE 6: WAL, CHECKPOINTS & CRASH RECOVERY
================================================================================
PREREQUISITES: Module 5
PURPOSE: WAL is PostgreSQL's durability mechanism. Every write is WAL-logged
  before it becomes visible. Checkpoint management determines recovery time
  and write I/O patterns.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 6.1: WAL Fundamentals [CON] [OP]
  - Understand the Write-Ahead Logging principle: every change to data files
    must be recorded in WAL before the data file is modified. This ensures
    crash recovery can reconstruct any partially-applied changes
  - Learn WAL segment file naming: 24-character hexadecimal, first 8 chars =
    timeline ID, next 8 chars = logical segment number, last 8 chars = block
    within segment. Example: 0000000100000001000000AB
  - Learn WAL segment size: 16MB default (configured at initdb, cannot change
    after). Larger segments = fewer file switches (better for high-write),
    fewer files in archive. Smaller = more switches, smaller archive files
  - Learn LSN (Log Sequence Number): unique position in WAL stream.
    Format: segment/offset (hex/hex). Example: 1/AB123456. Monotonically
    increasing. Use pg_current_wal_lsn() to see current write position
  - Use pg_wal_lsn_diff(lsn1, lsn2) to calculate bytes between two LSNs
  - Understand wal_level parameter: minimal (no replication), replica
    (streaming replication + WAL archiving), logical (everything in replica
    + logical decoding). Cannot reduce wal_level without restart. Increasing
    requires restart if currently minimal
  - Understand WAL segment lifecycle: created in pg_wal → filled by walwriter →
    archived by archive_command (if archive_mode=on) → recycled (renamed to
    future segment) or deleted

TASK 6.2: WAL Writer Process [CON]
  - walwriter process: periodically flushes WAL from wal_buffers (shared memory)
    to WAL segment files on disk
  - wal_writer_delay: time between automatic WAL flushes (default 200ms).
    At COMMIT, WAL is flushed immediately regardless of this setting
    (unless synchronous_commit is off)
  - wal_writer_flush_after: WAL writer flushes after accumulating this many
    WAL bytes, even before delay expires (default 1MB)
  - Understand group commit: multiple transactions committing near-simultaneously
    have their WAL records flushed together in one fsync. Reduces I/O
  - commit_delay: artificial delay before WAL flush to allow more transactions
    to join group commit (default 0 = disabled). Only useful for extremely
    high commit rates (thousands per second)
  - commit_siblings: minimum number of concurrent active transactions before
    commit_delay is applied (default 5). Prevents penalizing low-concurrency
    workloads

TASK 6.3: Checkpoint Mechanics [CON] [OP]
  - Checkpoint purpose: flush all dirty shared_buffers to data files on disk.
    After checkpoint completes, all changes up to the checkpoint LSN are
    guaranteed to be in data files. Crash recovery only needs to replay WAL
    from the checkpoint's REDO point
  - Checkpointer process: dedicated process that orchestrates checkpoints.
    Spreads writes over time (not all at once) to avoid I/O storm
  - checkpoint_timeout: maximum time between automatic checkpoints (default 5min).
    PostgreSQL starts a checkpoint either when timeout expires OR when
    max_wal_size WAL has been generated since last checkpoint, whichever
    comes first
  - max_wal_size: soft limit on total WAL size. When accumulated WAL exceeds
    this, checkpoint is forced (checkpoints_req). Default 1GB, typically
    too small for production
  - min_wal_size: minimum WAL to retain for recycling. WAL below this is kept
    for future use (recycled) rather than deleted
  - checkpoint_completion_target: fraction of checkpoint_timeout spent
    actively writing. Default 0.9 means checkpoint spreads writes over
    90% of checkpoint_timeout, leaving 10% buffer. Higher = more spread,
    lower = faster checkpoint (more I/O concentration)
  - Monitor pg_stat_bgwriter: checkpoints_timed (scheduled by timeout),
    checkpoints_req (forced by max_wal_size). Ratio: if checkpoints_req
    dominates, max_wal_size is too low

TASK 6.4: Crash Recovery Process [CON] [OP]
  - On crash: PostgreSQL reads last checkpoint record from pg_control to find
    the REDO point (WAL LSN where recovery must start)
  - Recovery replays WAL from REDO point forward: reads each WAL record, applies
    changes to data files (heap pages, indexes, etc.)
  - full_page_writes: first write to a page after checkpoint writes entire
    8KB page to WAL. Ensures recovery can reconstruct page even if partial
    write corrupted it before crash. Cost: increases WAL volume significantly
  - wal_compression: compress full-page writes in WAL (zlib, pglz, lz4, zstd).
    Trade-off: CPU for compression vs reduced WAL volume
  - After recovery completes: PostgreSQL comes online. Recovery time is
    proportional to WAL volume since last checkpoint
  - pg_controldata: inspect cluster state including last checkpoint location,
    REDO point, timeline, and other critical metadata

TASK 6.5: Monitoring WAL and Checkpoints [MON] [DIAG]
  - Monitor pg_stat_bgwriter: checkpoints_timed, checkpoints_req,
    checkpoint_write_time, checkpoint_sync_time, buffers_checkpoint
  - Monitor WAL generation rate: pg_wal_lsn_diff(pg_current_wal_lsn(), lsn_from_N_minutes_ago)
  - Monitor pg_wal directory size and file count
  - Check checkpoint frequency in PostgreSQL logs (log_checkpoints=on):
    "checkpoint starting: time" and "checkpoint complete: wrote X buffers,
    Y% of Z total; ... write=A s, sync=B s, total=C s"
  - Monitor buffers_backend: if high, shared_buffers is too small
  - Monitor buffers_clean and maxwritten_clean: if maxwritten_clean high,
    bgwriter is being throttled

COMMON FAILURES FOR MODULE 6:
────────────────────────────────────────────────────────────────

FAILURE 6.F1: WAL Disk Full
  Symptoms: "could not write to file pg_wal/...", "No space left on device"
    in logs. Transactions begin failing. All writes blocked
  Root causes: WAL accumulation from inactive replication slot (slot holds WAL
    from restart_lsn forward), archiving failure (archive_command failing
    silently → WAL not moved → pg_wal fills), max_wal_keep_size set too high,
    WAL generation spike (massive data load) exceeding max_wal_size
  Diagnosis: Check pg_wal directory size (du -sh pg_wal) and file count.
    Check pg_replication_slots: active=t means standby consuming WAL,
    active=f means slot holding WAL with no consumer. Check pg_stat_archiver:
    last_failed_wal, failed_count, last_failed_time. Check df on pg_wal partition
  Recovery: If replication slot inactive: drop slot (pg_drop_replication_slot)
    if standby permanently gone. Fix archive_command if archiving failing.
    Manually remove WAL segments older than all replication needs (dangerous:
    only if you know which are safe). Temporarily increase wal_keep_size.
    Add disk space to pg_wal partition

FAILURE 6.F2: Checkpoint I/O Storm
  Symptoms: Periodic I/O spikes visible in iostat, query latency spikes
    correlating with checkpoint timing, "checkpoints are occurring too
    frequently" in logs
  Root cause: max_wal_size too small for write workload. Every time
    max_wal_size WAL is generated (possibly every few minutes), checkpoint
    fires. checkpoint_completion_target too low, concentrating writes
  Diagnosis: pg_stat_bgwriter shows checkpoints_req >> checkpoints_timed.
    Logs show checkpoint frequency (e.g., every 3 minutes). iostat shows
    write I/O spikes at checkpoint times. checkpoint_write_time is high
  Recovery: Increase max_wal_size (calculate: hourly WAL generation rate × 2
    hours buffer = new max_wal_size). Increase checkpoint_completion_target
    to 0.9. Reduce checkpoint_timeout if checkpoints were only timed (not
    requested), but that's unlikely in this scenario

FAILURE 6.F3: Crash Recovery Taking Too Long
  Symptoms: After unexpected shutdown, PostgreSQL startup takes many minutes
    or hours before accepting connections
  Root cause: checkpoint_timeout was very long (hours) and crash occurred
    near the end of checkpoint interval → massive WAL to replay since
    last checkpoint
  Diagnosis: pg_controldata shows "Time of latest checkpoint" is hours ago.
    WAL volume since checkpoint is large (many GB). Startup logs show
    "redo starts at LSN X/Y" and slowly progresses
  Recovery: Wait for recovery to complete (cannot speed up). Prevention:
    reduce checkpoint_timeout (e.g., 15-30 min) so recovery window is
    bounded. Balance with checkpoint I/O cost

FAILURE 6.F4: Missing WAL Segment During Recovery
  Symptoms: "could not open file pg_wal/XXXXXXXX" during startup recovery,
    "invalid record length" after reaching gap in WAL
  Root cause: WAL segment was deleted (manually, or by pg_archivecleanup
    too aggressively), or WAL segment was corrupted
  Diagnosis: pg_waldump on the missing segment confirms it's absent.
    Check archive for segment if archived. Check if segment was recycled
    and no longer available
  Recovery: If WAL is in archive: restore to pg_wal, recovery continues.
    If WAL permanently lost: pg_resetwal -f to reset WAL (DATA LOSS:
    all recent transactions lost, database may have inconsistencies).
    Then rebuild from backup if possible

FAILURE 6.F5: Checkpoint Panel (Full Page Writes) Bloat
  Symptoms: WAL generation rate much higher than expected for update volume.
    pg_wal fills faster than calculated
  Root cause: full_page_writes=on causes first modification of each page
    after checkpoint to write entire 8KB page to WAL, even if only one
    byte changed. This can 2-5x WAL volume for certain workloads
  Diagnosis: Calculate expected WAL per transaction vs actual. If actual
    much higher, FPW is contributing. pg_waldump shows many FPI (Full Page
    Image) records
  Recovery: Enable wal_compression to reduce impact. Tune
    checkpoint_completion_target higher to reduce FPW frequency (fewer
    checkpoints = fewer FPW writes). Do NOT disable full_page_writes

LAYER 2: CONNECTED (after Modules 12-14)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 6.X1: WAL → Replication
    - WAL is the replication stream. WAL sender processes on primary read
      WAL and send to standby's WAL receiver
    - Replication slots hold WAL from restart_lsn until consumed by standby.
      Each slot = WAL retention demand on pg_wal
    - max_slot_wal_keep_size (PG13+): auto-invalidates slot if WAL retention
      exceeds this limit. Protects pg_wal from filling due to abandoned slot
    - pg_waldump: inspect exactly what WAL records are being sent to standby.
      Filter by transaction ID to see specific operations

  CROSS-TOPIC TASK 6.X2: WAL → Backup
    - WAL archiving (archive_mode=on + archive_command) copies WAL to archive
      location for point-in-time recovery
    - archive_command called for each WAL segment after it completes
    - Failed archive_command: WAL segment remains in pg_wal, archiver
      retries. pg_wal accumulates. archive_status directory tracks per-file
      status (ready, done, failed)
    - Backup + continuous WAL archive = PITR capability

  CROSS-TOPIC TASK 6.X3: Checkpoint → Vacuum
    - Vacuum generates WAL (heap modifications, index modifications
      recorded in WAL). Anti-wraparound vacuum generates significant WAL
    - Vacuum's WAL generation contributes to max_wal_size → can trigger
      checkpoint → checkpoint I/O + vacuum I/O compounds
    - Strategy: run intensive vacuum during low-write periods to avoid
      compounding checkpoint pressure with vacuum WAL

  CROSS-TOPIC TASK 6.X4: Checkpoint → OS Writeback Interaction
    - checkpoint writes dirty shared_buffers to data files
    - OS page cache also holds dirty pages; vm.dirty_ratio triggers
      OS-level writeback independently of PostgreSQL checkpoints
    - If both fire simultaneously: I/O contention
    - Tuning: ensure vm.dirty_ratio is low enough that OS writeback doesn't
      amplify checkpoint writes, but high enough for OS efficiency

  COMBINED FAILURE 6.XF1: WAL Disk Full from Replication Slot + Archive Failure
    - Standby goes down for planned 2-hour maintenance
    - Replication slot holds WAL from restart_lsn during outage
    - archive_command starts failing (network to archive destination down)
    - WAL accumulates: slot retention + failed archiving retention
    - pg_wal partition fills: database hangs
    - Diagnosis: Check slot wal_status (should be 'reserved' or 'extended'),
      check pg_stat_archiver last_failed_time and failed_count
    - Recovery: Drop slot if standby permanently gone (data loss for
      standby = requires rebuild). Fix archive destination connectivity.
      Manually remove oldest WAL segments if certain they're not needed
    - Prevention: set max_slot_wal_keep_size to safe value. Monitor
      archive_command success rate. Alert on WAL directory > 70%

  TASK 6.D1: WAL Internals [CON]
    - WAL record types: XLOG_HEAP_INSERT, XLOG_HEAP_UPDATE, XLOG_HEAP_DELETE,
      XLOG_HEAP_HOT_UPDATE, XLOG_HEAP_FREEZE, XLOG_BTREE_INSERT_LEAF, etc.
    - WAL page structure: 8KB pages (separate from heap pages), with
      WAL-specific headers and record structures
    - pg_waldump: inspect binary WAL content. Filter by transaction ID to
      trace a transaction's operations. Filter by relation to see all
      modifications to a table. Understand record types and their meaning
    - WAL switch: issued by pg_switch_wal() to force new WAL segment.
      archive_command receives old segment after switch completes
    - WAL segment lifecycle timeline: created → filled (maybe hours in
      low-write, minutes in high-write) → archived → recycled (renamed
      to future segment)

  TASK 6.D2: Checkpoint Tuning Calculus [DES]
    - Goal: minimize crash recovery time while avoiding checkpoint I/O
      impact on query workload
    - Calculate target checkpoint frequency:
      - Recovery time objective (RTO): how long can recovery take?
        If RTO = 5 minutes, checkpoint must run at most every 10 minutes
        (WAL replay approximately 2× checkpoint interval)
      - Calculate max_wal_size: measure WAL generation rate per hour.
        Set max_wal_size = (WAL per hour) × (desired maximum hours between
        forced checkpoints). For 1 hour: max_wal_size = hourly WAL rate
      - checkpoint_timeout: set to match desired max interval, but no
        longer than max_wal_size-derived interval
    - Checkpoint completion: checkpoint_completion_target = 0.9 spreads
      writes over 90% of interval. Higher = more spread, less I/O impact
      per second. Lower = faster checkpoint, more concentrated I/O
    - Special case: full_page_writes causes first modification after
      checkpoint to be expensive. Shorter checkpoint intervals = more
      FPW events. Longer = fewer FPW but more recovery time

  TASK 6.D3: Recovery Scenarios and Timeline Management [REC] [DES]
    - PITR recovery: restore base backup + recovery.conf specifying
      restore_command and recovery_target_time/LSN/XID/name
    - After PITR completes: recovery_target_action determines behavior:
      promote (become normal primary), pause (stay in recovery for
      investigation), shutdown
    - Timeline creation: each PITR or standby promotion creates new
      timeline. New WAL segments get new timeline number prefix.
      Old timeline continues to exist for old WAL. Useful for DR
      scenarios where you may roll back to original timeline
    - pg_rewind: if old primary diverged from new primary during failover,
      pg_rewind can rewind it to match new primary's timeline using
      WAL. Requires wal_log_hints=on or checksums enabled
    - Compare: full pg_basebackup (always works, takes time for large DB)
      vs pg_rewind (faster, requires wal_log_hints)

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 6:
    - WAL segment corruption (bit flip in WAL): symptoms (invalid record
      length, invalid magic number during recovery), diagnosis (pg_waldump
      on segment fails), recovery (restore WAL from archive, or accept
      recovery stops at corruption point + data loss after that point)
    - Checkpoint record in pg_control corrupted: symptoms (invalid primary
      checkpoint record, invalid secondary checkpoint record at startup),
      diagnosis (pg_controldata shows errors), recovery (restore pg_control
      from backup, or pg_resetwal with data loss)
    - full_page_writes=off then crash: partial writes not recoverable.
      Corruption possible. DO NOT disable full_page_writes in production
    - WAL archive gap: missing WAL segment in archive prevents PITR past
      that gap. Detection: restore attempt fails with missing segment.
      Recovery: only PITR up to gap. Prevention: verify archive continuity
    - Checkpoint during pg_basebackup: backup may take longer as checkpoint
      syncs all dirty buffers. Tune: run pg_basebackup with --checkpoint=fast
      or use backup from standby

MODULE 7: INDEXING — TYPES, DESIGN & MAINTENANCE
================================================================================
PREREQUISITES: Module 3 (page layout), Module 4 (MVCC)
PURPOSE: Indexes are the primary query performance mechanism. Poor index
  design or maintenance is the most common cause of production performance
  problems.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 7.1: B-tree Index Structure [CON] [OP]
  - B-tree (balanced tree): the default index type. Root → internal pages
    (branch) → leaf pages. Leaves contain (key, ctid) pairs pointing to
    heap tuples. ctid = (page_number, tuple_offset)
  - Understand index page structure: metadata header, index tuples (sorted
    by key), special space for page type information. Different from heap
    pages — index pages have index-specific internal structure
  - Insertion: find correct leaf by traversing from root, following key
    comparisons. Insert into leaf. If leaf full, split into two pages,
    promote separator to parent. If root full, split root (tree grows
    one level)
  - Deletion: index doesn't physically remove entries immediately (MVCC
    requires old versions for snapshots). Marks entry as dead. Vacuum
    removes dead index entries during index vacuum phase
  - B-tree supports: equality (=), range (<, <=, >, >=), BETWEEN, IN,
    IS NULL, IS NOT NULL, LIKE 'prefix%' (but NOT LIKE '%suffix' or
    '%middle%')
  - Composite index: index on (a, b). Supports: WHERE a = X (uses index),
    WHERE a = X AND b = Y (uses full index), WHERE b = Y (may not use
    index — column order matters)
  - Dead index tuples: row deletion leaves dead index entries. Vacuum's
    index vacuum phase removes them. Index bloat occurs when vacuum
    doesn't run

TASK 7.2: Index Types Overview [CON] [OP]
  - B-tree: default. Good for ordered scans, equality, range. Most
    versatile. For text: supports prefix matching (LIKE 'prefix%')
  - Hash: equality only. Smaller than B-tree for large keys (UUID,
    long text). Before PG10: not WAL-logged (unsafe for replication).
    Now fully safe. Use: when only equality queries and key is large
  - GiST (Generalized Search Tree): extensible framework. Used by PostGIS
    (geometry), range types (overlap, containment), full-text search
    (tsvector). Supports nearest-neighbor (KNN) search
  - SP-GiST (Space-Partitioned GiST): for unbalanced tree structures.
    IP addresses (inet), phone numbers, 2D points
  - GIN (Generalized Inverted Index): for composite values where you
    query by subset. Full-text search (tsvector: search by lexeme),
    arrays (contains, overlaps), JSONB (key existence, containment),
    trigrams (pg_trgm: similarity, LIKE '%middle%')
  - BRIN (Block Range INdex): very small index for naturally ordered
    large tables. Stores min/max per block range. Works for time-series
    (timestamp column correlated with physical order). Pages_per_range
    tuning critical
  - Bloom: probabilistic index (may have false positives). For many
    column equality filters. Requires bloom extension

TASK 7.3: Index Design Principles [DES]
  - Single-column vs composite: composite useful when queries filter on
    multiple columns. Leftmost column rule: index on (a,b) supports
    queries on 'a' but not 'b' alone
  - Column ordering in composite indexes:
    - Equality queries: most selective column first (reduces scan range)
    - Range queries: range column last (equality columns narrow scope,
      range scan on remaining)
    - ORDER BY: if ordering matches index, avoids Sort node
  - Covering indexes: include all columns needed by query in index
    (CREATE INDEX ... INCLUDE (non_key_column)). Enables index-only
    scans: heap access not needed if all columns in index
  - Partial indexes: WHERE clause to index only subset of rows.
    Use: index only active rows (WHERE deleted_at IS NULL), index
    only high-priority items (WHERE priority = 'high')
  - Expression indexes: index on function result. Use: case-insensitive
    search (lower(email)), date truncation (date_trunc('day', created_at))
  - Unique indexes: enforce uniqueness AND provide index. Can be partial
    (unique constraint on active rows only)
  - Index on foreign key columns: prevents full table lock on parent
    during DELETE/UPDATE of parent. ALTER TABLE ... ADD FOREIGN KEY
    always locks parent for duration; index on FK column allows lock
    to be brief

TASK 7.4: Index Maintenance [OP] [DIAG]
  - REINDEX: rebuild index from scratch. Offline: full table lock
    (AccessExclusiveLock). Online: REINDEX CONCURRENTLY — no lock,
    creates new index in background, swaps when complete (PG12+)
  - Index bloat detection: pgstattuple on index shows dead_tuple_percent,
    avg_leaf_density. pgstatindex (from pgstattuple) shows tree depth,
    leaf_fragmentation
  - Invalid indexes: failed CREATE INDEX CONCURRENTLY may leave index
    with indisvalid=false. Doesn't affect queries. Can be dropped
    and recreated. Check with: SELECT indexrelid::regclass FROM
    pg_index WHERE NOT indisvalid
  - Unused index detection: pg_stat_user_indexes.idx_scan = 0 for
    extended period. Exclude unique constraint indexes (used for
    constraint enforcement, not queries)
  - Duplicate index detection: same table, same column set, same
    column order, same predicates. Use information_schema or
    pg_index joins

COMMON FAILURES FOR MODULE 7:
────────────────────────────────────────────────────────────────

FAILURE 7.F1: Index Bloat
  Symptoms: Index size growing faster than table, index scans
    reading more pages than expected, REINDEX reduces size significantly
  Root cause: Heavy UPDATE/DELETE on indexed columns. Vacuum not keeping
    up with dead index entry creation. fillfactor too high for workload
  Diagnosis: pgstattuple(index) shows dead_tuple_percent > 30%.
    pg_stat_user_indexes shows idx_scan > 0 but high idx_blks_read
    (disk reads). Compare pg_relation_size before/after REINDEX
  Recovery: REINDEX CONCURRENTLY to rebuild without downtime.
    Or pg_repack (rebuilds table + indexes). Prevention: tune
    autovacuum, set appropriate fillfactor for index

FAILURE 7.F2: Missing Index → Sequential Scan
  Symptoms: Query slow, EXPLAIN shows "Seq Scan on large_table"
    with rows=millions and time=seconds
  Root cause: No index on columns used in WHERE clause, or index
    exists but planner doesn't choose it (see Module 8)
  Diagnosis: EXPLAIN ANALYZE shows sequential scan. pg_stat_user_tables
    shows high seq_scan count for that table. Check existing indexes
    via \d tablename
  Recovery: CREATE INDEX on appropriate columns. For production:
    CREATE INDEX CONCURRENTLY (no table lock). Verify query plan change

FAILURE 7.F3: Index Not Used by Planner
  Symptoms: Index exists on query columns, but EXPLAIN still shows
    sequential scan
  Root cause: Statistics wrong (planner estimates scan returns most
    of table → seq scan cheaper), data type mismatch (WHERE int_col = '123'
    with quotes → implicit cast prevents index use), function on indexed
    column (WHERE lower(col) = 'x' but index is on col, not lower(col)),
    LIKE with leading wildcard (WHERE col LIKE '%suffix' cannot use B-tree)
  Diagnosis: EXPLAIN ANALYZE — compare actual rows vs estimated rows.
    If mis-estimated: statistics stale. Check query for type mismatch
    or function wrapping
  Recovery: ANALYZE table if statistics stale. Create expression index
    if function needed. Rewrite query if type mismatch. Use GIN+pg_trgm
    for leading wildcard LIKE

FAILURE 7.F4: CREATE INDEX Failures
  Symptoms: CREATE INDEX fails, or CREATE INDEX CONCURRENTLY leaves
    invalid index
  Root causes: CREATE INDEX CONCURRENTLY can fail if: unique violation
    (for unique index), deadlock with other operations, statement_timeout
    expiry, crash during build. Leaves index with indisvalid=false
  Diagnosis: pg_index.indisvalid = false. Error in PostgreSQL log
    from build attempt
  Recovery: DROP INDEX CONCURRENTLY on invalid index. Fix root cause.
    Re-run CREATE INDEX CONCURRENTLY

FAILURE 7.F5: Too Many Indexes → Write Slowdown
  Symptoms: INSERT/UPDATE/DELETE operations slow. Each index on table
    must be updated on write. Vacuum takes longer (more indexes to scan)
  Root cause: Index proliferation: over time, indexes added for various
    queries, never removed. Some are duplicates or unused
  Diagnosis: pg_stat_user_indexes.idx_scan = 0 (unused). \d table
    shows many indexes (more than 5-8 for OLTP is suspicious).
    Measure: DML throughput drops as index count increases
  Recovery: Drop unused indexes (verify they're truly unused over
    full business cycle). Drop duplicate indexes. Consolidate
    overlapping indexes

LAYER 2: CONNECTED (after Modules 8-9)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 7.X1: Index → Query Planning
    - Planner evaluates multiple index scan options: which index
      has best selectivity? Should it use index scan, bitmap scan,
      or sequential scan?

    - Planner may choose different index for different WHERE values
      (statistics-based selectivity)
    - Index-only scan possible if all columns in index + VM bit set

  CROSS-TOPIC TASK 7.X2: Index → Vacuum
    - Each index on a table adds vacuum work: index vacuum phase
      must scan every index looking for dead entries
    - Table with 10 indexes: vacuum time dominated by index phase
    - maintenance_work_mem: insufficient memory = multiple passes
      over ALL indexes
    - vacuum_index_cleanup=off for insert-only tables (no dead
      index entries ever exist)

  CROSS-TOPIC TASK 7.X3: Index → Locking
    - CREATE INDEX takes ShareLock (allows reads, blocks writes)
      on table during build phase
    - CREATE INDEX CONCURRENTLY: takes ShareUpdateExclusiveLock
      briefly at start and end (allows reads/writes)
    - REINDEX CONCURRENTLY: similar minimal locking
    - What operations conflict with index creation? DDL, VACUUM FULL,
      CLUSTER (all take AccessExclusiveLock)

  COMBINED FAILURE 7.XF1: Index Bloat → Query Performance Degradation
    - Heavy UPDATE load on indexed columns → dead index entries
    - Vacuum cannot keep up → index bloats (3x ideal size)
    - Planner still chooses index (still faster than seq scan, barely)
    - But index reads 3x more pages → IO increases → latency increases
    - Concurrent queries increase → shared_buffers pressure increases
    - Vicious cycle: more queries = more buffer eviction = more disk
      reads for index = slower queries = more concurrent queries
    - Diagnosis: Compare pg_relation_size before/after REINDEX.
      pgstattuple shows dead_tuple_percent
    - Recovery: REINDEX CONCURRENTLY, tune autovacuum

LAYER 3: DEEP (after Module 11)
────────────────────────────────────────────────────────────────

  TASK 7.D1: B-tree Internals [CON]
    - Page split mechanics: 50/50 split normally. If inserting in
      sorted order (UUID v4, random), pages split unevenly, index
      becomes sparse (low page density). UUID v7 (time-sorted)
      inserts at end = efficient
    - Deduplication (PG13+): duplicate values in unique indexes
      (e.g., indexed column with few distinct values) stored once
      with a count. Large Posting List (LPL) for many duplicates.
      Reduces index size for low-cardinality columns
    - Fillfactor for indexes: during CREATE INDEX and REINDEX,
      fillfactor% of leaf page filled. Remaining space for future
      inserts without page splits. Good for insert-heavy tables
    - Metapage: page 0 of index, stores root page location, tree
      depth, statistics. Inspect with bt_metap()

  TASK 7.D2: Index Type Selection Matrix [DES]
    - Equality lookups only: Hash (smaller for large keys)
    - Range queries + sorting: B-tree
    - Text search (LIKE '%middle%', similarity): GIN + pg_trgm
    - Full-text search (tsvector): GIN (fast reads, slower writes)
    - Geometry/Geographic: GiST (PostGIS)
    - Array containment (@>, &&): GIN
    - JSONB containment/existence: GIN
    - Time-series, naturally ordered: BRIN (very small, 1000x smaller)
    - Many-column equality (warehouse): Bloom
    - For each: understand read speed, write overhead, index size,
      supported operators

  TASK 7.D3: Index Maintenance Strategy [DES]
    - Schedule: REINDEX CONCURRENTLY during maintenance window for
      bloated indexes. Don't wait for problems
    - Automated detection: query pgstattuple or bloat estimation
      queries weekly. Alert if > 30% bloat
    - pg_repack for online table+index rebuild with minimal locking
    - Partitioned tables: indexes are per-partition. Smaller indexes
      = faster REINDEX, can do one partition at a time

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 7:
    - Duplicate unique index entries (corruption): amcheck detects.
      Recovery: REINDEX, or restore from backup
    - Index pointing to non-existent heap tuple: pg_catcheck or amcheck.
      Recovery: REINDEX
    - B-tree page corruption: "invalid page in block" during index scan.
      Recovery: REINDEX
    - Failed REINDEX CONCURRENTLY: may leave old index invalid and new
      index partial (both invalid). Recovery: drop both, reindex again
    - BRIN summarization not happening: autosummarize=off, manual
      brin_summarize_range needed. Data outside summarized ranges
      requires full table scan

MODULE 8: QUERY PLANNING & EXPLAIN ANALYTICS
================================================================================
PREREQUISITES: Module 7 (must understand index types and structure)
PURPOSE: EXPLAIN is the window into PostgreSQL's query execution.
  Mastery means you never guess why a query is slow — you know.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 8.1: EXPLAIN Fundamentals [CON] [OP]
  - EXPLAIN: shows planner's predicted plan with estimated costs and
    row counts. Does NOT execute query
  - EXPLAIN ANALYZE: executes query, shows actual times and row counts
    alongside estimates. The gold standard for performance diagnosis
  - Reading plan output: plan is a tree, indented. Innermost (most
    indented) nodes execute first, feed outer nodes. Read from
    innermost to outermost, bottom to top
  - Plan node types and what they mean:
    Seq Scan: full table scan, reads every page
    Index Scan: traverse index, then fetch heap tuples
    Index Only Scan: all needed columns are in index, heap access skipped
      (requires visibility map bits set)
    Bitmap Heap Scan: build bitmap of interesting pages from index,
      then scan those pages in physical order
    Nested Loop: for each outer row, scan inner relation
    Hash Join: hash inner relation, probe with outer
    Merge Join: both inputs sorted on join key, merge like merge sort
    Sort: sort rows (by ORDER BY, DISTINCT, merge join prep)
    Hash: hash aggregate or hash join build phase
    Aggregate: group by aggregation
    Limit: stop after N rows

TASK 8.2: EXPLAIN Options [OP]
  - EXPLAIN (ANALYZE): actual timing, actual rows, loops
  - EXPLAIN (BUFFERS): shared_blks_hit/read/dirtied, local_blks_*,
    temp_blks_*. Shows cache efficiency and temp file usage
  - EXPLAIN (TIMING): per-node timing (default on). Turn off for
    less overhead on fast queries
  - EXPLAIN (VERBOSE): output columns, schema, table OIDs, etc.
  - EXPLAIN (COSTS): estimated costs (default on)
  - EXPLAIN (FORMAT JSON/YAML/XML): machine-readable output for
    analysis tools
  - EXPLAIN (SETTINGS): shows non-default GUC settings affecting plan
  - EXPLAIN (WAL): WAL generation per plan node

TASK 8.3: The Cost Model [CON]
  - Planner chooses plan with lowest estimated cost (arbitrary unit)
  - Cost parameters and their meanings:
    seq_page_cost (default 1.0): sequential page read cost
    random_page_cost (default 4.0): random page read cost.
      For SSD: set to 1.1-1.5 (random access nearly as fast as sequential)
    cpu_tuple_cost (0.01): processing one row
    cpu_index_tuple_cost (0.005): processing one index entry
    cpu_operator_cost (0.0025): evaluating a WHERE clause operator
  - How costs combine: total cost = startup cost + total cost.
    Startup: work done before first row can be returned.
    Total: all work including startup
  - Path generation: planner generates many possible query plans
    (paths), estimates cost for each using statistics, chooses cheapest

TASK 8.4: Reading EXPLAIN ANALYZE [DIAG] [CON]
  - Key fields per node:
    (actual time=XXX.XXX..YYY.YYY rows=ZZZZ loops=WWWW)
    First number: average startup time (first row) per loop
    Second number: average total time (all rows) per loop
    rows: actual rows returned per loop
    loops: how many times this node was executed
  - Finding bottlenecks: look for nodes where actual time dominates.
    Look for large difference between estimated rows and actual rows
    (indicates bad statistics)
  - Buffer usage: shared_blks_read = disk reads (slow), shared_blks_hit
    = buffer hits (fast). If reads high, shared_buffers may be too small
    or table too large to cache
  - Temp blocks: temp_blks_written indicates work_mem overflow for sort
    or hash. Increase work_mem for this query pattern
  - Nested loop: if inner loop has large row estimate but small actual,
    fine. If inner has large actual, nested loop explodes (outer_rows
    × inner_rows). May need hash join instead

TASK 8.5: Common Plan Patterns and What They Tell You [DIAG]
  - Seq Scan on large table where index exists: check cost settings
    (random_page_cost too high?), table stats (planner estimated
    most rows would be fetched?)
  - Index Scan + heap fetch where Index Only Scan should happen:
    check EXPLAIN (BUFFERS) — heap_blks_read high → VM bits stale
    → run VACUUM
  - Nested Loop with large actual inner: planner estimated inner=1
    but actually=10000. Bad statistics or correlated columns
  - Sort with "Sort Method: external merge Disk": work_mem too small
    for sort. Increase work_mem
  - Hash Join with "Buckets: X Batches: Y (originally Z)": if
    Batches > 1, hash table didn't fit in work_mem and spilled to
    disk. Increase work_mem
  - Materialize node: inner result cached for reuse. Usually
    intentional and fine

COMMON FAILURES FOR MODULE 8:
────────────────────────────────────────────────────────────────

FAILURE 8.F1: Query Plan Regression
  Symptoms: Query that was fast suddenly becomes slow. No code changes
  Root cause: Statistics changed (ANALYZE sampled different data
    distribution), data volume passed threshold (planner switches
    from index scan to seq scan), vacuum not run (VM bits stale,
    index-only scan no longer possible), planner parameter changed
  Diagnosis: Compare current EXPLAIN with historical (if available).
    Check pg_stat_statements for query performance over time.
    Check last_analyze timestamp. Check n_live_tup vs actual row count
  Recovery: ANALYZE the table. If needed, SET random_page_cost lower
    for this query. Use pg_hint_plan to force specific plan as
    emergency measure. Address root cause (missing index, tune
    autovacuum, update statistics target)

FAILURE 8.F2: Nested Loop Explosion
  Symptoms: EXPLAIN shows Nested Loop with outer rows=10, inner actual
    rows=100000 (expected=1). Total time enormous
  Root cause: Planner mis-estimated inner cardinality (expected few
    rows but got many). Caused by: stale statistics, correlated
    columns (planner assumes independence), missing extended
    statistics (CREATE STATISTICS)
  Diagnosis: EXPLAIN ANALYZE shows large actual/estimated mismatch
    on inner scan. Check pg_stats for column correlations
  Recovery: CREATE STATISTICS on correlated columns. Increase
    statistics target. Rewrite query to avoid correlated condition
    or use different join order

FAILURE 8.F3: Sort Spilling to Disk
  Symptoms: EXPLAIN ANALYZE shows "Sort Method: external merge Disk"
  Root cause: work_mem too small for the sort operation. Sort needs
    more memory than allocated
  Diagnosis: Look for "Sort" nodes with Method=external merge Disk.
    Check temp_blks_written in EXPLAIN (BUFFERS)
  Recovery: Increase work_mem for this session or globally (carefully).
    Rewrite query to sort fewer rows (more restrictive WHERE).
    Add index that provides pre-sorted data (avoids Sort node entirely)

FAILURE 8.F4: Index Not Chosen (Seq Scan Instead)
  Symptoms: EXPLAIN shows Seq Scan when index exists and you expect
    index scan
  Root causes: (1) Planner estimates seq scan is cheaper (fetching
    most of table, random_page_cost high). (2) Statistics stale
    (planner thinks table is empty). (3) Index not applicable
    (wrong data type, function-wrapped column). (4) Index is
    bloated (random_page_cost estimate higher from larger index)
  Diagnosis: Check estimated rows vs actual. If planner expects
    many rows but actual is few: stale statistics → ANALYZE.
    If actual is many rows: seq scan is correct choice.
    If index not applicable: check query for type mismatch
  Recovery: ANALYZE if stale. Create proper index if missing.
    Lower random_page_cost if on SSD (to 1.5 or 1.1).
    Run REINDEX if index is bloated

MODULE 9: LOCKING & CONCURRENCY CONTROL
================================================================================
PREREQUISITES: Module 4 (MVCC), Module 8 (understand how queries execute)
PURPOSE: Locking is the mechanism that prevents chaos when hundreds of
  connections modify the same data. Understanding locks is essential for
  diagnosing "hung" queries and designing concurrent applications.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 9.1: Lock Fundamentals [CON]
  - Why locks if we have MVCC? MVCC handles visibility (what you see).
    Locks handle concurrency control (who can modify what, when).
    MVCC provides snapshot isolation for readers. Locks prevent
    concurrent writers from corrupting each other's changes
  - Lock granularities: transaction level, relation (table) level,
    page level, tuple (row) level, advisory
  - Lock modes (table-level, from weakest to strongest):
    AccessShareLock       — SELECT takes this. Conflicts only with AEL
    RowShareLock          — SELECT FOR UPDATE/SHARE takes this
    RowExclusiveLock      — INSERT/UPDATE/DELETE takes this. Conflicts
                            with Share, ShareRowExcl, Exclusive, AEL
    ShareUpdateExclusive  — VACUUM, ANALYZE, CREATE INDEX CONCURRENTLY
                            takes this. Conflicts with same and higher
    ShareLock             — CREATE INDEX takes this on table
    ShareRowExclusiveLock — CREATE TRIGGER takes this
    ExclusiveLock         — REFRESH MATERIALIZED VIEW CONCURRENTLY takes this
    AccessExclusiveLock   — DROP, TRUNCATE, VACUUM FULL, ALTER TABLE
                            takes this. Blocks EVERYTHING including SELECT
  - Row-level locks: FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE, FOR KEY SHARE
    - FOR UPDATE: locks row for update. Blocks other FOR UPDATE/FOR SHARE
    - FOR NO KEY UPDATE: blocks other FOR UPDATE, does NOT block FOR KEY
      SHARE (used for foreign key checks)
    - FOR SHARE: blocks FOR UPDATE/NO KEY UPDATE, not FOR SHARE
    - FOR KEY SHARE: weakest, blocks only FOR UPDATE. Used by FK checks

TASK 9.2: pg_locks Deep Dive [OP] [DIAG]
  - Query pg_locks to see all locks. Join with pg_stat_activity for context
  - Interpret every pg_locks column:
    locktype: relation, transactionid, virtualxid, tuple, page, object,
      advisory, extend
    database: OID of database (or 0 for shared objects)
    relation: OID of relation (or NULL for non-relation locks)
    page/tuple: page or tuple number within relation
    virtualxid/virtualtransaction: virtual transaction IDs
    pid: backend process holding or waiting for this lock
    mode: lock mode name (e.g., AccessShareLock, RowExclusiveLock)
    granted: true = lock held, false = lock being waited for
    waitstart: when lock wait began (PG16+)
    fastpath: true if lock taken via fast-path mechanism (optimization)

TASK 9.3: Blocking Chain Detection [DIAG] [REC]
  - Find blocked queries: pg_stat_activity WHERE wait_event_type='Lock'
    AND wait_event='relation' (or 'transactionid', 'tuple')
  - Find blocker: for each blocked PID, find the PID holding the
    conflicting lock. Query pg_locks: blocked PID has NOT granted
    lock. Which PID has granted lock on same (database, relation,
    tuple)?
  - Build blocking tree: A blocks B, B blocks C, etc. Find root blocker
    (blocking others but not blocked itself)
  - Common blocker profiles:
    - Idle in transaction holding RowExclusiveLock (forgot COMMIT)
    - DDL waiting behind long SELECT (DDL tries for AccessExclusiveLock,
      must wait for all SELECTs to finish)
    - Row lock conflict (two transactions updating same row)
    - Prepared transaction holding locks (PREPARE TRANSACTION but
      never COMMIT PREPARED or ROLLBACK PREPARED)

TASK 9.4: Lock Monitoring and Prevention [MON] [DES]
  - log_lock_waits = on: logs every lock wait lasting > deadlock_timeout
    (default 1s). Essential for detecting lock contention
  - deadlock_timeout: PostgreSQL checks for deadlocks periodically.
    Default 1s is fine. Setting too high = deadlocks persist longer
  - lock_timeout: abort statement if lock not acquired within this time.
    Set per session or per role. Prevents DDL from blocking application
    indefinitely
  - idle_in_transaction_session_timeout: kill sessions stuck in
    idle-in-transaction. These hold locks and block vacuum
  - Monitor: pg_stat_activity with wait_event_type='Lock' (blocked count).
    pg_locks with granted=false count. Track trend

COMMON FAILURES FOR MODULE 9:
────────────────────────────────────────────────────────────────

FAILURE 9.F1: DDL Blocked by Long-Running Query
  Symptoms: ALTER TABLE, CREATE INDEX, or VACUUM FULL hangs indefinitely
  Root cause: DDL requires AccessExclusiveLock (AEL). AEL conflicts with
    ALL other lock modes. If any query holds even AccessShareLock
    (from SELECT) on that table, DDL waits in lock queue. All subsequent
    queries also queue behind DDL (lock queue is FIFO)
  Diagnosis: pg_stat_activity shows DDL with wait_event_type='Lock'.
    pg_locks shows DDL waiting for AccessExclusiveLock (granted=false).
    Find which PIDs hold conflicting locks (usually AccessShareLock from
    long-running SELECT)
  Recovery: Terminate the blocking queries. DDL proceeds. All queued
    queries also proceed
  Prevention: Set lock_timeout for DDL sessions. Never run DDL without
    first checking pg_stat_activity for long queries on target table

FAILURE 9.F2: Deadlock
  Symptoms: "ERROR: deadlock detected" in application logs or PostgreSQL
    log. One transaction rolled back, other continues
  Root cause: Circular lock dependency: T1 has lock on row A, waits for
    row B. T2 has lock on row B, waits for row A. Neither can proceed.
    PostgreSQL detects deadlock after deadlock_timeout (1s) and aborts
    one transaction
  Diagnosis: PostgreSQL log shows "DETAIL: Process X waits for ShareLock
    on transaction Y; blocked by process Z". Log shows both queries
  Recovery: The aborted transaction must retry. Application should
    implement retry logic for deadlock errors (SQLSTATE 40P01)
  Prevention: Consistent lock ordering (always lock rows in same order:
    parent before child, lower ID before higher ID). Shorter transactions.
    Use advisory locks for complex multi-table locking

FAILURE 9.F3: Idle in Transaction Holding Locks
  Symptoms: queries pile up in pg_stat_activity with wait_event_type='Lock',
    blocker shows state='idle in transaction'
  Root cause: Application started transaction, acquired locks, then
    became idle (waiting for user input, network delay, application logic).
    Transaction remains open, locks held. Vacuum also blocked
  Diagnosis: pg_stat_activity shows PID with state='idle in transaction',
    query_start is old, backend_xmin is set (blocking vacuum too)
  Recovery: pg_terminate_backend(pid) or pg_cancel_backend(pid).
    Application must handle disconnection gracefully
  Prevention: Set idle_in_transaction_session_timeout. Fix application
    to COMMIT/ROLLBACK promptly after business logic completes

FAILURE 9.F4: Lock Queue Buildup
  Symptoms: Many queries in pg_stat_activity with wait_event_type='Lock'.
    Connection count rising but not at max_connections yet. Application
    latency increasing
  Root cause: One query holds a lock that many other queries need.
    Lock queue is FIFO. All waiters line up. If blocker holds lock a
    long time, queue grows
  Diagnosis: pg_locks shows many NOT-granted locks for same
    (database/relation). Single PID has the granted lock
  Recovery: Terminate blocker. All queued queries resume
  Prevention: Keep transactions short. Use SELECT FOR UPDATE only
    when necessary. Consider SKIP LOCKED for queue-like workloads

FAILURE 9.F5: AccessExclusiveLock on Critical Table During Peak
  Symptoms: All queries on table hang, application errors, connections
    building up, potential max_connections exhaustion
  Root cause: Someone ran ALTER TABLE, VACUUM FULL, CLUSTER, or
    DROP/CREATE INDEX (non-CONCURRENTLY) during production hours
  Diagnosis: find PID holding AccessExclusiveLock on that relation
  Recovery: CANNOT safely cancel. Must wait for operation to complete.
    If it will take hours, evaluate: is downtime acceptable?
    If not, restart PostgreSQL (last resort, causes crash recovery)
  Prevention: NEVER run DDL without maintenance window approval.
    Use CONCURRENTLY variants (CREATE INDEX CONCURRENTLY,
    REINDEX CONCURRENTLY). Use pg_repack instead of VACUUM FULL

LAYER 2: CONNECTED (after Modules 5, 14)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 9.X1: Locking → Vacuum
    - VACUUM takes ShareUpdateExclusiveLock on table. Conflicts with:
      other ShareUpdateExclusive (another vacuum), ShareLock,
      ShareRowExclusiveLock, ExclusiveLock, AccessExclusiveLock
    - VACUUM FULL takes AccessExclusiveLock → blocks everything
    - Autovacuum can be blocked by DDL holding conflicting lock
    - Vacuum truncation (last phase) takes AccessExclusiveLock briefly.
      If standby query holds conflicting lock, truncation skipped

  CROSS-TOPIC TASK 9.X2: Locking → Replication
    - Hot standby conflicts: queries on standby may be cancelled due to
      conflicting WAL replay (recovery conflict). Types:
      - AccessExclusiveLock on primary → standby replay needs same →
        conflicts with standby queries
      - Buffer pin conflict: standby query reading page that WAL
        replay needs to modify
      - Snapshot conflict: vacuum on primary removed rows that standby
        query needs (if hot_standby_feedback=off)
    - max_standby_streaming_delay: how long WAL replay waits before
      cancelling conflicting standby queries

  CROSS-TOPIC TASK 9.X3: Locking → Connection Pooling
    - Transaction pooling resets session state between transactions.
      Locks held across transactions are impossible (pool kills
      connection on transaction end). Application cannot hold locks
      across "transactions" in transaction pooling mode

  COMBINED FAILURE 9.XF1: DDL Blocks All Queries → Connection Pool Exhaustion
    - ALTER TABLE on high-traffic table
    - DDL takes AccessExclusiveLock, waits for existing queries to finish
    - New queries queue behind DDL
    - PgBouncer connections all occupied (queries sitting in lock queue)
    - New client connections queue at PgBouncer (or get "too many clients")
    - Entire application freezes
    - Diagnosis: pg_locks shows AccessExclusiveLock waiting (NOT granted),
      many queries queued behind with granted=false
    - Recovery: Cancel DDL. Queries drain. Set lock_timeout on DDL to
      prevent future occurrences

LAYER 3: DEEP
────────────────────────────────────────────────────────────────

  TASK 9.D1: Lock Manager Internals [CON]
    - Lock table in shared memory: hash table keyed by (locktag_fields:
      locktype, database, relation, page, tuple, virtualxid,
      transactionid, classid, objid, objsubid)
    - Fast-path locking: for weak locks (AccessShareLock, RowShareLock)
      that don't conflict with most locks, PostgreSQL uses fast-path
      mechanism (per-backend array, no hash table lookup). Faster
      but limited slots (FP_LOCK_SLOTS_PER_BACKEND ≈ 16)
    - Lock queue: waiters for a given lockable object organized
      in FIFO queue. No priority. No "promote" mechanism

  TASK 9.D2: Deadlock Detection Algorithm [CON]
    - PostgreSQL builds waits-for graph (WFG): nodes are transactions,
      edges indicate "waiting for"
    - Deadlock detection runs when transaction waits > deadlock_timeout
    - If cycle detected in WFG: choose one transaction to abort.
      Choice based on: transaction that did least work (fewest WAL
      bytes, smallest cost), or transaction with deadlock_timeout
      configuration, or random if tied
    - pg_stat_database.deadlocks counter increments

  TASK 9.D3: Advisory Locks [OP] [DES]
    - Application-managed locks: pg_advisory_lock(key). Not tied to
      database objects. Application defines meaning
    - Use cases: distributed coordination, ensuring only one process
      runs a batch job, application-level mutex
    - Session-level vs transaction-level: session locks persist until
      released or session ends. Transaction locks released at COMMIT
    - Monitoring: pg_locks WHERE locktype='advisory' shows advisory
      locks. No built-in introspection for what they mean

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 9:
    - Orphaned prepared transaction holds locks forever
    - Lock wait timeout on critical application query (lock_timeout too short)
    - Advisory lock leak (session holds lock then idle forever)
    - Recovery conflict storm on standby (many queries cancelled)
    - FK check deadlock: concurrent inserts to parent/child tables

MODULE 10: STATISTICS, ANALYZE & PLANNER INTELLIGENCE
================================================================================
PREREQUISITES: Module 8 (query planning), Module 9 (locking for ANALYZE)
PURPOSE: The planner is only as good as its statistics. Understanding how
  statistics are collected, stored, and used is essential for plan diagnosis.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 10.1: Statistics Collection — ANALYZE [CON] [OP]
  - ANALYZE: samples random pages from table, estimates statistics from sample.
    Does not lock table (ShareUpdateExclusiveLock). Can run concurrently
  - ANALYZE table(column1, column2): analyze only specific columns
  - default_statistics_target (default 100): controls sample size. Higher =
    larger sample = more accurate statistics = slower ANALYZE
  - Per-column statistics target: ALTER TABLE t ALTER COLUMN c
    SET STATISTICS N; overrides default_statistics_target for that column.
    Useful for columns with skewed distributions or used in complex WHERE
  - How sample size is calculated: 300 × default_statistics_target rows.
    For target=100: 30,000 rows sampled (regardless of table size)

TASK 10.2: What Statistics Are Stored [CON] [OP]
  - pg_statistic: raw statistics data. Complex format (anyarray, anyarray
    for most-common-values, histogram). Most users query pg_stats instead
  - pg_stats: human-readable view. Key columns:
    - null_frac: fraction of NULLs in column
    - avg_width: average width of column values in bytes
    - n_distinct: number of distinct values. If positive: exact count.
      If negative: fraction of rows that are distinct (e.g., -0.5 means
      about 50% distinct). Large negative = high cardinality
    - most_common_vals: array of most frequent values (up to
      default_statistics_target entries)
    - most_common_freqs: corresponding frequency for each MCV
    - histogram_bounds: array of bucket boundaries dividing the
      remaining (non-MCV, non-NULL) values into equal-frequency buckets.
      Used for range selectivity
    - correlation: -1 to 1. Statistical correlation between physical
      row ordering and logical value ordering. High correlation (>0.5
      or <-0.5) means BRIN or index on this column likely efficient

TASK 10.3: How Planner Uses Statistics [CON]
  - Equality predicate (WHERE col = value): check MCV list.
    If value in MCV: selectivity = corresponding frequency.
    If not in MCV: selectivity = (1 - sum(mcv_freqs) - null_frac) /
      (n_distinct - count(MCV entries)). Assumes remaining values
      evenly distributed
  - Range predicate (WHERE col > value): use histogram.
    Find bucket containing value. Linearly interpolate position
    within bucket. Selectivity = fraction of histogram above value
  - Multiple predicates (WHERE a = X AND b = Y): planner multiplies
    individual selectivities (assumes column independence). This is
    a major source of mis-estimation
  - Join cardinality: estimated as (rows(A) × rows(B) × join_selectivity).
    Join selectivity from: most_common_vals overlap (if MCV available),
    or 1/max(n_distinct(a), n_distinct(b)) (rough estimate)

TASK 10.4: When ANALYZE Runs [MON]
  - Autovacuum-triggered autoanalyze: when n_mod_since_analyze >
    autovacuum_analyze_threshold + autovacuum_analyze_scale_factor ×
    n_live_tup. For default: 50 + 0.1 × rows. 1M rows: 100050 modifications
  - Manual ANALYZE: any time. Run after bulk load, after massive DELETE,
    after major UPDATE, after CREATE INDEX, during maintenance windows
  - pg_stat_user_tables: last_analyze, last_autoanalyze, analyze_count,
    autoanalyze_count, n_mod_since_analyze (estimated modifications since
    last ANALYZE)

COMMON FAILURES FOR MODULE 10:
────────────────────────────────────────────────────────────────

FAILURE 10.F1: Stale Statistics After Bulk Load
  Symptoms: Query that should use index does seq scan. EXPLAIN shows
    estimated rows=1 (or very low) but actual rows=massive
  Root cause: ANALYZE never ran after data load. Planner thinks table
    is empty or tiny
  Diagnosis: pg_stat_user_tables shows last_analyze is old (before load).
    n_live_tup shows new row count but statistics still old
  Recovery: ANALYZE table;. Verify plan improvement

FAILURE 10.F2: Planner Mis-Estimation from Column Correlation
  Symptoms: EXPLAIN estimates rows=100 but actual rows=100000.
    Multiple predicates in WHERE clause
  Root cause: Planner assumes column independence. WHERE city='NYC'
    selects 10% rows, WHERE state='NY' selects 10% rows. Planner
    estimates 1% (0.1 × 0.1). But these columns are correlated:
    almost all rows with city='NYC' also have state='NY'. Actual
    selectivity is ~10%, not 1%
  Diagnosis: Compare individual predicate selectivity with combined.
    If combined estimate = product of individuals but actual is
    much larger: correlation
  Recovery: CREATE STATISTICS ON city, state FROM table;
    Then ANALYZE. Extended statistics captures multi-column
    dependencies and MCV combinations

FAILURE 10.F3: Statistics Target Too Low for Skewed Column
  Symptoms: Queries on specific values slow, others fast.
    EXPLAIN shows good estimate for common values but bad for rare
  Root cause: default_statistics_target=100 may not capture full
    distribution for columns with many distinct values or extreme skew
  Diagnosis: Check pg_stats.most_common_vals for the column.
    If the value you're querying is not in MCV and not in histogram
    (too rare), planner assumes uniform distribution
  Recovery: ALTER TABLE t ALTER COLUMN c SET STATISTICS 1000;
    ANALYZE t; More statistics = larger MCV + finer histogram =
    better estimates for rare values

FAILURE 10.F4: ANALYZE Never Runs on Certain Tables
  Symptoms: last_analyze extremely old, autoanalyze_count=0
  Root cause: autovacuum_analyze_scale_factor too high for large
    table, or autovacuum disabled, or analyze threshold never reached
    because modifications are steady but low
  Diagnosis: check autovacuum settings on table. Check n_mod_since_analyze
    vs threshold
  Recovery: Manual ANALYZE. Reduce autovacuum_analyze_scale_factor
    for large tables. Schedule periodic ANALYZE via pg_cron

LAYER 2: CONNECTED (after Modules 7-8)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 10.X1: Statistics → Index Design
    - Statistics help identify: which columns are selective (good for
      indexes), which have skewed distribution (partial indexes on
      common values), which are correlated (extended statistics needed)
    - n_distinct value guides: unique columns = good primary key.
      Low n_distinct = index may not be selective enough for planner
      to choose it
    - correlation value: if close to 1, BRIN index is a candidate.
      If close to 0 (random), B-tree needed

  CROSS-TOPIC TASK 10.X2: Statistics → Partitioning
    - Partition pruning relies on n_distinct and constraints.
    - ANALYZE on parent table estimates partition sizes
    - Partition-level statistics: each partition has own pg_statistic
      entries. Planner uses partition-level stats for partition-wise
      operations

  CROSS-TOPIC TASK 10.X3: Statistics → Vacuum/ANALYZE Timing
    - VACUUM updates n_live_tup and n_dead_tup estimates in
      pg_stat_user_tables. These are used by autovacuum to decide
      when to vacuum and analyze
    - ANALYZE updates pg_statistic. These are used by planner
    - Both are needed: vacuum for bloat control, analyze for
      plan quality

  COMBINED FAILURE 10.XF1: Stale Statistics + Missing Index →
    Planner Disaster
    - Table loaded with 100M rows overnight. No ANALYZE after load
    - Planner thinks table has 1000 rows (from last ANALYZE at tiny size)
    - Query with WHERE indexed_col = X: planner thinks very few rows,
      chooses nested loop with small inner. Actual: 10M rows match
    - Nested loop executes 10M times. Query takes hours
    - Diagnosis: last_analyze timestamp, EXPLAIN ANALYZE shows massive
      actual/estimated mismatch
    - Recovery: ANALYZE table immediately. Plan may still be bad if
      new statistics reveal need for different index.
      Create appropriate index

LAYER 3: DEEP
────────────────────────────────────────────────────────────────

  TASK 10.D1: Extended Statistics Deep Dive [CON] [DES]
    - Types:
      - dependencies: tracks "column A determines column B" (functional
        dependency). Improves selectivity estimates for correlated predicates
      - ndistinct: tracks number of distinct value combinations across
        multiple columns. Improves group-by and join estimates
      - mcv: multi-column most-common-values. Improves equality estimates
        for value combinations
    - CREATE STATISTICS syntax and options
    - How to determine if extended statistics are needed: EXPLAIN ANALYZE
      shows mis-estimation with multiple predicates. Compare estimated
      rows with actual
    - Cost: extended statistics increase ANALYZE time and pg_statistic
      size. Use only for problematic column combinations

  TASK 10.D2: Statistics Internals [CON]
    - pg_statistic storage: per-column, per-table. Stored in pg_statistic
      catalog table (which itself gets analyzed and vacuumed)
    - ANALYZE implementation: picks random pages using
      ANALYZE's sampling algorithm. Each tuple on sampled page is read.
      Builds: MCV (frequency counting), histogram (sorted values),
      correlation (comparing physical order to value order)
    - Statistics invalidation: when table modified, statistics become
      "stale" but still used. At next ANALYZE, refreshed
    - Table-level stats in pg_class: relpages and reltuples are
      approximate (updated by VACUUM and ANALYZE). These inform
      planner's baseline row count estimates

  TASK 10.D3: Manual Statistics Tuning [DES]
    - Increase default_statistics_target globally: pros (better plans),
      cons (longer ANALYZE times, larger pg_statistic)
    - Per-column statistics: target specific columns used in WHERE/
      JOIN clauses
    - expression statistics (PG14+): CREATE STATISTICS on expressions
    - Statistics for functional indexes: expression index has its own
      statistics on the expression result

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 10:
    - ANALYZE sampling bias: bad random page selection leads to
      non-representative sample. Very rare. Rerun ANALYZE
    - pg_statistic bloat: frequent DDL (CREATE/DROP temp tables)
      causes dead rows in pg_statistic. Catalog tables need vacuum too
    - Expression index statistics missing: planner can't estimate
      expression selectivity without expression statistics (PG14+)

MODULE 11: PARTITIONING & DATA LIFECYCLE
================================================================================
PREREQUISITES: Module 5 (vacuum), Module 8 (query planning)
PURPOSE: Partitioning is the primary strategy for managing large tables.
  It improves query performance (partition pruning), vacuum performance
  (smaller per-partition vacuums), and data lifecycle (easy data removal).

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 11.1: Partitioning Concepts [CON]
  - What partitioning solves:
    1. Query performance: partition pruning eliminates partitions
       not matching WHERE conditions
    2. Maintenance: vacuum each partition independently (smaller).
       REINDEX each partition. Drop/archive old partitions instantly
    3. Data lifecycle: DETACH old partitions, ATTACH new partitions.
       DROP PARTITION is instant (no DELETE scan)
  - Partition types:
    RANGE: rows assigned to partitions based on range of key values.
      Use: time-series (by date), sequential IDs
    LIST: rows assigned based on discrete key values. Use: region,
      tenant, status
    HASH: rows assigned by hash of key. Use: even distribution across
      partitions, no logical grouping
  - Declarative partitioning (PG10+): CREATE TABLE ... PARTITION BY
    RANGE (col). CREATE TABLE ... PARTITION OF parent FOR VALUES FROM (...)
    TO (...). PostgreSQL manages routing
  - Inheritance-based (legacy): pre-PG10 method. CHECK constraints.
    Manual routing via triggers. Still used for some edge cases
  - Partition key: column(s) used to determine partition assignment.
    Must be part of primary key if primary key exists
  - Default partition: catches rows not matching any existing partition.
    Useful during partition management. But: default partition can
    accumulate data if new partitions not created

TASK 11.2: Partition Pruning [CON] [OP]
  - Plan-time pruning: planner eliminates partitions at plan time
    when WHERE conditions match partition boundaries. EXPLAIN shows
    only scanned partitions
  - Run-time pruning (PG11+): planner may not know exact values at
    plan time (e.g., prepared statement parameters). Executor prunes
    partitions at execution time. EXPLAIN ANALYZE shows:
    "Subplans Removed: N"
  - Pruning requirements: WHERE condition must reference partition
    key. Comparison operator must be recognized (=, <, >, BETWEEN, IN).
    No function wrapping on partition key
  - Test pruning: EXPLAIN SELECT * FROM partitioned_table WHERE
    partition_key = X; Check which partitions are scanned

TASK 11.3: Partition Management [OP]
  - Creating partitions: CREATE TABLE ... PARTITION OF parent
    FOR VALUES FROM (date1) TO (date2)
  - Detaching partitions: ALTER TABLE parent DETACH PARTITION child.
    Partition becomes independent table. No data movement. Instant
  - Attaching partitions: ALTER TABLE parent ATTACH PARTITION child
    FOR VALUES FROM (...) TO (...). May require validation if
    partition already has data outside range (CHECK constraint
    may be validated, but avoid with proper setup)
  - Dropping partitions: DROP TABLE child. Instant (no DELETE needed)
  - Archival pattern: DETACH old partition → rename → export →
    store elsewhere. OR: DETACH → attach to archive table

TASK 11.4: Indexing and Constraints on Partitions [CON] [OP]
  - Indexes are per-partition: CREATE INDEX on parent creates index
    on each partition individually. Not a "global index"
  - Unique constraints must include partition key: if table is
    partitioned by date, primary key must include date column.
    Cannot enforce global uniqueness without partition key
  - Foreign keys referencing partitioned table: supported (PG12+)
  - Foreign keys from partitioned table: supported (PG12+)

COMMON FAILURES FOR MODULE 11:
────────────────────────────────────────────────────────────────

FAILURE 11.F1: Partition Pruning Not Working
  Symptoms: EXPLAIN shows all partitions scanned despite WHERE on
    partition key. Query slow
  Root cause: function wrapped around partition key in WHERE clause
    (WHERE date(created_at) = '2024-01-01' instead of
    WHERE created_at >= '2024-01-01' AND created_at < '2024-01-02').
    Or data type mismatch causing implicit cast
  Diagnosis: EXPLAIN shows all partitions. Check WHERE clause for
    function calls on partition key
  Recovery: Rewrite query to avoid function wrapping on partition key.
    Use range conditions

FAILURE 11.F2: Partition Explosion
  Symptoms: thousands of partitions, planning time slow, system
    catalog queries slow
  Root cause: over-partitioning (daily partitions for 10-year
    history = 3650 partitions). Or too-fine granularity (hourly
    partitions)
  Diagnosis: SELECT count(*) FROM pg_class WHERE relkind='r' AND
    relispartition; Count partitions. Query planning time increased
  Recovery: consolidate partitions (merge monthly instead of daily).
    Drop or archive old partitions. General guideline: keep
    total partitions under a few thousand

FAILURE 11.F3: Data Leakage to Default Partition
  Symptoms: default partition growing large, queries on specific
    partitions return fewer rows than expected
  Root cause: new partitions not created in time. Rows with values
    not matching any defined partition silently go to default
  Diagnosis: pg_stat_user_tables on default partition shows
    rows > 0. Check expected partition boundaries vs actual
  Recovery: create missing partitions. Move rows from default
    to correct partitions. Then DETACH default (or leave as is).
    Prevention: pg_partman or cron job to create future partitions

FAILURE 11.F4: FK Validation Lock on Partition Attach
  Symptoms: ALTER TABLE parent ATTACH PARTITION takes long time,
    holds AccessExclusiveLock on parent, blocks queries
  Root cause: partition being attached has data, PostgreSQL must
    validate CHECK constraint (that all rows fit partition bounds).
    Similar to ATTACH with NOT VALID
  Diagnosis: pg_stat_activity shows ATTACH PARTITION with lock wait
  Recovery: ensure partition is empty or data is within bounds
    before attaching. Or use ATTACH with NOT VALID (if available
    for partition bounds)

LAYER 2: CONNECTED (after Modules 5, 7)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 11.X1: Partitioning → Vacuum
    - Each partition is independent relation for vacuum purposes
    - Autovacuum vacuums each partition independently
    - Advantage: vacuum on old partition (read-only, no dead tuples)
      completes instantly. Vacuum on active partition (today's data)
      vacuums small table
    - Without partitioning: one massive table, vacuum takes hours

  CROSS-TOPIC TASK 11.X2: Partitioning → Indexes
    - Indexes are per-partition. REINDEX on one partition is small
      and fast. REINDEX on massive unpartitioned table is huge
    - If query always filters by partition key, can create different
      indexes on different partitions (e.g., old data gets minimal
      indexes, recent data gets many indexes)

  CROSS-TOPIC TASK 11.X3: Partitioning → Query Planning
    - Query planning time scales with partition count (planner
      must evaluate each partition initially). With thousands of
      partitions, planning time increases
    - Partition-wise joins (PG11+) and partition-wise aggregates
      (PG11+): if two partitioned tables joined on same partition
      key, planner can join matching partition pairs directly
    - enable_partitionwise_join, enable_partitionwise_aggregate
      settings control this behavior

  COMBINED FAILURE 11.XF1: Unpartitioned Table Grows Beyond Manageable Size
    - Table: 2TB, 5 years of data, 50 indexes
    - Vacuum takes 3 days (mostly index vacuum phase: 50 indexes)
    - REINDEX impossible (downtime too long)
    - Queries on recent data scan all 2TB (no partition pruning)
    - Solution: partition by date (postgres_fdw migration or
      logical replication to new partitioned table)
    - Lesson: partition BEFORE table becomes unmanageable

LAYER 3: DEEP
────────────────────────────────────────────────────────────────

  TASK 11.D1: Partitioning Implementation Strategies [DES]
    - Greenfield: design table as partitioned from start
    - Brownfield: convert existing table to partitioned:
      Option A: CREATE new partitioned table, INSERT INTO ... SELECT
        FROM old, rename tables. Downtime: full copy time
      Option B: Logical replication from old to new partitioned table.
        Minimal downtime: switch application after sync complete
      Option C: pg_repack cannot repartition. Not applicable
    - Partition key selection: choose column always present in WHERE
      clause and JOIN conditions. Time for time-series. Tenant ID
      for multi-tenant

  TASK 11.D2: pg_partman (Partition Manager Extension) [OP] [AUT]
    - Automates creation of new partitions (premake = N future
      partitions)
    - Automates dropping/detaching old partitions (retention policy)
    - Handles time-based and ID-based partitioning
    - run_maintenance() called by pg_cron or external cron
    - Configuration: partman schema, template tables, retention
      settings

  TASK 11.D3: Sub-Partitioning [DES]
    - Partition of a partitioned table: two-level partitioning
      (e.g., partition by date, sub-partition by tenant_id)
    - Tradeoffs: more partitions, more management complexity,
      but finer pruning and parallelism
    - Use case: very large multi-tenant time-series

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 11:
    - Partition bound overlap: two partitions with overlapping ranges.
      INSERT fails. Fix: fix partition bounds
    - Row movement failure: UPDATE changes partition key (row must
      move to different partition). Requires row movement enabled
    - Sequence on partitioned table: sequences are per-parent, not
      per-partition. Can cause unexpected behavior
    - UPDATE on partition key without row_movement=on: fails

  CHAOS CARD 11.C1: Stop creating new partitions. Observe data leaking

  CHAOS CARD 11.C2: Create 2000 partitions. Measure query planning

  CHAOS CARD 11.C3: Run query that should prune partitions, but with

MODULE 12: STREAMING REPLICATION ARCHITECTURE
================================================================================
PREREQUISITES: Module 6 (WAL)
PURPOSE: Streaming replication is the foundation of high availability,
  read scaling, and disaster recovery in PostgreSQL.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 12.1: Streaming Replication Concepts [CON]
  - Architecture: Primary generates WAL → WAL sender process on primary
    reads WAL → sends over TCP connection → WAL receiver process on
    standby writes WAL → standby replays WAL (applies to data files)
  - Standby states: startup (reading initial WAL), catchup (processing
    WAL from archive), streaming (real-time applying), recovery
    (applying WAL before promotion)
  - Primary: accepts reads and writes. Generates WAL. Serves WAL to
    standbys via WAL sender processes
  - Hot standby: standby that accepts read-only queries while in
    recovery mode. hot_standby=on (default PG14+)
  - Warm standby: standby that applies WAL but does not accept queries.
    Older concept, less common now
  - Synchronous vs asynchronous replication:
    - Async: primary doesn't wait for standby to confirm WAL receipt.
      Fast writes, potential data loss on primary crash (unreplicated
      WAL lost)
    - Sync: primary waits for standby to confirm WAL is flushed to
      disk before committing transaction. Zero data loss on primary
      crash. Primary hangs if sync standby unavailable (unless
      synchronous_commit adjusted)

TASK 12.2: Setting Up Streaming Replication [OP]
  - Prerequisites: wal_level = replica (or logical). archive_mode
    optional but recommended for PITR. max_wal_senders >= number
    of standbys + 1 (for base backup)
  - On primary: create replication user with REPLICATION privilege.
    pg_hba.conf must allow replication connections from standby IP
  - On standby: pg_basebackup from primary to create initial data
    directory. Creates standby.signal file (PG12+, or recovery.conf
    in older versions). Configure primary_conninfo with connection
    details
  - Standby.signal: empty file. Presence tells PostgreSQL to start
    in recovery mode. PostgreSQL looks for WAL sources: streaming
    (primary_conninfo), archive (restore_command), pg_wal directory
  - Primary_conninfo: host, port, user, password, application_name
    (used as slot name if using replication slots)
  - Start standby: pg_ctl start. Standby begins recovery. Connects
    to primary via WAL receiver. Applies WAL as it arrives

TASK 12.3: Replication Monitoring [MON] [DIAG]
  - On primary (pg_stat_replication):
    application_name: standby identifier
    state: streaming (normal), catchup (applying archive), backup
      (during base backup), startup (initializing)
    sent_lsn: WAL position sent to standby
    write_lsn: WAL position standby has written to disk (OS buffer,
      not yet fsynced)
    flush_lsn: WAL position standby has flushed to disk (fsynced)
    replay_lsn: WAL position standby has applied to data files
    write_lag: time between WAL being sent and written on standby
    flush_lag: time between sent and flushed
    replay_lag: time between sent and replayed
    sync_state: async, sync, potential, quorum
  - On standby (pg_stat_wal_receiver):
    status: streaming, connecting, stopped
    conninfo: connection string used
    last_msg_send_time, last_msg_receipt_time: connection health
    latest_end_lsn: last WAL position received
    latest_end_time: timestamp of last received WAL

TASK 12.4: Replication Lag Understanding [CON] [DIAG]
  - Write lag: standby has received WAL but not yet written to disk
    (in OS buffer). Indicates slow disk on standby
  - Flush lag: WAL written but not flushed to disk. Indicates
    wal_sync_method slow or disk issue
  - Replay lag: WAL received but not applied to data files. Indicates
    standby CPU/IO can't keep up with WAL application rate
  - Common causes: standby hardware slower than primary, heavy read
    queries on standby slowing recovery, network bandwidth saturated,
    large WAL records (e.g., bulk load) causing replay spike
  - Monitoring: alert on replay_lag > threshold (e.g., 30 seconds)

COMMON FAILURES FOR MODULE 12:
────────────────────────────────────────────────────────────────

FAILURE 12.F1: Replication Disconnect
  Symptoms: pg_stat_replication shows state='' (empty, not streaming)
    or missing entry. pg_stat_wal_receiver shows connecting or stopped
  Root causes: network interruption, firewall change, pg_hba.conf
    changed on primary (replication entry removed), replication user
    password changed/expired, primary restarted and max_wal_senders
    capacity exceeded, standby SSL certificate expired
  Diagnosis: On standby: check pg_stat_wal_receiver status and
    conninfo. Test network connectivity (ping, telnet to port).
    Check PostgreSQL logs for "could not connect to the primary server"
  Recovery: Fix network/firewall. Update pg_hba.conf on primary and
    reload. Fix replication user credentials. Ensure max_wal_senders
    sufficient. Restart standby if needed

FAILURE 12.F2: Replication Lag Spike
  Symptoms: replay_lag in pg_stat_replication growing > 5 minutes,
    application reading from standby sees stale data
  Root causes: large write transaction on primary (millions of rows
    updated), standby hardware slower than primary (disk I/O),
    long-running query on standby causing recovery to wait (recovery
    conflict), network bandwidth saturated (if WAL volume exceeds
    bandwidth), checkpoint on standby causing replay pause
  Diagnosis: pg_stat_replication replay_lag value. Check standby
    system metrics (CPU, I/O). Check pg_stat_activity on standby
    for long queries
  Recovery: If large WAL volume from bulk operation: wait (will
    catch up). If hardware: upgrade standby. If network: upgrade
    bandwidth. If long query on standby: terminate or wait

FAILURE 12.F3: Standby Cannot Reconnect — WAL Missing
  Symptoms: standby starts, connects, then fails: "requested WAL
    segment X has already been removed"
  Root cause: standby disconnected for longer than primary retained
    WAL. Primary recycled/removed WAL segments the standby needs
    to catch up. WAL retention limited by: wal_keep_size,
    replication slots (not used or failing), archive
  Diagnosis: Check pg_wal on primary for the requested segment.
    Check wal_keep_size setting. Check if replication slot exists
    and is active
  Recovery: Rebuild standby from fresh pg_basebackup. Prevention:
    use replication slots (primary retains WAL needed by each
    slot). Or increase wal_keep_size. Or ensure WAL archive
    provides fallback if WAL gone from pg_wal

FAILURE 12.F4: Synchronous Replication Hang
  Symptoms: All write transactions on primary hang. pg_stat_activity
    shows many processes with wait_event_type='IPC', wait_event='SyncRep'
  Root cause: synchronous_commit=on (or remote_apply) with
    synchronous_standby_names configured, but sync standby(s)
    disconnected or crashed. Primary blocks all commits waiting
    for synchronous acknowledgment
  Diagnosis: pg_stat_replication shows no entry with
    sync_state='sync'. Check standby status
  Recovery: temporarily set synchronous_commit=local on primary to
    unblock writes (accepts data loss risk). Fix standby. Or
    change synchronous_standby_names to use ANY instead of FIRST
    (quorum), or reduce required sync standbys
  Prevention: use ANY N (synchronous_standby_names = 'ANY 1 (s1, s2)')
    so one standby being down doesn't block commits

FAILURE 12.F5: Recovery Conflict on Standby
  Symptoms: "ERROR: canceling statement due to conflict with recovery"
    on standby queries
  Root cause: WAL replay on standby needs to modify or remove data
    that a standby query is reading. Conflicts: (1) AccessExclusiveLock
    from DDL on primary. (2) Buffer pin conflict (page cleanup).
    (3) Snapshot conflict (vacuum removed row from primary that
    standby query needs)
  Diagnosis: standby log shows "canceled statement due to conflict".
    Check max_standby_streaming_delay setting
  Recovery: Application must retry cancelled queries. Increase
    max_standby_streaming_delay (WAL replay waits for query to
    finish). Set hot_standby_feedback=on (prevents vacuum from
    removing rows standby might need). Trade-off: hot_standby_feedback
    can cause primary bloat
  Prevention: long queries on standby should use hot_standby_feedback.
    Or isolate reporting queries to dedicated standby with
    max_standby_streaming_delay = -1

LAYER 2: CONNECTED (after Modules 14-15)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 12.X1: Replication → Backup
    - Backup from standby: reduces load on primary during
      pg_basebackup. Use --write-recovery-conf to create standby
      configuration automatically
    - Replication slots ensure WAL retained for backup duration
      when using pg_basebackup with --wal-method=stream

  CROSS-TOPIC TASK 12.X2: Replication → High Availability
    - Streaming replication is the transport layer for HA
    - Patroni uses streaming replication + WAL archiving for
      cluster synchronization
    - Failover: promote standby to primary via pg_ctl promote
      or pg_promote()

  CROSS-TOPIC TASK 12.X3: Replication → Vacuum (Hot Standby Feedback)
    - hot_standby_feedback: standby sends its oldest query snapshot
      (backend_xmin) to primary. Primary's vacuum cannot remove
      dead tuples that standby might need
    - Without feedback: vacuum on primary can remove tuples → standby
      query gets recovery conflict → query cancelled
    - Trade-off: feedback prevents standby query cancellation but
      can cause primary table bloat

  COMBINED FAILURE 12.XF1: Primary Crash + Standby Not Up-to-Date
    - Primary crashes (hardware failure)
    - Standby is 30 seconds behind (replay_lag)
    - 30 seconds of committed transactions exist in WAL on primary disk
    - If primary disk unrecoverable: those transactions lost
    - If primary disk recoverable: can recover WAL from primary disk,
      apply to standby, then promote → zero data loss
    - If primary disk gone: data loss = transactions in unreplicated WAL
    - Prevention: synchronous replication for zero data loss tolerance.
      Or accept async's minor data loss risk

LAYER 3: DEEP (after Module 15)
────────────────────────────────────────────────────────────────

  TASK 12.D1: Replication Slots Deep Dive [CON]
    - Physical replication slot: created on primary.
      pg_create_physical_replication_slot('slot_name')
      Standby connects with primary_slot_name = 'slot_name'
    - Slot guarantees: primary retains WAL from slot's restart_lsn
      until standby confirms it has been flushed (flush_lsn advances).
      Prevents WAL removal before standby consumes it
    - Inactive slot: standby disconnected, slot retains WAL.
      pg_wal fills. Danger! Monitor pg_replication_slots.active
    - wal_status: 'reserved' (WAL within max_wal_size, safe),
      'extended' (WAL retained beyond max_wal_size, filling pg_wal),
      'lost' (WAL needed by slot has been removed — standby must
      rebuild from backup)
    - max_slot_wal_keep_size (PG13+): if WAL retention for slot
      exceeds this, slot invalidated (wal_status='lost'). Prevents
      pg_wal from filling from abandoned slot

  TASK 12.D2: Cascading Replication [DES]
    - Standby can stream WAL to another standby (cascading)
    - Primary → Standby A → Standby B
    - Reduces load on primary (only serves WAL to direct standbys)
    - Fan-out: primary serves 5 standbys, each of those serve 5
      more = 30 standbys from one primary
    - Failure: if Standby A fails, Standby B orphans. Must
      reconnect to different upstream or rebuild

  TASK 12.D3: Timeline Management [CON]
    - Each time standby is promoted, new timeline created.
      Timeline number increments (1, 2, 3, ...)
    - PITR also creates new timeline
    - Old standbys must switch to new timeline after failover
    - pg_rewind: rewinds old primary to match new primary's
      timeline. Requires wal_log_hints=on or data checksums

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 12:
    - Replication slot accumulating WAL (standby detached)
    - Network fluctuation causing repeated connect/disconnect
    - max_wal_senders exhausted (too many standbys)
    - WAL receiver process crashes (standby restart needed)
    - pg_hba.conf missing replication entry after config change

MODULE 13: LOGICAL REPLICATION & ETL PATTERNS
================================================================================
PREREQUISITES: Module 12
PURPOSE: Logical replication replicates data changes at the row level,
  enabling selective replication, cross-version upgrades, and real-time
  ETL without physical WAL coupling.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 13.1: Logical Replication Concepts [CON]
  - Difference from streaming replication: streaming replicates WAL
    bytes (physical, block-level, entire cluster). Logical replicates
    row changes (logical, row-level, selective per table/publication)
  - Architecture: Publisher (primary) has publication (set of tables).
    WAL records decoded by logical decoding plugin → logical changes
    sent to subscriber → subscriber applies changes as SQL
  - Use cases: selective replication (replicate only some tables),
    cross-version upgrade (PG14→PG16), data warehousing (replicate
    OLTP to analytics), multi-master with conflict resolution,
    data distribution/sharding
  - Publication: defines which tables and operations (INSERT, UPDATE,
    DELETE, TRUNCATE) are replicated. Row filters (PG15+) and column
    lists (PG15+) for selective replication
  - Subscription: connects to publisher, receives changes, applies to
    local tables. Can specify copy_data=true (initial table sync)
  - WAL level must be logical. Each publication creates a logical
    replication slot on publisher

TASK 13.2: Setting Up Logical Replication [OP]
  - On publisher: wal_level = logical. Create user with REPLICATION
    privilege + write access to published tables. pg_hba.conf must
    allow replication connections
  - Create publication: specifying tables, operations
  - On subscriber: create table structure (schema must match published
    table). Create subscription with connection string, publication
    name, and slot options
  - Subscription creates: logical replication slot on publisher,
    logical replication worker on subscriber, optional initial
    table copy (copy_data)
  - Multiple subscriptions per subscriber. Multiple subscribers per
    publication. Many-to-many architecture possible

TASK 13.3: Logical Replication Monitoring [MON] [DIAG]
  - On publisher (pg_stat_replication): shows logical WAL sender.
    pg_replication_slots: slot_type='logical', active, restart_lsn
  - On subscriber (pg_stat_subscription): subscription name, PID of
    worker, received_lsn (WAL position received from publisher),
    latest_end_lsn (last WAL applied), latest_end_time, last_msg_send_time,
    last_msg_receipt_time, last_error (if any)
  - On subscriber (pg_stat_subscription_stats — PG15+): error count,
    number of times subscription applied changes
  - Monitor lag: compare publisher's pg_current_wal_lsn with
    subscriber's latest_end_lsn

TASK 13.4: Logical Replication Limitations [CON]
  - DDL is NOT replicated. CREATE TABLE, ALTER TABLE must be applied
    manually on subscriber (or via application migration tool)
  - Sequences are NOT replicated. Sequence values on subscriber may
    diverge. Must sync sequences separately (or use UUID primary keys)
  - Large objects (lo_*) are NOT replicated
  - Replication identity: each published table needs a way to identify
    which row to update/delete on subscriber. Options: PRIMARY KEY
    (default), UNIQUE index, or FULL (entire row as key — slow)
  - Schema changes on publisher: must be manually replicated to
    subscriber with matching column counts and types

COMMON FAILURES FOR MODULE 13:
────────────────────────────────────────────────────────────────

FAILURE 13.F1: Subscription Worker Error — Table Does Not Exist
  Symptoms: pg_stat_subscription shows error: "relation X does not exist"
  Root cause: table created on publisher but not on subscriber, or
    table name/schema differs
  Diagnosis: pg_stat_subscription last_error field. Check subscriber
    table existence and schema
  Recovery: Create table on subscriber with matching structure.
    ALTER SUBSCRIPTION ... REFRESH PUBLICATION to pick up new tables

FAILURE 13.F2: Replication Identity Missing
  Symptoms: subscriber error: "cannot replicate UPDATE/DELETE for
    table X without primary key"
  Root cause: published table has no PRIMARY KEY and no REPLICA IDENTITY
    set. Logical replication needs to identify which row to update/delete
  Diagnosis: subscriber pg_stat_subscription error. On publisher:
    \d+ tablename — check primary key
  Recovery: Add primary key to table. Or ALTER TABLE t REPLICA IDENTITY
    FULL (uses entire row as key — slow, scans all columns). Or create
    UNIQUE index

FAILURE 13.F3: Logical Replication Slot Fills pg_wal
  Symptoms: pg_wal directory growing, pg_replication_slots shows
    slot_type='logical', active=false or restart_lsn not advancing
  Root cause: subscriber disconnected or subscription worker stuck.
    Slot retains WAL from restart_lsn onward. Similar to streaming
    replication slot but more dangerous (logical slots can have
    replication identity)
  Diagnosis: pg_stat_subscription shows worker PID (NULL = not running),
    last_error. Check subscriber connectivity
  Recovery: Fix subscriber issue. If subscriber permanently gone:
    DROP SUBSCRIPTION on subscriber, then drop replication slot
    on publisher

FAILURE 13.F4: Unique Constraint Violation on Subscriber
  Symptoms: subscriber error: "duplicate key value violates unique
    constraint"
  Root cause: data already exists on subscriber (inserted outside
    replication, or conflict from two-way replication), then
    publisher sends same key value
  Diagnosis: pg_stat_subscription last_error
  Recovery: Manually resolve conflict (delete duplicate on subscriber,
    update subscriber row). Then ALTER SUBSCRIPTION ... REFRESH
    PUBLICATION or skip the conflicting transaction (advanced)

LAYER 2: CONNECTED (after Modules 14, 23)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 13.X1: Logical Replication → Upgrade
    - Major version upgrade with near-zero downtime: set up logical
      replication from old PG version to new PG version. Sync data.
      Switch application to new database. Minimal cutover time
    - Limitation: sequences must be manually synced at cutover.
      No DDL replication

  CROSS-TOPIC TASK 13.X2: Logical Replication → Backup
    - Logical slots are dropped during pg_restore unless handled.
      After pg_basebackup restore, logical slots must be recreated
    - Backup procedures must account for logical replication state

  CROSS-TOPIC TASK 13.X3: Logical Replication → Partitioning
    - Publication can include partitioned table (PG13+). All
      partitions automatically included
    - Row filters (PG15+) per-partition for finer control

  COMBINED FAILURE 13.XF1: Subscriber Down → Publisher WAL Accumulation
    - Subscriber goes down for maintenance (planned 4 hours)
    - Logical replication slot on publisher holds WAL
    - pg_wal grows, fills disk
    - Diagnosis: pg_replication_slots shows slot retaining WAL,
      pg_stat_subscription shows worker not running
    - Recovery: If subscriber will return soon: wait (ensure WAL
      disk has space). If subscriber permanently gone: drop slot.
      Prevention: max_slot_wal_keep_size with understanding that
      slot will be invalidated if exceeded

LAYER 3: DEEP
────────────────────────────────────────────────────────────────

  TASK 13.D1: Logical Decoding Internals [CON]
    - Logical decoding: reads WAL, reconstructs row-level changes
      from WAL records. Requires REPLICA IDENTITY or FULL to
      identify rows
    - Output plugin: transforms decoded changes into consumable format
      (pgoutput for built-in logical replication, test_decoding
      for debugging, wal2json for JSON output)
    - WAL logging: wal_level=logical writes additional WAL information
      needed for logical decoding. Slightly more WAL volume than
      wal_level=replica

  TASK 13.D2: Conflict Resolution Strategies [DES]
    - Two-way replication: both nodes publish and subscribe to each
      other. Row conflicts possible (same row updated on both sides)
    - Conflict resolution: PostgreSQL built-in doesn't resolve.
      Application must: use conflict-free data types (CRDT), use
      origin tracking (PG16+), or accept last-write-wins via
      application logic
    - Row filters for conflict avoidance: each node owns specific
      rows (by tenant_id, region), replication filtered accordingly

  TASK 13.D3: Logical Replication for ETL [DES]
    - Real-time ETL pipeline: OLTP PostgreSQL → logical replication →
      subscriber PostgreSQL (staging/warehouse). Transform data      on subscriber or via application
    - Use case: replicate from production to analytics database
    - Performance: consider subscriber write throughput. Apply
      parallelism via multiple subscriptions

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 13:
    - Subscriber out of sync after manual data change
    - WAL level change to logical requires restart
    - Publication/subscription name collision across environments
    - Initial data copy (copy_data=true) timeout on large tables

LAYER 4: CHAOS (ongoing, cumulative)

MODULE 14: BACKUP & RECOVERY ENGINEERING
================================================================================
PREREQUISITES: Module 6 (WAL), Module 12 (replication)
PURPOSE: Backups are the last line of defense against data loss. Recovery
  is the moment of truth. A DBA who hasn't tested restore doesn't have
  a backup.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 14.1: Backup Types and Tools [CON]
  - Logical backup: pg_dump (single database), pg_dumpall (all databases
    + globals). Outputs SQL text or custom format. Point-in-time
    recovery NOT possible. Used for: single database migration,
    schema-only backups, small databases, cross-version migration
  - Physical backup: pg_basebackup (full cluster snapshot). Copies
    entire PGDATA directory. Used as base for PITR. WAL must be
    archived separately for PITR capability
  - Backup tools comparison:
    pg_dump/pg_restore: logical, flexible, slow for large DBs
    pg_basebackup: physical, fast, full cluster only
    pgBackRest: physical, parallel, incremental, differential, PITR
    WAL-G: physical, cloud-native, S3/GCS/Azure, parallel
    Barman: physical, server-managed, streaming backup

TASK 14.2: Logical Backup (pg_dump) [OP]
  - pg_dump database > file: SQL plain text
  - pg_dump -Fc database -f file: compressed custom format (supports
    parallel restore, selective restore)
  - pg_dump -Fd database -f directory -j N: directory format with
    parallel dump (N workers)
  - Options: --schema-only, --data-only, -t table, -n schema,
    --exclude-table, --no-owner, --no-acl, --clean, --if-exists
  - pg_dumpall --globals-only: dump roles, tablespaces, databases list
  - Limitations: single transaction for consistency (may need
    --serializable-deferrable). Long-running dump may conflict.
    Does not include WAL for PITR

TASK 14.3: Physical Backup (pg_basebackup) [OP]
  - Full cluster backup: copies PGDATA including all databases,
    tablespaces, WAL (if streaming)
  - pg_basebackup -D backup_dir -Fp (plain directory) or -Ft (tar)
  - --wal-method=stream: WAL streamed during backup, backup is
    consistent without archive. --wal-method=fetch: WAL fetched
    from archive (must exist). --wal-method=none: rely on archive
    for WAL
  - --checkpoint=fast: force immediate checkpoint (faster start,
    more I/O)
  - --progress: show progress
  - --write-recovery-conf: auto-generate primary_conninfo for
    restoring as standby
  - Limitations: full cluster copy only. No incremental. No
    parallel restore from tar

TASK 14.4: Point-in-Time Recovery (PITR) Concepts [CON]
  - PITR requires: base backup + continuous WAL archive
  - Recovery targets: time (recovery_target_time), LSN
    (recovery_target_lsn), XID (recovery_target_xid),
    named restore point (recovery_target_name)
  - recovery_target_inclusive: include/exclude the exact target
    transaction
  - recovery_target_action: promote (become normal), pause
    (stay in recovery for checking), shutdown
  - restore_command: command to retrieve WAL from archive
  - Timeline: PITR creates new timeline (like standby promotion)

TASK 14.5: pg_restore and Recovery Testing [OP]
  - pg_restore from custom/directory format
  - pg_restore -j N: parallel restore
  - Selective restore: -t table, -n schema, -l (list contents)
  - Recovery testing: restore backup to separate instance.
    Verify database starts. Verify data integrity (row counts,
    sample queries). Run pg_verifybackup on physical backup
  - MUST practice: regularly test restore (monthly minimum).
    Untested backup = no backup

COMMON FAILURES FOR MODULE 14:
────────────────────────────────────────────────────────────────

FAILURE 14.F1: pg_dump Fails on Large Database
  Symptoms: pg_dump runs for hours then fails with error (connection
    lost, statement timeout, disk full)
  Root cause: dump duration exceeds statement_timeout, network
    timeout between pg_dump and server, destination disk fills,
    server restart during dump
  Diagnosis: check error message (timeout vs connection lost vs
    disk full). Check pg_stat_activity for dump session
  Recovery: Use parallel dump (-j) on directory format. Set
    statement_timeout=0 for dump session. Ensure destination disk
    space > database size. Use physical backup for very large DBs

FAILURE 14.F2: pg_basebackup Fails Mid-Backup
  Symptoms: "connection to server was lost" or "could not write to
    file"
  Root cause: network timeout (backup takes longer than TCP timeout),
    primary restart during backup, max_wal_senders exhausted (backup
    uses one WAL sender), disk full on backup destination
  Diagnosis: check error message. Check max_wal_senders vs current
    usage (pg_stat_replication count)
  Recovery: retry backup. Increase max_wal_senders. Use replication
    slot for backup (--wal-method=stream creates temporary slot).
    Ensure network stability

FAILURE 14.F3: PITR Fails — Missing WAL Segment
  Symptoms: restore_command returns error for specific WAL segment.
    Recovery stops with "requested WAL segment has already been
    removed"
  Root cause: WAL archive gap. The needed WAL segment was: never
    archived (archive_command failed), deleted prematurely
    (retention policy too short), corrupted in archive
  Diagnosis: identify the missing WAL segment name. Check archive
    for its presence. Check pg_stat_archiver history on source
  Recovery: PITR can only recover up to the gap. Data after gap
    is lost. Prevention: monitor archive_command success
    continuously. Archived WAL completeness check regularly

FAILURE 14.F4: Restored Database Won't Start
  Symptoms: PostgreSQL starts but immediately errors and shuts down,
    or starts in recovery and never promotes
  Root cause: Wrong PostgreSQL version (binary version mismatch
    with data directory), filesystem permissions incorrect after
    restore, pg_control corruption, archive_command not found,
    wrong recovery_target (set to future)
  Diagnosis: check PostgreSQL logs for specific error. Check
    pg_controldata vs PostgreSQL version
  Recovery: fix version mismatch (use correct binary). Fix
    permissions (chown -R postgres:postgres PGDATA). Fix
    recovery.conf settings. If recovery stuck in paused state:
    promote manually

FAILURE 14.F5: Restored Data Inconsistent
  Symptoms: database starts, queries work, but data is missing
    rows or inconsistent
  Root cause: backup taken while database was running with
    pg_start_backup not used (for file-level backup, not pg_basebackup),
    PITR stopped too early (before desired point), logical backup
    not consistent (concurrent writes during dump without --serializable)
  Diagnosis: verify row counts against expected. Check backup
    timestamp vs expected data state
  Recovery: restore from earlier (more complete) backup. Ensure
    proper backup procedures

LAYER 2: CONNECTED (after Modules 15, 25)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 14.X1: Backup → High Availability
    - Rebuilding standby: pg_basebackup from primary to provision
      new standby
    - After failover: old primary rebuilt as standby via pg_rewind
      (fast) or pg_basebackup (full copy)
    - Backup from standby: pg_basebackup can target standby to
      reduce primary I/O load

  CROSS-TOPIC TASK 14.X2: Backup → WAL Configuration
    - archive_command determines WAL archival reliability
    - archive_timeout: force WAL switch every N seconds to ensure
      WAL segments reach archive regularly (even low-write periods)
    - pg_stat_archiver monitoring critical for backup health

  CROSS-TOPIC TASK 14.X3: Backup → Upgrade
    - Always take full backup before pg_upgrade
    - Backup is rollback plan if upgrade fails
    - Logical replication upgrade: backup both old and new clusters

  COMBINED FAILURE 14.XF1: WAL Archive Fail → Backup Incomplete →
    PITR Impossible
    - archive_command starts failing (network, credentials)
    - pg_stat_archiver shows failures but no alert configured
    - Backup taken during period of archive failures
    - WAL needed for that backup's consistency is missing
    - Restore attempt fails

MODULE 15: HIGH AVAILABILITY — PATRONI DEEP DIVE
================================================================================
PREREQUISITES: Module 12 (streaming replication), Module 14 (backup)
PURPOSE: Automated failover is the standard for production PostgreSQL.
  Patroni is the most widely adopted solution. This module covers
  architecture, configuration, and operational procedures.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 15.1: HA Concepts [CON]
  - RTO (Recovery Time Objective): maximum acceptable downtime.
    For HA: typically 30 seconds to 5 minutes
  - RPO (Recovery Point Objective): maximum acceptable data loss.
    For HA with synchronous replication: zero. For async: seconds
  - Failover vs switchover: failover = unplanned (primary crashed,
    automatic or manual). Switchover = planned (maintenance, manual)
  - Split-brain: two nodes believing they're both primary. Worst
    HA failure mode. Simultaneous writes = diverged data
  - Fencing (STONITH): mechanism to ensure old primary is truly
    dead before promoting new primary. Patroni uses watchdog device
  - Quorum: minimum nodes needed for cluster to make decisions.
    For Patroni: DCS (Distributed Configuration Store) requires
    quorum. For synchronous replication: synchronous_standby_names
    defines quorum

TASK 15.2: Patroni Architecture [CON]
  - Components: Patroni daemon (runs on each node, manages PostgreSQL),
    DCS (etcd, Consul, ZooKeeper, or Kubernetes API — stores cluster
    state), REST API (health checks, cluster info), PostgreSQL itself
  - How Patroni works: each node's Patroni process monitors local
    PostgreSQL. Writes leader key to DCS (only one node holds
    leader key at a time — the primary). Other nodes are replicas.
    If leader key expires (leader node fails), another node acquires
    leader key → promotes its PostgreSQL to primary
  - DCS: etcd most popular. Distributed, uses Raft consensus.
    3 or 5 nodes for quorum. Stores: cluster configuration,
    member state, leader key with TTL
  - REST API: Patroni listens on port 8008. Endpoints: /health
    (is node healthy?), /leader (redirect to leader for writes),
    /replica (redirect to replica for reads), /read-only
  - HAProxy integration: HAProxy uses Patroni REST API for health
    checks. Routes writes to /leader, reads to /replica

TASK 15.3: Patroni Configuration [DES] [OP]
  - patroni.yml structure:
    scope: cluster name (must match on all nodes)
    name: node name (unique per node)
    restapi: listen address, connect_address (for other nodes)
    DCS configuration: etcd hosts, namespace
    bootstrap: initial cluster configuration (pg_hba, postgresql.conf
      parameters, initdb options, recovery settings)
    postgresql: listen address, data_dir, bin_dir, parameters,
      pg_hba, authentication (replication user)
    watchdog: Linux watchdog device for STONITH (prevents split-brain)
    tags: noloadbalance, nosync, replicatefrom, clonefrom
  - Bootstrap process: first node initializes PostgreSQL (initdb),
    registers in DCS as leader. Subsequent nodes clone from leader
    via pg_basebackup
  - DCS-stored configuration: patronictl edit-config to change
    PostgreSQL parameters. Configuration applies to all nodes.
    Some changes require restart → Patroni handles rolling restart

TASK 15.4: patronictl Commands [OP]
  - patronictl list: show cluster status (member, host, role, state,
    TL, lag in MB)
  - patronictl switchover: planned switchover. Promote specific
    candidate. Schedules and executes gracefully
  - patronictl failover: forced failover. Use when primary is dead.
    Promotes best candidate (or specified one)
  - patronictl reinit: rebuild a cluster member (re-clone from primary)
  - patronictl restart: restart a member (or rolling restart for
    all — schedules restart based on role)
  - patronictl pause/resume: maintenance mode. Paused cluster won't
    auto-failover
  - patronictl edit-config: change DCS-stored configuration
  - patronictl show-config: view effective configuration

COMMON FAILURES FOR MODULE 15:
────────────────────────────────────────────────────────────────

FAILURE 15.F1: Patroni Won't Promote — No Leader
  Symptoms: patronictl list shows no leader. Applications failing
    on writes. DCS shows no leader key
  Root causes: DCS quorum lost (etcd nodes down), network partition
    between Patroni nodes, all PostgreSQL instances down, watchdog
    triggered and no node healthy
  Diagnosis: Check DCS health (etcdctl endpoint health). Check
    Patroni logs on all nodes. Check if DCS is accessible from
    all nodes
  Recovery: Restore DCS quorum. If DCS permanently lost: restore
    DCS from backup. Manual promotion of best candidate as last
    resort (pg_ctl promote). Then rebuild Patroni cluster

FAILURE 15.F2: Split-Brain
  Symptoms: Two nodes in patronictl list show role='Leader'.
    Application writes going to two different nodes. Data divergence
  Root cause: DCS leader key expired but old leader didn't demote
    (watchdog failed, network blip, Patroni process hung). New
    leader elected. Old leader still accepting writes
  Diagnosis: patronictl list shows two leaders. Check data on both
    for divergence (timeline differences, row count differences)
  Recovery: STOP all application writes immediately. Determine
    which node has authoritative data (most recent timeline,
    highest LSN). Demote old leader (patronictl restart or manual
    pg_ctl stop). Rebuild demoted node as replica (patronictl reinit)
  Prevention: Ensure watchdog properly configured. Use synchronous
    replication. Monitor for split-brain detection

FAILURE 15.F3: Patroni Stuck in Paused Mode
  Symptoms: patronictl list shows cluster paused=True. No auto-
    failover occurring. Primary failure not handled
  Root cause: Someone ran patronictl pause for maintenance and
    forgot to resume. Or pause set in DCS configuration
  Diagnosis: patronictl list shows paused flag. patronictl show-config
    shows paused setting
  Recovery: patronictl resume to re-enable failover

FAILURE 15.F4: Standby Lag Prevents Switchover
  Symptoms: patronictl switchover fails: "standby is too far behind"
    or times out
  Root cause: Standby has significant replication lag (replay_lag
    high). maximum_lag_on_failover setting prevents promotion of
    lagging standby
  Diagnosis: patronictl list shows lag in MB column. pg_stat_replication
    shows replay_lag
  Recovery: Wait for standby to catch up. Or disable maximum_lag_on_failover
    (risk data loss). Or promote and accept lag-related data loss

FAILURE 15.F5: etcd Quorum Lost
  Symptoms: Patroni cannot write to DCS. patronictl list shows old
    state or errors. Cluster may enter read-only mode or fail to
    failover
  Root cause: Too many etcd nodes down (if 3-node etcd: 2 down =
    no quorum). Network partition between etcd nodes
  Diagnosis: etcdctl endpoint health on all etcd nodes
  Recovery: Restore enough etcd nodes to achieve quorum. If etcd
    cluster permanently destroyed: restore etcd from backup.
    If no etcd backup: manual Patroni cluster recovery

MODULE 16: CONNECTION POOLING — PGBOUNCER ARCHITECTURE
================================================================================
PREREQUISITES: Module 0 (process model), Module 15 (HA context)
PURPOSE: Connection pooling is mandatory for production PostgreSQL at scale.
  PgBouncer is the most widely used pooler. Understanding its modes,
  limitations, and integration with HA is essential.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 16.1: Why Connection Pooling Exists [CON]
  - PostgreSQL process model: each connection = one OS process.
    Process creation has cost (fork, memory allocation, catalog
    cache loading). Each connection consumes memory (work_mem,
    temp_buffers, catalog cache). Context switching between 1000s
    of processes adds CPU overhead
  - Production reality: 1000 application threads each opening
    connection = 1000 PostgreSQL backends. Even if idle, they
    consume resources. With transaction pooling: 1000 application
    threads share 50 PostgreSQL connections
  - Calculate: 500 connections × 10MB work_mem = 5GB RAM just in
    work_mem allocations. Plus shared_buffers, plus OS memory.
    Pooling to 50 connections = 500MB work_mem
  - Pooling benefits: reduced PostgreSQL connections (lower resource
    usage), connection reuse (avoid fork latency), queuing (prevent
    connection storms from reaching PostgreSQL)

TASK 16.2: PgBouncer Architecture [CON]
  - PgBouncer is a C application, single process, async I/O.
    Extremely efficient (handles 100K+ connections)
  - Listens on port (default 6432). Accepts client connections.
    Maintains pool of server connections to PostgreSQL
  - When client queries: PgBouncer assigns available server
    connection from pool, forwards query, returns result.
    Client connection and server connection are decoupled
  - Pool modes:
    Session pooling: client connection assigned to one server
      connection for entire session. Session variables, prepared
      statements, and SET commands persist. Least scalable but
      most compatible (like direct connection)
    Transaction pooling: server connection assigned only during
      transaction. Between transactions, server connection returned
      to pool. Most scalable. Limitations: no prepared statements,
      no SET with session scope, no LISTEN/NOTIFY across transactions,
      no temp tables across transactions
    Statement pooling: server connection assigned only for single
      statement. Most restrictive. Autocommit mode only
  - Most common: TRANSACTION pooling for web applications.
    SESSION pooling for admin tools, legacy apps

TASK 16.3: PgBouncer Configuration [DES] [OP]
  - pgbouncer.ini sections:
    [databases]: define database aliases, connection strings, pool sizes
    [pgbouncer]: global settings — listen_addr, listen_port,
      auth_type, auth_file, admin_users, stats_users, pool_mode,
      max_client_conn, default_pool_size, reserve_pool_size,
      reserve_pool_timeout, server_idle_timeout, client_idle_timeout,
      server_lifetime, server_connect_timeout
  - Pool sizing: default_pool_size = number of server connections
    per (database, user) pair. Total PostgreSQL connections =
    sum of all pool sizes across all (database, user) combinations
  - reserve_pool_size: extra connections available when pool
    exhausted. Prevents complete lockout. reserve_pool_timeout:
    how long to wait before assigning reserve connection
  - max_db_connections: global cap per database
  - PgBouncer authentication: auth_file (userlist.txt) contains
    usernames and password hashes. Can use auth_query to verify
    passwords against PostgreSQL directly (no local password file)

TASK 16.4: PgBouncer Monitoring [MON] [OP]
  - Admin console: connect to pgBouncer on virtual 'pgbouncer' database
  - SHOW POOLS: database, user, cl_active (client connections),
    cl_waiting (clients waiting for connection), sv_active (server
    connections in use), sv_idle (server connections idle in pool),
    sv_used (total server connections), sv_tested, sv_login, maxwait
    (longest client wait time)
  - SHOW STATS: total requests, total query time, avg query time,
    bytes received/sent
  - SHOW CLIENTS: per-client connection state, connect time, request time
  - SHOW SERVERS: per-server connection state, connect time, request time
  - SHOW DATABASES: per-database statistics
  - Key metrics: cl_waiting (if > 0, pool too small). maxwait (if
    growing, clients waiting longer). sv_idle (if 0, pool exhausted).
    sv_active ≈ pool_size (pool saturated)

COMMON FAILURES FOR MODULE 16:
────────────────────────────────────────────────────────────────

FAILURE 16.F1: "No more connections allowed (max_client_conn)"
  Symptoms: Error from PgBouncer. Application cannot connect
  Root cause: max_client_conn reached. Too many application
    connections to PgBouncer
  Diagnosis: SHOW STATS shows total_xact_count. Compare client
    connection count vs max_client_conn. SHOW CLIENTS count
  Recovery: Increase max_client_conn in PgBouncer (and ensure
    OS ulimit supports it). Reduce application idle connections
    (client_idle_timeout). Add more PgBouncer instances

FAILURE 16.F2: "No more connections allowed (max_db_connections)"
  Symptoms: New client connections to PgBouncer succeed but
    queries to specific database fail with that error
  Root cause: max_db_connections for that database reached across
    all pool users
  Diagnosis: SHOW DATABASES shows current_connections for affected db
  Recovery: Increase max_db_connections for that database. Reduce
    pool sizes. Check for connection leaks (sv_idle high but
    connections not released)

FAILURE 16.F3: Prepared Statement Error in Transaction Pooling
  Symptoms: "prepared statement 'X' does not exist" or similar
  Root cause: Application using PREPARE/EXECUTE or driver-level
    prepared statements (like JDBC's PreparedStatement). In
    transaction pooling, server connection changes between
    transactions → prepared statements are lost
  Diagnosis: Identify if application uses prepared statements.
    Check if pool_mode=transaction
  Recovery: Switch to session pooling (less scalable) or disable
    prepared statements in application. Or use PgBouncer WITH
    statement-level prepared statement support (PgBouncer 1.21+
    with max_prepared_statements)

FAILURE 16.F4: PgBouncer Becomes Bottleneck
  Symptoms: cl_waiting growing, maxwait increasing, application
    latency high despite PostgreSQL being under capacity
  Root cause: Pool size too small. Application demand exceeds
    available server connections. PgBouncer queues clients
  Diagnosis: SHOW POOLS shows cl_waiting, cl_active, sv_active.
    sv_active close to pool_size. maxwait > 0
  Recovery: Increase pool_size for affected database/user pair.
    Or add more PgBouncer instances. Or reduce application
    connection demand (application-side pooling)

FAILURE 16.F5: Authentication Failure After Password Change
  Symptoms: PgBouncer accepts connection but queries fail with
    authentication error on PostgreSQL
  Root cause: Password changed in PostgreSQL but not updated in
    PgBouncer auth_file (userlist.txt) or auth_query not configured
  Diagnosis: SHOW SERVERS shows login failures. Check PgBouncer
    logs for auth errors
  Recovery: Update auth_file or password in PostgreSQL. Reload
    PgBouncer (RELOAD command or systemd reload). Consider
    auth_query to eliminate duplicate credential management

  TASK 16.D1: PgBouncer Internals [CON]
    - Single-threaded event loop: uses epoll/kqueue for async I/O.
      Handles thousands of connections in one process
    - Connection lifecycle: client connects → PgBouncer auths client →

      forwards query → receives result → returns to client →
      returns server to pool (in transaction mode)

  TASK 16.D2: Alternative Poolers [DES]

      management. More features, heavier, more complex
    - Odyssey: multi-threaded pooler from Yandex. Transaction pooling

    - Supavisor: newer pooler from Supabase. Cloud-native design
    - Application-level pooling: connection pools in application

      for scale

    - Single PgBouncer: handles 100K+ connections. CPU bound

    - PgBouncer monitoring at scale: aggregate SHOW POOLS

MODULE 17: PERFORMANCE TUNING — MEMORY, I/O, OS
================================================================================
PREREQUISITES: Module 6 (checkpoints), Module 15 (HA), Module 16 (pooling)
PURPOSE: System-level tuning integrates PostgreSQL with the operating
  system and hardware. Memory configuration, I/O subsystem, and kernel
  parameters directly determine PostgreSQL performance.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 17.1: Memory Configuration Deep Dive [DES]
  - shared_buffers: PostgreSQL's primary cache. General guidance:
    25% of RAM for dedicated database server. Diminishing returns
    above 8-16GB in most workloads (scanning large buffer pool
    has cost). Buffer cache hit ratio should be >95% (from
    pg_statio_* views)
  - effective_cache_size: planner's estimate of total cache
    available (shared_buffers + OS page cache). Does NOT allocate
    memory — only informs planner decisions. Typical: 50-75%
    of total RAM. Larger value → planner more likely to use
    index scans (assumes heap data cached)
  - work_mem: per-operation memory (sorts, hashes). NOT per-query
    (a query can use multiple work_mem allocations). NOT per-session
    (each operation allocates its own). Danger: max_connections ×
    work_mem × parallel workers can exceed RAM. Tuning: set low
    globally, override per session for analytical queries
  - maintenance_work_mem: used by VACUUM, CREATE INDEX, REINDEX,
    ALTER TABLE, CLUSTER. Higher = faster maintenance. Safe to
    set high (maintenance operations are few). autovacuum_work_mem
    overrides for autovacuum workers (PG17+)
  - temp_buffers: per-session cache for temporary tables. Increase
    for applications using temp tables heavily
  - wal_buffers: WAL write buffer. Default = 1/32 of shared_buffers
    (capped at 64MB). Usually sufficient. Increase to 64MB for
    heavy write workloads

TASK 17.2: I/O Configuration [DES]
  - random_page_cost: planner's cost of random page access relative
    to sequential. Default 4.0 (HDD assumption: random = 4× slower
    than sequential). For SSD/NVMe: 1.1-1.5. For HDD+SSD mixed:
    set per tablespace
  - effective_io_concurrency: concurrent I/O requests for bitmap
    heap scans. For SSDs: 200. For NVMe: 200-800. For HDD: 2.
    Tells planner how many parallel I/Os are beneficial
  - maintenance_io_concurrency: similar for maintenance operations
    (PG13+). For VACUUM, CREATE INDEX
  - wal_sync_method: how WAL writes are synchronized. OS-default
    usually fine. Open options: fdatasync, fsync, open_datasync,
    open_sync. Test with pg_test_fsync for optimal

TASK 17.3: Workload-Based Resource Allocation [DES]
  - OLTP workload (many small transactions):
    - shared_buffers: moderate (25% RAM)
    - work_mem: low (4-16MB) — queries are simple
    - effective_cache_size: 75% RAM (caching is critical)
    - max_connections: managed by pooler (PgBouncer)
  - OLAP/DWH workload (few large queries):
    - shared_buffers: moderate (25% RAM) — most data won't fit anyway
    - work_mem: high (256MB-1GB) per session — sorts are large
    - effective_cache_size: 75% RAM
    - max_connections: low (few concurrent analytical queries)
    - max_parallel_workers_per_gather: high
  - Mixed workload: prioritize. Tune for OLTP responsiveness
    (lower work_mem), override per session for analytical queries

TASK 17.4: Operating System Monitoring [MON]
  - CPU: overall utilization, iowait (disk wait), steal (VM
    hypervisor stealing CPU). High iowait = disk bottleneck.
    High steal = VM overcommitted
  - Memory: free, used, buffered, cached. available (most important
    — how much can be allocated without swapping). swap usage (any
    non-zero is warning for PostgreSQL)
  - Disk I/O: iostat -x. await (service time + queue time), util
    (busy %), r/s and w/s (IOPS), rkB/s and wkB/s (throughput).
    High await (>10ms for SSD) = I/O problem. High util (>70%)
    = I/O saturation
  - Network: throughput, errors, retransmissions. For replication
    bandwidth monitoring
  - Process: postgres process count vs max_connections. Context
    switching rate (cs in vmstat). High context switch = too
    many active processes

COMMON FAILURES FOR MODULE 17:
────────────────────────────────────────────────────────────────

FAILURE 17.F1: OOM Killer Terminates PostgreSQL
  Symptoms: PostgreSQL process disappears. dmesg shows "Out of
    memory: Killed process N (postgres)". Application errors
    about lost connection. PostgreSQL log shows unexpected
    termination
  Root cause: Total memory demand > available RAM.
    (shared_buffers + work_mem × active_connections × parallel_workers
    + maintenance_work_mem + OS memory) exceeds RAM. Linux OOM
    killer selects a process to kill
  Diagnosis: dmesg for OOM event. Correlate with connection count
    spike, maintenance operation start, or parallel query execution
  Recovery: Adjust memory configuration (reduce work_mem, reduce
    connections, increase RAM). Set vm.overcommit_memory=2 to
    prevent overcommit

FAILURE 17.F2: Swap Usage Degrading Performance
  Symptoms: Queries intermittently slow. iostat shows I/O wait
    spikes not matching checkpoint pattern. free shows swap
    usage > 0
  Root cause: Not enough RAM. OS swapped out PostgreSQL memory
    to disk (likely shared_buffers pages). When PostgreSQL needs
    those pages, read from swap (disk I/O)
  Diagnosis: free shows swap usage. vmstat shows si (swap in)
    and so (swap out). High si during PostgreSQL activity confirms
  Recovery: Reduce shared_buffers to fit in available RAM. Add
    RAM. Set vm.swappiness=1 to discourage swapping. Ensure
    enough available memory for OS

FAILURE 17.F3: CPU I/O Wait High
  Symptoms: iostat shows util high, await high. PostgreSQL queries
    slow. CPU %iowait high (20%+)
  Root cause: Disk subsystem cannot keep up with I/O demand.
    Causes: checkpoints (write pressure), heavy sequential scans
    (read pressure), vacuum running, temp file writes (work_mem
    too small), shared_buffers too small (reads go to disk)
  Diagnosis: iostat identifies which device. iotop identifies
    which PostgreSQL process (backend, checkpointer, etc.).
    pg_stat_activity shows wait events (DataFileRead = reading,
    DataFileWrite = writing)
  Recovery: Identify and address root cause (tune checkpoints,
    increase shared_buffers, increase work_mem, add faster storage)

FAILURE 17.F4: Too Many Context Switches
  Symptoms: vmstat cs (context switches) very high (>100K/sec).
    PostgreSQL throughput plateau despite low CPU utilization
  Root cause: Too many active PostgreSQL backends contending for
    CPU. Each connection = process. OS scheduler spends more
    time switching than executing
  Diagnosis: vmstat shows high cs. PostgreSQL has many connections
    in 'active' state
  Recovery: Reduce active connections via connection pooling.
    Reduce max_connections. Use PgBouncer transaction pooling

MODULE 18: QUERY OPTIMIZATION DEEP DIVE
================================================================================
PREREQUISITES: Module 8 (EXPLAIN), Module 10 (statistics), Module 7 (indexing)
PURPOSE: Move beyond reading EXPLAIN to actively rewriting and optimizing
  queries. This is where you transform from someone who can diagnose to
  someone who can fix.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 18.1: Identify Optimization Targets [DIAG]
  - Use pg_stat_statements to find high-impact queries: top by total_time
    (biggest cumulative impact), top by mean_time (slowest per execution),
    top by calls (most frequent), top by temp_blks_written (work_mem candidates)
  - Understand: optimizing a query called 1M times/day from 10ms to 5ms
    saves more total time than optimizing a query called once/day from
    10s to 1s
  - Use pg_stat_statements with snapshots: take periodic snapshots, diff
    to find queries getting worse over time (plan regression)
  - Look for queries with high stddev_time: inconsistent performance suggests
    plan flipping or parameter sensitivity

TASK 18.2: Rewrite Patterns — Subquery to JOIN [CON] [OP]
  - Identify correlated subqueries: subquery in WHERE clause that references
    outer query columns. For each outer row, subquery executes once.
    Equivalent JOIN usually executes once with hash/merge join
  - NOT IN with NULL trap: WHERE col NOT IN (SELECT nullable_col FROM t2)
    returns NO rows if t2.nullable_col contains any NULL. Rewrite to
    NOT EXISTS or use anti-join
  - IN vs EXISTS: IN with subquery materializes full result. EXISTS
    stops at first match. For large subquery results, EXISTS often faster
  - Scalar subquery in SELECT: executes once per result row. If result
    is large, consider LEFT JOIN or LATERAL instead

TASK 18.3: Rewrite Patterns — DISTINCT and GROUP BY [CON] [OP]
  - Unnecessary DISTINCT: application removes duplicates that don't exist
    or don't matter. DISTINCT forces sort or hash aggregate. If rows
    already unique (by primary key), DISTINCT is waste
  - DISTINCT vs GROUP BY: semantically different but some queries use
    DISTINCT when GROUP BY is intended. Use correct one
  - COUNT(DISTINCT col1, col2) vs COUNT(DISTINCT (col1, col2)): different
    semantics. Multiple COUNT(DISTINCT) in one query is expensive
    (each requires separate sort/hash)
  - Multiple aggregations on same GROUP BY: one scan does all. But
    COUNT(DISTINCT) forces multiple passes. Consider pre-grouping
    with CTE if multiple DISTINCTs needed

TASK 18.4: Rewrite Patterns — LIMIT and OFFSET [CON] [OP]
  - OFFSET large value: PostgreSQL must scan all rows before OFFSET,
    then discard them. For page 1000 with LIMIT 20, scans 20000 rows,
    returns 20. Efficiency: 0.1%
  - Keyset pagination (cursor pagination): WHERE id > last_seen_id
    ORDER BY id LIMIT N. Uses index, scans only N rows. Requires
    ordering column to be unique and sequential
  - Keyset pagination with non-unique columns: WHERE (col, id) >
    (last_col, last_id). Composite index on (col, id)
  - When OFFSET is acceptable: small result sets (< 1000 total rows)
    where entire result is scanned once

TASK 18.5: Rewrite Patterns — UNION vs UNION ALL vs OR [CON] [OP]
  - UNION: removes duplicates (requires sort or hash). UNION ALL:
    no dedup, appends results. If rows are already distinct between
    branches, use UNION ALL
  - OR condition on different columns: WHERE a = X OR b = Y.
    PostgreSQL can't use index on a AND index on b simultaneously
    (needs bitmap OR which is available). Sometimes UNION ALL
    (SELECT ... WHERE a=X UNION ALL SELECT ... WHERE b=Y) is faster
    because each branch uses its own index
  - OR with one index: if only one column has index, OR may scan
    both branches (index scan for indexed part, sequential scan
    for unindexed). UNION ALL with indexed branch first is better

COMMON FAILURES FOR MODULE 18:
────────────────────────────────────────────────────────────────

FAILURE 18.F1: Query Works in Dev, Fails in Production
  Symptoms: query fast in development (small data), slow in
    production (millions of rows)
  Root cause: plan changed based on data volume. Nested loop
    fine for 100 rows, terrible for 1M rows. Planner may switch
    to hash join (fine) or stay with nested loop and explode
  Diagnosis: EXPLAIN ANALYZE in production (or on production-
    scale staging). Compare plans between environments
  Recovery: Create index enabling better plan. Rewrite query
    to be data-volume-insensitive. Use pg_hint_plan as
    temporary fix if plan must be forced

FAILURE 18.F2: N+1 Query Problem
  Symptoms: application loads list of N items, then executes
    separate query for each item (N additional queries = N+1 total)
  Root cause: ORM or application code loading related data in loop
  Diagnosis: pg_stat_statements shows many executions of same
    query with different parameters. Application log shows
    many small queries in sequence
  Recovery: Rewrite as single JOIN query or use ORM eager loading.
    Change application pattern to batch queries

FAILURE 18.F3: Implicit Type Cast Prevents Index Use
  Symptoms: EXPLAIN shows Seq Scan instead of Index Scan.
    WHERE clause has: int_col = '123' (string value)
  Root cause: '123' is text, PostgreSQL implicitly casts int_col
    to text → function on indexed column → index cannot be used
  Diagnosis: EXPLAIN VERBOSE shows cast on column. Compare
    data types of column and compared value
  Recovery: Use correct data type in query. Check ORM-generated
    SQL for type mismatches

FAILURE 18.F4: Function-Wrapped Indexed Column
  Symptoms: Index on created_at. WHERE date(created_at) = '2024-01-01'.
    EXPLAIN shows Seq Scan
  Root cause: date() function wraps column. Index is on
    created_at, not date(created_at). PostgreSQL can't use index
  Diagnosis: EXPLAIN shows no index scan despite index existence
  Recovery: Rewrite as range: WHERE created_at >= '2024-01-01'
    AND created_at < '2024-01-02'. This uses index directly.
    Or create expression index on date(created_at)

LAYER 3: DEEP
────────────────────────────────────────────────────────────────

  TASK 18.D1: Advanced Join Optimization [CON]
    - Lateral joins: foreach outer row, execute subquery.
      Appropriate when inner subquery uses outer columns
      and returns few rows per outer row
    - Semi-join and anti-join: EXISTS and NOT EXISTS respectively.
      Planner may rewrite to JOIN internally, but not always
    - Join removal: PostgreSQL can remove unnecessary joins
      if no columns selected from joined table and FK guarantees
      rows exist. Requires FK constraint and no nullable FK

  TASK 18.D2: Materialized View Strategy [DES]
    - When to create: expensive aggregation/join queried frequently,
      base data changes slowly (minutes/hours not seconds)
    - REFRESH MATERIALIZED VIEW: full rebuild. CONCURRENTLY: no
      lock, requires unique index. Compare time: REFRESH vs
      application query
    - Staleness management: how old can data be? Schedule refresh
      accordingly. Or use incremental refresh (application-managed)
    - Materialized view on standby: offload refresh load

  TASK 18.D3: CTE Optimization [CON]
    - Pre-PG12: CTE always materialized (optimization fence).
      Planner couldn't push predicates into CTE or reorder
      joins across CTE boundary
    - PG12+: MATERIALIZED or NOT MATERIALIZED hint on CTE.
      NOT MATERIALIZED allows planner to inline CTE into
      main query (like subquery)
    - Recursive CTE: performance risks. Always test with
      realistic data volumes. Add termination conditions.
      Consider cycle detection (CYCLE clause PG14+)

  TASK 18.D4: Parallel Query Optimization [CON] [DES]
    - When parallel query helps: large sequential scans,
      large hash joins, large aggregates
    - When parallel query hurts: OLTP queries (startup overhead
      exceeds benefit), queries that are already fast (< few ms),
      when I/O is bottleneck (more workers = more I/O contention)
    - Tuning: max_parallel_workers_per_gather (workers per query),
      max_parallel_workers (total workers across all queries),
      max_worker_processes (total background workers)
    - Parallel query limitations: cannot be parallel if query
      modifies data with certain DML, if using SERIALIZABLE,
      if function is not PARALLEL SAFE

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 18:
    - Recursive CTE infinite loop (no termination, fills temp files)
    - Materalized view refresh timeout (statement_timeout)
    - Parallel query causes memory exhaustion
    - Scalar subquery returns more than 1 row (runtime error)

MODULE 19: EXTENSIONS ECOSYSTEM
================================================================================
PREREQUISITES: Module 7 (indexing), Module 18 (query optimization)
PURPOSE: Extensions extend PostgreSQL into specialized domains. A senior
  DBA must know when to use extensions and their operational implications.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 19.1: Extension Management [OP] [CON]
  - Installation: shared_preload_libraries (loaded at server start,
    required for some extensions like pg_stat_statements, pg_cron,
    pg_audit, Citus). Other extensions: CREATE EXTENSION (loaded
    per database)
  - Discover available extensions: pg_available_extensions
  - Installed extensions: pg_extension, \dx
  - Extension version tracking: pg_available_extension_versions
  - Extension upgrade: ALTER EXTENSION ... UPDATE
  - Upgrade implications: extensions must be compatible with new
    PostgreSQL version. Check before pg_upgrade. Some extensions
    in contrib (shipped with PostgreSQL, always compatible).
    Third-party extensions require separate upgrade

TASK 19.2: pg_stat_statements [MON] [OP]
  - Purpose: aggregates query statistics. Most important
    performance monitoring extension
  - Configuration: shared_preload_libraries, pg_stat_statements.track
    (all, top, none), pg_stat_statements.max (number of distinct
    queries tracked, default 5000 — increase for busy systems),
    pg_stat_statements.track_utility (track COPY, VACUUM, etc.)
  - Key fields: queryid (hash of normalized query), calls, total_time,
    min_time, max_time, mean_time, stddev_time, rows, shared_blks_hit,
    shared_blks_read, shared_blks_dirtied, shared_blks_written,
    local_blks_hit/read/dirtied/written, temp_blks_read/written,
    blk_read_time, blk_write_time, wal_bytes
  - Query normalization: literals replaced with $1, $2. Same
    query pattern with different values → same queryid
  - Reset: pg_stat_statements_reset() resets all counters. Better:
    take snapshots and diff
  - Usage: find top queries by total_time, mean_time, calls,
    temp_blks_written. Track query performance over time

TASK 19.3: PostGIS — Geospatial [CON] [OP]
  - Purpose: geospatial data types, indexes, and functions
  - Data types: geometry (planar), geography (spherical)
  - Index: GiST on geometry/geography column. Speeds up spatial
    queries (ST_Contains, ST_Intersects, ST_DWithin, ST_Distance)
  - Nearest neighbor: <-> operator with GiST index. ORDER BY
    location <-> point LIMIT N
  - Coordinate systems: SRID (Spatial Reference ID). Transform
    with ST_Transform
  - Common patterns: find points within radius, find nearest N,
    geofencing, route planning
  - Operational: PostGIS version must match PostgreSQL version
    compatibility matrix. Backup/restore includes PostGIS types.
    pg_upgrade requires PostGIS upgrade

TASK 19.4: Full-Text Search (FTS) [CON] [OP]
  - Purpose: text search with linguistic features (stemming,
    ranking, dictionaries)
  - Data types: tsvector (document, tokenized for search),
    tsquery (search query)
  - Index: GIN on tsvector column. Speeds up @@ (match) operator
  - Text search functions: to_tsvector(config, text) converts
    text to tsvector. to_tsquery, plainto_tsquery,
    websearch_to_tsquery convert search strings
  - Ranking: ts_rank, ts_rank_cd for result ordering
  - Dictionaries: stop words (remove common words), stemming
    (reduce to root), thesaurus (synonyms), synonym dictionary
  - Multi-language: different text search config per language

TASK 19.5: JSONB [CON] [OP]
  - Purpose: document store within relational database
  - Operators: -> (get field as jsonb), ->> (get field as text),
    @> (contains), <@ (contained by), ? (key exists), ?| (any
    key exists), ?& (all keys exist)
  - Index: GIN on jsonb column for containment queries ((data @>
    '{"key":"value"}')). GIN with jsonb_path_ops (smaller, only
    top-level containment). B-tree expression index on extracted
    field ((data->>'field') for equality/range)
  - jsonpath (PG12+): XPath-like query language for JSONB.
    jsonb_path_query, jsonb_path_exists
  - Trade-offs: flexible schema, easy to store varying data.
    But: no type safety, no foreign keys, index only on known
    patterns, larger storage than normalized tables

TASK 19.6: Other Key Extensions [CON]
  - pg_cron: scheduled jobs within PostgreSQL. Use for periodic
    maintenance (VACUUM specific tables, materialized view refresh,
    partition management)
  - pg_partman: automated partition management. Creates new
    partitions, drops old based on retention policy
  - pg_repack: online table/index rebuild without long locks.
    Alternative to VACUUM FULL
  - pgvector: vector similarity search for ML embeddings.
    Index types: IVFFlat, HNSW. Operators: <-> (L2), <=> (inner
    product), <#> (cosine)
  - pg_trgm: trigram matching for fuzzy text search. LIKE
    '%middle%' with GIN index on trigrams. Similarity (similarity()
    function)
  - postgres_fdw: access data in other PostgreSQL databases
    (and other databases with appropriate FDW). Push-down
    of WHERE clauses, joins to remote side
  - amcheck: verify index and heap integrity. Detect corruption
  - pageinspect: inspect page internals (used in Module 3)
  - pg_buffercache: inspect shared_buffers contents

MODULE 20: SECURITY ARCHITECTURE
================================================================================
PREREQUISITES: Module 1 (installation), Module 2 (catalogs)
PURPOSE: Security is not a feature, it's an architecture. This module
  covers authentication, authorization, encryption, and auditing.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 20.1: Authentication — pg_hba.conf Mastery [CON] [OP]
  - pg_hba.conf format: type, database, user, address, method, options
  - Connection types: local (Unix socket), host (TCP with or without SSL),
    hostssl (TCP with SSL required), hostnossl (TCP without SSL)
  - Authentication methods:
    trust (no password — NEVER use in production except for local
      replication with Unix socket), reject (deny immediately),
    scram-sha-256 (current standard, salted challenge-response),
    md5 (deprecated, weak), password (plaintext — NEVER use),
    peer (OS username mapping), ident (RFC 1413 ident server),
    cert (SSL client certificate), ldap, radius, pam, gssapi
  - Entry order: first matching entry applies. More specific entries
    must come before general entries
  - CIDR notation: IP range in host/hostssl lines. Single IP: /32.
    Network: /24, /16

TASK 20.2: Role Management [CON] [OP]
  - Role types: LOGIN (can connect), SUPERUSER (bypass all checks),
    CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS, INHERIT
  - Role membership: GRANT role TO user. INHERIT vs NOINHERIT
  - Role hierarchy: role can be member of another role. Privileges
    inherited (or not, depending on INHERIT)
  - pg_roles, pg_authid, pg_auth_members views
  - Best practice: create group roles (no LOGIN) for privilege
    assignments. Create user roles (LOGIN) that are members of
    group roles. No direct privilege grants to users

TASK 20.3: Privileges [CON] [OP]
  - Object types and their privileges:
    DATABASE: CONNECT, CREATE, TEMP
    SCHEMA: USAGE, CREATE
    TABLE: SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
    SEQUENCE: USAGE, SELECT, UPDATE
    FUNCTION: EXECUTE
  - GRANT ... ON object TO role
  - REVOKE ... ON object FROM role
  - Default privileges: ALTER DEFAULT PRIVILEGES sets privileges
    for future objects created by a role in a schema
  - Column-level privileges: GRANT SELECT (col1, col2) ON table TO role
  - Public schema: pre-PG15, PUBLIC had CREATE privilege on public
    schema (security risk). Revoke: REVOKE CREATE ON SCHEMA public FROM PUBLIC

TASK 20.4: Row-Level Security (RLS) [CON] [OP]
  - Purpose: restrict which rows a user can see/modify, per policy
  - Enable: ALTER TABLE t ENABLE ROW LEVEL SECURITY
  - Policy: CREATE POLICY name ON table FOR SELECT/INSERT/UPDATE/DELETE
    TO role USING (condition) WITH CHECK (condition)
  - USING: which rows are visible (SELECT, UPDATE, DELETE)
  - WITH CHECK: which rows can be created/modified (INSERT, UPDATE)
  - Bypass: table owner and superuser bypass RLS by default.
    Can force RLS on owner: ALTER TABLE t FORCE ROW LEVEL SECURITY
  - Performance: RLS conditions are effectively added to every
    query on the table. Indexes on columns used in RLS conditions
    are critical

TASK 20.5: SSL/TLS Configuration [OP]
  - Server certificates: ssl_cert_file, ssl_key_file, ssl_ca_file
  - Client certificate verification: ssl_ca_file + pg_hba.conf
    with cert method
  - SSL parameters: ssl_min_protocol_version (TLSv1.2 minimum),
    ssl_ciphers (restrict to strong ciphers)
  - Certificate management: expiration monitoring, renewal process,
    reload without restart

COMMON FAILURES FOR MODULE 20:
────────────────────────────────────────────────────────────────

FAILURE 20.F1: "no pg_hba.conf entry for host"
  Symptoms: User cannot connect from specific IP
  Root cause: missing pg_hba.conf entry for that host/network.
    Or entry exists but uses wrong CIDR mask
  Diagnosis: Check pg_hba.conf for matching entry. Verify CIDR
    includes the IP. Check entry order (more specific first)
  Recovery: Add correct pg_hba.conf entry. Reload PostgreSQL

FAILURE 20.F2: Permission Denied on Table
  Symptoms: "ERROR: permission denied for table X"
  Root cause: role lacks SELECT/INSERT/UPDATE/DELETE privilege
    on table. Schema USAGE privilege missing
  Diagnosis: Check table privileges (psql \dp tablename or
    information_schema.table_privileges). Check schema USAGE
    (information_schema.schema_privileges)
  Recovery: GRANT appropriate privilege. Don't GRANT ALL —
    follow least privilege principle

FAILURE 20.F3: RLS Policy Blocks Expected Access
  Symptoms: RLS enabled on table. User query returns 0 rows
    when rows exist. User INSERT fails with policy violation
  Root cause: RLS policy USING or WITH CHECK condition not
    matching user's data. Policy applies to user unexpectedly
  Diagnosis: SELECT * FROM pg_policies WHERE tablename='X'.
    Test policy condition as the affected user
  Recovery: Fix policy condition. Or add additional policy.
    Or disable RLS temporarily if safe

FAILURE 20.F4: SSL Certificate Expired
  Symptoms: Connections fail with SSL error. Existing connections
    may continue working until they disconnect
  Root cause: Server or CA certificate expired
  Diagnosis: Check certificate validity (openssl x509 -in
    server.crt -noout -dates)
  Recovery: Replace certificate with renewed one. Reload
    PostgreSQL (no restart needed). Monitor certificate
    expiration

FAILURE 20.F5: SUPERUSER Account Compromise
  Symptoms: Unexpected changes to database objects, suspicious
    queries
  Root cause: superuser password leaked, or application using
    superuser account
  Diagnosis: pg_stat_activity shows unusual superuser activity.
    Database log shows superuser DDL
  Recovery: Change compromised password. Revoke superuser from
    application accounts. Audit superuser membership (there
    should be very few). Enable pgaudit for superuser actions

LAYER 2: CONNECTED (after Modules 14, 16)
────────────────────────────────────────────────────────────────

  CROSS-TOPIC TASK 20.X1: Security → Replication
    - Replication user needs REPLICATION privilege
    - pg_hba.conf must allow replication connections
    - Replication traffic should be encrypted (SSL)

  CROSS-TOPIC TASK 20.X2: Security → Connection Pooling
    - PgBouncer authentication: auth_file or auth_query
    - PgBouncer shouldn't use trust auth
    - Pool user should have minimal privileges

  CROSS-TOPIC TASK 20.X3: Security → Backup
    - Backup contains all data, including sensitive
    - Backup encryption: pgBackRest/WAL-G encryption
    - Backup access control: only authorized DBA access

  COMBINED FAILURE 20.XF1: Security Incident Response
    - Detected: suspicious queries, unexpected schema changes
    - Contain: revoke compromised user access, kill sessions
    - Investigate: pg_stat_statements for suspicious queries,
      PostgreSQL log analysis, pg_audit log
    - Recover: restore from backup if data modified, change

    - Prevent: implement least privilege, enable auditing,

LAYER 3: DEEP
────────────────────────────────────────────────────────────────

  TASK 20.D1: Encryption at Rest [DES]
    - PostgreSQL core: no built-in tablespace encryption
    - Options: filesystem-level encryption (LUKS), storage-level
      encryption (AWS EBS encryption), pg_tde extension
      (CyberTec), pg_tle (AWS Trusted Language Extensions)
    - Trade-offs: performance overhead, key management complexity

  TASK 20.D2: Audit Logging with pgaudit [OP] [DES]
    - pgaudit extension: detailed audit logging
    - Configuration: pgaudit.log (which statement classes to
      audit: READ, WRITE, DDL, ROLE, etc.), pgaudit.log_level
      (log level for audit entries)
    - Per-role auditing: pgaudit.log set per role
    - Audit log destination: PostgreSQL log (can ship to
      centralized log system)
    - Compliance: HIPAA, PCI-DSS, SOX requirements

  TASK 20.D3: Security Hardening Checklist [DES]
    - Remove public schema CREATE privilege
    - Limit superuser to 1-2 accounts (DBA personal accounts,
      not application)
    - Use SCRAM-SHA-256 (not md5)
    - Enforce SSL/TLS 1.2+
    - Enable password expiration (valid_until in pg_roles)
    - Set statement_timeout and lock_timeout per role
    - Restrict listen_addresses to specific interfaces
    - Implement firewall (iptables, security groups)
    - Regular security audit: unused roles, excessive privileges

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 20:
    - SQL injection via application (DBA must detect from logs)
    - Privilege escalation via SECURITY DEFINER function
    - RLS bypass via LEAKPROOF function
    - Data exfiltration via COPY TO PROGRAM

MODULE 21: ENTERPRISE MONITORING — PROMETHEUS + GRAFANA
================================================================================
PREREQUISITES: Modules 1-20 (all core knowledge)
PURPOSE: Production databases require continuous monitoring. Prometheus
  and Grafana are the industry standard open-source stack.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 21.1: Prometheus + postgres_exporter Setup [OP] [MON]
  - postgres_exporter: Prometheus exporter that connects to
    PostgreSQL and exposes metrics via HTTP endpoint
  - Connection: single PostgreSQL connection, runs queries
    (from queries.yaml or default metrics) to collect metrics
  - Multi-target: one postgres_exporter can scrape multiple
    PostgreSQL instances (via target parameter)
  - Default metrics: pg_stat_database, pg_stat_bgwriter,
    pg_stat_replication, pg_stat_user_tables (limited),
    database size, connection count, replication lag,
    locks (limited)
  - Custom metrics: queries.yaml defines additional queries.
    Must be careful: slow queries in exporter can cause scrape
    timeouts. Queries must use pg_stat_* views, not direct
    table scans

TASK 21.2: Key Metrics to Monitor [MON] [DES]
  - Service: pg_isready (up/down)
  - Connections: pg_stat_database.numbackends, max_connections
    utilization %
  - Transactions: xact_commit, xact_rollback rate. Deadlocks
    rate (pg_stat_database.deadlocks)
  - Cache: blks_hit / (blks_hit + blks_read) ratio per database
  - Replication: pg_stat_replication replay_lag (bytes and time),
    standby count
  - WAL: pg_wal directory size, WAL generation rate
  - Vacuum: n_dead_tup per table, last_autovacuum age,
    tables approaching wraparound
  - Locks: waiting locks count
  - Disk: filesystem usage, projected full time
  - System: CPU, memory, swap, I/O (from node_exporter)

TASK 21.3: Grafana Dashboards [MON] [OP]
  - PostgreSQL Overview: connections, TPS, cache hit ratio,
    replication lag, top queries by time
  - PostgreSQL Details: per-database stats, per-table bloat,
    autovacuum workers, checkpoint frequency
  - Replication: per-standby lag in bytes and time,
    WAL send rate, sync state
  - Query Performance: pg_stat_statements top queries,
    query throughput, latency percentiles
  - System: CPU, memory, disk I/O, network
  - Alerting: configured in Alertmanager (Module 22)

TASK 21.4: pg_stat_statements in Prometheus [MON]
  - exporter queries: query pg_stat_statements for top queries.
    Must be careful: pg_stat_statements query can itself be
    expensive (pg_stat_statements is a view, not a table)
  - Solution: periodic snapshot into monitoring-specific table
    (pg_stat_statements_snapshots), exporter reads from there
  - Metrics: calls, total_time, mean_time, rows, shared_blks_hit,
    shared_blks_read, temp_blks_written. Per queryid

TASK 21.5: Log Monitoring with pgBadger [MON] [OP]
  - pgBadger: log analysis tool that generates HTML report from
    PostgreSQL log files (with log_line_prefix configured)
  - Requires: log_min_duration_statement, log_checkpoints,
    log_connections, log_disconnections, log_lock_waits,
    log_temp_files enabled
  - Generates: query statistics (top slow queries, queries by
    type, by user), connection statistics (peak connections),
    checkpoint statistics, vacuum statistics, lock wait report,
    error report
  - Usage: daily cron job generating HTML report. Useful for
    post-mortem analysis and trend analysis

────────────────────────────────────────────────────────────────

FAILURE 21.F1: postgres_exporter Causing Load

  Diagnosis: pg_stat_activity shows exporter PID running

MODULE 22: ALERTING & INCIDENT RESPONSE
================================================================================
PREREQUISITES: Module 21 (monitoring)
PURPOSE: Monitoring tells you something is wrong. Alerting tells you
  in time to fix it. Incident response is the process of fixing it.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 22.1: Alert Design Principles [DES]
  - Signal vs noise: alerts must be actionable. If an alert
    fires and the response is "oh, that always happens, ignore
    it" — it's noise. Delete or re-tune it
  - SLI (Service Level Indicator): what you measure (e.g.,
    replication lag in seconds, query latency p95)
  - SLO (Service Level Objective): target for SLI (e.g.,
    replication lag < 30 seconds, query latency p95 < 100ms)
  - Alert threshold: set below SLO to give response time.
    For SLO of <30s, alert at >10s (warning), >20s (critical)
  - Alert duration (for): how long condition must persist
    before firing. Prevents flapping. For 30s threshold:
    for 5m (must be sustained)
  - Severity levels: P1 (critical, immediate response: database
    down, disk full, sync standby dead), P2 (high, within 30min:
    replication lag high, connections near max), P3 (warning,
    next business day: slow vacuum, bloat approaching threshold),
    P4 (info: backup completed, failover test completed)

TASK 22.2: PostgreSQL-Specific Alerts [DES] [MON]
  - Service down: pg_isready fails. Critical. Immediate response
  - Disk space: PGDATA > 80% (warning), > 90% (critical).
    pg_wal > 70% (warning). Archive storage > 80% (warning)
  - Replication lag: replay_lag > 10s (warning), > 30s (critical).
    Standby count < expected (critical)
  - Wraparound: age(datfrozenxid) > 1B (warning), > 1.5B (critical)
  - Connections: numbackends / max_connections > 80% (warning)
  - Lock wait: waiting locks > 0 for > 60s
  - Deadlocks: deadlock rate > threshold (per minute)
  - Checkpoints: checkpoints_req / checkpoints_timed > 1 (warning:
    forced checkpoints dominating)
  - Cache hit ratio: < 95% (warning), < 90% (critical)
  - Vacuum: tables with n_dead_tup/n_live_tup > 0.2 and
    last_autovacuum > 1 hour ago (warning)
  - Long queries: queries running > 5 minutes (warning)
  - Idle in transaction: > 2 minutes (warning)
  - Backup age: last backup > 25 hours (warning), > 30 hours
    (critical for daily backup)
  - SSL certificate: expiry < 30 days (warning), < 7 days (critical)

TASK 22.3: Notification Channels [OP]
  - PagerDuty/OpsGenie: P1/P2 alerts → on-call rotation
  - Slack/Teams: all alerts (with channel per severity)
  - Email: daily digest of P3/P4 alerts
  - SMS: P1 only (when PagerDuty not available)
  - Webhook: integrate with ITSM (ServiceNow, Jira)

TASK 22.4: Incident Response Process [LEAD]
  - Detection: alert fires, or user reports issue
  - Triage: on-call acknowledges, assesses severity
  - Investigation: run diagnostic queries (Module 2 portfolio),
    check monitoring dashboards, check logs
  - Mitigation: apply fix to stop the bleeding (may be temporary)
  - Resolution: permanent fix applied, verified
  - Post-mortem: blameless analysis: what happened, timeline,
    root cause, how detected, how to prevent, action items

TASK 22.5: Runbook Creation [LEAD] [AUT]
  - For each alert: runbook entry with —
    Symptom: what the alert means
    Urgency: how quickly to respond
    Diagnosis steps: specific queries to run
    Mitigation steps: what to do to stop immediate impact
    Resolution steps: how to permanently fix
    Escalation: when to escalate, to whom
  - Runbook must be: accessible during incident (not in a system
    that depends on the database being up), up-to-date, tested
  - Runbook for "Database Down":
    1. Check if PostgreSQL process is running
    2. Check system logs for crash/OOM
    3. Try to start PostgreSQL
    4. If fails: check error message (disk full, corrupted file)
    5. If won't start: restore from backup or promote standby
    6. Notify stakeholders

COMMON FAILURES FOR MODULE 22:
────────────────────────────────────────────────────────────────

FAILURE 22.F1: Alert Storm
  Symptoms: 50 alerts fire simultaneously. On-call overwhelmed
  Root cause: single root cause triggers many alerts (e.g.,
    disk full → PostgreSQL down + replication down + backups
    failing + application down = 50 alerts). All from one cause
  Diagnosis: Identify common root cause. Alertmanager grouping
    should reduce noise
  Recovery: Fix root cause. Tune alert dependencies (inhibition
    rules: if PostgreSQL down, suppress replication lag alert)
  Prevention: implement alert inhibition and grouping

FAILURE 22.F2: Alert Fire But No One Responds
  Symptoms: Alert in PagerDuty, no acknowledgment for 30 min
  Root cause: On-call rotation not configured, person on-call
    unavailable, notification channel broken, alert fatigue
    (too many false positives, team ignores)
  Diagnosis: Check on-call schedule in PagerDuty. Check
    notification delivery logs
  Recovery: Fix on-call rotation. Reduce alert noise. Implement
    escalation (if not ack'd in 5 min, escalate to manager)

FAILURE 22.F3: Runbook Out of Date
  Symptoms: On-call follows runbook steps, they don't work
    or make things worse
  Root cause: Runbook written for old version, never tested,
    describes procedure that no longer applies
  Diagnosis: Follow runbook on test system. Compare with
    actual system behavior
  Recovery: Update runbook. Schedule regular runbook review
    and testing

FAILURE 22.F4: Missed Alert Due to Monitoring Gap
  Symptoms: Incident discovered by users, not monitoring
  Root cause: No alert defined for this failure mode. Or
    metric not being collected. Or alert threshold too
    permissive
  Diagnosis: Post-mortem identifies monitoring gap
  Recovery: Add metric collection if missing. Add alert.
    Review all failure modes from Modules 1-20 for monitoring
    coverage

MODULE 23: AUTOMATION — ANSIBLE, TERRAFORM, CI/CD
================================================================================
PREREQUISITES: Module 1 (installation), Module 21 (monitoring)
PURPOSE: Manual operations don't scale. Automation ensures consistency,

  Recovery: Restore from backup. Prevention: always include
    environment confirmation (script prints "Running against
    PRODUCTION database 'X' at host 'Y'. Type 'YES' to
    continue"). Use different credentials per environment

MODULE 24: UPGRADES & ZERO-DOWNTIME MIGRATIONS
================================================================================
PREREQUISITES: Module 12 (replication), Module 14 (backup)
PURPOSE: PostgreSQL major versions are released annually. Upgrading
  safely with minimal downtime is a critical DBA skill.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 24.1: Minor Version Upgrades [OP]
  - Minor version: bug fixes and security patches only. No
    new features, no catalog changes, no data format changes
  - Process: install new packages, restart PostgreSQL (or
    pg_ctl restart). Can also use pg_ctl -D PGDATA -m fast stop
    then start
  - Patroni: rolling restart (patronictl restart). Restarts
    replicas first, then switches over primary, restarts old
    primary. Zero application downtime
  - Risk: extremely low. Test on staging anyway
  - Post-upgrade: verify version, check logs for warnings,
    run application smoke tests

TASK 24.2: pg_upgrade for Major Version Upgrades [CON] [OP]
  - pg_upgrade: in-place upgrade of data directory to new
    major version. Fast (minutes, not hours for large DBs)
  - Modes: --link (hard links, old cluster unusable after,
    fastest), --clone (copy-on-write, filesystem must support),
    copy (full file copy, safest, slowest, needs double disk)
  - Pre-check: pg_upgrade --check. Validates: extension
    compatibility, catalog differences, storage format
    compatibility. MUST PASS before actual upgrade
  - Process:
    1. Install new PostgreSQL version binaries
    2. Stop both old and new clusters (if running — pg_upgrade
       runs on stopped clusters)
    3. Run pg_upgrade
    4. Start new cluster
    5. Run analyze_new_cluster.sh (generated by pg_upgrade)
    6. Verify application works
    7. Run delete_old_cluster.sh to remove old data (after
       verification)
  - Downtime: minutes for --link mode. Clusters must be
    stopped during upgrade
  - Rollback: if upgrade fails, restore from pre-upgrade backup

TASK 24.3: Logical Replication for Zero-Downtime Upgrade [CON] [DES]
  - When pg_upgrade downtime is unacceptable (or extension
    incompatibility prevents pg_upgrade)
  - Process:
    1. Set up new PostgreSQL major version instance
    2. On old: CREATE PUBLICATION for all tables
    3. On new: CREATE SUBSCRIPTION, copy_data=true (or use
       pg_dump for initial schema+data)
    4. Let replication catch up (near-zero lag)
    5. Stop application writes (brief downtime: seconds)
    6. Wait for replication to fully catch up
    7. Sync sequences on new instance
    8. Point application to new instance
    9. Start writes on new instance
    10. Drop subscription, drop publication
  - Limitations: DDL must be manually applied to both
    instances. Sequences not replicated (manual sync).
    Large objects not replicated. Some extensions have
    custom upgrade paths

TASK 24.4: Extension Compatibility During Upgrade [CON] [DIAG]
  - Before upgrade: list all extensions in old cluster
    (\dx). For each:
    - Is it a contrib extension? (shipped with PostgreSQL,
      always compatible with new version — no upgrade needed
      for extension itself)
    - Is it third-party? Check compatibility matrix with
      new PostgreSQL major version
    - Some extensions require separate upgrade (PostGIS
      often needs upgrade between major PG versions)
  - pg_upgrade --check will detect incompatible extensions
  - After upgrade: ALTER EXTENSION ... UPDATE if extension
    has newer version available for new PostgreSQL

COMMON FAILURES FOR MODULE 24:
────────────────────────────────────────────────────────────────

FAILURE 24.F1: pg_upgrade --check Fails
  Symptoms: Check reports errors: extension incompatibility,
    catalog corruption, encoding issues, tablespace issues
  Root cause: (1) Third-party extension not compatible with
    new PG version — must upgrade extension or drop it before
    upgrade. (2) Logical replication slots exist — must drop
    them. (3) Some pg_upgrade checks require specific extension
    updates
  Diagnosis: Read check output carefully. Each error has
    specific meaning
  Recovery: Fix each issue reported. For extension incompatibility:
    install compatible extension version in new PostgreSQL.
    For replication slots: drop logical slots, recreate after
    upgrade. Rerun --check until clean

FAILURE 24.F2: pg_upgrade Fails Mid-Upgrade
  Symptoms: pg_upgrade starts but fails partway through.
    Data in inconsistent state
  Root cause: Disk full during copy, permission error, OS
    kill (OOM), unexpected files in data directory
  Diagnosis: Check pg_upgrade log files
  Recovery: Restore from pre-upgrade backup. Do NOT attempt
    to start new cluster if upgrade failed — data may be
    corrupted. If --link mode: old cluster is untouched
    (links were created to new location, but old data still
    exists). Can restart old cluster

FAILURE 24.F3: Post-Upgrade Application Errors
  Symptoms: Upgrade successful, new cluster starts, but
    application queries fail or return wrong results
  Root causes: (1) Collation version mismatch — text indexes
    may need REINDEX. (2) Deprecated function removed.
    (3) Planner behavior changed. (4) Extension version
    changed behavior
  Diagnosis: Check PostgreSQL logs for errors. Compare
    EXPLAIN output for critical queries between old and
    new version. Test application on staging before production
  Recovery: REINDEX for collation issues. Update application
    code for deprecated functions. If critical: rollback
    to old version (restart old cluster)

FAILURE 24.F4: Logical Replication Upgrade — Sequence Desync
  Symptoms: After cutover to new instance, duplicate key
    errors on INSERT. Sequences on new instance returning
    values that already exist
  Root cause: Sequences are not replicated by logical
    replication. New instance sequences start at 1 or
    whatever was set during schema creation. While replication
    was running, old instance consumed sequence values.
    New instance didn't see those increases
  Diagnosis: Compare last_value in sequences between old
    and new instances
  Recovery: Before cutover, on old instance: SELECT
    setval('seq_name', (SELECT max(id) FROM table) + 1000)
    to advance sequences beyond current max. Then sync
    sequence values to new instance. Or: after cutover,
    update sequences on new instance to max(id) + 1

FAILURE 24.F5: Application Assumes Specific PostgreSQL Version
  Symptoms: After upgrade, application uses function that
    was removed or changed in new version. Version check
    fails
  Root cause: Application code tied to specific PG version
  Diagnosis: Application logs show function not found error.
    Check PostgreSQL release notes for removed functions
  Recovery: Update application code. Run application
    compatibility tests as part of upgrade testing

  TASK 24.D1: pg_upgrade Internals [CON]
    - pg_upgrade copies or links data files from old PGDATA
      to new PGDATA
    - For --link mode: creates hard links (same inode, no
      extra disk space). Old and new PGDATA must be on
      same filesystem (hard link limitation). After upgrade:
      both directories point to same data blocks. Deleting
      old cluster removes directory entries but data blocks
      remain (referenced by new cluster)
    - What pg_upgrade does: (1) Copies configuration files,
      (2) Links/copies data files, (3) Upgrades system
      catalogs (runs pg_upgrade_support functions to
      migrate catalog format), (4) Creates new WAL and
      transaction status
    - What pg_upgrade doesn't do: (1) Change data file format
      (binary compatible across major versions), (2) Reindex
      (indexes remain same format), (3) Update statistics
      (run analyze_new_cluster.sh)

  TASK 24.D2: Testing Upgrade on Different Hardware [DES]
    - Upgrade test environment: should match production
      PostgreSQL version, extensions, approximate data
      volume, similar hardware
    - Restore production backup to test server, run pg_upgrade,
      test application
    - Measure: upgrade duration, application compatibility,
      query performance changes
    - Rollback test: restore pre-upgrade backup, verify
      old version still works correctly

  TASK 24.D3: Multi-Version Upgrade Path [DES]
    - Upgrading from PG13 to PG17: can do directly
      (pg_upgrade supports skipping intermediate versions)
    - Or: incremental upgrades (PG13→14→15→16→17). Each
      step tests compatibility. Slower but safer for
      very old versions
    - Extension path: check each extension's supported
      PostgreSQL version range

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 24:
    - pg_upgrade on filesystem without hard link support
      (NFS, some virtual filesystems)
    - WAL directory missing or incorrectly configured
      for new cluster
    - New PostgreSQL binary compiled with different options
      than old (missing extension support)
    - Old cluster has unlogged tables (pg_upgrade requires
      them to be truncated or dropped)

MODULE 25: DISASTER RECOVERY & BUSINESS CONTINUITY
================================================================================
PREREQUISITES: All preceding modules
PURPOSE: DR is the ultimate test of DBA competence. When everything
  fails, you must recover. This module integrates backup, replication,
  HA, and procedural knowledge.

LAYER 1: SURFACE
────────────────────────────────────────────────────────────────

TASK 25.1: DR Planning [DES]
  - Define RTO (Recovery Time Objective): maximum acceptable
    time to restore service after disaster. Drives:
    backup restore speed, standby promotion speed, DNS/VIP
    cutover speed
  - Define RPO (Recovery Point Objective): maximum acceptable
    data loss measured in time. Drives: replication sync mode,
    WAL archival frequency, backup frequency
  - Disaster scenarios (ranked by likelihood and impact):
    - Primary database server failure (hardware)
    - Primary database filesystem corruption
    - Accidental DROP TABLE/DATABASE
    - Data center/availability zone failure
    - Region failure (cloud provider regional outage)
    - Ransomware/corruption of entire database
    - PostgreSQL bug causing data corruption
  - DR strategy for each scenario: documented, tested

TASK 25.2: DR Architecture Patterns [DES]
  - Single region HA (not full DR): Patroni cluster within
    one AZ or multiple AZs. Protects against server failure.
    Does NOT protect against AZ or region failure
  - Cross-region DR with async standby: primary in region A,
    async standby in region B. RPO = replication lag
    (seconds to minutes). RTO = promote standby + DNS cutover
    (minutes)
  - Cross-region DR with sync standby: sync standby in
    region A (same region, low latency), async standby in
    region B. Primary fails: promote sync standby (zero data
    loss). Region A fails: promote async standby in region B
    (RPO = lag). Trade-off: sync in same region protects
    against server failure without performance penalty of
    cross-region sync
  - Backup-based DR: restore from backup in new region.
    RPO = time since last backup (hours). RTO = backup
    restore time + WAL replay (hours). Slowest but simplest
  - Logical replication DR: logical replication to DR site.
    Allows selective replication. Sequences and DDL not
    replicated (manual)

TASK 25.3: DR Procedures and Runbooks [LEAD] [REC]
  - Runbook for "Primary Region Lost":
    1. Confirm region failure (not just network partition)
       — check cloud provider status, try connecting from
       multiple locations
    2. Decision: declare disaster, initiate DR
    3. If async standby in DR region: verify standby state
       (is it up? lag?)
    4. Promote standby in DR region
    5. Verify promotion: can accept writes, data integrity
    6. Update DNS/VIP to point to new primary
    7. Update application configuration (connection strings)
    8. Verify application functionality
    9. Notify stakeholders: DR activated, estimated recovery
       time, known data loss (if any)
    10. After primary region restored: rebuild as standby
        (or keep DR as primary, rebuild old primary as
        standby — decision based on proximity to users)

TASK 25.4: DR Testing [OP] [REC]
  - DR test types:
    - Tabletop: walk through runbook with team. No actual
      systems changed. Finds gaps in procedures
    - Simulation: test specific component (promote standby,
      DNS cutover, application reconnect). Real systems
      involved but controlled
    - Full DR drill: simulate complete primary failure.
      Cut over to DR site. Run production traffic from
      DR site for defined period. Cut back. Full validation
  - DR test frequency: tabletop quarterly, simulation
    quarterly, full drill annually
  - DR test validation:
    - RTO: actual time from disaster declaration to
      application serving traffic
    - RPO: data difference between primary at failure
      and DR after promotion (compare row counts, sample
      recent transactions)
    - Application: all critical functions work from DR
    - Performance: DR site can handle production load
  - Post-test: document results, identified issues, action
    items. Update runbook

TASK 25.5: Backup Verification for DR [OP]
  - Backup restore test: regularly (monthly) restore most
    recent backup to isolated environment. Verify:
    database starts, basic queries work, expected tables
    and data present
  - PITR validation: restore backup + replay WAL to specific
    point. Verify data consistency at that point
  - Cross-region backup: ensure backup is stored in different
    region from primary (for region failure DR). Test restore
    from cross-region backup
  - Backup integrity: pg_verifybackup, pgBackRest check,
    WAL-G verify

COMMON FAILURES FOR MODULE 25:
────────────────────────────────────────────────────────────────

FAILURE 25.F1: DR Test Reveals Backup Is Unusable
  Symptoms: During DR drill, backup restore fails.
    pg_verifybackup reports errors. Database won't start
  Root cause: Backup was corrupted (disk error on backup
    storage). Backup script was failing silently.
    archive_command was failing, WAL archive incomplete
  Diagnosis: Check backup tool logs from time of backup.
    Check pg_stat_archiver history
  Recovery: Restore earlier backup (if available). Accept
    greater data loss. Fix backup process immediately
  Prevention: Automated backup verification after each
    backup. Automated restore test regularly

FAILURE 25.F2: DR Promotion Leaves Standby Unusable
  Symptoms: Standby promoted successfully, but applications
    fail with query errors
  Root cause: Standby was in recovery mode and didn't apply
    all WAL (lag). Some data is missing. Or: standby had
    different extensions installed. Or: connection pooling
    points to wrong port
  Diagnosis: Check pg_stat_replication on old primary
    (if up). Check standby logs during promotion. Test
    application queries manually
  Recovery: If WAL available: apply missing WAL before
    promotion. If not: accept data loss. Fix application
    connection routing

FAILURE 25.F3: Split-Brain During DR Transition
  Symptoms: Both old primary and DR standby accepting writes.
    Applications routed to different nodes
  Root cause: Network partition (primary region not actually
    down, just unreachable from DR decision point). DR was
    activated, standby promoted. Primary still running,
    applications in primary region still writing
  Diagnosis: Data divergence detected (different data on
    both nodes). Timeline mismatch
  Recovery: STOP ALL WRITES. Determine which node has
    authoritative data. Discard writes on other node.
    pg_rewind if possible. Manual conflict resolution if not
  Prevention: Fencing mechanism (ensure old primary is
    truly isolated before promoting). Always attempt to
    shut down old primary before promoting standby

FAILURE 25.F4: DNS/VIP Failover Delays RTO
  Symptoms: Standby promoted successfully, but application
    still connecting to old primary IP
  Root cause: DNS TTL too high (cached old IP). VIP not
    moved or moved slowly. HAProxy not updated
  Diagnosis: nslookup database.example.com from application
    server. Ping to VIP. Check HAProxy backend status
  Recovery: Decrease DNS TTL (plan ahead). Manual DNS flush
    or hosts file entry as emergency. Fix VIP/HAProxy config
  Prevention: Low DNS TTL (60s). Automated VIP movement.
    Health checks from application side

FAILURE 25.F5: DR Runbook Relies on Person Who Left Company
  Symptoms: DR event occurs. Runbook references "ask Alice
    for credentials" or "use Bob's script". Alice/Bob left
  Root cause: Runbook not updated, not self-contained.
    Credentials not in shared vault
  Diagnosis: Attempt to follow runbook. Encounter
    dependencies on unavailable people
  Recovery: Escalate, access needed credentials through
    emergency process (manager, vault break-glass)
  Prevention: Runbook must be standalone — anyone on
    team can execute. Credentials in shared password
    manager with emergency access. Regular runbook review
    and testing by different team members

LAYER 2: CONNECTED (after all modules)

  CROSS-TOPIC TASK 25.X1: DR → Everything

  CROSS-TOPIC TASK 25.X2: DR → Economics
    - DR costs: idle infrastructure in DR region
      (compute, storage, data transfer for replication)
    - Insurance analogy: DR is insurance against
      catastrophic loss. Premium = DR infrastructure
      cost. Coverage = RPO/RTO
    - Business case: cost of downtime per hour vs
      annual DR cost. DR is justified if: annual
      downtime probability × hourly cost × hours
      downtime > DR annual cost

  COMBINED FAILURE 25.XF1: Worst Case — Complete Data Loss
    All copies fail:
    - Primary down (server destroyed)
    - Replication lag caused data loss on standby
    - Backup corrupted (undetected)
    - Offsite backup also corrupted (same script bug)
    - WAL archive incomplete
    This is a business-ending event for many companies.
    For a DBA: ensure this NEVER happens through:
    - Multiple backup methods (pg_dump + physical)
    - Multiple backup destinations (different cloud
      providers, different regions)
    - Automated backup verification
    - Regular restore testing
    - Independent validation (someone other than the
      automation script writer verifies backups)

LAYER 3: DEEP
────────────────────────────────────────────────────────────────

  TASK 25.D1: Multi-Site Active-Active (Advanced) [DES]
    - True active-active: both sites accept writes.
      Conflict resolution required
    - PostgreSQL solutions: BDR (Bi-Directional Replication)
      from EDB, pgEdge, or custom logical replication
      with conflict resolution
    - Complexity: high. Application must handle conflicts.
      Not recommended unless business requirements demand it
    - Alternative: active-passive with fast failover is
      sufficient for most organizations

  TASK 25.D2: Chaos Engineering for Databases [DES]
    - Netflix Simian Army concept applied to databases
    - Automated DR testing: randomly kill primary,
      verify application recovers within RTO
    - Chaos experiment: network latency injection,
      disk fill, process kill
    - Measure: time to detect, time to recover, data
      consistency after recovery
    - Run in production (start with non-production):
      chaotic testing builds real confidence

  TASK 25.D3: DR Documentation [LEAD]
    - DR plan document: architecture diagrams, contact
      list (with alternates), step-by-step runbooks,
      decision criteria, rollback procedures
    - Stakeholder communication templates: initial
      notification, status updates, resolution notice
    - Compliance: document DR test results for auditors
      (SOC2, HIPAA, PCI-DSS)

  EXHAUSTIVE FAILURE CATALOG FOR MODULE 25:
    - DR site credentials expired (AWS keys rotated,
      forgot to update DR site)
    - DR site PostgreSQL version too old (forgot to
      upgrade DR standby)
    - Data sovereignty violation (DR in wrong country)
    - Application hard-coded to primary region endpoints
