Wrong. And if you go into your first production DBA role thinking that way, you're going to spend a lot of sleepless nights.

I've been doing this for twenty years, and I can tell you with absolute certainty: more database performance problems are caused by *bad* indexes than by no indexes at all. I mean that. A few years back, I was called into a financial services company that was getting hammered by slow reports. They had 247 indexes on a single table. Two hundred and forty-seven. Most of them did nothing. Some of them actively hurt query performance. It took me three weeks to clean that mess up, and in the process, I saved them about forty thousand dollars a month in hardware that they didn't need to buy.

So here's what we're going to do today. We're going to build your mental model from the ground up. You're going to understand *why* an index exists, *how* PostgreSQL actually uses it, and — critically — *when* you should build one and when you should walk away.

Let's start with the fundamental question: What is an index?

================================================================================
WHAT IS AN INDEX? (THE HONEST ANSWER)
================================================================================

An index is, at its core, a data structure that trades disk space and write performance for faster reads. That's it. Everything else is details.

Think about the back of a textbook — the index. You don't read the entire textbook looking for mentions of "database transactions." You flip to the back, look up "transactions," and it tells you "see pages 142, 187, 203." You go directly there. Without that index, you'd read page one, page two, page three... for hundreds of pages. That's expensive and stupid.

A database index works exactly the same way. Instead of scanning every single row in a table to find the ones you want, the index lets you jump directly to the rows that match your search. It's a lookup mechanism.

Now, you might ask: if indexes are so great, why don't we just index everything?

Good question. Here's why. When you insert, update, or delete a row in a table that has an index on it, PostgreSQL has to *maintain* that index. It has to update the index structure. And that costs time and disk I/O. It also costs disk space — the index is stored separately from the table, and if you have fifty indexes, you're storing that data fifty times over.

In production, I've seen servers where the total size of indexes exceeded the size of the actual tables by three to four times. That means every single write operation is four times more expensive than it needs to be. And for a busy OLTP system, that's a killer.

So indexes are not free. They're a trade-off. Good database design means *choosing* the right indexes for your workload. Not index-everything, and not index-nothing. Something in the middle.

================================================================================
THE B-TREE: HOW INDEXES ACTUALLY WORK
================================================================================

Okay, let me tell you how PostgreSQL actually implements indexes. The default, and the one you'll use 99% of the time, is called a B-Tree. (That's B-Tree, not Binary Tree. B stands for "balanced." A computer scientist named Rudolf Bayer invented it in 1971, and honestly, it's still brilliant.)

Here's the concept. Imagine you have a table with a million rows, and you want to find all customers with the last name "Smith." Without an index, you read all million rows from disk — worst case, you touch every row. That's expensive.

With a B-Tree index, the data is organized in a tree structure. The tree has a *root* node at the top, intermediate nodes in the middle, and *leaf* nodes at the bottom. Each node can hold multiple entries. And here's the key part: the data in the tree is *sorted*.

So if you're looking for "Smith," PostgreSQL starts at the root node, which might tell it, "If you're looking for names from A-M, go left. If you're looking for N-Z, go right." It goes right. The next node might say, "A-I go left, J-Z go right." It goes right again. And it keeps drilling down until it reaches the leaf nodes, which contain actual row identifiers (called TIDs — tuple identifiers) pointing back to the table.

The beautiful part? Because the data is sorted and the tree is balanced, PostgreSQL can find any value in a million rows by touching maybe... twenty nodes. Instead of a million disk reads, you do twenty. That's a *five-thousand-times* speedup. That's the power of an index.

And yes, I'm talking about disk reads. If those twenty nodes are in memory (the buffer cache), it's even faster — microseconds. If they're on disk, it's milliseconds. Either way, it beats scanning a million rows.

================================================================================
SEEKS, SCANS, AND LOOKUPS: WHAT YOUR QUERY IS ACTUALLY DOING
================================================================================

Alright, now I want to introduce three terms that you're going to hear constantly in this course, and you absolutely must understand the difference.

**Index Seek**: The query uses the index to jump directly to the rows it needs. This is what you want. Fast. Efficient. You're finding your starting point and reading forward from there.

**Index Scan**: The query reads the entire index from top to bottom. This is less efficient than a seek, but sometimes it's unavoidable. For instance, if you ask for "all customers," well, you can't avoid reading the whole index.

**Lookup** (or Bookmark Lookup): Once the index finds the row identifier, it has to go back to the main table to fetch the actual data. This is a second trip to disk. It's not bad, but it's not free.

Let me show you this in action. I'm going to create a simple demo table.

Go ahead, open psql or whatever tool you're using to connect to Postgres. Let's type this together.

---

CREATE TABLE customers (
    customer_id BIGINT PRIMARY KEY,
    last_name VARCHAR(100),
    first_name VARCHAR(100),
    email VARCHAR(100),
    phone VARCHAR(20),
    created_at TIMESTAMP
);

---

Okay, now let's load some data. I'm going to insert a million rows. This is going to take a minute.

---

INSERT INTO customers (customer_id, last_name, first_name, email, phone, created_at)
SELECT 
    g.id,
    'Smith'::VARCHAR,
    'John'::VARCHAR || g.id,
    'john' || g.id || '@example.com',
    '555-' || LPAD((g.id % 10000)::TEXT, 4, '0'),
    CURRENT_TIMESTAMP - (random() * INTERVAL '365 days')
FROM generate_series(1, 1000000) AS g(id);

---

Good. While that's running, let me explain what we just did. `generate_series` is a Postgres function that creates a set of rows with sequential numbers. We're inserting a million customers, all with last name "Smith" (I'm lazy; in real data, they'd be diverse). The important part is that we have a lot of rows to work with.

Okay, it's done. Now let's run a query against this table without any index:

---

EXPLAIN ANALYZE
SELECT customer_id, first_name, email
FROM customers
WHERE last_name = 'Smith' AND first_name LIKE 'John%';

---

Hit enter. Look at the output. You'll see something like:

    Seq Scan on customers
    Filter: ((last_name = 'Smith'::text) AND (first_name ~~* 'John%'))
    Rows: 1000000

That's a "Sequential Scan" — also called a "Table Scan." PostgreSQL is reading the entire table in sequence, from the first row to the last, applying filters as it goes. It had to examine all 1 million rows.

Now, let's create an index on the `last_name` column:

---

CREATE INDEX idx_customers_last_name ON customers(last_name);

---

Now let's run the same query again:

---

EXPLAIN ANALYZE
SELECT customer_id, first_name, email
FROM customers
WHERE last_name = 'Smith' AND first_name LIKE 'John%';

---

Look at what changed. Now you'll see something like:

    Index Scan using idx_customers_last_name on customers
    Index Cond: (last_name = 'Smith')
    Filter: (first_name ~~* 'John%')
    Rows: 1000000

Interesting, right? We *created* an index on `last_name`, and PostgreSQL *used* it — but it still read 1 million rows. Why? Because every single row in our table has `last_name = 'Smith'`. The index brought us to the first Smith, but then we had to scan through all the Smiths.

In a real-world table with diverse last names — say, ten thousand different last names — that index would have brought us to just the Smiths, and we'd be reading maybe ten thousand rows, not a million. That's a 100x improvement.

The key takeaway: an index is only useful if it reduces the number of rows you have to examine. If you're going to touch 99% of the table anyway, an index doesn't help much.

================================================================================
INSTRUCTOR WARNING: THE COVERING INDEX TRAP
================================================================================

Okay, I'm going to stop here and tell you something critical. This is a war story.

I worked at a company that was running a real-time trading platform. Millions of trades per second. Genuinely high-volume. The lead DBA was obsessed with performance, and in 2014, he read an article about "covering indexes" and became convinced that the solution to all of our problems was to build massive covering indexes that included every column needed for a query.

He was half-right, as many obsessed people are.

A covering index — which we'll get into in a moment — is an index that includes all the columns a query needs, so the database never has to look up the actual table. It's just "covering" everything the query wants. It's fast. It's elegant.

The problem? He built hundreds of them. Every index he created had fifteen, twenty, thirty columns in it. And because the system was so high-volume, maintaining those indexes was consuming 60% of the database CPU. Queries that should have run in 10 milliseconds were taking 500 milliseconds because the *writes* were slow. The database was thrashing.

It took us three months to fix. We had to delete three hundred indexes. It was chaos.

Here's the lesson: **Just because you *can* build a covering index doesn't mean you *should*. Measure first. Understand your workload. Don't optimize for the select queries if it means destroying the performance of your inserts and updates.**

Okay. End of warning. Let me teach you covering indexes the right way.

================================================================================
COVERING INDEXES: AVOIDING THE TABLE LOOKUP
================================================================================

So here's the concept. When you run a query, PostgreSQL has to:

1. Use the index to find the row identifiers (TIDs)
2. Go back to the table and fetch the actual data

That second step — step 2 — is called a "lookup" or sometimes a "bookmark lookup." It's another disk operation. If your index doesn't have the data you need, you have to go back to the table and get it.

A **covering index** is an index that *includes* all the columns you need so you never have to go back to the table. The index has everything. PostgreSQL can satisfy the entire query from the index alone.

In PostgreSQL, you do this with the `INCLUDE` clause. Let me show you.

---

CREATE INDEX idx_customers_lastname_covering 
ON customers(last_name) 
INCLUDE (first_name, email);

---

This index is organized by `last_name`, but it also includes `first_name` and `email`. Now, when you run a query that needs those columns, PostgreSQL can get everything from the index without going back to the main table.

Let's test it:

---

EXPLAIN ANALYZE
SELECT customer_id, first_name, email
FROM customers
WHERE last_name = 'Smith'
LIMIT 10;

---

You'll see something like:

    Index Only Scan using idx_customers_lastname_covering on customers
    Index Cond: (last_name = 'Smith')
    Rows: 10

Notice it says "Index Only Scan" — not "Index Scan" followed by a lookup. The index satisfied the entire query. That's the covering index in action.

Now, here's the nuance. The `INCLUDE` columns are not part of the index's *structure*. You can't search on them. The index is still organized by `last_name`. The INCLUDE columns are just… along for the ride. They're stored in the leaf nodes but not in the intermediate nodes.

Why does that matter? Because it makes them cheap. Your index is still small and efficient. You're not bloating the structure with a bunch of extra data at every level. You're just saying, "When you get to the leaf, also grab these columns."

Use covering indexes when:
- You have specific queries that are running constantly
- The query requires only a few columns beyond the index key
- You're willing to pay a small amount of extra storage for faster reads

Don't use them when:
- You're trying to cover every possible query
- You have lots of writes (maintaining the INCLUDE columns has a cost)
- The columns you're including are large (TEXT, JSON, etc.)

================================================================================
COMPOSITE INDEXES: THE REAL POWER
================================================================================

Now, let's talk about composite indexes — indexes with more than one column. This is where indexing gets interesting, because *column order matters*. It matters a lot.

Let me create a new scenario. Let's say you have a table of orders, and you frequently query it like this:

"Give me all orders from customer 42 placed in the last 30 days."

That query has two conditions: `customer_id` and `created_at`. You *could* create two separate indexes — one on `customer_id` and one on `created_at`. But that's inefficient. PostgreSQL would have to use one index, find the rows, then apply the second condition as a filter.

Better to create a *composite* index that covers both columns:

---

CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    customer_id BIGINT,
    created_at TIMESTAMP,
    total_amount DECIMAL(10, 2),
    status VARCHAR(20)
);

INSERT INTO orders (order_id, customer_id, created_at, total_amount, status)
SELECT 
    g.id,
    (random() * 100000)::BIGINT,
    CURRENT_TIMESTAMP - (random() * INTERVAL '365 days'),
    (random() * 10000)::DECIMAL,
    CASE WHEN random() < 0.5 THEN 'completed' ELSE 'pending' END
FROM generate_series(1, 1000000) AS g(id);

---

Now, the question is: when you create a composite index, what order should the columns be in?

This is critical. The answer depends on your query patterns. PostgreSQL uses the index *left to right*. So if your index is:

    CREATE INDEX idx_orders_customer_date ON orders(customer_id, created_at);

PostgreSQL can efficiently search for:
- WHERE customer_id = 42 (uses the whole index)
- WHERE customer_id = 42 AND created_at > '2024-01-01' (uses the whole index)

But it *cannot* efficiently search for:
- WHERE created_at > '2024-01-01' (only uses the customer_id part, which doesn't help)

Why? Because the index is organized primarily by `customer_id`. The rows are sorted first by customer_id, then by created_at within each customer_id. If you don't have a customer_id, you can't use the first level of the tree.

This is called the **"leading column" problem**. The leftmost column in your composite index is the most important one. It has to be part of every query you want the index to help with, or the index can't help at all.

So here's the rule: Put your most selective column first — the column that filters out the most rows. Then put the next-most selective column second. And so on.

In our case, if you're filtering 100,000 customers to customer_id 42, that's way more selective than filtering dates. So `customer_id` first, `created_at` second. That's the right order.

Let me show you this in action:

---

CREATE INDEX idx_orders_customer_date 
ON orders(customer_id, created_at);

EXPLAIN ANALYZE
SELECT order_id, total_amount
FROM orders
WHERE customer_id = 42 AND created_at > '2024-01-01';

---

You'll see an Index Seek — fast. PostgreSQL jumped right to customer 42, then scanned forward to just the recent orders. Maybe a hundred rows examined instead of a million.

Now let's see what happens if you query by date only:

---

EXPLAIN ANALYZE
SELECT order_id, total_amount
FROM orders
WHERE created_at > '2024-01-01';

---

You'll probably see a Seq Scan — a table scan — because the index doesn't help. It's organized by customer first, so starting with a date filter is inefficient.

This is why you can't just throw a composite index at every query. You have to think about your access patterns. What queries are running? How are they filtering? Build the indexes to match.

In a mature production system, the DBA usually has documentation that lists the top fifty queries — the ones that actually matter — and indexes are built around those. You don't try to optimize every possible query. You optimize the ones that matter.

================================================================================
THE QUERY OPTIMIZER: HOW POSTGRESQL DECIDES
================================================================================

At this point, you might be asking: "How does PostgreSQL decide whether to use an index or not?"

That's the job of the *query optimizer*, also called the *query planner*. It's a component of PostgreSQL that looks at your SQL query and decides the cheapest way to execute it.

When you run:

    SELECT * FROM customers WHERE last_name = 'Smith';

The optimizer looks at the query and thinks: "I have two choices. I can scan the whole table, or I can use the index on last_name. Which is cheaper?"

To make that decision, it uses *statistics*. PostgreSQL gathers statistics about your tables — how many rows, how many distinct values, how spread out the data is. It uses these statistics to estimate how many rows a query will return.

Then it calculates the cost of each option:
- Table scan: read all N rows = cost of N * disk_read_cost
- Index scan: read X index nodes + Y table lookups = cost of (X + Y) * disk_read_cost

Whichever costs less, that's what it uses.

Here's the thing though: *the optimizer can be wrong*. If your statistics are stale, the optimizer might make a bad decision. Or if the statistics show that 90% of the rows have `last_name = 'Smith'`, a table scan might actually be cheaper than an index, because you're going to read almost everything anyway.

This is why we use the `ANALYZE` command. It updates the statistics:

---

ANALYZE customers;

---

Run that periodically. I usually have it running on a nightly schedule. If you don't keep your statistics fresh, the optimizer will start making bad decisions.

You can also see what the optimizer thinks by using `EXPLAIN`:

    EXPLAIN SELECT * FROM customers WHERE last_name = 'Smith';

And if you add `ANALYZE` to actually run the query and see what *really* happened:

    EXPLAIN ANALYZE SELECT * FROM customers WHERE last_name = 'Smith';

The difference between the estimated rows and the actual rows tells you whether the statistics are accurate.

Alright, let me give you a concrete example of how this all ties together.

================================================================================
PUTTING IT TOGETHER: A COMPLETE EXAMPLE
================================================================================

Let me build out a realistic scenario. You're the DBA for an e-commerce company. The application team comes to you and says, "Our customer search is slow. Can you speed it up?"

You ask them what the query looks like. They tell you:

    SELECT customer_id, last_name, first_name, email
    FROM customers
    WHERE last_name LIKE 'Smit%'
    AND created_at > CURRENT_DATE - INTERVAL '1 year'
    ORDER BY last_name, first_name;

Okay, let's break down what they need:

1. They're searching for last names starting with "Smit" (LIKE is a pattern match)
2. They only care about customers created in the last year
3. They want the results sorted by last name and first name
4. They need four columns: customer_id, last_name, first_name, email

Now, let's think about indexing. A LIKE 'Smit%' can use a B-Tree index on `last_name` because it's a prefix match. An index can find all last names starting with "Smit" efficiently. But `created_at > CURRENT_DATE - INTERVAL '1 year'` is a range condition. That can also use an index. And the ORDER BY can use an index too, if we structure things right.

Here's what I'd build:

---

CREATE INDEX idx_customers_lastname_created 
ON customers(last_name, created_at)
INCLUDE (first_name, email);

---

This index:
- Is organized by last_name first, created_at second (matching the query filters)
- Includes first_name and email (so we don't need a lookup)

Now let's see how it performs:

---

EXPLAIN ANALYZE
SELECT customer_id, last_name, first_name, email
FROM customers
WHERE last_name LIKE 'Smit%'
AND created_at > CURRENT_DATE - INTERVAL '1 year'
ORDER BY last_name, first_name;

---

This should give you an "Index Only Scan" using the index we just created. Efficient. Fast.

But here's something important I want to show you. Let me run a different query:

---

EXPLAIN ANALYZE
SELECT customer_id, last_name, first_name, email
FROM customers
WHERE created_at > CURRENT_DATE - INTERVAL '1 year'
AND last_name LIKE 'Smit%'
ORDER BY last_name, first_name;

---

Same WHERE conditions, different order. Same results, right? Same index? Let me show you.

Actually, yes. The WHERE clause order doesn't matter. PostgreSQL is smart enough to reorder the conditions. The optimizer looks at the index and says, "I can use this index no matter which condition was written first."

But here's one more scenario. What if they ask for a different query:

---

EXPLAIN ANALYZE
SELECT customer_id, last_name, first_name, email
FROM customers
WHERE first_name = 'John'
AND created_at > CURRENT_DATE - INTERVAL '1 year';

---

Now we're filtering by `first_name`, which is not the leading column of our index. The index still might be used, but inefficiently. PostgreSQL would have to scan the whole index, then filter by first_name. That's not ideal.

If this became a frequent query, you might need a different index, or you'd add first_name to the existing index. But you can't add it as a leading column without breaking other queries. This is the balancing act.

In a real production system, you'd collect query metrics. You'd see what's running. You'd build indexes around the top 80% of the workload and accept that 20% of queries might not be perfect. That's pragmatism.

LAB EXERCISE: BUILD AND ANALYZE YOUR OWN INDEXES
================================================================================

Alright, here's what you're going to do. I want you to do this hands-on. You're going to build some indexes, measure their impact, and learn by doing.

**Part 1: Create the base scenario**

Run these commands. They'll create a realistic orders table with some data:

---

DROP TABLE IF EXISTS orders CASCADE;

CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    order_date TIMESTAMP NOT NULL,
    ship_date TIMESTAMP,
    total_amount DECIMAL(10, 2),
    status VARCHAR(20)
);

INSERT INTO orders (order_id, customer_id, product_id, order_date, ship_date, total_amount, status)
SELECT 
    g.id,
    (random() * 10000)::BIGINT,
    (random() * 1000)::BIGINT,
    CURRENT_TIMESTAMP - (random() * INTERVAL '2 years'),
    CURRENT_TIMESTAMP - (random() * INTERVAL '365 days'),
    (random() * 5000)::DECIMAL,
    CASE 
        WHEN random() < 0.7 THEN 'shipped'
        WHEN random() < 0.2 THEN 'pending'
        ELSE 'cancelled'
    END
FROM generate_series(1, 500000) AS g(id);

ANALYZE orders;

---

**Part 2: Understand the baseline**

Now, write out the execution plan for this query without any indexes:

---

EXPLAIN ANALYZE
SELECT customer_id, COUNT(*) as order_count, SUM(total_amount) as total_spent
FROM orders
WHERE status = 'shipped'
AND order_date > CURRENT_DATE - INTERVAL '1 year'
GROUP BY customer_id
LIMIT 20;

---

Write down how many rows were examined. This is your baseline.

**Part 3: Create a composite index**

Now create an index that you think will help this query:

---

CREATE INDEX idx_orders_status_date ON orders(status, order_date);

---

Re-run the EXPLAIN ANALYZE. Did it get better? By how much? Write down the numbers.

**Part 4: Try a different order**

Delete the index and try the columns in reverse order:

---

DROP INDEX idx_orders_status_date;

CREATE INDEX idx_orders_status_date ON orders(order_date, status);

---

Re-run the EXPLAIN ANALYZE again. Is it better or worse? Why do you think that is?

**Part 5: The covering index experiment**

Now try adding an INCLUDE clause to cover the columns you need:

---

DROP INDEX idx_orders_status_date;

CREATE INDEX idx_orders_status_date 
ON orders(status, order_date) 
INCLUDE (customer_id, total_amount);

---

Re-run the EXPLAIN ANALYZE. Is it an "Index Only Scan"? How much faster?

**Part 6: Think about the trade-offs**

Now, think about this: These indexes are helping your SELECT queries. But what about INSERT? Update the index size. Create a test that inserts 10,000 new rows and time how long it takes *with* the indexes versus *without* them.

---

DELETE FROM orders; -- Clear for the test

-- Time this without indexes:
INSERT INTO orders (order_id, customer_id, product_id, order_date, ship_date, total_amount, status)
SELECT 
    g.id + 1000000,
    (random() * 10000)::BIGINT,
    (random() * 1000)::BIGINT,
    CURRENT_TIMESTAMP - (random() * INTERVAL '2 years'),
    CURRENT_TIMESTAMP - (random() * INTERVAL '365 days'),
    (random() * 5000)::DECIMAL,
    'shipped'
FROM generate_series(1, 10000) AS g(id);

---

Notice how long that took. Now recreate the index and try it again. You'll see the difference.

This is the trade-off. Faster reads, slower writes.

================================================================================
CLOSING WORDS
================================================================================

Alright, we've covered a lot of ground in the past hour. Let me summarize:

An index is a data structure that makes *reads* faster and *writes* slower. It's organized as a B-Tree, which uses a hierarchy of sorted nodes to allow PostgreSQL to find data in logarithmic time instead of linear time. That's powerful.

But indexes aren't free. Every write operation has to update the indexes. Every index consumes disk space. So you build indexes strategically, around your actual query patterns.

When you build a composite index, column order matters. The leftmost column is the most important. When you want to avoid lookups, use INCLUDE. When you want to understand what PostgreSQL is actually doing, use EXPLAIN ANALYZE. And when in doubt, measure. Don't guess.

Here's what I want you to take away from this lecture:

1. **Understand the trade-off.** Faster reads, slower writes. Always. Choose wisely.

2. **Know your queries.** Before you build an index, know what queries you're trying to optimize. Don't optimize in a vacuum.

3. **Measure everything.** EXPLAIN ANALYZE is your best friend. Use it constantly.

4. **Don't over-index.** It's tempting. It feels productive. But I've seen systems thrashed by maintenance overhead because someone indexed everything. Resist the temptation.

5. **Document your indexes.** In production, someone needs to know *why* an index exists. Was it built for a specific slow query? Is it still being used? Put comments in your code.

Over the next couple of weeks, you're going to learn about partial indexes, expression indexes, and more exotic index types. You'll learn about index maintenance and bloat. You'll learn about VACUUM and ANALYZE in depth. And all of that is building on the foundation we laid today.

But the core concept never changes: an index is a tool for fast lookups. Use it when you need it, and know the cost when you do.

You've got this. Get good at understanding indexes now, and you'll never struggle with database performance. I promise you that.

QUICK REFERENCE: INDEX COMMAND CARD
================================================================================

** CREATE A BASIC INDEX **

    CREATE INDEX index_name ON table_name(column_name);

** CREATE A COMPOSITE INDEX **

    CREATE INDEX index_name ON table_name(column1, column2, column3);

** CREATE A COVERING INDEX (PostgreSQL 11+) **

    CREATE INDEX index_name 
    ON table_name(search_columns) 
    INCLUDE (columns_to_include);

** VIEW QUERY EXECUTION PLAN (estimated) **

    EXPLAIN
    SELECT ...

** VIEW QUERY EXECUTION PLAN (actual, runs the query) **

    EXPLAIN ANALYZE
    SELECT ...

** UPDATE TABLE STATISTICS **

    ANALYZE table_name;

** UPDATE STATISTICS FOR ONE INDEX **

    ANALYZE table_name(column_name);

** LIST ALL INDEXES ON A TABLE **

    \d table_name    -- in psql
    -- or
    SELECT indexname FROM pg_indexes WHERE tablename = 'table_name';

** CHECK INDEX SIZE **

    SELECT indexname, pg_size_pretty(pg_relation_size(indexrelid)) 
    FROM pg_indexes 
    WHERE tablename = 'table_name';

** DROP AN INDEX **

    DROP INDEX IF EXISTS index_name;

** DROP AN INDEX (concurrently, without locking) **

    DROP INDEX CONCURRENTLY index_name;

** CREATE AN INDEX CONCURRENTLY (doesn't lock the table for writes) **

    CREATE INDEX CONCURRENTLY index_name ON table_name(column_name);

** DISABLE AN INDEX (for testing) **

    ALTER INDEX index_name UNUSABLE;

** RE-ENABLE AN INDEX **

    ALTER INDEX index_name REBUILD;
