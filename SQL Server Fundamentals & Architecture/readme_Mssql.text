MODULE 5: BACKUP & RECOVERY MASTERY ════════════════════════════════════════════
│
├── Backup Types
│   ├── Full Backup: Complete database, Base for all restores
│   ├── Differential Backup: Changes since last full, Cumulative
│   ├── Transaction Log Backup: Point-in-time recovery, Log truncation
│   ├── File/Filegroup Backup: Partial backups, Large DB strategy
│   ├── Copy-Only Backup: Out-of-band, Doesn't break backup chain
│   └── Tail-Log Backup: Before restore, Capture uncommitted transactions
│
├── Recovery Models
│   ├── Simple
│   │   ├── Log auto-truncates at checkpoint
│   │   ├── No point-in-time recovery
│   │   └── Use: Dev/Test, Data warehouses, Non-critical DBs
│   │
│   ├── Full
│   │   ├── All transactions logged
│   │   ├── Point-in-time recovery possible
│   │   ├── Requires log backups to truncate log
│   │   └── Use: Production OLTP, Critical systems
│   │
│   └── Bulk-Logged
│       ├── Minimal logging for bulk operations
│       ├── Log backups still required
│       ├── Point-in-time recovery limited during bulk ops
│       └── Use: Large data loads, Index rebuilds
│
├── Backup Strategy
│   ├── RPO (Recovery Point Objective): Max acceptable data loss
│   ├── RTO (Recovery Time Objective): Max acceptable downtime
│   ├── Backup Schedule Examples
│   │   ├── OLTP: Full (weekly) + Diff (daily) + Log (every 15-30 min)
│   │   ├── DW: Full (weekly) + Diff (daily), Simple recovery
│   │   └── Critical: Full (daily) + Log (every 5-15 min)
│   │
│   └── Backup Verification: RESTORE VERIFYONLY, Test restores
│
├── Backup Implementation
│   ├── T-SQL Commands: BACKUP DATABASE, BACKUP LOG
│   ├── Backup Options
│   │   ├── COMPRESSION: Reduce size (CPU overhead)
│   │   ├── CHECKSUM: Detect corruption
│   │   ├── INIT vs NOINIT: Overwrite vs Append
│   │   ├── COPY_ONLY: Independent backup
│   │   └── WITH NORECOVERY: Prepare for log restores
│   │
│   ├── Backup Destinations
│   │   ├── Local Disk: Fast, Limited retention
│   │   ├── Network Share: Central storage
│   │   ├── Tape: Long-term archival
│   │   ├── Azure Blob Storage: Cloud backup (URL)
│   │   └── Backup to multiple destinations: Redundancy
│   │
│   └── Maintenance Plans: Automated backup schedules
│
├── Transaction Log Management
│   ├── Log Architecture: VLFs (Virtual Log Files), Active/Inactive portions
│   ├── Log Growth: Fixed size increments, Monitor growth events
│   ├── Log Truncation: After checkpoint (Simple), After log backup (Full/Bulk)
│   ├── Log Full Issues
│   │   ├── Causes: No log backups, Long transaction, Replication delay
│   │   ├── Resolution: Take log backup, Kill long transaction, Check replication
│   │   └── Emergency: Switch to Simple (data loss risk), Shrink log
│   │
│   └── Log Monitoring: sys.dm_db_log_space_usage, DBCC LOGINFO
│
├── Backup Monitoring & Maintenance
│   ├── Last Backup Check: msdb.dbo.backupset, sp_BackupHistory
│   ├── Backup History Retention: msdb cleanup, sp_delete_backuphistory
│   ├── Failed Backup Alerts: SQL Agent alerts, Email notifications
│   ├── Backup File Management: Retention policy, Archive to tape/cloud
│   └── Backup Testing: Regular restore drills, Document procedures
│
└── Backup Troubleshooting
    ├── Backup Failures: Disk space, Permissions, Network issues
    ├── Slow Backups: Compression, Multiple files, Backup to SSD
    ├── Suspect Backup Files: RESTORE HEADERONLY, RESTORE VERIFYONLY
    └── Backup Chain Breaks: COPY_ONLY backups, Recovery model changes
│

MODULE 6: DATABASE RESTORE OPERATIONS ══════════════════════════════════════════
│
├── Restore Types
│   ├── Complete Restore: Full + Diff + Logs
│   ├── Point-in-Time Restore: STOPAT specific time
│   ├── Page Restore: Corrupt page recovery (Enterprise only)
│   ├── Piecemeal Restore: Filegroup-by-filegroup (large DBs)
│   └── File/Filegroup Restore: Partial restore scenarios
│
├── Restore Scenarios
│   ├── Database Refresh: Dev/Test from Production backups
│   ├── Disaster Recovery: Complete database loss
│   ├── Point-in-Time Recovery: User error, Data corruption at known time
│   ├── Corrupted Object: Restore to temp DB, Copy object
│   └── System Database Restore: master (single-user mode), model, msdb
│
├── Restore Process
│   ├── Pre-Restore Checks
│   │   ├── Verify backup files exist and are valid
│   │   ├── Check disk space: Data + Log files
│   │   ├── Identify backup chain: Full → Diff → Logs
│   │   ├── Kill active connections: WITH REPLACE, Set SINGLE_USER
│   │   └── Tail-log backup (if source DB accessible)
│   │
│   ├── Restore Execution
│   │   ├── RESTORE DATABASE: Full backup with NORECOVERY
│   │   ├── RESTORE DATABASE: Differential (if exists) with NORECOVERY
│   │   ├── RESTORE LOG: Each log backup in sequence with NORECOVERY
│   │   └── RESTORE DATABASE: Final step with RECOVERY (brings DB online)
│   │
│   └── Post-Restore Tasks
│       ├── DBCC CHECKDB: Verify integrity
│       ├── Update Statistics: sp_updatestats
│       ├── Fix Orphaned Users: sp_change_users_login 'Auto_Fix'
│       ├── Verify Logins: Restore SQL Agent jobs if needed
│       └── Test Application Connectivity
│
├── Restore Options & Techniques
│   ├── WITH REPLACE: Overwrite existing database
│   ├── WITH MOVE: Relocate files to different paths
│   ├── WITH RECOVERY: Bring database online (default)
│   ├── WITH NORECOVERY: Keep in restoring state for more backups
│   ├── WITH STANDBY: Read-only access between log restores
│   ├── STOPAT: Point-in-time restore to specific datetime
│   ├── STOPATMARK/STOPBEFOREMARK: LSN-based restore
│   └── PARTIAL Restore: Primary filegroup first, others later
│
├── System Database Restores
│   ├── master Database
│   │   ├── Start SQL in single-user mode: sqlservr.exe -m
│   │   ├── RESTORE DATABASE master
│   │   ├── Service restarts automatically after restore
│   │   └── Rebuild master (last resort): Setup.exe /ACTION=REBUILDDATABASE
│   │
│   ├── model Database: Restore like user database
│   ├── msdb Database: Restore like user database, SQL Agent history restored
│   └── tempdb: Cannot restore, Rebuilt on every restart
│
├── Advanced Restore Scenarios
│   ├── Cross-Version Restore: Backup from older version, Restore to newer
│   ├── Cross-Server Restore: Different server name, Orphaned user issues
│   ├── Partial Restore: Large DB, restore critical filegroups first
│   ├── Page Restore: Enterprise Edition, Online operation (CHECKDB identifies pages)
│   └── Snapshot Revert: RESTORE DATABASE FROM DATABASE_SNAPSHOT
│
├── Restore Troubleshooting
│   ├── Insufficient Space: Check data/log file sizes in backup
│   ├── Backup Chain Break: Missing differential or log backups
│   ├── Wrong Restore Order: Full → Diff → Logs sequence
│   ├── Access Denied: SQL service account permissions on backup files
│   ├── Corrupted Backup: RESTORE VERIFYONLY, Try alternate backup
│   └── Orphaned Users: sp_change_users_login, ALTER USER with SID
│
└── Restore Validation & Documentation
    ├── RESTORE HEADERONLY: View backup metadata
    ├── RESTORE FILELISTONLY: List files in backup
    ├── RESTORE VERIFYONLY: Verify backup integrity
    ├── Document Restore Procedures: DR runbook
    └── Practice Restore Drills: Quarterly testing, Time restoration
│

MODULE 7: DATABASE MAINTENANCE & AUTOMATION ════════════════════════════════════
│
├── Index Maintenance
│   ├── Index Fragmentation
│   │   ├── Logical Fragmentation: Page order disorder
│   │   ├── Extent Fragmentation: Physical disk scatter
│   │   ├── Detection: sys.dm_db_index_physical_stats
│   │   └── Thresholds: <10% (ignore), 10-30% (reorg), >30% (rebuild)
│   │
│   ├── Maintenance Operations
│   │   ├── ALTER INDEX REBUILD
│   │   │   ├── Recreates index, Removes fragmentation, Updates statistics
│   │   │   ├── ONLINE option (Enterprise), Requires 2x space temporarily
│   │   │   └── SORT_IN_TEMPDB: Offload sort operations
│   │   │
│   │   ├── ALTER INDEX REORGANIZE
│   │   │   ├── Online operation, Minimal impact
│   │   │   ├── Logical defrag only, Compacts LOB pages
│   │   │   └── Less resource intensive than rebuild
│   │   │
│   │   └── Statistics Update: UPDATE STATISTICS, Auto-update settings
│   │
│   └── Maintenance Strategy
│       ├── Schedule: Off-peak hours, Weekly/monthly based on fragmentation rate
│       ├── Prioritize: Critical tables, High-usage indexes first
│       ├── Monitor: Index usage (sys.dm_db_index_usage_stats), Remove unused indexes
│       └── Fill Factor: 80-90 for heavy writes, 100 for read-only
│
├── Statistics Maintenance
│   ├── Statistics Importance: Query optimizer decisions
│   ├── Auto Create/Update: Enabled by default, May lag on large tables
│   ├── Manual Updates: UPDATE STATISTICS, sp_updatestats
│   ├── Full Scan vs Sample: Accuracy vs Performance trade-off
│   └── Statistics Aging: sp_autostats, Check last update date
│
├── Database Integrity Checks

│   │   └── Run with: SQL Agent job, Notify on failure
│   │
│   ├── DBCC CHECKTABLE: Single table validation
│   ├── DBCC CHECKALLOC: Allocation structure only (faster)
│   └── DBCC CHECKCATALOG: System catalog consistency
│
├── SQL Server Agent Jobs

├── AlwaysOn AG Concepts

│   ├── Endpoints: TCP port for database mirroring (default 5022)

├── Database Mirroring (Deprecated)

│   ├── Cons: Single database, No read access, Deprecated

MODULE 16: REPLICATION (TRANSACTIONAL, SNAPSHOT) ═══════════════════════════════
│
├── Replication Overview
│   ├── Purpose: Data distribution, Reporting, Load balancing
│   ├── Method: Publish-Subscribe model
│   ├── Latency: Near real-time (transactional) to scheduled (snapshot)
│   └── Use Cases: DW ETL, Reporting, Data consolidation
│
├── Replication Components
│   ├── Publisher: Source database, Articles to replicate
│   ├── Subscriber: Destination database(s), Receives replicated data
│   ├── Distributor: Middleman, Stores replication metadata, Distributes changes
│   ├── Publication: Collection of articles to replicate
│   ├── Article: Table, Stored procedure, View, or Function
│   └── Subscription: Subscriber's registration to a publication
│
├── Replication Types
│   ├── Snapshot Replication
│   │   ├── Method: Full copy at scheduled intervals
│   │   ├── Use Case: Infrequent changes, Reference data, Full refresh acceptable
│   │   ├── Pros: Simple, No continuous overhead
│   │   ├── Cons: High latency, Network/CPU spike during snapshot
│   │   └── Agents: Snapshot Agent, Distribution Agent
│   │
│   ├── Transactional Replication
│   │   ├── Method: Initial snapshot + Continuous transaction replication
│   │   ├── Use Case: Near real-time, OLTP to DW, Reporting
│   │   ├── Pros: Low latency, Continuous sync
│   │   ├── Cons: Overhead on publisher, Complex troubleshooting
│   │   └── Agents: Snapshot, Log Reader, Distribution Agents
│   │
│   └── Merge Replication
│       ├── Method: Bidirectional synchronization
│       ├── Use Case: Mobile users, Occasionally connected, Conflict resolution
│       ├── Pros: Bidirectional, Offline support
│       ├── Cons: Complex, Conflict handling, Performance overhead
│       └── Agents: Snapshot, Merge Agents
│
├── Replication Agents
│   ├── Snapshot Agent
│   │   ├── Purpose: Generate initial snapshot (schema + data)
│   │   ├── Runs: At publication creation, Or on-demand/scheduled
│   │   ├── Output: .sch (schema), .bcp (data) files in snapshot folder
│   │   └── Impact: Locks tables briefly during snapshot
│   │
│   ├── Log Reader Agent
│   │   ├── Purpose: Reads transaction log (publisher), Identifies replicated transactions
│   │   ├── Runs: Continuously (transactional replication)
│   │   ├── Marks: Sets replication flag in log (allows log truncation)
│   │   └── Stores: Commands in distribution database
│   │
│   ├── Distribution Agent
│   │   ├── Purpose: Applies changes to subscriber
│   │   ├── Runs: Continuously (push) or on-demand (pull)
│   │   ├── Reads: Distribution database commands
│   │   └── Applies: INSERT/UPDATE/DELETE to subscriber tables
│   │
│   └── Merge Agent
│       ├── Purpose: Synchronizes changes bidirectionally
│       ├── Conflict Detection: Identifies conflicting changes
│       ├── Conflict Resolution: Applies resolution policy
│       └── Runs: On schedule or on-demand

├── Distributor Configuration
│   ├── Local Distributor
│   │   ├── Same Instance as Publisher: Simple setup
│   │   ├── Pros: No additional server needed
│   │   ├── Cons: Additional load on publisher
│   │   └── Use: Small-scale replication, Dev/Test
│   │
│   ├── Remote Distributor
│   │   ├── Separate Instance: Offload distribution work
│   │   ├── Pros: Reduced publisher load, Better scalability
│   │   ├── Cons: Additional server, Network dependency
│   │   └── Use: Production, High-volume replication

MODULE 17: CAPACITY PLANNING & STORAGE MANAGEMENT ══════════════════════════════
│
├── Capacity Planning Fundamentals
│   ├── Purpose: Forecast resource needs, Prevent outages, Budget planning
│   ├── Key Metrics: CPU, Memory, Disk Space, Disk I/O, Network
│   ├── Planning Horizon: 6-12 months typical, 3-5 years for major investments
│   └── Review Frequency: Quarterly reviews, Monthly for fast-growing systems
│
├── Baseline & Trend Analysis
│   ├── Establish Baseline
│   │   ├── Capture Current State: CPU, Memory, Disk, I/O during normal operations
│   │   ├── Performance Counters: PerfMon collection (30-day minimum)
│   │   ├── Database Sizes: sys.master_files, Weekly snapshots
│   │   ├── Workload: Query stats, Transactions per second, Connections
│   │   └── Peak vs Average: Identify peak usage periods
│   │
│   ├── Trend Analysis
│   │   ├── Historical Data: 6-12 months of metrics
│   │   ├── Growth Rate: Calculate monthly/quarterly growth percentage
│   │   │   └── Formula: (Current - Previous) / Previous * 100
│   │   │
│   │   ├── Forecasting: Linear regression, Exponential (if accelerating)
│   │   └── Seasonality: Account for business cycles (year-end, holidays)
│   │
│   └── Key Indicators
│       ├── Database Growth Rate: MB/day, GB/month
│       ├── Transaction Growth: TPS increase over time
│       ├── User Growth: Active connections trend
│       ├── Query Complexity: Average execution time trends
│       └── Backup Size Growth: Storage capacity planning
│
├── Storage Capacity Planning
│   ├── Database Size Forecasting
│   │   ├── Current Size: sys.master_files (size * 8 KB / 1024 / 1024)
│   │   ├── Growth Rate: Historical data (6+ months)
│   │   ├── Forecast: Current Size + (Growth Rate * Time Period)
│   │   ├── Buffer: Add 20-30% buffer for unexpected growth
│   │   └── Index Space: Factor in index rebuild space (2x largest index)
│   │
│   ├── Transaction Log Sizing
│   │   ├── Workload-Based: Measure log generation rate (MB/hour)
│   │   ├── Backup Frequency: Higher frequency = smaller log
│   │   ├── Formula: Log Rate * Backup Interval * 2 (safety margin)
│   │   ├── Monitor: sys.dm_db_log_space_usage, VLF count
│   │   └── Best Practice: Fixed size, Prevent excessive autogrow
│   │
│   ├── TempDB Sizing
│   │   ├── Workload-Dependent: Sorts, Hash joins, Temp tables, Version store
│   │   ├── Baseline: Monitor sys.dm_db_file_space_usage during peak
│   │   ├── Formula: Peak Usage * 1.5 (growth buffer)
│   │   ├── Multiple Files: 1 per core (max 8 initially), Equal size
│   │   └── Separate Disk: Fast I/O, Isolated from user databases
│   │
│   ├── Backup Storage
│   │   ├── Full Backup Size: Typically 30-60% of database size (compression)
│   │   ├── Differential: 10-30% of full backup (cumulative)
│   │   ├── Log Backups: Sum of log generation between backups
│   │   ├── Retention: Days/weeks of retention * Daily backup size
│   │   └── Formula: (Full * Retention Days/7) + (Diff * Retention Days) + (Log * Retention * Frequency)
│   │
│   └── Storage Alerts
│       ├── Data Files: <15% free space
│       ├── Log Files: <20% free space
│       ├── Backup Location: <20% free space
│       └── TempDB: <20% free space
│
├── Disk I/O Capacity Planning
│   ├── I/O Performance Metrics
│   │   ├── IOPS: Input/Output Operations Per Second
│   │   ├── Latency: Avg Disk sec/Read, Avg Disk sec/Write (<20ms target)
│   │   ├── Throughput: MB/sec read and write
│   │   └── Queue Length: Avg Disk Queue Length (<2 per spindle)
│   │
│   ├── Calculate IOPS Requirements
│   │   ├── Baseline: Current IOPS (PerfMon: Disk Transfers/sec)
│   │   ├── Read/Write Ratio: Separate read and write IOPS
│   │   ├── Growth Factor: Apply database growth rate
│   │   ├── Peak Load: 2-3x average for peak periods
│   │   └── Disk Type
│   │       ├── HDD (7200 RPM): ~75-100 IOPS
│   │       ├── HDD (15K RPM): ~175-210 IOPS
│   │       ├── SSD (SATA): ~5,000-10,000 IOPS
│   │       └── SSD (NVMe): ~50,000-500,000 IOPS
│   │
│   ├── Storage Configuration
│   │   ├── RAID Levels
│   │   │   ├── RAID 1: 50% usable, Good read performance
│   │   │   ├── RAID 5: 75% usable (4 disks), Slow writes (parity)
│   │   │   ├── RAID 10: 50% usable, Best performance (recommended)

│   │   │   ├── TempDB: Separate volume (RAID 10 or SSD)
│   │   │   └── Backups: Separate volume (RAID 5/6 acceptable)

│   │   └── SAN vs Local Storage
│   │       ├── SAN: Centralized, Scalable, Expensive
