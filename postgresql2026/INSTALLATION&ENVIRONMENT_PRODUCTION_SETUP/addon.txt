WHY THIS MATTERS
================================================================================

Welcome. Let me start with a question that many people don't ask until their

installation, and why does it matter?"

The truth is this: 90% of PostgreSQL production failures are NOT bugs in

haunt you for years.

Here's what I've seen:

* A company loses $100,000 per hour because their database won't start. Root
  cause: shared memory kernel parameter set incorrectly three years ago.

* A bank's reporting system becomes unusable for 6 hours. Root cause: locale
  encoding mismatch introduced during OS update.

* A startup's database mysteriously "goes slow" until people add more RAM.
  Root cause: swappiness tuning never done, causing the OS to page memory
  to disk instead of using available RAM.

These aren't theoretical. I've lived through all three.

The good news: with 20+ years of experience and the lessons I'm about to
teach you, you can avoid 95% of these problems.

WHAT IS POSTGRESQL, AND WHY INSTALL MATTERS
================================================================================

PostgreSQL is a relational database that runs on top of Linux (or other
operating systems). It's not a standalone program like a calculator. It's a
complex system that needs:

1. The OS to provide memory, storage, networking, and process management
2. You to configure that OS correctly
3. PostgreSQL installed properly on top of that configured OS
4. PostgreSQL configured to use those resources safely and efficiently

Think of it like building a house:
- The OS is the foundation and framing
- PostgreSQL installation is the plumbing and wiring
- Configuration is about using those utilities correctly

If your foundation is cracked, no amount of beautiful furniture fixes the
problem. Similarly, a perfect PostgreSQL configuration running on a badly
tuned OS is like luxury furniture in a house with water damage.

THE CASCADING IMPACT OF INSTALLATION DECISIONS
================================================================================

Every choice made during installation cascades:

Decision: "Let's install from source instead of using PGDG"
↓
Impact: You must manually manage updates, library compatibility, and security
        patches forever. Your team now needs to understand compilation.

Decision: "Let's use SQL_ASCII encoding"
↓
Impact: You cannot store non-ASCII data. Years later, your business expands
        to India, and suddenly you can't store Hindi text. Disaster.

Decision: "Let's skip data checksums to save CPU"
↓
Impact: Silent data corruption becomes possible. You find corrupted data 6
        months later, and have no backup that's clean. Cost: business loss.

Decision: "WAL and data files on the same disk"
↓
Impact: During high-load INSERT workloads, both are competing for I/O.
        Performance tanks. Application users see timeouts.

This lecture teaches you to make decisions that pay dividends every single
day for the lifetime of your production system.

PART 2: CORE CONCEPTS - STEP BY STEP

CONCEPT 1: WHAT HAPPENS WHEN YOU INSTALL POSTGRESQL
================================================================================

Let's break down PostgreSQL installation into its components. Installation
is not magic. It follows a clear pattern.

INSTALLATION METHOD OPTIONS

1. Package Manager (apt, yum)
   - Simplest for beginners
   - Usually includes PostgreSQL 12 or later
   - Handled by Linux distribution maintainers
   - Problem: Usually only one version available

2. PGDG Repository (PostgreSQL Global Development Group)
   - Official PostgreSQL packages
   - Multiple versions available (14, 15, 16, 17, etc.)
   - Recommended for production
   - Gives you choice and control

3. From Source (Compile yourself)
   - Maximum control
   - Requires knowledge of compilation
   - Not recommended unless you have specific needs
   - Takes 30+ minutes per install
   - Maintenance burden is yours forever

4. Docker/Containers
   - Good for development
   - Encapsulates everything
   - Still needs OS configuration outside the container
   - Can hide real system-level problems

For production, I recommend PGDG for 95% of use cases. It's the Goldilocks
choice: professional, maintained, flexible, and straightforward.

WHAT ACTUALLY GETS INSTALLED

When you install PostgreSQL, you get:

1. PostgreSQL BINARY FILES
   Location: /usr/lib/postgresql/16/bin/ (example for version 16)
   
   Key binaries:
   - postgres: The main server daemon
   - initdb: Creates a new database cluster
   - pg_ctl: Controls the database server (start/stop)
   - createdb, createuser: Create databases and users
   - psql: Interactive command-line tool
   - pg_dump, pg_restore: Backup/restore tools
   
   Think of these as the tools. They're like hammers, nails, and saws.
   Installation puts them in your toolbox.

2. POSTGRESQL SYSTEM LIBRARIES
   Location: /usr/lib/postgresql/16/lib/
   
   These are shared libraries that PostgreSQL uses. Like dependency files
   that PostgreSQL loads at runtime. They provide:
   - Data encoding functions
   - Compression algorithms
   - Cryptography
   - Full-text search support

3. POSTGRESQL CONFIGURATION AND DOCUMENTATION
   Location: /usr/share/postgresql/16/
   
   - Sample configuration files
   - SQL support files
   - Documentation

4. POSTGRESQL SYSTEM USER
   A Linux user account that owns and runs PostgreSQL.
   Usually: postgres
   
   Why? Process isolation and security.

5. SYSTEMD SERVICE FILE (on modern Linux)
   Location: /etc/systemd/system/postgresql.service
   
   This tells Linux how to start/stop PostgreSQL at boot.

WHAT DOES NOT HAPPEN

Installation does NOT create:
- Any databases
- Any data files
- Any tables

This is intentional. Installation is about deploying the software. Cluster
initialization (next topic) is about creating the actual database.

MULTI-VERSION ENVIRONMENTS

This is important: you can install multiple PostgreSQL versions on ONE server.

Example: You have PostgreSQL 14 running in production. You want to test
PostgreSQL 16. You can install both.

Location structure:
/usr/lib/postgresql/14/bin/  ← Version 14 binaries
/usr/lib/postgresql/16/bin/  ← Version 16 binaries

The /usr/bin/postgresql-setup script manages which version is "active".

Why would you do this?
- Test major version upgrades without disrupting production
- Run multiple applications with different version requirements
- Gradually migrate from old to new version

Important: Only ONE version runs at a time on a given port. But the
binaries for all versions coexist peacefully on disk.

CONCEPT 2: INITDB AND CLUSTER INITIALIZATION
================================================================================

Now you've installed PostgreSQL. The binaries are in place. Next step:
CREATE A DATABASE CLUSTER.

This is the single most important operation you'll perform. Let me explain
why, then walk you through it.

WHAT IS A "DATABASE CLUSTER"?

A PostgreSQL "cluster" is NOT a multi-node setup (confusing name, sorry).

A cluster is: the complete collection of databases, configuration files,
and log files managed by a single PostgreSQL instance.

It's called a cluster because:
- It's a cohesive unit
- It has a single point of management
- Everything inside uses shared resources (memory, ports, etc.)

On a single server, you can have:
- One cluster (common)
- Two clusters on different ports (less common, but possible)
- Never more than a few

THE INITDB PROCESS: WHAT ACTUALLY HAPPENS

When you run:
  sudo -u postgres initdb -D /var/lib/postgresql/16/main

PostgreSQL runs a series of steps:

STEP 1: CREATE THE DIRECTORY STRUCTURE

initdb creates /var/lib/postgresql/16/main/ with subdirectories:

base/
  ├── 1/           ← System objects (pg_catalog)
  ├── 13109/       ← template0 database
  ├── 13110/       ← template1 database
  └── 16384/       ← Default "postgres" database
  
global/
  ├── pg_control   ← Critical: cluster state and metadata
  ├── pg_filenode.map
  └── pg_xact/     ← Transaction metadata
  
pg_wal/           ← Write-Ahead Log (more on this later)
  └── 000000010000000000000001  ← WAL segment files
  
pg_log/           ← Server logs
  └── ...
  
pg_twophase/      ← Two-phase commit state
pg_notify/        ← NOTIFY/LISTEN support
pg_replslot/      ← Replication slots
pg_stat/          ← Statistics

STEP 2: WRITE CRITICAL CLUSTER METADATA

initdb writes pg_control, a binary file that contains:

- PostgreSQL version number (important: prevents old versions from running
  a newer cluster)
- Cluster initialization date
- WAL segment size (very important, set once, cannot change)
- Checkpoint state
- Timeline ID (important for recovery)
- Data checksums (ON or OFF)

pg_control is THE most important file in your cluster. If it's corrupted,
PostgreSQL won't start at all.

Analogy: pg_control is like your passport. Without it, you can't cross
borders. PostgreSQL won't run without it.

STEP 3: INITIALIZE TEMPLATE DATABASES

initdb creates two special databases:
- template0: Never modified. Used as blueprint for CREATE DATABASE
- template1: Can be modified. Also used as blueprint

Why two? Simple answer: You customize template1 for your site defaults
(extensions, users, schemas). But if you mess up template1, you still have
template0 to recover.

When you later run:
  CREATE DATABASE mydb;

PostgreSQL copies template0 (or template1) to create mydb. This is why
what you put in templates matters.

STEP 4: WRITE INITIAL WAL SEGMENT

initdb creates the first WAL segment (we cover WAL later, but preview: WAL
is a transaction log).

Initial WAL file: 000000010000000000000001

This is where PostgreSQL starts writing transaction records once it boots.

STEP 5: SET OWNERSHIP AND PERMISSIONS

All files created belong to the "postgres" Linux user and group.

Example:
-rw------- postgres postgres pg_control

Only postgres can read it (permission 600).

This is security: other Linux users cannot steal data or corrupt it.

THE INITDB COMMAND: KEY PARAMETERS

When you initialize, you set critical options:

sudo -u postgres initdb \
  -D /var/lib/postgresql/16/main \
  --encoding=UTF8 \
  --locale=en_US.UTF-8 \
  --data-checksums

Breaking this down:

-D /var/lib/postgresql/16/main
  ↓
  Specifies PGDATA directory (where all cluster files live)
  Once set here, PostgreSQL knows to look there forever
  Change it = broken PostgreSQL

--encoding=UTF8
  ↓
  Sets character encoding (huge importance, next section)
  Once set, changing it requires pg_dump + full re-initialization
  Get this wrong = cannot store international text

--locale=en_US.UTF-8
  ↓
  Sets collation and ctype behavior
  Affects sorting, comparison, case behavior
  Once set, changing requires re-initialization
  Impact: is "apple" equal to "APPLE"? Depends on locale.

--data-checksums
  ↓
  Enables block-level checksums (storage protection)
  Performance cost: ~1-3% CPU
  Value gained: detect silent data corruption
  I recommend this for production, always

CRITICAL POINT: ENCODING AND LOCALE ARE SET ONCE, CANNOT BE CHANGED

This is not like a configuration parameter you adjust. Encoding and locale
are baked into the cluster structure.

If you initialize with SQL_ASCII and later realize you need UTF-8:
- You must pg_dump all data
- Destroy the cluster (initdb -D clears it)
- Re-initialize with UTF-8
- Restore data
- Downtime: hours or days depending on database size

This is catastrophic. That's why it's Concept 2, explained heavily upfront.

================================================================================
CONCEPT 3: ENCODING AND LOCALE - THE MOST MISUNDERSTOOD TOPIC
================================================================================

This section is longer because encoding and locale cause more production
disasters per line of code than any other topic.

WHAT IS CHARACTER ENCODING?

A character encoding is a mapping from symbols (letters, numbers, punctuation)
to numbers that computers can store.

HISTORY: ASCII

In the beginning, there was ASCII.

ASCII mapping (tiny excerpt):
65 = 'A'
97 = 'a'
48 = '0'
32 = ' ' (space)

ASCII uses 7 bits per character, allowing 128 characters total. Enough for
English. Not enough for:
- Accented characters (é, ñ, ü)
- Non-Latin scripts (Cyrillic, Greek, Chinese, Arabic, Devanagari)
- Symbols (€, ©, emoji)

THE PROBLEM: MULTI-BYTE CHARACTERS

How do you store 'é' (Latin Small Letter E with Acute)?

In ASCII? You can't. It doesn't exist.

Solution 1: CREATE EXTENDED ASCII
Extended ASCII uses 8 bits per character (256 possible). Includes accented
Latin characters but still no Asian languages.

Problem: Different vendors chose different mappings for the 128-256 range.
Latin1 ≠ Latin2 ≠ Windows-1252. Chaos.

Solution 2: UTF-8 (Unicode)

UTF-8 is variable-length encoding:
- ASCII characters: 1 byte (backward compatible)
- Latin accents: 2 bytes
- Greek/Cyrillic: 2 bytes
- CJK (Chinese/Japanese/Korean): 3-4 bytes
- Emoji: 4 bytes

Example:
'A' = 1 byte: 0x41
'é' = 2 bytes: 0xC3 0xA9
'中' (Chinese) = 3 bytes: 0xE4 0xB8 0xAD
'😀' (emoji) = 4 bytes: 0xF0 0x9F 0x98 0x80

UTF-8 is self-synchronizing: if you see a byte sequence, you always know
how many bytes form a character.

UTF-8 supports every language on Earth. It's the de facto standard.

POSTGRESQL'S ENCODING OPTIONS

PostgreSQL supports multiple encodings:

UTF8 (alias UTF-8 or UTF8)
  ✓ Supports all languages
  ✓ Industry standard
  ✓ Slight storage overhead (some characters use 3-4 bytes)
  Recommendation: USE THIS FOR PRODUCTION. Always.

LATIN1 (ISO 8859-1, alias LATIN)
  ✓ Supports European languages
  ✗ Cannot store CJK, Cyrillic, Arabic, Devanagari, emoji
  ✗ Legacy
  Do not use unless you have a specific reason

SQL_ASCII
  ✗ NOT A REAL ENCODING
  ✗ Pretends everything is ASCII
  ✗ Accepts any byte sequence without validation
  ✓ Technically allows "any bytes" but causes disasters
  NEVER use this. I mean it.

OTHERS (EUC_JP, EUC_KR, SHIFT_JIS, etc.)
  ✓ Legacy support for specific regions
  ✗ Limit you to one language region
  Not recommended for new systems

WHAT HAPPENS IF YOU CHOOSE WRONG?

Scenario 1: SQL_ASCII Selected

You initialize with SQL_ASCII. Everything works because PostgreSQL doesn't
validate. Months later:

INSERT INTO users (name) VALUES ('José García');

This inserts fine (bytes are stored). But:

SELECT name FROM users WHERE name = 'Jose Garcia';

Returns nothing! Why? Because PostgreSQL's internal text functions don't
know how to handle accented characters. Your comparison logic breaks.

Later, you try to use full-text search:
  SELECT * FROM documents WHERE to_tsvector(content) @@ to_tsquery('café');

This crashes. PostgreSQL's text processing assumes ASCII. Non-ASCII bytes
confuse it.

Scenario 2: LATIN1 Selected, but later need UTF-8

You have 5 years of data. Customer from China wants to store names. You
can't. Database says:

ERROR: invalid byte sequence for encoding "LATIN1": 0xe4 0xb8 0xad

You're stuck:
- Can't insert
- Can't change encoding without re-initialization
- Must plan downtime, pg_dump, reinit, restore

Cost: lost business, downtime, emergency meetings.

Scenario 3: UTF-8 Selected (CORRECT)

Everything works. Any language, anytime. Years later, you expand to new
markets. No problems.

HOW POSTGRES VALIDATES ENCODING

PostgreSQL stores data as raw bytes. At various points, it validates:

1. Data Input
   When you INSERT a string with non-ASCII characters, PostgreSQL checks:
   "Is this valid for the encoding?"
   
   If invalid, error:
   ERROR: invalid byte sequence for encoding "UTF8": ...
   
   This prevents garbage data.

2. String Operations
   When you use functions like LOWER(), UPPER(), SUBSTRING():
   PostgreSQL must understand character boundaries.
   
   If encoding is wrong, it corrupts the string:
   SUBSTRING('hello', 2, 3) with encoding confusion might return 'llo'
   but might return garbage bytes.

3. Collation (Sorting)
   When you ORDER BY name:
   PostgreSQL must know: does 'é' come before 'f'?
   This depends on encoding AND locale (next section).

LOCALE: THE SECOND HALF OF THE PUZZLE

Encoding answers: "How are characters represented as bytes?"
Locale answers: "How do I sort, compare, and classify characters?"

WHAT IS LOCALE?

Locale is a set of cultural rules for a language/region.

Examples:
en_US.UTF-8 (English, United States, UTF-8 encoding)
de_DE.UTF-8 (German, Germany, UTF-8 encoding)
ja_JP.UTF-8 (Japanese, Japan, UTF-8 encoding)
fr_FR.UTF-8 (French, France, UTF-8 encoding)

Each locale defines:
- Collation: How characters sort (A-Z vs a-z vs accents)
- Ctype: Character classification (is this a letter, digit, space?)
- Monetary: How currency is displayed
- Numeric: How numbers are formatted (. vs , for decimals)
- Time: Date/time formats

COLLATION: THE PRACTICAL IMPACT

Scenario: You have a table with:
'apple'
'Apple'
'APPLE'
'àpple'  (a with grave accent)
'Àpple'

You run: SELECT * FROM fruits ORDER BY name;

What order do you get?

It depends on locale!

Case 1: C locale (POSIX)
"C" is the computer's language. Uses ASCII byte values only.
Order: APPLE, Apple, APPLE (uppercase before lowercase in ASCII)

Wait, that's confusing. Let me clarify:

In ASCII:
65 = 'A'
97 = 'a'

So byte 65 < byte 97. Uppercase comes first.

Result: APPLE, Apple, apple

Case 2: en_US.UTF-8 locale
English (US). Treats lowercase and uppercase as equivalent, then sorts by
position. Accented characters come at the end (usually).

Result: apple, Apple, APPLE, àpple, Àpple

Case 3: de_DE.UTF-8 locale
German. In German, 'ä' is treated as a variant of 'a'. Sorts differently.

Result: apple, àpple, Apple, Àpple, APPLE

POSTGRES LOCALE IMPACT: LC_COLLATE AND LC_CTYPE

PostgreSQL uses two locale settings:

LC_COLLATE
  Controls sorting and string comparison
  Set at initdb, baked into index B-trees
  Changing it requires dropping and rebuilding all indexes

LC_CTYPE
  Controls character classification
  Affects LIKE, UPPER, LOWER, etc.
  Changing it requires re-initialization

WHY IS THIS CRITICAL?

When you create an index:

CREATE INDEX idx_fruits ON fruits (name);

PostgreSQL builds a B-tree index using LC_COLLATE to determine sort order.
If you later change locale, that index is WRONG. Queries give incorrect
results.

Example:
1. Initialize cluster with C locale
2. Create: CREATE INDEX idx_users ON users (last_name);
3. Insert data: 'Zebra', 'Apple'
4. Query: SELECT * FROM users ORDER BY last_name; → Returns Zebra, Apple
5. Someone changes locale to en_US.UTF-8 (bad idea, but happens)
6. Same query: SELECT * FROM users ORDER BY last_name;
7. Index is consulted, but index ordering is now wrong
8. Results might be garbage

This is a SILENT data corruption. Query returns wrong results without
error.

INITIALIZATION: ENCODING AND LOCALE DECISION

You must decide at initdb time:

sudo -u postgres initdb -D /var/lib/postgresql/16/main \
  --encoding=UTF8 \
  --locale=en_US.UTF-8 \
  --lc-collate=en_US.UTF-8 \
  --lc-ctype=en_US.UTF-8

Once set, these are permanent. Change them requires:
1. pg_dump entire database
2. Destroy cluster (rm -rf PGDATA)
3. Re-initialize with new settings
4. Restore data
5. Downtime: hours/days

BEST PRACTICE RECOMMENDATION

For production systems targeting international users:

encoding: UTF8 (always)
locale: C.UTF-8 or POSIX (deterministic, portable)

OR

encoding: UTF8
locale: en_US.UTF-8 (if primarily English-speaking region)

Do NOT use SQL_ASCII. Do NOT use LATIN1. These are footguns.

CONCEPT 4: WAL FUNDAMENTALS AND SEGMENT SIZING
================================================================================

WAL stands for Write-Ahead Log. It's one of the most important concepts
in PostgreSQL.

WHY WAL EXISTS: DURABILITY

Imagine PostgreSQL crashes (power loss, kernel panic, kernel OOM killer).

Without WAL: You restart PostgreSQL. Did your last transaction commit
or not? Unknown. If it partially wrote data, that data is corrupted.

With WAL: Before PostgreSQL modifies data on disk, it writes the change
to a log. If there's a crash, PostgreSQL replays the log on startup and
recovers consistently.

WAL is the reason PostgreSQL can crash-recover safely.

THE WAL WRITE SEQUENCE

1. Client issues: UPDATE users SET name = 'Bob' WHERE id = 1;

2. PostgreSQL processes the update in memory (in a buffer)

3. PostgreSQL writes a record to the WAL buffer: "Change bytes 1024-1032
   in file base/16384/12345 to contain Bob's name"

4. Application calls COMMIT

5. PostgreSQL writes: "COMMIT record for transaction 12345" to WAL

6. PostgreSQL calls fsync() on the WAL file to force it to disk

7. fsync() returns (confirms data is durable)

8. PostgreSQL returns to client: "COMMIT OK"

9. Only LATER (at next checkpoint), PostgreSQL writes the actual changed
   data to base/16384/12345

KEY INSIGHT: Data is durable because it's in WAL, not because it's in
the main data file yet.

Analogy: You're a bank teller. A customer deposits money. You don't
immediately put cash in the vault. You write a receipt in a transaction
log. The receipt is proof. Later, during reconciliation, you move cash
to the vault.

WAL SEGMENTS: FILES ON DISK

WAL is written to files called segments. Default size: 16 MB per segment.

Location: PGDATA/pg_wal/

Filename pattern: 000000010000000000000001

That hex string is a timeline and sequence number. PostgreSQL creates them
sequentially:

000000010000000000000001  ← First segment
000000010000000000000002  ← Second segment
000000010000000000000003  ← Third segment
...
000000010000000000000FFF  ← 4095th segment (16 MB × 4095 = ~64 GB)
0000000100000001000000001  ← Then continues with different timeline ID

WAL SEGMENT SIZE: IMMUTABLE AND IMPORTANT

When you initialize the cluster, you set WAL segment size:

sudo -u postgres initdb -D /var/lib/postgresql/16/main \
  --wal-segment-size=16MB

Default: 16 MB
Other options: 1 MB, 2 MB, 4 MB, 8 MB, 32 MB, 64 MB

16 MB is standard for most workloads. Larger segments help if:
- You have sustained high write loads (hundreds of MB/sec)
- Your storage I/O is slow and benefits from batching

Smaller segments help if:
- You want faster recovery time (more frequent checkpoints)
- Your storage can handle many small files

WHY SEGMENT SIZE IS IMMUTABLE

Segment size is written to pg_control. If you later try to run PostgreSQL
with a different segment size, it detects the mismatch:

ERROR: WAL segment size in pg_control is 16777216, but this binary uses
16777216

(Numbers are in bytes)

To change segment size: re-initialize the cluster.

WAL ARCHIVING: KEEPING HISTORY

PostgreSQL continues writing to WAL segments. Eventually, segments become
"inactive" (no longer being written to). At that point, they can be:

1. Recycled: WAL segment file is renamed and reused
   Example: 000000010000000000000001 becomes 000000010000000000000042
   
   This saves space because you don't create infinite new files.

2. Archived: WAL segment is copied to archive location
   Example: s3://my-backup/wal/000000010000000000000001
   
   Archive is kept for disaster recovery and replication.

Configuration in postgresql.conf:

wal_keep_size = 1GB
  ↓
  Keep at least 1 GB of WAL segments on disk.
  Helps standby servers catch up if they lag.

archive_mode = on
archive_command = 'aws s3 cp %p s3://backup-bucket/%f'
  ↓
  When a WAL segment fills, execute this command.
  %p = source path, %f = filename

WAL AND DURABILITY: KEY PRINCIPLE

The critical principle: fsync() on WAL is what guarantees durability.

If fsync() lies to you (e.g., SSD cache says "written" but power fails
before actual disk write), data can be lost.

This is why storage choice matters. More on this in Storage Strategy section.

PERFORMANCE IMPACT: FSYNC COST

Each COMMIT requires fsync(). If fsync() is slow, COMMIT is slow, and
application transactions slow down.

Measurement example:
- With good SSD: fsync() ~1 ms
- With slow disk: fsync() ~5-10 ms
- With spinning disk: fsync() ~10-20 ms

If your application does:
  BEGIN; UPDATE; INSERT; COMMIT; (3x per second)

Total transaction throughput = 3 / (10 ms) = 300 TPS

With better storage (1 ms fsync):
  Total throughput = 3 / (1 ms) = 3000 TPS

Storage impacts throughput dramatically.

SYNCHRONOUS_COMMIT: A DANGEROUS KNOB

PostgreSQL has a parameter:

synchronous_commit = on  ← Default
  ↓
  COMMIT waits for fsync() on WAL

synchronous_commit = off  ← Dangerous
  ↓
  COMMIT returns immediately without fsync()
  WAL is written in background asynchronously
  If power loss: last few committed transactions might be lost

Why would you turn this off?
- Massive throughput boost (10x or more)
- Trade-off: lose durability

When would you use it?
- Non-critical data (caching layers, analytics)
- Willing to accept data loss in exchange for speed
- NOT for production transactional systems

DO NOT use synchronous_commit = off in production unless you fully
understand the consequences.

CONCEPT 5: DATA CHECKSUMS AND CORRUPTION PREVENTION
================================================================================

Silent data corruption is a DBA's nightmare.

Your database appears fine. Backups run. Queries work. But somewhere, a
bit flipped from 0 to 1 due to cosmic ray, bad RAM, or storage hardware
failure. You don't know it. Corruption spreads. Months later, you discover
data is corrupted. Your backups are corrupted too (they have the same data).

What do you do? Hopefully you have a backup from before the corruption
started. Hopefully you can restore it. Hopefully you accept the data loss.

Data checksums are PostgreSQL's defense.

WHAT IS A CHECKSUM?

A checksum is a small number computed from a larger block of data.

Simple example:
Data: 0x01 0x02 0x03 0x04
Checksum (sum of bytes): 0x0A

If you later read the data:
0x01 0x02 0x03 0x05 (one byte corrupted!)
Checksum (sum of bytes): 0x0B

Checksum mismatch! Corruption detected.

Real checksums (CRC32, CRC64) are more sophisticated. PostgreSQL uses CRC-32C.

HOW POSTGRESQL CHECKSUMS WORK

With data checksums enabled:

1. PostgreSQL writes a page (8 KB) of data
2. Computes CRC32C of that page
3. Stores CRC in the page header (16 bytes)
4. Writes page to disk

Later:

1. PostgreSQL reads the page from disk
2. Computes CRC32C of the page content
3. Compares computed CRC with stored CRC
4. If mismatch: data corruption detected, error raised

ENABLING CHECKSUMS

Checksums must be enabled at initdb time:

sudo -u postgres initdb -D /var/lib/postgresql/16/main \
  --data-checksums

Verification: Look in postgres logs after startup:
"data checksums are enabled"

PERFORMANCE COST

Checksums add ~1-3% CPU overhead:
- CRC computation requires CPU cycles
- Every page read/write pays the cost

But value gained: Detect corruption instead of silently returning garbage.

For production, this is a worthwhile trade-off.

DETECTING CORRUPTION AT RUNTIME

PostgreSQL has a tool: pg_verify_checksums

sudo -u postgres pg_verify_checksums -D /var/lib/postgresql/16/main

This validates every page's checksum. If corruption exists, it reports it:

Checksum verification failed in file "base/16384/12345", block 1234: ...

Then:
- Restore that file from backup
- Or re-initialize if it's recoverable

REAL-WORLD SCENARIO

I once worked at a company with a PostgreSQL database on a SAN (Storage
Area Network). The SAN had a firmware bug that occasionally corrupted
blocks.

Without checksums: We'd have discovered this only when someone noticed
"why is this customer's record weird?" Six months of corrupted data already
backed up.

With checksums: Within days, PostgreSQL reported:
"Checksum verification failed in file base/16384/12345, block 500"

We isolated the corruption to that single table, restored from backup,
and investigated the SAN. Found and fixed the firmware.

Checksums saved us from data loss and months of confusion.

BEST PRACTICE

For production systems, always enable data checksums. The 1-3% CPU cost
is minimal. The protection is invaluable.

================================================================================
CONCEPT 6: PRODUCTION FILESYSTEM ARCHITECTURE
================================================================================

Where do PostgreSQL files live? How do you organize them? This affects
performance and recoverability.

PGDATA: THE ROOT DIRECTORY

All PostgreSQL files live under PGDATA.

Typical path: /var/lib/postgresql/16/main/

Inside PGDATA:

base/
  Contains databases.
  Each database is a subdirectory with numeric name (OID).
  Example:
    base/1/       ← postgres database (system objects)
    base/13109/   ← template0
    base/13110/   ← template1
    base/16384/   ← Your custom databases start here

global/
  Cluster-wide objects.
  Contains pg_control (critical metadata).

pg_wal/
  Write-Ahead Log segments.
  Contains 000000010000000000000001, 000000010000000000000002, etc.

pg_log/ (or log/ in newer versions)
  Server logs.
  Contains error messages, query logs if enabled.

pg_replslot/
  Replication slot data.
  Used for streaming replication.

pg_stat/
  Statistics.
  Auto-vacuum worker data, table statistics, etc.

OWNERSHIP AND PERMISSIONS

All files belong to postgres user, group postgres:

drwx------ postgres postgres /var/lib/postgresql/16/main/

Permission 700 means:
- Owner (postgres) can read, write, execute
- Group cannot access
- Others cannot access

This is important security. Only the postgres process should access these
files.

FILESYSTEM TYPE

What filesystem should PGDATA be on?

Recommended: ext4 or XFS
- Both are mature
- Both handle crash recovery well
- Both support important features: sparse files, large files

Avoid: btrfs (newer, less stable, complexity)
Avoid: NFS (networked file system - slow, consistency issues)

TABLESPACES: SPREADING DATA ACROSS DISKS

PGDATA must be on one filesystem. But you can spread databases across
additional filesystems using tablespaces.

Why? Performance and space management.

Example setup:
- /var/lib/postgresql/16/main/ on SSD (PGDATA, system databases)
- /ssd1/tablespace1/ on NVMe (high-performance analytical database)
- /ssd2/tablespace2/ on SSD (archive database, less critical)

Define tablespace:

CREATE TABLESPACE tblspc1 LOCATION '/ssd1/tablespace1';

Then create database there:

CREATE DATABASE analytics TABLESPACE tblspc1;

Now:
- postgresql database: on /var/lib/postgresql/16/main/
- analytics database: on /ssd1/tablespace1/

Tables in analytics read/write from the NVMe disk, getting dedicated I/O.

ADVANTAGES OF TABLESPACES

1. I/O Isolation
   Analytical database heavy I/O doesn't impact transactional database.

2. Space Management
   One database grows too large? Expand that tablespace independently.

3. Performance Tuning
   Put hot database on fast SSD. Cold database on cheaper slower storage.

DISADVANTAGES

1. Complexity
   More things to manage, backup, and monitor.

2. Backup Complications
   Tablespaces must be backed up separately.
   Recovery is more complex.

3. More Failure Points
   If /ssd1/tablespace1/ goes down, that database is unavailable.

BEST PRACTICE

For most systems: Keep everything in PGDATA on one good SSD. Simpler,
more manageable.

Use tablespaces only if you have specific performance needs (e.g., your
analytics workload is genuinely IO-constrained and separate from OLTP).

WAL SEPARATION: WAL ON ITS OWN DISK

One common advanced setup: WAL on separate physical disk from data.

Why?
- WAL is sequential writes (optimized access pattern)
- Data is random writes (different access pattern)
- Separate disks = no I/O contention

Setup:
1. Create /wal-disk/pg_wal/ on separate SSD
2. At initdb:
   sudo -u postgres initdb -D /var/lib/postgresql/16/main \
     -X /wal-disk/pg_wal

-X (capital X) specifies WAL directory.

Result:
- PGDATA: /var/lib/postgresql/16/main/ (on fast SSD)
- pg_wal: /wal-disk/pg_wal/ (on faster/separate SSD)

Performance impact: Can help in high-concurrency write-heavy workloads.

But complexity trade-off: Backup and recovery are harder.

LOGGING LOCATION

Logs are typically in:
PGDATA/log/ (new systems)
PGDATA/pg_log/ (older systems)

Logs contain:
- Error messages
- Warnings
- Slow queries (if enabled)
- Checkpoint activity

Logs are not critical for durability (data is durable via WAL). But logs
are critical for:
- Troubleshooting
- Performance analysis
- Compliance auditing

You should:
1. Monitor logs regularly
2. Archive logs separately from PGDATA
3. Never let logs fill the disk (monitor free space)

ARCHIVE DIRECTORY: LONG-TERM WAL STORAGE

WAL segments are kept in pg_wal/ for only a few hours/days. Older segments
are recycled (reused for new WAL).

If you need to recover from a backup, you need WAL segments since the
backup was taken. This is where archive comes in.

Archive configuration:

archive_mode = on
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'

Every WAL segment, once filled, is copied to /archive/.

/archive/ contains:
000000010000000000000001
000000010000000000000002
000000010000000000000003
...

Retention: Keep archive for at least 7 days (or however long your backup
retention is).

BACKUP STRATEGY IMPLICATIONS

Filesystem layout affects backup complexity.

Simple layout (everything in PGDATA):
- One directory to back up
- Clean, straightforward recovery

Complex layout (PGDATA + multiple tablespaces + separate WAL):
- Multiple directories to back up
- More chances for mistakes
- Harder to test recovery

DIRECTORY STRUCTURE CHECKLIST FOR PRODUCTION

✓ PGDATA: /var/lib/postgresql/16/main/
✓ WAL: PGDATA/pg_wal/ (unless separated for performance)
✓ Logs: PGDATA/log/
✓ Ownership: postgres:postgres
✓ Permissions: 0700 (drwx------)
✓ Filesystem: ext4 or XFS
✓ Storage: SSD or NVMe (not spinning disk)
✓ Monitoring: Free space alerts on all filesystems
✓ Backup: PGDATA backed up daily with WAL archive

================================================================================
CONCEPT 7: STORAGE STRATEGY - HARDWARE AND ARCHITECTURE
================================================================================

Choosing the right storage is not optional in production. Storage choices
cascade into performance, reliability, and cost.

STORAGE TECHNOLOGIES

1. SPINNING DISK (HDD)
   - Mechanical spinning platter
   - Seek time: 5-10 ms per random access
   - Sequential throughput: 100-200 MB/sec
   - Cost: Cheap ($0.02/GB)
   
   PROS:
   - Inexpensive
   - High capacity available
   
   CONS:
   - Slow random I/O (5-10 ms per seek)
   - High latency
   - Physical failure more likely (moving parts)
   
   SUITABLE FOR:
   - Archive systems (cold data)
   - Backups
   - NOT production transactional systems

2. SSD (Solid State Drive)
   - Flash memory, no moving parts
   - Random I/O: 0.1-1 ms (50-100x faster than HDD)
   - Sequential throughput: 300-550 MB/sec
   - Cost: Moderate ($0.10/GB)
   - Typical capacity: 1-4 TB per drive
   
   PROS:
   - Fast random I/O
   - Reliable
   - Lower latency than HDD
   
   CONS:
   - Wear out after many write cycles
   - Can fail suddenly without warning
   - Cost
   
   SUITABLE FOR:
   - Production databases (OLTP)
   - High-concurrency workloads
   - Small to medium datasets (< 5 TB)

3. NVMe (Non-Volatile Memory Express)
   - Same flash memory as SSD but different interface
   - Random I/O: 0.05-0.2 ms
   - Throughput: 3000-7000 MB/sec (10-50x faster than SSD)
   - Cost: Similar to SSD now ($0.08/GB)
   - Typical capacity: 500 GB - 2 TB per drive
   
   PROS:
   - Extremely fast
   - Excellent for sustained high-throughput workloads
   - Latency measured in microseconds
   
   CONS:
   - Can overheat under sustained load
   - Expensive compared to spinning disk
   
   SUITABLE FOR:
   - Production databases with high concurrency
   - OLAP/analytical workloads (sequential reads)
   - High-throughput streaming applications

IMPACT ON POSTGRESQL PERFORMANCE

Scenario 1: Spinning Disk
Database size: 100 GB
Workload: 100 concurrent users, OLTP
Seek time per random read: 8 ms

User query needs 1000 random page reads.
Time: 1000 × 8 ms = 8 seconds
User sees: 8 second response time
Bad experience.

Scenario 2: SSD
Same database, same workload
Random I/O latency: 0.5 ms

User query needs 1000 random page reads.
Time: 1000 × 0.5 ms = 500 ms
User sees: 0.5 second response time
Good experience.

Scenario 3: NVMe
Same database, same workload
Random I/O latency: 0.1 ms

Time: 1000 × 0.1 ms = 100 ms
User sees: 0.1 second response time
Excellent experience.

In storage, low latency compounds into user-perceived speed.

RAIDS: Reliability Through Redundancy

RAID stands for Redundant Array of Inexpensive Disks.

RAID 0 (Striping)
Data split across multiple disks.
Example with 2 disks:
Block 1 → Disk A
Block 2 → Disk B
Block 3 → Disk A
Block 4 → Disk B

PROS:
- Double the throughput (both disks read/write in parallel)

CONS:
- If ANY disk fails, ALL data is lost
- Reliability halved
- Not suitable for production

RAID 1 (Mirroring)
Data written to two disks simultaneously.
Example:
Block A → Disk A and Disk B (simultaneously)

PROS:
- If one disk fails, the other has complete data
- Reliability: If single disk failure rate is 1%, dual disk failure is 1% × 1% = 0.01%

CONS:
- Costs 2x the storage (only 50% usable)
- Slightly slower writes (must write to both)

SUITABLE FOR:
- Production critical systems
- Small datasets
- When storage cost isn't critical

RAID 5 (Striping with Parity)
Data and parity distributed across 3+ disks.
Example with 3 disks:
Block 1 → Disk A
Block 2 → Disk B
Parity (1 XOR 2) → Disk C
Block 3 → Disk A
Block 4 → Disk B
Parity (3 XOR 4) → Disk C

PROS:
- Survives ONE disk failure
- Uses 67% of space (for 3 disks) instead of 50% (RAID 1)
- Better space efficiency

CONS:
- Slower write performance (must calculate parity)
- Rebuild after disk failure is slow (risk of 2nd failure during rebuild)
- Complex

SUITABLE FOR:
- Large storage capacity needs
- Medium importance data
- When cost/space matters more than performance

RAID 6 (RAID 5 with double parity)
Like RAID 5 but with TWO parity blocks.
Survives TWO disk failures.

PROS:
- Better fault tolerance

CONS:
- Even slower writes (double parity calculation)
- Higher complexity

BEST PRACTICE FOR POSTGRESQL

For production:
- RAID 1 for small (< 2 TB) critical databases
- RAID 5 or RAID 6 for large datasets
- Avoid RAID 0

But honestly: Modern cloud storage (AWS EBS, Google Persistent Disk, Azure
Managed Disks) handles RAID internally. You don't manage it. Cloud providers
replicate data automatically.

If using cloud:
- Use managed databases (RDS for PostgreSQL, Azure Database, Cloud SQL)
- Or run PostgreSQL on persistent block storage with built-in replication
- Don't worry about RAID; trust the provider

IF ON-PREMISES:

RAID 1 for:
- Small production databases
- High-performance critical systems
- Example: 500 GB database on RAID 1 mirrored SSDs

RAID 5/6 for:
- Large production databases (> 2 TB)
- Cost-sensitive situations
- Example: 10 TB analytical database on RAID 6 HDDs or SSDs

WAL STORAGE STRATEGY

WAL is written sequentially. Sequential I/O is not latency-sensitive; it's
throughput-sensitive.

Implication: WAL doesn't need the fastest storage.

Options:
1. WAL on same SSD as data (simplest, adequate for most)
2. WAL on cheaper SSD, data on faster SSD (balances cost and performance)
3. WAL on spinning disk (NOT RECOMMENDED - fsync() on spinning disk is slow,
   bottlenecking COMMIT performance)

If using RAID:
- Data: RAID 1 or RAID 5
- WAL: RAID 1 (WAL durability is critical)

ARCHIVE STORAGE

Archive is long-term WAL storage for recovery and replication.

Use case: 2 years of WAL segments backed up for compliance.

Storage options:
- Spinning disk (cheap, OK for archive)
- Tape (cheapest for decades-long retention)
- Object storage (S3, Azure Blob)

Archive doesn't need to be fast. It needs to be durable and cheap.

================================================================================
CONCEPT 8: POSTGRESQL PROCESS ENVIRONMENT
================================================================================

PostgreSQL is a Linux process. How it runs depends on:
- User account that starts it
- File permissions
- Resource limits (ulimits)
- Environment variables
- Service manager (systemd)

POSTGRESQL SYSTEM USER

During installation, a user account "postgres" is created.

Verify:
$ id postgres
uid=105(postgres) gid=112(postgres) groups=112(postgres)

This user owns PGDATA and runs the PostgreSQL process.

Why a dedicated user?
- Security isolation
- Resource accountability
- Prevents other users from accessing database files

USER PERMISSIONS MODEL

File permissions on PGDATA:

drwx------ postgres postgres /var/lib/postgresql/16/main/
drwx------ postgres postgres /var/lib/postgresql/16/main/base/
drwx------ postgres postgres /var/lib/postgresql/16/main/pg_wal/

Permission 0700 (user rwx, group ---, other ---):
- postgres can read, write, execute
- No one else can access

This is intentional. Even the "root" user cannot directly read data files
(without using sudo).

STARTING THE POSTGRESQL PROCESS

PostgreSQL runs as a daemon (background process).

Method 1: pg_ctl (manual)

sudo -u postgres pg_ctl -D /var/lib/postgresql/16/main start

This:
1. Changes to postgres user
2. Runs postgres binary
3. Forks to background
4. Returns control to you

Method 2: systemd service (recommended)

sudo systemctl start postgresql@16

systemd is Linux's modern service manager. It:
1. Starts PostgreSQL at boot time
2. Restarts if it crashes
3. Manages logging
4. Handles dependencies

Systemd service file location:
/etc/systemd/system/postgresql@16.service

Content (simplified):

[Unit]
Description=PostgreSQL 16 database server
After=network.target

[Service]
Type=notify
User=postgres
ExecStart=/usr/lib/postgresql/16/bin/postgres -D /var/lib/postgresql/16/main
ExecReload=/bin/kill -HUP $MAINPID
Restart=always

[Install]
WantedBy=multi-user.target

This tells systemd:
- Start as "postgres" user
- Run this binary with this PGDATA
- Auto-restart if it crashes
- Enable at boot

POSTGRESQL PROCESS HIERARCHY

When PostgreSQL starts:

1. Postmaster process (parent)
   - Listens on port 5432
   - Accepts connections
   - Forks worker processes

2. Worker processes (children)
   - Handle client connections
   - Execute queries
   - Write to shared buffers
   
   Example process list:
   postgres     12345  0.5  0.2  /usr/lib/postgresql/16/bin/postgres -D /var/lib/postgresql/16/main
   postgres     12346  0.0  0.1  postgres: postgres testdb [local] idle
   postgres     12347  0.0  0.1  postgres: postgres testdb [local] idle in transaction
   postgres     12348  0.5  0.3  postgres: postgres testdb [local] UPDATE

3. Background worker processes
   - autovacuum: Cleans up dead rows
   - wal writer: Flushes WAL to disk
   - background writer: Writes dirty pages to disk
   - checkpoint: Performs checkpoints

ULIMITS: RESOURCE LIMITS

ulimit controls per-process resource limits.

Critical ones for PostgreSQL:

nofile (open file descriptors)
  Each connection needs file descriptors. Default: 1024
  Calculation: connections × 3 + buffers
  Example: 200 connections × 3 + 100 = 700
  Recommendation: Set to 65536

nproc (processes per user)
  Number of processes postgres user can create. Default: 512
  PostgreSQL creates many (parent + children + workers)
  Recommendation: Set to 4096 or higher

memlock (locked memory)
  Used for huge pages. Default: limited
  Recommendation: unlimited (if using huge pages)

SETTING ULIMITS

Method 1: Temporary (current session only)

ulimit -n 65536
ulimit -u 4096

Method 2: Persistent (systemd)

Edit /etc/systemd/system/postgresql@16.service:

[Service]
LimitNOFILE=65536
LimitNPROC=4096

Then:
sudo systemctl daemon-reload
sudo systemctl restart postgresql@16

Verify:

su - postgres
ulimit -a

Should show new limits.

ENVIRONMENT VARIABLES

PostgreSQL respects certain environment variables:

PGDATA (not usually needed with systemd, but useful in scripts)
  Path to cluster directory

PGHOST, PGPORT, PGUSER, PGPASSWORD
  Used by client tools (psql, pg_dump) to connect

Example:

export PGDATA=/var/lib/postgresql/16/main
export PGHOST=localhost
export PGPORT=5432
export PGUSER=postgres

su - postgres
pg_ctl status

SIGNAL HANDLING

PostgreSQL responds to signals:

SIGTERM (graceful shutdown)
  pg_ctl stop
  PostgreSQL stops accepting new connections
  Waits for existing transactions to complete
  Clean shutdown

SIGQUIT (immediate shutdown)
  Dangerous. Immediate process termination.
  Can cause data corruption if transactions in progress.
  Avoid unless emergency.

SIGHUP (reload config)
  pg_ctl reload
  PostgreSQL re-reads postgresql.conf
  Many parameters reload without restart
  Some require restart

SIGUSR1 (log rotation)
  If using built-in logging, rotates log file
  Useful for logrotate integration

SERVICE DEPENDENCIES

PostgreSQL often depends on other services:

sudo systemctl start postgresql@16
  ↓
Depends on: network.target

So systemd ensures:
1. Network is ready
2. Then PostgreSQL starts

If you have custom setup (e.g., PostgreSQL depends on mounted storage):

[Unit]
After=network.target /mnt/data.mount

Tells systemd: Don't start PostgreSQL until /mnt/data is mounted.

SERVICE MONITORING

systemd tracks service health:

sudo systemctl status postgresql@16

Shows:
- Is it running?
- Restart count
- Last restart reason
- Recent journal entries

Enable auto-restart:

[Service]
Restart=always
RestartSec=10

This restarts PostgreSQL if it crashes, waiting 10 seconds between attempts.

For production: enable auto-restart. For development: optional.

================================================================================
CONCEPT 9: LINUX KERNEL TUNING FOR POSTGRESQL
================================================================================

Linux kernel parameters affect PostgreSQL performance and reliability.

What are kernel parameters? They're OS-level settings that control how
the kernel allocates and manages resources.

KEY PARAMETERS FOR POSTGRESQL

1. SHARED MEMORY (SHMMAX, SHMALL)

PostgreSQL allocates large blocks of shared memory for:
- Buffer pool (pages cache)
- Shared buffers
- Query working memory

Kernel limits how much shared memory one process can allocate.

Check current limits:

$ cat /proc/sys/kernel/shmmax
2147483648          ← 2 GB (default, too small!)

PostgreSQL needs more. Recommendation:

Physical RAM / 2

Example: 64 GB RAM → need 32 GB shared memory

Set in /etc/sysctl.conf:

kernel.shmmax = 34359738368  (32 GB in bytes)

Then apply:

sudo sysctl -p

Or directly:

echo 34359738368 | sudo tee /proc/sys/kernel/shmmax

Verification:

$ cat /proc/sys/kernel/shmmax
34359738368         ← Success

2. SHARED MEMORY PAGES (SHMALL)

Number of shared memory pages available system-wide.

Calculation:
SHMALL (pages) = SHMMAX (bytes) / page size (typically 4096)

Example:
32 GB = 34359738368 bytes
34359738368 / 4096 = 8388608 pages

In /etc/sysctl.conf:

kernel.shmall = 8388608

3. SEMAPHORES (KERNEL.MSGMNI, KERNEL.SEMMNI, ETC)

Semaphores are kernel synchronization primitives. PostgreSQL uses them.

Check:

$ cat /proc/sys/kernel/msgmni
32000              ← Number of message queues

PostgreSQL documentation recommends:

kernel.msgmni = 16384
kernel.semmni = 256
kernel.semmns = 32768
kernel.semmsl = 256

More on semaphores: Advanced topic. Suffice to say: Set these once, don't
touch them again.

4. FILE DESCRIPTORS SYSTEM-WIDE

Kernel limits total file descriptors across all processes.

Check:

$ cat /proc/sys/fs/file-max
2097152            ← Max FDs system-wide

If many PostgreSQL connections + OS processes:

fs.file-max = 2097152  ← Default usually OK

But also set per-process ulimits (already covered).

5. MEMORY OVERCOMMIT (VM.OVERCOMMIT_MEMORY)

This controls whether the kernel allows processes to allocate more memory
than physically available.

Check:

$ cat /proc/sys/vm/overcommit_memory
0                  ← Default: heuristic

Values:
0 = Heuristic (kernel estimates and may refuse)
1 = Always allow (can lead to OOM)
2 = Never allow (strict limit)

PostgreSQL recommendation: 2 (strict)

In /etc/sysctl.conf:

vm.overcommit_memory = 2

Why? Strict memory accounting prevents surprises.

With overcommit_memory = 0, the kernel may allow PostgreSQL to allocate
more memory than available. If all memory fills, OOM killer kicks in and
shoots processes randomly. Disaster.

With overcommit_memory = 2, PostgreSQL knows exactly how much memory it can
use. No surprises.

6. MEMORY SWAPPINESS (VM.SWAPPINESS)

Swappiness controls how aggressively the kernel pages memory to disk.

Check:

$ cat /proc/sys/vm/swappiness
30                 ← Default (moderate)

Behavior with 30:
When RAM usage reaches 70%, kernel starts paging to disk.

Problem: Paging to disk is SLOW (10-100x slower than RAM).

PostgreSQL needs data in RAM for performance. Paging ruins this.

Recommendation: Set to 1-10

In /etc/sysctl.conf:

vm.swappiness = 1

With swappiness = 1:
Kernel almost never pages unless absolutely necessary.

If you have 64 GB RAM and allocate 32 GB for PostgreSQL buffers, the remaining
32 GB is available for OS cache and other processes. You shouldn't need swap.

7. TRANSPARENT HUGE PAGES (THP)

Modern CPUs support "huge pages" (2 MB pages instead of 4 KB).

Huge pages reduce memory management overhead. But PostgreSQL sometimes
doesn't benefit (depending on access patterns).

Recommendation for PostgreSQL: Disable THP

Check:

$ cat /sys/kernel/mm/transparent_hugepage/enabled
[always] madvise never

Disable (permanently):

In /etc/sysctl.conf or kernel boot params, disable THP.

Or at runtime:

echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled

Why disable? PostgreSQL's memory access patterns sometimes conflict with THP.

Alternative: Use explicit huge pages. More on that in next section.

8. TCP SETTINGS FOR DATABASE NETWORK

If PostgreSQL is networked (non-localhost connections):

net.ipv4.tcp_keepalives_idle = 60
  ↓
  Keepalive packets sent every 60 seconds
  Prevents firewalls from dropping idle connections

net.ipv4.tcp_keepalives_intvl = 10
  ↓
  Retry keepalive every 10 seconds if no response

net.ipv4.tcp_keepalives_probes = 3
  ↓
  Send 3 keepalive probes before giving up

These prevent "ghost" connections (connections that appear open but are
actually dead due to network issues).

APPLYING KERNEL TUNING PERSISTENTLY

Create a file: /etc/sysctl.d/99-postgresql.conf

Content:

# PostgreSQL kernel tuning
kernel.shmmax = 34359738368
kernel.shmall = 8388608
kernel.msgmni = 16384
kernel.semmni = 256
kernel.semmns = 32768
kernel.semmsl = 256
vm.overcommit_memory = 2
vm.swappiness = 1
fs.file-max = 2097152

Apply:

sudo sysctl -p /etc/sysctl.d/99-postgresql.conf

Verify:

sudo sysctl -a | grep -E "(shmmax|shmall|swappiness)"

KERNEL TUNING CHECKLIST FOR PRODUCTION

✓ SHMMAX set to RAM / 2
✓ SHMALL set to SHMMAX / 4096
✓ MSGMNI, SEMMNI, SEMMNS set appropriately
✓ Overcommit memory = 2
✓ Swappiness = 1-10
✓ THP disabled (or use explicit huge pages)
✓ file-max adequate for your load
✓ TCP keepalive settings configured for networked deployments

================================================================================
CONCEPT 10: MEMORY MANAGEMENT - HUGE PAGES AND OOM
================================================================================

Memory is PostgreSQL's most valuable resource. Efficient memory management
is critical.

BUFFER POOL AND SHARED BUFFERS

PostgreSQL allocates a large buffer pool (shared_buffers in postgresql.conf).

Default: 128 MB
Recommendation: 25% of system RAM (for OLTP), 50% (for data warehouse)

Example: 64 GB RAM → 16 GB shared_buffers

This buffer pool caches pages (8 KB chunks of data files).

How it works:

1. Client query needs page 1000
2. PostgreSQL checks: Is page 1000 in buffer pool?
3. Yes? Use it. (Fast, memory access ~100 ns)
4. No? Read from disk (Slow, I/O latency ~1 ms)

With large buffer pool:
- More pages fit in memory
- Fewer disk reads
- Faster queries

Memory efficiency: More memory = more caching = better performance.

HUGE PAGES: REDUCING TLB MISSES

TLB is Translation Lookaside Buffer. It's CPU cache that maps virtual memory
addresses to physical addresses.

With default 4 KB pages:
64 GB of data = 16 million pages

TLB can only hold ~1000-4000 entries. Most page accesses miss the TLB,
requiring a slower page table walk.

With huge pages (2 MB):
64 GB of data = 32,000 pages

TLB hit rate much higher. Fewer page table walks.

Performance gain: ~5-10% for large datasets.

ENABLING HUGE PAGES

Linux supports two ways:

1. Transparent Huge Pages (automatic, system-wide)
   Problem: Can cause latency spikes (page compaction)
   Not recommended for PostgreSQL

2. Explicit Huge Pages (manual, process-specific)
   Recommended for PostgreSQL

Steps to enable explicit huge pages:

Step 1: Allocate huge pages at boot

Edit /etc/sysctl.conf or /etc/sysctl.d/99-postgresql.conf:

vm.nr_hugepages = 8192

Example: 8192 huge pages × 2 MB = 16 GB of huge pages

Step 2: Verify allocation

$ cat /proc/meminfo | grep Huge
HugePages_Total: 8192
HugePages_Free: 8192
Hugepagesize: 2048 kB

Step 3: Enable in PostgreSQL

In postgresql.conf:

huge_pages = try

This tells PostgreSQL: "Use huge pages if available, but don't fail if
unavailable."

Step 4: Restart PostgreSQL

sudo systemctl restart postgresql@16

Verify in logs:

$ tail -20 /var/log/postgresql/postgresql-16-main.log
...
"large pages" = on

Success!

WORKING MEMORY AND QUERY EXECUTION

work_mem parameter controls memory allocated per operation (sort, hash join).

Default: 4 MB
Recommendation: 10-50 MB for OLTP, depends on system

Example:
SELECT * FROM orders ORDER BY amount DESC LIMIT 10;

If result set > work_mem, PostgreSQL spills to disk (slower).

If result set < work_mem, stays in memory (faster).

With 100 concurrent queries:
Worst case memory: 100 × work_mem × 5 (number of operations) = 500 × work_mem

If work_mem = 50 MB:
Worst case = 25 GB used just for query working memory

This is why shared_buffers + work_mem must be balanced against system RAM.

MEMORY PLANNING FORMULA

Total memory budget: System RAM - OS budget - Other processes

Example: 64 GB system
- OS buffer cache: 2 GB
- Other processes: 2 GB
- Available for PostgreSQL: 60 GB

Within PostgreSQL's 60 GB:
- shared_buffers: 15 GB (25%)
- work_mem budget: 30 GB (for 200 connections × 50 MB × 3 ops)
- maintenance_work_mem: 2 GB (autovacuum, index creation)
- Headroom: 13 GB (safety buffer, OS caching)

This ensures PostgreSQL doesn't exhaust RAM and trigger OOM killer.

OUT-OF-MEMORY (OOM) KILLER

If system RAM exhausts, Linux kernel activates OOM killer.

OOM killer's logic: "Processes are hogging memory. Kill the worst offender."

"Worst offender" is determined by:
- Memory usage (higher = more likely to kill)
- oom_score_adj (process priority, can be adjusted)

PostgreSQL can be killed.

Impact: PostgreSQL process dies. Connections drop. Database unavailable.

Prevention: Size memory allocation to never exhaust system RAM.

PROTECTING POSTGRESQL FROM OOM KILLER

Set oom_score_adj to negative value (lower priority to kill).

In /etc/systemd/system/postgresql@16.service:

[Service]
OOMScoreAdjust=-900

This tells OOM killer: "Don't kill PostgreSQL unless absolutely necessary."

Values:
-1000 = Never kill PostgreSQL
-900 = Very low priority to kill (recommended)
0 = Normal priority (default)
+900 = High priority to kill

With -900, if OOM killer activates, it will kill other processes before
PostgreSQL.

MEMORY PRESSURE AND PERFORMANCE

As memory approaches saturation, performance degrades:

50% used: Normal performance
70% used: OS starts paging
80% used: Significant paging, severe slowdown
95% used: OOM killer may activate

Monitor memory:

$ free -h
              total        used        free      shared  buff/cache   available
Mem:           63Gi       35Gi        10Gi       512Mi       17Gi        27Gi

Healthy: used + buff/cache ≈ 70-80% total
Unhealthy: available < 5% of total

If unhealthy, either:
- Add more RAM
- Reduce shared_buffers
- Reduce work_mem
- Optimize queries to use less memory

MONITORING MEMORY IN POSTGRESQL

View what's using memory:

SELECT datname, usename, backend_start, state
FROM pg_stat_activity
ORDER BY xact_start ASC;

Long-running idle transactions lock memory. Terminate them if safe:

SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle in transaction' AND xact_start < NOW() - INTERVAL '1 hour';

View buffer pool hit ratio:

SELECT 
  sum(heap_blks_read) as heap_read, 
  sum(heap_blks_hit) as heap_hit, 
  sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read)) as ratio
FROM pg_statio_user_tables;

Ratio > 0.99 = Good (99% hit rate)
Ratio < 0.90 = Buffer pool too small

CONCEPT 11: OS WRITEBACK VS POSTGRESQL CHECKPOINTS
================================================================================

This is an advanced concept that explains interactions between the OS and
PostgreSQL.

Background: When you write data to a file, it doesn't immediately hit disk.
The OS buffers it.

OS WRITEBACK MECHANISM

Write sequence:

1. Application calls write() system call
   "Write this data to file"

2. OS copies data to page cache (in-memory buffer)
   Returns immediately to application

3. Application continues (unblocked)

4. OS background daemon (writeback daemon) flushes page cache to disk
   Periodically, triggered by:
   - Time elapsed (dirty_expire_centisecs, default 3000 = 30 seconds)
   - Page cache fills (dirty_ratio, default 20%)
   - fsync() called explicitly

Analogy: You tell a librarian "File this book." They put it in a staging
area. Later, during their quiet time, they file it properly. If you ask
urgently (fsync), they file it immediately.

POSTGRESQL FSYNC BEHAVIOR

When PostgreSQL commits a transaction:

1. Write data to WAL buffer (in memory)
2. Call fsync() on WAL file
3. fsync() tells OS: "Flush this to disk NOW"
4. OS writeback daemon writes to disk synchronously
5. fsync() returns when disk write is confirmed
6. PostgreSQL returns COMMIT to client

fsync() is expensive because it forces synchronous disk I/O.

If you have high COMMIT rate (1000/sec):
1000 fsync() calls/sec = 1000 disk waits = ~1 second of wall-clock time
per second of committed transactions.

This is why storage I/O latency matters. Faster fsync = faster commits.

POSTGRESQL CHECKPOINT MECHANISM

Checkpoint is when PostgreSQL writes all dirty data pages from buffer pool
to disk.

Why checkpoints? Because WAL is the source of truth. If PostgreSQL crashes,
it replays WAL. But WAL files accumulate. Checkpoints mark "up to this
point, data is safely on disk, discard older WAL."

Checkpoint sequence:

1. PostgreSQL decides checkpoint is needed
   (Time elapsed, WAL accumulated, or explicit CHECKPOINT command)

2. PostgreSQL starts checkpoint process:
   - Writes all dirty pages from buffer to disk
   - Calls fsync() on all dirty files
   - Writes checkpoint record to WAL
   - Advances WAL position (old WAL can be deleted/archived)

3. During checkpoint, I/O is heavy
   - All dirty pages being written concurrently
   - Spikes in disk utilization
   - May impact user queries

Checkpoint impact:
- Latency spike (queries slower during checkpoint)
- Throughput spike (lots of I/O)
- WAL growth (new WAL segments created faster)

CONFIGURATION PARAMETERS

checkpoint_timeout (default 15 minutes)
  If no checkpoint happens for this long, trigger one

max_wal_size (default 1 GB)
  If WAL grows beyond this, trigger checkpoint
  Larger value = longer checkpoint spacing = less frequent spikes

Example:
checkpoint_timeout = 15m
max_wal_size = 2GB

With 100 MB/sec write rate:
Time to fill 2 GB: 20 seconds
So checkpoint every 20 seconds (or 15 minutes, whichever is first)

During checkpoint, brief I/O spike.

INTERACTION WITH OS WRITEBACK

OS writeback is also flushing pages. If checkpoint and writeback collide:

1. checkpoint calls fsync() on 1000s of pages
2. OS writeback trying to flush same pages
3. Disk I/O contention
4. Both slow down

This is a known problem in database systems. Databases often tune
checkpoint parameters to space out checkpoints, reducing overlap with
OS writeback.

CHECKPOINT TUNING

Balance:
- Frequent checkpoints: Lots of I/O spikes, more I/O total
- Infrequent checkpoints: Rare spikes, but WAL grows large, recovery
  slower if crash

Recommendation:
- OLTP: checkpoint_timeout = 15-20 minutes, max_wal_size = 2-4 GB
- OLAP: checkpoint_timeout = 30 minutes, max_wal_size = 5-10 GB
- High-write workloads: More conservative, e.g., max_wal_size = 5-10 GB

Monitor checkpoint activity:

SELECT * FROM pg_stat_bgwriter;

Key columns:
checkpoints_timed: Checkpoints triggered by timeout
checkpoints_req: Checkpoints triggered by WAL accumulation
checkpoint_write_time: Total I/O time for checkpoints
checkpoint_sync_time: Total fsync() time for checkpoints

If checkpoints_req >> checkpoints_timed, max_wal_size is too small.

WRITEBACK AND PAGE CACHE

The OS page cache (distinct from PostgreSQL buffer pool) also holds pages.

If shared_buffers is 16 GB and system RAM is 64 GB:
- 16 GB: PostgreSQL's shared buffers
- ~20 GB: OS page cache (Linux allocates free RAM for caching)
- ~28 GB: Available for other processes, malloc, etc.

During heavy I/O:
- PostgreSQL dirties pages in shared_buffers
- OS sees dirty pages, starts writeback
- Writeback competes with PostgreSQL's own I/O

Result: I/O becomes non-deterministic.

Mitigation:
- Large shared_buffers (reduce reliance on OS cache)
- Tune vm.dirty_ratio to control when OS starts writeback
- Use writeback priority (ionice) to prioritize PostgreSQL I/O

Advanced tuning:
vm.dirty_ratio = 10
  ↓
  OS starts writeback when page cache reaches 10% of RAM
  Writes get triggered earlier, preventing sudden spike

vm.dirty_background_ratio = 5
  ↓
  Background writeback starts at 5%, keeping it gentle

PART 3: COMMON PRODUCTION FAILURES AND ROOT CAUSE ANALYSIS
================================================================================

Now let's apply what we've learned to real failures. This is where theory
becomes wisdom.

FAILURE 1: POSTGRESQL FAILS TO START
================================================================================

Symptom: Server reboot. PostgreSQL doesn't start. Error in systemd journal.

$ sudo journalctl -u postgresql@16 -n 20

Possible outputs and root causes:

CAUSE 1A: PGDATA NOT FOUND

ERROR: cannot access the server data directory "/var/lib/postgresql/16/main": 
No such file or directory

Root cause:
- PGDATA accidentally deleted
- Mount point didn't mount (e.g., SAN not connected)
- Wrong path in systemd service file

Diagnosis:
$ sudo -u postgres ls -la /var/lib/postgresql/16/main/
ls: cannot access '/var/lib/postgresql/16/main/': No such file or directory

Recovery:
1. Check if backup exists
   $ ls /backup/postgresql/

2. If yes, restore from backup
3. If no, cluster is lost
   - What do you have? Full database backups?
   - If not, data recovery may be impossible

Prevention:
- Automated daily backups with monitoring
- Test backup restoration monthly
- Monitor: alert if PostgreSQL doesn't start within 5 minutes of boot

CAUSE 1B: PERMISSION DENIED

ERROR: could not access file "/var/lib/postgresql/16/main/pg_control": 
Permission denied

Root cause:
- PGDATA ownership wrong (not postgres:postgres)
- PGDATA permissions wrong (not 0700)
- Running PostgreSQL as wrong user

Diagnosis:
$ ls -la /var/lib/postgresql/16/main/pg_control
-rw------- root root /var/lib/postgresql/16/main/pg_control
                ^^^^
         Wrong owner!

Recovery:
$ sudo chown -R postgres:postgres /var/lib/postgresql/16/main/
$ sudo chmod -R 700 /var/lib/postgresql/16/main/

Then try start:
$ sudo systemctl start postgresql@16

Prevention:
- Don't run manual commands as root
- Always use: sudo -u postgres command
- Systemd service runs as postgres user (no sudo needed)

CAUSE 1C: INSUFFICIENT SHARED MEMORY

ERROR: could not create shared memory segment: "No space left on device"

Root cause:
- Kernel shmmax too small
- Shared buffers in postgresql.conf > shmmax

Diagnosis:
$ cat /proc/sys/kernel/shmmax
2147483648    ← 2 GB default

$ grep shared_buffers /var/lib/postgresql/16/main/postgresql.conf
shared_buffers = 8GB    ← Oops, larger than shmmax!

Recovery:
Option 1: Reduce shared_buffers:
$ sudo su - postgres
$ psql -d postgres
ALTER SYSTEM SET shared_buffers = '2GB';
SELECT pg_reload_conf();

Then restart PostgreSQL.

Option 2: Increase kernel shmmax:
$ echo 8589934592 | sudo tee /proc/sys/kernel/shmmax
$ sudo sysctl -p

Then restart PostgreSQL.

Prevention:
- Set shmmax at initial configuration (RAM / 2)
- Size shared_buffers accordingly (25% RAM for OLTP)
- Monitor: alert if shared_buffers > shmmax

CAUSE 1D: PORT CONFLICT

ERROR: could not bind IPv4 socket: Address already in use

Root cause:
- Another PostgreSQL instance running on port 5432
- Another service (not PostgreSQL) using port 5432

Diagnosis:
$ sudo netstat -tuln | grep 5432
tcp    0  0 127.0.0.1:5432  0.0.0.0:*  LISTEN  12345

Or:
$ sudo lsof -i :5432
COMMAND    PID  USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
postgres 12345 postgres 3u IPv4  234567    0t0  TCP localhost:5432 (LISTEN)

Recovery:
If legitimate old PostgreSQL:
  $ sudo systemctl stop postgresql@16
  $ sudo kill 12345
  $ sudo systemctl start postgresql@16

If another service:
  $ sudo lsof -i :5432
  Find which service, stop it or use different port

If you want PostgreSQL on different port:
  In postgresql.conf:
  port = 5433
  
  Then:
  $ sudo systemctl restart postgresql@16

Prevention:
- Only one PostgreSQL instance per port
- Use standard port 5432 for main instance
- Use high ports (5433+) for secondary instances
- Monitor: alert if port is in use by unexpected process

FAILURE 2: LOCALE AND ENCODING ERRORS
================================================================================

Symptom: Queries work sometimes, fail at other times. Errors about encoding.

$ sudo -u postgres psql testdb
testdb=> SELECT * FROM names WHERE name LIKE '%é%';
ERROR: invalid byte sequence for encoding "UTF8": 0xc3 0xa9

Root cause:
- Data inserted with wrong encoding
- Locale mismatch between client and server

CAUSE 2A: SQL_ASCII CLUSTER, UTF-8 DATA

If cluster initialized with SQL_ASCII:

$ sudo -u postgres -i
postgres@server:~$ psql -U postgres
postgres=# SELECT encoding FROM pg_database WHERE datname = 'postgres';
 encoding
----------
 5        ← 5 = SQL_ASCII

Data inserted:
INSERT INTO users VALUES ('José');

Later, queries fail:
SELECT * FROM users WHERE name = 'Jose';
  ↓
  Returns nothing because PostgreSQL doesn't understand accents

Or:
SELECT lower(name) FROM users;
  ↓
  May return garbage bytes

Recovery (nightmare scenario):
1. pg_dump entire database to SQL file
2. Destroy cluster
3. Re-initialize with UTF-8
4. Restore from dump

Downtime: Hours or days.

Prevention:
- Initialize with UTF8 always
- Verify encoding before writing production data
- Test with international characters before deployment

CAUSE 2B: COLLATION MISMATCH

You have a database with en_US.UTF-8 locale. You create index:

CREATE INDEX idx_names ON users (name);

Index is built with en_US.UTF-8 collation. Later, someone changes locale:

ALTER DATABASE testdb SET locale = 'C';

(Note: You can't actually change locale without re-initialization, but
pretend this is a hypothetical)

Now index ordering is wrong:
SELECT * FROM users ORDER BY name;
  ↓
  Returns in different order than index suggests

Results are inconsistent, confusing.

Root cause:
- Locale change (shouldn't happen, but...)
- Index not rebuilt after locale change
- Locale migration error

Recovery:
1. Rebuild all indexes:
   REINDEX DATABASE testdb;

2. Or drop and recreate:
   DROP INDEX idx_names;
   CREATE INDEX idx_names ON users (name);

Prevention:
- Never change locale after initialization
- If must migrate locales: Plan migration, test thoroughly
- Always re-build indexes after any locale change

FAILURE 3: PERMISSION AND FILE ACCESS ERRORS
================================================================================

Symptom: PostgreSQL runs, but some operations fail with permission errors.

Error examples:
ERROR: could not create file "base/16384/12345": Permission denied
ERROR: could not read file "base/16384/12346": Operation not permitted
ERROR: WAL segment missing

CAUSE 3A: DATADIR OWNERSHIP WRONG

PGDATA ownership is mixed (some files owned by postgres, some by root):

$ ls -la /var/lib/postgresql/16/main/
drwx------ postgres postgres ./
drwx------ postgres postgres base/
-rw------- root root global/pg_control  ← WRONG!

Root cause:
- Manual file operations as root
- Restore from backup preserving wrong ownership
- Disk permissions issue

Recovery:
$ sudo chown -R postgres:postgres /var/lib/postgresql/16/main/
$ sudo chmod -R 700 /var/lib/postgresql/16/main/

Verify:
$ ls -la /var/lib/postgresql/16/main/ | head -5
total 128
drwx------ postgres postgres .
drwx------ postgres postgres base

Then restart PostgreSQL.

Prevention:
- Always use postgres user for PGDATA operations
- Backup/restore tools must preserve ownership
- Use: sudo -u postgres pg_dump, sudo -u postgres pg_restore

CAUSE 3B: TABLESPACE MOUNT POINT MISSING

You have a tablespace on /ssd1/tablespace1/:

$ psql testdb -c "\db"
     Name     |     Owner    | Location
---------------+--------------+----------
 pg_default   | postgres     | 
 pg_global    | postgres     |
 tblspc1      | postgres     | /ssd1/tablespace1

One day, /ssd1 mount fails:

$ mount | grep ssd1
(nothing)

Attempts to access tblspc1 databases fail:

ERROR: could not open file "pg_tblspc/16384/PG_16_201909212": No such
file or directory

Recovery:
1. Re-mount the filesystem
   $ sudo mount /ssd1

2. If mount fails, repair filesystem
   $ sudo fsck /dev/sda1 (example)

3. If repair fails, restore from backup

Prevention:
- Monitor mount points
- Alert if mount fails
- Use /etc/fstab with "nofail" option to prevent boot hang if mount fails

FAILURE 4: RESOURCE EXHAUSTION (ULIMITS)
================================================================================

Symptom: PostgreSQL crashes or behaves erratically under high load.

Error in logs:
ERROR: could not create new process for connection: Cannot allocate memory
ERROR: too many open files

Root cause:
- ulimits set too low
- System resource exhaustion

CAUSE 4A: TOO MANY OPEN FILES

With 500 concurrent connections:
- Each connection needs file descriptors
- Default ulimit nofile = 1024
- With 500 connections × 3 FDs = 1500 > 1024

Diagnosis:
$ ulimit -n
1024    ← Too low!

Recovery:
Edit /etc/systemd/system/postgresql@16.service:

[Service]
LimitNOFILE=65536

Then:
$ sudo systemctl daemon-reload
$ sudo systemctl restart postgresql@16

Verify:
$ su - postgres
$ ulimit -n
65536    ← Success!

Prevention:
- Size ulimits based on expected connection count
- Calculation: connections × 3 + 100 (buffer) = recommended nofile
- Monitor: Track open FDs per PostgreSQL process

CAUSE 4B: TOO MANY PROCESSES

With large number of PostgreSQL workers:

$ ps aux | grep postgres | wc -l
512

If ulimit nproc = 512:

ERROR: could not fork new process: No child processes

Recovery:
Edit /etc/systemd/system/postgresql@16.service:

[Service]
LimitNPROC=4096

Then:
$ sudo systemctl daemon-reload
$ sudo systemctl restart postgresql@16

Prevention:
- Set nproc = 10 × expected max connections
- Monitor: Track process count

FAILURE 5: OUT-OF-MEMORY (OOM) KILLER
================================================================================

Symptom: PostgreSQL process suddenly dies. Systemd shows OOMKilled.

$ sudo systemctl status postgresql@16
...
Main process exited, code=exited, status=137/n/a
OOMKilled=yes

Root cause:
- System RAM exhausted
- OOM killer targeting PostgreSQL

CAUSE 5A: UNDERSIZED SHARED_BUFFERS CAUSES EXCESSIVE PAGING

shared_buffers = 256 MB (too small)
System RAM: 64 GB

PostgreSQL keeps missing buffer pool, forcing disk reads. OS caches read data.
OS page cache fills (32 GB). System RAM exhausted. OOM killer activates.

Recovery (immediate):
1. Increase available memory
   $ free -h    ← Check memory

2. Terminate unneeded processes
   $ ps aux | grep <process> | grep -v grep | awk '{print $2}' | xargs kill

3. Restart PostgreSQL

Fix (permanent):
1. Increase shared_buffers
   ALTER SYSTEM SET shared_buffers = '16GB';
   SELECT pg_reload_conf();

2. Tune vm.swappiness to 1 (prevent paging)
   $ echo 1 | sudo tee /proc/sys/vm/swappiness

3. Plan upgrade: RAM is bottleneck

Prevention:
- Size shared_buffers appropriately (25% RAM for OLTP)
- Set OOMScoreAdjust = -900 in systemd service
- Monitor memory usage
- Alert when available memory < 10% total RAM

CAUSE 5B: RUNAWAY QUERY USING EXCESSIVE WORK_MEMORY

Query that should use 100 MB work_mem instead uses 4 GB due to:
- Bad query plan
- No statistics (stale after bulk load)
- Incorrect work_mem setting

System RAM fills. OOM killer fires.

Recovery:
1. Find running queries:
   SELECT pid, query, state FROM pg_stat_activity 
   WHERE state != 'idle' 
   ORDER BY query_start ASC;

2. Terminate long-running query:
   SELECT pg_terminate_backend(pid) 
   FROM pg_stat_activity 
   WHERE query_start < NOW() - INTERVAL '30 minutes';

3. Analyze query (after system stabilizes):
   EXPLAIN ANALYZE SELECT ...

4. Fix: Optimize query, add index, gather stats (ANALYZE)

Prevention:
- Monitor slow queries (log_statement, log_duration)
- Review EXPLAIN ANALYZE before production deployment
- Keep statistics fresh (autovacuum ANALYZE on)
- Set reasonable work_mem limits

FAILURE 6: STARTUP SEQUENCE FAILURES
================================================================================

Symptom: PostgreSQL starts but doesn't fully initialize. Partial startup.

Error in logs:
FATAL: recovery failed

Or:
FATAL: invalid page in block

Root cause:
- Corrupt pg_control
- Incomplete recovery after crash
- Filesystem corruption

CAUSE 6A: CORRUPT PG_CONTROL

pg_control is corrupted due to:
- Power loss during write
- Storage hardware failure
- Cosmic ray bit flip (rare)

Diagnosis:
PostgreSQL won't start at all:

ERROR: pg_control version number differs from server version

Or:
ERROR: could not read pg_control

Recovery (requires backup):
1. If backup of PGDATA exists:
   $ sudo -u postgres pg_ctl -D /var/lib/postgresql/16/main stop
   $ sudo rm -rf /var/lib/postgresql/16/main/
   $ sudo -u postgres restore-from-backup.sh
   $ sudo -u postgres pg_ctl -D /var/lib/postgresql/16/main start

2. If no backup: Database is unrecoverable

Prevention:
- Enable data checksums (detect pg_control corruption)
- Daily backups with testing
- Monitor: Store backup verification results

CAUSE 6B: INCOMPLETE RECOVERY AFTER CRASH

PostgreSQL crashes during UPDATE:

1. Changes written to WAL
2. Changes NOT yet written to data file
3. Crash occurs
4. On restart, PostgreSQL replays WAL
5. But WAL replay fails (corrupted WAL record)

Error:
FATAL: WAL record has invalid length

Recovery:
1. Check WAL directory:
   $ ls -la /var/lib/postgresql/16/main/pg_wal/ | tail -5

2. If WAL files exist and are recent (within hours):
   PostgreSQL should recover automatically

3. If recovery stuck for >5 minutes:
   - Check logs for error message
   - Try pg_ctl start -l /tmp/postgres.log (foreground mode for debugging)

4. If WAL truly corrupted:
   - Restore from backup
   - Re-apply WAL from archive

Prevention:
- Data checksums (detect corruption)
- Reliable storage (RAID 1 for WAL)
- Regular backup + restore testing

PART 4: REAL-WORLD FAILURE SCENARIOS AND RECOVERY
================================================================================

Let's walk through complete scenarios. These are based on real incidents
I've handled.

SCENARIO 1: THE 3 AM OUTAGE - PORT CONFLICTS
================================================================================

TIME: 3:47 AM

Alert: "PostgreSQL is down"

YOUR RESPONSE STEPS:

Step 1: Verify the problem

$ sudo systemctl status postgresql@16
● postgresql@16.service - PostgreSQL 16 database server
   Loaded: loaded (/etc/systemd/system/postgresql@16.service; enabled; vendor preset: enabled)
   Active: failed (Result: exit-code) since Fri 2025-02-14 03:45:22 UTC; 38s ago
  Process: 2345 ExecStart=/usr/lib/postgresql/16/bin/postgres -D /var/lib/postgresql/16/main (code=exited, status=3)

Process exited with code 3. Not a crash (which is exit code 139). A startup error.

Step 2: Check logs

$ sudo journalctl -u postgresql@16 -n 50 --no-pager

... [timestamp] LOG: starting PostgreSQL 16.0 on x86_64-pc-linux-gnu
... [timestamp] LOG: listening on IPv4 address "127.0.0.1", port 5432
... [timestamp] FATAL: could not bind IPv4 socket: Address already in use
... [timestamp] HINT: Is another postmaster already running on port 5432?
... [timestamp] LOG: aborting startup due to fatal error

"Address already in use" = port conflict.

Step 3: Find what's using port 5432

$ sudo netstat -tuln | grep 5432
tcp  0  0 127.0.0.1:5432  0.0.0.0:*  LISTEN  1234

Or more detailed:
$ sudo lsof -i :5432
COMMAND    PID  USER   FD   TYPE  DEVICE SIZE/OFF NODE NAME
postgres 1234 postgres 3u IPv4  234567    0t0  TCP localhost:5432 (LISTEN)

PID 1234 is using the port.

Step 4: Is PID 1234 PostgreSQL?

$ ps aux | grep 1234 | grep -v grep
postgres  1234  0.0  0.2  /usr/lib/postgresql/16/bin/postgres -D /var/lib/postgresql/16/main

Yes, it's PostgreSQL (old instance).

Step 5: Why is there an old instance?

Theory: systemd tried to start new instance, but old one never fully shut down.

Check process tree:
$ ps auxf | grep postgres | head -20

Shows: Old postgres process (parent) still running.

Step 6: Forcefully stop old instance

$ sudo kill -9 1234

Then start PostgreSQL:
$ sudo systemctl start postgresql@16

Step 7: Verify it started

$ sudo systemctl status postgresql@16
● postgresql@16.service - PostgreSQL 16 database server
   Loaded: loaded (/etc/systemd/system/postgresql@16.service; enabled; vendor preset: enabled)
   Active: active (running) since Fri 2025-02-14 03:52:14 UTC; 2s ago

SUCCESS. Database is running.

Step 8: Root cause analysis

Why did old process not shut down?

Check logs from before the restart:

$ sudo journalctl -u postgresql@16 -n 200 --no-pager
(20 minutes ago)
FATAL: recovery failed
...

Ah! PostgreSQL crashed during startup (possibly recovery failed). The
process was left in zombie state.

Step 9: Investigate why recovery failed

Check latest WAL files:
$ ls -la /var/lib/postgresql/16/main/pg_wal/ | tail -10

Check for data corruption:
$ sudo -u postgres pg_verify_checksums -D /var/lib/postgresql/16/main

If checksums fail, restore from backup.

If checksums OK, recovery should succeed.

Step 10: Prevent recurrence

a) Monitor PostgreSQL startup:
   Alert if service fails to start within 5 minutes of boot

b) Implement health check:
   $ /usr/lib/postgresql/16/bin/pg_isready -h localhost
   
   Run every minute, alert if fails

c) Log rotation to prevent disk fill:
   $ sudo logrotate -f /etc/logrotate.d/postgresql
   
   Ensure logs are rotated and compressed

SCENARIO 2: THE SILENT DATA CORRUPTION - NO CHECKSUMS
================================================================================

TIME: 2 weeks after an unnoticed power loss

PROBLEM: Customer reports wrong data in reports.

Value of invoice should be $1000, shows as $9.42.

YOUR RESPONSE:

Step 1: Check the data

$ psql production_db
production_db=> SELECT id, invoice_amount, created_at 
FROM invoices WHERE id = 12345;

 id    | invoice_amount |  created_at
-------+----------------+--------------------
 12345 | 9.42           | 2025-02-14 10:30:00

Step 2: Check audit logs

Do you have insert/update logs?
No? That's problem #1.

Step 3: Check pg_control for corruption

$ sudo -u postgres pg_verify_checksums -D /var/lib/postgresql/16/main

No checksums enabled! That's problem #2.

Output:
pg_verify_checksums: checksums disabled
(Cannot detect corruption without checksums)

Step 4: Find when corruption happened

If you have WAL archives and backups:
- Restore backup from 3 days ago (before corruption likely started)
- Replay WAL up to corruption point
- Detect when amount changed from 1000 to 9.42

If no WAL archive: Lost ability to investigate.

Step 5: Immediate action

a) Disable automatic vacuum to preserve state:
   ALTER SYSTEM SET autovacuum = off;
   SELECT pg_reload_conf();

b) Backup corrupted database for forensics:
   $ sudo -u postgres pg_dump production_db > /backup/corrupted_db.sql

c) Restore clean backup:
   $ sudo -u postgres psql < /backup/production_db_2025_02_12.sql

d) Query: Where's the data loss?
   What changed between backup and now?

Step 6: Implement prevention

a) Enable data checksums:
   Requires full re-initialization (downtime).

b) Daily backup verification:
   Restore backup to test database nightly.
   Verify row counts match.

c) Archive WAL for forensic analysis:
   archive_mode = on
   archive_command = 'aws s3 cp %p s3://backup-bucket/wal/%f'

d) Monitor system for power loss risk:
   If running on-premises with unreliable power:
   - Install UPS
   - Test failover monthly
   - Alert on power anomalies

LESSON: Data checksums + backups + WAL archive = confidence in recovery.

SCENARIO 3: THE SLOW INSERTS - UNDERSIZED SHARED_BUFFERS
================================================================================

TIME: Gradual degradation over weeks

PROBLEM: INSERT rate declining. Application timeouts increasing.

YOUR RESPONSE:

Step 1: Check application logs

INSERT taking 5 seconds (should take <100 ms).

Step 2: Check PostgreSQL logs

$ sudo tail -100 /var/log/postgresql/postgresql-16-main.log | grep -i "slow\|duration"

Lots of slow queries. Checkpoint activity in logs.

Step 3: Check system metrics

$ free -h
              total        used        free      shared  buff/cache   available
Mem:           64Gi       53Gi         2Gi       512Mi       8Gi        11Gi

Memory 82% used. Only 11 Gi available. Paging likely.

$ vmstat 1 5
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in    cs us sy id wa
 0  2   1024   2.1Gi  512Mi 8Gi    200  400   100 50000   5000  8000 30 20 10 40
                ^       swapped in ↑    ↑       ↑
                                       swapped out
                                       block I/O very high
                                       wait I/O high (40%)

This shows:
- Paging happening (swpd > 0, si/so > 0)
- High disk I/O (bo = block output = disk writes)
- High I/O wait (wa = 40%, CPU waiting for disk)

Step 4: Check PostgreSQL configuration

$ psql -U postgres -c "SHOW shared_buffers;"
 shared_buffers
----------------
 256MB

With 64 GB RAM, 256 MB is WAY too small (should be ~16 GB).

Step 5: Investigate why shared_buffers is small

Likely: PostgreSQL installed years ago, never tuned for larger hardware.

Step 6: Fix the problem

a) Calculate new value:
   64 GB × 25% = 16 GB

b) Update configuration:
   ALTER SYSTEM SET shared_buffers = '16GB';

c) Restart PostgreSQL:
   $ sudo systemctl restart postgresql@16
   
   (This restarts PostgreSQL, requiring a brief downtime)

d) Verify:
   $ psql -U postgres -c "SHOW shared_buffers;"
    shared_buffers
   ----------------
    16GB

e) Monitor memory after restart:
   $ free -h (should show <50% used)

f) Monitor application performance:
   INSERT latency should drop to <100 ms

Step 7: Tune other related parameters

Also tune:
- work_mem: Based on connections and available memory
- effective_cache_size: Helps query planner estimate memory
- checkpoint parameters: If checkpoints spiking during inserts

Step 8: Root cause analysis

Why was shared_buffers never sized correctly?

- Installation happened years ago, hardware upgraded but config not
- No performance baselines established
- No monitoring for memory efficiency

PREVENTION:
- Document all configuration decisions
- Review periodically (annual)
- Monitor: Track buffer pool hit ratio
  SELECT sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read))
  FROM pg_statio_user_tables;
  
  If < 0.99, consider increasing shared_buffers

PART 5: TROUBLESHOOTING MINDSET AND METHODOLOGY
================================================================================

The best troubleshooters think systematically, not randomly.

Here's the framework I use:

STEP 1: UNDERSTAND THE SYMPTOM (NOT THE PROBLEM)

Symptom: "Database is slow"
Problem: Could be 100 different things

Ask clarifying questions:
- When did it start? (Gradual or sudden?)
- Which queries are slow? (All or specific?)
- Is CPU high? Disk? Memory?
- Did anything change recently?

STEP 2: GATHER METRICS

Every investigation starts with data:

System metrics:
$ top               ← CPU, memory, load
$ iostat 1 5        ← Disk I/O
$ netstat -s        ← Network
$ vmstat 1 5        ← Virtual memory
$ df -h             ← Disk usage

PostgreSQL metrics:
$ ps aux | grep postgres    ← Process count
$ lsof -p $(pidof postgres) ← Open files
$ psql -c "SHOW shared_buffers;"  ← Configuration
$ psql -c "SELECT * FROM pg_stat_bgwriter;"  ← Background activity

STEP 3: FORM HYPOTHESES (NOT JUMP TO CONCLUSIONS)

Based on metrics, form hypotheses. Multiple, ranked by likelihood:

Symptom: Slow queries
Hypothesis 1: Buffer pool hit rate low (too much disk I/O)
  Evidence: iostat shows high disk read rate, high wait I/O
  
Hypothesis 2: Long checkpoints causing I/O spikes
  Evidence: Checkpoint activity in logs, I/O spikes every 15 minutes
  
Hypothesis 3: Missing indexes
  Evidence: EXPLAIN shows seq scans on large tables
  
Hypothesis 4: Memory pressure (paging)
  Evidence: vmstat shows si/so > 0, wa% high

STEP 4: TEST HYPOTHESES SYSTEMATICALLY

Don't change things randomly. Test methodically.

Test Hypothesis 1:
SELECT 
  sum(heap_blks_hit) as cache_hit, 
  sum(heap_blks_read) as cache_miss,
  ROUND(100.0 * sum(heap_blks_hit) / (sum(heap_blks_hit) + 
    sum(heap_blks_read)), 2) as hit_ratio
FROM pg_statio_user_tables;

If hit_ratio < 0.99:
→ Hypothesis 1 confirmed: Buffer pool too small
→ Increase shared_buffers

If hit_ratio = 0.99:
→ Hypothesis 1 rejected: Memory allocation OK
→ Test next hypothesis

Test Hypothesis 2:
SELECT 
  checkpoints_timed, 
  checkpoints_req, 
  checkpoint_write_time,
  checkpoint_sync_time 
FROM pg_stat_bgwriter;

If checkpoints_req > checkpoints_timed:
→ Hypothesis 2 confirmed: Max_wal_size too small
→ Increase max_wal_size

Test Hypothesis 3:
SELECT 
  schemaname,
  tablename,
  seq_scan,
  seq_tup_read,
  idx_scan,
  idx_tup_fetch
FROM pg_stat_user_tables
ORDER BY seq_scan DESC LIMIT 10;

If large tables have seq_scan >> 1000:
→ Hypothesis 3 likely: Missing indexes
→ Run EXPLAIN on those queries, add indexes

STEP 5: ISOLATE THE PROBLEM

If multiple issues exist, fix one at a time.

Example: Both buffer pool too small AND checkpoint tuning bad.

Fix #1: Increase shared_buffers
Restart. Measure improvement.

If queries now faster: Problem #1 fixed
If queries still slow: Problem #2 (checkpoints) is the remaining issue

This isolation is critical. Multiple changes = cannot isolate root cause.

STEP 6: IMPLEMENT AND VERIFY FIX

Change configuration
Restart affected service
Measure: Did the symptom improve?

Example:
ALTER SYSTEM SET shared_buffers = '16GB';
SELECT pg_reload_conf();
sudo systemctl restart postgresql@16
free -h    ← Should show < 50% memory used

STEP 7: DOCUMENT AND PREVENT RECURRENCE

Document in your runbook:
1. Problem: [Symptom]
2. Root cause: [Analysis]
3. Solution: [What changed]
4. Verification: [How to confirm]
5. Prevention: [Monitoring]

Example:
Problem: Slow INSERT queries
Root cause: shared_buffers = 256 MB too small for 64 GB system
Solution: Increased to 16 GB, restarted PostgreSQL
Verification: Buffer cache hit ratio increased to 99.8%
Prevention: Monitor pg_stat_bgwriter daily, alert if hit ratio < 0.95

PART 6: SUMMARY AND OPERATIONAL PRINCIPLES
================================================================================

We've covered enormous ground. Let's synthesize.

THE FIVE IMMUTABLE PRINCIPLES OF POSTGRESQL PRODUCTION

Principle 1: DURABILITY IS PARAMOUNT

Everything in PostgreSQL is designed around durability.
- WAL ensures committed data survives crashes
- Checksums detect corruption
- FSYNC guarantees persistence

Cost: Some throughput overhead for COMMIT operations.
Value: Data you can trust.

In production: Never compromise durability for speed.
Never disable fsync, checksums, or WAL.

Principle 2: INITIALIZATION DECISIONS ARE PERMANENT

Encoding, locale, WAL segment size, cluster location.
Set wrong = hours or days of downtime to fix.

Always ask before initializing:
- Is my encoding correct? (UTF-8, always)
- Is my locale correct? (en_US.UTF-8 or POSIX)
- Is my PGDATA on the right filesystem? (Good SSD)
- Is WAL on the right disk? (Fast, or same as PGDATA)

Double-check. Then triple-check.

Principle 3: MEMORY IS EVERYTHING

PostgreSQL speed = data in memory.
Slow PostgreSQL = data on disk.

Sizing:
- shared_buffers: 25% RAM (OLTP), 50% (OLAP)
- OS budget: 10% RAM
- work_mem: Depends on connections
- Headroom: 10-15% RAM unallocated

Memory exhaustion = OOM killer = PostgreSQL dies.

Monitor memory. Alert when available < 10% total.

Principle 4: STORAGE MATTERS

PostgreSQL lives on storage. Storage determines:
- Startup time (IOPS on initialization)
- Query latency (random I/O latency)
- COMMIT latency (fsync latency on WAL)
- Recovery time (checkpoint interval)

SSD/NVMe >> HDD for production.

RAID 1 for mission-critical.
RAID 5/6 for large datasets.

WAL on fast storage. Data on consistent storage.

Principle 5: OPERATE WITH CERTAINTY

Never make changes without understanding consequences.
Never guess at configuration.

Measure before and after every change.

Tools:
- pg_stat_statements: Track query performance
- pg_stat_bgwriter: Track background activity
- pg_stat_user_tables: Track table access patterns
- EXPLAIN ANALYZE: Understand query plans
- vmstat, iostat: Understand OS behavior

Data beats guessing.

✓ Encoding = UTF-8

✓ Cluster successfully initialized
✓ PostgreSQL starts cleanly

✓ shmmax set (RAM / 2)

  - Start PostgreSQL manually

  - Promote standby to primary (if using HA)

COMMON PITFALLS TO AVOID

1. Using SQL_ASCII encoding
   Impact: Cannot store international data, string operations fail
   Avoid: Always use UTF-8

2. Undersized shared_buffers
   Impact: Excessive disk I/O, slow queries, paging
   Avoid: Set to 25% RAM minimum

3. Ignoring kernel tuning
   Impact: Startup failures, performance limitations, crashes
   Avoid: Apply standard tuning before first production load

4. No data checksums
   Impact: Silent data corruption undetectable
   Avoid: Enable at initialization

5. No backup strategy
   Impact: Any corruption = data loss
   Avoid: Automated daily backups + restore testing

6. Using spinning disk for primary database
   Impact: 10x slower than SSD, poor query latency
   Avoid: Use SSD/NVMe for production

7. Running PostgreSQL as root
   Impact: Security vulnerability, wrong permissions
   Avoid: Always run as "postgres" user

8. Changing locale or encoding after initialization
   Impact: Index corruption, wrong query results
   Avoid: Get it right the first time

9. Filling disk (logs, WAL, or data)
   Impact: Database becomes read-only, unavailable
   Avoid: Monitor free disk space, alert at 85%

10. Not testing recovery procedures
    Impact: When disaster strikes, recovery fails
    Avoid: Monthly restore tests to backup location

FINAL THOUGHTS: THE DBA MINDSET

Being a PostgreSQL DBA in production is about:

1. Anticipation: What could go wrong? Plan for it.
2. Preparation: Have backups, runbooks, and monitoring ready.
3. Monitoring: See problems before they become disasters.
4. Methodical problem-solving: Gather data, form hypotheses, test.
5. Humility: The system will surprise you. Stay curious.
6. Documentation: Future you will thank present you.

The best production PostgreSQL systems are not interesting. They're boring.
They run reliably, consistently, without surprises.

This is your goal: A boring PostgreSQL database that just works.

To achieve it: Follow principles, avoid pitfalls, monitor relentlessly,
and trust data over intuition.
