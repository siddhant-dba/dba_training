Step 0.1: Verify PostgreSQL Service Status
================================================================================
CONCEPT:
  Before any security changes, establish a known-good baseline. In production,
  you never apply security controls to a broken system - you'll create 
  impossible-to-debug situations where you can't tell if access failure is due
  to misconfiguration or your new security policy.

COMMAND:
--------

EXPECTED OUTPUT:
----------------

WHAT THIS VALIDATES:
--------------------
✓ PostgreSQL process is running
✓ Socket/port is open and listening
✓ Database is not in recovery mode
✓ Connection pooling is functional

----------

Check: docker exec -it pg-db systemctl status postgresql (if systemd)

Step 0.4: Backup Current pg_hba.conf
================================================================================
CONCEPT:
  pg_hba.conf is the ONLY file controlling authentication. One wrong entry 
  can lock out all users including postgres superuser. In production, always
  keep the last-known-good config and test changes on a clone first.

---------

# Create timestamped backup

  /var/lib/postgresql/data/pg_hba.conf.backup.$(date +%Y%m%d_%H%M%S)

# Copy backup outside container (for disaster recovery)
docker cp pg-db:/var/lib/postgresql/data/pg_hba.conf /tmp/pg_hba.conf.original

EXPECTED OUTPUT:
----------------

# TYPE  DATABASE        USER            ADDRESS                 METHOD

host    all             all             0.0.0.0/0               md5

WHAT THIS VALIDATES:
--------------------
✓ You have rollback capability
✓ You can see current insecure settings (trust, md5, 0.0.0.0/0)
✓ Backup exists both inside and outside container

The default config above is INSECURE:

- 'md5' = outdated hash, vulnerable to rainbow tables
- '0.0.0.0/0' = allows entire internet if port exposed

================================================================================
TASK 1.1: MULTI-TIER pg_hba.conf POLICY
================================================================================

SECURITY OBJECTIVES:
====================
1. Implement Zero Trust networking (explicit allow, implicit deny)
2. Enforce least-privilege access (role-based, database-specific)
3. Eliminate weak authentication methods (trust, md5)
4. Use modern cryptographic authentication (scram-sha-256)
5. Prepare for certificate-based authentication (peer/cert)

THREAT MODEL:
=============
- Attacker on dev_wifi (192.168.100.0/24) → MUST be rejected entirely
- Compromised app-srv credentials → Limited to app_db only, no postgres DB
- MitM on corp_vpn → Mitigated by SSL (implemented in Task 1.2)
- Lateral movement from app-srv to mgmt functions → Prevented by DB isolation


Step 1.1.1: Design the HBA Policy Matrix
================================================================================
CONCEPT:
  pg_hba.conf is processed TOP-TO-BOTTOM, first match wins. Order matters
  critically. More specific rules (single IPs, specific DBs) go first,
  broader rules (subnets, all databases) go last, reject rules go at end.

POLICY MATRIX:
--------------
Source          | Database | User     | Auth Method        | SSL  | Allowed?
----------------|----------|----------|--------------------|------|----------
jumpbox (local) | postgres | dba      | peer               | N/A  | ✓
jumpbox (10.0.2.10) | postgres | dba  | scram-sha-256      | reqd | ✓
app-srv (10.0.1.20) | app_db | app_user | scram-sha-256    | reqd | ✓
corp_vpn (10.0.1.0/24) | app_db | app_user | scram-sha-256 | reqd | ✓
dev_wifi (192.168.100.0/24) | all | all | reject          | N/A  | ✗
localhost       | all      | postgres | peer               | N/A  | ✓
default         | all      | all      | reject             | N/A  | ✗

REASONING:
----------
- Local socket (peer) for emergency superuser access (no network = no lockout)
- Jumpbox gets postgres DB only (monitoring, backups, not application data)
- App tier gets app_db only (principle of least privilege)
- SSL required for all network connections (Task 1.2 will enforce verify-full)
- dev_wifi explicitly rejected (not just omitted - log the attempts)
- Catch-all reject (deny by default, not implicit trust)


Step 1.1.2: Write the New pg_hba.conf
================================================================================
COMMAND:
--------
docker exec -it pg-db bash -c 'cat > /var/lib/postgresql/data/pg_hba.conf.new <<'\''HBAEOF'\''
# PostgreSQL Client Authentication Configuration File
# ====================================================
# Phase 1 Security Hardening - Multi-Tier Access Control
# Applied: $(date)
#
# PROCESSING ORDER: First matching rule wins
# SECURITY LEVEL: Production-grade, zero-trust
#
# FORMAT:
# TYPE  DATABASE        USER            ADDRESS                 METHOD

# ============================================================================
# LOCAL SOCKET CONNECTIONS (Emergency Access)
# ============================================================================
# Allow postgres superuser via local socket only (no network exposure)
# Auth: peer = trust OS-level user identity (no password needed)
# Use case: docker exec -it pg-db psql -U postgres
local   all             postgres                                peer

# Allow DBA role via local socket for maintenance
local   postgres        dba                                     peer

# ============================================================================
# MANAGEMENT ZONE (10.0.2.0/24) - Monitoring & Administration
# ============================================================================
# Jumpbox: Allow DBA access to postgres database only (not app data)
# Auth: scram-sha-256 = modern password hashing (not reversible)
# Future: Will add clientcert=verify-full in Task 1.2
hostssl postgres        dba             10.0.2.10/32            scram-sha-256

# Reject any other management zone access explicitly
hostnossl all           all             10.0.2.0/24             reject
hostssl   all           all             10.0.2.0/24             reject

# ============================================================================
# CORPORATE VPN ZONE (10.0.1.0/24) - Application Access
# ============================================================================
# App server: Allow app_user to app_db only (database isolation)
# Auth: scram-sha-256 over SSL (Task 1.2 will enforce certificate validation)
hostssl app_db          app_user        10.0.1.20/32            scram-sha-256

# Broader corp_vpn subnet (if app-srv scales horizontally)
hostssl app_db          app_user        10.0.1.0/24             scram-sha-256

# Explicitly deny corp_vpn access to postgres database (privilege separation)
hostssl postgres        all             10.0.1.0/24             reject

# Deny non-SSL from corp_vpn
hostnossl all           all             10.0.1.0/24             reject

# ============================================================================
# DEVELOPER WIFI ZONE (192.168.100.0/24) - TOTAL LOCKDOWN
# ============================================================================
# Explicitly reject all developer access (not production-safe network)
# This logs attempts - pure omission would silently fall through to default reject
host    all             all             192.168.100.0/24        reject
hostssl all             all             192.168.100.0/24        reject

# ============================================================================
# LOCALHOST CONNECTIONS (Container Internal)
# ============================================================================
# Allow postgres superuser from localhost (for init scripts, cron jobs)
hostssl all             postgres        127.0.0.1/32            scram-sha-256
hostssl all             postgres        ::1/128                 scram-sha-256

# ============================================================================
# DEFAULT DENY (Catch-All Rule)
# ============================================================================
# Reject everything else (zero-trust: explicit allow only)
host    all             all             0.0.0.0/0               reject
host    all             all             ::/0                    reject
HBAEOF
'

WHAT THIS DOES:
---------------
✓ Eliminates all 'trust' authentication (password required everywhere)
✓ Eliminates all 'md5' authentication (upgraded to scram-sha-256)
✓ Enforces database-level isolation (app_user cannot touch postgres DB)
✓ Enforces network-zone isolation (dev_wifi completely blocked)
✓ Prepares for SSL enforcement (hostssl instead of host)
✓ Maintains emergency access (local socket with peer auth)

VERIFY THE FILE WAS CREATED:
----------------------------
docker exec -it pg-db cat /var/lib/postgresql/data/pg_hba.conf.new

Step 1.1.6: Enable Query Logging for Authentication Events
================================================================================
CONCEPT:
  Security controls without logging = security theater. In production,
  you must log auth failures to detect brute-force, lateral movement,
  or misconfiguration. This also helps debug legitimate connection issues.

COMMANDS:
---------
docker exec -it pg-db psql -U postgres <<'EOF'
-- Enable connection logging
ALTER SYSTEM SET log_connections = 'on';
ALTER SYSTEM SET log_disconnections = 'on';

-- Log all authentication attempts (success and failure)
ALTER SYSTEM SET log_line_prefix = '%t [%p] %u@%d from %h ';

-- Set log level to capture security events
ALTER SYSTEM SET log_min_messages = 'warning';

-- Log duration of long-running queries (performance + security)
ALTER SYSTEM SET log_min_duration_statement = 1000;  -- 1 second

-- Show current settings
SELECT name, setting, source FROM pg_settings 
WHERE name IN ('log_connections', 'log_disconnections', 'log_line_prefix');

-- Reload to apply
SELECT pg_reload_conf();
EOF

TASK 1.2: STRICT SSL/TLS WITH CERTIFICATE VALIDATION
================================================================================

SECURITY OBJECTIVES:
====================
1. Prevent man-in-the-middle attacks (MitM) on database connections
2. Enforce mutual TLS (both server and client authentication)
3. Bind certificates to specific hostnames (prevent cert reuse)
4. Use modern TLS 1.3 with strong cipher suites
5. Implement certificate-based authentication (stronger than passwords)

THREAT MODEL:
=============
- ARP spoofing on corp_vpn → Mitigated by certificate pinning
- Compromised network switch → Cannot decrypt TLS 1.3 traffic
- Stolen password → Useless without client certificate
- Certificate theft → Limited by CN validation and short expiry


Step 1.2.1: Install OpenSSL and Create CA Directory Structure
================================================================================
CONCEPT:
  Public Key Infrastructure (PKI) requires a Certificate Authority (CA) to
  sign certificates. In production, you'd use an internal CA (HashiCorp Vault,
  AWS ACM Private CA). For this lab, we'll create a self-signed CA.

COMMANDS:
---------
docker exec -it pg-db bash -c '
# Install OpenSSL if not present
apt-get update && apt-get install -y openssl

# Create CA directory structure
mkdir -p /var/lib/postgresql/ca/{private,certs,newcerts}
cd /var/lib/postgresql/ca

# Initialize CA database
touch index.txt
echo 1000 > serial

# Set restrictive permissions (private keys must be secret)
chmod 700 private
'

WHAT THIS VALIDATES:
--------------------
✓ OpenSSL available for certificate operations
✓ CA directory follows X.509 best practices
✓ Private key directory protected (only postgres user can read)


Step 1.2.2: Create Root CA Certificate
================================================================================
CONCEPT:
  The Root CA is the trust anchor. Anyone with this CA cert can validate
  certificates you sign. In production, this would be stored in an HSM or
  air-gapped machine. Compromise = total PKI collapse.

COMMAND:
--------
docker exec -it pg-db bash -c 'cat > /var/lib/postgresql/ca/openssl.cnf <<'\''CAFEOF'\''
[ ca ]
default_ca = CA_default

[ CA_default ]
dir               = /var/lib/postgresql/ca
certs             = $dir/certs
crl_dir           = $dir/crl
new_certs_dir     = $dir/newcerts
database          = $dir/index.txt
serial            = $dir/serial
private_key       = $dir/private/ca.key
certificate       = $dir/certs/ca.crt
default_md        = sha256
default_days      = 3650
preserve          = no
policy            = policy_loose

[ policy_loose ]
countryName             = optional
stateOrProvinceName     = optional
localityName            = optional
organizationName        = optional
organizationalUnitName  = optional
commonName              = supplied
emailAddress            = optional

[ req ]
default_bits        = 4096
distinguished_name  = req_distinguished_name
string_mask         = utf8only
default_md          = sha256
x509_extensions     = v3_ca

[ req_distinguished_name ]
countryName                     = Country Name (2 letter code)
stateOrProvinceName             = State or Province Name

Step 1.2.3: Generate PostgreSQL Server Certificate
================================================================================
CONCEPT:
  The server certificate CN (Common Name) MUST match the hostname clients
  use to connect. If they connect via IP, CN should be IP. If via DNS, CN
  should be FQDN. Mismatch = TLS validation failure.

CRITICAL: Our pg-db hostname for this lab
  - From corp_vpn: 10.0.1.10
  - From mgmt_zone: 10.0.2.20
  - Hostname: pg-db (Docker internal DNS)
  
We'll create a cert with Subject Alternative Names (SAN) for all three.

COMMAND:
--------

prompt              = no

C  = US
ST = California
L  = SanFrancisco
O  = LabOrg
OU = Database Servers
CN = pg-db.internal

keyUsage = keyEncipherment, dataEncipherment
extendedKeyUsage = serverAuth
subjectAltName = @alt_names

DNS.2 = pg-db.internal
DNS.3 = localhost
IP.1  = 10.0.1.10
IP.2  = 10.0.2.20
IP.3  = 127.0.0.1

# Generate server private key (unencrypted for auto-start)
openssl genrsa -out private/server.key 2048

# Create Certificate Signing Request (CSR)

# Sign server cert with CA (valid 1 year)

chmod 600 private/server.key
chmod 644 certs/server.crt certs/ca.crt
'

Step 1.2.4: Configure PostgreSQL to Use SSL
================================================================================
CONCEPT:
  PostgreSQL needs to know where certs are and which TLS versions/ciphers
  to accept. Modern config = TLS 1.2+ only, disable weak ciphers.

COMMANDS:
---------
docker exec -it pg-db psql -U postgres <<'EOF'
-- Enable SSL
ALTER SYSTEM SET ssl = 'on';

-- Point to certificate files
ALTER SYSTEM SET ssl_cert_file = '/var/lib/postgresql/ca/certs/server.crt';
ALTER SYSTEM SET ssl_key_file = '/var/lib/postgresql/ca/private/server.key';
ALTER SYSTEM SET ssl_ca_file = '/var/lib/postgresql/ca/certs/ca.crt';

-- Enforce TLS 1.2 and 1.3 only (disable SSLv3, TLS 1.0, TLS 1.1)
ALTER SYSTEM SET ssl_min_protocol_version = 'TLSv1.2';

-- Use strong cipher suites only (ECDHE for perfect forward secrecy)
ALTER SYSTEM SET ssl_ciphers = 'HIGH:MEDIUM:+3DES:!aNULL:!eNULL:!EXPORT:!DES:!MD5:!PSK:!RC4';

-- Prefer server cipher order (server chooses strongest cipher)
ALTER SYSTEM SET ssl_prefer_server_ciphers = 'on';

-- Show current SSL settings
SELECT name, setting FROM pg_settings WHERE name LIKE 'ssl%';

-- Restart required for SSL changes
\q
EOF

# Restart PostgreSQL to apply SSL configuration
docker restart pg-db

# Wait for startup
sleep 5
docker exec -it pg-db pg_isready -h localhost

# Verify SSL is enabled
docker exec -it pg-db psql -U postgres -c "SHOW ssl;"

Step 1.2.5: Update pg_hba.conf to Enforce SSL and Client Certificates
================================================================================
CONCEPT:
  Current pg_hba.conf uses 'hostssl' but doesn't validate client certs.
  We'll add 'clientcert=verify-full' to require clients to present valid
  certificates signed by our CA. This is mutual TLS (mTLS).

COMMAND:
--------
docker exec -it pg-db bash -c 'cat > /var/lib/postgresql/data/pg_hba.conf <<'\''HBAEOF2'\''
# PostgreSQL Client Authentication Configuration File
# ====================================================
# Phase 1 Security Hardening - SSL + Certificate Validation
# Applied: $(date)
#
# SECURITY LEVEL: Production-grade, mutual TLS

# ============================================================================
# LOCAL SOCKET CONNECTIONS (Emergency Access)
# ============================================================================
local   all             postgres                                peer
local   postgres        dba                                     peer

# ============================================================================
# MANAGEMENT ZONE (10.0.2.0/24) - Monitoring & Administration
# ============================================================================
# Jumpbox: Require client certificate + password (defense in depth)
hostssl postgres        dba             10.0.2.10/32            scram-sha-256 clientcert=verify-full

# Reject non-SSL and unauthorized mgmt access
hostnossl all           all             10.0.2.0/24             reject
hostssl   all           all             10.0.2.0/24             reject

# ============================================================================
# CORPORATE VPN ZONE (10.0.1.0/24) - Application Access
# ============================================================================
# App server: Require client certificate + password
hostssl app_db          app_user        10.0.1.20/32            scram-sha-256 clientcert=verify-full
hostssl app_db          app_user        10.0.1.0/24             scram-sha-256 clientcert=verify-full

# Deny access to postgres database from corp_vpn
hostssl postgres        all             10.0.1.0/24             reject
hostnossl all           all             10.0.1.0/24             reject

# ============================================================================
# DEVELOPER WIFI ZONE (192.168.100.0/24) - TOTAL LOCKDOWN
# ============================================================================

hostssl all             all             192.168.100.0/24        reject

# ============================================================================

Step 1.2.6: Generate Client Certificates for DBA and App User
================================================================================
CONCEPT:
  Client certificates authenticate the user to the server. The CN field
  MUST match the PostgreSQL role name. Without this match, even with valid
  signature, authentication fails.

COMMANDS:
---------
docker exec -it pg-db bash -c '
cd /var/lib/postgresql/ca

# Generate DBA client certificate
openssl genrsa -out private/dba.key 2048

openssl req -new -key private/dba.key -out dba.csr \
  -subj "/C=US/ST=California/L=SanFrancisco/O=LabOrg/OU=DBAs/CN=dba"

openssl x509 -req -in dba.csr -CA certs/ca.crt -CAkey private/ca.key \
  -passin pass:CASecurePass2024 -CAcreateserial -out certs/dba.crt \
  -days 365 -sha256

# Generate app_user client certificate  
openssl genrsa -out private/app_user.key 2048

openssl req -new -key private/app_user.key -out app_user.csr \
  -subj "/C=US/ST=California/L=SanFrancisco/O=LabOrg/OU=Applications/CN=app_user"

openssl x509 -req -in app_user.csr -CA certs/ca.crt -CAkey private/ca.key \
  -passin pass:CASecurePass2024 -CAcreateserial -out certs/app_user.crt \
  -days 365 -sha256

# Verify client certificates
openssl x509 -in certs/dba.crt -noout -subject
openssl x509 -in certs/app_user.crt -noout -subject

# Set permissions
chmod 600 private/dba.key private/app_user.key
chmod 644 certs/dba.crt certs/app_user.crt
'

TASK 1.3: NETWORK ISOLATION (PORT & LISTEN ADDRESS)

SECURITY OBJECTIVES:
====================
1. Reduce attack surface (non-standard port)
2. Prevent accidental exposure (bind to specific IPs only)

THREAT MODEL:
=============
- Port scanner (nmap) → Won't find DB on standard 5432

- Accidental Docker port publish → Binds to wrong interface
- Automated exploit scripts → Target 5432, not 15432


Step 1.3.1: Change PostgreSQL Listen Port
================================================================================
CONCEPT:
  Default port 5432 is well-known (IANA registered). Changing it doesn't
  provide real security (security by obscurity), but it reduces noise from
  automated scanners and makes firewall rules more granular. In production,
  combine with proper firewall rules.

COMMANDS:
---------
docker exec -it pg-db psql -U postgres <<'EOF'
-- Change port from 5432 to 15432
ALTER SYSTEM SET port = 15432;

-- Show current setting (won't take effect until restart)
SHOW port;

-- Restart required for port change
\q
EOF

# Restart PostgreSQL
docker restart pg-db

# Wait for startup
sleep 5

# Verify new port is listening
docker exec -it pg-db ss -tlnp | grep postgres

EXPECTED OUTPUT:
----------------

 port 
------

[After restart]

WHAT THIS VALIDATES:
--------------------
✓ Port changed to 15432
✓ PostgreSQL listening on new port
✓ Old port (5432) no longer bound

Step 1.3.2: Bind to Specific Network Interfaces Only
================================================================================
CONCEPT:
  Default listen_addresses='*' binds to 0.0.0.0 (all interfaces). This is
  dangerous if container has public interface. Bind only to required IPs:
  - 10.0.1.10 (corp_vpn interface)
  - 10.0.2.20 (mgmt_zone interface)
  - NOT 127.0.0.1 (prevent localhost bypass)
  - NOT 0.0.0.0 (prevent wildcard binding)

COMMANDS:
---------
docker exec -it pg-db psql -U postgres -p 15432 <<'EOF'
-- Bind only to specific private interfaces
ALTER SYSTEM SET listen_addresses = '10.0.1.10,10.0.2.20';

-- Show current setting
SHOW listen_addresses;

-- Restart required
\q
EOF

# Restart PostgreSQL
docker restart pg-db
sleep 5

# Verify listening addresses
docker exec -it pg-db ss -tlnp | grep 15432

EXPECTED OUTPUT:
----------------
ALTER SYSTEM

LISTEN  0  128  10.0.2.20:15432  0.0.0.0:*  users:(("postgres",pid=1235,fd=8))

WHAT THIS VALIDATES:
--------------------
✓ Listening ONLY on specified IPs

TROUBLESHOOTING GUIDE
================================================================================

SYMPTOM: "Connection refused"
DIAGNOSIS: Port not listening OR firewall blocking
FIX: 
  docker exec -it pg-db ss -tlnp | grep 15432
  docker exec -it jumpbox nc -zv 10.0.2.20 15432

SYMPTOM: "FATAL: pg_hba.conf rejects connection"
DIAGNOSIS: HBA rule missing or wrong order
FIX:
  docker exec -it pg-db cat /var/lib/postgresql/data/pg_hba.conf
  Check source IP, database, user match
  Verify rule order (more specific rules first)

SYMPTOM: "connection requires a valid client certificate"
DIAGNOSIS: clientcert=verify-full but cert not presented
FIX:
  ls -l ~/.postgresql/postgresql.{crt,key,root.crt}
  chmod 600 ~/.postgresql/postgresql.key
  psql "...sslmode=verify-full"

SYMPTOM: "certificate authentication failed"
DIAGNOSIS: Certificate CN doesn't match username
FIX:
  openssl x509 -in ~/.postgresql/postgresql.crt -noout -subject
  Verify CN=<username>

SYMPTOM: "SSL error: certificate verify failed"
DIAGNOSIS: Server certificate not trusted by client
FIX:
  Ensure ~/.postgresql/root.crt contains CA certificate
  psql "...sslmode=verify-full" (not just require)

SYMPTOM: Locked out completely
EMERGENCY FIX:
  docker cp /tmp/pg_hba.conf.original pg-db:/var/lib/postgresql/data/pg_hba.conf
  docker exec -it pg-db psql -U postgres -c "SELECT pg_reload_conf();"
  OR
  docker restart pg-db
