================================================================================
  BACKUP TAXONOMY — TWO MINUTES OF CONTEXT
================================================================================

Before we touch a command, I need everyone aligned on vocabulary.

  PHYSICAL BACKUP — a binary copy of the PostgreSQL data directory. Includes
  every file, every page, every relation. You can't inspect it without
  restoring it. You CAN do point-in-time recovery from it combined with WAL.
  Tools: pgBackRest, WAL-G, pg_basebackup.

  LOGICAL BACKUP — a SQL-level export of database objects. Human-readable
  (custom format aside). You CAN inspect it, selectively restore from it,
  and move it between PostgreSQL versions. Slower for large databases.
  Tools: pg_dump, pg_dumpall.

  WAL ARCHIVING — continuous shipping of WAL segment files to an archive
  location (local disk, S3, GCS). Combined with a physical base backup,
  this enables PITR — Point-in-Time Recovery — which means you can recover
  to any second in history, not just the moment the backup was taken.

  PITR — the crown jewel of PostgreSQL recovery. Requires: (1) a base backup
  AND (2) continuous WAL archive from the time of that backup to now.
  Without both, you cannot do PITR.

These are not interchangeable. You need BOTH logical and physical strategies.
Logical for surgical restores. Physical for full restores and PITR. Any shop
running only one is at risk.

================================================================================
  RUNBOOK 01: BACKUP INTEGRITY CHECK FAILS
  File: 03_backup_recovery/backup_integrity_check_fails.md
================================================================================

Your monitoring reports that the backup integrity check failed. Before you
escalate this, before you panic, before you do anything else — understand
exactly what FAILED. "Integrity check failed" can mean five different things
depending on your tooling, and each one has a different response.

── DIAGNOSIS ──────────────────────────────────────────────────────────────────

```bash
# pgBackRest: verbose check output tells you exactly what failed:
pgbackrest --stanza=main --log-level-console=detail check

# What pgbackrest check actually verifies:
# 1. Archive WAL can be retrieved for all backup ranges.
# 2. The backup manifest is intact and checksums match.
# 3. The stanza configuration is consistent.

# For pg_dump logical backups — check file integrity:
pg_restore --list /backup/pgdump/mydb_$(date +%Y%m%d).dump > /dev/null
echo "Exit code: $?"   # 0 = intact, non-zero = corrupted

# Verify checksum of the backup file:
sha256sum /backup/pgdump/mydb_$(date +%Y%m%d).dump
# Compare against the .sha256 file written at backup time.

# For WAL-G: verify backup:
wal-g backup-verify LATEST

# Physical backup page-level verification (pgBackRest):
pgbackrest --stanza=main verify
```

```sql
-- Check WAL archiver for gaps (if archiving is healthy, no integrity gaps):
SELECT
    archived_count,
    failed_count,
    last_archived_wal,
    last_archived_time,
    last_failed_wal,
    last_failed_time,
    stats_reset
FROM pg_stat_archiver;
```

── STEP-BY-STEP PROCEDURE ─────────────────────────────────────────────────────

Root Cause A: WAL gap in the archive — backup exists but WAL range is incomplete.

1. **Identify the missing WAL segment:**

   ```bash
   # pgBackRest will name the specific segment in the error:
   pgbackrest --stanza=main --log-level-console=detail check 2>&1 \
       | grep -i "error\|missing\|archive"

   # The error will look like:
   # "unable to find WAL segment 000000010000000000000042 in the archive"
   ```

2. **Check if the segment exists on the primary's pg_wal:**

   ```bash
   ls /var/lib/postgresql/15/main/pg_wal/ | grep 000000010000000000000042
   ```

   If it's still there — re-archive it manually:

   ```bash
   # Get the archive_command from postgresql.conf and run it manually:
   archive_cmd=$(psql -At -c "SHOW archive_command;")
   # Replace %f with the filename and %p with the full path:
   # e.g., if archive_command = 'pgbackrest --stanza=main archive-push %p'
   pgbackrest --stanza=main archive-push \
       /var/lib/postgresql/15/main/pg_wal/000000010000000000000042
   ```

   If it's NOT there — it was recycled. The backup with this gap is
   UNRECOVERABLE for PITR through that window. Take a new base backup.

Root Cause B: Backup manifest checksum mismatch.

3. **The backup file itself is corrupt:**

   ```bash
   # pgBackRest:
   pgbackrest --stanza=main verify
   # Will show which files have checksum mismatches.
   ```

   If files are corrupt — the backup is not usable. Do not delete it yet
   (forensic value). Run a new backup immediately:

   ```bash
   pgbackrest --stanza=main --type=full backup
   ```

Root Cause C: Configuration mismatch (archive_command doesn't match stanza).

4. **Verify stanza config matches postgresql.conf:**

   ```bash
   pgbackrest --stanza=main stanza-upgrade
   cat /etc/pgbackrest/pgbackrest.conf
   psql -c "SHOW archive_command;"
   ```

── VERIFICATION ───────────────────────────────────────────────────────────────

```bash
# Clean check output — no errors, archive test passes:
pgbackrest --stanza=main check
# Expected: "check command end: completed successfully"

# List backups — confirm a valid set exists:
pgbackrest --stanza=main info
```

── ROLLBACK ───────────────────────────────────────────────────────────────────

There is no rollback for a failed integrity check. The action is: take a fresh
backup. Never delete an old backup until a new one is verified. Keep N+1 backups
at all times — N is your retention requirement, +1 is the current backup being
verified before the oldest is pruned.

================================================================================
  RUNBOOK 02: BACKUP VERIFICATION AUTOMATION
  File: 03_backup_recovery/backup_verification_automation.md
================================================================================

I want to say something that I feel strongly about, so I'm going to say it
plainly: a backup you have never restored is not a backup. It is a file. It
might be a perfectly good file. You won't know until you test it.

Automated backup verification means: on a schedule, in a test environment,
restore your backup and run validation queries. Every night. Without fail.

── DIAGNOSIS / PRE-FLIGHT ─────────────────────────────────────────────────────

```bash
# Check whether you currently have ANY automated restore testing:
crontab -l | grep -i restore
ls /opt/scripts/ | grep -i verify
ls /opt/scripts/ | grep -i restore
# If these return nothing — you have a gap. This runbook closes it.
```

── STEP-BY-STEP PROCEDURE ─────────────────────────────────────────────────────

1. **Design the verification pipeline** — the minimum viable version:

   Step 1: Restore the latest backup to a dedicated verify instance.
   Step 2: Run validation queries (row counts, checksums, spot checks).
   Step 3: Report the result to your monitoring system.
   Step 4: Keep the verify instance running for 24 hours before pruning.

2. **Build the verification script:**

   ```bash
   #!/usr/bin/env bash
   # /opt/scripts/verify_backup.sh
   set -euo pipefail

   STANZA="main"
   VERIFY_PGDATA="/var/lib/postgresql/verify/data"
   VERIFY_PORT=5433
   LOG="/var/log/backup_verify_$(date +%Y%m%d_%H%M%S).log"
   ALERT_EMAIL="dba-alerts@company.com"

   log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "$LOG"; }

   log "=== BACKUP VERIFICATION STARTING ==="

   # Step 1: Restore latest backup to verify location
   log "Restoring latest pgBackRest backup..."
   rm -rf "$VERIFY_PGDATA"
   mkdir -p "$VERIFY_PGDATA"
   chmod 700 "$VERIFY_PGDATA"

   pgbackrest --stanza="$STANZA" \
       --pg1-path="$VERIFY_PGDATA" \
       --recovery-option="recovery_target=immediate" \
       --recovery-option="recovery_target_action=promote" \
       restore \
       >> "$LOG" 2>&1

   # Step 2: Start verify instance on a different port
   log "Starting verification PostgreSQL instance on port $VERIFY_PORT..."
   cat >> "$VERIFY_PGDATA/postgresql.conf" << EOF
   port = $VERIFY_PORT
   hot_standby = off
   archive_mode = off
   EOF

   pg_ctlcluster 15 verify start 2>> "$LOG"
   sleep 10

   # Step 3: Run validation queries
   log "Running validation queries..."

   VERIFY_PSQL="psql -p $VERIFY_PORT -U postgres -d postgres"

   # Check database is accepting connections:
   $VERIFY_PSQL -c "SELECT version();" >> "$LOG" 2>&1

   # Row count spot checks (customise per your schema):
   $VERIFY_PSQL -At -c "
       SELECT schemaname||'.'||tablename, reltuples::bigint
       FROM pg_class c
       JOIN pg_namespace n ON n.oid = c.relnamespace
       WHERE relkind = 'r'
         AND schemaname NOT IN ('pg_catalog','information_schema')
       ORDER BY reltuples DESC LIMIT 10;
   " >> "$LOG" 2>&1

   # Application-level spot check (add your own):
   # $VERIFY_PSQL -d myapp -c "SELECT count(*) FROM orders WHERE created_at > now() - interval '7 days';"

   # Step 4: Report
   log "=== VERIFICATION COMPLETED SUCCESSFULLY ==="

   # Post result to monitoring (Prometheus pushgateway example):
   # echo "backup_verify_success 1" | curl --data-binary @- \
   #     http://pushgateway:9091/metrics/job/backup_verify

   # Or mail the log:
   mail -s "Backup Verification: SUCCESS $(date +%Y-%m-%d)" \
       "$ALERT_EMAIL" < "$LOG"

   # Cleanup verify instance:
   pg_ctlcluster 15 verify stop
   rm -rf "$VERIFY_PGDATA"
   ```

   Error handling: wrap the entire script in a trap that sends failure alerts:

   ```bash
   trap 'mail -s "BACKUP VERIFY FAILED $(date)" "$ALERT_EMAIL" < "$LOG"; \
         pg_ctlcluster 15 verify stop 2>/dev/null; exit 1' ERR
   ```

3. **Schedule it in cron (daily, off-peak):**

   ```bash
   # crontab -e as postgres user:
   0 3 * * * /opt/scripts/verify_backup.sh >> /var/log/backup_verify_cron.log 2>&1
   ```

4. **Add dedicated monitoring alert:** if verify has not reported SUCCESS in
   the last 25 hours — alert. This catches silent cron failures.

── VERIFICATION ───────────────────────────────────────────────────────────────

```bash
# Run the script manually first time to confirm it works end-to-end:
/opt/scripts/verify_backup.sh

# Check the log:
tail -50 /var/log/backup_verify_*.log

# Confirm the verify instance starts and queries return expected data.
```

── ROLLBACK ───────────────────────────────────────────────────────────────────

The verify instance runs on a separate data directory and port. It is
completely isolated from production. If the script fails midway — stop the
verify instance manually and clean up the temp data directory:
`pg_ctlcluster 15 verify stop; rm -rf /var/lib/postgresql/verify/data`
Production is never touched by this process.

================================================================================
  RUNBOOK 03: DISASTER RECOVERY DRILL CHECKLIST
  File: 03_backup_recovery/disaster_recovery_drill_checklist.md
================================================================================

A DR drill is a rehearsal. You simulate the worst-case scenario — total primary
loss, datacenter unavailable — and you execute your recovery procedures with
a stopwatch running. The goal is not to pass. The goal is to find the gaps
before a real incident does.

I've been part of DR drills where we discovered:
  - The restore script referenced a bucket that was renamed two months ago.
  - The recovery point we needed was in a backup tier with 4-hour retrieval.
  - The application team had no documented procedure for pointing the app at
    a restored database on a new hostname.
  - Nobody knew the password for the monitoring database.

Every one of those discoveries was painful in a drill and would have been
catastrophic in a real event.

── DIAGNOSIS / PRE-FLIGHT ─────────────────────────────────────────────────────

```bash
# Before the drill: confirm backup state is healthy:
pgbackrest --stanza=main info
pgbackrest --stanza=main check

# Confirm WAL archive is current (no older than your RPO target):
psql -c "SELECT last_archived_time, now() - last_archived_time AS archive_age
         FROM pg_stat_archiver;"
# archive_age should be < 5 minutes for standard OLTP.
```

================================================================================
  RUNBOOK 04: PG_DUMP / RESTORE TROUBLESHOOTING
  File: 03_backup_recovery/pg_dump_restore_troubleshooting.md
================================================================================

pg_dump is the workhorse of logical backup. It is deceptively simple on the
surface — pg_dump mydb > mydb.sql — and deceptively complex when something
goes wrong. The most common failure modes: version mismatches, permission
errors, encoding problems, large-object handling, and tablespace paths.

── DIAGNOSIS ──────────────────────────────────────────────────────────────────

```bash
# Check pg_dump version vs server version (must be same MAJOR version or newer):
pg_dump --version
psql -c "SELECT version();"

# For a failed dump: check exit code and stderr:
pg_dump -Fc -d mydb -f /tmp/mydb.dump 2>/tmp/dump_errors.txt
echo "Exit code: $?"
cat /tmp/dump_errors.txt

# For a failed restore: check pg_restore exit code:
pg_restore -d mydb_restore /tmp/mydb.dump 2>/tmp/restore_errors.txt
echo "Exit code: $?"
cat /tmp/restore_errors.txt
```

```sql
-- Check for objects that may cause dump issues:
-- Large objects:
SELECT count(*) AS large_objects FROM pg_largeobject_metadata;

-- Tables with unusual storage parameters:
SELECT relname, reloptions FROM pg_class
WHERE reloptions IS NOT NULL AND relkind = 'r';

-- Extensions that may not exist on the target:
SELECT extname, extversion FROM pg_extension ORDER BY extname;
```

── STEP-BY-STEP PROCEDURE ─────────────────────────────────────────────────────

Root Cause A: pg_dump version mismatch.

1. **Always use the server-version pg_dump binary:**

   ```bash
   # Bad:
   pg_dump -Fc mydb > mydb.dump   # uses whatever pg_dump is in PATH

   # Good:
   /usr/lib/postgresql/15/bin/pg_dump -Fc mydb > mydb.dump
   # Use the version that MATCHES the source server.
   ```

Root Cause B: Permission errors during dump.

2. **The dump role must have SELECT on all tables:**

   ```sql
   -- Grant read access to dump role:
   GRANT CONNECT ON DATABASE mydb TO backup_user;
   GRANT USAGE ON SCHEMA public TO backup_user;
   GRANT SELECT ON ALL TABLES IN SCHEMA public TO backup_user;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public
       GRANT SELECT ON TABLES TO backup_user;
   ```

Root Cause C: Encoding mismatch on restore.

3. **Restore target database must match source encoding:**

   ```sql
   -- Check source encoding:
   SELECT pg_encoding_to_char(encoding) FROM pg_database WHERE datname = 'mydb';

   -- Create target with matching encoding:
   CREATE DATABASE mydb_restore
       ENCODING = 'UTF8'
       LC_COLLATE = 'en_US.UTF-8'
       LC_CTYPE = 'en_US.UTF-8'
       TEMPLATE = template0;  -- IMPORTANT: use template0, not template1
   ```

Root Cause D: Tablespace references on restore.

4. **If the source had custom tablespaces that don't exist on the target:**

   ```bash
   # Redirect tablespace to pg_default on restore:
   pg_restore -d mydb_restore \
       --tablespace-map="old_tablespace_name=pg_default" \
       /backup/mydb.dump
   ```

Root Cause E: Large object errors.

5. **pg_dump needs a superuser or the lo_compat_privileges setting to dump
   large objects:**

   ```bash
   # Use superuser for dump if large objects are present:
   pg_dump -Fc -U postgres mydb > mydb.dump

   # On restore: large objects restore automatically with the dump.
   # For plain SQL format: you must use pg_dump with -b (include blobs):
   pg_dump -Fp -b mydb > mydb.sql
   ```

Root Cause F: Partial restore errors (some objects failed, others succeeded).

6. **Use --exit-on-error with pg_restore for critical restores. Without it,
   pg_restore continues past errors and returns exit code 1 at the end:**

   ```bash
   # Strict mode — fails fast on first error:
   pg_restore --exit-on-error -d mydb_restore /backup/mydb.dump

   # For non-critical restores where some errors are acceptable:
   pg_restore -d mydb_restore /backup/mydb.dump 2>&1 | grep "^pg_restore: error"
   ```

7. **Restore only specific tables (surgical restore):**

   ```bash
   # List the dump contents:
   pg_restore --list /backup/mydb.dump | grep -i "orders"

   # Restore only the orders table and its indexes:
   pg_restore -d mydb_restore \
       -t orders \
       /backup/mydb.dump
   ```

── VERIFICATION ───────────────────────────────────────────────────────────────

```sql
-- After restore: compare row counts between source and target:
-- On SOURCE:
SELECT relname, reltuples FROM pg_class WHERE relkind = 'r'
AND relnamespace = 'public'::regnamespace
ORDER BY reltuples DESC;

-- On TARGET: same query — counts should match (or be close for MVCC reasons).

-- Verify indexes exist:
SELECT indexname FROM pg_indexes WHERE tablename = 'orders';
```

── ROLLBACK ───────────────────────────────────────────────────────────────────

pg_dump is non-destructive on the source. If a restore goes wrong, drop the
target database and start again: `DROP DATABASE mydb_restore;`
Never restore into a production database directly — always restore to a named
recovery database and validate before swapping.

================================================================================
  RUNBOOK 05: PGBACKREST HA SETUP
  File: 03_backup_recovery/pgbackrest_ha_setup.md
================================================================================

pgBackRest is the tool I recommend to everyone. Not because it's the only
option — WAL-G is excellent too, we'll cover it next — but because pgBackRest
has the most complete feature set for PostgreSQL specifically: incremental
backups, delta restore, parallel processing, built-in retention, S3/GCS/Azure
support, backup from standby, and the cleanest verify workflow in the business.

HA setup for pgBackRest means: the backup repository is accessible from
multiple nodes, and backups can be taken from a standby (offloading I/O from
the primary). This is production-grade backup design.

── DIAGNOSIS / PRE-FLIGHT ─────────────────────────────────────────────────────

```bash
# Confirm pgBackRest version (should be 2.47+ for latest features):
pgbackrest version

# Check repository accessibility from all nodes:
pgbackrest --stanza=main repo-ls /  # test repository access

# Check S3 credentials if using S3 repository:
aws s3 ls s3://your-backup-bucket/ --request-payer requester
```

── STEP-BY-STEP PROCEDURE ─────────────────────────────────────────────────────

1. **Install pgBackRest on primary AND all standbys:**

   ```bash
   # Debian/Ubuntu:
   apt-get install -y pgbackrest

   # Or from source:
   # https://pgbackrest.org/user-guide.html#installation
   ```

2. **Configure the pgbackrest.conf on each node** — the global section
   defines the repository; the stanza section defines the cluster:

   ```ini
   # /etc/pgbackrest/pgbackrest.conf (same file on ALL nodes)

   [global]
   # Repository configuration — use S3 for shared access across nodes:
   repo1-type=s3
   repo1-path=/pgbackrest
   repo1-s3-bucket=your-backup-bucket
   repo1-s3-endpoint=s3.amazonaws.com
   repo1-s3-region=us-east-1
   repo1-s3-key=AKIAIOSFODNN7EXAMPLE
   repo1-s3-key-secret=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY

   # OR for local/NFS repository (simpler for on-prem):
   # repo1-type=posix
   # repo1-path=/backup/pgbackrest

   repo1-retention-full=2          # keep 2 full backups
   repo1-retention-diff=7          # keep 7 differential backups

   # Parallel processing — tune to your server:
   process-max=4
   log-level-console=warn
   log-level-file=info

   # Compress backups:
   compress-type=lz4
   compress-level=1

   [main]
   pg1-path=/var/lib/postgresql/15/main
   pg1-port=5432
   pg1-user=postgres

   # HA: also register the standby so backup can be taken from it:
   pg2-path=/var/lib/postgresql/15/main
   pg2-port=5432
   pg2-host=<standby_ip>
   pg2-host-user=postgres
   ```

3. **Create the stanza on the PRIMARY:**

   ```bash
   sudo -u postgres pgbackrest --stanza=main stanza-create
   ```

4. **Verify setup:**

   ```bash
   sudo -u postgres pgbackrest --stanza=main check
   # Expected: "check command end: completed successfully"
   ```

5. **Take your first full backup:**

   ```bash
   sudo -u postgres pgbackrest --stanza=main --type=full backup
   pgbackrest --stanza=main info
   ```

6. **Configure backup FROM STANDBY** — this is the HA advantage. Heavy backup
   I/O hits the standby, not the primary:

   ```bash
   # Run this from the STANDBY server, targeting the standby's data dir:
   sudo -u postgres pgbackrest --stanza=main \
       --pg1-host=<primary_ip> \   # pgBackRest needs primary for catalog
       backup --type=full
   ```

   The backup reads data from the standby but WAL and catalog info from the
   primary. Your primary CPU and I/O stay unaffected.

7. **Schedule backups in cron:**

   ```bash
   # crontab -e as postgres user:
   # Full backup: Sunday 1 AM
   0 1 * * 0 pgbackrest --stanza=main --type=full backup
   # Differential backup: Mon-Sat 1 AM
   0 1 * * 1-6 pgbackrest --stanza=main --type=diff backup
   # Incremental: every 6 hours
   0 */6 * * * pgbackrest --stanza=main --type=incr backup
   ```

── VERIFICATION ───────────────────────────────────────────────────────────────

```bash
# Full info output — shows backup history and WAL archive status:
pgbackrest --stanza=main info

# Expected output includes:
# status: ok
# db (prior):      backup set with begin/end times
# archive: min/max WAL, whether current WAL is archived

# Full integrity check:
pgbackrest --stanza=main verify
```

── ROLLBACK ───────────────────────────────────────────────────────────────────

If pgBackRest configuration causes postgresql.conf conflicts (archive_command
mismatch), revert postgresql.conf and reload. The stanza can be deleted from
the repository with `pgbackrest --stanza=main stanza-delete --force` but this
destroys all backups in that stanza — only do this to start over completely.

================================================================================
  RUNBOOK 06: PITR RECOVERY PROCEDURES
  File: 03_backup_recovery/pitr_recovery_procedures.md
================================================================================

Point-in-Time Recovery. This is the one. If you leave this course knowing
how to do exactly one thing from the backup module — make it PITR.

PITR lets you say: "Restore the database to the state it was in at 14:23:47 on
June 15th." Not the morning. Not the day. The second. You can use it to recover
from a dropped table, a botched migration, a corrupted data load — anything
where you know WHEN things went wrong and want to wind back to just before.

PITR requires:
  1. A full base backup taken BEFORE the target recovery time.
  2. Continuous WAL archive from the base backup time through the target time.
  Without BOTH of these — PITR is not possible.

── DIAGNOSIS ──────────────────────────────────────────────────────────────────

```bash
# Confirm a base backup exists that predates your target recovery time:
pgbackrest --stanza=main info
# Look at the backup "begin" timestamps. Your target time must be AFTER
# the begin of a backup, not before.

# Confirm WAL archive covers the target time:
# pgBackRest shows the min/max archived WAL in 'info' output.
# You need: archive min <= backup begin AND archive max >= target time.

# Identify the approximate LSN of the target recovery point:
# Check application logs for the timestamp of the problematic event.
# Check PostgreSQL logs:
grep -i "drop\|truncate\|delete" /var/log/postgresql/postgresql-*.log \
    | grep "2024-06-15" | tail -20
```

── STEP-BY-STEP PROCEDURE ─────────────────────────────────────────────────────

1. **Identify your recovery target precisely:**

   PITR targets in PostgreSQL:
     - `--target-time`     = restore to a specific timestamp (most common)
     - `--target-lsn`      = restore to a specific WAL position
     - `--target-xid`      = restore until a specific transaction ID commits
     - `--target-name`     = restore to a named restore point (if you created one)
     - `--type=immediate`  = restore to end of backup (no WAL replay)

   ```sql
   -- If you need to find the XID of the problematic transaction:
   -- In pg_log, enable log_line_prefix = '%m [%p] %q%u@%d XID=%x '
   -- Or check pg_waldump output for transaction details.
   ```

2. **Create a named restore point BEFORE running risky operations (proactive):**

   ```sql
   -- Run this before any migration or bulk operation:
   SELECT pg_create_restore_point('pre_migration_20240615');
   -- Now you can PITR to exactly this point by name.
   ```

3. **Stop the target instance and restore (pgBackRest method):**

   ```bash
   # NEVER restore over a running production instance.
   # Use a separate recovery data directory.
   RECOVERY_DIR="/var/lib/postgresql/15/recovery"
   mkdir -p "$RECOVERY_DIR"

   pgbackrest --stanza=main \
       --pg1-path="$RECOVERY_DIR" \
       --type=time \
       --target="2024-06-15 14:23:00 UTC" \
       --target-action=promote \
       --target-exclusive=y \    # stops BEFORE the target time commit
       restore
   ```

   `--target-exclusive` means: stop just BEFORE transactions that committed
   AT the target time. Usually what you want — exclude the bad transaction.

4. **Start the recovery instance and monitor WAL replay:**

   ```bash
   # Add recovery port override:
   echo "port = 5433" >> "$RECOVERY_DIR/postgresql.conf"
   pg_ctlcluster 15 recovery start

   # Watch the log for recovery progress:
   tail -f /var/log/postgresql/postgresql-$(date +%Y-%m-%d)-recovery.log

   # Expected log output during replay:
   # "started streaming WAL from archive"
   # "recovery stopping before commit of transaction..."  ← you'll see the target
   # "pausing at the end of recovery"
   # "database system is ready to accept read only connections"  ← in pause mode
   ```

5. **Validate the recovery point is correct:**

   ```sql
   -- Connect to recovery instance (port 5433):
   psql -p 5433 -d mydb

   -- Is the dropped table back?
   \dt orders

   -- Is the row count consistent with pre-incident state?
   SELECT count(*) FROM orders;

   -- Check the timestamp of the last committed record in a key table:
   SELECT max(created_at) FROM orders;
   ```

6. **If the point is correct — promote:**

   ```sql
   -- Option A: SQL promote
   SELECT pg_wal_replay_resume();  -- if paused in recovery

   -- Option B: pg_ctl promote
   -- pg_ctl promote -D /var/lib/postgresql/15/recovery
   ```

7. **If the recovery point is wrong — adjust and re-run:**

   ```bash
   # Stop recovery instance:
   pg_ctlcluster 15 recovery stop

   # Re-run pgBackRest restore with adjusted target:
   pgbackrest --stanza=main \
       --pg1-path="$RECOVERY_DIR" \
       --type=time \
       --target="2024-06-15 14:20:00 UTC" \   # 3 minutes earlier
       --target-action=pause \
       restore
   ```

── VERIFICATION ───────────────────────────────────────────────────────────────

```sql
-- After promotion: confirm the instance is primary:
SELECT pg_is_in_recovery();   -- FALSE

-- Confirm the recovery time boundary was what you wanted:
SELECT timeline_id FROM pg_control_checkpoint();  -- will be > 1

-- Application smoke test — critical business queries:
SELECT count(*) FROM orders;
SELECT max(created_at) FROM orders;
SELECT * FROM orders ORDER BY created_at DESC LIMIT 5;
```

── ROLLBACK ───────────────────────────────────────────────────────────────────

The original production database is untouched during a PITR restore (you
restored to a new directory and port). If the recovery is not what you needed,
stop the recovery instance, delete the recovery data directory, and re-run
with a different target. You can iterate until you find the right point.

Once the recovery instance is promoted and you've swapped production to it —
there is no rollback. Take a new backup immediately after swap-over.

================================================================================
  RUNBOOK 07: RECOVER DROPPED TABLE
  File: 03_backup_recovery/recover_dropped_table.md
================================================================================

The phone rings. A developer's voice says: "I think I dropped the wrong table."
You ask which table. They tell you. You ask what environment. They pause for
too long.

This happens. Not often. But it happens. And the way you handle the first five
minutes determines whether you lose data or not.

Rule one: don't touch anything until you know what you have.

── DIAGNOSIS ──────────────────────────────────────────────────────────────────

```bash
# Confirm the drop happened and when:
grep -i "drop table" /var/log/postgresql/postgresql-$(date +%Y-%m-%d).log | tail -10
# Note the exact timestamp.

# Is log_ddl enabled? (it should be):
psql -c "SHOW log_min_duration_statement; SHOW log_statement;"
```

```sql
-- Check pg_log for the DROP:
-- (if using log_destination = 'csvlog')
-- Also check pg_stat_activity for who ran it (if the session is still alive):
SELECT pid, usename, application_name, query_start, query
FROM pg_stat_activity
WHERE query ILIKE '%drop%table%'
ORDER BY query_start DESC;

-- Confirm the table is gone:
\dt orders   -- or:
SELECT count(*) FROM pg_class WHERE relname = 'orders';   -- should return 0
```

── STEP-BY-STEP PROCEDURE ─────────────────────────────────────────────────────

OPTION A: You have PITR capability and the drop was recent (< RPO window).

This is the clean path. Follow Runbook 06. Target the timestamp just before
the DROP TABLE command. Extract the table and load it into production.

1. **Perform PITR to a recovery instance (see Runbook 06).**

2. **Once recovery instance is running — export ONLY the dropped table:**

   ```bash
   # On the recovery instance (port 5433):
   pg_dump -p 5433 -d mydb \
       -t public.orders \
       -Fc \
       -f /tmp/orders_recovered.dump

   # Restore only that table into production:
   pg_restore -d mydb \
       -t orders \
       /tmp/orders_recovered.dump
   ```

3. **Stop and discard the recovery instance.**

OPTION B: You have a pg_dump logical backup from the same day.

4. **Extract the table from the dump:**

   ```bash
   # List the dump contents to find the table:
   pg_restore --list /backup/mydb_$(date +%Y%m%d).dump | grep -i orders

   # Restore only the orders table:
   pg_restore -d mydb \
       -t orders \
       /backup/mydb_$(date +%Y%m%d).dump
   ```

   Note: you'll lose data from the time of the dump to the time of the drop.
   That's the cost of not having WAL archiving / PITR.

OPTION C: Delayed replica (replica running with recovery_min_apply_delay).

   Some environments deliberately lag a standby by 30–60 minutes as a
   "time machine". If the table was dropped less than the delay ago, the
   table STILL EXISTS on the delayed replica.

   ```sql
   -- Check if you have a delayed replica:
   SHOW recovery_min_apply_delay;   -- on each standby

   -- If delay > age of drop: stop the delayed replica,
   -- promote it, and export the table BEFORE it applies the drop.
   ```

5. **For the future: create a dedicated delayed replica** — this is one of
   the highest-ROI HA configurations for production:

   ```bash
   # On a standby: postgresql.conf
   recovery_min_apply_delay = 1h    # lags primary by 1 hour
   # This standby will be 1 hour behind — and can rescue you from any
   # accidental drop/truncate within that window.
   ```

── VERIFICATION ───────────────────────────────────────────────────────────────

```sql
-- Table exists:
\dt orders

-- Row count matches pre-drop expectation:
SELECT count(*) FROM orders;

-- Data looks correct (spot check a few rows):
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;

-- Indexes are restored:
SELECT indexname FROM pg_indexes WHERE tablename = 'orders';
```

── ROLLBACK ───────────────────────────────────────────────────────────────────

If the restore inserts duplicate data (table already partially existed or was
re-created before recovery): `TRUNCATE orders; DROP TABLE orders;` then re-run
the restore. If the recovery dump is too old and an acceptable data loss window
must be agreed with business — document and obtain sign-off before closing.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

================================================================================
  RUNBOOK 08: RESTORE SINGLE CORRUPTED TABLE
  File: 03_backup_recovery/restore_single_corrupted_table.md
================================================================================

This is the scenario that caused that six-hour outage I mentioned at the start
of this session. A single table's data was corrupted by a bad application
deployment — wrong UPDATE statement, missing WHERE clause. The table is large.
The database is 2 TB. A full restore would take hours. We needed the table.

The technique: restore the backup to a separate instance, extract just the
affected table, reload it into production. Surgical. No downtime on other
tables. If you know this procedure, you can turn a 4-hour outage into a
30-minute one.

── DIAGNOSIS ──────────────────────────────────────────────────────────────────

```sql
-- Identify the scope of corruption:
-- Option A: the data was logically corrupted (wrong values):
SELECT count(*) FROM orders WHERE status NOT IN ('pending','processing','complete','cancelled');
-- If this returns thousands of rows with garbage values — logical corruption.

-- Option B: check for physical page corruption (amcheck):
CREATE EXTENSION IF NOT EXISTS amcheck;
SELECT bt_index_check('orders_pkey'::regclass, heapalloc := true);
-- Error here = physical corruption.

-- How big is the affected table?
SELECT pg_size_pretty(pg_total_relation_size('public.orders'));
-- This tells you how long the extract will take.
```

```bash
# When did the corruption occur? Check logs:
grep -i "update\|corrupt" /var/log/postgresql/postgresql-$(date +%Y-%m-%d).log \
    | grep orders | tail -20
```

── STEP-BY-STEP PROCEDURE ─────────────────────────────────────────────────────

1. **Communicate first** — before you start any restore, tell the application
   team: "The orders table data is corrupted from [time]. I am recovering it.
   ETA [X] minutes. Do not modify the orders table during recovery."

2. **Disable writes to the affected table during recovery:**

   ```sql
   -- Revoke INSERT/UPDATE/DELETE temporarily:
   REVOKE INSERT, UPDATE, DELETE ON public.orders FROM app_user;
   -- Or use a maintenance mode flag in your application.
   ```

3. **Identify the last good backup (before corruption time):**

   ```bash
   pgbackrest --stanza=main info
   # Note the backup "begin" timestamp that predates the corruption.
   ```

4. **Restore to a recovery instance (parallel to production):**

   ```bash
   RECOVERY_DIR="/var/lib/postgresql/15/table_recovery"
   mkdir -p "$RECOVERY_DIR"

   # PITR to just before the corruption:
   pgbackrest --stanza=main \
       --pg1-path="$RECOVERY_DIR" \
       --type=time \
       --target="2024-06-15 09:00:00 UTC" \
       --target-action=promote \
       restore

   # Start recovery instance:
   echo "port = 5433" >> "$RECOVERY_DIR/postgresql.conf"
   echo "archive_mode = off" >> "$RECOVERY_DIR/postgresql.conf"
   pg_ctlcluster 15 tablerecovery start
   ```

5. **Export ONLY the corrupted table from the recovery instance:**

   ```bash
   # Use parallel dump for speed on large tables:
   pg_dump -p 5433 -d mydb \
       -t public.orders \
       --no-acl --no-owner \
       -Fc \
       --jobs=4 \
       -f /tmp/orders_clean.dump

   # Verify dump completed:
   pg_restore --list /tmp/orders_clean.dump | wc -l
   ```

6. **Swap the corrupted table in production:**

   ```sql
   -- On PRODUCTION: rename corrupted table (keep as forensic backup):
   ALTER TABLE public.orders RENAME TO orders_corrupted_20240615;

   -- Create empty shell (pg_restore will populate it):
   -- (pg_restore will CREATE TABLE as part of the dump)
   ```

   ```bash
   # Restore the clean table into production:
   pg_restore -d mydb \
       -t orders \
       --data-only \        # if schema already matches
       /tmp/orders_clean.dump
   # Or omit --data-only to restore schema + data:
   pg_restore -d mydb \
       /tmp/orders_clean.dump
   ```

7. **Re-enable writes:**

   ```sql
   GRANT INSERT, UPDATE, DELETE ON public.orders TO app_user;
   ```

8. **Reconcile the gap** — between the PITR point and the corruption time,
   there may be legitimate transactions. Work with the application team to
   identify them from application logs and replay them manually or accept
   the data loss.

── VERIFICATION ───────────────────────────────────────────────────────────────

```sql
-- Table is restored and clean:
SELECT count(*) FROM orders;
SELECT count(*) FROM orders
WHERE status NOT IN ('pending','processing','complete','cancelled');
-- Should return 0 (no corrupted statuses).

-- Indexes rebuilt:
SELECT indexname FROM pg_indexes WHERE tablename = 'orders';

-- Application can write:
INSERT INTO orders (customer_id, status, created_at)
VALUES (1, 'pending', now());
-- Should succeed.
```

── ROLLBACK ───────────────────────────────────────────────────────────────────

The corrupted table was renamed (not dropped) in step 6. If the restored table
has issues: rename the clean one away and rename the corrupted one back.
`ALTER TABLE orders RENAME TO orders_restored_bad;`
`ALTER TABLE orders_corrupted_20240615 RENAME TO orders;`
You're back to the pre-restore state.

================================================================================
  RUNBOOK 09: WAL ARCHIVING FAILS
  File: 03_backup_recovery/wal_archiving_fails.md
================================================================================

When WAL archiving fails, you're not in an immediate production crisis — but
you are in an undetected backup crisis. Every minute WAL archiving is broken,
your PITR window shrinks. If WAL archiving fails long enough and the primary
recycles the WAL segments that weren't archived — those segments are gone
forever. No PITR through that window. Your last good PITR point is now hours
or days in the past.

This is a P1 incident. Treat it that way.

── DIAGNOSIS ──────────────────────────────────────────────────────────────────

```sql
-- Primary indicator: failed_count > 0 or last_failed_time is recent:
SELECT
    archived_count,
    failed_count,
    last_archived_wal,
    last_archived_time,
    last_failed_wal,
    last_failed_time,
    now() - last_archived_time AS time_since_last_archive
FROM pg_stat_archiver;
```

```bash
# What error is the archive_command generating?
grep -i "archive\|archiv" /var/log/postgresql/postgresql-$(date +%Y-%m-%d).log \
    | tail -30

# What is the current archive_command?
psql -c "SHOW archive_command;"

# Test the archive_command manually against a real WAL file:
LAST_WAL=$(ls -t /var/lib/postgresql/15/main/pg_wal/ \
    | grep -v '\.history\|\.partial' | head -1)
echo "Testing with WAL file: $LAST_WAL"

# If archive_command = 'pgbackrest --stanza=main archive-push %p':
pgbackrest --stanza=main archive-push \
    /var/lib/postgresql/15/main/pg_wal/$LAST_WAL \
    --log-level-console=detail

# If S3-based:
aws s3 cp /var/lib/postgresql/15/main/pg_wal/$LAST_WAL \
    s3://your-bucket/wal/ 2>&1
```

── STEP-BY-STEP PROCEDURE ─────────────────────────────────────────────────────

Root Cause A: Archive destination is full or unreachable.

1. **Check disk space on the archive destination:**

   ```bash
   # Local archive:
   df -h /mnt/wal_archive/

   # S3: check if bucket exists and permissions are intact:
   aws s3 ls s3://your-bucket/pgbackrest/
   aws iam get-user   # confirm credentials work
   ```

   Fix: free disk space, restore permissions, or fix credentials. Once fixed,
   archive resumes automatically — PostgreSQL retries the archive_command.

Root Cause B: archive_command script has an error (syntax, path, permissions).

2. **Check the script for common issues:**

   ```bash
   # Permissions on pgbackrest binary:
   ls -la $(which pgbackrest)
   sudo -u postgres pgbackrest --version   # can the postgres user run it?

   # Check stanza config:
   sudo -u postgres pgbackrest --stanza=main check
   ```

Root Cause C: archive_status directory shows failed WAL segments.

3. **Inspect pg_wal/archive_status:**

   ```bash
   ls /var/lib/postgresql/15/main/pg_wal/archive_status/ | head -20
   # .ready  = waiting to be archived
   # .done   = successfully archived
   # Files with no extension = failed archive attempts

   # Count of pending archives:
   ls /var/lib/postgresql/15/main/pg_wal/archive_status/ \
       | grep '\.ready' | wc -l
   ```

4. **After fixing the root cause — force a WAL switch to trigger immediate
   archive of pending segments:**

   ```sql
   SELECT pg_switch_wal();
   -- Waits a moment, then:
   SELECT last_archived_time, last_failed_time FROM pg_stat_archiver;
   ```

Root Cause D: archive_mode = off or archive_command = '' (misconfiguration).

5. **Re-enable archiving:**

   ```bash
   # Both require a restart:
   # postgresql.conf:
   archive_mode = on
   archive_command = 'pgbackrest --stanza=main archive-push %p'
   ```

   ```bash
   pg_ctlcluster 15 main restart
   ```

   *** INSTRUCTOR WARNING ***
   Changing archive_mode requires a PostgreSQL restart — not just a reload.
   If you change archive_command only (not archive_mode), a reload is enough.
   Know the difference. An accidental restart during peak hours is painful.

── VERIFICATION ───────────────────────────────────────────────────────────────

```sql
-- After fix: failed_count should stop incrementing,
-- archived_count should resume incrementing,
-- last_archived_time should be recent (< 5 minutes):
SELECT archived_count, failed_count,
       last_archived_time,
       now() - last_archived_time AS archive_age
FROM pg_stat_archiver;
```

```bash
# Trigger a WAL segment and confirm it archives:
psql -c "SELECT pg_switch_wal();"
sleep 10
psql -c "SELECT last_archived_time FROM pg_stat_archiver;"
```

── ROLLBACK ───────────────────────────────────────────────────────────────────

If the archive_command was changed and the new command is not working:
revert to the previous command and reload. The postgres archive process will
retry failed segments automatically. WAL segments accumulate in pg_wal until
archived — watch disk usage if archiving is down for more than a few minutes.

================================================================================
  RUNBOOK 10: WAL-G CONTINUOUS ARCHIVING
  File: 03_backup_recovery/wal_g_continuous_archiving.md
================================================================================

WAL-G is the cloud-native alternative to pgBackRest. Originally developed at
Citus Data, now open source, widely adopted in Kubernetes environments and
by teams running PostgreSQL on cloud infrastructure. Its main advantages:
extremely fast restores using delta compression, native support for S3, GCS,
Azure Blob, and Swift — and a clean, simple CLI.

If your shop is Kubernetes-heavy or you're on managed cloud infrastructure
without the ability to run a pgBackRest repository host — WAL-G is often the
right choice.

── DIAGNOSIS ──────────────────────────────────────────────────────────────────

```bash
# Check WAL-G version:
wal-g --version

# List available backups:
wal-g backup-list

# Check WAL archive status (same pg_stat_archiver as always):
psql -c "SELECT archived_count, failed_count, last_archived_time,
                last_failed_wal, last_failed_time
         FROM pg_stat_archiver;"

# List WAL segments in storage:
wal-g wal-show 2>&1 | head -30
```

── STEP-BY-STEP PROCEDURE ─────────────────────────────────────────────────────

1. **Install WAL-G:**

   ```bash
   # Download the latest release binary:
   WALG_VERSION=$(curl -s https://api.github.com/repos/wal-g/wal-g/releases/latest \
       | grep '"tag_name"' | sed -E 's/.*"([^"]+)".*/\1/')

   curl -L https://github.com/wal-g/wal-g/releases/download/${WALG_VERSION}/\
   wal-g-pg-ubuntu-20.04-amd64.tar.gz | tar xz

   mv wal-g /usr/local/bin/wal-g
   chmod +x /usr/local/bin/wal-g
   ```

2. **Configure WAL-G environment** — WAL-G reads from environment variables
   or a configuration file:

   ```bash
   # /etc/wal-g/wal-g.conf (or set via environment in systemd unit):
   cat > /etc/wal-g/wal-g.conf << 'EOF'
   WALG_S3_PREFIX=s3://your-bucket/wal-g/cluster-name
   AWS_REGION=us-east-1
   AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE
   AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY

   # OR use IAM role (preferred in production):
   # WALG_S3_PREFIX=s3://your-bucket/wal-g/cluster-name
   # (no access key needed — relies on instance role)

   # Compression:
   WALG_COMPRESSION_METHOD=lz4

   # Concurrent uploads for WAL:
   WALG_UPLOAD_CONCURRENCY=2

   # Concurrent disk operations for backup:
   WALG_DOWNLOAD_CONCURRENCY=4

   # Retention:
   WALG_RETAIN_FIND_FULL=7   # keep 7 full backups
   EOF

   chmod 640 /etc/wal-g/wal-g.conf
   chown postgres:postgres /etc/wal-g/wal-g.conf
   ```

3. **Configure postgresql.conf to use WAL-G as archive_command:**

   ```bash
   # postgresql.conf:
   wal_level = replica           # or logical
   archive_mode = on
   archive_command = '. /etc/wal-g/wal-g.conf && wal-g wal-push %p >> /var/log/wal-g-archive.log 2>&1'
   archive_timeout = 60          # force WAL rotation every 60 seconds max
   ```

   ```bash
   psql -c "SELECT pg_reload_conf();"
   # Note: archive_mode changes require restart, archive_command does not.
   ```

4. **Take the first full base backup:**

   ```bash
   sudo -u postgres bash -c '. /etc/wal-g/wal-g.conf && wal-g backup-push \
       /var/lib/postgresql/15/main'

   # Monitor progress:
   tail -f /var/log/wal-g-backup.log
   ```

5. **Configure restore_command for PITR:**

   ```bash
   # postgresql.conf (or in recovery.conf for older versions):
   restore_command = '. /etc/wal-g/wal-g.conf && wal-g wal-fetch %f %p >> /var/log/wal-g-restore.log 2>&1'
   ```

6. **PITR with WAL-G:**

   ```bash
   # List available backups:
   wal-g backup-list

   # Restore to a specific backup:
   wal-g backup-fetch /var/lib/postgresql/15/recovery LATEST
   # Or a specific backup name:
   wal-g backup-fetch /var/lib/postgresql/15/recovery base_20240615T010000Z

   # Create recovery.conf (PG 11 and earlier) or recovery signal (PG 12+):
   # PG 12+: create standby.signal or recovery.signal:
   touch /var/lib/postgresql/15/recovery/recovery.signal

   # Add recovery target to postgresql.conf in recovery dir:
   cat >> /var/lib/postgresql/15/recovery/postgresql.conf << 'EOF'
   restore_command = '. /etc/wal-g/wal-g.conf && wal-g wal-fetch %f %p'
   recovery_target_time = '2024-06-15 14:23:00 UTC'
   recovery_target_action = 'promote'
   EOF

   pg_ctlcluster 15 recovery start
   ```

7. **Schedule backups:**

   ```bash
   # /etc/cron.d/wal-g-backup:
   # Full backup daily at 2 AM:
   0 2 * * * postgres . /etc/wal-g/wal-g.conf && \
       wal-g backup-push /var/lib/postgresql/15/main >> /var/log/wal-g-backup.log 2>&1

   # Purge old backups (keep 7):
   30 2 * * * postgres . /etc/wal-g/wal-g.conf && \
       wal-g delete retain FIND_FULL 7 --confirm >> /var/log/wal-g-delete.log 2>&1
   ```

── VERIFICATION ───────────────────────────────────────────────────────────────

```bash
# List backups — confirm latest backup is recent:
wal-g backup-list

# WAL archiving is healthy:
psql -c "SELECT archived_count, last_archived_time FROM pg_stat_archiver;"

# Test WAL fetch (simulates what PITR does):
wal-g wal-fetch 000000010000000000000001 /tmp/wal-test-fetch
echo "WAL fetch exit: $?"
rm -f /tmp/wal-test-fetch
```

── ROLLBACK ───────────────────────────────────────────────────────────────────

To switch back from WAL-G to another archive_command: update postgresql.conf
archive_command and reload. WAL-G data in object storage remains intact —
you can still use it for PITR even after switching tools. Old backups can be
cleaned up with `wal-g delete everything --confirm` when no longer needed
(irreversible — confirm carefully).

── PGBACKREST ESSENTIALS ────────────────────────────────────────────────────

  Check stanza health:       pgbackrest --stanza=main check
  Full backup:               pgbackrest --stanza=main --type=full backup
  Differential backup:       pgbackrest --stanza=main --type=diff backup
  Incremental backup:        pgbackrest --stanza=main --type=incr backup
  List backups:              pgbackrest --stanza=main info
  Full integrity verify:     pgbackrest --stanza=main verify

  Restore (PITR, to new dir):
    pgbackrest --stanza=main \
        --pg1-path=/var/lib/postgresql/15/recovery \
        --type=time \
        --target="YYYY-MM-DD HH:MM:SS UTC" \
        --target-action=promote \
        restore

  Restore (latest, immediate):
    pgbackrest --stanza=main \
        --pg1-path=<data_dir> \
        --type=immediate \
        --target-action=promote \
        restore

── WAL-G ESSENTIALS ─────────────────────────────────────────────────────────

  Push base backup:          wal-g backup-push /var/lib/postgresql/15/main
  List backups:              wal-g backup-list
  Fetch backup (PITR prep):  wal-g backup-fetch <data_dir> LATEST
  Verify backup:             wal-g backup-verify LATEST
  Show WAL status:           wal-g wal-show
  Delete old backups:        wal-g delete retain FIND_FULL 7 --confirm

── PG_DUMP / RESTORE ────────────────────────────────────────────────────────

  Dump full database:
    pg_dump -Fc -d mydb -f /backup/mydb_$(date +%Y%m%d).dump

  Dump single table:
    pg_dump -Fc -d mydb -t public.orders -f /backup/orders.dump

  List dump contents:        pg_restore --list /backup/mydb.dump
  Restore full database:     pg_restore -d mydb_restore /backup/mydb.dump
  Restore single table:      pg_restore -d mydb -t orders /backup/mydb.dump
  Restore data only:         pg_restore -d mydb --data-only /backup/mydb.dump

── ARCHIVING STATUS ─────────────────────────────────────────────────────────

  Archive health check:
    SELECT archived_count, failed_count,
           last_archived_time, last_failed_wal, last_failed_time
    FROM pg_stat_archiver;

  Archive age alert (alert if > 5 min):
    SELECT now() - last_archived_time AS archive_age FROM pg_stat_archiver;

  Force WAL rotation:        SELECT pg_switch_wal();

── RECOVERY INSTANCE LIFECYCLE ──────────────────────────────────────────────

  Start on alternate port:
    echo "port = 5433" >> /var/lib/postgresql/15/recovery/postgresql.conf
    pg_ctlcluster 15 recovery start

  Check recovery progress:
    psql -p 5433 -c "SELECT pg_is_in_recovery(), now() - pg_last_xact_replay_timestamp();"

  Promote recovery instance:
    psql -p 5433 -c "SELECT pg_wal_replay_resume();"
    # or: pg_ctl promote -D /var/lib/postgresql/15/recovery

  Stop and discard recovery instance:
    pg_ctlcluster 15 recovery stop
    rm -rf /var/lib/postgresql/15/recovery

── CREATE RESTORE POINT BEFORE RISKY OPERATIONS ─────────────────────────────

    SELECT pg_create_restore_point('pre_migration_YYYYMMDD');
    -- Then PITR: --type=name --target='pre_migration_YYYYMMDD'

── KEY THRESHOLDS ───────────────────────────────────────────────────────────

  archive_age > 5 min       → WARNING: archiving may be slow/failing
  archive_age > 15 min      → ALERT: investigate immediately
  failed_count increasing   → ALERT: archive_command is broken
  No restore test in 24h    → ALERT: automation broken
  No DR drill in 90 days    → Schedule one this week

── REMEMBER ─────────────────────────────────────────────────────────────────

  A backup never restored is just a file.
  PITR needs: base backup AND continuous WAL archive.
  Never restore into production directly — always restore to a named DB first.
  Rename before drop: orders → orders_old, then restore. Never drop first.
  RPO = how much data you can afford to lose.
  RTO = how long recovery can take. Know both numbers. Own them.
