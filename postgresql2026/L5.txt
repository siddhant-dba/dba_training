LEVEL 5 OVERVIEW
-----------------
At L1 you identified. At L2 you understood. At L3 you operated.
At L4 you designed and led. At L5 you INFLUENCE BEYOND YOUR ORGANISATION.

L5 is the Principal / Staff Engineer level. Your scope is no longer "make
this organisation's databases work well." It is "shape how the industry
approaches database problems." This means contributing to open source,
publishing your thinking, building reusable frameworks others adopt,
advising organisations beyond your own, and architecting for scale most
people never encounter.

L5 tasks have no answer key. They are evaluated on rigor of reasoning,
originality, and whether the output could withstand scrutiny from the
PostgreSQL global community — core contributors, other Staff Engineers,
and conference audiences. Where L4 asked you to design for your organisation,
L5 asks you to produce work generalisable enough that strangers would
benefit from it.

L5 Promotion Criteria: You will be ready for L6 when you have produced
artifacts that exist independently of your employer — a patch, a published
standard, a framework with external adopters, a talk that changed how
people think. Competence is assumed at L5. What is being tested is
contribution and judgment under genuine ambiguity.

TASK TITLE: Investigate and Document a PostgreSQL Source-Level Behaviour
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
At L4 you used PostgreSQL's documented behaviour to design systems. At L5
you go beyond documentation when it is incomplete or you suspect a gap
between documented and actual behaviour. This requires reading the C source,
forming a hypothesis, and proving it experimentally — the same skill that
underlies bug reports accepted by the PostgreSQL project.

SCENARIO
You have observed in production that checkpoint timing under
checkpoint_completion_target does not behave exactly as the documentation
describes under heavy concurrent write load. You suspect the actual pacing
algorithm has edge cases not covered in the docs.

YOUR TASK (Source investigation and documentation)
1. Read the documented behaviour:
   - PostgreSQL docs on checkpoint_completion_target
   - Note what is promised: checkpoint I/O spread evenly across the interval

2. Locate the relevant source:
   - Clone the PostgreSQL source (git clone the official repo)
   - Find the checkpointer process code (src/backend/postmaster/checkpointer.c)
   - Trace the pacing logic (CheckpointWriteDelay function and callers)

3. Form a hypothesis:
   - Example: "Under high WAL generation rate, the checkpointer's progress
     calculation lags because it is based on buffer count, not WAL volume,
     causing I/O to bunch toward the end of the checkpoint interval"

4. Design an experiment to test the hypothesis:
   - Set up a test instance with controlled, reproducible write load
   - Instrument: log checkpoint write progress at fine granularity
   - Vary the parameter under test (checkpoint_completion_target, workload shape)
   - Capture: actual I/O pacing vs theoretical even distribution

5. Run the experiment and analyse results:
   - Plot actual vs expected I/O distribution over the checkpoint interval
   - Does the data support your hypothesis?
   - If not, revise the hypothesis and re-test (this is real research — expect
     to be wrong at least once)

6. Document your findings as if submitting to pgsql-hackers:
   - Clear problem statement
   - Reproducible test case (exact steps, exact PostgreSQL version)
   - Data (graphs, raw numbers)
   - Proposed explanation grounded in the source code (cite file/function/line)
   - Why this matters practically (what production scenario does it affect)

7. Decide on next action:
   - If this is a genuine documentation gap: draft a doc patch
   - If this is a genuine behaviour bug: draft a bug report
   - If your hypothesis was wrong: document why, this is still valuable

SAFETY
Risk: Low — investigation is on test infrastructure. Caution: do not
publish unverified claims about PostgreSQL internals; verify thoroughly
before any public claim, as incorrect public claims damage credibility.

Skill : Source-level investigation — hypothesis formation, experimental design, technical writing for expert audiences

TASK TITLE: Design and Propose a PostgreSQL Extension to Solve a Generalisable Problem
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
At L4 you selected and configured existing extensions. At L5 you identify
a problem that no existing extension solves well, and you design one. This
task takes you from extension consumer to extension author — the same path
followed by the creators of pg_stat_statements, pgvector, and TimescaleDB.

SCENARIO
Across multiple organisations you have advised, you have noticed teams
struggle to answer: "Which queries are about to violate their historical
performance baseline?" pg_stat_statements gives cumulative stats, not
trend-aware alerting. No widely-used extension solves this well at the
database layer (most solutions are external monitoring tools, which lack
the low-latency, in-database view).

YOUR TASK (Extension design and prototype)
1. Define the problem precisely:
   - What specific gap exists? (cumulative stats reset on restart, no
     built-in trend/baseline tracking inside PostgreSQL itself)
   - Why does this matter? (early detection without external tooling
     dependency, useful for embedded/edge PostgreSQL deployments)
   - Who would use this? (DBAs without budget for full observability stacks)

2. Survey the existing landscape:
   - What does pg_stat_statements provide and not provide?
   - What do external tools (pganalyze, Datadog) provide that PostgreSQL itself does not?
   - Is there prior art (abandoned extensions, hackers list discussions)?
   - Document why a new approach is justified, not just "not invented here"

3. Design the extension architecture:
   - Hooks needed: likely a planner/executor hook to capture per-call timing
   - Storage: a ring buffer or summarised table of historical snapshots
   - Computation: rolling baseline calculation (e.g. exponentially weighted
     moving average per queryid)
   - API: a SQL function/view exposing "queries currently deviating from baseline"

4. Prototype a minimal version:
   - Write a basic C extension skeleton (or a PL/pgSQL approximation if a
     full C extension is out of scope for this exercise)
   - Implement: capture, baseline calculation, deviation query
   - Test: demonstrate it correctly flags a deliberately degraded query

5. Write the extension proposal document (as if for pgsql-hackers or for
   public GitHub release):
   - Problem statement
   - Design rationale (why this approach over alternatives)
   - API specification
   - Performance overhead analysis (what does this cost in the hot path?)
   - Comparison to existing solutions

6. Plan the contribution path:
   - Standalone open-source extension (PGXN) — fastest, lowest barrier
   - Proposal to pg_stat_statements core (extend existing extension) — higher
     barrier, more impact if accepted
   - Choose one and justify

SAFETY
Risk: Low — prototype on test systems. Any hook into planner/executor
must be tested thoroughly for production safety before any real deployment.

SKILL BUILT
Area  : Database Server / Instance
Skill : Extension design and authorship — problem definition, prior art research, prototyping, contribution strategy

productively rather than defensively, and what does this reveal about the
importance of the prior-art research step you did in step 2?

TASK TITLE: Publish a Rigorous Comparative Study of Multi-Tenancy Strategies
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
At L3/L4 you chose a multi-tenancy strategy for one application. At L5 you
produce the study that helps the entire industry choose correctly — with
real measurements, not received wisdom repeated from blog posts.

SCENARIO
The "database per tenant vs shared schema vs RLS" debate is full of strong
opinions and thin data. You decide to settle key open questions with a
rigorous, reproducible benchmark and publish it.

YOUR TASK (Comparative research and publication)
1. Define the research questions precisely:
   - At what tenant count does database-per-tenant become operationally
     unmanageable (backup time, connection overhead, migration fan-out)?
   - What is the actual query performance overhead of RLS at 100 / 1,000 /
     10,000 tenants in a shared table?
   - How does index bloat differ between shared-schema and schema-per-tenant
     at equivalent total data volume?

2. Design the experimental methodology:
   - Build representative schemas for each strategy
   - Generate synthetic but realistic tenant data at multiple scales
   - Define the workload (mix of reads/writes representative of SaaS apps)
   - Control variables: same hardware, same PostgreSQL version, same data volume

3. Run the experiments and collect data:
   - Latency distributions (not just averages) at each tenant count
   - Resource consumption (CPU, memory, connections) per strategy
   - Operational metrics (backup duration, migration duration, time to add
     a new tenant)

4. Analyse honestly:
   - Where does conventional wisdom hold up?
   - Where does it not? (This is often the most valuable finding)
   - What are the genuine trade-off boundaries (not "it depends" — actual numbers)

5. Write the study for publication:
   - Methodology section detailed enough for independent reproduction
   - Results with appropriate statistical treatment (not cherry-picked runs)
   - Discussion that acknowledges limitations
   - Clear, actionable guidance: "if your tenant count is below X, choose A;
     above Y, choose B; the RLS overhead becomes significant when Z"

6. Prepare for community scrutiny:
   - Publish your benchmark code and data, not just conclusions
   - Anticipate: "your hardware was unusual," "your workload doesn't match
     mine," "did you tune PostgreSQL correctly for each scenario?"

2. Design the investigation methodology:
   - If real data is available to you (anonymised incident data across

   - If real data is insufficient: construct a rigorous case-study analysis
     of public incidents at certified organisations, examining exactly
     which control(s) should have prevented the specific incident and why
     they did not

   - Is it the case that controls test for the EXISTENCE of a process

     unnecessary access")?
   - Where specifically does paperwork compliance diverge from operational
     safety?

4. Propose what would actually close the gap:
   - More outcome-based controls vs process-based controls?
   - Specific database control additions that current frameworks miss?
   - Be specific and actionable, not just "compliance theatre is bad"

   - Acknowledge what compliance programmes DO achieve (forcing minimum

   - Do not overstate "compliance is useless" if your evidence does not
