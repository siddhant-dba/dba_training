TASK TITLE: Diagnose and Resolve a Connection Pool Exhaustion Incident
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 
WHY THIS MATTERS
Connection pool exhaustion is one of the most frequent production incidents
a DBA handles. You must be able to diagnose the root cause (idle sessions,
connection leaks, legitimate spike) and take appropriate action without
causing a wider outage.
 
SCENARIO
Your monitoring alert fires: "PostgreSQL connection count at 95 of 100."
Applications report timeouts. You have 10 minutes to resolve before
customer-facing impact becomes severe.
 
YOUR TASK (No step-by-step — use your judgement)
1. Diagnose the root cause:
   - Is this an idle session leak (aged sessions doing nothing)?
   - Is this a connection spike (legitimate new load)?
   - Are sessions stuck waiting for locks?
   - Is something continuously opening connections without closing?
 
2. Identify which database/role is consuming the most connections.
 
3. Determine whether to:
   - Terminate idle-in-transaction sessions (safe)
   - Increase max_connections (requires restart — risky)
   - Investigate and close the connection leak source
 
4. Execute your chosen remediation step.
 
5. Verify the connection count dropped and applications recovered.
 
6. Post-incident: document the root cause, what you did, and what
   configuration or monitoring change would have prevented this.
 
SAFETY
Risk: Medium
Terminating connections impacts running queries. Proceed only after you
have verified they are blocking others. On production, notify the
application team before massive termination.
 
SKILL BUILT
Area  : Database Server / Instance
Skill : Incident diagnosis and remediation — independent decision-making under time pressure
 
REVIEW QUESTION
After you terminate 30 blocked sessions, new connections still fail with
"too many clients." What is the ONE thing you should check before increasing
max_connections, and what problem could increasing it WITHOUT checking first
cause?

TASK TITLE: Tune PostgreSQL Instance Parameters for a Known Workload Type
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 
WHY THIS MATTERS
PostgreSQL's default configuration assumes a generic server. A DBA must
be able to assess a workload (OLTP, OLAP, batch processing) and apply
appropriate parameter tuning. This is not reading a checklist — it is
making informed decisions based on system behaviour.
 
SCENARIO
You are asked to optimize PostgreSQL for a known workload:
- High-frequency OLTP transactions (5,000 TPS, 100,000 concurrent connections)
- 64GB RAM server
- Data size: 200GB
- SSD storage
- Business requirement: sub-100ms query latency
 
YOUR TASK (Use your knowledge from L1-L2, no guidance given)
1. Identify which parameters matter MOST for this workload type.
 
2. Calculate appropriate values for:
   - shared_buffers
   - effective_cache_size
   - work_mem
   - maintenance_work_mem
   - max_connections (or use a connection pooler — which is better?)
   - checkpoint parameters (checkpoint_timeout, max_wal_size)
   - log parameters for OLTP
 
3. Document your reasoning for each choice.
 
4. Apply your changes to postgresql.conf, reload, and verify.
 
5. Run a simulated OLTP workload (bulk inserts + selects) and compare
   query performance BEFORE and AFTER tuning using EXPLAIN ANALYZE
   and pg_stat_statements.
 
6. Take a baseline of pg_stat_bgwriter and pg_stat_activity metrics
   and note what changed after tuning.
 
SAFETY
Risk: Medium
Parameter changes require testing on a training instance first. Some changes
(max_connections, wal_level) require a RESTART. Always have a recovery plan.
 
SKILL BUILT
Area  : Database Server / Instance
Skill : Workload-based parameter tuning — assessment, calculation, and verification
 
REVIEW QUESTION
For this OLTP workload, you chose work_mem = 512MB. What problem could
this cause with 100,000 concurrent connections, and what is the correct
approach to work_mem tuning for high-concurrency OLTP vs batch queries?

TASK TITLE: Perform a Production-Grade Upgrade: Minor Version (e.g., 15.2 → 15.5)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 
WHY THIS MATTERS
Minor version upgrades (within the same major version) are low-risk but
still require careful planning and validation. A DBA must be able to
execute an upgrade with zero downtime or planned maintenance windows.
 
SCENARIO
PostgreSQL 15.2 is running in production. PostgreSQL 15.5 is available
with important security and bug fixes. You have a 30-minute maintenance
window scheduled.
 
YOUR TASK (Use your operational knowledge)
1. Pre-upgrade checklist:
   - Verify which packages are installed (use dpkg)
   - Check if standby replicas are running the same version
   - Confirm backups are recent and valid
   - Review PostgreSQL 15.5 release notes for breaking changes
 
2. Plan your upgrade sequence:
   - Will you update standby first or primary first? Why?
   - Do you need to coordinate with the application team?
   - What is your rollback plan?
 
3. Execute the upgrade:
   - Update the PostgreSQL packages on Debian
   - Verify the binary version changed
   - Perform a controlled restart (or no restart for minor versions?)
   - Confirm the instance started and recovered cleanly
   - Run a sanity query on every database to confirm functionality
 
4. Post-upgrade validation:
   - Compare performance metrics before/after
   - Check all scheduled backups and WAL archiving still work
   - Verify replication (if any standby exists) is in sync
 
5. Document the upgrade in your change log with start/end times
   and any issues encountered.
 
SAFETY
Risk: Low
Minor version upgrades are usually safe. Always back up before starting.
Test the upgrade on a development server first if possible.
 
SKILL BUILT
Area  : Database Server / Instance
Skill : Minor version upgrade execution — planning, coordination, validation
 
REVIEW QUESTION

a package dependency issue. Replication is now broken (primary is 15.5,
standby is 15.2). Can they talk? What must you do immediately, and what
is the long-term fix?

TASK TITLE: Investigate and Resolve a Performance Degradation Over Time
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 
WHY THIS MATTERS
A system that works fine on day 1 but degrades over weeks is a classic DBA
problem. The root cause is often not a sudden change but an accumulation
of work (dead tuples, stale statistics, bloat). You must diagnose this
systematically without being given the answer.
 
SCENARIO
A database that has been running for 6 weeks is now taking 3x longer to
complete the same nightly batch job. Nothing obvious changed in the application.
You have until tomorrow morning to fix it.
 
YOUR TASK (Diagnose independently)
1. Rule in/out each of these potential causes:
   - Stale statistics (when was ANALYZE last run on key tables?)
   - Table/index bloat (dead tuples, missing VACUUM)
   - Growing table size (is the data actually larger now?)
   - Slow query plans changing (EXPLAIN the slow queries)
   - Lock contention on specific tables
   - Disk I/O bottleneck or cache hit ratio degradation
 
2. For the top 5 slowest queries, capture EXPLAIN ANALYZE output
   and compare row estimates to actual rows — are estimates wrong?
 
3. Check autovacuum activity — is it running often enough?
 
4. Identify the root cause and execute a fix:
   - If stale stats: run ANALYZE and re-test query performance
   - If bloat: VACUUM (or VACUUM FULL if >50% dead tuples)
   - If bad query plan: check if it's a planning bug or data distribution
 
5. Implement a permanent monitoring solution to catch this earlier next time.
 
SAFETY
Risk: Medium
VACUUM FULL locks tables and requires exclusive access. Perform during
a maintenance window. Regular VACUUM is safe anytime.
 
SKILL BUILT
Area  : Database Server / Instance
Skill : Performance degradation triage — systematic root cause identification
 
REVIEW QUESTION

TASK TITLE: Plan and Execute a Controlled Restart During Business Hours
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 
WHY THIS MATTERS
Sometimes a restart is unavoidable — a critical parameter needs changing, or
a corrupted shared buffer cache must be cleared. A DBA must be able to restart
PostgreSQL with MINIMAL application disruption, not a full outage.
 
SCENARIO
A critical parameter (max_connections, shared_buffers) must be changed
during business hours. You cannot wait for the scheduled 2 AM maintenance
window. You have 1 hour to perform the restart with <5 minutes of downtime.
 
YOUR TASK (Plan and execute)
1. Pre-restart coordination:
   - Notify the application team when you will restart and how long it will take
   - Disable automated alerts/monitoring that might trigger false alarms
   - Confirm a backup was taken in the last 24 hours
   - Have a rollback plan (what if something goes wrong?)
 
2. Create a checklist of validation steps you will perform IMMEDIATELY
   after restart completes:
   - Instance online and accepting connections?
   - All databases accessible?
   - Replication (if any) re-synced?
   - First slow query executes correctly?
   - No errors in the server log?
 
3. Execute the restart:
   - Make the configuration change
   - Use pg_ctlcluster stop --mode fast (not immediate)
   - Verify it is stopped (wait for postmaster PID to disappear)
   - Start it back up
   - Measure and record the startup time
 
4. Run your validation checklist immediately after startup.
 
5. Document:
   - Reason for restart
   - Start time, stop time, restart duration
   - Any issues encountered
   - Verification steps taken
   - Time when full availability was restored
 
SAFETY
Risk: Medium
A restart disconnects ALL sessions. Coordinating with the application team
is essential. A fast stop is safer than immediate — it allows in-flight
transactions to finish before shutdown.
 
SKILL BUILT
Area  : Database Server / Instance
Skill : Controlled restart execution — planning, coordination, validation under time pressure

TASK TITLE: Diagnose Unexplained Slow Queries and Build a Query Optimization Plan
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 
WHY THIS MATTERS
Slow queries are the #1 performance complaint users report. A DBA must be able
to identify which queries are slow (not just guess), prove it with data, and
recommend optimizations — or escalate intelligently to the development team.
 
SCENARIO
Users report "the system is slow" but cannot point to a specific feature.
You have pg_stat_statements enabled. You need to identify the actual slow
queries, quantify the impact, and recommend fixes.
 
YOUR TASK (No guidance — use your operational knowledge)
1. Use pg_stat_statements to answer:
   - Which queries consume the MOST total time? (Biggest system impact)
   - Which queries have the WORST average latency? (Worst user experience)
   - Which queries perform the MOST disk I/O? (Storage stress)
 
2. For each of the top 3 slow queries:
   - Run EXPLAIN ANALYZE and interpret the plan
   - Check if row estimates match actual rows (stale stats?)
   - Identify if it is using indexes or doing full table scans
   - Calculate the I/O cost (shared_blks_read) relative to hit rate
 
3. For each slow query, propose ONE optimization:
   - Missing index?
   - Query rewrite (join order, WHERE clause)?
   - Stale statistics (need ANALYZE)?
   - Table design issue (denormalization needed)?
   - Application cache opportunity?
 
4. Test your proposed optimization on a copy of the data:
   - Create the index (CONCURRENTLY)
   - Re-run EXPLAIN ANALYZE
   - Measure the improvement
   - Calculate the storage cost of the index
 
5. Prepare a recommendation:
   - Which optimization would have the MOST impact?
   - What is the risk/effort to implement?
   - What monitoring would prove the optimization worked?
 
SAFETY
Risk: Low
EXPLAIN ANALYZE always executes the query (but doesn't modify data for SELECT).
Testing on a copy of data is safe. CREATE INDEX CONCURRENTLY does not lock.

Area  : Database Server / Instance

TASK TITLE: Design and Implement a High-Availability Instance Configuration
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 
WHY THIS MATTERS
A single PostgreSQL server is not "highly available." A DBA at the operational
level must understand streaming replication architecture and be able to set
up a primary + standby pair with automatic failover capability (or manual
failover at minimum).
 
SCENARIO
You are asked to design HA for an existing single-instance PostgreSQL database.
Requirements:
- RTO < 5 minutes (failover time acceptable)
- RPO < 1 hour (loss of 1 hour of data unacceptable)
- Automatic failover is desired but manual is acceptable
 
Your current instance: 15.5, 200GB data, 100 TPS sustained load
 
YOUR TASK (Design then implement)
1. Architecture decision:
   - Will you use streaming replication or logical replication? Why?
   - Synchronous or asynchronous replication? Tradeoffs?
   - Where will the standby server be located? (physical or cloud)
   - Will you use a failover manager (pg_auto_failover, Patroni) or manual?
 
2. For your chosen architecture, document:
   - Primary PostgreSQL configuration needed
   - Standby PostgreSQL configuration
   - WAL archiving requirements
   - Network assumptions (how do primary/standby communicate?)
   - DNS failover strategy (if using one)
 
3. Implement the configuration (simulate with two instances on your
   training server, or document the steps):
   - Set up WAL archiving on primary
   - Configure primary for replication (wal_level, max_wal_senders)
   - Take a pg_basebackup for the standby
   - Start the standby and verify replication begins
   - Monitor pg_stat_replication on the primary
   - Monitor pg_stat_wal_receiver on the standby
 
4. Test a planned failover:
   - Promote the standby to primary
   - Verify the new primary accepts writes
   - Document the failover time and any data loss
   - Consider: Can you switch back to the original primary? How?
 
5. Create a failover runbook documenting:
   - How to detect the primary is down
   - How to promote the standby
   - How to communicate the failover to applications
   - How to rebuild the failed primary as a new standby
 
SAFETY
Risk: Medium
Replication setup requires careful coordination of WAL, recovery.conf, and
standby_mode. Test thoroughly on non-production servers first.
 
SKILL BUILT
Area  : Database Server / Instance
Skill : HA architecture design and implementation — replication setup and failover

TASK TITLE: Build a Comprehensive Monitoring and Alerting Strategy
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 
WHY THIS MATTERS
A DBA at L3 cannot rely on ad-hoc monitoring. You must build a proactive
system that warns you of problems BEFORE users notice. This requires
threshold-based alerting on key metrics and a clear escalation path.
 
SCENARIO
You are building the monitoring infrastructure for a production PostgreSQL
instance. You need to identify:
- Which metrics matter most?
- What thresholds warrant an alert?
- How will alerts be delivered (email, Slack, PagerDuty)?
- How will you prevent alert fatigue (too many false positives)?
 
YOUR TASK (Design and partially implement)
1. Identify 15-20 key metrics to monitor. For each, define:
   - The metric name
   - Why it matters
   - The WARNING threshold
   - The CRITICAL threshold
   - What the alert should SAY (actionable, not cryptic)
 
   Examples:
   - Cache hit ratio < 95% → WARNING
   - Cache hit ratio < 90% → CRITICAL
   - Connection count > 80% of max → WARNING
   - Connection count = max → CRITICAL
   - Replication lag > 5 min → WARNING
   - Replication lag > 30 min → CRITICAL
   - Backup age > 26 hours → WARNING
   - XID wraparound age > 1.5 billion → CRITICAL
 
2. Write a monitoring SQL script that runs these checks and outputs
   in a format suitable for parsing (JSON or CSV):
   - Metric name
   - Current value
   - Threshold
   - Status (OK / WARNING / CRITICAL)
 
3. Build a simple wrapper script that:
   - Runs the monitoring SQL
   - Parses the output
   - Sends email/log alerts for anything > OK
   - Includes the metric value and recommendation in the alert
 
4. Schedule the monitoring script to run every 5 minutes via cron.
 
5. Create a runbook for each alert type:

TASK TITLE: Respond to a Critical Incident — Disk Space Running Out
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 
WHY THIS MATTERS
One of the most severe incidents a DBA handles is "disk full." Writes fail,
replication breaks, backups are impossible. You must be able to diagnose
where space is being consumed and take emergency action to free space without
data loss or corruption.
 
SCENARIO
Alert fires at 3:15 AM: "PostgreSQL disk usage 98%!"
You have <30 minutes of writes left before the filesystem fills completely
and PostgreSQL becomes read-only.
 
Root causes could be:
- pg_wal directory is huge (archiving failed)
- A table grew unexpectedly (runaway inserts)
- Backups are stacking up and not being cleaned (rotation broken)
- Log files are not rotating (log_rotation misconfigured)
- Core dumps from a crash
 
YOUR TASK (Diagnose and respond without guidance)
1. Immediately establish what is taking disk space:
   - du -sh on each major directory under /var/lib/postgresql/
   - du -sh on /var/log/postgresql/
   - Is it pg_wal? Backups? Data files? Logs?
 
2. Based on what you find, take the appropriate emergency action:
   - If pg_wal is full → WAL archiving failed; move or delete old WAL?
   - If backups are stacking → manually delete old backups
   - If logs are huge → truncate or compress them
   - If a table grew → investigate the insert source (is it still running?)
 
3. Understand the consequences of each action:
   - Deleting WAL files that haven't been archived = potential RPO loss
   - Compressing logs = lose forensic detail from old logs
   - Can you delete backups safely?
 
4. Make a decision and execute it.
 
5. Verify:
   - Disk usage dropped enough to buy time
   - PostgreSQL is still running and accepts writes
   - No data corruption is evident
 
6. Post-incident (after the crisis is over):
   - Root cause analysis: WHY did this happen?
   - Configuration fix: Set up proper log rotation, WAL archiving
   - Process fix: Add disk utilization monitoring before it hits 98%
   - Storage planning: Calculate growth rate and estimate when you'll outgrow the current disk
 
SAFETY
Risk: CRITICAL
Deleting the wrong files can cause permanent data loss. Understand what each
file is BEFORE you delete it. When in doubt, ask for help or take a backup first.

   - Performance is not degraded (compare EXPLAIN plans before/after)?

   - Document the upgrade in your change log
   - Update documentation for the new version
   - Plan next: When will you upgrade 15 to 16?

Manage a "project database" through its complete lifecycle:
- Week 1: Provision for a new project
- Weeks 2-8: Manage growth and performance
- Week 9: Project ends; secure data, plan deprovisioning
- Week 10: Decommission, ensuring compliance with data retention
 
YOUR TASK (Simulate a 10-week lifecycle)
1. WEEK 1 — Provision:
   - Create the database with appropriate settings
   - Set up roles, schemas, access control
   - Configure backups
   - Set up monitoring
 
2. WEEKS 2-8 — Growth Management:
   - Simulate data growth (INSERT sample data weekly)
   - Monitor table sizes, growth trends
   - Analyze growth: is it linear? Sustainable?
   - Address performance as the database grows
   - Manage bloat (run VACUUM as needed)
   - Analyze and adjust access control as team membership changes
 
3. WEEK 8 — Project Review:
   - Assess whether the database is still meeting requirements
   - Have requirements changed? (storage, users, performance)
   - Document lessons learned about capacity planning
 
4. WEEK 9 — End of Project:
   - Retain the data per compliance requirements (e.g., 7 years for financial)
   - Create a final archival backup (move to cold storage if possible)
   - Disable write access (convert to read-only or read-archive)
   - Revoke active user access
   - Document the database state for future audit

   - Otherwise: Archive the database (backup to tape/S3, drop from active server)

   - Document the deprovisioning in change logs

   - What would you do differently next time?
   - Did your capacity planning prove accurate?
   - Were there surprises in growth, performance, or access control?

SCENARIO
Three privilege requests come in:

2. Analyst needs SELECT on all tables in a database (now has SELECT on none)
3. Contractor needs INSERT/UPDATE on specific tables during a data migration
 
YOUR TASK (Evaluate and grant appropriate privileges)
1. For each request:
   - Understand the actual business need (not what they asked for)
   - Determine the MINIMUM necessary privilege to meet that need
   - Evaluate the risk
   - Determine the scope (temporary or permanent?)
   - Decide: approve, approve with restrictions, or deny
 
2. For Request 1 (SUPERUSER for debugging):
   - Why is debugging transactions requiring SUPERUSER? Investigate.
   - Is there a narrower privilege that would work? (e.g., CONNECT to the DB)
   - If SUPERUSER is truly needed: limit it to a temporary role, set an expiry
   - Document the specific issue being debugged
 
3. For Request 2 (SELECT all tables):
   - Grant SELECT on the schema(s), not all tables individually
   - Use ALTER DEFAULT PRIVILEGES to handle future tables
   - Consider: do they need to see ALL tables or just some? Narrow the scope.

   - Create a temporary role valid for 2 weeks
   - Grant only INSERT/UPDATE on the specific tables
   - Set up logging to audit their activity during the migration
   - Schedule automatic revocation when the migration ends

   - What information must a requester provide?
   - What is the approval process?
   - How are temporary privileges tracked and revoked?
   - How is abuse detected and prevented?

Risk: Medium

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
An unauthorized access allegation has been made. The legal and security teams
are demanding proof of whether unauthorized access occurred. A DBA must be
able to construct an evidence timeline from logs, not guess or panic.

SCENARIO
A customer alleges: "On June 15 at 3:47 PM, someone accessed our customer
database and exported our customer list (table: customers, >100k rows)."
You must answer: Did this happen? Who did it? Prove it with evidence.

YOUR TASK (Forensic investigation)
1. Establish a timeline:
   - When was the export detected? (what time, what triggered the alert?)
   - What is the time window of the alleged access? (3:47 PM ±30 minutes)
   - What is the earliest sign of suspicious activity in the logs?

2. Identify what access would be needed:
   - SELECT on the customers table
   - Sufficient permissions on that role
   - Ability to export data (pg_dump? Application API? Raw SELECT?)

3. Search the PostgreSQL log for evidence:
   - Filter for connections during the time window
   - Look for SELECT queries against the customers table
   - Identify which role(s) executed them
   - Note the client IP address for each connection

4. Cross-reference with other evidence:
   - System authentication logs (sudologs, /var/log/auth.log)
   - Application logs (if the export was via API)
   - File system logs (was data written to disk/network?)
   - Database activity monitoring (if DAM tools are in place)

5. Build the evidence narrative:
   - Timeline of who connected when
   - What queries they executed
   - What data was accessed
   - Conclusion: Did unauthorized access occur? By whom?

6. Document your findings:
   - Be factual and specific
   - Avoid speculation
   - Note gaps in evidence (what logs were NOT available?)
   - Preserve all evidence for legal/compliance teams

SAFETY
Risk: Medium
Breach investigations are high-stakes. Document everything, preserve logs,
involve legal/security teams. Do not destroy or modify any evidence.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Theory is good; practice is better. A DBA should periodically attempt to break
into their own database to find weaknesses. This "red-team" exercise reveals
gaps in security controls before a real attacker does.

SCENARIO
Your organization is doing an internal penetration test. Your role: attempt
to gain unauthorized access to a non-production PostgreSQL instance and
extract sensitive data. Find vulnerabilities. Report them.

YOUR TASK (Ethical penetration testing)
1. Reconnaissance:
   - What is the database IP/port? (scan the network)
   - What version is it? (banner grabbing)
   - What databases exist? (brute force or information leakage)
   - What roles exist? (check for leaky error messages)

2. Attempt common attack vectors:

   Vector 1: Default credentials
   - Try: psql -U postgres (password: postgres, password: empty)
   - Try: other default roles (admin, sa, guest)

   Vector 2: Weak credentials
   - Attempt common passwords (12345, password, company name)
   - Use wordlist-based attacks if you have time

   Vector 3: Network-level:
   - Can you connect from anywhere? (should be restricted)
   - Can you use cleartext passwords without SSL? (should be forbidden)

   Vector 4: SQL injection (if an application endpoint is exposed)
   - Attempt: ' OR '1'='1 in login fields
   - Attempt: UNION-based injection

3. Escalation: If you gain access with low privileges:
   - Can you escalate to superuser? (via poorly configured functions)
   - Can you read other databases? (via pg_catalog)
   - Can you execute OS commands? (via copy to/from)

4. Data extraction: If you gain access:
   - Can you SELECT from sensitive tables?
   - Can you export the data? (pg_dump, COPY, SELECT INTO)
   - Can you bulk export it off the system? (no firewall rules?)

5. Document findings:
   - What vulnerabilities did you find?
   - How severe is each? (Critical, High, Medium, Low)
   - Can they be exploited in the real world?
   - What controls prevented further escalation?

6. Create remediation plan:
   - Weakness 1: Default credentials on postgres role → Force password change
   - Weakness 2: No SSL enforcement → Enforce hostssl in pg_hba.conf
   - Weakness 3: Overprivileged role → Reduce permissions
   - Etc.

SAFETY
Risk: CRITICAL — This is intentional "hacking"
Only perform on non-production, authorized test systems. Get explicit
written permission. Never test on production. Follow your organization's
penetration testing policies.

TASK TITLE: Diagnose and Recover From Data Corruption
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Data corruption is every DBA's nightmare. Silent corruption (where invalid
data goes undetected) is worse. A DBA must be able to detect corruption,
quantify its extent, and recover with minimal data loss.

SCENARIO
A table's integrity check fails: amcheck reports a B-tree structure error.
Queries against this table return wrong results. You must:
1. Confirm and quantify the corruption
2. Decide: Restore from backup vs attempt online repair
3. Execute recovery with minimal downtime

YOUR TASK (Corruption investigation and recovery)
1. Detect corruption:
   - Run amcheck on all indexes:
       sudo -u postgres psql -d mydb -c \
       "SELECT bt_index_parent_check(indexname::regclass) \
        FROM pg_indexes WHERE tablename = 'corrupted_table';"

   - Run consistency checks on heap:
       REINDEX INDEX CONCURRENTLY idx_name;

   - Query the table and note unusual results

2. Quantify the damage:
   - How many rows are affected?
   - Is the index only corrupt (fixable online) or the heap (requires restore)?
   - What is the business impact? (read errors? write errors? both?)

3. Decide on recovery approach:

   Option A: Online repair (if only index corruption):
   - REINDEX INDEX CONCURRENTLY idx_name;
   - Verify amcheck passes post-reindex
   - Resume normal operations
   - Time required: Minutes to hours

   Option B: Restore from backup (if heap corruption):
   - Stop writes to the corrupted table
   - Restore the table from a known-good backup
   - Replay WAL if needed (PITR to latest point)
   - Time required: Depends on table size, backup location

4. Prevent future corruption:
   - What caused it? (Hardware failure? Software bug? Physical damage?)
   - Run hardware diagnostics (memtest, disk SMART checks)
   - Consider enabling data checksums (postgresql config)
   - Increase monitoring: run amcheck regularly

5. Document the incident:
   - When was corruption detected?
   - What was the scope? (one index? multiple tables?)
   - What recovery action was taken?
   - How long did recovery take?
   - Root cause: physical or logical?

SAFETY
Risk: HIGH
Data corruption is unpredictable. Backups are your primary recovery tool.
Test restores before corruption strikes. Have a detailed recovery procedure.

SKILL BUILT
Area  : Data Management
Skill : Corruption detection and recovery — amcheck, REINDEX, selective restore

TASK TITLE: Perform Point-in-Time Recovery (PITR) With Partial Data Loss
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Sometimes you do not want to restore to the exact moment the last backup
was taken. You want to recover to a specific point in time AFTER the backup
(using WAL). This requires understanding WAL recovery, recovery targets, and
exclusive backups.

SCENARIO
At 14:45:30 on June 15, a bad query deleted 5,000 customer records by mistake.
You have:
- A full backup from 09:00 (before the deletion)
- WAL archive containing all activity from 09:00 to now
- A requirement to recover to 14:45:25 (5 seconds before the deletion)

YOUR TASK (PITR recovery)
1. Verify recovery requirements:
   - Last backup: 09:00
   - Recovery target: 14:45:25 (before the deletion)
   - Data loss tolerance: 20 seconds (from 14:45:25 to 14:45:45)
   - Is this acceptable? (Business decision)

2. Prepare a recovery server:
   - Set up an isolated environment (not production)
   - You will restore the backup here, replay WAL, and verify the result

3. Extract the backup and prepare recovery:
   - tar xzf backup.tar.gz -C /var/lib/postgresql/
   - Create a recovery.conf with recovery targets:

       recovery_target_timeline = 'latest'
       recovery_target_time = '2025-06-15 14:45:25'
       recovery_target_inclusive = off  -- stop BEFORE this time, not on it

4. Start recovery:
   - The standby will replay WAL up to the recovery target
   - It will exit recovery mode when the target is reached

5. Verify the recovery:
   - Check the recovered data: SELECT count(*) FROM customers;
   - Did you recover what was deleted? (Check a few rows)
   - Is the data correct? (Spot check some values)
   - Are there any NULL values or oddities?

6. Plan the cutover:
   - This recovered server is now your "new source of truth"
   - You must migrate the data back to production:
     * Option A: pg_dump the recovered database → restore to prod
     * Option B: Use replication to sync the recovered DB back to prod
     * Option C: Plan a full cutover to the recovered instance

7. Execute cutover carefully:
   - Notify users of the downtime
   - Stop writes to the original database
   - Verify WAL has been fully replayed
   - Perform final data validation
   - Switch application connection strings to the recovered instance
   - Resume writes

SAFETY
Risk: HIGH
PITR recovery loses data after the recovery target time. Ensure this is
acceptable. Have a rollback plan (revert to original if recovery failed).

SKILL BUILT
Area  : Data Management
Skill : Point-in-Time Recovery — WAL replay, recovery targets, data validation

REVIEW QUESTION

TASK TITLE: Investigate and Resolve a Backup Failure
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Backup failures are silent until they are not. A backup that fails silently
for weeks means you have NO recovery point. A DBA must be able to detect
failures, diagnose root causes, and fix them urgently.

SCENARIO
Your automated backup job failed for the last 3 days. You only discover it
when a restore is needed. The last good backup is 3 days old.

YOUR TASK (Backup failure triage)
1. Determine scope:
   - Which databases are affected? (All or just one?)
   - How many days of backups are missing? (3 days)
   - What is the business impact? (Restore can only go back 3 days)

2. Identify root cause:
   - Check the backup script logs:
       tail -100 /var/log/postgresql/backup.log

   Common failure causes:
   - Disk full (no space for backup file)
   - Backup destination filesystem unavailable (NFS mount failed)
   - Archive destination full (backup waits for WAL archiving)
   - Insufficient database permissions
   - Network issues (if backing up to remote location)

3. Fix the root cause immediately:
   - If disk full: delete old backups, expand filesystem, retry
   - If mount failed: remount, verify connectivity, retry
   - If archive full: clear archive directory, retry archiving
   - If permission issue: fix role/OS permissions, retry

4. Attempt an emergency backup:
   - Run pg_dump or pg_basebackup NOW (before further data loss)
   - Direct output to a different filesystem if the usual one is full
   - Verify the backup completed successfully:
       pg_restore -l backup_file | head -20

5. Implement a workaround while diagnosing further:
   - If the usual backup location is broken: backup to a different location
   - If the backup script is broken: run manual backups until fixed
   - Set up temporary monitoring to confirm backups are happening

6. Fix the automated backup system:
   - Repair the script (wrong path? wrong permissions?)
   - Re-enable automated backups
   - Monitor the next 3 backup cycles to confirm they succeed

7. Review and improve:
   - Why did the failure go unnoticed for 3 days?
   - No monitoring for successful backup completion?
   - Add: alert if backup fails, alert if no backup in 24 hours

SAFETY
Risk: CRITICAL
Backup failures mean no recovery option. Respond urgently. Do not delay
diagnosis hoping it will fix itself.

TASK TITLE: Plan and Execute a Large Table Migration (Zero-Downtime)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
A 100GB table needs to change structure (add a column, change data type,
alter partitioning). You cannot take the table offline. A DBA must design
a zero-downtime migration using logical replication, CONCURRENTLY indexes,
or table versioning.

SCENARIO
The "orders" table (500GB) needs a new column "order_status_updated_at".
Currently it uses timestamps without timezone. You cannot lock the table.
The migration window is a Friday evening (4 hours).

YOUR TASK (Large table migration planning)
1. Assess the migration:
   - Size: 500GB (will take hours to rewrite)
   - Downtime tolerance: 4 hours on Friday evening
   - Approach: Add new column with default value

2. Design the migration approach:

   Option A: Minimal downtime (5 minutes)
   - Use ALTER TABLE ADD COLUMN with DEFAULT
   - PostgreSQL doesn't rewrite the table (just updates the schema)
   - Time required: Seconds
   - Risk: Default value might not be what you want

   Option B: Full rewrite during maintenance window (4 hours)
   - Create a new table with the correct structure
   - COPY data from old table to new (with any transformations)
   - Swap table names using ALTER TABLE RENAME
   - Time required: 2-4 hours depending on CPU/I/O
   - Downtime: Time for COPY + swap (30 mins - 2 hours depending on speed)

   Option C: Zero-downtime using logical replication
   - Create a publication on the old table
   - Create a subscription on a replica table
   - Catch up the replica to the primary
   - Swap names (atomic cutover)
   - Time required: 12-24 hours to replicate 500GB

3. Choose Option B (minimal downtime during approved window):
   - Friday 18:00: Notify users (database will be briefly unavailable)
   - Friday 18:05: Begin migration

4. Execute:
   - Create temporary new table with correct schema
   - COPY data from old to new (with progress monitoring)
   - Create indexes on new table (CONCURRENTLY) — can happen in parallel
   - Validate: row counts match, spot check data

5. Perform the cutover:
   - Begin transaction:
       BEGIN;
       ALTER TABLE orders RENAME TO orders_old;
       ALTER TABLE orders_new RENAME TO orders;
       COMMIT;
   - Time for cutover: Seconds

6. Post-cutover:
   - Drop the old table: DROP TABLE orders_old;
   - Inform users the database is back online
   - Run ANALYZE on the new table

7. Monitoring:
   - Application queries still execute correctly?
   - Query performance vs before? (should be same or better)
   - No replication lag if this is replicated?

SAFETY
Risk: High
A large table migration can cause downtime if something goes wrong. Test
on a copy first. Have a rollback plan (rename old table back).

WHY THIS MATTERS
Data inconsistencies (foreign key violations, out-of-sync replicas,
orphaned records) often develop silently. A DBA must have systematic
checks to find them and fix them.

SCENARIO
A business report shows unexpected results. Investigation reveals:
- Orders exist with customer_id that don't exist in the customers table
- Inventory counts don't match the sum of order line items
- Some rows are missing expected values (NULLs where NOT NULL expected)

YOUR TASK (Data consistency audit and repair)
1. Identify inconsistencies:
   - Foreign key violations:
       SELECT o.id FROM orders o LEFT JOIN customers c ON o.customer_id=c.id
       WHERE c.id IS NULL AND o.customer_id IS NOT NULL;

   - Inventory sync issues:
       SELECT i.item_id, i.quantity,
              (SELECT count(*) FROM order_lines WHERE item_id=i.item_id)
              AS counted_qty
       FROM inventory i
       WHERE i.quantity != (SELECT count(*)...);

   - Missing values:
       SELECT COUNT(*) FROM orders WHERE customer_id IS NULL;

2. Quantify the damage:
   - How many orphaned orders? (10? 1000? 10000?)
   - How far out of sync is the inventory? (1%? 50%?)
   - How many rows have unexpected NULLs?

3. Decide on correction strategy:

   Option A: Delete inconsistent data
   - DELETE FROM orders WHERE customer_id NOT IN (SELECT id FROM customers)
   - Risk: Lose legitimate orders if the customer was deleted by mistake

   Option B: Correct the inconsistency
   - ADD a default customer for orphaned orders
   - UPDATE inventory SET quantity = (subquery) to correct counts
   - Risk: Might mask a deeper application bug

   Option C: Leave it and fix the process
   - Document the inconsistency
   - Add constraints/triggers to prevent future inconsistencies
   - Require application fix before data cleanup

4. Implement the fix:
   - Wrap in a transaction for safety
   - Back up before making changes
   - Execute the correction
   - Verify: rerun the inconsistency query, should return 0 rows

5. Investigate root cause:
   - Why did inconsistencies develop?
   - Application logic error? (wrong inserts)
   - Manual intervention? (DBA error)
   - Missing constraints? (DELETE CASCADE not set up)

6. Implement prevention:
   - Add FOREIGN KEY constraints if missing
   - Add CHECK constraints for invalid values
   - Add triggers to keep totals in sync
   - Periodic consistency audits (weekly?)

SAFETY
Risk: High
Data correction can delete legitimate data. Understand the inconsistency
before fixing it. Have a rollback plan.

SKILL BUILT

Skill : Data consistency detection and repair — constraint analysis, bulk corrections

TASK TITLE: Manage Tablespaces for Storage Optimization and HA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Tablespaces allow you to place tables and indexes on different disks —
critical for optimizing I/O, managing storage growth, and implementing HA
where failover nodes have access to shared storage.

SCENARIO
You have:
- SSD storage (fast, small, expensive): 500GB
- HDD storage (slow, large, cheap): 4TB
- A requirement to place hot tables on SSD, cold tables on HDD
- Replication that requires both primary and standby access to storage

YOUR TASK (Tablespace optimization and HA)
1. Design tablespace layout:
   - Tablespace "ssd_hot": On /mnt/ssd for active tables (orders, customers)
   - Tablespace "hdd_archive": On /mnt/hdd for historical tables (audit logs, archives)
   - Tablespace "pg_default": On /var/lib/postgresql (system + misc)

2. Assess current table sizes:
   - Which tables are "hot"? (frequent access, large, worth SSD space)
   - Which are "cold"? (infrequent access, historical, can use HDD)

3. Create tablespaces:
   - Create directories with correct permissions
   - CREATE TABLESPACE commands

4. Migrate tables:
   - Move hot tables to ssd_hot:
       ALTER TABLE orders SET TABLESPACE ssd_hot;
   - Move cold tables to hdd_archive:
       ALTER TABLE audit_logs SET TABLESPACE hdd_archive;
   - Move indexes strategically (frequently queried indexes to SSD)

5. Implement for HA:
   - If using shared storage (SAN, NAS): both primary and standby can access
   - If using local disks: replica must have its own tablespaces on local disks
   - Design: Primary has ssd_hot data, replica has local tablespace copies

6. Monitor storage usage:
   - Set up alerts for each tablespace reaching capacity
   - Track growth trends
   - Plan: When will SSD be full? When will HDD be full?

7. Optimize over time:

TASK TITLE: Respond to Replication Lag Incident
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
If your standby is lagging hours behind the primary, PITR depends on the
standby (if primary fails, you can only recover to the standby's lag point).
A DBA must detect lag, diagnose the cause, and resolve it urgently.

SCENARIO
Your standby replica is 4 hours behind the primary (should be < 1 minute).
Applications are failing over to read-only standby, but it returns stale data.
You must diagnose and fix the lag.

YOUR TASK (Replication lag diagnosis and recovery)
1. Measure the lag:
   - On primary: SELECT pg_current_wal_lsn();
   - On standby: SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();
   - Calculate: How far behind is the standby? (byte offset = lag)

2. Determine the bottleneck:
   - Is the standby NOT RECEIVING WAL from primary?
     (receive_lsn == replay_lsn, both far behind current_lsn)
     → Network issue, replication connection broken
   - Is the standby RECEIVING but NOT REPLAYING? (receive_lsn > replay_lsn)
     → Standby is CPU-bound or I/O-bound, cannot keep up with replay speed

3. Fix network/replication issues:
   - If replication connection is broken:
     * Check pg_stat_replication on primary — is standby still connected?
     * Check pg_stat_wal_receiver on standby — is it trying to connect?
     * Verify network connectivity between primary and standby
     * Verify pg_hba.conf allows replication connections
     * Restart replication if necessary

4. Fix CPU/I/O bottlenecks:
   - If standby is CPU-bound:
     * Check pg_stat_activity on standby during replay
     * Identify the slow queries being replayed
     * Can those queries be parallelized? (max_parallel_workers_per_gather)
   - If standby is I/O-bound:
     * Check iostat on standby — is disk at 100% utilization?
     * Is the standby's disk slower than primary? (upgrade disk if needed)
     * Consider: async I/O, increasing cache, load balancing

5. Temporary mitigation:
   - If standby cannot keep up: pause non-critical writes on primary
     (reduces WAL generation → reduces lag accumulation)
   - If standby's disk is failing: migrate to better hardware
   - Temporarily increase wal_keep_size to preserve WAL on primary
     (buys time while standby catches up)

6. Monitor recovery:
   - Lag should decrease as standby catches up
   - Once lag < 1 minute, resume normal operations
   - Monitor for 24 hours to ensure lag does not recur

7. Root cause analysis:
   - Why did lag develop?
   - Application spike (too many writes)?
   - Network slowdown?
   - Standby hardware failure?
   - Implement: alerts to catch this earlier next time

SAFETY
Risk: High
Replication lag means you have lost HA (no fast failover). Address urgently.
Do not ignore hoping it resolves.

TASK TITLE: Plan and Implement Table Partitioning for Performance
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
A 1TB table with billions of rows can be slow to scan or vacuum. Partitioning
divides it into smaller chunks, improving query speed (can scan just the needed
partition) and maintenance speed (VACUUM one partition, not the whole table).

SCENARIO
The "events" table has 5 billion rows and is growing 100M rows/month. Queries
take 30 seconds scanning the whole table. You need to partition it by date
to improve performance.

YOUR TASK (Partitioning design and implementation)
1. Assess partitioning suitability:
   - Is the table large? (1TB+, yes)
   - Does it have a natural partition key? (date column, yes)
   - Will queries often filter on the partition key? (events.event_date, yes)
   - Will partitions be balanced in size? (roughly equal monthly data, yes)

2. Design the partition scheme:
   - Partition by: event_date (monthly partitions)
   - Range: Each month becomes one partition (2025-01, 2025-02, etc.)
   - Retention: Keep 2 years, archive older (2-year rolling window)
   - Result: 24 partitions, each ~400GB

3. Plan the migration:
   - Create partitioned table with same schema (events_new)
   - Migrate data from old table to new (COPY or INSERT...SELECT)
   - Create indexes on each partition (CONCURRENTLY)
   - Swap table names

4. Implement:
   - CREATE TABLE events_new (event_id, event_date, ...)
     PARTITION BY RANGE (event_date) ...
   - CREATE TABLE events_202501 PARTITION OF events_new
     FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
   - (Repeat for each month)

5. Migrate data:
   - INSERT INTO events_new SELECT * FROM events;
   - This distributes rows automatically to the correct partition

6. Enable partition pruning:
   - Set enable_partition_pruning = on
   - PostgreSQL will now automatically exclude unneeded partitions

7. Test queries:
   - EXPLAIN shows partition pruning in action?
   - Query speed improved? (should be much faster on one partition)

8. Manage ongoing:
   - Each month, create new partition for new data
   - Each year, drop or archive 2-year-old partitions
   - Automate: CREATE RULE or trigger to auto-create partitions

SAFETY
Risk: High
Partitioning changes query behavior and can break applications if they
don't account for partitioning. Test thoroughly. Have a rollback plan.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS

database size and costs.

SCENARIO
Your database contains 3 years of audit logs (50GB). Only the last month is
frequently accessed. You need to:
- Keep last month in production (hot)
- Archive months 2-12 to a read-only cold store (warm)
- Archive older than 1 year to offline tape (cold)

YOUR TASK (Archival and retention planning)
1. Classify data by temperature:
   - HOT: audit_logs where created_at > now() - interval '1 month'
   - WARM: audit_logs where created_at between 1 month and 1 year ago
   - COLD: audit_logs older than 1 year

2. Design archival architecture:
   - HOT stays in production database
   - WARM moves to a separate "archive" database (same PostgreSQL instance)
   - COLD moves to S3 or tape (compressed, encrypted, offline)

3. Implement HOT → WARM transition:
   - Create archive_db (separate database for archived data)
   - CREATE TABLE audit_logs_archive in archive_db (same schema)
   - Monthly job: Move audit_logs older than 1 month to archive_db:
       INSERT INTO archive_db.audit_logs_archive
       SELECT * FROM audit_logs WHERE created_at < now() - interval '1 month';
       DELETE FROM audit_logs WHERE created_at < now() - interval '1 month';

4. Implement WARM → COLD transition:
   - Monthly dump of archive_db (pg_dump)
   - Compress: gzip
   - Encrypt: gpg or OpenSSL
   - Upload to S3 or tape
   - Delete the pg_dump from online storage

5. Track what was archived:
   - Maintain a manifest: what data was archived when
   - Document: when it was archived, where it is stored, how to restore it
   - Example: audit_logs_archive_2024-12-01.sql.gz.gpg on S3, restore in <1 hour

6. Implement retention policies:
   - How long do you keep COLD archives? (7 years for tax? 10 years for legal?)
   - After retention expires: delete securely (shred)
   - Document: when each archive will expire

7. Test restoration:
   - Quarterly: restore a cold archive and verify it's intact
   - Confirm decryption, decompression, and restore to test database succeed

8. Reduce costs:
   - Production DB reduced from 50GB to 10GB (only hot data)
   - Archive DB reduced as data moves to cold storage
   - S3 storage is 1/10th the cost of production SSD

SAFETY
Risk: Medium
Archival errors can make data impossible to restore. Test thoroughly.
Maintain encrypted backups of your encryption keys (if you encrypt archives).

SCENARIO

1. Failover to the warm standby
2. Verify data integrity
3. Restore services
4. Measure RTO and RPO achieved
5. Document lessons learned

YOUR TASK (Full DR drill execution)
1. Pre-drill preparation:
   - Notify all stakeholders: "We're running a DR drill 9 AM - 12 PM Saturday"
   - Document current state (backups, replication status, connections)
   - Have a rollback plan to restore to pre-drill state

2. Simulate the disaster:
   - "Assume primary data center is offline, all applications have lost connectivity"
   - Note the time: this is your RTO baseline

3. Execute failover:
   - Promote standby to primary:
       sudo -u postgres psql -d postgres -c "SELECT pg_promote();"
   - Verify: standby is now accepting writes

   - Restart applications

   - Run consistency checks: counts, checksums

   - Compare to pre-disaster snapshots: any data loss?

   - RTO achieved: time from disaster declaration to services restored
   - RPO achieved: how much data was lost (data as of what timestamp?)
   - Compare to SLA: did you meet your RTO/RPO targets?

7. Run the backup plan:
   - Attempt a restore from backups to a third server
   - Can you restore to the disaster time (for evidence/audit)?

8. Document findings:
   - What went wrong?
   - What took longer than expected?
   - What was the data loss?
   - Improvement recommendations

9. Rollback to pre-drill state:
   - Promote original primary back to primary
   - Resync standby
   - Verify everything is back to normal

SAFETY

TASK TITLE: Identify and Rebuild Bloated Indexes
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Indexes accumulate dead entries as underlying data is updated/deleted.
A bloated index occupies more disk space, has more pages to scan, and
harms query performance. A DBA must identify bloated indexes and rebuild
them efficiently (without locking the table).

SCENARIO
You notice that certain queries have slowed down slightly. Disk space
is being consumed more than expected. Analysis reveals several indexes
are 50%+ bloat (dead entries, wasted space).

YOUR TASK (Index bloat detection and remediation)
1. Identify bloated indexes:
   - Query pg_stat_user_indexes and compare size to expected size
   - Check: are there unused indexes consuming space?
   - Look for high ratio of pages scanned vs actual data (bloat indicator)

2. Use pgstattuple to measure bloat precisely:
   - Install the extension: CREATE EXTENSION pgstattuple;
   - Measure index bloat: SELECT pgstattuple('index_name');
   - Note: bloat percentage for each index

3. Prioritize which to rebuild:
   - High bloat (>40%) + frequently used = priority rebuild
   - High bloat + rarely used = candidate for deletion
   - Low bloat (<10%) = leave alone

4. Rebuild indexes without locking:
   - REINDEX INDEX CONCURRENTLY index_name;
   - This creates a new index, swaps it in place, drops the old one
   - No locks on the table during this process

5. Verify the rebuild:
   - Query pgstattuple again — bloat should be near 0%
   - Query size should be significantly smaller
   - Query performance on queries using this index

6. Implement prevention:
   - Monitor index bloat monthly
   - Set up alerts if any index exceeds 30% bloat
   - Adjust autovacuum parameters if indexes are bloating too fast

SAFETY
Risk: Low
REINDEX INDEX CONCURRENTLY is safe. It does not lock the table for writes.
The index is unavailable briefly during the swap, but that is transparent to users.

TASK TITLE: Diagnose and Prevent Deadlocks
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Deadlocks occur when two transactions lock resources in opposite order
(Transaction A locks Row 1, wants Row 2; Transaction B locks Row 2, wants Row 1).
PostgreSQL detects deadlocks and rolls back one transaction. A DBA must
find deadlock patterns and help the application avoid them.

SCENARIO
Your application reports frequent deadlock errors (1-2 per hour). Users
see "ERROR: deadlock detected" and have to retry their operations. You
must find the root cause and prevent future deadlocks.

YOUR TASK (Deadlock diagnosis and prevention)
1. Find deadlock evidence in the log:
   - Search for "deadlock" in PostgreSQL logs
   - Extract: which queries were involved? Which tables?
   - Note the pattern: are the same tables always involved?

2. Understand the deadlock cycle:
   - Each deadlock log entry shows: which query locked what, in what order
   - Trace the cycle: Query A → Row 1 → wait for Row 2, Query B → Row 2 → wait for Row 1
   - This is a classic deadlock pattern

3. Identify the root cause:
   - Is the application accessing tables in inconsistent order?
   - Is there a long-running transaction holding locks unnecessarily?
   - Are there missing indexes causing longer lock holds?

4. Implement prevention:
   - Option A: Enforce consistent lock order (application must always lock A before B)
   - Option B: Reduce transaction duration (shorter transactions = fewer conflicts)
   - Option C: Add indexes (faster queries = shorter lock holds)
   - Option D: Use NOWAIT or SKIP LOCKED to fail fast instead of waiting

5. Verify the fix:
   - Monitor deadlock frequency — should drop to zero
   - If not zero: deadlock pattern involves different tables or different order

6. Document for the application team:
   - What deadlock was happening
   - Why it happened (inconsistent lock order)
   - What the application should do differently
   - Provide code example showing the correct order

SAFETY
Risk: Medium
Deadlock fixes often require application changes. Coordinate with the
development team. Some fixes (adding indexes) are DB-only and safe.

Skill : Deadlock investigation and prevention — lock cycle analysis, application coordination

TASK TITLE: Respond to Memory Pressure and OOM (Out of Memory) Incident
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
PostgreSQL is memory-intensive. A poorly tuned query (huge work_mem) or a
connection spike can exhaust RAM. The system begins swapping, performance
collapses. A DBA must quickly respond: kill processes, adjust parameters,
or restart.

SCENARIO
At 3 PM, your monitoring alerts: "Available memory < 100MB" on the database
server. Queries are timing out. The system is swapping heavily (iostat shows
swap I/O). You need to restore functionality immediately.

YOUR TASK (Memory incident response)
1. Assess the situation immediately:
   - How much swap is in use? (swapon --show, free -h)
   - Is the server actually out of memory or just under pressure?
   - Which process is using the most memory? (ps aux --sort=-%mem)

2. Identify the culprit:
   - Is it PostgreSQL itself? (shared_buffers too large?)
   - Is it a runaway query? (huge work_mem allocation?)
   - Is it a connection spike? (too many sessions, each with work_mem allocated?)

3. Take emergency action:
   - Option A: Kill the largest query:
       SELECT pid FROM pg_stat_activity ORDER BY memory DESC LIMIT 1;
       SELECT pg_terminate_backend(pid);
   - Option B: Lower work_mem temporarily:
       SET work_mem TO '1MB';  (default is probably 4MB, this is emergency mode)
   - Option C: Restart PostgreSQL (nuclear option, causes downtime)
   - Option D: Add swap or RAM (if possible in your infrastructure)

4. Monitor recovery:
   - Memory freed? Swap usage dropping?
   - Queries executing normally again?
   - No new errors in the log?

5. Root cause analysis (after emergency):
   - Why did memory get exhausted?
   - Was there a valid reason (large sort operation)?
   - Or a bug (misconfigured connection pooler opening too many connections)?
   - Or a surprise spike in query complexity?

6. Implement prevention:
   - Add more RAM if this is a capacity issue
   - Lower work_mem if it was over-allocated
   - Set up connection pooling (limits total connections)
   - Set up memory alerts at 70%, 80%, 90% thresholds

SAFETY
Risk: HIGH
Memory exhaustion causes performance collapse and can lead to OS killing
PostgreSQL processes (OOM killer). Respond urgently. Have a recovery plan.

   - Re-run iostat — is disk utilization lower?

TASK TITLE: Tune Connection Pooler (PgBouncer) for Load Balancing
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
PostgreSQL has a hard limit on connections (max_connections). Applications
often open too many connections. A connection pooler (PgBouncer, Pgpool-II)
multiplexes many application connections into fewer PostgreSQL connections,
preventing exhaustion.

SCENARIO
Your application opens 500 connections to PostgreSQL, but your max_connections
is 100 (only 3 actually needed). The application frequently hits "connection
limit" errors. You deploy PgBouncer as a pooler between the application
and PostgreSQL.

YOUR TASK (Pooler configuration and tuning)
1. Install and configure PgBouncer:
   - Configuration file: /etc/pgbouncer/pgbouncer.ini
   - Database section: point to your PostgreSQL instance
   - Client authentication: credential file

2. Set pool parameters intelligently:
   - pool_mode = transaction (each transaction gets a connection)
   - max_client_conn = 1000 (app can open up to 1000 connections to pooler)
   - default_pool_size = 10 (pooler maintains 10 connections per database)
   - min_pool_size = 5 (keep at least 5 warm)

3. Test the pooler:
   - Application connects to pooler (localhost:6432) instead of PostgreSQL (localhost:5432)
   - Verify: queries execute normally
   - Check: PostgreSQL shows only ~10 connections (not 500)

4. Monitor pooler performance:
   - SHOW POOLS in PgBouncer to see current connection state
   - SHOW CLIENTS to see connected applications
   - Monitor: is the pooler becoming a bottleneck?

5. Tune based on results:
   - If pooler CPU is high: increase pool size (fewer multiplexing)
   - If pooler memory is high: decrease pool size or max_client_conn
   - If transactions are slow: verify pooler is not the culprit

6. Troubleshoot common issues:
   - Application error "no more connections": increase max_client_conn
   - Pooler hanging: check for idle connections, timeout settings
   - Queries timing out: verify pool_mode is appropriate (transaction vs session)

SAFETY
Risk: Medium
Pooler misconfiguration can cause connection exhaustion or transaction failures.
Test thoroughly before production deployment. Have a rollback plan (direct to
PostgreSQL if pooler fails).

TASK TITLE: Implement Result Set Caching for Expensive Queries
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Some queries are expensive and rarely change (reference data, slowly-changing
dimensions). Caching results at the application or database layer can provide
dramatic performance improvements without touching the expensive query.

SCENARIO
A reporting query takes 30 seconds to run but is requested 100+ times per day.
The data changes once per day. Currently, every request re-runs the full query.
You want to cache the result for 24 hours.

YOUR TASK (Query result caching design)
1. Identify cacheable queries:
   - Which queries are slow? (>5 seconds)
   - Which have data that doesn't change frequently? (daily? hourly?)
   - Which are requested multiple times? (100+ times/day?)

2. Choose a caching layer:
   - Option A: Application cache (Redis, Memcached)
     Pros: fast, flexible
     Cons: requires application changes
   
   - Option B: PostgreSQL materialized view
     Pros: database-level, simple
     Cons: requires REFRESH, can block reads
   
   - Option C: Hybrid (refresh MV in background, serve from application cache)
     Pros: best of both
     Cons: most complex

3. For PostgreSQL Materialized View approach:
   - CREATE MATERIALIZED VIEW expensive_query AS
     SELECT * FROM ... (the expensive query);
   - Query the view instead of the base tables:
     SELECT * FROM expensive_query;
   - Result is instant (pre-computed)

4. Set up automated refresh:
   - Create a job that runs REFRESH MATERIALIZED VIEW CONCURRENTLY
   - Schedule: every 24 hours (or hourly if data changes more often)
   - CONCURRENTLY allows reads during refresh (no downtime)

5. Monitor cache effectiveness:
   - Before: 30 seconds per request × 100 = 3000 seconds of query time per day
   - After: instant view access, 1 REFRESH of 30 seconds per day
   - Savings: 2970 seconds per day (99% improvement)

6. Handle cache invalidation:
   - If underlying data changes unexpectedly, refresh the view immediately
   - Option: trigger on base tables that refreshes the view on INSERT/UPDATE

SAFETY
Risk: Low
Materialized views are safe (just pre-computed data). REFRESH CONCURRENTLY
does not lock reads. Test thoroughly to ensure results are still correct.

TASK TITLE: Detect and Reduce Alert Fatigue
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Too many alerts (especially false positives) cause alert fatigue: on-call
people ignore alerts because most are noise. A DBA must tune alerting to
signal actual problems, not normal variance.

SCENARIO
Your monitoring system sends 500+ alerts per day. Most are false positives
(traffic spikes that recover on their own, transient timeouts). On-call
team ignores them. A real problem gets lost in the noise.

YOUR TASK (Alert strategy refinement)
1. Audit current alerts:
   - List all alerts in your monitoring system
   - For each alert: how often did it fire last month?
   - For each alert: how many were "real problems" vs false positives?

2. Classify alerts:
   - Critical (requires immediate action): < 5% false positive rate acceptable
   - Warning (investigate soon): < 10% false positive rate acceptable
   - Info (nice to know): use dashboards, not alerts

3. Tune thresholds to reduce noise:
   - Alert: "Cache hit ratio < 90%" fires 100 times/month
     But: recovers on its own in 5 minutes 99% of the time
     Solution: Increase threshold to < 80%, or require 5 consecutive failures

   - Alert: "Replication lag > 10 seconds" fires 200 times/month
     But: lag < 1 minute resolves naturally (network recovery)
     Solution: Alert if lag > 5 minutes, not > 10 seconds

4. Implement smarter alerting:
   - Alert fatigue fix: require multiple failures before alerting (confirmation)
   - Example: "alert if CPU > 90% for 5 minutes straight" (not any spike)
   - Example: "alert if replication lag > 5 minutes, then re-alert every 5 minutes"

5. Measure improvement:
   - Track: alert volume before/after tuning
   - Track: real problems caught
   - Track: false positives eliminated
   - Goal: < 1 false positive per week at critical level

6. Create an escalation playbook:
   - Critical alert → page on-call within 1 minute
   - Warning alert → email, escalate to page if no response in 30 min
   - Info alert → log and review in daily standup

SAFETY
Risk: Medium
Over-tuning alerts (raising thresholds too high) can cause you to miss real
problems. Keep critical thresholds conservative. Test alert tuning on a copy
first.

TASK TITLE: Plan and Execute a Workload Migration Between Servers
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Eventually, you need to move a database to better hardware, cloud, or
decommissioned hardware. A workload migration must preserve performance:
moving to slower hardware can break SLAs.

SCENARIO
You need to migrate a production database from a physical server (fast CPUs,
old disks) to a cloud instance (newer CPUs, different I/O characteristics).
The application requires < 100ms P95 latency. You must ensure the new
hardware meets this SLA.

YOUR TASK (Workload migration planning and execution)
1. Characterize the current workload:
   - Peak QPS (queries per second)
   - Query latency distribution (p50, p95, p99)
   - Peak memory usage
   - Peak disk I/O

2. Assess the new hardware:
   - CPU: faster? different architecture?
   - Disk: SSD vs HDD? same throughput?
   - Memory: sufficient for working set?
   - Network: latency to clients?

3. Predict performance on new hardware:
   - If CPU is faster: queries should be faster
   - If disk is slower: I/O queries might be slower
   - If network latency is higher: remote clients see higher latency

4. Plan a test migration:
   - Restore a backup to the new hardware
   - Run the same workload (replay pg_stat_statements)
   - Measure: latency distribution, throughput, resource usage
   - Compare to production baseline

5. Execute the actual migration:
   - Plan maintenance window or zero-downtime migration
   - Migrate using pg_basebackup or logical replication
   - Validate: data integrity, performance
   - Monitor: watch for performance regressions

6. Validate post-migration:
   - Check: P95 latency < 100ms as required?
   - Check: no unexpected slowdowns?
   - Monitor: for 24 hours to catch issues

7. Document lessons:
   - Did the new hardware perform as expected?
   - Were there surprises?
   - What would you do differently next time?

SAFETY
Risk: High
Workload migrations can cause performance regressions or data loss if not
executed carefully. Test thoroughly. Have a rollback plan.

TASK TITLE: Investigate Performance Baseline Drift Over Months
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Over time, performance degrades (tables grow, bloat increases, statistics
drift). A DBA should track performance baselines and flag when drift exceeds
acceptable thresholds.

SCENARIO
A report query that took 10 seconds 6 months ago now takes 25 seconds. No
code changed. You need to understand: Is this normal growth? Or is there a
problem?

YOUR TASK (Performance baseline analysis)
1. Establish historical baselines:
   - 6 months ago: execution time 10 sec, table size 10GB
   - 3 months ago: execution time 12 sec, table size 20GB
   - Now: execution time 25 sec, table size 30GB

2. Analyze the trend:
   - Is performance degrading linearly? (10→12→25 is not linear, something changed)
   - Is it correlated with table size? (size doubled from month 3 to now, time doubled)
   - Or is something else causing it?

3. Investigate the cause:
   - Run EXPLAIN on the query now vs 6 months ago (from history if you have it)
   - Check: is the plan the same or different?
   - Check: statistics stale? (last ANALYZE when?)
   - Check: missing index that might have been dropped?

4. Remediate:
   - If statistics stale: run ANALYZE
   - If plan is different: investigate why (see plan regression task)
   - If table grew significantly: add indexes, partition, or archive old data

5. Implement monitoring:
   - Set up performance trend tracking
   - Alert if query time increases > 20% month-over-month
   - Proactively investigate before users complain

SAFETY
Risk: Low
Analysis is read-only. Remediation (ANALYZE, index creation) is standard
maintenance.

TASK TITLE: Stream Real-Time Metrics for Operational Dashboards
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
A DBA needs real-time visibility into database health: connections, transactions,
cache hit ratio. Static dashboards (updated every 5 minutes) miss fast-changing
events. Streaming metrics enable real-time monitoring.

SCENARIO
You want to build a real-time dashboard showing: active connections, current
QPS, cache hit ratio, replication lag — all updating every second.

YOUR TASK (Streaming metrics implementation)
1. Identify key metrics to stream:
   - Connection count (current value)
   - Queries per second (rate)
   - Cache hit ratio (derived metric)
   - Replication lag (bytes behind)
   - Transaction throughput (TPS)

2. Design the data collection:
   - Query pg_stat_activity every 1 second (connection count, current queries)
   - Query pg_stat_database every 1 second (cache hits/reads)
   - Query pg_stat_replication every 1 second (lag)
   - Calculate rates (TPS = (xact_commit now - xact_commit 1sec ago) / 1)

3. Set up a metrics sink:
   - Option A: Write to a time-series database (Prometheus, InfluxDB)
   - Option B: Stream to a message queue (Kafka) for real-time consumption
   - Option C: Simple approach: aggregate in PostgreSQL, expose via endpoint

4. Build a dashboard:
   - Display current metrics with automatic refresh (1-second updates)
   - Show trends (sparklines for last hour)
   - Show alerts overlaid (when alerts fired)

5. Monitor the monitoring:
   - Does querying pg_stat_activity 60 times/minute cause load?
   - Can the system handle the query volume?
   - Is the latency of metrics collection acceptable (<100ms)?

6. Validate accuracy:
   - Compare streaming metrics to manual queries
   - Confirm no data loss or gaps
   - Test what happens if a metric source fails

SAFETY
Risk: Low
Streaming metrics query pg_stat_activity, which is read-only and lightweight.
Validate performance impact first.

TASK TITLE: Build a Performance Testing Framework for SLA Validation
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Before deploying changes to production, you must prove they don't break SLAs.
A performance testing framework simulates production workload on a test system
and validates that latency, throughput, and resource usage are acceptable.

SCENARIO
You plan to add a new index to a critical table. Before deploying, you must
prove it improves query latency without degrading write performance. Your
SLA: P95 latency < 100ms for reads, < 500ms for writes.

YOUR TASK (Performance testing framework design)
1. Capture the production workload:
   - Use pgBadger or pg_stat_statements history to extract actual queries
   - Export: top 100 queries by frequency and duration
   - Create a test workload script that replays these queries

2. Set up a test database:
   - Restore a production backup to a test server
   - Ensure test server has similar specs to production (or document differences)

3. Run baseline tests (before changes):
   - Run the workload script, collect timing data
   - Measure: P50, P95, P99 latency for each query type
   - Measure: throughput (QPS)
   - Measure: resource usage (CPU, memory, I/O)
   - Record baseline.txt

4. Apply the proposed change:
   - Add the index
   - Rerun the workload (same script, same load)
   - Collect timing data again: results_with_index.txt

5. Compare results:
   - Did read latency improve? (target: < 100ms P95)
   - Did write latency degrade? (must stay < 500ms P95)
   - Did throughput increase? (goal: higher is better)
   - Did resources improve? (CPU lower, I/O lower)

6. Validate against SLA:
   - Does the change keep you within SLA?
   - If yes: safe to deploy
   - If no: either reject the change or revise the index design

7. Document for production:
   - What change was tested
   - What was the baseline
   - What were the improvements
   - When was it tested, by whom

SAFETY
Risk: Medium
Performance testing is done on a test system, so no production risk. But if
testing is inadequate, you might deploy a change that breaks SLA in production.
Test thoroughly, test repeatedly, involve the application team.

TASK TITLE: Recover From Corrupted Backups
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Your latest backup is corrupted (unreadable, incomplete, or invalid). Your
recovery plan is broken. A DBA must be able to use older backups, WAL
recovery, or other methods to get the database back online with minimal
data loss.

SCENARIO
The latest full backup fails to restore: pg_restore exits with "corrupt data"
errors. The backup from 2 days ago is also corrupt (same issue). You need
to recover the database NOW.

YOUR TASK (Corrupted backup recovery)
1. Assess the damage:
   - Can you restore from the 2-day-old backup? (no, corrupt)
   - How old is the next good backup? (5 days old?)
   - Can you do PITR on the old backup to get more recent data?

2. Investigate what corrupted the backup:
   - Was the backup process interrupted? (power loss? network failure?)
   - Is the backup file incomplete? (check file size vs expected)
   - Is the corruption in the backup file or in the database?

3. Attempt recovery using PITR:
   - Restore the 5-day-old good backup
   - Apply WAL to recover to the current point-in-time (if WAL is intact)
   - This gives you more recent data than the 5-day baseline

4. If WAL is also unavailable:
   - Restore the oldest available good backup (when?)
   - Estimate data loss (from backup point to now)
   - Is this acceptable?

5. Rebuild the database:
   - Restore the backup to a test server
   - Verify: all data intact, no corruption
   - Copy the restored data back to production

6. Implement backup verification:
   - Monthly restore tests (catch corruption early)
   - Verify backup integrity before declaring success
   - Test both full backup AND incremental backups

SAFETY
Risk: CRITICAL
This is a full disaster recovery scenario. Data loss is likely. Focus on
minimizing it. Have multiple backups in different locations.

TASK TITLE: Execute and Validate PITR Procedures Quarterly
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
A PITR procedure that has never been tested is worthless. A DBA must
quarterly (or more) run a full PITR recovery to ensure the process works,
document the actual recovery time, and catch issues before they matter.

SCENARIO
Your PITR procedure is documented: "Restore backup, apply WAL to target
time, promote standby." You have never actually run it. You must execute
it quarterly to ensure it works.

YOUR TASK (PITR procedure validation)
1. Schedule the drill:
   - Pick a time when production is not critical (Friday evening?)
   - Notify stakeholders: "We're testing recovery procedures 2-5 PM"
   - Allocate a test server (isolated from production)

2. Execute the PITR recovery step-by-step:
   - Find a backup that is at least 1 week old (so you have WAL to apply)
   - Restore the backup to the test server
   - Choose a recovery target: "recover to 3 days after the backup was taken"
   - Apply WAL up to that point
   - Note the actual time taken at each step

3. Validate the recovered data:
   - Connect to the recovered database
   - Run consistency checks: table counts, checksums
   - Verify: no data loss, no corruption
   - Compare to production data at that point-in-time

4. Measure recovery metrics:
   - RTO: time from "start recovery" to "database accepts connections"
   - RPO: data loss (compare recovered data to what should have been there)
   - Compare to SLA requirements

5. Document findings:
   - What worked as expected?
   - What took longer than documented?
   - What issues did you encounter?
   - What would you do differently in a real disaster?

6. Improve the procedure:
   - Update timings if they changed
   - Add workarounds for issues discovered
   - Schedule the next drill

SAFETY
Risk: Medium
PITR drills on a test system are safe. But if you discover the procedure
is broken, you have time to fix it (unlike a real disaster).

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Auditors (external or internal) will ask you to prove compliance: "Show us
your backups," "Prove data is encrypted," "Demonstrate access control."
A DBA must be able to produce evidence quickly.

SCENARIO
An external auditor (SOC 2 compliance) is visiting next week. They will
ask for proof of: backup procedures, data encryption, access control,
disaster recovery capability. You have one week to prepare evidence.

YOUR TASK (Compliance evidence preparation)
1. Audit the compliance requirements:
   - What is being audited? (SOC 2, GDPR, HIPAA, ISO 27001?)
   - What are the specific database-related requirements?
   - What evidence is needed? (policies, procedures, test results, logs)

2. Prepare backup evidence:
   - Show: backup schedule, last 4 weeks of backups, sizes, status
   - Demonstrate: restore procedure works (recent restore test logs)
   - Document: retention policy, off-site replication, encryption

3. Prepare encryption evidence:
   - Document: which data is encrypted? (data at rest? in transit?)
   - Show: certificate validity (if SSL/TLS)
   - Show: encryption key management (rotation schedule, access control)

4. Prepare access control evidence:
   - Document: role definitions, privilege levels
   - Show: logs of access control changes (who granted access, when, why)
   - Demonstrate: least privilege is enforced (developers don't have DBA access)

5. Prepare disaster recovery evidence:
   - Document: RTO/RPO targets
   - Show: latest DR drill results (when tested, how long recovery took)
   - Demonstrate: replica is active and synced

6. Create a compliance package:
   - Executive summary (1 page): compliance overview
   - Detailed procedures: backup, encryption, access control, DR
   - Evidence: logs, test results, configuration
   - Signed attestation: "Procedures are current and followed"

7. Prepare for questions:
   - Anticipate audit questions: "What if primary fails? What if backup fails?"
   - Have answers ready with supporting evidence

TASK TITLE: Implement Change Management Process for Database Changes
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Ad-hoc database changes (someone makes a config change without telling anyone)
cause problems: "Why is the database slow?" "Who disabled archiving?"
A change management process ensures all changes are intentional, reversible,
and coordinated.

SCENARIO
Your organization has no formal change management process. Developers directly
modify database schemas. DBAs discover undocumented parameter changes. You
need to implement a controlled process.

YOUR TASK (Change management system design)
1. Define what is a "change":
   - Schema changes (CREATE TABLE, ALTER COLUMN)
   - Configuration changes (parameter modifications)
   - Access changes (role modifications)
   - Infrastructure changes (backup changes, replication changes)

2. Design the process:
   - Step 1: Request (who wants to make what change, why?)
   - Step 2: Review (DBA approves, assesses risk, plans procedure)
   - Step 3: Schedule (assign maintenance window, notify stakeholders)
   - Step 4: Test (verify change works as intended)
   - Step 5: Deploy (execute in production)
   - Step 6: Verify (confirm change is correct)
   - Step 7: Document (record what changed, when, who, why)

3. Create a change template:
   - Change ID (unique tracking number)
   - Description (what is changing)
   - Reason (why is this change needed)
   - Impact (who does it affect, what is the risk)
   - Rollback plan (how to revert if something breaks)
   - Testing results (proof it was tested)
   - Approval (who signed off)

4. Set up a change tracking system:
   - Simple: spreadsheet or wiki page
   - Complex: Jira, ServiceNow, or change management tool
   - Minimum: track all changes, allow search by date/person/impact

5. Enforce the process:
   - Make ad-hoc changes impossible (restrict DBA access unless approved)
   - Or: log all changes and audit for non-compliant changes
   - Or: require change ticket number in a comment before executing

6. Report on changes:
   - Monthly: summary of changes made, approved/rejected
   - Track: mean time to complete a change request
   - Track: change rollback rate (high rate = process is broken)

SAFETY
Risk: Medium
Over-controlling change can slow down critical fixes. Balance control with
agility (emergency bypass process for urgent changes).

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
After an incident, a postmortem is essential: what happened, why, how do

SCENARIO
A 2-hour production outage occurred: replication broke, failover failed,
the standby was not ready. The business lost $50,000. Conduct a postmortem.

YOUR TASK (Incident postmortem)
1. Gather the timeline:
   - 10:15 AM: Primary database becomes unavailable (power loss)
   - 10:20 AM: Monitoring alerts fire
   - 10:25 AM: On-call DBA starts investigation
   - 10:45 AM: Decide to failover to standby
   - 11:00 AM: Standby promotion fails (not ready)
   - 12:15 PM: Manual data restoration from backup
   - 12:30 PM: Services restored

2. Root cause analysis (5 Whys):
   - Why did failover fail? Standby was not ready
   - Why was standby not ready? Replication was lagging 30 minutes
   - Why was replication lagging? WAL archiving was failing
   - Why was archiving failing? Archive disk was full
   - Why was archive disk full? No monitoring, old archives not being cleaned

3. Contributing factors:
   - No HA automation (someone had to manually decide to failover)
   - No disk space alerts (archive disk filled silently)
   - No replication lag alerts
   - Manual processes instead of automated failover

4. Immediate actions (emergency fixes):
   - Clean up the archive disk
   - Set up disk space alerts (immediately)
   - Manual replication sync (verify standby catches up)

5. Short-term improvements (within 1 week):
   - Add replication lag monitoring
   - Automate WAL archive cleanup
   - Document failover procedure (so on-call knows what to do)

6. Long-term improvements (1-3 months):
   - Implement automated failover (pg_auto_failover or similar)
   - Add backup alerting (notify if backups fail)
   - Set up metrics collection for all key indicators

7. Assign ownership:
   - Archive cleanup: DBA team
   - Monitoring: DevOps team
   - Automation: DBA + DevOps together

8. Schedule follow-up:
   - 1 week: verify immediate actions are done
   - 1 month: confirm short-term improvements deployed
   - Quarterly: track long-term improvements progress

SAFETY
Risk: None (postmortems are blameless analysis, not blame assignment)

SCENARIO

YOUR TASK (Full-scale DR drill)
1. Pre-drill preparation:
   - Notify all stakeholders: "12-hour DR drill, Saturday 8 AM - 8 PM"
   - Gather teams: DBAs, DevOps, application teams, management
   - Set expectations: we're testing EVERYTHING, not just DB failover

2. Phase 1 — Declare disaster (8 AM):
   - Assume primary data center is gone
   - All systems in primary DC are unreachable
   - Goal: restore services on standby infrastructure

3. Phase 2 — Database failover (8-9 AM):
   - Promote standby to primary
   - Verify database is accepting writes
   - Measure: time to failover (RTO baseline)
   - Check: data integrity, no corruption

4. Phase 3 — Application failover (9-10 AM):
   - Restart application servers (or redirect to DR app servers)
   - Update DNS to point to DR application IPs
   - Verify: applications can connect to new database
   - Test: basic functionality works

5. Phase 4 — Sustained operations (10 AM - 7 PM):
   - Run load tests, simulated user traffic
   - Monitor: database performance, stability
   - Monitor: application performance
   - Run: actual business queries to verify correctness

6. Phase 5 — Failback (7-8 PM):
   - Assume original primary data center is back online
   - Plan: how to fail back to primary
   - Execute: failback procedure (or just document for now)
   - Verify: primary is now primary again

7. Document findings:
   - What worked?
   - What failed?
   - What was slower than expected?
   - What is missing?
   - Overall: RTO achieved? RPO achieved?

8. Stakeholder review:
   - Present findings to management
   - Explain what needs improvement
   - Get agreement on improvement timeline

SAFETY
Risk: CRITICAL — This is a full-scale simulation
Only run on DR infrastructure, never on production. Have a team ready to
abort the drill if something goes catastrophically wrong.

WHY THIS MATTERS
SLAs define expectations: availability, latency, data loss tolerance. If SLAs

SCENARIO

You've been running DR drills and found that achieving these SLAs costs 3x
your current infrastructure budget. Time to revisit.

YOUR TASK (SLA review and adjustment)
1. Analyze current performance:
   - Last 12 months: actual availability was 99.98% (better than required 99.95%)
   - Actual RTO from failures: 90 minutes average (vs 30-minute SLA)
   - Actual RPO: 0 (we have not lost any data, WAL archiving is solid)

2. Understand the cost of SLAs:
   - 99.95% availability: requires standby, automated failover ($200k/year infrastructure)
   - 99.99% (5-nines): requires multi-region, active-active ($500k/year)
   - RTO 30 min: requires pre-running DR infrastructure
   - RPO < 1 hour: requires synchronous replication or frequent backups

   - How much downtime can the business tolerate?
   - How much data loss can be accepted?
   - What is the cost of downtime? ($1000/min? $10000/min?)
   - What is the cost of the infrastructure to meet SLAs?

4. Propose revised SLAs:
   - Availability: 99.9% (3-nines) — acceptable, saves cost
   - RTO: 4 hours — achievable with current backups + PITR
   - RPO: 1 hour — acceptable with WAL archiving

5. Model the cost savings:
   - Current: $200k/year infrastructure for 4-nines + 30-min RTO
   - Revised: $50k/year infrastructure for 3-nines + 4-hour RTO
   - Savings: $150k/year
   - Risk: 52 minutes more downtime/year (1 incident of 52 min)

6. Present to business:
   - "We can save $150k/year with revised SLAs"
   - "This means accepting 1 hour of downtime per year (on average)"
   - "Cost of that 1 hour: $1000/min × 60 = $60k"
   - "Net benefit: $90k/year, or we have budget for better monitoring"

SAFETY
Risk: Low (this is strategic planning, not system changes)
But be careful: lowering SLAs could cause business impact if actual downtime
exceeds the new SLA.

   - Legal says: "Hold data for customer ABC (litigation)"
   - Implement: retention_hold table that blocks automatic deletion
   - Verify: deletes are skipped if a hold exists

4. Batch the deletions:
   - Don't delete 1M rows in one query (locks table)
   - Instead: delete in batches of 10,000 rows in a loop
   - Log progress

5. Verify compliance:
   - Monthly report: how many rows were deleted per table
   - Audit trail: timestamp, count, confirmation deletion succeeded
   - Exception report: any retention holds still active, why

6. Test the system:
   - Create test data with a known old date
   - Run the retention job
   - Confirm data was deleted
   - Confirm audit log shows the deletion

SAFETY
Risk: CRITICAL — Automated deletion is permanent
Test extensively. Have a recovery plan (can you restore from backup if
something goes wrong?). Always log what was deleted.
