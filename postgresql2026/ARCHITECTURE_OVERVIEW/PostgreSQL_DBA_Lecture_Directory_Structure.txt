A 30-Minute Technical Lecture for DBA Diploma Students

Alright, everyone, settle in. We've been talking about PostgreSQL processes for a couple of weeks now — postmaster, the backend servers, bgwriter, autovacuum, all those little workers running around. Today we're going to look at what they're actually *touching* on disk. And I'm telling you right now, what's about to make sense to you in the next half hour is going to save your life more than once in your careers. I've seen DBAs lose jobs because they didn't understand this. I've also seen DBAs get promoted because they *did*.

So let's pull back the curtain on the PostgreSQL data directory. We call it $PGDATA in the shell, and it's basically PostgreSQL's filing cabinet — everything the system needs to stay alive and remember what happened lives in there.

================================================================================
THE FOREST BEFORE THE TREES
================================================================================

First, let me give you the 30,000-foot view. When you install PostgreSQL, one of the first things you do is create a cluster. You run `initdb` and point it at a directory, and PostgreSQL says, "Okay, I'm going to fill this place with files I need to operate." That directory becomes your $PGDATA. Everything inside it is sacred. You touch the wrong file, you corrupt the wrong file, or you delete the wrong file, and suddenly you're the person explaining to the VP why the production database is down and there's no backup.

Now, I've been doing this for two decades, and I have watched — with my own eyes — a junior DBA attempt to "clean up" the pg_wal directory because they thought old files were junk. They weren't junk. They were transaction logs that hadn't been archived yet. The database went down. It was chaos. Don't be that person.

Here's the key thing you need to hold in your head: PostgreSQL stores databases, configurations, transaction logs, lock files, temporary runtime stuff, and metadata in very specific places. It's *organized*. Not randomly. Once you understand the structure, you understand how PostgreSQL thinks, and that's half the battle as a DBA.

Let me show you what's actually in there. Let's get hands-on.

================================================================================
GETTING EYES ON YOUR CLUSTER
================================================================================

Okay, go ahead and open a terminal. I want you to see this on your own machine. First, find out where your PostgreSQL cluster actually lives. Type this:

    sudo -u postgres psql -c "SHOW data_directory;"

What did you get? That's your $PGDATA. Write it down. Most likely, if you're on Linux and you did a standard install, it's something like /var/lib/postgresql/14/main or /var/lib/postgresql/15/main. On macOS, it might be /usr/local/var/postgres. On Windows with standard install, probably C:\Program Files\PostgreSQL\15\data. The exact path doesn't matter — what matters is that *that's the directory PostgreSQL cares about*.

Now let's list what's in there. Go ahead and type:

    ls -la /path/to/your/data_directory

(Replace that path with whatever you got from SHOW data_directory.)

You're going to see a bunch of files and directories that probably look like gibberish if this is your first time. A lot of two-letter directories. Files with numbers. Maybe some that start with "pg_". That's the filing cabinet. We're about to organize what all that means.

================================================================================
THE BIG DIRECTORIES: YOUR MENTAL MAP
================================================================================

Let me walk you through the main zones. Think of the data directory like a house with different rooms. Each room stores a specific type of thing.

---
base/ — Your Databases Live Here
---

This is the most important directory on day one. Every database you create in your PostgreSQL cluster gets its own directory inside base/. The directory name is the OID of the database — the Object IDentifier. It's a number. PostgreSQL internally refers to databases by these numbers, not by name.

Let me show you. Type this:

    sudo -u postgres psql -c "SELECT datname, oid FROM pg_database WHERE datname = 'postgres';"

That OID? That's the directory name inside base/. So if your postgres database has OID 1, there's a directory called base/1/ that contains all the physical files for that database.

Here's a story from the field: About five years ago, I had a consultant on my team who needed to move a development database. They looked at the size of base/20942/ on disk, thought, "I'll just tar that up and move it." They did. Database wouldn't start. Why? Because they moved the directory but didn't update the symlinks or the catalog metadata. PostgreSQL was still looking for database OID 20942, but the OID had changed when it was restored on the new system. It took us three hours to figure out what happened. The lesson: *Never* manually move directories inside $PGDATA. Always use `pg_dump` and `pg_restore`, or proper backup tools, or replication. The filesystem is not your friend here.

Inside each base/OID/ directory, you'll find actual table files. Let me show you:

    sudo -u postgres ls -la /var/lib/postgresql/14/main/base/1/ | head -20

You'll see files that look like: 2619, 2620, 2621, etc. Those are the filenode numbers. Each file is typically one table or one index. PostgreSQL stores them as separate files on disk. When you create a table, PostgreSQL assigns it a filenode number and stores it as a file with that number.

---
global/ — Cluster-Wide Metadata
---

Next room: global/. This directory holds the shared catalog tables. These are tables that belong to the *entire cluster*, not to any specific database. What goes in here? System tables like pg_database (which databases exist), pg_tablespace (which tablespaces are configured), pg_roles (who the users are), pg_authid (authentication info). If you want to know what users exist in your PostgreSQL cluster, PostgreSQL looks in global/.

Why does this matter? Because these files are crucial. If something corrupts global/1260 — the file containing pg_roles — you have a problem. You can't log in. The whole cluster is essentially locked out.

---
pg_wal/ — The Transaction Log, aka WAL
---

Now here's the most important directory after base/ and global/. This is pg_wal/. WAL stands for "Write-Ahead Logging," and it's where PostgreSQL stores the transaction log — the record of everything that's changed. Remember when we talked about the walwriter process? This is what it's writing to.

PostgreSQL records *every* change — every INSERT, UPDATE, DELETE, TRUNCATE — in these WAL files before it writes the actual data to disk. This is how PostgreSQL keeps transactions safe. If the server crashes, PostgreSQL can replay the WAL to recover to a consistent state.

Go ahead and look:

    sudo -u postgres ls -la /var/lib/postgresql/14/main/pg_wal/ | head -20

You're going to see a bunch of files with hex names like 000000010000000000000001, 000000010000000000000002, etc. Those are WAL segment files. Each segment is 16 MB by default. PostgreSQL writes to them sequentially. When one fills up, it moves to the next.

Here's a critical warning — and I mean this: **Never, ever delete files from pg_wal/ manually.** Not even if they look old. Not even if your disk is full. That's how you lose data. If you need to reclaim space, use `pg_archivewals` or proper archiving tools that *extract* the WAL and then tell PostgreSQL it's safe to delete the segment. PostgreSQL knows which WAL files it still needs. You probably don't.

I've seen this go wrong. Someone's disk filled up. They panicked. They deleted pg_wal files. The database couldn't start because it needed those logs. Data loss. Angry customers. That could be you in two years if you don't take this seriously.

---
pg_stat/ and pg_stat_tmp/ — Statistics
---

These two directories hold statistics. pg_stat/ is the persistent statistics — data about your tables and indexes that PostgreSQL has gathered and written to disk. Things like "this table has 50,000 rows and is 2.5 MB." pg_stat_tmp/ is temporary, in-memory stuff being gathered right now.

The stats collector process we talked about earlier? It's writing to pg_stat_tmp/ and periodically flushing to pg_stat/. You use these statistics to understand your workload. The query planner uses them to decide how to execute queries efficiently. If statistics are stale, the planner makes bad decisions. That's why autovacuum includes ANALYZE.

In practice, you'll rarely touch these. PostgreSQL manages them. But you should know they exist and that you can check how recent they are.

---
pg_tblspc/ — Tablespace Symlinks
---

Quick one: pg_tblspc/ is a directory of symlinks. It points to tablespaces — alternate locations where data can be stored. By default, everything lives in the main data directory. But you can say, "I want to store this table on this faster SSD over here," or "I want this index on a different disk." You create a tablespace, and PostgreSQL puts a symlink in pg_tblspc/ pointing to it.

As a DBA, tablespaces are a *production* tool. In development, you probably won't use them. But in a busy production database, you might have your main tables on one set of drives, your indexes on faster SSDs, and your temporary space on throwaway storage. The ability to separate things by performance class is valuable. And the way PostgreSQL knows where to find everything? These symlinks.

---
pg_logical/ — Logical Replication State
---

We haven't gotten into logical replication yet in this course — that's coming in week eight — but I want you to know this directory exists. When you set up logical replication (where you replicate specific tables to another database, not necessarily the whole cluster), PostgreSQL keeps track of that state here. Replication slots, decoder state, plugin information. Don't touch it.

---
pg_xact/ — Transaction Commit Status
---

Here's something most developers never think about: PostgreSQL needs to remember, for every transaction ever run, whether it committed or rolled back. It can't keep that in memory — too much data, server might crash. So it writes it here.

When PostgreSQL is trying to figure out whether a row is visible to your query, it needs to know: "Did the transaction that created this row commit or roll back?" It looks in pg_xact/. This was called pg_clog in older versions — the commit log. They renamed it to pg_xact/ in PostgreSQL 10.

The files in here are compact — they don't take up much space — but they're essential. PostgreSQL automatically cleans up old transaction status once it's no longer needed, so you don't think about this. But it's good to know it's there.

---
pg_subtrans/ — Subtransaction Status
---

PostgreSQL has SAVEPOINTs, which are essentially nested transactions. When you create a savepoint, you're creating a subtransaction. PostgreSQL needs to track whether each subtransaction committed or rolled back, separate from its parent. That information lives here.

You probably won't directly work with this, but it's part of PostgreSQL's architectural elegance. The system is very careful about tracking the status of everything.

---
pg_multixact/ — Shared Row-Level Locks
---

When multiple transactions hold locks on the same row, PostgreSQL needs to remember all of them. It stores that information here. Multixact stands for "multi-transaction." If transaction A locks a row for updating, and transaction B tries to also update it, PostgreSQL needs to remember that both transactions have a claim on that row.

Again, this is handled automatically. You're not manually creating multixacts. PostgreSQL does it. But you should know the files are there and what they mean.

---
pg_commit_ts/ — Commit Timestamps
---

This directory stores the timestamp when each transaction committed. PostgreSQL can tell you, "Transaction 42857 committed at 2024-03-15 14:32:05.234." This is useful for point-in-time recovery, debugging, and auditing.

This feature has to be enabled at cluster initialization with --with-wal-segsize or in postgresql.conf. It's not on by default everywhere, so not every cluster has these files. But if you need to know exactly when something changed, this is how you find out.

---
pg_dynshmem/ — Dynamic Shared Memory
---

PostgreSQL uses shared memory for things like buffer caches and lock tables. Sometimes it needs to allocate shared memory dynamically at runtime. This directory holds those files. On most systems, this is backed by /dev/shm or POSIX shared memory. If you're having memory issues or strange behavior, sometimes files here get corrupted or left behind. Rarely a problem in practice.

---
pg_notify/ — LISTEN/NOTIFY State
---

When you use PostgreSQL's LISTEN and NOTIFY features — which let your application get notified of events — the daemon process handling that keeps state here. If you're using NOTIFY for application-level signaling, this is quietly doing work behind the scenes.

---
pg_serial/ — Serializable Transaction State
---

SERIALIZABLE is the highest isolation level in PostgreSQL. Transactions at this level need extra bookkeeping so PostgreSQL can prevent certain race conditions. This directory stores that state. Most applications use READ COMMITTED or REPEATABLE READ, so you might never see anything interesting here. But it's there for correctness.

---
pg_snapshots/ — Exported Snapshots
---

When you export a snapshot — which is an advanced feature that lets different backends see the exact same state of the data — PostgreSQL stores metadata about that snapshot here. Rarely used. But it's there.

---
pg_twophase/ — Prepared Two-Phase Commits
---

In some distributed systems, you need to prepare a commit, get acknowledgment from other systems, and then actually commit. This is called two-phase commit, or 2PC. PostgreSQL supports this. If you have a prepared transaction that hasn't finished yet, state about it lives here.

I'll be honest with you: I've seen this in very large distributed systems. Most of you won't use it. But it's good to know it exists, because someday you might inherit a system that does, and you'll need to know how to clean up a stuck prepared transaction.

================================================================================
THE FILES OUTSIDE THE DIRECTORIES
================================================================================

Okay, so those are the big directories. But there are also important files sitting right in $PGDATA itself. Let me show you a few.

---
postgresql.conf
---

This is the main configuration file. Remember when we talked about postgresql.conf in week one? This is it. It sits right in $PGDATA. When PostgreSQL starts up, it reads this file. You change settings here, you restart the server or do a reload, and PostgreSQL reconfigures itself.

---
postgresql.auto.conf
---

This is auto-generated. When you run ALTER SYSTEM, changes go here, not to postgresql.conf. This exists so you don't accidentally overwrite your manual edits to postgresql.conf.

---
pg_hba.conf
---

This is the "host-based authentication" config file. It controls who can connect from where, and how they authenticate. Change this wrong, lock yourself out. I've done it. Not fun.

---
pg_ident.conf
---

Maps operating system usernames to PostgreSQL roles. If you're using ident authentication, this is what controls it.

---
postmaster.pid
---

This file contains the process ID of the currently running postmaster. PostgreSQL writes it on startup, reads it on shutdown. If this file exists and there's no actual postmaster running at that PID, you have a stale lock — the cluster isn't running but PostgreSQL thinks it is. PostgreSQL will refuse to start. You have to remove this file manually. But be careful — if the postmaster *is* actually running and you remove this, you can corrupt the database.

---
PG_VERSION
---

Simple file. Contains the major version number of PostgreSQL. If you accidentally upgrade PostgreSQL but forget to run pg_upgrade, and the PG_VERSION number doesn't match your binary, PostgreSQL will refuse to start. Safety mechanism.

================================================================================
LIVE DEMO: EXPLORING YOUR CLUSTER
================================================================================

Alright, let's actually look at this. I want you to do this on your own machine. I'm going to walk you through it.

First, find your data directory again:

    export PGDATA=$(sudo -u postgres psql -c "SHOW data_directory" -t | tr -d ' ')

Now let's see the structure:

    cd $PGDATA
    ls -la

You should see something like:

    drwx------  base
    drwx------  global
    -rw-------  pg_control
    drwx------  pg_wal
    drwx------  pg_stat_tmp
    -rw-------  postgresql.conf
    -rw-------  postgresql.auto.conf
    -rw-------  pg_hba.conf
    -rw-------  pg_ident.conf
    -rw-------  postmaster.pid
    -rw-------  PG_VERSION
    ...and more

Now, let's see what's actually in base/:

    sudo -u postgres ls -la $PGDATA/base/

You'll see directories named with numbers. Those are OIDs. Let's find out what database corresponds to which OID:

    sudo -u postgres psql -c "SELECT datname, oid FROM pg_database ORDER BY oid;"

See that? postgres database is probably OID 1. template0 is probably OID 4. template1 is probably OID 5. Now let's look inside one:

    sudo -u postgres ls -la $PGDATA/base/1/ | head -20

Those numbered files are tables and indexes. Let's find out which table is which. Type this:

    sudo -u postgres psql -c "SELECT relname, relfilenode FROM pg_class WHERE relkind = 'r' LIMIT 10;"

See how relfilenode matches the filenames you're seeing? That's the connection. A table named pg_class has a relfilenode number, and that's the actual filename on disk.

Now, let's look at the WAL directory:

    sudo -u postgres ls -la $PGDATA/pg_wal/ | head -20

Those hex names are WAL segments. Each one is 16 MB. PostgreSQL writes to them in sequence. See which one is current:

    sudo -u postgres ls -la $PGDATA/pg_wal/ | grep "^-" | tail -1

That's probably the current active WAL segment. PostgreSQL is writing to it right now.

Want to see something cool? Let's do a transaction and watch the WAL grow:

    sudo -u postgres psql postgres << 'EOF'
CREATE TABLE demo (id INT, name TEXT);
INSERT INTO demo VALUES (1, 'Alice'), (2, 'Bob'), (3, 'Charlie');
\q
EOF

Now check the WAL again:

    sudo -u postgres ls -la $PGDATA/pg_wal/ | tail -5

Did you see a new segment? Or did the current one grow? Depending on how much data that was, you might not have created a whole new segment. But the point is, every change you made was recorded in pg_wal/ before it was written to the actual table file.

Clean up that table:

    sudo -u postgres psql postgres -c "DROP TABLE demo;"

================================================================================
WHY THIS MATTERS: REAL SCENARIOS
================================================================================

Now, let me tell you why I'm making you understand this. It's not academic. It's practical.

**Scenario 1: The Disk Filled Up**

It's Saturday night. You get a page. The database is read-only suddenly. Your monitoring shows the disk is 100% full. You log in, and you see that pg_wal/ is taking up 40 GB. What do you do?

If you understand the directory structure, you know:
1. pg_wal/ is transaction logs. They're still needed if they haven't been archived.
2. You don't delete them.
3. You check if WAL archiving is working. Maybe it stopped, and logs are piling up.
4. You increase available disk space or configure archiving to actually archive files.

If you *don't* understand it, you might panic and delete pg_wal/ files. That kills the database.

**Scenario 2: Weird Permission Errors**

Someone (not you, obviously) ran a script that changed permissions on the $PGDATA directory. Now PostgreSQL won't start. It can't access its files.

If you understand permissions, you fix it:

    sudo chown -R postgres:postgres /var/lib/postgresql/14/main/
    sudo chmod 700 /var/lib/postgresql/14/main/
    sudo -u postgres pg_ctl start -D /var/lib/postgresql/14/main/

Done. But you had to know that PostgreSQL needs to own the directory.

**Scenario 3: Recovering from a Failed Upgrade**

You upgraded PostgreSQL from 14 to 15, but something went wrong. Your old 14 data is still there. Can you go back? Yes, but you need to know which version owns the files.

Check PG_VERSION:

    sudo -u postgres cat /var/lib/postgresql/14/main/PG_VERSION

It says 14. That tells you that the data on disk is version 14 format. If you try to run PostgreSQL 15 against it without running pg_upgrade, it will refuse to start. That's by design — it's protecting you.

================================================================================
INSTRUCTOR WARNING: WHAT NOT TO DO IN PRODUCTION
================================================================================

Alright, I'm going to get serious for a moment. Listen up. I'm going to tell you the things I have seen destroy production databases, and I'm going to tell you once very clearly: Do not do these things.

**1. Never manually edit files in $PGDATA.**

I don't care if you think you know what you're doing. I don't care if you found a StackOverflow post that says it'll work. The files in $PGDATA are in a very specific format that PostgreSQL understands. If you edit them with a text editor, you will corrupt them. The corruption might not be immediately obvious. The database might start up. It might work for a week. Then it'll crash, and your data will be gone or inconsistent.

**2. Never delete files from pg_wal/ or pg_xact/ without knowing exactly what you're doing.**

These files are the source of truth for transaction state. PostgreSQL needs them. If you delete them, you might lose data. I've seen it. Twice.

**3. Never do a raw filesystem copy of the data directory while PostgreSQL is running.**

Someone once said, "I'll just tar up the data directory and move it to another server." PostgreSQL was running during the tar. The backup was inconsistent. When they tried to restore it, the database wouldn't start. They lost a day of work. Use pg_dump. Use WAL archiving and streaming replication. Use proper backup tools. Not the filesystem.

**4. Never chmod 777 or chown root on the data directory.**

PostgreSQL must own its data directory. It must be mode 700. Anything else is a security hole and a functionality problem. If you change permissions, the database dies. If you let root own it, PostgreSQL's backend processes can't write to it.

Seriously, never. I've seen a consultant do this "to test something," and it took me two hours to figure out what was wrong.

**5. Never assume a backup is good without testing it.**

You backup databases. Great. But if you don't restore one and verify it works, you don't have a backup. You have a file. One DBA I knew backed up for three years without ever testing a restore. When they finally needed to restore, the backups were corrupted. Three years of data lost. The lesson: Test your restores. Monthly. I mean it.

LAB EXERCISE: YOUR CLUSTER ANATOMY
================================================================================

Alright, hands-on time. You have 15 minutes. Do these exercises on your machine. I'll walk around and help if you get stuck.

**Exercise 1: Map Your Databases**

In psql, run:

    SELECT datname, oid, spcname FROM pg_database 
    JOIN pg_tablespace ON pg_database.spcname = spcname 
    ORDER BY oid;

For each database, verify that a directory with that OID exists in $PGDATA/base/. Write down the OID and database name for at least three databases.

**Exercise 2: Count Your Tables**

Pick one database (say, postgres). In psql, while connected to that database, run:

    SELECT COUNT(*) FROM pg_class WHERE relkind = 'r';

This counts the number of tables in that database. Now count the files in the corresponding directory in base/:

    sudo -u postgres ls $PGDATA/base/OID/ | wc -l

They won't be exactly the same (tables aren't the only things with a relfilenode, and some things are in other files), but they should be in the same ballpark. What's the difference?

**Exercise 3: Watch the WAL**

Run this to see the current active WAL file:

    sudo -u postgres ls -la $PGDATA/pg_wal/ | grep "^-" | tail -1

Note the name and the size. Now, in psql, do a big transaction:

    CREATE TABLE big_table (id INT PRIMARY KEY, data TEXT);
    INSERT INTO big_table SELECT generate_series(1, 100000), 'row number ' || generate_series(1, 100000);

Check the WAL again. Did the active segment grow? Did a new segment appear? What do you see?

Clean up:

    DROP TABLE big_table;

**Exercise 4: Check Configuration**

Look at your postgresql.conf:

    sudo -u postgres cat $PGDATA/postgresql.conf | grep -v "^#" | grep -v "^$" | head -20

See what settings are uncommented? Try to understand a few. Run this command to see all settings:

    SELECT name, setting FROM pg_settings WHERE source = 'configuration file' LIMIT 10;

These settings are read from postgresql.conf when the server starts.

**Exercise 5: Replication Slot Exploration (Bonus)**

If you've set up logical replication (we'll do this in week 8), look in pg_logical/:

    sudo -u postgres ls -la $PGDATA/pg_logical/

What do you see? If you don't see anything, that's fine — you probably don't have replication set up yet. But that's where it would be.

================================================================================
CONNECTING THE DOTS
================================================================================

Okay, let me tie this back to what we've already learned. Remember the postmaster process we talked about? It's sitting in the $PGDATA directory, reading postgresql.conf and PG_VERSION on startup. It's launching backend processes that are writing to pg_wal/ and reading from and writing to base/. The bgwriter is flushing dirty buffers to the table files in base/. The walwriter is flushing the WAL buffer to pg_wal/. The checkpointer is making sure everything is synced to disk. The autovacuum worker is compacting files in base/.

The stats collector is writing statistics to pg_stat_tmp/ and flushing to pg_stat/. When you create a table, PostgreSQL creates a file in base/ with a relfilenode number. When you run a query, it reads from that file. Every change is logged to pg_wal/. When you archive the WAL, you're extracting those transaction logs and storing them elsewhere so you can recover to any point in time.

The whole system is a massive, coordinated filing system. Once you understand the physical layout, the logical layout makes so much more sense.

Before you leave today, here's what I want you to remember for when you're on call:

- Know where your $PGDATA is. Know it cold.
- Know which database corresponds to which OID. Know how to map them.
- Know that base/ is where data lives. Know that pg_wal/ is where transaction logs live.
- Know that you don't delete from pg_wal/. Ever. Full stop.
- Know that postgresql.conf controls your settings.
- Know that postmaster.pid needs to be removed if it's stale.
- Know that permissions matter. PostgreSQL owns $PGDATA. Always.
- Know that a backup isn't a backup until you've tested restoring it.
- Know that if you don't understand something, you ask. You don't guess.

Do these things, and you'll be fine. You'll be the DBA people trust. You'll be the DBA who doesn't lose data. And trust me, that'll get you far.

QUICK-REFERENCE COMMAND CARD
================================================================================

FIND YOUR DATA DIRECTORY:
    sudo -u postgres psql -c "SHOW data_directory;"

LIST DATABASES AND THEIR OIDs:
    sudo -u postgres psql -c "SELECT datname, oid FROM pg_database ORDER BY oid;"

LIST TABLES IN CURRENT DATABASE AND THEIR FILENODES:
    SELECT relname, relfilenode FROM pg_class WHERE relkind = 'r';

CHECK CURRENT WAL SEGMENT:
    sudo -u postgres ls -la $PGDATA/pg_wal/ | tail -5

VIEW ACTIVE POSTGRESQL CONFIG:
    sudo -u postgres psql -c "SELECT name, setting FROM pg_settings WHERE source = 'configuration file';"

CHECK DATABASE DIRECTORY SIZES:
    du -sh $PGDATA/base/*

FIND LARGEST TABLES:
    SELECT schemaname, tablename, pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS size
    FROM pg_tables 
    ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC 
    LIMIT 10;

RESTART POSTGRESQL:
    sudo systemctl restart postgresql

START POSTGRESQL MANUALLY:
    sudo -u postgres pg_ctl start -D /path/to/data_directory

STOP POSTGRESQL GRACEFULLY:
    sudo -u postgres pg_ctl stop -D /path/to/data_directory

STOP POSTGRESQL FORCEFULLY (DANGEROUS):
    sudo -u postgres pg_ctl stop -D /path/to/data_directory -m immediate

VERIFY DATA DIRECTORY OWNERSHIP (should be postgres:postgres with mode 700):
    ls -ld /path/to/data_directory

FIX DATA DIRECTORY PERMISSIONS:
    sudo chown -R postgres:postgres /path/to/data_directory
    sudo chmod 700 /path/to/data_directory

REMOVE STALE POSTMASTER.PID (only if sure postmaster is NOT running):
    sudo rm /path/to/data_directory/postmaster.pid

EXPORT PGDATA FOR EASY REFERENCE:
    export PGDATA=$(sudo -u postgres psql -c "SHOW data_directory" -t | tr -d ' ')
    cd $PGDATA

VIEW POSTGRESQL CONFIG FILES:
    cat $PGDATA/postgresql.conf
    cat $PGDATA/pg_hba.conf
    cat $PGDATA/pg_ident.conf
