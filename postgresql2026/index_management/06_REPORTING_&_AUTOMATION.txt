================================================================================
THE REPORTING MINDSET: AUDIENCE MATTERS
================================================================================

Before I teach you the mechanics, let's talk about mindset.

When you create a report, you have to think about *who you're reporting to*. And adjust your message accordingly.

**For your fellow DBAs (technical audience):**
- Lots of detail
- Specific SQL queries
- Before/after metrics
- Performance numbers

**For management/finance (business audience):**
- Cost impact
- Risk mitigation
- Storage savings
- Performance improvement in business terms (not "query latency reduced 200ms", but "page load time improved 15%")

**For executives (decision-makers):**
- One-page summary
- Top three action items
- Cost savings or risk reduction
- Nothing longer than five minutes to read

I typically create a tiered report:

1. **Executive Summary** (one page, high-level)
2. **Detailed Findings** (5-10 pages, technical, for DBAs)
3. **Appendix** (raw data and queries)

The executive summary might say: "We found 5 indexes to delete, saving 2 GB of storage and reducing weekly maintenance time by 4 hours."

The detailed findings might say: "The indexes idx_orders_date_old, idx_customers_legacy, idx_sales_region, idx_products_sku_dupe, and idx_transactions_backup have not been scanned in 180+ days. Index definitions [attached]. Recommendation: delete all five. Risk assessment: low, based on absence of scan activity and confirmed redundancy with newer indexes."

See how the message changes based on audience? You're saying the same thing, but in a way each audience can understand and act on.

================================================================================
THE DATA COLLECTION FRAMEWORK: PERSISTENT CAPTURE
================================================================================

Before you can report, you need to collect data. And you need to collect it *consistently over time*.

This is critical. A snapshot tells you what's happening *right now*. But a trend tells you what's happening *over time*. Trends are way more valuable for decision-making.

Here's the framework I use:

**Step 1: Create a schema for historical data**

---

CREATE SCHEMA IF NOT EXISTS dba_reports;

CREATE TABLE IF NOT EXISTS dba_reports.index_snapshots (
    snapshot_date DATE NOT NULL,
    schemaname VARCHAR(100) NOT NULL,
    tablename VARCHAR(100) NOT NULL,
    indexname VARCHAR(100) NOT NULL,
    index_size_bytes BIGINT NOT NULL,
    table_size_bytes BIGINT NOT NULL,
    idx_scan BIGINT NOT NULL,
    idx_tup_read BIGINT NOT NULL,
    idx_tup_fetch BIGINT NOT NULL,
    table_inserts BIGINT NOT NULL,
    table_updates BIGINT NOT NULL,
    table_deletes BIGINT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS dba_reports.fragmentation_analysis (
    analysis_date DATE NOT NULL,
    schemaname VARCHAR(100) NOT NULL,
    tablename VARCHAR(100) NOT NULL,
    indexname VARCHAR(100) NOT NULL,
    index_size_bytes BIGINT NOT NULL,
    table_size_bytes BIGINT NOT NULL,
    size_ratio NUMERIC(10, 2) NOT NULL,
    fragmentation_estimate VARCHAR(50) NOT NULL,
    health_status VARCHAR(50) NOT NULL,
    priority VARCHAR(50) NOT NULL,
    recommended_action VARCHAR(500),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS dba_reports.maintenance_actions (
    action_id SERIAL PRIMARY KEY,
    action_date DATE NOT NULL,
    action_type VARCHAR(50) NOT NULL, -- 'REINDEX', 'DROP', etc.
    schemaname VARCHAR(100),
    tablename VARCHAR(100),
    indexname VARCHAR(100),
    status VARCHAR(50), -- 'COMPLETED', 'FAILED', 'PENDING'
    size_before_bytes BIGINT,
    size_after_bytes BIGINT,
    duration_seconds INTEGER,
    notes TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

---

**Step 2: Create a data collection script**

This script runs weekly (or daily, depending on your needs) and captures the current state:

---

-- weekly_snapshot.sql

INSERT INTO dba_reports.index_snapshots 
(snapshot_date, schemaname, tablename, indexname, index_size_bytes, 
 table_size_bytes, idx_scan, idx_tup_read, idx_tup_fetch, 
 table_inserts, table_updates, table_deletes)
SELECT 
    CURRENT_DATE,
    i.schemaname,
    i.tablename,
    i.indexname,
    pg_relation_size(i.indexrelid),
    pg_relation_size(t.oid),
    i.idx_scan,
    i.idx_tup_read,
    i.idx_tup_fetch,
    t.n_tup_ins,
    t.n_tup_upd,
    t.n_tup_del
FROM pg_stat_user_indexes i
JOIN pg_stat_user_tables t ON i.tablename = t.relname
WHERE i.schemaname NOT IN ('pg_catalog', 'information_schema', 'dba_reports');

---

**Step 3: Create the analysis script**

This script runs after the snapshot and does the analysis:

---

-- weekly_analysis.sql

INSERT INTO dba_reports.fragmentation_analysis
(analysis_date, schemaname, tablename, indexname, index_size_bytes, 
 table_size_bytes, size_ratio, fragmentation_estimate, health_status, priority)
SELECT 
    CURRENT_DATE,
    schemaname,
    tablename,
    indexname,
    index_size_bytes,
    table_size_bytes,
    ROUND((index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) * 100, 2) as ratio,
    CASE 
        WHEN (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 2.0 THEN 'LIKELY FRAGMENTED'
        WHEN (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 1.5 THEN 'POSSIBLY FRAGMENTED'
        ELSE 'NORMAL'
    END as fragmentation,
    CASE 
        WHEN idx_scan = 0 THEN 'UNUSED'
        WHEN idx_scan > 0 AND (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 2.0 THEN 'UNHEALTHY'
        WHEN idx_scan > 0 AND (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 1.5 THEN 'AT RISK'
        ELSE 'HEALTHY'
    END as health,
    CASE 
        WHEN idx_scan = 0 THEN 'HIGH'
        WHEN idx_scan > 1000 AND (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 1.5 THEN 'HIGH'
        WHEN (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 2.0 THEN 'MEDIUM'
        ELSE 'LOW'
    END as priority
FROM dba_reports.index_snapshots
WHERE snapshot_date = CURRENT_DATE;

================================================================================
CONFIDENCE SCORING: MAKING RECOMMENDATIONS DEFENSIBLE
================================================================================

Here's something critical: when you recommend an action (like deleting an index), you need to be confident. You need to be able to defend it if something goes wrong.

A confidence score is a numerical ranking (usually 0-100) that indicates how confident you are in a recommendation.

For the "unused index" scenario, here's how I calculate confidence:

---

-- Calculate confidence score for index deletion recommendation

SELECT 
    indexname,
    idx_scan,
    days_since_creation,
    days_since_last_use,
    CASE 
        WHEN idx_scan = 0 AND days_since_creation >= 90 THEN 100
        WHEN idx_scan = 0 AND days_since_creation >= 30 THEN 80
        WHEN idx_scan = 0 AND days_since_creation >= 7 THEN 60
        WHEN idx_scan > 0 AND days_since_last_use >= 180 THEN 95
        WHEN idx_scan > 0 AND days_since_last_use >= 90 THEN 85
        WHEN idx_scan > 0 AND days_since_last_use >= 30 THEN 70
        ELSE 0
    END as confidence_score,
    CASE 
        WHEN idx_scan = 0 AND days_since_creation >= 90 
        THEN 'Very safe to delete. Index never used since creation, many days ago.'
        WHEN idx_scan > 0 AND days_since_last_use >= 180 
        THEN 'Likely safe. Index has not been used in 6+ months.'
        WHEN idx_scan > 0 AND days_since_last_use >= 90 
        THEN 'Probably safe. No scans in 3+ months. Test in non-prod first.'
        WHEN idx_scan = 0 AND days_since_creation >= 30 
        THEN 'Cautious recommendation. Never used, but recently created.'
        ELSE 'Not recommended for deletion yet.'
    END as recommendation_rationale
FROM (
    SELECT 
        indexname,
        idx_scan,
        EXTRACT(DAY FROM (CURRENT_DATE - pg_stat_file('base/' || 
            (SELECT oid FROM pg_database WHERE datname = current_database())::TEXT || 
            '/' || indexrelid::TEXT)::TIMESTAMP))::INTEGER as days_since_creation,
        EXTRACT(DAY FROM (CURRENT_DATE - to_timestamp(
            (SELECT stats_reset FROM pg_stat_user_indexes i2 WHERE i2.indexrelid = i.indexrelid))))::INTEGER as days_since_last_use
    FROM pg_stat_user_indexes i
) subq
ORDER BY confidence_score DESC;

---

(Note: The file modification time approach above is approximate. In practice, you might track index creation date in your metadata table.)

The key insight: a confidence score lets you prioritize. High confidence (95+) items go in your "do this immediately" list. Medium confidence (70-90) items go in "plan for next month." Low confidence items you monitor but don't act on yet.

In your reports, you present only high-confidence recommendations. This protects you if something goes wrong. You can say, "We had very high confidence in this recommendation based on [data]."

BASH AUTOMATION: THE weekly_unused_indexes_report.sh SCRIPT
================================================================================

Now let me show you how to automate this. I'm going to build a bash script that:

1. Connects to PostgreSQL
2. Runs analysis queries
3. Generates a report in both text and HTML formats
4. Emails it to stakeholders
5. Logs everything

Here's the script:

---

#!/bin/bash

#===============================================================================
# Weekly Index Health Report Generator
# Purpose: Analyze PostgreSQL indexes and generate actionable reports
# Schedule: Sundays at 8:00 AM via cron
# Author: DBA Team
# Last Updated: 2024-01-22
#===============================================================================

set -euo pipefail

# Configuration
readonly DB_HOST="${DB_HOST:-localhost}"
readonly DB_PORT="${DB_PORT:-5432}"
readonly DB_USER="${DB_USER:-postgres}"
readonly DB_NAME="${DB_NAME:-production}"
readonly REPORT_DIR="/var/log/dba_reports"
readonly REPORT_DATE=$(date +%Y-%m-%d)
readonly REPORT_TIME=$(date '+%Y-%m-%d %H:%M:%S')
readonly REPORT_FILE="${REPORT_DIR}/index_report_${REPORT_DATE}.txt"
readonly HTML_FILE="${REPORT_DIR}/index_report_${REPORT_DATE}.html"
readonly LOG_FILE="${REPORT_DIR}/index_report_${REPORT_DATE}.log"
readonly EMAIL_TO="${EMAIL_TO:-dba-team@company.com}"
readonly PSQL_OPTS="-h ${DB_HOST} -p ${DB_PORT} -U ${DB_USER} -d ${DB_NAME}"

# Colors for output
RED='\033[0;31m'
GREEN='\033[0;32m'
YELLOW='\033[1;33m'
NC='\033[0m' # No Color

#===============================================================================
# LOGGING FUNCTIONS
#===============================================================================

log() {
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "${LOG_FILE}"
}

log_error() {
    echo -e "${RED}[ERROR]${NC} $*" | tee -a "${LOG_FILE}"
}

log_success() {
    echo -e "${GREEN}[SUCCESS]${NC} $*" | tee -a "${LOG_FILE}"
}

#===============================================================================
# MAIN FUNCTIONS
#===============================================================================

setup_environment() {
    log "Setting up environment..."
    
    # Create report directory if it doesn't exist
    mkdir -p "${REPORT_DIR}"
    
    # Initialize log file
    {
        echo "================================================================================"
        echo "Index Health Report - Execution Log"
        echo "Start Time: ${REPORT_TIME}"
        echo "Database: ${DB_NAME}"
        echo "================================================================================"
    } > "${LOG_FILE}"
    
    log "Environment ready. Report directory: ${REPORT_DIR}"
}

test_database_connection() {
    log "Testing database connection..."
    
    if psql ${PSQL_OPTS} -c "SELECT 1" > /dev/null 2>&1; then
        log_success "Database connection successful"
        return 0
    else
        log_error "Failed to connect to database"
        return 1
    fi
}

generate_text_report() {
    log "Generating text report..."
    
    {
        echo "================================================================================"
        echo "WEEKLY INDEX HEALTH REPORT"
        echo "Week Ending: ${REPORT_DATE}"
        echo "Generated: ${REPORT_TIME}"
        echo "Database: ${DB_NAME}"
        echo "================================================================================"
        echo ""
        echo "EXECUTIVE SUMMARY"
        echo "─────────────────────────────────────────────────────────────────────────────────"
        
        # Get summary metrics
        psql ${PSQL_OPTS} -t -c "
        SELECT 
            'Total Indexes Analyzed: ' || COUNT(*) || E'\n' ||
            'Unused Indexes: ' || SUM(CASE WHEN idx_scan = 0 THEN 1 ELSE 0 END) || E'\n' ||
            'Possibly Fragmented: ' || 
            SUM(CASE WHEN (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 1.5 THEN 1 ELSE 0 END) || E'\n' ||
            'Total Index Storage: ' || pg_size_pretty(SUM(index_size_bytes)) || E'\n' ||
            'Unused Index Storage: ' || 
            pg_size_pretty(SUM(CASE WHEN idx_scan = 0 THEN index_size_bytes ELSE 0 END))
        FROM dba_reports.index_snapshots
        WHERE snapshot_date = CURRENT_DATE;
        " >> "${REPORT_FILE}"
        
        echo ""
        echo "ACTION ITEMS (High Confidence)"
        echo "─────────────────────────────────────────────────────────────────────────────────"
        
        # Get unused indexes
        psql ${PSQL_OPTS} -t -c "
        SELECT 
            indexname || E'\n' ||
            '  Storage: ' || pg_size_pretty(index_size_bytes) || E'\n' ||
            '  Scans: ' || idx_scan || E'\n' ||
            '  Recommendation: DELETE' || E'\n'
        FROM dba_reports.fragmentation_analysis
        WHERE analysis_date = CURRENT_DATE
        AND health_status = 'UNUSED'
        AND priority = 'HIGH'
        ORDER BY index_size_bytes DESC
        LIMIT 5;
        " >> "${REPORT_FILE}"
        
        echo ""
        echo "DETAILED FINDINGS"
        echo "─────────────────────────────────────────────────────────────────────────────────"
        
        # Get fragmentation details
        psql ${PSQL_OPTS} -t -c "
        SELECT 
            'Index: ' || indexname || E'\n' ||
            '  Table: ' || tablename || E'\n' ||
            '  Size Ratio: ' || size_ratio::TEXT || '%' || E'\n' ||
            '  Status: ' || health_status || E'\n' ||
            '  Action: ' || recommended_action || E'\n'
        FROM dba_reports.fragmentation_analysis
        WHERE analysis_date = CURRENT_DATE
        AND health_status IN ('UNHEALTHY', 'AT RISK')
        ORDER BY size_ratio DESC;
        " >> "${REPORT_FILE}"
        
        echo ""
        echo "Report generated successfully"
        
    } > "${REPORT_FILE}" 2>&1
    
    log_success "Text report generated: ${REPORT_FILE}"
}

    <div class="container">
        <h1>Weekly Index Health Report</h1>
EOF
        echo "        <p>Generated: $(date '+%Y-%m-%d %H:%M:%S') | Database: ${DB_NAME}</p>"
        
        cat <<'EOF'
        
        <h2>Executive Summary</h2>
        <div class="summary-box">
            <p>Index health status and key metrics from this week's analysis.</p>
        </div>
EOF
        
        # Add metrics
        psql ${PSQL_OPTS} -H -c "
        SELECT 
            'Metric' as metric,
            'Value' as value
        UNION ALL
        SELECT 
            'Total Indexes',
            COUNT(*)::TEXT
        FROM dba_reports.index_snapshots
        WHERE snapshot_date = CURRENT_DATE;
        " >> "${HTML_FILE}"
        
        cat <<'EOF'
        
        <h2>Action Items</h2>
        <table>
            <tr>
                <th>Index Name</th>
                <th>Storage</th>
                <th>Status</th>
                <th>Priority</th>
                <th>Action</th>
            </tr>

        # Add action items from database
        psql ${PSQL_OPTS} -t -c "
        SELECT 
            '<tr><td>' || indexname || '</td>' ||
            '<td>' || pg_size_pretty(index_size_bytes) || '</td>' ||
            '<td>' || health_status || '</td>' ||
            '<td class=\"' || LOWER(priority) || '\">' || priority || '</td>' ||
            '<td>' || COALESCE(recommended_action, 'Monitor') || '</td></tr>'
        FROM dba_reports.fragmentation_analysis
        WHERE analysis_date = CURRENT_DATE
        ORDER BY priority DESC, index_size_bytes DESC
        LIMIT 10;
        " >> "${HTML_FILE}"
        
        cat <<'EOF'
        </table>
        
        <div class="footer">
            <p>This is an automated report. For questions, contact the DBA team.</p>
        </div>
    </div>
</body>
</html>
EOF
    } > "${HTML_FILE}" 2>&1
    
    log_success "HTML report generated: ${HTML_FILE}"
}

SELECT 
    CURRENT_DATE,
    i.schemaname,
    i.tablename,
    i.indexname,
    pg_relation_size(i.indexrelid),
    pg_relation_size(t.oid),
    i.idx_scan,
    i.idx_tup_read,
    i.idx_tup_fetch,
    t.n_tup_ins,
    t.n_tup_upd,
    t.n_tup_del
FROM pg_stat_user_indexes i
JOIN pg_stat_user_tables t ON i.tablename = t.relname
WHERE i.schemaname NOT IN ('pg_catalog', 'information_schema', 'dba_reports');
EOF
    
    log_success "Snapshot captured"
}

analyze_indexes() {
    log "Running analysis..."
    
    psql ${PSQL_OPTS} -f - <<'EOF'
INSERT INTO dba_reports.fragmentation_analysis
(analysis_date, schemaname, tablename, indexname, index_size_bytes, 
 table_size_bytes, size_ratio, fragmentation_estimate, health_status, priority)
SELECT 
    CURRENT_DATE,
    schemaname,
    tablename,
    indexname,
    index_size_bytes,
    table_size_bytes,
    ROUND((index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) * 100, 2),
    CASE 
        WHEN (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 2.0 THEN 'LIKELY'
        WHEN (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 1.5 THEN 'POSSIBLE'
        ELSE 'NORMAL'
    END,
    CASE 
        WHEN idx_scan = 0 THEN 'UNUSED'
        WHEN idx_scan > 0 AND (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 2.0 THEN 'UNHEALTHY'
        WHEN idx_scan > 0 AND (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 1.5 THEN 'AT RISK'
        ELSE 'HEALTHY'
    END,
    CASE 
        WHEN idx_scan = 0 THEN 'HIGH'
        WHEN idx_scan > 1000 AND (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 1.5 THEN 'HIGH'
        WHEN (index_size_bytes::FLOAT / NULLIF(table_size_bytes, 0)) > 2.0 THEN 'MEDIUM'
        ELSE 'LOW'
    END
FROM dba_reports.index_snapshots
WHERE snapshot_date = CURRENT_DATE;
EOF
    
    log_success "Analysis complete"
}

send_report() {
    log "Sending report via email..."
    
    if [[ -f "${REPORT_FILE}" ]]; then
        {
            cat "${REPORT_FILE}"
            echo ""
            echo "HTML version available at: ${HTML_FILE}"
        } | mail -s "Weekly Index Health Report - ${REPORT_DATE}" "${EMAIL_TO}"
        
        log_success "Report emailed to ${EMAIL_TO}"
    else
        log_error "Report file not found, email not sent"
        return 1
    fi
}

cleanup() {
    log "Cleaning up..."
    
    # Archive old reports (keep last 12 weeks)
    find "${REPORT_DIR}" -name "index_report_*.txt" -mtime +84 -delete
    find "${REPORT_DIR}" -name "index_report_*.html" -mtime +84 -delete
    
    log_success "Cleanup complete"
}

================================================================================
HISTORICAL TREND TRACKING: THE LONG VIEW
================================================================================

The real power of reporting comes from tracking trends over time.

With weeks or months of historical data, you can answer questions like:
- Is our index fragmentation getting better or worse?
- Are we maintaining our indexes effectively?
- What's the total storage trend?
- Which tables are most problematic?

Here's a query to show trends:

---

SELECT 
    DATE_TRUNC('week', analysis_date)::DATE as week_ending,
    COUNT(*) as total_indexes,
    SUM(CASE WHEN health_status = 'UNUSED' THEN 1 ELSE 0 END) as unused_count,
    SUM(CASE WHEN health_status = 'UNHEALTHY' THEN 1 ELSE 0 END) as unhealthy_count,
    SUM(CASE WHEN health_status = 'AT RISK' THEN 1 ELSE 0 END) as at_risk_count,
    pg_size_pretty(SUM(index_size_bytes)) as total_storage,
    ROUND(AVG(size_ratio), 2) as avg_fragmentation_ratio
FROM dba_reports.fragmentation_analysis
GROUP BY week_ending
ORDER BY week_ending DESC
LIMIT 12;

---

Run this quarterly and present it to management. Show trends. Show improvement. This is how you justify continued investment in DBA maintenance work.

** CALCULATE CONFIDENCE SCORE **

    SELECT 
        indexname,

            WHEN idx_scan = 0 AND

            THEN 100
            WHEN idx_scan = 0 AND
