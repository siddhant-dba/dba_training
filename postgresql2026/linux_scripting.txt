TASK TITLE: The Skeleton Contract
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
OBJECTIVE
Build a script skeleton that separates orchestration from logic using a main() function pattern, with disciplined exit-code use.

TASKS
- Script must define a main() function as the single entry point; the only top-level executable statement outside function/variable definitions is the call to main "$@".
- Script must support at least 3 distinct exit codes, each tied to a different failure category (e.g. bad usage, missing dependency, operation failure), plus 0 for success.
- No business logic may live outside a function -- top-level code is limited to definitions and the final main call.
- Script must work correctly with zero arguments, one argument, and multiple arguments without crashing.

VALIDATION
- Run with no args, valid args, and intentionally invalid args; confirm distinct, correct exit codes via $? after each run.
- Inspect the script to confirm no executable statement exists outside a function definition except the trailing main call.

FAILURE SCENARIOS
- Script is invoked with an unexpected number of arguments.
- Script is sourced instead of executed.

COMMON MISTAKES
- Letting "setup" code leak outside any function ("just this one line, it's fine").
- Returning exit codes from functions but never propagating them to the script's actual exit status.

REVIEW QUESTIONS
- Why does mixing orchestration and logic in main() reduce testability?
- What's the difference between a function's return value and the script's exit status, and where can that distinction silently break?

TASK TITLE: One Job Per Function
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
OBJECTIVE
Decompose a multi-step operation into single-responsibility functions communicating only through explicit inputs/outputs.

TASKS
- Build a script simulating a 4-stage process (e.g. validate -> prepare -> execute -> verify), each stage in its own function.
- No function may read or write a variable it wasn't passed -- data passes only through parameters and local return-by-stdout conventions.
- Each function must do exactly one observable thing; if you can describe a function's job with "and," split it.
- main() should read as a high-level summary of the process when viewed alone, with no implementation detail visible.

VALIDATION
- Read main() in isolation; confirm a new team member could describe the script's behavior from main() alone without reading any other function.
- Temporarily disable one stage function and confirm the failure is isolated and clearly attributable to that stage.

FAILURE SCENARIOS
- One stage produces output the next stage doesn't expect.
- A stage is skipped or called out of order.

COMMON MISTAKES
- Using global variables as a shortcut instead of proper parameter passing.
- Functions that both compute a value and print logging output mixed into the same stdout stream used for return values.

REVIEW QUESTIONS
- What breaks first when two functions implicitly share state through globals instead of parameters?
- How would you test stage 3 in isolation without running stages 1, 2, and 4?

TASK TITLE: Scope Discipline
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
OBJECTIVE
Build a script demonstrating controlled variable scope across nested function calls, with zero accidental leakage.

TASKS
- Build a script with at least 3 levels of nested function calls (function A calls B calls C).
- Every variable used inside a function that is not a parameter must be declared local; only a deliberately chosen, minimal set may be intentionally global, and that choice must be evident through naming convention.
- Design the script so that two unrelated nested functions reusing the same variable name (e.g. i, result) cannot cause incorrect behavior.
- Provide a way to verify, at runtime, that no unintended global variables were created during execution.

VALIDATION
- Run the script, then inspect the shell's variable table afterward (if sourced) to confirm no unexpected globals exist.
- Deliberately reuse a common variable name in two unrelated nested functions and confirm no cross-contamination occurs.

FAILURE SCENARIOS
- A function is called recursively and scope discipline must hold across recursive depth.
- Two sibling functions are called in sequence and accidentally share a leaked variable name.

COMMON MISTAKES
- Forgetting local on loop counters inside functions.
- Assuming local is the default in Bash (it isn't).

REVIEW QUESTIONS
- Why is Bash's default global scope dangerous in scripts beyond ~100 lines?
- What real production bug class does undisciplined scoping tend to cause?

TASK TITLE: The Exit Code Map
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
OBJECTIVE
Design and enforce a standardized, documented exit-code scheme for a script meant to be called by cron and alerting systems.

TASKS
- Design at least 6 distinct exit codes (0 = success), each a specific, mutually exclusive failure category (e.g. usage error, dependency missing, precondition failed, operation failed, partial success, timeout).
- Every exit point must use a named constant or clearly labeled value -- no bare unexplained integers scattered through the code.
- Guarantee that the LAST exit code reflects the true overall outcome even if intermediate functions fail and are recovered from.
- Build a self-check mode (a flag) that deliberately triggers each failure category on demand, so every exit code can be validated without needing real failure conditions.

VALIDATION
- Use the self-check mode to trigger every exit code and confirm $? matches the documented value for each.
- Confirm a downstream caller could reliably distinguish all categories using only $?.

FAILURE SCENARIOS
- Multiple failure types occur in the same run -- which exit code should win, and why?
- A function fails internally but the script "recovers" and continues -- what should the final exit code be?

COMMON MISTAKES
- Reusing the same exit code for unrelated failure types out of laziness.
- Letting a later successful step overwrite the exit code of an earlier real failure.

REVIEW QUESTIONS
- Why do undocumented or inconsistent exit codes erode trust in automation built on top of a script?
- How would an alerting system's logic differ if it could rely on exit codes versus having to parse log text?

TASK TITLE: Dual-Purpose Script
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
OBJECTIVE
Build a script that behaves correctly both when executed directly and when sourced as a library, with no unwanted side effects in either mode.

TASKS
- Script must detect whether it is being executed or sourced, and only run main()/exit when executed directly.
- When sourced, the script must expose its functions for reuse without printing output, setting traps, or calling exit/main automatically.
- Any setup the script needs must not be forced onto a script that sources it, unless explicitly requested.
- Provide a documented, intentional way for a sourcing script to opt into full standalone behavior if desired.

VALIDATION
- Execute the script directly and confirm full normal behavior including correct exit codes.
- Source the script from a second test script, call one of its functions directly, and confirm no unwanted exit, output, or option changes occurred.

FAILURE SCENARIOS
- A sourcing script unintentionally inherits an exit call meant only for standalone mode, killing its own shell session.
- Sourcing the script twice in the same session causes duplicate function/trap definitions or errors.

COMMON MISTAKES
- Using exit instead of return inside functions meant to be reusable.
- Forgetting that set -e / set -u inside a sourced script can silently change caller behavior.

REVIEW QUESTIONS
- Why is detecting execution-vs-sourcing mode foundational to building a reusable internal library?
- What's a realistic incident that could result from a sourced script changing shell options out from under its caller?

TASK TITLE: Trap-Proof Structure
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
OBJECTIVE
Ensure a script's structure guarantees cleanup runs exactly once, regardless of where or how it fails.

TASKS
- Build a script that creates at least one temporary resource (a temp file/dir or a lock) early in execution.
- Implement cleanup via trap bound to EXIT (and ideally INT/TERM) so the resource is removed no matter which function fails, how deep the call stack is, or whether the script exits normally, via error, or via signal.
- Cleanup must run exactly once even under multiple overlapping exit paths (e.g. an explicit exit deep in a nested function plus a top-level error).
- The script's structure must make it obvious, just from reading main(), that cleanup is guaranteed -- it should not depend on every function "remembering" to clean up.

VALIDATION
- Force failures at 3 different points in the call stack (early, middle, late) and confirm the temp resource is removed every time.
- Send SIGINT mid-execution and confirm cleanup still runs.

FAILURE SCENARIOS
- The script is killed with SIGKILL (untrappable) -- what's the structural implication, and how should the design account for that risk elsewhere?
- Cleanup itself fails partway through.

COMMON MISTAKES
- Putting cleanup code only at the "end" of main(), unreachable if an earlier step exits early.
- Defining the trap after the resource has already been created, leaving a window where failure skips cleanup.

REVIEW QUESTIONS
- Why must a trap be set before the resource it protects is created?
- What categories of failure can never be caught by a trap, and how does that change how you'd design resource safety?

OBJECTIVE
Build a CLI argument parser supporting both flags and value-bearing options for a backup-utility front-end, with strict validation.

TASKS

- Using positional $1, $2 indexing that breaks the moment option order changes.
- Silently accepting unknown flags instead of failing loudly.

- What's the operational cost of a script that silently ignores a typo'd flag instead of failing?
- How would you extend this parser to add a new option without touching unrelated logic?

OBJECTIVE
Validate structured input representing a database connection target before any operation is attempted.

TASKS
- Accept a hostname/IP, a port, and a database name as input.
- Validate the port is numeric and within the valid 1-65535 range.
- Validate the hostname is a plausible hostname/IP format without needing to resolve it over the network.

FAILURE SCENARIOS
- Input contains leading/trailing whitespace that looks valid but would fail downstream.
- Port is technically numeric but reserved/clearly wrong for the stated purpose (e.g. port 0).

COMMON MISTAKES
- Validating "is it non-empty" but not "is it the right shape."
- Bundling all field errors into one generic "invalid input" message that doesn't say which field.

REVIEW QUESTIONS
- Why does field-specific validation feedback matter more in automation than in a human-facing tool?
- What's the risk of validating format but not range (or vice versa)?

Build a usage/help system that activates both on request and automatically on misuse.

TASKS

- How would you guarantee usage() and the actual parser never go out of sync as the script grows?

TASK TITLE: One Script, Two Audiences
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
OBJECTIVE
Design a script supporting both interactive human use and automated/orchestrated invocation from a single codebase, each with appropriate UX.

TASKS
- Build a script performing one core operation that can be run interactively (prompts/confirmations, readable progress, colorized output where appropriate) and non-interactively (no prompts, machine-parseable output, deterministic exit codes) -- same underlying logic, different presentation layer.
- The script must correctly auto-detect or be explicitly told which mode applies, and behave appropriately without two separate maintained codebases.
- Confirmation prompts appropriate for interactive use must have a sane, explicit, pre-decided default/behavior for non-interactive mode -- never silently hang waiting for input that will never come.
- Core operation logic must live in exactly one place, with the two "audiences" being a thin presentation layer around shared logic.

VALIDATION
- Run the script interactively and confirm a sensible human experience. Run it non-interactively (e.g. with stdin redirected from /dev/null) and confirm it never hangs and produces appropriately machine-friendly output, with both modes producing the same underlying correct result.

FAILURE SCENARIOS
- The script is run non-interactively but a flag necessary to specify the otherwise-interactive default wasn't provided -- does it fail clearly, or silently guess?

COMMON MISTAKES
- Building two semi-duplicated implementations that inevitably drift apart in behavior over time.
- Leaving a confirmation prompt that can hang forever if stdin isn't a terminal and no non-interactive default/flag was provided.

REVIEW QUESTIONS
- Why is "two parallel implementations for two audiences" a maintenance trap, and how does a shared-core design avoid it?
- What must always be true about a confirmation prompt's behavior when input can't actually be provided?

TASK TITLE: Traceable Behavior Changes
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
OBJECTIVE
Build versioning and changelog discipline into a script itself, so behavior changes are traceable across its operational lifetime.

TASKS
- The script must report its own version (e.g. via --version), incremented whenever observable behavior changes -- not for cosmetic edits.
- Build an internal changelog, embedded in or shipped alongside the script, documenting what changed in each version specifically in terms of observable behavior, not implementation detail.
- Evolve your script through at least 2 versions with one genuine observable behavior change between them, demonstrating that the version number and changelog entry correctly reflect that the change occurred.
- Identify a way an operator running this script in production, months from now, could determine "did this script's behavior change recently, and if so, how" without digging through commit history or source diffs.

VALIDATION
- Produce version 1 and document its behavior. Make one real, observable behavior change for version 2 and confirm the version flag, changelog, and actual behavior all consistently reflect exactly what changed and nothing else silently did.

FAILURE SCENARIOS
- A "minor" internal refactor unintentionally changes an observable edge-case behavior, but the version/changelog isn't updated because the author didn't think of it as a "real" change -- how does discipline around this get enforced rather than relying on memory?

COMMON MISTAKES
- Bumping version numbers for purely cosmetic changes while failing to bump them for subtle-but-real behavior changes.
- Writing changelog entries in terms of internal implementation rather than observable behavior an operator would actually notice or care about.

REVIEW QUESTIONS
- Why does "observable behavior change" matter more than "code changed" as the trigger for a version bump in an operational script?
- How would an operator, months later, use a well-maintained version/changelog discipline to quickly determine whether a recent issue correlates with a recent script change?
