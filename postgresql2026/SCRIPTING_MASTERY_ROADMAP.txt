This is not a coding bootcamp. This is operational engineering training.

You are learning to think like a Senior DBA who automates, diagnoses, and
operates production systems under pressure, with visibility, accountability,
and zero tolerance for failure.

Every script must answer:
  - Why does a DBA need this? (business value)
  - What breaks? (failure modes)
  - How do I know if it worked? (validation)
  - What do I do if it fails? (rollback/recovery)
  - Who needs to know? (logging/alerting)

NOT: "Here's a clever Bash one-liner."
YES: "Here's a production script with error handling, logging, audit trails,
      and validated success criteria."

DAY 1-2: LINUX FILESYSTEM & PERMISSIONS (Why DBAs Care)
────────────────────────────────────────────────────────────────────────────
CONCEPT
  - Filesystem hierarchy (/, /var, /home, /opt, /data)
  - Inodes, blocks, metadata
  - Permission model (rwx for user/group/other)
  - File ownership and group membership
  - Special permissions (setuid, setgid, sticky bit)

PRODUCTION RELEVANCE
  - PostgreSQL data directory lives on disk (usually /var/lib/postgresql or /data)
  - Permissions control who can read/write WAL, backups, config files
  - Disk full is a common incident; understanding inodes vs blocks matters
  - Backup permissions determine who can restore
  - Log rotation requires write access to pg_log/

COMMON MISTAKES
  - Running PostgreSQL with wrong ownership (postgres:postgres is required)
  - World-readable data directory (SECURITY RISK)
  - Backup files with wrong permissions (restore fails)
  - Not checking available inodes (df shows space, but inode exhaustion blocks writes)
  - Mounted filesystems with noexec flag (PostgreSQL cannot start)

REAL-WORLD INCIDENT
  [2019] Production PostgreSQL stopped accepting writes. "No space left on device."
  Investigation: "df -h" showed 15% free. But "df -i" showed 97% inode usage.
  Root cause: Log rotation script died; /var/log filled with 4M small files.
  Fix: Delete old logs, restart PostgreSQL.
  Lesson: Check both space AND inodes. Both matter.

BEST PRACTICES
  1. PostgreSQL data directory always: /data (or dedicated mount) with mode 700
  2. PostgreSQL binary/config in /opt or /usr/lib/postgresql (system managed)
  3. Backups in /backups with restricted permissions (backup user only)
  4. Logs in /var/log/postgresql with rotation policy (14 days default)
  5. Temporary files in /tmp or /var/tmp with cleanup
  6. All PostgreSQL files owned by postgres:postgres
  7. Regular monitoring: df -h, df -i, du -sh for top directories

SECURITY CONSIDERATIONS
  - Data directory must NOT be world-readable (encryption keys, configs exposed)
  - Backup files must be readable only by backup user
  - WAL archiving files require careful permission management
  - Audit logs must not be modifiable by regular users

PERFORMANCE CONSIDERATIONS
  - Filesystem choice matters (ext4, xfs, zfs)
  - I/O scheduling affects PostgreSQL latency
  - RAID configuration affects recovery time
  - SSD vs HDD trade-offs

MONITORING CONSIDERATIONS
  - Alert when filesystem reaches 80%, 90%, 95%
  - Alert when inode usage exceeds 85%
  - Monitor disk growth trend (capacity planning)
  - Track I/O wait percentage (iostat)

TROUBLESHOOTING APPROACH
  1. Run "df -h" and "df -i" to see space and inode usage
  2. Use "du -sh /*" to identify large directories
  3. Check "lsblk" to see mounted filesystems and their types
  4. Review "mount" output to check mount options (noexec, nodev, nosuid)
  5. Use "stat" on data directory to verify owner and permissions
  6. Check "iostat -x 1" for I/O performance

EXERCISE 1.1: Filesystem Audit
  - Log into your PostgreSQL server
  - Run: ls -lad /data /var/lib/postgresql /backups
  - Run: df -h; df -i; du -sh /data /var/lib/postgresql /var/log/postgresql
  - Create a simple file in /data/test and verify permissions
  - Answer: What is the owner/group/permission of the PostgreSQL data directory?
  - Answer: How much space/inodes are available?
  - Answer: What is the growth rate? (du now vs. one month ago)

EXERCISE 1.2: Permission Model
  - Create a test directory: mkdir -p /tmp/pg_test
  - Change ownership: chown postgres:postgres /tmp/pg_test
  - Set permissions to 700: chmod 700 /tmp/pg_test
  - Try to read as different user (if applicable)
  - Answer: Who can read/write/execute? Why does this matter?
  - Answer: What happens if permissions are 777?

DAY 3-4: USERS, GROUPS & PROCESSES (Process Privilege Model)
────────────────────────────────────────────────────────────────────────────
CONCEPT
  - User/group model in Linux (/etc/passwd, /etc/group)
  - UID/GID (numeric identifiers)
  - Process ownership and execution context
  - Process hierarchy (parent/child, PID/PPID)
  - Signal handling (SIGTERM, SIGKILL, etc.)

PRODUCTION RELEVANCE
  - PostgreSQL runs as "postgres" user (non-root, security boundary)
  - Backup scripts may run as "backup" user (least privilege)
  - Replication requires trust between postgres user on primary and standby
  - Cron jobs run with specific user context (postgres, root, monitoring user)
  - Process monitoring requires understanding PID/PPID relationships
  - Signals control how you safely stop/restart PostgreSQL

COMMON MISTAKES
  - Running PostgreSQL as root (SECURITY NIGHTMARE)
  - Running backup as postgres, then trying to restore as root (permission denied)
  - Not understanding signal delivery (SIGKILL vs SIGTERM)
  - Killing parent process, expecting children to die (they don't always)
  - Not checking process owner in monitoring scripts

REAL-WORLD INCIDENT
  [2018] Backup script ran as root. After restore, all files were root-owned.
  PostgreSQL couldn't start (permission denied on data files).
  Production down 2 hours while fixing permissions.
  Lesson: Always run backups as the service user, not root.

BEST PRACTICES
  1. PostgreSQL always runs as "postgres" user (UID typically 26 on Linux)
  2. Backup scripts run as "postgres" or dedicated "backup" user
  3. Monitoring scripts can run as "postgres" or special "pgmon" user
  4. Replication scripts run as "postgres"
  5. Configuration files should be readable by postgres, not world-readable
  6. Always check process owner before sending signals
  7. Use ps -u postgres to see all PostgreSQL processes
  8. Use kill -0 <PID> to check if process exists before operating on it

SECURITY CONSIDERATIONS
  - Never run PostgreSQL as root
  - Never trust scripts that change user context (sudo, su)
  - Backup user should not have shell access
  - Monitoring user should have minimal permissions
  - Replication trust requires careful user/host validation

PERFORMANCE CONSIDERATIONS
  - Process scheduling affects query latency
  - Context switching overhead (too many processes)
  - Memory per process (work_mem, shared_buffers impact)

MONITORING CONSIDERATIONS
  - Alert if PostgreSQL process dies
  - Monitor number of PostgreSQL connections/processes
  - Track process resource usage (CPU, memory)
  - Alert on zombie processes (dead children not reaped)

TROUBLESHOOTING APPROACH
  1. Check if PostgreSQL is running: ps aux | grep postgres
  2. Find main PostgreSQL PID: pg_lsclusters or ps aux (look for "postgres -D")
  3. List all child processes: ps --ppid <main_PID>
  4. Check process owner: ps -u postgres
  5. Inspect process file descriptors: ls -l /proc/<PID>/fd
  6. Check process limits: cat /proc/<PID>/limits

EXERCISE 1.3: Process Inspection
  - Run: ps aux | grep postgres (find PostgreSQL processes)
  - Note: which process is the main postgres process? (parent)
  - Note: which are child processes? (backends, workers)
  - Run: ps -ef --forest | grep postgres (see parent/child tree)
  - Answer: What is the PID of the main postgres process?
  - Answer: How many child processes are there?
  - Answer: What user owns the processes?

EXERCISE 1.4: User Model
  - Run: id postgres (show user/group of postgres account)
  - Run: getent passwd postgres (show /etc/passwd entry)
  - Run: groups postgres (show group memberships)
  - Try: su - postgres (switch to postgres user, exit when done)
  - Answer: What is the UID/GID?
  - Answer: What is the home directory?
  - Answer: What groups is postgres in?

DAY 5-6: ENVIRONMENT VARIABLES & SHELL BASICS (DBA Context)
────────────────────────────────────────────────────────────────────────────
CONCEPT
  - Environment variables (PATH, HOME, USER, PS1, etc.)
  - Shell initialization files (.bashrc, .bash_profile, .profile)
  - Setting environment for child processes
  - Variable scope (global vs. local)
  - Special variables ($?, $0, $@, $#, etc.)

PRODUCTION RELEVANCE
  - PostgreSQL looks for PGDATA, PGVERSION, etc.
  - Backup scripts set PGPASSWORD to authenticate without prompting
  - Monitoring scripts read MONITORING_USER, ALERT_EMAIL from environment
  - Cron jobs have minimal environment (PATH may not be set)
  - Replication scripts require specific role/password env vars
  - DBA tools (psql, pg_dump) respond to PGHOST, PGPORT, PGUSER, PGPASSWORD

COMMON MISTAKES
  - Cron jobs fail because PATH is not set (can't find psql, pg_dump)
  - Scripts hardcode passwords instead of using environment
  - Not exporting variables (child processes don't inherit)
  - Assuming HOME or USER are set in cron context
  - Not understanding variable expansion ($ precedence)

REAL-WORLD INCIDENT
  [2017] Backup cron job failed silently for 30 days.
  Manual backup worked fine: pg_dump ran in shell with all variables set.
  Investigation: Cron environment is minimal; pg_dump path was not in $PATH.
  Full path required: /usr/lib/postgresql/XX/bin/pg_dump
  Lesson: Always use full paths in cron jobs. Never assume PATH.

BEST PRACTICES
  1. Always use full paths in cron jobs: /usr/bin/psql, /usr/lib/postgresql/XX/bin/*
  2. Set PGHOST, PGPORT, PGUSER explicitly (don't assume defaults)
  3. Never hardcode passwords; use .pgpass or PGPASSWORD env var
  4. Export variables in scripts that spawn child processes: export VAR=value
  5. Use ${VAR:-default} syntax to provide defaults
  6. Echo debug variables at start of script (helps troubleshooting)
  7. Set PS1 in shell startup to identify environment (dev/staging/prod)

SECURITY CONSIDERATIONS
  - Never export PGPASSWORD or other secrets in shell history
  - .pgpass should be mode 600 (readable by user only)
  - Use PGOPTIONS to set options without embedding in scripts
  - Sanitize environment variables before using in commands
  - Don't trust environment variables for authentication decisions

PERFORMANCE CONSIDERATIONS
  - Large PATH variable means slower command lookup
  - Environment size affects process startup time (usually negligible)

MONITORING CONSIDERATIONS
  - Log environment at script start for troubleshooting
  - Alert if critical variables are unset (PGHOST, PGDATA)

TROUBLESHOOTING APPROACH
  1. Run: env (see all environment variables)
  2. Run: echo $PATH (check command search path)
  3. Run: which psql (find psql location)
  4. Run: echo $PGHOST; echo $PGPORT; echo $PGUSER (check PG variables)
  5. In cron context: */1 * * * * env > /tmp/cron_env.txt (capture cron env)
  6. Compare cron env vs. interactive shell env

EXERCISE 1.5: Environment Variables
  - Run: env | grep PG (see PostgreSQL environment variables)
  - Run: echo $SHELL; echo $HOME; echo $USER
  - Run: which psql; which pg_dump
  - Answer: What is the full path to psql?
  - Answer: What environment variables does PostgreSQL use?
  - Answer: What would happen if PGHOST is not set?

EXERCISE 1.6: Shell Initialization
  - View: cat ~/.bashrc (see what's in your shell startup)
  - View: cat ~/.bash_profile
  - Add: echo "PATH=$PATH" to your .bashrc, logout/login
  - Answer: Where are bash initialization files? What order are they loaded?
  - Answer: What variables are set by default?

DAY 7-8: STANDARD I/O, PIPES & REDIRECTION (Text Processing)
────────────────────────────────────────────────────────────────────────────
CONCEPT
  - stdin (file descriptor 0)
  - stdout (file descriptor 1)
  - stderr (file descriptor 2)
  - Pipes (|) and redirection (>, >>, <, 2>&1)
  - Command substitution
  - Here documents (heredoc)

PRODUCTION RELEVANCE
  - Backup scripts log to stdout (captured in cron email)
  - Error messages go to stderr (can be separated from normal output)
  - Monitoring scripts pipe output through grep, awk, sort
  - Replication monitoring reads output of pg_stat_replication
  - Log analysis requires piping through grep, awk, sed
  - Health check scripts combine multiple command outputs

COMMON MISTAKES
  - Not separating stdout and stderr (errors mixed with normal output)
  - Not redirecting output to file (cron sends everything to email)
  - Pipe breaking on error (command fails, next pipe doesn't get input)
  - Not quoting variables with spaces in redirection
  - Not understanding file descriptor ordering (2>&1 vs 1>&2)

REAL-WORLD INCIDENT
  [2016] Health check script ran every minute, output went to cron email.
  Server's mail queue grew to 100GB in 3 days.
  Root cause: No redirection; output was emailed per run.
  Fix: Add ">> /var/log/healthcheck.log 2>&1" to cron job.
  Lesson: Always redirect output in production cron jobs.

BEST PRACTICES
  1. Always redirect stdout and stderr in cron jobs
  2. Use >> (append) for logs, not > (overwrite)
  3. Separate stdout and stderr when needed: command 2>/tmp/errors.log
  4. Pipe through tee to both display and log: command | tee -a log.txt
  5. Use heredoc for multi-line text: cat << 'EOF' ... EOF
  6. Test pipes before using in production (does data flow correctly?)
  7. Log with timestamp: command 2>&1 | while read line; do echo "$(date) $line"; done

SECURITY CONSIDERATIONS
  - Don't redirect to world-readable files (logs may contain sensitive data)
  - Don't pipe secrets through grep (leaves in process list momentarily)
  - Sanitize stderr before logging (may contain passwords from failed commands)

PERFORMANCE CONSIDERATIONS
  - Pipes create subshells (slight overhead, usually negligible)
  - Large amounts of data through pipes (memory buffering)
  - Appending to very large log files (seek time on disk)

MONITORING CONSIDERATIONS
  - Log all output for troubleshooting
  - Alert on specific patterns in stderr (FATAL, ERROR)
  - Monitor log file growth (rotation needed?)

TROUBLESHOOTING APPROACH
  1. Test command with explicit redirection: command > /tmp/test.log 2>&1
  2. Check if output is going to right place: tail /tmp/test.log
  3. Use "set -x" in script to see what's executing
  4. Verify pipes work: echo "test" | cat (should print "test")
  5. Check file permissions: ls -l on output files

EXERCISE 1.7: I/O Redirection
  - Run: echo "hello" > /tmp/test.txt (redirect stdout)
  - Run: cat /tmp/test.txt (verify it worked)
  - Run: echo "world" >> /tmp/test.txt (append)
  - Run: cat /tmp/test.txt (should have two lines)
  - Run: ls /nonexistent 2>/dev/null (suppress error)
  - Run: ls /nonexistent 2>&1 (redirect error to stdout)

EXERCISE 1.8: Pipes
  - Run: ps aux | grep postgres (pipe output to grep)
  - Run: ps aux | grep postgres | wc -l (count lines)
  - Run: echo -e "one\ntwo\nthree" | while read line; do echo "Line: $line"; done
  - Answer: How many pipes can you chain together?
  - Answer: What happens if one command in a pipe fails?

DAY 9-10: EXIT CODES & ERROR DETECTION (DBA Reliability)
────────────────────────────────────────────────────────────────────────────
CONCEPT
  - Exit codes (0 = success, 1-255 = failure)
  - $? variable (last exit code)
  - set -e (exit on error)
  - set -o pipefail (pipe failures)
  - Error handling patterns

PRODUCTION RELEVANCE
  - Backup script must exit non-zero if backup fails (alerting depends on this)
  - Replication check must return 0 only if replication is healthy
  - Monitoring scripts must signal failure to monitoring system
  - Cron job relies on exit code to determine if action succeeded
  - Incident response scripts must communicate success/failure clearly

COMMON MISTAKES
  - Not checking exit codes (script continues after failure)
  - Using "set -e" without understanding its limitations
  - Not using pipefail (first command in pipe fails silently)
  - Hardcoding exit codes (should return specific codes for specific failures)
  - Not propagating exit codes from subshells

REAL-WORLD INCIDENT
  [2020] Backup script had no error checking. Backup command failed silently.
  For 2 weeks, no valid backups existed. Recovery point objective violated.
  Root cause: Script didn't check pg_dump exit code or log errors.
  Lesson: Every critical command must be checked. Log failures. Alert ops.

BEST PRACTICES
  1. Always check exit codes: if ! command; then ... fi
  2. Use "set -e" at start of scripts (exit on error, with caveats)
  3. Use "set -o pipefail" (fail if any command in pipe fails)
  4. Exit with specific codes (0=success, 1=general error, 2=usage, etc.)
  5. Log all errors to stderr before exiting
  6. Return exit code from functions
  7. Use || to handle errors: command || { log error; exit 1; }

SECURITY CONSIDERATIONS
  - Don't ignore errors (silent failure = undetected compromise)
  - Verify command success before acting on output
  - Log failures for audit trail

PERFORMANCE CONSIDERATIONS
  - set -e and pipefail have negligible performance impact

MONITORING CONSIDERATIONS
  - Alert on non-zero exit code
  - Track exit codes in monitoring system
  - Distinguish between different failure types (code 1, 2, 3...)

TROUBLESHOOTING APPROACH
  1. Run command, check exit code: command; echo $?
  2. Add "echo $?" after each step in script during debugging
  3. Use "set -x" to see which command failed
  4. Test error conditions deliberately (delete file, disconnect network)
  5. Verify error messages are clear and actionable

EXERCISE 1.9: Exit Codes
  - Run: true; echo $? (should be 0)
  - Run: false; echo $? (should be 1)
  - Run: psql -h nonexistent -c 'select 1' 2>/dev/null; echo $?
  - Create /tmp/test_exit.sh with:

      echo "PostgreSQL not ready"
      exit 1
    fi
    echo "PostgreSQL ready"
    exit 0
  - Run: bash /tmp/test_exit.sh; echo "Exit code: $?"
  - Answer: What exit code means what? Why does it matter?

EXERCISE 1.10: set -e and pipefail
  - Create /tmp/test_set_e.sh:
    set -e
    false
    echo "This line should not print"
  - Run: bash /tmp/test_set_e.sh (should exit before echo)
  - Create /tmp/test_pipefail.sh:

    false | true
    echo "Exit: $?"
  - Answer: What does pipefail do differently?
  - Answer: When would you use set -e? When would it be dangerous?

DAY 11-12: CRON, LOGGING & SCHEDULING (Operational Foundation)
────────────────────────────────────────────────────────────────────────────
CONCEPT
  - Cron daemon and crontab format
  - Cron environment (minimal PATH, no terminal)
  - Cron output handling (email vs. log files)
  - Logging standards (timestamp, level, context)
  - Log rotation
  - Systemd timer as alternative to cron

PRODUCTION RELEVANCE
  - Backup scripts run on cron schedule (daily, hourly)
  - Replication monitoring runs every minute
  - Health checks run every 5 minutes
  - Cleanup scripts (old logs, temp files) run nightly
  - Capacity planning reports run weekly
  - Cron is the primary scheduler for DBA automation

COMMON MISTAKES
  - Cron jobs failing due to missing PATH
  - Cron output sent to email (mail queue grows)
  - No logging (can't debug issues)
  - Overlapping cron jobs (two instances running simultaneously)
  - Not using full paths (script can't find psql, pg_dump)
  - Not setting PGHOST, PGPORT explicitly
  - Cron jobs without timeout (can hang indefinitely)

REAL-WORLD INCIDENT
  [2021] Backup cron ran every 2 hours. One run took 4 hours.
  Next run started before first finished. Both locked database.
  Production unresponsive for 1 hour.
  Fix: Add flock/lock file to prevent concurrent runs.
  Lesson: Production cron jobs need lock files, timeouts, explicit environment.

BEST PRACTICES
  1. Always use full paths: /usr/lib/postgresql/XX/bin/psql
  2. Set environment explicitly: PGHOST, PGPORT, PGUSER, PGPASSWORD
  3. Redirect output to log file, never to email: >> /var/log/backup.log 2>&1
  4. Add lock file to prevent concurrent runs: flock -n /var/run/backup.lock
  5. Add timeout: timeout 3600 command (kill if >1 hour)
  6. Log with timestamp at start/end
  7. Check exit code and log it
  8. Rotate logs regularly (logrotate or manual script)
  9. Keep cron logs in /var/log/cron or application-specific logs
  10. Test cron job manually before deploying: bash -x script.sh

SECURITY CONSIDERATIONS
  - Cron job runs with user's privileges (use postgres user)
  - Output may contain sensitive data (log permissions: mode 600)
  - .pgpass must be mode 600
  - crontab readable only by owner and root

PERFORMANCE CONSIDERATIONS
  - Cron job scheduling affects database load (don't run all at once)
  - Long-running jobs should have timeout
  - Overlapping jobs can cause lock contention

MONITORING CONSIDERATIONS
  - Alert if cron job doesn't run (systemd timer or monitoring)
  - Alert if cron job takes too long
  - Monitor cron log for errors: grep CRON /var/log/syslog
  - Alert on exit code != 0

TROUBLESHOOTING APPROACH
  1. Check cron logs: grep CRON /var/log/syslog or /var/log/cron
  2. Test cron environment: env -i /bin/sh -c 'command' (minimal env)
  3. Test cron job manually: bash /path/to/script.sh
  4. Check if cron daemon is running: ps aux | grep cron
  5. Verify crontab: crontab -l (for current user) or crontab -u postgres -l
  6. Check mail queue: mailq (if output is being emailed)
  7. Test with explicit environment: PGHOST=localhost /path/to/script.sh

EXERCISE 1.11: Cron Basics
  - View: crontab -l (see your current cron jobs)
  - View: sudo crontab -u postgres -l (see postgres user's cron jobs)
  - Create test script /tmp/cron_test.sh:
    #!/bin/bash
    echo "Cron test ran at $(date)" >> /tmp/cron_test.log
  - Run: chmod +x /tmp/cron_test.sh

  - Wait 1 minute, check: tail /tmp/cron_test.log
  - Answer: Did it run? What time was it?
  - Answer: What is the cron environment? (compare to your shell env)

EXERCISE 1.12: Logging Standards
  - Create /tmp/backup_test.sh:
    #!/bin/bash
    LOG="/var/log/backup_test.log"
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] Backup started" >> "$LOG"

  - Check: cat /var/log/backup_test.log
  - Answer: What information should be in a production log?
  - Answer: How would you format timestamps for easy parsing?

DAY 13-14: INTRODUCTION TO POSTGRESQL OPERATIONS (Context)
────────────────────────────────────────────────────────────────────────────
CONCEPT
  - PostgreSQL architecture (processes, memory, files)
  - Data directory structure
  - Connection model (user/database/role authentication)
  - pg_isready, psql connection strings
  - Basic health checks

PRODUCTION RELEVANCE
  - DBA automation focuses on backing up, monitoring, replicating PostgreSQL
  - Must understand what PostgreSQL looks like at OS level
  - Must know how to connect and run queries from shell
  - Must understand data directory layout
  - Incident response requires quick health assessment

COMMON MISTAKES
  - Assuming PostgreSQL is running when it's not (check pg_isready)
  - Not understanding connection failures (host/port/user wrong)
  - Hardcoding credentials instead of using .pgpass
  - Not understanding role/user model (pg roles != OS users)
  - Not knowing what postgresql.conf controls

REAL-WORLD INCIDENT
  [2015] Script tried to connect to PostgreSQL, failed silently (no error checking).
  Automation ran blindly for hours while database was down.
  Root cause: pg_isready check was commented out during testing.
  Lesson: Always verify PostgreSQL is running before operating on it.

BEST PRACTICES
  1. Always start scripts with pg_isready check
  2. Use connection strings: psql -h host -U user -d database
  3. Never hardcode credentials; use .pgpass or environment
  4. Understand PGHOST, PGPORT, PGUSER, PGPASSWORD (order of precedence)
  5. Know the data directory layout (pg_wal, pg_data, pg_log)
  6. Understand tablespace concept (where data lives on disk)
  7. Check pg_catalog.pg_database for critical metadata

SECURITY CONSIDERATIONS
  - Never pass password on command line (use .pgpass)
  - Don't log connection strings (may contain passwords)
  - Understand role-based access control (GRANT/REVOKE)
  - SSL/TLS encryption for remote connections

PERFORMANCE CONSIDERATIONS
  - Connection pooling for high-frequency connections
  - Idle connections waste memory
  - Connection limits (max_connections) must be planned

MONITORING CONSIDERATIONS
  - Alert if PostgreSQL is down (pg_isready)
  - Monitor active connections
  - Monitor long-running queries
  - Track connection count trends

TROUBLESHOOTING APPROACH
  1. Check if PostgreSQL is running: pg_isready -h localhost -p 5432
  2. Check listen address: grep "^listen_addresses" postgresql.conf
  3. Check connection limits: psql -c "show max_connections"
  4. List active connections: psql -c "select * from pg_stat_activity"
  5. Check roles: psql -c "\du"
  6. Check databases: psql -c "\l"

EXERCISE 1.13: PostgreSQL Basics
  - Run: pg_isready -h localhost -p 5432 -U postgres

DAY 15-16: VARIABLES & PARAMETER EXPANSION
────────────────────────────────────────────────────────────────────────────
CONCEPT
  - Variable assignment (VAR=value, VAR="value with spaces")
  - Parameter expansion ($VAR, ${VAR})
  - Default values (${VAR:-default})
  - String length (${#VAR})
  - Substring (${VAR:offset:length})
  - Pattern substitution (${VAR//pattern/replace})
  - Quoting rules (single vs double quotes)

PRODUCTION RELEVANCE
  - Configuration values stored in variables
  - Database names, hostnames, ports from environment
  - Backup paths constructed dynamically
  - Error messages with embedded variables
  - Parsing command output into variables

COMMON MISTAKES
  - Not quoting variables with spaces: echo $VAR (breaks if spaces)
  - Using single quotes when variable expansion needed
  - Not using ${VAR} syntax (looks like $VARIABLE1, means VAR then 1)
  - Assuming variables persist across pipes (subshell isolation)
  - Not initializing variables (undefined = empty string)

REAL-WORLD INCIDENT
  [2014] Script had BACKUP_PATH=$BASE_PATH/$DB_NAME
  DB_NAME had space: "Production DB"
  Result: BACKUP_PATH became two separate paths in subsequent commands.
  Backup created in wrong directory, unnoticed for days.
  Fix: Always quote: BACKUP_PATH="$BASE_PATH/$DB_NAME"
  Lesson: Quote all variables. Always. No exceptions.

BEST PRACTICES
  1. Always quote variables: "${VAR}", not $VAR
  2. Use lowercase for local variables, UPPERCASE for constants
  3. Initialize variables at start: VAR=""
  4. Use ${VAR:-default} for optional values
  5. Use ${VAR:?error message} to assert variables are set
  6. Use ${VAR/old/new} for string replacement
  7. Never use eval
  8. Document variable purpose in comments

SECURITY CONSIDERATIONS
  - Don't store passwords in variables (use environment/files)
  - Sanitize variables used in commands (avoid injection)
  - Don't expose variables in process list (ps aux)

PERFORMANCE CONSIDERATIONS
  - Variable lookup is O(1) (negligible)
  - String expansion can be slow on large strings (rarely an issue)

MONITORING CONSIDERATIONS
  - Log key variables at script start (helps troubleshooting)

TROUBLESHOOTING APPROACH
  1. Use "set -x" to see variable expansion
  2. Add "echo" statements to print variables at checkpoints
  3. Use "${VAR}" and check if it's empty: [ -z "${VAR}" ]

DAY 17-18: CONDITIONALS & TESTING
────────────────────────────────────────────────────────────────────────────
CONCEPT
  - if/then/else/elif
  - Test operators: [ ], [[ ]] (preferred in Bash)
  - File tests: -f, -d, -r, -w, -x
  - String tests: =, !=, -z (empty), -n (not empty)
  - Numeric tests: -eq, -ne, -lt, -le, -gt, -ge
  - Boolean operators: &&, ||, !

PRODUCTION RELEVANCE
  - Check if file exists before operating on it
  - Check if PostgreSQL is running before backup
  - Check if variable is empty before using it
  - Conditional logic in monitoring (alert if threshold exceeded)
  - Error handling based on exit codes

COMMON MISTAKES
  - Using [ ] in Bash (POSIX, less capable; use [[ ]])
  - Not quoting variables in tests: [ $VAR = "value" ] fails if $VAR empty
  - Confusing = and == (both work, but -eq for numbers)
  - Not using -f, -d, -r tests (assume file exists)
  - Forgetting spaces around operators: [$VAR="value"] is invalid

REAL-WORLD INCIDENT
  [2019] Script tested if file exists: if [ -f $BACKUP_FILE ]; then
  BACKUP_FILE was empty (variable unset).
  Condition evaluated true (no file to delete).
  Script tried to delete root directory (wildcard expansion).
  Lesson: Always quote variables. Always use file tests. Always check assumptions.

BEST PRACTICES
  1. Use [[ ]] instead of [ ] (more capable, safer)
  2. Always quote variables: [[ -f "${FILE}" ]]
  3. Use -f for files, -d for directories
  4. Use -r, -w, -x for permission checks
  5. Use -z for empty, -n for non-empty strings
  6. Use -eq, -ne, -lt, etc. for numeric comparisons
  7. Combine conditions with && and ||
  8. Use early return pattern: if ! condition; then return 1; fi
  9. Indent logic clearly (makes bugs obvious)

SECURITY CONSIDERATIONS
  - Don't trust user input in conditions (inject defensive checks)
  - Use -r for permission checks (file readable before using)

PERFORMANCE CONSIDERATIONS
  - [[ ]] is slightly slower than [ ] (usually negligible)
  - File tests cause stat() syscalls (expensive on network filesystems)

MONITORING CONSIDERATIONS
  - Log the condition that failed (helps troubleshooting)

TROUBLESHOOTING APPROACH
  1. Add "set -x" to see which branch is taken
  2. Test condition manually: [[ -f /path/to/file ]] && echo "Exists"
  3. Check variable: echo "VAR=$VAR" before using in condition

DAY 19-20: LOOPS (for, while, until)
────────────────────────────────────────────────────────────────────────────
CONCEPT
  - for loop (iterate over list, C-style loop)
  - while loop (while condition true)
  - until loop (until condition true)
  - break and continue
  - Loop variable scope

PRODUCTION RELEVANCE
  - Process multiple databases
  - Iterate over list of hosts (primary, standby, replica)
  - Process lines from query output
  - Retry logic (loop until success or max attempts)
  - Batch operations (process files in /var/backups)

COMMON MISTAKES
  - Not quoting variables in for loop: for file in $list (globbing issue)
  - Assuming loop variables survive outside loop (they don't in subshells)
  - Infinite loops without timeout mechanism
  - Not tracking iteration count (retry logic fails)
  - Modifying list while iterating (undefined behavior)

REAL-WORLD INCIDENT
  [2018] Script iterated over databases from query output.
  Query output was piped to while loop (subshell).
  Loop modified variables. After loop, variables were empty.
  Script continued with undefined behavior (deleted wrong data).
  Lesson: Understand subshell scope. Use process substitution or readarray.

BEST PRACTICES
  1. Use for loop with quoted list: for db in "${DATABASES[@]}"
  2. Use while read for line-by-line input: while read line; do ... done
  3. Use process substitution to avoid subshells: while read line; do ... done < <(cmd)
  4. Or use readarray: readarray -t LINES < <(cmd)
  5. Add timeout to while loops: MAX_ATTEMPTS=10; ATTEMPT=0; while ...
  6. Log iteration progress for debugging
  7. Break early if operation succeeds

SECURITY CONSIDERATIONS
  - Be careful with word splitting in loops (sanitize input)
  - Don't iterate over untrusted lists

PERFORMANCE CONSIDERATIONS
  - for loop with glob expansion can be slow (10k+ files)
  - while read is slower than pure Bash loops (spawns processes)
  - Use process substitution to avoid subshells

MONITORING CONSIDERATIONS
  - Log progress at each iteration (helps identify which item fails)
  - Alert if loop takes too long (timeout mechanism)

TROUBLESHOOTING APPROACH
  1. Add echo at each iteration: echo "Processing: $ITEM"
  2. Use "set -x" to see loop execution
  3. Test loop logic in isolation

CONCEPT

PRODUCTION RELEVANCE

  - Exit codes guide monitoring/alerting

COMMON MISTAKES

  6. Return specific exit codes (1=general, 2=usage, etc.)
  7. Document error codes in comments

  - Sanitize before using in commands
  - Don't trust user input

PERFORMANCE CONSIDERATIONS
  - Validation overhead is negligible

MONITORING CONSIDERATIONS

  - Alert on specific error patterns

TROUBLESHOOTING APPROACH

────────────────────────────────────────────────────────────────────────────
CONCEPT
  - set -x for debugging (shell expansion tracing)
  - Arithmetic expansion: $((expression))
  - Pattern matching and regex
  - Brace expansion: {1..10}, {a,b,c}
  - Ternary operator: ${VAR:+value_if_set}

PRODUCTION RELEVANCE
  - Debugging script logic
  - Performing calculations (connection counts, disk usage)
  - Pattern matching in log analysis
  - Shorthand for many-item operations

COMMON MISTAKES
  - set -x left on in production (reveals sensitive info)
  - Arithmetic without $(( )) (interpreted as string)
  - Not understanding precedence in arithmetic
  - Regex without proper escaping
  - Brace expansion with variables (doesn't expand $VAR)

REAL-WORLD INCIDENT
  [2020] Performance monitoring script ran with set -x accidentally left on.
  Script processed PGPASSWORD and other secrets.
  set -x logged everything to stderr, which was piped to log file.
  Secrets exposed in plaintext logs.
  Lesson: Never commit set -x to production. Use controlled debugging.

BEST PRACTICES
  1. Use set -x only for debugging, wrap in conditional: [[ "${DEBUG:-0}" == "1" ]]
  2. Disable set -x in production: [[ "${DEBUG:-0}" == "1" ]] && set -x
  3. Use arithmetic for calculations: RESULT=$((a + b))
  4. Use pattern matching for simple cases: [[ "$VAR" =~ pattern ]]
  5. Document regex patterns (they're hard to read)
  6. Use ${VAR:+value} for conditional expansion
  7. Use ${VAR:=default} to set default if unset

SECURITY CONSIDERATIONS
  - Never enable set -x in production (logs secrets)
  - Sanitize regex input (don't use user input directly)

PERFORMANCE CONSIDERATIONS
  - set -x has negligible overhead (only active during debugging)
  - Arithmetic is fast (native Bash)

MONITORING CONSIDERATIONS
  - Log debug information separately from production logs

TROUBLESHOOTING APPROACH
  1. Enable DEBUG=1 to activate set -x conditionally
  2. Use set -x before problem area, set +x after
  3. Test regex patterns separately

    #!/bin/bash
    
    ################################################################################
    # PURPOSE: Template for DBA automation scripts
    # USAGE: ./script.sh [-c config_file] [-v verbose] database_name
    # AUTHOR: DBA Team
    # DATE: 2024-12-17
    ################################################################################
    
    set -euo pipefail
    
    # Configuration
    CONFIG_FILE="${CONFIG_FILE:-./.dba_config}"
    SCRIPT_NAME=$(basename "$0")
    SCRIPT_DIR=$(dirname "$(readlink -f "$0")")
    LOG_DIR="${LOG_DIR:-/var/log/dba}"
    LOG_FILE="${LOG_DIR}/${SCRIPT_NAME%.sh}.log"
    
    ################################################################################
    # LOGGING
    ################################################################################
    
    log() {
      local level="$1"
      shift
      local message="$*"
      echo "[$(date '+%Y-%m-%d %H:%M:%S')] [$level] $message" | tee -a "$LOG_FILE"
    }
    
    log_info() { log "INFO" "$@"; }
    log_error() { log "ERROR" "$@" >&2; }
    log_warn() { log "WARN" "$@"; }
    
    ################################################################################
    # FUNCTIONS
    ################################################################################
    
    usage() {
      cat << EOF
    Usage: $SCRIPT_NAME [OPTIONS] database_name
    
    OPTIONS:
      -c FILE    Configuration file (default: $CONFIG_FILE)
      -v         Verbose output (enable set -x)
      -h         Show this help message
    
    EXAMPLES:
      $SCRIPT_NAME testdb
      $SCRIPT_NAME -c /etc/dba.conf proddb
    EOF
    }
    
    cleanup() {
      local exit_code=$?
      log_info "Script exiting with code $exit_code"
      return $exit_code
    }
    
    main() {
      log_info "Script started by $(whoami)"
      
      [[ $# -eq 0 ]] && { usage; exit 2; }
      
      local dbname="$1"
      log_info "Operating on database: $dbname"
      
      # TODO: Add logic here
      
      log_info "Script completed successfully"
    }
    
    ################################################################################
    # INITIALIZATION
    ################################################################################
    
    trap cleanup EXIT
    
    mkdir -p "$LOG_DIR"
    
    # Parse options
    while getopts "c:vh" opt; do
      case $opt in
        c) CONFIG_FILE="$OPTARG" ;;
        v) set -x ;;
        h) usage; exit 0 ;;
        *) usage; exit 2 ;;
      esac
    done
    shift $((OPTIND - 1))
    
    main "$@"
