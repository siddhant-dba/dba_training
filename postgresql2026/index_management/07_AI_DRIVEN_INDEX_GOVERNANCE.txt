================================================================================
FIRST, LET'S TALK ABOUT THE ARCHITECTURE
================================================================================

Before I get into the SQL and the code, I want you to picture the whole system in your head. Because today we're building something bigger than a single query or script.

Here's the architecture:

Layer 1 — Data Collection
    Your PostgreSQL database generates statistics continuously. pg_stat_user_indexes, pg_stat_user_tables, pg_stat_statements. We've captured these before. This layer is the raw ingredient.

Layer 2 — Structured Reporting
    We take that raw data and shape it into a structured JSON document. Not a text file, not a CSV, not a pretty HTML report. A JSON document with a well-defined schema. Why JSON? Because AI models and APIs consume JSON extremely well. It's the lingua franca of modern data exchange.

Layer 3 — AI Analysis
    We send the JSON document to an AI model (I'll show you how to do this via API call from bash) and ask it to analyze the indexes. We use a carefully crafted prompt that gives the AI context about PostgreSQL, your specific database, and what we want it to evaluate. It returns a structured recommendation.

Layer 4 — Decision Engine
    The AI recommendation gets processed by a rules-based decision engine we build ourselves. This is not just "do what the AI says." This engine has our own business rules, confidence thresholds, and safety gates. It produces a validated action list.

Layer 5 — Human Review
    The action list goes to a DBA for review. Not everything, just the things the engine flags for human judgment. High-confidence, low-risk items can proceed automatically. Medium-confidence items need a DBA to sign off. Low-confidence items get flagged for deeper investigation.

Layer 6 — Execution and Audit
    Approved actions execute against the database using scripts we control. Every action is logged to our audit table. Results are measured and fed back into the data collection layer for the next cycle.

That's six layers. And today we're building all of them.

================================================================================
LAYER 2: BUILDING THE JSON REPORT
================================================================================

This is where things start to get different from what you've done before.

You're not generating a text report for a human to read. You're generating a structured JSON document that an AI model will consume. The structure matters enormously. Think of it as writing a data contract between your database analysis layer and your AI analysis layer.

I want you to understand something about how AI models work. They're pattern matchers trained on enormous amounts of text. They understand structured data very well — especially JSON. When you give an AI model a well-structured JSON payload, it can reason about it almost like a human DBA would, but in seconds.

But if your JSON is poorly structured, ambiguous, or missing key context, the AI will fill in gaps with guesses. And those guesses can be confidently wrong. So we're going to define a clear, rich JSON schema.

Here's the schema I've developed and refined over the last couple of years. I'll break it down piece by piece.

Good. Now the core piece — the JSON report generation function. This is a PostgreSQL function that queries all the relevant system views and compiles them into a structured JSON document.

---

CREATE OR REPLACE FUNCTION dba_governance.generate_index_report(
    p_schema TEXT DEFAULT NULL,
    p_table  TEXT DEFAULT NULL
)
RETURNS JSONB
LANGUAGE plpgsql
AS $$
DECLARE
    v_report JSONB;
    v_snapshot_id BIGINT;
BEGIN

    -- First, capture a snapshot for historical tracking
    INSERT INTO dba_governance.index_snapshots
        (snapshot_date, db_name, schemaname, tablename, indexname,
         index_def, index_type, is_unique, is_primary,
         index_size_bytes, table_size_bytes,
         idx_scan, idx_tup_read, idx_tup_fetch,
         table_n_ins, table_n_upd, table_n_del, table_n_live)
    SELECT
        CURRENT_DATE,
        current_database(),
        i.schemaname,
        i.tablename,
        i.indexname,
        pg_get_indexdef(i.indexrelid),
        am.amname,
        ix.indisunique,
        ix.indisprimary,
        pg_relation_size(i.indexrelid),
        pg_relation_size(t.oid),
        i.idx_scan,
        i.idx_tup_read,
        i.idx_tup_fetch,
        t.n_tup_ins,
        t.n_tup_upd,
        t.n_tup_del,
        t.n_live_tup
    FROM
        pg_stat_user_indexes i
        JOIN pg_stat_user_tables t ON i.tablename = t.relname
            AND i.schemaname = t.schemaname
        JOIN pg_index ix ON ix.indexrelid = i.indexrelid
        JOIN pg_class c ON c.oid = i.indexrelid
        JOIN pg_am am ON am.oid = c.relam
    WHERE
        i.schemaname NOT IN ('pg_catalog', 'information_schema', 'dba_governance')
        AND (p_schema IS NULL OR i.schemaname = p_schema)
        AND (p_table IS NULL OR i.tablename = p_table);

    -- Now build the JSON report
    SELECT
        jsonb_build_object(
            'report_metadata', jsonb_build_object(
                'generated_at',     NOW()::TEXT,
                'report_date',      CURRENT_DATE::TEXT,
                'database_name',    current_database(),
                'db_version',       version(),
                'schema_filter',    COALESCE(p_schema, 'all'),
                'table_filter',     COALESCE(p_table, 'all'),
                'report_type',      'index_governance_analysis',
                'format_version',   '2.1'
            ),

            'database_summary', jsonb_build_object(
                'total_indexes',       COUNT(*),
                'total_index_storage', pg_size_pretty(SUM(pg_relation_size(i.indexrelid))),
                'total_index_bytes',   SUM(pg_relation_size(i.indexrelid)),
                'unused_index_count',  SUM(CASE WHEN i.idx_scan = 0 THEN 1 ELSE 0 END),
                'unused_index_bytes',  SUM(CASE WHEN i.idx_scan = 0 THEN pg_relation_size(i.indexrelid) ELSE 0 END),
                'tables_analyzed',     COUNT(DISTINCT i.tablename),
                'heavily_modified_tables',
                    (SELECT jsonb_agg(tbl)
                     FROM (
                         SELECT relname AS tbl
                         FROM pg_stat_user_tables
                         WHERE n_tup_ins + n_tup_upd + n_tup_del > 10000
                         AND schemaname NOT IN ('pg_catalog','information_schema','dba_governance')
                         ORDER BY n_tup_ins + n_tup_upd + n_tup_del DESC
                         LIMIT 5
                     ) h)
            ),

            'indexes', jsonb_agg(
                jsonb_build_object(
                    'index_identity', jsonb_build_object(
                        'schema',           i.schemaname,
                        'table',            i.tablename,
                        'index_name',       i.indexname,
                        'index_type',       am.amname,
                        'is_unique',        ix.indisunique,
                        'is_primary_key',   ix.indisprimary,
                        'full_definition',  pg_get_indexdef(i.indexrelid)
                    ),
                    'size_metrics', jsonb_build_object(
                        'index_size_bytes', pg_relation_size(i.indexrelid),
                        'index_size_human', pg_size_pretty(pg_relation_size(i.indexrelid)),
                        'table_size_bytes', pg_relation_size(t.oid),
                        'table_size_human', pg_size_pretty(pg_relation_size(t.oid)),
                        'size_ratio',       ROUND(
                            (pg_relation_size(i.indexrelid)::FLOAT /
                             NULLIF(pg_relation_size(t.oid), 0))::NUMERIC, 4
                        )
                    ),
                    'usage_metrics', jsonb_build_object(
                        'idx_scan',         i.idx_scan,
                        'idx_tup_read',     i.idx_tup_read,
                        'idx_tup_fetch',    i.idx_tup_fetch,
                        'read_fetch_ratio', CASE
                            WHEN i.idx_tup_fetch = 0 THEN NULL
                            ELSE ROUND((i.idx_tup_read::FLOAT /
                                        NULLIF(i.idx_tup_fetch, 0))::NUMERIC, 2)
                        END,
                        'scans_per_day_estimate', CASE
                            WHEN s.stats_reset IS NULL THEN NULL
                            ELSE ROUND((i.idx_scan::FLOAT /
                                GREATEST(EXTRACT(EPOCH FROM (NOW() - s.stats_reset)) / 86400, 1)
                            )::NUMERIC, 2)
                        END
                    ),
                    'write_load', jsonb_build_object(
                        'table_inserts',        t.n_tup_ins,
                        'table_updates',        t.n_tup_upd,
                        'table_deletes',        t.n_tup_del,
                        'total_modifications',  t.n_tup_ins + t.n_tup_upd + t.n_tup_del,
                        'live_rows',            t.n_live_tup,
                        'mods_per_scan',        CASE
                            WHEN i.idx_scan = 0 THEN NULL
                            ELSE ROUND(
                                ((t.n_tup_ins + t.n_tup_upd + t.n_tup_del)::FLOAT /
                                 NULLIF(i.idx_scan, 0))::NUMERIC, 2
                            )
                        END
                    ),
                    'health_indicators', jsonb_build_object(
                        'is_unused',        i.idx_scan = 0,
                        'is_low_use',       i.idx_scan BETWEEN 1 AND 10,
                        'fragmentation_risk', CASE
                            WHEN (pg_relation_size(i.indexrelid)::FLOAT /
                                  NULLIF(pg_relation_size(t.oid), 0)) > 2.0 THEN 'HIGH'
                            WHEN (pg_relation_size(i.indexrelid)::FLOAT /
                                  NULLIF(pg_relation_size(t.oid), 0)) > 1.5 THEN 'MEDIUM'
                            ELSE 'LOW'
                        END,
                        'high_write_low_read', (
                            (t.n_tup_ins + t.n_tup_upd + t.n_tup_del) > 10000
                            AND i.idx_scan < 50
                        )
                    ),
                    'history', jsonb_build_object(
                        'prior_week_scans', (
                            SELECT s2.idx_scan
                            FROM dba_governance.index_snapshots s2
                            WHERE s2.indexname = i.indexname
                            AND s2.tablename = i.tablename
                            AND s2.snapshot_date = CURRENT_DATE - 7
                            LIMIT 1
                        ),
                        'prior_month_scans', (
                            SELECT s2.idx_scan
                            FROM dba_governance.index_snapshots s2
                            WHERE s2.indexname = i.indexname
                            AND s2.tablename = i.tablename
                            AND s2.snapshot_date = CURRENT_DATE - 30
                            LIMIT 1
                        ),
                        'weeks_captured', (
                            SELECT COUNT(DISTINCT snapshot_date)
                            FROM dba_governance.index_snapshots s2
                            WHERE s2.indexname = i.indexname
                            AND s2.tablename = i.tablename
                        )
                    )
                )
                ORDER BY pg_relation_size(i.indexrelid) DESC
            )
        ) INTO v_report
    FROM
        pg_stat_user_indexes i
        JOIN pg_stat_user_tables t ON i.tablename = t.relname
            AND i.schemaname = t.schemaname
        JOIN pg_index ix ON ix.indexrelid = i.indexrelid
        JOIN pg_class c ON c.oid = i.indexrelid
        JOIN pg_am am ON am.oid = c.relam
        LEFT JOIN pg_stat_bgwriter s ON TRUE
    WHERE
        i.schemaname NOT IN ('pg_catalog', 'information_schema', 'dba_governance')
        AND (p_schema IS NULL OR i.schemaname = p_schema)
        AND (p_table IS NULL OR i.tablename = p_table);

    RETURN v_report;

END;
$$;

---

Let me walk through what this function does, because there's a lot going on.

It takes two optional parameters: schema name and table name. If you pass NULL for both, it analyzes the entire database. That's what you usually want for a full governance report. But you can narrow it to a specific schema or table when you're doing focused work.

First, it inserts a snapshot into our `index_snapshots` table. Remember from Phase 6 — we talked about persisting statistics before they get reset on a restart. This function does that automatically every time it runs.

Then it builds the JSON report. The structure has four top-level keys:

`report_metadata` — Context about when the report was generated, which database, which version. The AI model needs this to contextualize its recommendations. A recommendation that's valid on PostgreSQL 14 might differ on PostgreSQL 16.

`database_summary` — High-level numbers: total indexes, total storage, how many are unused, which tables are heavily modified. This gives the AI a "30,000-foot view" before it dives into details.

`indexes` — This is the main payload. An array of index objects, each with five nested objects: identity, size metrics, usage metrics, write load, and health indicators. Rich, structured, everything the AI needs to make a decision.

`history` — Historical scan counts from prior snapshots. This is critically important because it transforms the analysis from a snapshot into a trend. A zero-scan index from yesterday could have been a hundred-scans-per-day index two weeks ago, and the stats reset because of a restart. History protects you from that false positive.

================================================================================
LAYER 3: THE AI ANALYSIS — PROMPT ENGINEERING FOR DBAS
================================================================================

Now we get to the part that most people find mysterious. How do you actually talk to an AI model? What do you say? How do you get back something useful instead of vague generalities?

The answer is prompt engineering. And I'm going to demystify it for you.

A prompt to an AI model is just a set of instructions plus context. It's not magic. It's communication. You're telling the model who it is, what it knows, what you want it to do, and what format you want back.

Good prompts have four components:

1. **Role definition**: "You are a PostgreSQL DBA expert..." This sets the model's frame of reference.
2. **Context**: The data you're providing, plus any background the model needs to interpret it.
3. **Task specification**: Exactly what you want it to do, in precise terms.
4. **Output format**: What you want back, in what structure.

Let me show you the prompt template I've developed. This is real. This is what I use.

I want to pause here and explain why this prompt is built the way it is.

The system prompt tells the AI its identity. Notice I'm not vague. I'm not saying "you're a database expert." I'm listing specific PostgreSQL concepts — pg_stat_user_indexes, REINDEX CONCURRENTLY, fill factor, left-prefix rules. This activates the model's specific PostgreSQL knowledge base rather than generic database knowledge.

The rules section is the most important part. These are my business rules — my decades of experience encoded as constraints. Rule 2 is critical: never recommend DROP if we have fewer than 2 weeks of history. Because if a DBA restarted PostgreSQL last week, all scan counts are zero. Blindly dropping everything with zero scans based on one snapshot is a disaster. I learned that the hard way. Rule 1 is obvious once you've worked in production — drop a unique index and your application starts accepting duplicate data. Not good.

The confidence scoring guide calibrates the model's scoring to my risk framework. Anything 95-100 can be auto-executed. Anything 70-84 needs my sign-off.

The output format is rigid and precise. I want JSON back, nothing else, with specific field names. This makes it easy to parse programmatically.

I'm not exaggerating. Let me tell you what happened to a DBA team I know. They built an AI-driven automation system very similar to what we're building today. But they didn't build the human-in-the-loop layer properly. They set the auto-execution threshold at 70% confidence and walked away.

The AI analyzed a database that had recently been migrated. A bunch of indexes had been rebuilt during migration. The stats were fresh — scan counts were low across the board. The AI confidently recommended dropping 30 indexes with 70-80% confidence scores.

The automation executed 26 of them overnight.

By 9 AM, the application was throwing errors. Queries that had relied on those indexes were timing out. They weren't unused — they were just new, post-migration, and hadn't accumulated scan counts yet. The AI didn't know about the migration context. It only knew what the numbers said.

The DBA team spent two days recreating indexes and explaining to the business why their platform was degraded.

Here is what I want you to remember about this story: **the AI did exactly what it was told. The failure was in the design of the governance system — specifically the absence of proper human oversight thresholds.**

In our system, the rules are:
- Confidence >= 95, risk = LOW: Auto-execution is permitted, but we still log and notify
- Confidence 85-94, risk = LOW/MEDIUM: Requires DBA sign-off in the workflow table
- Confidence < 85 OR risk = HIGH: Full human review before any action
- Zero-scan indexes with history < 2 weeks: MONITOR only, no action

Now let's look at how to actually call an AI API from bash and feed it our JSON report. I'm going to use the Anthropic API as an example since that's what's accessible to you, but this pattern works with any REST-based AI API.

---

#!/bin/bash

#=============================================================================
# ai_index_analyzer.sh
# Calls an AI model with our index governance JSON report
# and returns structured recommendations
#=============================================================================

set -euo pipefail

# Configuration
readonly DB_HOST="${DB_HOST:-localhost}"
readonly DB_PORT="${DB_PORT:-5432}"
readonly DB_USER="${DB_USER:-postgres}"
readonly DB_NAME="${DB_NAME:-production}"
readonly DB_SCHEMA="${DB_SCHEMA:-public}"
readonly AI_API_KEY="${ANTHROPIC_API_KEY:?ERROR: ANTHROPIC_API_KEY not set}"
readonly AI_MODEL="claude-sonnet-4-6"
readonly AI_API_URL="https://api.anthropic.com/v1/messages"
readonly WORK_DIR="/tmp/dba_governance"
readonly TIMESTAMP=$(date +%Y%m%d_%H%M%S)
readonly REPORT_JSON_FILE="${WORK_DIR}/report_${TIMESTAMP}.json"
readonly AI_RESPONSE_FILE="${WORK_DIR}/ai_response_${TIMESTAMP}.json"
readonly LOG_FILE="${WORK_DIR}/ai_analyzer_${TIMESTAMP}.log"

PSQL="psql -h ${DB_HOST} -p ${DB_PORT} -U ${DB_USER} -d ${DB_NAME}"

#=============================================================================
# LOGGING
#=============================================================================

log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "${LOG_FILE}"; }
die() { echo "[FATAL] $*" >&2; exit 1; }

#=============================================================================
# STEP 1: GENERATE THE JSON REPORT
#=============================================================================

generate_report() {
    log "Generating index report for schema: ${DB_SCHEMA}..."

    mkdir -p "${WORK_DIR}"

    ${PSQL} -t -c \
        "SELECT dba_governance.generate_index_report('${DB_SCHEMA}')" \
        > "${REPORT_JSON_FILE}" \
        2>> "${LOG_FILE}" \
        || die "Failed to generate index report from PostgreSQL"

    # Validate the JSON is non-empty
    if [[ ! -s "${REPORT_JSON_FILE}" ]]; then
        die "Report JSON is empty — check database connection and permissions"
    fi

    local INDEX_COUNT
    INDEX_COUNT=$(python3 -c "
import json, sys
d = json.load(open('${REPORT_JSON_FILE}'))
print(len(d.get('indexes', [])))
" 2>/dev/null || echo "0")

    log "Report generated. Indexes found: ${INDEX_COUNT}"
    [[ ${INDEX_COUNT} -gt 0 ]] || die "No indexes found in report"
}

#=============================================================================
# STEP 2: LOAD THE PROMPT FROM DATABASE
#=============================================================================

load_prompt() {
    log "Loading AI prompt template (v2.1)..."

    SYSTEM_PROMPT=$(${PSQL} -t -A -c \
        "SELECT system_prompt FROM dba_governance.ai_prompts
         WHERE prompt_version = 'v2.1' AND is_active = TRUE LIMIT 1" \
        2>> "${LOG_FILE}") \
        || die "Failed to load system prompt"

    USER_PROMPT_TEMPLATE=$(${PSQL} -t -A -c \
        "SELECT user_prompt_template FROM dba_governance.ai_prompts
         WHERE prompt_version = 'v2.1' AND is_active = TRUE LIMIT 1" \
        2>> "${LOG_FILE}") \
        || die "Failed to load user prompt template"

    log "Prompt template loaded (version v2.1)"
}

#=============================================================================
# STEP 3: BUILD THE REQUEST PAYLOAD
#=============================================================================

build_request() {
    log "Building API request payload..."

    local REPORT_CONTENT
    REPORT_CONTENT=$(cat "${REPORT_JSON_FILE}")

    # Substitute the report JSON into the user prompt template
    local USER_PROMPT
    USER_PROMPT="${USER_PROMPT_TEMPLATE/\{\{REPORT_JSON\}\}/${REPORT_CONTENT}}"

    # Build the JSON payload for the API
    python3 - <<PYEOF
import json, sys

system_prompt = """${SYSTEM_PROMPT}"""
user_prompt   = """${USER_PROMPT}"""

payload = {
    "model":      "${AI_MODEL}",
    "max_tokens": 8000,
    "system":     system_prompt,
    "messages": [
        {
            "role":    "user",
            "content": user_prompt
        }
    ]
}

with open("${WORK_DIR}/api_request_${TIMESTAMP}.json", "w") as f:
    json.dump(payload, f)

print("Payload built successfully")
PYEOF

    log "API request payload built"
}

#=============================================================================
# STEP 4: CALL THE AI API
#=============================================================================

call_ai_api() {
    log "Calling AI API (model: ${AI_MODEL})..."

    local HTTP_STATUS
    HTTP_STATUS=$(curl -s -o "${AI_RESPONSE_FILE}" -w "%{http_code}" \
        -X POST "${AI_API_URL}" \
        -H "x-api-key: ${AI_API_KEY}" \
        -H "anthropic-version: 2023-06-01" \
        -H "content-type: application/json" \
        -d @"${WORK_DIR}/api_request_${TIMESTAMP}.json" \
        2>> "${LOG_FILE}")

    if [[ "${HTTP_STATUS}" != "200" ]]; then
        log "API returned HTTP ${HTTP_STATUS}"
        cat "${AI_RESPONSE_FILE}" >> "${LOG_FILE}"
        die "AI API call failed with status ${HTTP_STATUS}"
    fi

    log "AI API call successful (HTTP 200)"
}

#=============================================================================
# STEP 5: EXTRACT AND VALIDATE THE AI RESPONSE
#=============================================================================

extract_response() {
    log "Extracting AI analysis from response..."

    python3 - <<PYEOF
import json, sys

with open("${AI_RESPONSE_FILE}") as f:
    raw = json.load(f)

# Extract the text content from the API response
content_blocks = raw.get("content", [])
ai_text = ""
for block in content_blocks:
    if block.get("type") == "text":
        ai_text += block.get("text", "")

# Parse the AI's JSON response
try:
    ai_json = json.loads(ai_text.strip())
except json.JSONDecodeError as e:
    print(f"ERROR: AI response is not valid JSON: {e}", file=sys.stderr)
    print(f"Raw response: {ai_text[:500]}", file=sys.stderr)
    sys.exit(1)

# Validate required keys
required_keys = ["analysis_metadata", "executive_summary", "index_decisions"]
missing = [k for k in required_keys if k not in ai_json]
if missing:
    print(f"ERROR: AI response missing required keys: {missing}", file=sys.stderr)
    sys.exit(1)

# Save the clean AI analysis
with open("${WORK_DIR}/ai_analysis_${TIMESTAMP}.json", "w") as f:
    json.dump(ai_json, f, indent=2)

# Print summary
summary = ai_json.get("executive_summary", {})
print(f"Analysis complete:")
print(f"  Health score:         {summary.get('overall_health_score', 'N/A')}/100")
print(f"  DROP candidates:      {summary.get('drop_candidates', 0)}")
print(f"  REBUILD candidates:   {summary.get('rebuild_candidates', 0)}")
print(f"  CREATE candidates:    {summary.get('create_candidates', 0)}")
print(f"  MONITOR candidates:   {summary.get('monitor_candidates', 0)}")
PYEOF

    log "AI analysis extracted and validated"
}

#=============================================================================
# STEP 6: STORE IN DATABASE
#=============================================================================

store_results() {
    log "Storing analysis results in governance database..."

    python3 - <<PYEOF
import json, subprocess, sys

with open("${REPORT_JSON_FILE}") as f:
    report_data = json.load(f)

with open("${WORK_DIR}/ai_analysis_${TIMESTAMP}.json") as f:
    ai_data = json.load(f)

summary = ai_data.get("executive_summary", {})

# Build INSERT statement
insert_sql = f"""
INSERT INTO dba_governance.ai_analysis_log
    (analysis_date, db_name, payload_json, ai_response,
     model_used, prompt_version,
     total_indexes, drop_candidates, rebuild_candidates, create_candidates)
VALUES (
    CURRENT_DATE,
    current_database(),
    '{json.dumps(report_data).replace("'", "''")}',
    '{json.dumps(ai_data).replace("'", "''")}',
    '${AI_MODEL}',
    'v2.1',
    {len(report_data.get('indexes', []))},
    {summary.get('drop_candidates', 0)},
    {summary.get('rebuild_candidates', 0)},
    {summary.get('create_candidates', 0)}
)
RETURNING analysis_id;
"""

result = subprocess.run(
    ["psql", "-h", "${DB_HOST}", "-p", "${DB_PORT}",
     "-U", "${DB_USER}", "-d", "${DB_NAME}", "-t", "-c", insert_sql],
    capture_output=True, text=True
)

if result.returncode != 0:
    print(f"ERROR storing analysis: {result.stderr}", file=sys.stderr)
    sys.exit(1)

analysis_id = result.stdout.strip()
print(f"Analysis stored with ID: {analysis_id}")

# Now insert individual decisions
for decision in ai_data.get("index_decisions", []):
    exec_sql = (decision.get("execution_sql") or "").replace("'", "''")
    reasoning = (decision.get("reasoning") or "").replace("'", "''")

    decision_sql = f"""
    INSERT INTO dba_governance.index_decisions
        (analysis_id, decision_date, schemaname, tablename, indexname,
         action, confidence_score, ai_reasoning, execution_sql)
    VALUES (
        {analysis_id},
        CURRENT_DATE,
        '{decision.get("schema_name", "")}',
        '{decision.get("table_name", "")}',
        '{decision.get("index_name", "")}',
        '{decision.get("action", "MONITOR")}',
        {decision.get("confidence_score", 0)},
        '{reasoning}',
        '{exec_sql}'
    );
    """

    subprocess.run(
        ["psql", "-h", "${DB_HOST}", "-p", "${DB_PORT}",
         "-U", "${DB_USER}", "-d", "${DB_NAME}", "-c", decision_sql],
        capture_output=True, text=True
    )

print(f"Stored {len(ai_data.get('index_decisions', []))} decisions")
PYEOF

    log "Results stored in governance database"
}

#=============================================================================
# MAIN
#=============================================================================

main() {
    log "=== AI Index Governance Analysis Starting ==="

    generate_report
    load_prompt
    build_request
    call_ai_api
    extract_response
    store_results

    log "=== Analysis Complete ==="
    log "Results in: ${WORK_DIR}/ai_analysis_${TIMESTAMP}.json"
    log "Review decisions: SELECT * FROM dba_governance.index_decisions

main "$@"

Walk through this with me. The script has six steps in sequence:

Step 1: Calls our PostgreSQL function and saves the JSON report to a file.

Step 2: Loads the prompt from the database. I store prompts in the database deliberately — it means you can version them, update them without touching scripts, and track which version of the prompt produced which recommendations.

Step 3: Substitutes the real report data into the prompt template. The `{{REPORT_JSON}}` placeholder gets replaced with the actual JSON.

Step 4: Calls the AI API using curl. Note that the API key comes from an environment variable. Never hardcode API keys in scripts.

Step 5: Extracts the AI's response. The API returns the full response wrapped in Anthropic's message structure. We extract the text content and parse it as JSON. We also validate that the required keys are present.

Step 6: Stores everything in the database. The full payload, the full AI response, and individual decisions for each index. This creates our audit trail.

LAYER 4: THE DECISION ENGINE
================================================================================

The AI gives us recommendations with confidence scores. But we don't execute them blindly. We run them through a decision engine.

The decision engine applies our governance rules on top of the AI recommendations. Think of it as a final safety layer before anything touches production.

---

CREATE OR REPLACE FUNCTION dba_governance.apply_decision_rules(
    p_analysis_id BIGINT
)
RETURNS TABLE (
    indexname           TEXT,
    tablename           TEXT,
    ai_action           TEXT,
    final_action        TEXT,
    confidence_score    INTEGER,
    auto_execute        BOOLEAN,
    requires_approval   BOOLEAN,
    block_reason        TEXT
)
LANGUAGE plpgsql
AS $$
BEGIN
    RETURN QUERY
    SELECT
        d.indexname,
        d.tablename,
        d.action                            AS ai_action,

        -- Override AI action based on safety rules
        CASE
            -- RULE 1: Never drop primary keys or unique indexes automatically
            WHEN d.action = 'DROP'
            AND EXISTS (
                SELECT 1 FROM pg_index ix
                JOIN pg_class c ON c.oid = ix.indexrelid
                WHERE c.relname = d.indexname
                AND (ix.indisprimary OR ix.indisunique)
            )
            THEN 'KEEP'

            -- RULE 2: Insufficient history — downgrade to MONITOR
            WHEN d.action = 'DROP'
            AND (
                SELECT COALESCE(
                    (s.ai_response -> 'index_decisions' -> 0 -> 'tags'),
                    '[]'::JSONB
                ) @> '["insufficient_history"]'::JSONB
                FROM dba_governance.ai_analysis_log s
                WHERE s.analysis_id = p_analysis_id
            )
            THEN 'MONITOR'

            -- RULE 3: Confidence below threshold — downgrade action
            WHEN d.action = 'DROP' AND d.confidence_score < 70
            THEN 'MONITOR'

            WHEN d.action = 'REBUILD' AND d.confidence_score < 60
            THEN 'MONITOR'

            -- Default: accept AI recommendation
            ELSE d.action
        END                                 AS final_action,

        d.confidence_score,

        -- Auto-execute criteria: must be >= 95 confidence, LOW risk, DROP or REBUILD
        (
            d.confidence_score >= 95
            AND d.action IN ('DROP', 'REBUILD')
            AND d.human_override = FALSE
        )                                   AS auto_execute,

        -- Requires approval: anything 70-94 or any CREATE
        (
            d.confidence_score BETWEEN 70 AND 94
            OR d.action = 'CREATE'
        )                                   AS requires_approval,

        -- Reason for any block or downgrade
        CASE
            WHEN d.action = 'DROP'
            AND EXISTS (
                SELECT 1 FROM pg_index ix
                JOIN pg_class c ON c.oid = ix.indexrelid
                WHERE c.relname = d.indexname
                AND (ix.indisprimary OR ix.indisunique)
            )
            THEN 'SAFETY BLOCK: Primary key or unique constraint — cannot drop'

            WHEN d.action = 'DROP' AND d.confidence_score < 70
            THEN 'LOW CONFIDENCE: Downgraded to MONITOR — insufficient evidence for DROP'

            WHEN d.action = 'REBUILD' AND d.confidence_score < 60
            THEN 'LOW CONFIDENCE: Insufficient fragmentation evidence'

            ELSE NULL
        END                                 AS block_reason

    FROM dba_governance.index_decisions d
    WHERE d.analysis_id = p_analysis_id
    ORDER BY d.confidence_score DESC;
END;
$$;

Now let's create the approval workflow. This is the human-in-the-loop piece:

---

CREATE OR REPLACE FUNCTION dba_governance.approve_decision(
    p_decision_id   BIGINT,
    p_approved_by   TEXT,
    p_approved      BOOLEAN,
    p_override_reason TEXT DEFAULT NULL
)
RETURNS TEXT
LANGUAGE plpgsql
AS $$
DECLARE
    v_action    TEXT;
    v_exec_sql  TEXT;
    v_result    TEXT;
BEGIN
    -- Get the decision
    SELECT action, execution_sql
    INTO v_action, v_exec_sql
    FROM dba_governance.index_decisions
    WHERE decision_id = p_decision_id;

    IF NOT FOUND THEN
        RETURN 'ERROR: Decision ID not found';
    END IF;

    -- Record the approval
    UPDATE dba_governance.index_decisions
    SET
        approved        = p_approved,
        approved_by     = p_approved_by,
        approved_at     = NOW(),
        override_reason = p_override_reason,
        human_override  = (p_override_reason IS NOT NULL)
    WHERE decision_id = p_decision_id;

    IF p_approved AND v_exec_sql IS NOT NULL THEN
        -- Execute the approved SQL
        BEGIN
            EXECUTE v_exec_sql;

            UPDATE dba_governance.index_decisions
            SET
                executed        = TRUE,
                executed_at     = NOW(),
                result_status   = 'SUCCESS'
            WHERE decision_id = p_decision_id;

            v_result := 'SUCCESS: ' || v_action || ' executed for decision ' || p_decision_id;

        EXCEPTION WHEN OTHERS THEN
            UPDATE dba_governance.index_decisions
            SET
                result_status = 'FAILED',
                result_notes  = SQLERRM
            WHERE decision_id = p_decision_id;

            v_result := 'ERROR: Execution failed — ' || SQLERRM;
        END;
    ELSE
        v_result := 'Decision ' || p_decision_id || ' recorded as '
                    || CASE WHEN p_approved THEN 'APPROVED (awaiting execution)'
                       ELSE 'REJECTED' END;
    END IF;

    RETURN v_result;
END;
$$;

So the workflow is:

1. AI makes recommendations → stored in `index_decisions`
2. Decision engine applies safety rules → identifies what can auto-execute vs. what needs approval
3. For auto-execute items: run automatically during maintenance window
4. For requires-approval items: DBA reviews and calls `approve_decision()`
5. For rejected items: logged with reason

SELECT
    d.decision_id,

    d.action,
    d.confidence_score,
    d.ai_reasoning,
    d.risk_level,
    d.execution_sql,
    CASE
        WHEN d.confidence_score >= 95 THEN 'AUTO-EXECUTE ELIGIBLE'
        WHEN d.confidence_score >= 85 THEN 'STRONG RECOMMENDATION'
        WHEN d.confidence_score >= 70 THEN 'MODERATE CONFIDENCE'
        ELSE 'INVESTIGATE FIRST'
    END AS approval_guidance,
    pg_size_pretty(s.index_size_bytes) AS current_size,
    s.idx_scan AS current_scans,
    s.table_n_ins + s.table_n_upd + s.table_n_del AS table_modifications
FROM
    dba_governance.index_decisions d
    LEFT JOIN LATERAL (
        SELECT *
        FROM dba_governance.index_snapshots
        WHERE indexname = d.indexname
        AND tablename = d.tablename
        ORDER BY snapshot_date DESC
        LIMIT 1
    ) s ON TRUE
WHERE
    d.approved IS NULL
    AND d.decision_date = CURRENT_DATE
ORDER BY
    d.confidence_score DESC,
    s.index_size_bytes DESC;

---

Now any DBA can run:

    SELECT * FROM dba_governance.pending_approvals;

And they'll see a clean list of what needs their attention, ordered by confidence and impact.

================================================================================
LAYER 5: MULTI-WEEK TREND ANALYSIS
================================================================================

Here's where the historical tracking becomes genuinely powerful.

After a few weeks of running this system, you start to see patterns. Indexes that cycle between used and unused (probably batch jobs). Indexes whose scan counts are growing (perhaps a new feature was deployed). Indexes that are consistently fragmented week over week (a maintenance problem, not a fragmentation problem).

No single snapshot can tell you any of this. But four weeks of snapshots can.

---

-- Trend analysis view: week-over-week change in key metrics

CREATE OR REPLACE VIEW dba_governance.index_trends AS
WITH weekly AS (
    SELECT
        indexname,
        tablename,
        schemaname,
        snapshot_date,
        idx_scan,
        index_size_bytes,
        table_size_bytes,
        LAG(idx_scan, 1) OVER (
            PARTITION BY indexname, tablename
            ORDER BY snapshot_date
        ) AS prev_week_scans,
        LAG(index_size_bytes, 1) OVER (
            PARTITION BY indexname, tablename
            ORDER BY snapshot_date
        ) AS prev_week_size,
        COUNT(*) OVER (
            PARTITION BY indexname, tablename
        ) AS weeks_of_data
    FROM dba_governance.index_snapshots
)
SELECT
    w.schemaname,
    w.tablename,
    w.indexname,
    w.snapshot_date,
    w.weeks_of_data,
    w.idx_scan                              AS current_scans,
    w.prev_week_scans,
    w.idx_scan - COALESCE(w.prev_week_scans, 0) AS scan_delta,
    ROUND(
        CASE
            WHEN COALESCE(w.prev_week_scans, 0) = 0 THEN NULL
            ELSE ((w.idx_scan - w.prev_week_scans)::FLOAT /
                   NULLIF(w.prev_week_scans, 0)) * 100
        END::NUMERIC, 2
    )                                       AS scan_change_pct,
    pg_size_pretty(w.index_size_bytes)      AS current_size,
    w.index_size_bytes - COALESCE(w.prev_week_size, 0) AS size_growth_bytes,
    CASE
        WHEN w.idx_scan = 0 AND COALESCE(w.prev_week_scans, 0) = 0
        THEN 'PERSISTENTLY_UNUSED'
        WHEN w.idx_scan = 0 AND COALESCE(w.prev_week_scans, 0) > 0
        THEN 'RECENTLY_STOPPED'
        WHEN w.idx_scan > 0 AND COALESCE(w.prev_week_scans, 0) = 0
        THEN 'RECENTLY_STARTED'
        WHEN w.idx_scan > w.prev_week_scans * 1.5
        THEN 'RAPIDLY_GROWING'
        WHEN w.idx_scan < w.prev_week_scans * 0.5
        THEN 'RAPIDLY_DECLINING'
        ELSE 'STABLE'
    END                                     AS usage_trend,
    CASE
        WHEN w.index_size_bytes > COALESCE(w.prev_week_size, 0) * 1.2
        THEN 'GROWING_FAST'
        WHEN w.index_size_bytes < COALESCE(w.prev_week_size, 0) * 0.8
        THEN 'SHRINKING'
        ELSE 'STABLE'
    END                                     AS size_trend
FROM weekly w
WHERE w.snapshot_date = CURRENT_DATE
ORDER BY w.tablename, w.indexname;

---

This view tells you at a glance what's happening to each index over time. The `usage_trend` column is particularly valuable for the AI analysis — I feed this into the JSON report as part of the `history` section so the AI can factor trends into its recommendations.

Here's a practical query for generating the trend summary you'd include in your executive report:

---

SELECT
    usage_trend,
    COUNT(*) AS index_count,
    STRING_AGG(schemaname || '.' || tablename || '.' || indexname, ', ')
        AS examples
FROM dba_governance.index_trends
GROUP BY usage_trend
ORDER BY index_count DESC;

---

And here's a query that finds the most worrying patterns — indexes that are both growing fast AND declining in usage:

---

SELECT
    schemaname,
    tablename,
    indexname,
    current_scans,
    scan_change_pct,
    current_size,
    size_growth_bytes,
    usage_trend,
    size_trend
FROM dba_governance.index_trends
WHERE (usage_trend = 'RAPIDLY_DECLINING' AND size_trend = 'GROWING_FAST')
   OR usage_trend = 'PERSISTENTLY_UNUSED'
ORDER BY size_growth_bytes DESC;

---

An index that's growing fast but being used less — that's textbook fragmentation combined with a workload shift. That needs attention.

PUTTING IT ALL TOGETHER: THE COMPLETE PIPELINE

Let me now show you the complete automated pipeline in a single orchestration script. This is what you'd deploy to run weekly.

---

#!/bin/bash

#=============================================================================
# index_governance_pipeline.sh
# Full AI-driven index governance pipeline
# Cron: 0 7 * * 0  (every Sunday at 7:00 AM)
#=============================================================================

set -euo pipefail

readonly PIPELINE_START=$(date +%Y%m%d_%H%M%S)
readonly LOG_DIR="/var/log/dba_governance"
readonly LOG_FILE="${LOG_DIR}/pipeline_${PIPELINE_START}.log"
readonly LOCK_FILE="/tmp/index_governance.lock"
readonly DB_NAME="${DB_NAME:-production}"
readonly DB_USER="${DB_USER:-postgres}"
readonly ADMIN_EMAIL="${ADMIN_EMAIL:-dba-team@company.com}"

PSQL="psql -U ${DB_USER} -d ${DB_NAME}"

mkdir -p "${LOG_DIR}"

log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "${LOG_FILE}"; }

# Prevent overlapping runs
exec 200>"${LOCK_FILE}"
flock -n 200 || { log "Pipeline already running. Exiting."; exit 1; }

#=============================================================================
# PIPELINE STAGES
#=============================================================================

stage_01_snapshot() {
    log "=== STAGE 1: Capture Snapshot ==="
    ${PSQL} -c "SELECT dba_governance.generate_index_report() IS NOT NULL
                AS snapshot_captured;" >> "${LOG_FILE}" 2>&1
    log "Snapshot captured"
}

stage_02_trend_analysis() {
    log "=== STAGE 2: Trend Analysis ==="
    ${PSQL} -t -c "
        SELECT
            'Trend Summary: ' ||
            COUNT(*) || ' indexes tracked | ' ||
            SUM(CASE WHEN usage_trend = 'PERSISTENTLY_UNUSED' THEN 1 ELSE 0 END)
                || ' persistently unused | ' ||
            SUM(CASE WHEN usage_trend = 'RAPIDLY_GROWING' THEN 1 ELSE 0 END)
                || ' rapidly growing'
        FROM dba_governance.index_trends;
    " >> "${LOG_FILE}" 2>&1
    log "Trend analysis complete"
}

stage_03_ai_analysis() {
    log "=== STAGE 3: AI Analysis ==="
    bash /usr/local/bin/ai_index_analyzer.sh >> "${LOG_FILE}" 2>&1
    log "AI analysis complete"
}

stage_04_apply_rules() {
    log "=== STAGE 4: Apply Governance Rules ==="
    local ANALYSIS_ID
    ANALYSIS_ID=$(${PSQL} -t -c \
        "SELECT analysis_id FROM dba_governance.ai_analysis_log
         ORDER BY created_at DESC LIMIT 1;")

    ${PSQL} -c "SELECT * FROM dba_governance.apply_decision_rules(${ANALYSIS_ID});" \
        >> "${LOG_FILE}" 2>&1

    log "Governance rules applied to analysis ID: ${ANALYSIS_ID}"
}

stage_05_auto_execute() {
    log "=== STAGE 5: Auto-Execute High-Confidence Actions ==="

    # Pull high-confidence, low-risk approved actions
    local SQL_COMMANDS
    SQL_COMMANDS=$(${PSQL} -t -A -c "
        SELECT execution_sql
        FROM dba_governance.index_decisions d
        WHERE d.decision_date = CURRENT_DATE
        AND d.approved IS NULL          -- Not yet reviewed (auto-eligible)
        AND d.confidence_score >= 95
        AND d.action IN ('DROP', 'REBUILD')
        AND d.execution_sql IS NOT NULL
        AND d.execution_sql != '';
    ")

    if [[ -z "${SQL_COMMANDS}" ]]; then
        log "No auto-execute candidates today"
        return 0
    fi

    local COUNT=0
    while IFS= read -r CMD; do
        [[ -z "${CMD}" ]] && continue
        log "Auto-executing: ${CMD}"
        if ${PSQL} -c "${CMD}" >> "${LOG_FILE}" 2>&1; then
            log "SUCCESS: ${CMD}"
            ((COUNT++)) || true
        else
            log "FAILED: ${CMD} — check log for details"
        fi
    done <<< "${SQL_COMMANDS}"

    log "Auto-executed ${COUNT} maintenance actions"
}

stage_06_generate_report() {
    log "=== STAGE 6: Generate Weekly Report ==="

    local REPORT_FILE="${LOG_DIR}/weekly_report_$(date +%Y%m%d).txt"

    {
        echo "============================================================"
        echo "WEEKLY INDEX GOVERNANCE REPORT"
        echo "Generated: $(date '+%Y-%m-%d %H:%M:%S')"
        echo "Database: ${DB_NAME}"
        echo "============================================================"
        echo ""
        echo "GOVERNANCE DASHBOARD"
        echo "------------------------------------------------------------"
        ${PSQL} -c "SELECT metric_category, metric_value, metric_description
                    FROM dba_governance.governance_dashboard;"
        echo ""
        echo "PENDING DBA APPROVALS"
        echo "------------------------------------------------------------"
        ${PSQL} -c "SELECT decision_id, tablename, indexname, action,
                           confidence_score, approval_guidance, current_size
                    FROM dba_governance.pending_approvals
                    LIMIT 20;"
        echo ""
        echo "AI RECOMMENDATIONS SUMMARY"
        echo "------------------------------------------------------------"
        ${PSQL} -c "SELECT action, COUNT(*) AS count,
                           AVG(confidence_score)::INT AS avg_confidence
                    FROM dba_governance.index_decisions
                    WHERE decision_date = CURRENT_DATE
                    GROUP BY action ORDER BY count DESC;"
        echo ""
        echo "Full log: ${LOG_FILE}"

    } > "${REPORT_FILE}" 2>&1

    # Email the report
    if command -v mail &>/dev/null; then
        mail -s "Index Governance Report — $(date +%Y-%m-%d)" \
            "${ADMIN_EMAIL}" < "${REPORT_FILE}"
        log "Report emailed to ${ADMIN_EMAIL}"
    fi

    log "Report saved: ${REPORT_FILE}"
}

#=============================================================================
# MAIN
#=============================================================================

log "=== PIPELINE START ==="
stage_01_snapshot
stage_02_trend_analysis
stage_03_ai_analysis
stage_04_apply_rules
stage_05_auto_execute
stage_06_generate_report
log "=== PIPELINE COMPLETE ==="

---

And the cron entry:

    0 7 * * 0 DB_NAME=production DB_USER=postgres ANTHROPIC_API_KEY=your_key_here \
              /usr/local/bin/index_governance_pipeline.sh
