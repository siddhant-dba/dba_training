Alright, settle in. We're going to talk about something that sounds boring — configuration — but I promise you, this is where most of the headaches come from in production. And I'm talking about headaches that keep you up at night, calling your boss, wondering if you're making a terrible decision.

Think about what we've covered so far. We looked at processes. We looked at the directory structure. We looked at shared memory. Now here's the question: who decides HOW big shared memory is? Who decides HOW MANY processes can connect? Who decides WHEN to compact your transaction logs? Who decides what to log, when to checkpoint, what the defaults are?

The answer is: configuration. And PostgreSQL's configuration system is not simple. It's layered. It's got fallbacks. It's got reload-time changes and restart-time changes and per-session overrides. Get this wrong, and you'll spend three months chasing performance problems that are actually just bad configuration.

I'm going to show you how to navigate this system. And more importantly, I'm going to teach you HOW TO THINK about it so you don't get tangled up.


--- THE FILES THEMSELVES ---

Let me start with the physical files. When you start PostgreSQL, the postmaster goes looking for configuration. On your system right now, where is it?

Go to your PGDATA directory — remember TASK 0.2, when we navigated into the filesystem? Go there. What's the top level?

  cd $PGDATA
  ls -la | head -20

You should see a file called `postgresql.conf`. That's the main configuration file. It's a text file. You can open it with vim, nano, cat, whatever. Let me show you:

  head -100 postgresql.conf

You'll see hundreds of lines. Most of them are commented out with a `#`. They're defaults. The uncommented ones are the settings that have been explicitly changed from the defaults.

Here's the thing most people don't know: you can have MULTIPLE configuration files. PostgreSQL supports includes. Look near the top of postgresql.conf:

  include_dir = 'conf.d'

That line tells PostgreSQL: "After you read this file, also read every .conf file in the conf.d subdirectory." This is huge. This is how you organize configuration. You don't put everything in one file.

Let me show you what's typically there:

  ls -la conf.d/

You might see things like:
  - 10-performance.conf
  - 20-replication.conf
  - 30-logging.conf
  - 40-security.conf

See the numbering? That's a pattern. It tells you the ORDER in which they're read. If a setting appears in both 10-performance.conf and 30-logging.conf, the one in 30-logging.conf wins because it's read last. This is intentional. You can override settings by including them in a later file.

Now, there's also a file you shouldn't usually edit directly:

  cat postgresql.auto.conf

This file is GENERATED by PostgreSQL. It contains settings that were changed using the SQL command ALTER SYSTEM. We'll come back to that.

The order of precedence is:
1. postgresql.conf is read first
2. include directives in postgresql.conf pull in other files (like conf.d/)
3. postgresql.auto.conf is read last
4. SQL-level overrides (ALTER SYSTEM) are stored in postgresql.auto.conf

So if you want something to ALWAYS be the override, you put it in postgresql.auto.conf. Or better yet, you use ALTER SYSTEM from SQL.

Why would you do that? Because you can reload it without restarting the server. But we'll get to that.


--- THE MENTAL MODEL: CONTEXT ---

Now here's where it gets interesting. Not all configuration changes are the same. Some require a full restart. Some can be reloaded on the fly. Some are per-session. Some are read-only.

The word PostgreSQL uses for this is "context." Every setting has a context. And if you understand context, you understand everything about how configuration works.

Let me break it down:

**POSTMASTER context**: This setting can ONLY be changed by restarting the database. Examples: shared_buffers, max_connections, work_mem. Why? Because these are allocated at startup time. The postmaster carves out memory, forks processes, sets up structures. You can't change that while it's running. You have to stop, change, and start.

**SIGHUP context**: This setting can be changed by reloading the configuration WITHOUT restarting. How? The postmaster receives a SIGHUP signal (you send it via `pg_ctl reload` or `SELECT pg_reload_config();`), re-reads the configuration files, and applies the new values. Examples: log_statement, log_duration, checkpoint frequency settings. Backends pick up the new values on their next opportunity.

**USER context**: This setting can be changed PER SESSION by the user. You can change it with a SET command. It only affects your session, not anyone else's. Examples: search_path, work_mem, statement_timeout. These are temporary and session-local.

**SUPERUSER context**: Like USER context, but only superusers can change them. Examples: log_connections. A regular user can't change the logging settings, but a superuser can.

**BACKEND context**: This is set once, at connection start time. Usually read from postgresql.conf. Can't be changed after connection is established.

**INTERNAL context**: This is read-only. You can look at the value, but you can't change it. Examples: server_version, block_size.

Now, why do I care about this? Because I've watched DBAs try to change max_connections with a SET command in a session, think it worked, restart the server, and wonder why it didn't stick. That's because max_connections is POSTMASTER context. SET doesn't work. Only a restart works.

And I've watched other DBAs restart the entire database to change log_statement, when a simple `pg_ctl reload` would have worked. That's downtime you didn't need to take.

Understand context, and you avoid these mistakes.


--- LOOKING AT SETTINGS WITH pg_settings ---

Now let's see all this in action. Connect to your database:

  psql -U postgres

And run this query:

  SELECT name, setting, unit, context 
    FROM pg_settings 
   WHERE name LIKE '%shared%' 
   ORDER BY name;

What you see is a table of every configuration setting, its current value, the unit of measurement, and most importantly, the CONTEXT.

See shared_buffers? You'll see context is "postmaster". That means restart.

See log_statement? You'll see context is "superuser". That means superuser can set it with SET, or change it in postgresql.conf and reload.

Let me show you a more complete view. This is powerful:

  SELECT 
    name, 
    setting, 
    unit, 
    context, 
    source, 
    sourcefile, 
    pending_restart
  FROM pg_settings 
  WHERE category = 'Memory'
  ORDER BY name;

Now you're seeing:
- **name**: the parameter name
- **setting**: the current value
- **unit**: what the unit is (8kB, ms, etc.)
- **context**: what level can change it
- **source**: where was it set? (default, configuration file, command line, etc.)
- **sourcefile**: which file was it set in?
- **pending_restart**: is this a POSTMASTER context change that hasn't been applied yet?

That last column — pending_restart — is critical. It tells you: "You changed this, it's waiting for a restart, but it's not active yet."

Let me show you something. Let's look at all the parameters that require a restart:

  SELECT name, setting, unit, context, source 
    FROM pg_settings 
   WHERE context = 'postmaster' 
   ORDER BY name;

Count them in your head. There are a lot. These are all the things that require a restart to change.

Now compare with SIGHUP context:

  SELECT name, setting, unit, context, source 
    FROM pg_settings 
   WHERE context = 'sighup' 
   ORDER BY name;

Also a lot. These are the things you can reload on the fly.

This is diagnostic gold. When you're troubleshooting, you come here. You ask: "What's actually set right now? Where did that value come from? Do I need a restart or a reload to change it?"


--- THE CRITICAL WAR STORY ---

I'm going to stop and tell you a story right now that happened in 2013. This is from my own career, and I'm still embarrassed about it.

I was managing a PostgreSQL cluster with maybe 500GB of data. It was a busy OLTP system. High throughput. Lots of short transactions.

The application team came to me and said, "We're getting connection timeouts. Increase max_connections."

So I did. I edited postgresql.conf. I changed max_connections from 100 to 300. I ran `pg_reload_config();`

The connection timeouts didn't stop.

I think: "Maybe I didn't reload properly." I run it again. Nothing.

Then I check pg_settings:

  SHOW max_connections;

It still says 100!

What happened?

I changed the FILE. But PostgreSQL hadn't restarted. max_connections is POSTMASTER context. A reload doesn't apply POSTMASTER changes. You HAVE to restart.

I didn't know that. Or I forgot. And I spent two hours troubleshooting, thinking the reload didn't work, when what I actually needed to do was RESTART.

When I finally did, the server shut down, recovered WAL, came back up, and the new max_connections value was there.

But in that two hours, I had basically told the application team, "I fixed it," when I hadn't. They kept trying to open connections. It kept failing. I looked foolish. I learned a lesson.

Here's the lesson: if you change a POSTMASTER context parameter, you MUST restart. There's no shortcut. There's no clever reload trick. You restart. Period.

Always check pg_settings first to see the context. Always. It takes ten seconds. It saves you hours.


--- CHANGING CONFIGURATION: THE THREE WAYS ---

Okay, so you know WHERE configuration is. You know what CONTEXT means. Now let's talk about HOW to change it.

There are three mechanisms:

**METHOD 1: Edit postgresql.conf (or included files) and reload or restart**

You open the file in an editor. You change the value. You either:
  - Run `pg_ctl reload` (for SIGHUP context changes)
  - Run `SELECT pg_reload_config();` (same thing, from SQL)
  - Run `pg_ctl restart` (for POSTMASTER context changes)

Pros: Everything ends up in the file. It persists across restarts. It's documented.
Cons: You have to edit a file. You have to remember to reload or restart.

**METHOD 2: ALTER SYSTEM**

You're connected to the database. You run:

  ALTER SYSTEM SET shared_buffers = '2GB';

This writes the value to postgresql.auto.conf. PostgreSQL will read it next time it starts up (or reloads, for SIGHUP context parameters).

Then you reload or restart:

  SELECT pg_reload_config();  -- for SIGHUP changes
  -- or pg_ctl restart for POSTMASTER changes

Pros: You don't have to edit a file manually. It's SQL. You can script it.
Cons: It's not in postgresql.conf, so your documentation is fragmented.

**METHOD 3: SET (session-only)**

You're connected. You run:

  SET log_statement = 'all';

This changes the setting for YOUR session ONLY. No one else sees it. It disappears when you disconnect.

Pros: No file editing. No restart needed. Instant.
Cons: It's temporary. It's not persistent. Only works for certain context types (USER, SUPERUSER, BACKEND).

Now, which should you use in production?

My opinion: Use METHOD 1 (edit files) for most things. It's documented. It's version-controlled. You can see the history. You can explain why a setting is what it is.

Use METHOD 2 (ALTER SYSTEM) only when you're making ONE-OFF changes that you'll revert or adjust frequently, or when you're automating configuration via scripts.

Use METHOD 3 (SET) for testing and temporary things only. Never for production baseline configuration.

Why do I care? Because I've seen databases where the configuration is scattered across: a file, ALTER SYSTEM calls, and some SET statements in connection pooler startup scripts. And three years later, no one knows what the baseline is supposed to be.

Keep it organized. Put the baseline in postgresql.conf. Version control it. Document why each setting is what it is. That's how you run a professional database.


--- UNDERSTANDING KEY PARAMETERS BY CONTEXT ---

Let me teach you to categorize parameters. This is a skill.

I'm going to ask you to run this query and we'll go through some results together:

  SELECT name, setting, unit, context, category 
    FROM pg_settings 
   ORDER BY context, name;

What you're looking at is EVERY parameter, grouped by context. Let's talk about the critical ones in each category.

**POSTMASTER CONTEXT — Requires Full Restart:**

These are allocated at startup. You CANNOT change them with a reload.

- `shared_buffers`: The size of PostgreSQL's private buffer pool. Default is 128MB. Way too small for production. Usually 25% of RAM.
- `max_connections`: Maximum number of concurrent connections. Default is 100. Each connection uses memory. Don't set it much higher than you need.
- `work_mem`: Memory allocated PER OPERATION (per sort, per hash table, etc.). Default is 4MB. If you're doing a big sort, you want more. But don't go crazy. You can have 50 connections, each doing a sort, each using 256MB. That's 12GB for work_mem alone. Do the math.
- `maintenance_work_mem`: Memory for maintenance operations like VACUUM and CREATE INDEX. Default is 64MB. Make this bigger. These are usually not concurrent. You can afford to allocate more.
- `max_parallel_workers_per_gather`: How many worker processes can a single query use? Default is 2. For big analytics queries, you might want more. For OLTP, 2 is fine.

You CANNOT change any of these with SET or with a reload. You MUST restart. Check the pending_restart column after you change them:

  ALTER SYSTEM SET shared_buffers = '4GB';
  SELECT name, setting, pending_restart FROM pg_settings 
   WHERE name = 'shared_buffers';

You'll see `pending_restart = true`. That means: "This is set in the config, but it's not active. You need to restart to activate it."

**SIGHUP CONTEXT — Reload Only:**

You can change these by reloading the configuration. No restart needed.

- `log_statement`: What statements to log? 'all', 'mod', 'ddl', 'none'. This is huge for debugging. In prod, you might log 'ddl' to catch schema changes. In development, you might log 'all' to see every query.
- `log_duration`: Log the duration of every query? Yes or no. Helps you find slow queries.
- `log_min_duration_statement`: Only log queries that take longer than this many milliseconds. Set it to 1000 to only log queries that take more than a second. Critical for finding slow queries without logging everything.
- `log_connections` and `log_disconnections`: Log when people connect and disconnect. Useful for auditing.
- `checkpoint_timeout`: How often to force a checkpoint? Default is 5 minutes. A checkpoint is when all dirty pages get flushed to disk. More frequent = safer but slower. Less frequent = faster but more crash recovery time.

You can change these with:

  ALTER SYSTEM SET log_statement = 'all';
  SELECT pg_reload_config();

Boom. Done. No restart. The change is live immediately.

**USER CONTEXT — Per-Session:**

You can change these with SET for your session only.

- `search_path`: What schemas to search for tables? Default is 'public'. If you SET search_path = 'myschema, public', your session will look in myschema first, then public.
- `statement_timeout`: Abort any statement that takes longer than this. Very useful. You can SET it to 60000 (60 seconds) to ensure no query runs forever.
- `work_mem`: Wait, this is also POSTMASTER context for the global default. But you can SET it per-session to override. "For this session, I'm running a big sort, so give me 1GB of work_mem."
- `random_page_cost`: A cost parameter used by the query planner. On SSDs, you might lower it. On HDDs, you might raise it. SET it to tune planning for a specific query.

These don't affect other sessions. When you disconnect, they go away. Useful for testing or one-off queries.

**INTERNAL CONTEXT — Read-Only:**

You can look at these, but you can't change them.

- `server_version`: What version is this server? 13.2, 14.5, etc.
- `block_size`: 8192 (8KB). This is compiled in. You can't change it.
- `data_directory`: Where is PGDATA? This is set at initdb time. You can't change it without moving everything.

These are informational. Use them to understand your system, not to configure it.

Now, go back to the query. Look at pg_settings. Find three POSTMASTER parameters. Find three SIGHUP parameters. Find three USER parameters. You should be able to look at the context and predict what you can change without restarting.

This is a skill. Practice it.


--- THE MOST COMMON MISTAKE ---

I want to tell you the most common configuration mistake I see in production.

Someone reads that PostgreSQL is "slow by default" and decides to "optimize" it. So they google "best postgresql configuration" and they copy a config from some blog post written by someone who optimized for THEIR workload, not the general case.

They set:

  shared_buffers = 256GB
  work_mem = 512MB
  maintenance_work_mem = 2GB
  random_page_cost = 1.1
  effective_cache_size = 768GB

And suddenly their query plans change. Suddenly they're using parallel workers. Suddenly they're doing sequential scans instead of index scans. And the queries are SLOWER than they were before.

What happened? They didn't understand their workload. They just copied numbers.

Here's the right approach:

1. Run the database with defaults for a week. Monitor it. See what happens.
2. Identify the real bottleneck. Is it CPU? Disk I/O? Memory? Locks?
3. Change ONE parameter to address that bottleneck. Just one.
4. Measure. Does it help?
5. If yes, keep it. If no, revert it. Then try another.

This takes discipline. You don't copy a config. You build one. Piece by piece. Based on YOUR data.

I've seen DBAs inherit a database with these crazy optimized settings for a workload that changed three years ago. The settings don't apply anymore. But no one dares change them because "someone optimized this." Meanwhile, it's running like garbage.

Be brave enough to ask: "Why is this set to this value?" If no one knows, change it back to the default and see what happens. Often, the answer is: "This improved performance for Query X in 2018, but we haven't run Query X in three years."

Configuration should be intentional and documented. If it's not, clean it up.


--- PRACTICAL EXERCISE: MAPPING YOUR CONFIGURATION ---

Alright, let's do this live. I want you to:

1. Connect to your PostgreSQL instance:

   psql -U postgres

2. Run this query to see your current critical settings:

   SELECT name, setting, unit, context, source, pending_restart 
     FROM pg_settings 
    WHERE name IN ('shared_buffers', 'max_connections', 'work_mem', 
                   'log_statement', 'log_duration', 'checkpoint_timeout',
                   'max_parallel_workers_per_gather', 'effective_cache_size')
    ORDER BY name;

   Take a screenshot. Write down these values. This is your current baseline.

3. Check what's in postgresql.conf:

   \! grep -E "^[^#]" /path/to/postgresql.conf | head -20

   Replace /path/to with your PGDATA. You're looking for uncommented lines.

4. Look at postgresql.auto.conf:

   \! cat /path/to/postgresql.auto.conf

   Are there any ALTER SYSTEM settings there? What are they?

5. Now, make a test change. Let's change log_duration (SIGHUP context, no restart needed):

   ALTER SYSTEM SET log_duration = on;

6. Verify it's in the file:

   \! grep log_duration /path/to/postgresql.auto.conf

7. Reload the configuration:

   SELECT pg_reload_config();

8. Verify it took effect:

   SHOW log_duration;

9. Revert it:

   ALTER SYSTEM RESET log_duration;
   SELECT pg_reload_config();

10. Now test a POSTMASTER parameter. Let's try max_connections. Run:

    ALTER SYSTEM SET max_connections = 200;

11. Check pending_restart:

    SELECT name, setting, pending_restart 
      FROM pg_settings 
     WHERE name = 'max_connections';

    You'll see `pending_restart = true`. This is active in the config, but not live yet.

12. Try to use it:

    SHOW max_connections;

    Still shows the OLD value! Because it's not restarted yet.

13. Verify your change is in the file anyway:

    \! grep max_connections /path/to/postgresql.auto.conf

14. Revert it (because we don't actually want to restart):

    ALTER SYSTEM RESET max_connections;

This exercise shows you:
— How to check what's set
— How to change things with ALTER SYSTEM
— How to reload for SIGHUP parameters
— How pending_restart tells you a parameter is waiting for a restart
— The difference between "changed in config" and "actually active"

This is the mental model. Get this, and you understand configuration.


--- TYING IT TOGETHER ---

Here's what we've covered:

**Configuration is layered.** Files are read in order. postgresql.conf, then include_dir, then postgresql.auto.conf. Later values override earlier ones. This is by design. Use it to organize your configuration logically.

**Context determines when changes take effect.** POSTMASTER requires restart. SIGHUP requires reload. USER is per-session. INTERNAL is read-only. Always check pg_settings before making a change. It takes ten seconds. It prevents hours of pain.

**Always check pending_restart.** If you change a POSTMASTER parameter and see pending_restart = true, it means the change is waiting for a restart. The database won't use it until you restart. Don't fool yourself into thinking the change is active.

**Edit thoughtfully.** Don't copy someone else's configuration. Understand YOUR workload. Change one thing at a time. Measure the impact. Document why each setting is what it is.

**Keep a baseline.** Version control your postgresql.conf. Keep it in git. You should be able to look at the history and say, "On March 15th, we changed shared_buffers from 2GB to 4GB because of X." That's professional.

And here's the bigger picture: PostgreSQL is not slow by default. It's CAUTIOUS by default. The defaults are conservative. They work on a laptop with 2GB of RAM and a single user. In production, you WILL need to tune. But tune intentionally. Not by accident.


--- QUICK REFERENCE CARD FOR CONFIGURATION DISCOVERY ---

Commands you need to remember:

1. FIND POSTGRESQL.CONF:

   find $PGDATA -name "postgresql.conf"
   cat $PGDATA/postgresql.conf | head -50

2. CHECK WHAT'S ACTUALLY SET RIGHT NOW:

   SELECT name, setting, unit, context, source 
     FROM pg_settings 
    WHERE name = 'setting_name'
    ORDER BY name;

3. FIND ALL POSTMASTER CONTEXT PARAMETERS (REQUIRE RESTART):

   SELECT name, setting, unit, context 
     FROM pg_settings 
    WHERE context = 'postmaster' 
    ORDER BY name;

4. FIND ALL SIGHUP CONTEXT PARAMETERS (RELOAD ONLY):

   SELECT name, setting, unit, context 
     FROM pg_settings 
    WHERE context = 'sighup' 
    ORDER BY name;

5. FIND ALL USER/SUPERUSER CONTEXT PARAMETERS (SESSION-LEVEL):

   SELECT name, setting, unit, context 
     FROM pg_settings 
    WHERE context IN ('user', 'superuser') 
    ORDER BY name;

6. CHECK IF PENDING RESTART IS NEEDED:

   SELECT name, setting, pending_restart 
     FROM pg_settings 
    WHERE pending_restart = true;

   If you see rows here, you changed POSTMASTER parameters and need to restart.

7. CHANGE CONFIGURATION PERSISTENTLY:

   ALTER SYSTEM SET parameter_name = 'value';
   SELECT pg_reload_config();  -- for SIGHUP parameters
   -- OR: pg_ctl restart       -- for POSTMASTER parameters

8. CHANGE CONFIGURATION FOR THIS SESSION ONLY:

   SET parameter_name = 'value';

9. REVERT A CHANGE:

   ALTER SYSTEM RESET parameter_name;
   SELECT pg_reload_config();

10. VIEW POSTGRESQL.AUTO.CONF (GENERATED BY ALTER SYSTEM):

    \! cat $PGDATA/postgresql.auto.conf

11. VIEW WHAT'S IN AN INCLUDE DIRECTORY:

    \! ls -la $PGDATA/conf.d/

12. CHECK WHICH FILE A SETTING CAME FROM:

    SELECT name, setting, sourcefile, sourceline 
      FROM pg_settings 
     WHERE name = 'setting_name';

THE CRITICAL RULES:
— POSTMASTER context = must restart
— SIGHUP context = reload only (pg_ctl reload or pg_reload_config())
— USER context = SET for current session only
— Always check pg_settings before assuming a change worked
— Always check pending_restart after changing POSTMASTER parameters
— Keep configuration in version control
— Change one thing at a time
— Measure the impact of each change
