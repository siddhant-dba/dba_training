TASK TITLE: Respond to a Security Breach Allegation With Evidence Collection
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
An unauthorized access allegation has been made. The legal and security teams
are demanding proof of whether unauthorized access occurred. A DBA must be
able to construct an evidence timeline from logs, not guess or panic.

SCENARIO
A customer alleges: "On June 15 at 3:47 PM, someone accessed our customer
database and exported our customer list (table: customers, >100k rows)."
You must answer: Did this happen? Who did it? Prove it with evidence.

YOUR TASK (Forensic investigation)
1. Establish a timeline:
   - When was the export detected? (what time, what triggered the alert?)
   - What is the time window of the alleged access? (3:47 PM ±30 minutes)
   - What is the earliest sign of suspicious activity in the logs?

2. Identify what access would be needed:
   - SELECT on the customers table
   - Sufficient permissions on that role
   - Ability to export data (pg_dump? Application API? Raw SELECT?)

3. Search the PostgreSQL log for evidence:
   - Filter for connections during the time window
   - Look for SELECT queries against the customers table
   - Identify which role(s) executed them
   - Note the client IP address for each connection

4. Cross-reference with other evidence:
   - System authentication logs (sudologs, /var/log/auth.log)
   - Application logs (if the export was via API)
   - File system logs (was data written to disk/network?)
   - Database activity monitoring (if DAM tools are in place)

5. Build the evidence narrative:
   - Timeline of who connected when
   - What queries they executed
   - What data was accessed
   - Conclusion: Did unauthorized access occur? By whom?

6. Document your findings:
   - Be factual and specific
   - Avoid speculation
   - Note gaps in evidence (what logs were NOT available?)
   - Preserve all evidence for legal/compliance teams

SAFETY
Risk: Medium
Breach investigations are high-stakes. Document everything, preserve logs,
involve legal/security teams. Do not destroy or modify any evidence.

TASK TITLE: Detect and Revoke Overprivileged Roles (Privilege Creep Audit)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Privilege creep happens over time — a contractor who was granted SELECT
on one schema six months ago never had it revoked, and accumulates more.
A DBA must periodically audit and reclaim unnecessary privileges.

SCENARIO
An audit requests: "Show us all roles with elevated privileges that should
not have them." You need to identify and revoke overprivileged accounts.

YOUR TASK (Privilege audit and remediation)
1. Query all roles and their privilege flags:
   - Which roles are SUPERUSER? (Only postgres should be)
   - Which roles can CREATE databases? (Only DBA roles should)
   - Which roles can CREATE roles? (Only DBA roles should)

2. For non-DBA roles, check their object-level privileges:
   - What schemas can they access?
   - What tables/views can they modify?
   - Do they have more privileges than their job requires?

3. Cross-reference with your organization's role matrix:
   - Developer role should have: SELECT, INSERT, UPDATE on appschema
   - Analyst role should have: SELECT only on reporting schema
   - Etc.

4. Identify violations:
   - A contractor account with CREATEDB=true (should be false)
   - A developer with CONNECT on all databases (should be one DB)
   - A former employee account still having privileges (should be deleted)

5. For each violation, determine action:
   - Immediate revoke (urgent security risk)?
   - Revoke + notify user (courtesy before revoking)?
   - Deny (if the user will notice immediately)?

6. Execute the revocations:
   - ALTER ROLE to remove privilege flags
   - REVOKE to remove object-level privileges
   - Document the change (reason, date, who approved)

7. Re-audit post-remediation:
   - Verify the revoke worked
   - Confirm the user can still do their job
   - Update your documentation

SAFETY
Risk: Medium
Revoking privileges can break applications. Notify teams before revoking.
Test on a copy first. Have a recovery plan if something breaks.

SKILL BUILT
Area  : Security (Server Level)

TASK TITLE: Plan and Implement SSL/TLS Hardening for All Connections
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Unencrypted database connections expose credentials and data on the network.
A DBA must harden SSL/TLS comprehensively: generate proper certificates,
configure mutual TLS, and enforce encryption on all client connections.

SCENARIO
Your security audit found that PostgreSQL allows unencrypted connections.
You need to:
1. Generate proper SSL certificates
2. Configure PostgreSQL to require SSL
3. Ensure clients can connect
4. Maintain backward compatibility where safe

YOUR TASK (SSL/TLS hardening)
1. Generate a self-signed certificate (or use a CA-signed one):
   - Create private key and certificate
   - Set correct permissions (read-only by postgres user)
   - Verify certificate validity and expiry

2. Configure PostgreSQL:
   - Enable SSL (ssl = on)
   - Point to the certificate and key files
   - Choose SSL protocol version (TLSv1.2 minimum)
   - Require SSL for network connections (hostssl rules in pg_hba.conf)

3. Update pg_hba.conf:
   - Replace 'host' rules with 'hostssl' for network connections
   - Keep 'local' for Unix socket (no SSL needed)
   - Remove any 'host ... trust' rules (dangerous + now unencrypted)

4. Restart PostgreSQL and verify:
   - Instance comes up cleanly?
   - Connections over TCP work with SSL?
   - Unix socket connections still work?

5. Test client connections:
   - psql with sslmode=require
   - psql with sslmode=prefer (falls back if SSL fails)
   - Verify query results match expectations

6. Plan for client compatibility:
   - Which applications connect to PostgreSQL?
   - Do they support SSL? (Most modern ones do)
   - Which need configuration changes?

7. Communicate the change:
   - Send connection string updates to all teams
   - Document: why, when, how to connect
   - Support rollback in case of critical application incompatibility

SAFETY
Risk: Medium
Enforcing SSL can break applications that don't support it. Test thoroughly.
Have a rollback plan (allow unencrypted connections temporarily if needed).

Area  : Security (Server Level)
Skill : SSL/TLS implementation and hardening — certificate generation, enforcement

TASK TITLE: Respond to a Compliance Violation Finding
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
A compliance audit (SOC 2, ISO 27001, HIPAA, GDPR) will find violations.
A DBA must understand the violation, assess the impact, and remediate
quickly or justify why it cannot be fixed immediately.

SCENARIO
A compliance audit found: "PostgreSQL backups are stored in an unencrypted
S3 bucket. This violates data at rest encryption requirements."
You have 30 days to remediate or justify an exception.

YOUR TASK (Compliance remediation)
1. Understand the violation:
   - What is the requirement? (Encrypt all backups at rest)
   - Why is it violated? (Backups currently in unencrypted S3)
   - What is the business impact if fixed? (Operational changes needed)
   - What is the risk if NOT fixed? (Compliance failure, audit failure)

2. Assess feasibility of remediation:
   - Encrypt S3 buckets (easy, no operational impact)
   - Use encrypted EBS volumes (requires infrastructure change)
   - Use encrypted backup tools (pgbackrest with encryption)
   - Move backups to a different storage system (large change)

3. Choose a remediation path:
   - Least effort: Enable S3 encryption (server-side, Amazon-managed)
   - More secure: Enable S3 encryption (customer-managed keys)
   - Comprehensive: Use pgbackrest with encryption

4. Create a remediation plan:
   - What will you do? (implement S3 encryption)
   - By when? (within 30 days, target: 2 weeks)
   - What is the testing procedure?
   - How do you verify the fix? (confirm backups are encrypted)
   - What is the impact to restore procedures? (minimal if server-side encryption)

5. Document the violation response:
   - Finding: Backups not encrypted at rest
   - Root cause: Storage was provisioned without encryption
   - Remediation: Enable S3-side encryption
   - Verification: Backup restore test post-remediation
   - Prevention: Update infrastructure standards to require encryption

6. If remediation is not feasible, request an exception:
   - Explain why it cannot be fixed in 30 days
   - Propose interim controls (limit who can access S3)
   - Commit to a future remediation date
   - Risk acceptance: Document who approved the risk

SAFETY
Risk: Low for this task
Enabling encryption is safe. Changing backup tools requires testing.

TASK TITLE: Construct an Audit Trail From Logs for a Suspected Data Exfiltration
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
When data is suspected to have been exfiltrated, you must prove (or disprove)
it by building a complete audit trail: who accessed what, when, and whether
the data left the system. This requires correlating multiple log sources.

SCENARIO
A sensitive table (financial_records, 5,000 rows) was discovered to be
missing 500 rows. You must investigate: Were they deleted? Exported?
Who did it? When?

YOUR TASK (Audit trail construction)
1. Determine the scope:
   - When was the deletion/export discovered?
   - When did it likely occur? (work backwards from discovery)
   - Which role(s) had DELETE access? SELECT access?

2. Search PostgreSQL logs for evidence:
   - Filter for DELETE statements against financial_records
   - Filter for SELECT with large result sets (indicates export)
   - Note timestamp, user, client IP for each

3. Correlate with system logs:
   - Look in /var/log/auth.log for sudo access to postgres user
   - Look for pg_dump or psql invocations
   - Check cron logs for scheduled exports

4. Verify the missing rows:
   - Query the live table: count vs expected?
   - Check if there's a backup from before the deletion
   - Can you identify WHICH rows are missing? (by ID range)

5. Build the timeline:
   - June 15, 10:00 AM: User alice connected as role finance_app
   - June 15, 10:05 AM: DELETE from financial_records WHERE ... 500 rows deleted
   - June 15, 10:15 AM: Data not exported (no pg_dump evidence)
   - Conclusion: Intentional data deletion by alice, not exfiltration

6. Identify the root cause:
   - Was this an accident (wrong WHERE clause)?
   - Was this intentional (user had legitimate reason)?
   - Was this malicious (unauthorized user)?

7. Determine if data left the system:
   - No SELECT exports to files (no evidence in logs)
   - No bulk downloads via API (check application logs)
   - Conclusion: Data likely not exfiltrated, just deleted

SAFETY
Risk: Medium
Investigations can implicate employees. Be factual, fair, and preserve evidence.
Involve legal/HR as appropriate.

TASK TITLE: Implement Multi-Factor Authentication (MFA) for Database Access
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Passwords alone are insufficient. A DBA at L3 understands MFA options for
database access (not just OS-level MFA) and can design/implement them.

SCENARIO
Your security team mandates: "All privileged database access (DBA role, 
superuser) must use multi-factor authentication by Q2."

YOUR TASK (MFA design and implementation)
1. Identify MFA options for PostgreSQL:
   - OS-level MFA (PAM integration) — most flexible
   - Client certificate authentication (mutual TLS)
   - One-time passwords (TOTP) — not native to PostgreSQL
   - LDAP/Kerberos with MFA — backend integration

2. Choose an approach:
   - For DBAs: OS-level MFA via PAM (requires SSH to jump host)
   - For applications: Client certificate + password
   - For legacy: Kerberos with MFA backend

3. Implement for DBAs (OS-level PAM):
   - Configure PAM on the PostgreSQL server
   - Set up TOTP (Time-based One-Time Password) with tools like Google Authenticator
   - Require password + TOTP for postgres OS user access
   - Test: DBA can su to postgres with password + TOTP only

4. Implement for applications (certificate-based):
   - Generate client certificates (one per application)
   - Configure PostgreSQL to require certificates
   - Update pg_hba.conf to use 'cert' authentication
   - Applications present the certificate + password on connect

5. Create an enrollment process:
   - How do DBAs get TOTP seed?
   - Where is the seed stored securely?
   - What is the backup method if they lose their phone?

6. Test thoroughly:
   - DBA can connect with password + TOTP? ✓
   - DBA cannot connect with password alone? ✓
   - Application can connect with certificate + password? ✓
   - Backup method works (out-of-band token)? ✓

SAFETY
Risk: High
MFA can lock people out if not tested thoroughly. Have a bypass method
for emergency access. Test on a copy first.

TASK TITLE: Detect and Investigate Suspicious Database Activity (Anomaly Detection)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Malicious activity often has a pattern — unusual queries, access at odd times,
from unusual IPs. A DBA should be able to spot anomalies and investigate them
before they cause data loss.

SCENARIO
Your monitoring alerts you to unusual activity:
- A service account connected from a new IP at 3 AM (usually connects at 9 AM)
- Executed SELECT * from sensitive_table with a limit 1,000,000 (unusual query)
- Transferred 2GB of data in 5 minutes (unusual volume)

Is this malicious? Legitimate? How do you respond?

YOUR TASK (Anomaly investigation)
1. Establish baseline behavior:
   - When does this service account normally connect?
   - What are normal query patterns?
   - What is normal data volume?
   - Normal geographic/IP distribution?

2. Analyze the anomaly:
   - 3 AM connection (off-hours) — suspicious but could be batch job

   - If suspicious: monitor closely but don't terminate yet
   - If legitimate: update your baseline expectations

   - Malicious: Unauthorized access, confirmed theft attempt

6. Remediate:
   - If legitimate: update your alert thresholds
   - If suspicious: investigate further, increase logging
   - If malicious: incident response, revoke compromised credentials, forensics

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
When a database is deprovisioned, the data must be destroyed securely such
that it cannot be recovered. A DBA must understand data destruction best
practices and execute them during deprovisioning.

SCENARIO
A customer database will be permanently deleted. It contains PII (personally
identifiable information) and financial data. You must:
1. Ensure all data is unrecoverable after deletion
2. Maintain an audit trail of the deletion
3. Comply with data protection regulations (GDPR, CCPA, etc.)

YOUR TASK (Secure deprovisioning)
1. Prepare for secure deletion:
   - Back up the database (to prove it existed) to secure archive
   - Prepare a deletion checklist
   - Notify data subjects (if required by regulation)
   - Confirm legal approval to delete

2. Implement data destruction:
   - Overwrite all data before deletion:
       sudo -u postgres psql -d customer_db -c \
       "DROP TABLE customer_data CASCADE; -- destroy table"
   - This removes data from the database, but file system recovery might be possible
   - For higher security: Use pg_basebackup to move data to /dev/zero storage
   - Or: Use an encrypted tablespace — encrypt with a key you then destroy

3. Verify destruction:
   - Can the database be recovered from backups? (No)
   - Can the data be recovered from the file system? (Unlikely if overwritten)
   - Are there copies elsewhere? (Check replication, archives, archives)

4. File system-level destruction:
   - Securely overwrite the PostgreSQL cluster data directory
   - Tools: shred, srm, or dd with /dev/urandom
   - Verify: ls -la /var/lib/postgresql/XX/main/ shows empty (or nonexistent)

5. Audit trail and documentation:
   - Record: When deleted, by whom, for what reason
   - Evidence: Timestamps, commands executed, final state verification
   - Archive: Store the deletion record in a compliance management system
   - Report: Provide certification to the data subject or regulator

6. Handle remaining copies:
   - Backups: Destroy old backups or move to offline secure storage
   - WAL archives: Destroy or securely store
   - Replication standbys: Delete the database from standbys too
   - Application caches: Clear if they cached customer data

SAFETY
Risk: CRITICAL
Data destruction is permanent. Verify that deletion is actually required
and authorized. Have legal/compliance sign-off before proceeding.

SCENARIO

YOUR TASK (Ethical penetration testing)

   - What version is it? (banner grabbing)

   - What roles exist? (check for leaky error messages)

   Vector 1: Default credentials

   - Can you SELECT from sensitive tables?
   - Can you export the data? (pg_dump, COPY, SELECT INTO)
   - Can you bulk export it off the system? (no firewall rules?)

5. Document findings:
   - What vulnerabilities did you find?
   - How severe is each? (Critical, High, Medium, Low)
   - Can they be exploited in the real world?
   - What controls prevented further escalation?

6. Create remediation plan:
   - Weakness 1: Default credentials on postgres role → Force password change
   - Weakness 2: No SSL enforcement → Enforce hostssl in pg_hba.conf
   - Weakness 3: Overprivileged role → Reduce permissions
   - Etc.

TASK TITLE: Diagnose and Recover From Data Corruption
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Data corruption is every DBA's nightmare. Silent corruption (where invalid
data goes undetected) is worse. A DBA must be able to detect corruption,
quantify its extent, and recover with minimal data loss.

SCENARIO
A table's integrity check fails: amcheck reports a B-tree structure error.
Queries against this table return wrong results. You must:
1. Confirm and quantify the corruption
2. Decide: Restore from backup vs attempt online repair
3. Execute recovery with minimal downtime

YOUR TASK (Corruption investigation and recovery)
1. Detect corruption:
   - Run amcheck on all indexes:
       sudo -u postgres psql -d mydb -c \
       "SELECT bt_index_parent_check(indexname::regclass) \
        FROM pg_indexes WHERE tablename = 'corrupted_table';"

   - Run consistency checks on heap:
       REINDEX INDEX CONCURRENTLY idx_name;

   - Query the table and note unusual results

2. Quantify the damage:
   - How many rows are affected?
   - Is the index only corrupt (fixable online) or the heap (requires restore)?
   - What is the business impact? (read errors? write errors? both?)

3. Decide on recovery approach:

   Option A: Online repair (if only index corruption):
   - REINDEX INDEX CONCURRENTLY idx_name;
   - Verify amcheck passes post-reindex
   - Resume normal operations
   - Time required: Minutes to hours

   Option B: Restore from backup (if heap corruption):
   - Stop writes to the corrupted table
   - Restore the table from a known-good backup
   - Replay WAL if needed (PITR to latest point)
   - Time required: Depends on table size, backup location

4. Prevent future corruption:
   - What caused it? (Hardware failure? Software bug? Physical damage?)
   - Run hardware diagnostics (memtest, disk SMART checks)
   - Consider enabling data checksums (postgresql config)
   - Increase monitoring: run amcheck regularly

5. Document the incident:
   - When was corruption detected?
   - What was the scope? (one index? multiple tables?)
   - What recovery action was taken?
   - How long did recovery take?
   - Root cause: physical or logical?

SAFETY
Risk: HIGH
Data corruption is unpredictable. Backups are your primary recovery tool.
Test restores before corruption strikes. Have a detailed recovery procedure.

TASK TITLE: Perform Point-in-Time Recovery (PITR) With Partial Data Loss
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Sometimes you do not want to restore to the exact moment the last backup
was taken. You want to recover to a specific point in time AFTER the backup
(using WAL). This requires understanding WAL recovery, recovery targets, and
exclusive backups.

SCENARIO
At 14:45:30 on June 15, a bad query deleted 5,000 customer records by mistake.
You have:
- A full backup from 09:00 (before the deletion)
- WAL archive containing all activity from 09:00 to now
- A requirement to recover to 14:45:25 (5 seconds before the deletion)

YOUR TASK (PITR recovery)
1. Verify recovery requirements:
   - Last backup: 09:00
   - Recovery target: 14:45:25 (before the deletion)
   - Data loss tolerance: 20 seconds (from 14:45:25 to 14:45:45)
   - Is this acceptable? (Business decision)

2. Prepare a recovery server:
   - Set up an isolated environment (not production)
   - You will restore the backup here, replay WAL, and verify the result

3. Extract the backup and prepare recovery:
   - tar xzf backup.tar.gz -C /var/lib/postgresql/
   - Create a recovery.conf with recovery targets:

       recovery_target_timeline = 'latest'
       recovery_target_time = '2025-06-15 14:45:25'
       recovery_target_inclusive = off  -- stop BEFORE this time, not on it

4. Start recovery:
   - The standby will replay WAL up to the recovery target
   - It will exit recovery mode when the target is reached

5. Verify the recovery:
   - Check the recovered data: SELECT count(*) FROM customers;
   - Did you recover what was deleted? (Check a few rows)
   - Is the data correct? (Spot check some values)
   - Are there any NULL values or oddities?

6. Plan the cutover:
   - This recovered server is now your "new source of truth"
   - You must migrate the data back to production:
     * Option A: pg_dump the recovered database → restore to prod
     * Option B: Use replication to sync the recovered DB back to prod
     * Option C: Plan a full cutover to the recovered instance

7. Execute cutover carefully:
   - Notify users of the downtime
   - Stop writes to the original database
   - Verify WAL has been fully replayed
   - Perform final data validation
   - Switch application connection strings to the recovered instance
   - Resume writes

SAFETY
Risk: HIGH
PITR recovery loses data after the recovery target time. Ensure this is
acceptable. Have a rollback plan (revert to original if recovery failed).

TASK TITLE: Investigate and Resolve a Backup Failure
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Backup failures are silent until they are not. A backup that fails silently
for weeks means you have NO recovery point. A DBA must be able to detect
failures, diagnose root causes, and fix them urgently.

SCENARIO
Your automated backup job failed for the last 3 days. You only discover it
when a restore is needed. The last good backup is 3 days old.

YOUR TASK (Backup failure triage)
1. Determine scope:
   - Which databases are affected? (All or just one?)
   - How many days of backups are missing? (3 days)
   - What is the business impact? (Restore can only go back 3 days)

2. Identify root cause:
   - Check the backup script logs:
       tail -100 /var/log/postgresql/backup.log

   Common failure causes:
   - Disk full (no space for backup file)
   - Backup destination filesystem unavailable (NFS mount failed)
   - Archive destination full (backup waits for WAL archiving)
   - Insufficient database permissions
   - Network issues (if backing up to remote location)

3. Fix the root cause immediately:
   - If disk full: delete old backups, expand filesystem, retry
   - If mount failed: remount, verify connectivity, retry
   - If archive full: clear archive directory, retry archiving
   - If permission issue: fix role/OS permissions, retry

4. Attempt an emergency backup:
   - Run pg_dump or pg_basebackup NOW (before further data loss)
   - Direct output to a different filesystem if the usual one is full
   - Verify the backup completed successfully:
       pg_restore -l backup_file | head -20

5. Implement a workaround while diagnosing further:
   - If the usual backup location is broken: backup to a different location
   - If the backup script is broken: run manual backups until fixed
   - Set up temporary monitoring to confirm backups are happening

6. Fix the automated backup system:
   - Repair the script (wrong path? wrong permissions?)
   - Re-enable automated backups
   - Monitor the next 3 backup cycles to confirm they succeed

7. Review and improve:
   - Why did the failure go unnoticed for 3 days?
   - No monitoring for successful backup completion?
   - Add: alert if backup fails, alert if no backup in 24 hours

SAFETY
Risk: CRITICAL
Backup failures mean no recovery option. Respond urgently. Do not delay
diagnosis hoping it will fix itself.

SKILL BUILT

Skill : Backup failure diagnosis and recovery — root cause analysis, emergency mitigation

TASK TITLE: Plan and Execute a Large Table Migration (Zero-Downtime)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
A 100GB table needs to change structure (add a column, change data type,
alter partitioning). You cannot take the table offline. A DBA must design
a zero-downtime migration using logical replication, CONCURRENTLY indexes,
or table versioning.

SCENARIO
The "orders" table (500GB) needs a new column "order_status_updated_at".
Currently it uses timestamps without timezone. You cannot lock the table.
The migration window is a Friday evening (4 hours).

YOUR TASK (Large table migration planning)
1. Assess the migration:
   - Size: 500GB (will take hours to rewrite)
   - Downtime tolerance: 4 hours on Friday evening
   - Approach: Add new column with default value

2. Design the migration approach:

   Option A: Minimal downtime (5 minutes)
   - Use ALTER TABLE ADD COLUMN with DEFAULT
   - PostgreSQL doesn't rewrite the table (just updates the schema)
   - Time required: Seconds
   - Risk: Default value might not be what you want

   Option B: Full rewrite during maintenance window (4 hours)
   - Create a new table with the correct structure
   - COPY data from old table to new (with any transformations)
   - Swap table names using ALTER TABLE RENAME
   - Time required: 2-4 hours depending on CPU/I/O
   - Downtime: Time for COPY + swap (30 mins - 2 hours depending on speed)

   Option C: Zero-downtime using logical replication
   - Create a publication on the old table
   - Create a subscription on a replica table
   - Catch up the replica to the primary
   - Swap names (atomic cutover)
   - Time required: 12-24 hours to replicate 500GB

3. Choose Option B (minimal downtime during approved window):
   - Friday 18:00: Notify users (database will be briefly unavailable)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS

orphaned records) often develop silently. A DBA must have systematic
checks to find them and fix them.

SCENARIO
A business report shows unexpected results. Investigation reveals:
- Orders exist with customer_id that don't exist in the customers table
- Inventory counts don't match the sum of order line items
- Some rows are missing expected values (NULLs where NOT NULL expected)

YOUR TASK (Data consistency audit and repair)
1. Identify inconsistencies:
   - Foreign key violations:
       SELECT o.id FROM orders o LEFT JOIN customers c ON o.customer_id=c.id
       WHERE c.id IS NULL AND o.customer_id IS NOT NULL;

   - Inventory sync issues:
       SELECT i.item_id, i.quantity,
              (SELECT count(*) FROM order_lines WHERE item_id=i.item_id)
              AS counted_qty
       FROM inventory i
       WHERE i.quantity != (SELECT count(*)...);

   - Missing values:
       SELECT COUNT(*) FROM orders WHERE customer_id IS NULL;

2. Quantify the damage:
   - How many orphaned orders? (10? 1000? 10000?)
   - How far out of sync is the inventory? (1%? 50%?)
   - How many rows have unexpected NULLs?

3. Decide on correction strategy:

   Option A: Delete inconsistent data
   - DELETE FROM orders WHERE customer_id NOT IN (SELECT id FROM customers)
   - Risk: Lose legitimate orders if the customer was deleted by mistake

   Option B: Correct the inconsistency
   - ADD a default customer for orphaned orders
   - UPDATE inventory SET quantity = (subquery) to correct counts
   - Risk: Might mask a deeper application bug

   Option C: Leave it and fix the process
   - Document the inconsistency
   - Add constraints/triggers to prevent future inconsistencies
   - Require application fix before data cleanup

4. Implement the fix:
   - Wrap in a transaction for safety
   - Back up before making changes
   - Execute the correction
   - Verify: rerun the inconsistency query, should return 0 rows

5. Investigate root cause:
   - Why did inconsistencies develop?
   - Application logic error? (wrong inserts)
   - Manual intervention? (DBA error)
   - Missing constraints? (DELETE CASCADE not set up)

6. Implement prevention:
   - Add FOREIGN KEY constraints if missing
   - Add CHECK constraints for invalid values
   - Add triggers to keep totals in sync
   - Periodic consistency audits (weekly?)

TASK TITLE: Respond to Replication Lag Incident
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
If your standby is lagging hours behind the primary, PITR depends on the
standby (if primary fails, you can only recover to the standby's lag point).
A DBA must detect lag, diagnose the cause, and resolve it urgently.

SCENARIO
Your standby replica is 4 hours behind the primary (should be < 1 minute).
Applications are failing over to read-only standby, but it returns stale data.
You must diagnose and fix the lag.

YOUR TASK (Replication lag diagnosis and recovery)
1. Measure the lag:
   - On primary: SELECT pg_current_wal_lsn();
   - On standby: SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();
   - Calculate: How far behind is the standby? (byte offset = lag)

2. Determine the bottleneck:
   - Is the standby NOT RECEIVING WAL from primary?
     (receive_lsn == replay_lsn, both far behind current_lsn)
     → Network issue, replication connection broken
   - Is the standby RECEIVING but NOT REPLAYING? (receive_lsn > replay_lsn)
     → Standby is CPU-bound or I/O-bound, cannot keep up with replay speed

3. Fix network/replication issues:
   - If replication connection is broken:
     * Check pg_stat_replication on primary — is standby still connected?
     * Check pg_stat_wal_receiver on standby — is it trying to connect?
     * Verify network connectivity between primary and standby
     * Verify pg_hba.conf allows replication connections
     * Restart replication if necessary

4. Fix CPU/I/O bottlenecks:
   - If standby is CPU-bound:
     * Check pg_stat_activity on standby during replay
     * Identify the slow queries being replayed
     * Can those queries be parallelized? (max_parallel_workers_per_gather)
   - If standby is I/O-bound:
     * Check iostat on standby — is disk at 100% utilization?
     * Is the standby's disk slower than primary? (upgrade disk if needed)
     * Consider: async I/O, increasing cache, load balancing

5. Temporary mitigation:
   - If standby cannot keep up: pause non-critical writes on primary
     (reduces WAL generation → reduces lag accumulation)
   - If standby's disk is failing: migrate to better hardware
   - Temporarily increase wal_keep_size to preserve WAL on primary
     (buys time while standby catches up)

6. Monitor recovery:
   - Lag should decrease as standby catches up
   - Once lag < 1 minute, resume normal operations
   - Monitor for 24 hours to ensure lag does not recur

7. Root cause analysis:
   - Why did lag develop?
   - Application spike (too many writes)?
   - Network slowdown?
   - Standby hardware failure?
   - Implement: alerts to catch this earlier next time

SAFETY
Risk: High
Replication lag means you have lost HA (no fast failover). Address urgently.
Do not ignore hoping it resolves.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
A 1TB table with billions of rows can be slow to scan or vacuum. Partitioning
divides it into smaller chunks, improving query speed (can scan just the needed
partition) and maintenance speed (VACUUM one partition, not the whole table).

SCENARIO

take 30 seconds scanning the whole table. You need to partition it by date

YOUR TASK (Partitioning design and implementation)

   - Is the table large? (1TB+, yes)
   - Does it have a natural partition key? (date column, yes)
   - Will queries often filter on the partition key? (events.event_date, yes)
   - Will partitions be balanced in size? (roughly equal monthly data, yes)

2. Design the partition scheme:
   - Partition by: event_date (monthly partitions)
   - Range: Each month becomes one partition (2025-01, 2025-02, etc.)
   - Retention: Keep 2 years, archive older (2-year rolling window)
   - Result: 24 partitions, each ~400GB

3. Plan the migration:
   - Create partitioned table with same schema (events_new)
   - Migrate data from old table to new (COPY or INSERT...SELECT)
   - Create indexes on each partition (CONCURRENTLY)
   - Swap table names

4. Implement:
   - CREATE TABLE events_new (event_id, event_date, ...)
     PARTITION BY RANGE (event_date) ...
   - CREATE TABLE events_202501 PARTITION OF events_new
     FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
   - (Repeat for each month)

5. Migrate data:
   - INSERT INTO events_new SELECT * FROM events;
   - This distributes rows automatically to the correct partition

6. Enable partition pruning:
   - Set enable_partition_pruning = on
   - PostgreSQL will now automatically exclude unneeded partitions

7. Test queries:
   - EXPLAIN shows partition pruning in action?
   - Query speed improved? (should be much faster on one partition)

8. Manage ongoing:
   - Each month, create new partition for new data
   - Each year, drop or archive 2-year-old partitions
   - Automate: CREATE RULE or trigger to auto-create partitions

SAFETY
Risk: High

2. Verify data integrity
3. Restore services

1. Pre-drill preparation:
   - Notify all stakeholders: "We're running a DR drill 9 AM - 12 PM Saturday"
   - Document current state (backups, replication status, connections)

   - "Assume primary data center is offline, all applications have lost connectivity"
   - Note the time: this is your RTO baseline

   - Promote standby to primary:

   - Compare to SLA: did you meet your RTO/RPO targets?

7. Run the backup plan:
   - Attempt a restore from backups to a third server
   - Can you restore to the disaster time (for evidence/audit)?

8. Document findings:
   - What went wrong?
   - What took longer than expected?
   - What was the data loss?
   - Improvement recommendations

9. Rollback to pre-drill state:
   - Promote original primary back to primary
   - Resync standby
   - Verify everything is back to normal

         WHERE deleted_at IS NOT NULL
         AND deleted_at < now() - interval '3 years';

         -- Keep medical_records minimum 6 years, delete after
         DELETE FROM medical_records
         WHERE created_at < now() - interval '6 years';
       END;
       $$ LANGUAGE plpgsql;

3. Track deletions for compliance:
   - Maintain an audit log: what was deleted, when, why
   - Provide proof to auditors: "All GDPR deletion requests were processed"

4. Handle data subject requests:
   - Process "right to be forgotten" requests:
     * Find all data belonging to user_id X
     * Mark for deletion (mark record, schedule delete in 90 days)
     * Notify user: "Your data will be deleted in 90 days"
     * After 90 days: actually delete

5. Manage backup retention:
   - Backups older than 30 days: delete
   - Archives older than 7 years: delete
   - Encrypted backups: destroy the encryption key after retention expires
     (makes backup unrecoverable)

6. Audit and report:
   - Monthly: generate report of what was deleted
   - Quarterly: confirm deletion policies are being enforced
   - Annually: compliance certification (all GDPR/HIPAA requirements met)

7. Handle retention disputes:
   - A user requests deletion, but legal says "keep for litigation"
   - Implement: retention hold override (legal team can block deletion)
   - Log: who placed the hold, when, why

SAFETY
Risk: HIGH
Complying with retention regulations is mandatory. Failing to delete on time
= compliance violation. Deleting too early = regulatory violation.
Automate it and monitor it.

Skill : Compliance data retention — automated enforcement, audit trails, holds

TASK TITLE: Build and Operate a Complete Backup and Recovery Workflow
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
A complete backup strategy includes: daily backups, WAL archiving, backup
verification, restore procedures, documentation, and regular testing. This
is your insurance policy. A DBA at L3 must design and operate it end-to-end.

SCENARIO
Design and implement a production-grade backup system for a 1TB database:
- RTO: 4 hours (acceptable downtime)
- RPO: 1 hour (acceptable data loss)
- Compliance: Keep backups for 7 years
- Budget: Reasonable cost

YOUR TASK (Complete backup workflow design)
1. Design the architecture:
   - Daily full backup (takes 4 hours, stores 1TB compressed = 500GB)
   - Hourly WAL archiving (enables PITR within 1 hour)
   - Off-site replication (backup copies to S3 for disaster)
   - Backup verification (test restore monthly)

2. Implement the backup script:
   - pg_basebackup once daily (or pg_dump for logical backup)
   - Compress and encrypt
   - Upload to S3 or archive location
   - Maintain a manifest (when, size, checksum)
   - Alert if backup fails

3. Implement WAL archiving:
   - archive_command sends each WAL file to the archive location
   - Monitor pg_stat_archiver: confirmed backups are happening
   - Delete archived WAL once backup is confirmed

4. Implement backup verification:
   - Monthly: restore a backup to a test server
   - Perform consistency checks
   - Run a sample query, confirm results
   - Document: "Backup from YYYY-MM-DD verified OK"

5. Retention and lifecycle:
   - Backups kept online (S3) for 30 days
   - Backups 30+ days moved to Glacier (cheaper, slower restore)
   - Backups 7+ years: delete per legal policy

6. Disaster recovery procedure:
   - Document: step-by-step restore from backup
   - Include: time estimates, resources needed, validation steps
   - Make it repeatable: test every quarter

7. Monitoring and alerting:
   - Alert: backup failed
   - Alert: backup older than 25 hours (violates RPO)
   - Alert: test restore failed (backup is unreadable)
   - Dashboard: backup status, last successful backup, restore time estimate

8. Document the system:
   - What backups are kept where?
   - How to restore? How long does it take?
   - Who is responsible? (escalation path)
   - What if something breaks?

SAFETY
Risk: CRITICAL
The backup system is your safety net. Every failure here directly impacts
RTO/RPO. Test extensively. Automate as much as possible. Monitor
continuously. Have no single points of failure.

SKILL BUILT
Area  : Data Management
Skill : Complete backup system design — integration, verification, disaster recovery
