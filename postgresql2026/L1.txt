TASK TITLE: Locate and Verify Your PostgreSQL Installation
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
A DBA must know exactly what version is installed, how it was installed, and
where the binaries live. Without this, you cannot patch, upgrade, or support
the instance under your care.

STEPS
1. Check if PostgreSQL is installed and get its version:
       psql --version
       pg_lsclusters

2. Find the PostgreSQL binary location:
       which psql
       which pg_ctlcluster

3. List all installed PostgreSQL packages on Debian:
       dpkg -l | grep postgresql

4. Note the major version number (e.g., 14, 15, 16). The major version
   controls the data directory structure and upgrade paths.

5. Find where the binaries are stored for your version (replace XX):
       ls /usr/lib/postgresql/XX/bin/

6. Record the following for your notes:
       - Installed version(s)
       - Binary path
       - Package name(s) installed

SAFETY
Risk: None
These are all read-only discovery commands. Nothing is changed.

SKILL BUILT
Area  : Database Server / Instance
Skill : PostgreSQL installation identification and binary location awareness

REVIEW QUESTION

for a DBA?

TASK TITLE: Discover the PostgreSQL Cluster Layout on Debian
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Debian uses a cluster-based layout (pg_ctlcluster) that differs from vanilla
PostgreSQL. DBAs must understand this structure because all configuration,
startup, and data paths follow it. Misunderstanding this causes misconfigurations.

STEPS
1. List all clusters on this system:
       pg_lsclusters

2. Identify and record for each cluster shown:
       - Version
       - Cluster name
       - Port number
       - Status (online/down)
       - Data directory path
       - Log file path

3. Navigate to the data directory (replace version and cluster name):
       ls -la /var/lib/postgresql/XX/main/

4. Identify these key files and directories inside the data directory:
       PG_VERSION           — stores the version number
       postgresql.conf      — main config file
       pg_hba.conf          — client authentication config
       pg_ident.conf        — ident map config
       global/              — global catalog tables
       base/                — per-database storage
       pg_wal/              — write-ahead log files

5. Check the config directory (may differ from data dir on Debian):
       ls /etc/postgresql/XX/main/

SAFETY
Risk: None
Read-only directory listing. No modifications made.

SKILL BUILT
Area  : Database Server / Instance
Skill : Debian PostgreSQL cluster structure and layout awareness

TASK TITLE: Identify the PostgreSQL System Service and Its Current State
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
A DBA must know how the database service is managed by the OS. On Debian,
PostgreSQL runs as a systemd service. Knowing how to check its state, read
its logs, and understand its process tree is foundational for all operations
and incident response.

STEPS
1. Check the systemd service status for PostgreSQL (replace XX):
       sudo systemctl status postgresql@XX-main.service
   Or check the general service:
       sudo systemctl status postgresql

2. Note the following from the output:
       - Active state (running/stopped/failed)
       - PID of the main postgres process
       - Recent log lines shown at the bottom

3. View the PostgreSQL process tree using the postgres OS user:
       ps aux | grep postgres

4. Identify what each process type is:
       - postmaster     — the main parent process
       - checkpointer   — handles checkpoint writes
       - background writer — flushes dirty pages
       - walwriter      — writes WAL to disk
       - autovacuum     — automatic maintenance
       - stats collector — collects activity stats

5. Check which port PostgreSQL is listening on:
       ss -tlnp | grep postgres
   Or:
       sudo netstat -tlnp | grep postgres

6. Verify the OS user PostgreSQL runs as:
       ps aux | grep postmaster | grep -v grep

SAFETY
Risk: None
All read-only observation commands. No service interaction.

Area  : Database Server / Instance
Skill : PostgreSQL service state awareness and background process identification

TASK TITLE: Read and Understand the PostgreSQL Server Log
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
The PostgreSQL server log is the first place a DBA looks when something goes
wrong. You must know where it lives, how it is structured, and how to read
it before any incident occurs.

STEPS
1. Find the current log file location. On Debian, logs go to:
       ls /var/log/postgresql/

2. View the tail of the current log file (replace with actual filename):
       sudo tail -50 /var/log/postgresql/postgresql-XX-main.log

3. Alternatively, view logs via journald:
       sudo journalctl -u postgresql -n 50 --no-pager

4. In the log output, identify and note examples of these log entry types:
       LOG:     — informational messages (startup, shutdown, checkpoints)
       WARNING: — non-critical issues worth investigating
       ERROR:   — a failed operation (connection refused, query error)
       FATAL:   — a session was terminated
       PANIC:   — the entire server must restart

5. Look for the startup sequence in the log. Find lines such as:
       "database system was shut down"
       "entering standby mode" (if replica)
       "database system is ready to accept connections"

6. Check how logging is configured:
       grep -E "^log_destination|^logging_collector|^log_directory|^log_filename" \
       /etc/postgresql/XX/main/postgresql.conf

SAFETY
Risk: None
Read-only log viewing. No configuration changes.

SKILL BUILT
Area  : Database Server / Instance
Skill : PostgreSQL log file location, structure, and log level identification

REVIEW QUESTION
What is the difference between a LOG, WARNING, ERROR, FATAL, and PANIC
message in PostgreSQL logs? Give a real-world example of when you would
expect to see each one.

TASK TITLE: Explore Key postgresql.conf Parameters at the Instance Level
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
postgresql.conf is the master configuration file for the instance. A DBA
must know its location, structure, and the most important parameters before
ever touching it. Reading it before writing it is a non-negotiable discipline.

STEPS
1. Open the configuration file for reading only (do not edit):
       sudo less /etc/postgresql/XX/main/postgresql.conf

2. Locate and write down the current values for these parameters:
       listen_addresses     — which IPs the server listens on
       port                 — TCP port (default 5432)
       max_connections      — max simultaneous connections
       shared_buffers       — memory for caching data
       work_mem             — memory per sort/hash operation
       maintenance_work_mem — memory for maintenance tasks (VACUUM etc.)
       wal_level            — WAL verbosity (minimal/replica/logical)
       max_wal_size         — max size before checkpoint is triggered
       checkpoint_timeout   — max time between automatic checkpoints
       log_min_duration_statement — log queries slower than this (ms)

3. Notice how commented-out lines (starting with #) show defaults.
   Note which of the above are currently commented out vs active.

4. Query the live running values from inside psql (safer than reading file):
       sudo -u postgres psql -c "SHOW ALL;" | grep -E \
       "listen_addresses|max_connections|shared_buffers|work_mem|wal_level"

5. Compare: does the file value match the running value? Note any differences.

SAFETY
Risk: None
Reading the file with "less" and querying with SHOW ALL are completely safe.
Do not edit the file during this task.

SKILL BUILT
Area  : Database Server / Instance
Skill : postgresql.conf structure awareness and key instance-level parameters

TASK TITLE: Identify What Databases Exist Inside the Instance
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Before managing anything, a DBA must be able to enumerate what is running
inside an instance. Knowing the system databases (template0, template1,
postgres) versus user databases is essential for safe operation.

STEPS
1. Connect to the instance as the postgres superuser:
       sudo -u postgres psql

2. List all databases:
       \l
   Or for more detail:
       \l+

3. Record for each database:
       - Name
       - Owner
       - Encoding
       - Collate / Ctype
       - Size (from \l+)
       - Access privileges

4. Identify these special system databases and understand their role:
       template0  — pristine template, cannot be connected to normally,
                    used as the base when creating new DBs with custom encoding
       template1  — default template for new databases, can be modified
       postgres   — default admin database, used for initial connections

5. Check the OID (object identifier) of each database:
       SELECT oid, datname, datdba, pg_size_pretty(pg_database_size(datname))
       FROM pg_database;

6. Exit psql:
       \q

SAFETY
Risk: None
Read-only queries inside psql. No changes made.

Area  : Database Server / Instance
Skill : Instance-level database enumeration and system database awareness

REVIEW QUESTION

TASK TITLE: Locate and Understand the WAL Directory
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
The Write-Ahead Log (WAL) is the heartbeat of PostgreSQL's durability and
replication system. A DBA must know where it lives, what it looks like, and
why it must never be deleted manually. Disk space issues in pg_wal have
caused production outages.

STEPS
1. Navigate to the WAL directory (replace XX and cluster name):
       sudo ls -lh /var/lib/postgresql/XX/main/pg_wal/

2. Note the following:
       - Filename format: 24-character hex strings (e.g., 000000010000000000000001)
       - Each WAL segment is 16MB by default
       - How many segments currently exist
       - Total size of the pg_wal directory

3. Check the WAL segment size configured on this instance:
       sudo -u postgres psql -c "SHOW wal_segment_size;"

4. Understand WAL filenames. Each 24-char name contains:
       - First 8 chars: timeline ID
       - Next 8 chars: WAL log number
       - Last 8 chars: segment number within that log
   Look at a real filename from step 1 and decode its parts.

5. Check current WAL-related settings:
       sudo -u postgres psql -c "SHOW wal_level;"
       sudo -u postgres psql -c "SHOW archive_mode;"
       sudo -u postgres psql -c "SHOW max_wal_size;"
       sudo -u postgres psql -c "SHOW min_wal_size;"

6. Check the current WAL write position:
       sudo -u postgres psql -c "SELECT pg_current_wal_lsn();"

SAFETY
Risk: None (read-only observation)
NEVER delete files from pg_wal manually. This task only reads the directory.

SKILL BUILT
Area  : Database Server / Instance
Skill : WAL directory structure, segment format, and WAL configuration awareness

REVIEW QUESTION

TASK TITLE: Identify System Catalog Views That Describe the Instance State
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
PostgreSQL exposes all its internal state through system catalog views.
A DBA at any level must know which views to query first when assessing
the health of an instance. These are your instruments panel.

STEPS
1. Connect to the instance:
       sudo -u postgres psql

2. Run each query and note what it tells you:

   -- Instance uptime and server start time:
   SELECT pg_postmaster_start_time(),
          now() - pg_postmaster_start_time() AS uptime;

   -- PostgreSQL version string:
   SELECT version();

   -- Current active connections:
   SELECT count(*) FROM pg_stat_activity;

   -- All current connections with state:
   SELECT pid, usename, application_name, client_addr, state, wait_event_type
   FROM pg_stat_activity
   ORDER BY state;

   -- Instance-level statistics (resets on restart):
   SELECT * FROM pg_stat_bgwriter;

   -- Current WAL receiver status (shows if this is a replica):
   SELECT * FROM pg_stat_wal_receiver;

   -- Current WAL sender status (shows if this is a primary with replicas):
   SELECT * FROM pg_stat_replication;

   -- Tablespace locations:
   SELECT spcname, pg_tablespace_location(oid) FROM pg_tablespace;

3. Exit psql:
       \q

SAFETY
Risk: None
All SELECT-only queries against system catalog views.

SKILL BUILT
Area  : Database Server / Instance
Skill : System catalog awareness — instance health views and what they reveal

REVIEW QUESTION

a connection? What states can you see, and which state would concern you
most if you saw many connections stuck in it?

TASK TITLE: Discover How Databases Are Structured Inside PostgreSQL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Provisioning starts with knowing how PostgreSQL organises databases on disk
and in its catalogs. Each database is isolated in storage and catalog —
understanding this prevents mistakes when provisioning or deprovisioning.

STEPS
1. Connect as postgres superuser:
       sudo -u postgres psql

2. List all databases with their OIDs:
       SELECT oid, datname FROM pg_database ORDER BY oid;

3. Note the OID of a user database (not template0/template1/postgres).
   Then find its physical location on disk — each database has its own
   directory under base/ named after its OID:
       \q
       sudo ls /var/lib/postgresql/XX/main/base/

4. Compare the OID numbers from pg_database to the directory names under
   base/. They should match.

5. Return to psql and check the default tablespace:
       sudo -u postgres psql -c \
       "SELECT spcname, pg_tablespace_location(oid) FROM pg_tablespace;"

6. Understand the two built-in tablespaces:
       pg_default — where user databases and tables go by default
       pg_global  — where global system catalogs go (pg_database, pg_authid)

SAFETY
Risk: None
Read-only catalog queries and directory listing.

SKILL BUILT

       local  all        all              peer

       host   — TCP/IP connections (cleartext or SSL)

       peer   — OS username must match PG username (local only)
       md5    — MD5 hashed password

       reject — always denied

       grep postgres /etc/postgresql/XX/main/pg_hba.conf

TASK TITLE: Understand Password Storage and Authentication Methods
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
PostgreSQL supports multiple password hashing methods. Using weak methods
(MD5) instead of strong ones (SCRAM-SHA-256) is a security vulnerability.
A DBA must know what is in use and how to identify which method each
user's password is stored with.

STEPS
1. Connect as superuser:
       sudo -u postgres psql

2. Check what password encryption method is currently configured:
       SHOW password_encryption;

3. Look at stored password hashes for login roles
   (pg_authid is superuser-only):
       SELECT rolname,
              CASE
                WHEN rolpassword IS NULL THEN 'no password'
                WHEN rolpassword LIKE 'SCRAM-SHA-256$%' THEN 'scram-sha-256'
                WHEN rolpassword LIKE 'md5%' THEN 'md5 (weak)'
                ELSE 'unknown'
              END AS password_method
       FROM pg_authid
       WHERE rolcanlogin = true;

4. Note which roles are using MD5 (weak) vs SCRAM-SHA-256 (strong).

5. Check the current setting for password_encryption in postgresql.conf:
       grep password_encryption /etc/postgresql/XX/main/postgresql.conf

6. Check pg_hba.conf to see what authentication methods are accepted:
       grep -v "^#" /etc/postgresql/XX/main/pg_hba.conf | grep -v "^$"

7. Understand the difference:
       md5          — password sent as MD5 hash, weak, deprecated
       scram-sha-256 — challenge-response, much stronger, use this
       peer         — OS user identity, no password over wire

Risk: None

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
PostgreSQL security is not only inside the database. The OS user, file
permissions, and socket permissions are part of the security perimeter.
If OS-level controls are weak, database-level controls can be bypassed.

STEPS
1. Check the OS user PostgreSQL runs as:
       ps aux | grep postmaster | grep -v grep

2. Check the postgres OS user's properties:
       id postgres
       getent passwd postgres

3. Verify the data directory permissions (only postgres user should own it):
       ls -la /var/lib/postgresql/
       ls -la /var/lib/postgresql/XX/
       sudo ls -la /var/lib/postgresql/XX/main/

   Expected: owner = postgres, permissions = 700 (drwx------)
   Any other permissions are a security finding.

4. Check the Unix socket file:
       ls -la /var/run/postgresql/
   Note the socket file (e.g., .s.PGSQL.5432) and its permissions.

5. Check the config file permissions — only root and postgres should read them:
       ls -la /etc/postgresql/XX/main/

6. Verify PostgreSQL is not running as root (this would be a critical finding):
       ps aux | grep "postgres" | grep -v grep | awk '{print $1}'

7. Check if the postgres OS user has a shell or can be su'd to:
       grep postgres /etc/passwd
   Ideally shell should be /bin/bash or /bin/sh — but login should be
   restricted via sudo policy, not by setting nologin on the postgres user.

       grep -E "^log_connections|^log_disconnections|^log_duration|\

       sudo tail -30 /var/log/postgresql/postgresql-XX-main.log \
       | grep -E "connection|authentication|password"

       - Who disconnects?
       - What SQL is being run?
       - Failed authentication attempts?

TASK TITLE: Survey Object-Level Privileges on Key System Objects
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

every object (tables, schemas, functions). A DBA must understand how to
read these grants and spot privilege escalation paths (e.g., PUBLIC having
access to sensitive schemas or functions).

STEPS
1. Connect to psql:
       sudo -u postgres psql

2. Check schema-level privileges on the public schema:
       \dn+ public
   Or:
       SELECT nspname,
              nspacl
       FROM pg_namespace
       WHERE nspname = 'public';

   Note: In PostgreSQL 15+, the PUBLIC role no longer has CREATE on public
   schema by default. In earlier versions it does — this is a security issue.

3. Check what privileges PUBLIC has by default:
       SHOW search_path;
       SELECT has_schema_privilege('public','public','CREATE') AS public_can_create;

4. List grants on a user table if one exists:
       \c yourdatabase
       \dp yourtable

5. Check if PUBLIC has been granted any dangerous privileges:
       SELECT grantee, table_schema, table_name, privilege_type
       FROM information_schema.role_table_grants
       WHERE grantee = 'PUBLIC';

6. Check function security — look for SECURITY DEFINER functions
   (these run with owner privileges, a common privilege escalation vector):
       SELECT proname, prosecdef, proowner::regrole
       FROM pg_proc
       WHERE prosecdef = true;

TASK TITLE: Understand pg_dump Output Formats and What They Contain
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
pg_dump has multiple output formats, and choosing the wrong one makes
restore operations harder, slower, or impossible in some scenarios. A DBA
must understand what each format produces before running their first backup.

STEPS
1. Read the format options for pg_dump:
       pg_dump --help | grep -A2 "\-F"

2. Understand the four formats:
       -Fp  plain     — human-readable SQL text file
       -Fc  custom    — compressed binary, supports parallel restore
       -Fd  directory — one file per object, supports parallel restore
       -Ft  tar       — TAR archive, limited flexibility

3. Create a test backup of the postgres database in each format
   (these are small and safe on an idle instance):
       sudo -u postgres pg_dump -Fp postgres > /tmp/test_plain.sql
       sudo -u postgres pg_dump -Fc postgres > /tmp/test_custom.dump
       sudo -u postgres pg_dump -Fd postgres -f /tmp/test_dir_dump/

4. Compare the sizes:
       ls -lh /tmp/test_plain.sql /tmp/test_custom.dump
       du -sh /tmp/test_dir_dump/

5. Look at the plain SQL backup to understand its structure:
       head -60 /tmp/test_plain.sql

6. Use pg_restore to inspect the contents of the custom format without
   actually restoring it:
       pg_restore -l /tmp/test_custom.dump | head -40

7. Clean up:
       rm /tmp/test_plain.sql /tmp/test_custom.dump
       rm -rf /tmp/test_dir_dump/

SAFETY
Risk: Low
Backup operations are read-only — they do not modify the source database.
The /tmp directory is used only; no production paths are written to.

TASK TITLE: Locate and Understand WAL Archiving Configuration
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
WAL archiving is what enables Point-in-Time Recovery (PITR). Without it,
you can only restore to the moment of the last full backup, not to any
arbitrary point in time. A DBA must know whether archiving is active
and how it is configured.

STEPS
1. Check whether WAL archiving is enabled:
       sudo -u postgres psql -c "SHOW archive_mode;"
       sudo -u postgres psql -c "SHOW archive_command;"

2. Check the WAL level (archiving requires at minimum 'replica'):
       sudo -u postgres psql -c "SHOW wal_level;"

3. Check archive_mode and archive_command in the config file:
       grep -E "archive_mode|archive_command|archive_library" \
       /etc/postgresql/XX/main/postgresql.conf

4. Understand what archive_command does:
       - PostgreSQL calls this shell command once per WAL segment
       - The command must copy the WAL file to a safe archive location
       - If the command returns non-zero, PostgreSQL retries and cannot
         recycle the WAL segment (pg_wal grows until archiving succeeds)

5. Check the current archive status from inside psql:
       sudo -u postgres psql -c "SELECT * FROM pg_stat_archiver;"
   Note:
       archived_count  — number of successfully archived WAL files
       last_archived_wal — most recently archived file
       failed_count     — number of failed archive attempts (non-zero = problem)
       last_failed_wal  — last file that failed to archive

6. Check if an archive directory has been set up on this system:
       ls /var/lib/postgresql/archive/ 2>/dev/null || \
       echo "No archive directory found at default path"

TASK TITLE: Understand VACUUM and Its Role in PostgreSQL Data Management
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
PostgreSQL uses MVCC (Multi-Version Concurrency Control), which means deleted
and updated rows are not removed immediately — they become "dead tuples."
VACUUM is what reclaims this space. Without it, tables bloat and queries slow
down. A DBA must understand this before managing any active database.

STEPS
1. Understand MVCC dead tuples at a high level:
       sudo -u postgres psql -c \
       "SELECT relname,
               n_live_tup,
               n_dead_tup,
               last_vacuum,
               last_autovacuum,
               last_analyze,
               last_autoanalyze
        FROM pg_stat_user_tables
        ORDER BY n_dead_tup DESC;"

2. Check autovacuum configuration:
       sudo -u postgres psql -c \
       "SELECT name, setting, unit
        FROM pg_settings
        WHERE name LIKE 'autovacuum%'
        ORDER BY name;"

3. Check if autovacuum is enabled:
       sudo -u postgres psql -c "SHOW autovacuum;"

4. Look at the autovacuum worker processes currently running:
       sudo -u postgres psql -c \
       "SELECT pid, query, state, wait_event_type, wait_event
        FROM pg_stat_activity
        WHERE query LIKE 'autovacuum%';"

5. Understand the difference between these VACUUM variants:
       VACUUM          — reclaims dead tuple space (does not return to OS)
       VACUUM FULL     — rewrites the table, returns space to OS (takes lock)
       VACUUM ANALYZE  — vacuums AND updates query planner statistics
       ANALYZE         — only updates planner statistics (no vacuuming)

6. Check for tables that have not been vacuumed recently:
       sudo -u postgres psql -c \
       "SELECT relname, last_autovacuum, n_dead_tup
        FROM pg_stat_user_tables
        WHERE last_autovacuum IS NULL
           OR last_autovacuum < now() - interval '7 days'
        ORDER BY n_dead_tup DESC;"

SAFETY
Risk: None
Read-only catalog queries. No VACUUM commands are run in this task.

TASK TITLE: Understand Table and Index Bloat Using System Catalogs
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Bloat is wasted space inside tables and indexes that PostgreSQL cannot reuse
for new data without VACUUM. Undetected bloat degrades query performance and
wastes disk. A DBA must be able to identify and quantify it.

STEPS
1. Connect to a user database (or postgres if no other exists):
       sudo -u postgres psql -d postgres

2. Check table sizes including total size (data + indexes + TOAST):
       SELECT schemaname,
              relname AS tablename,
              pg_size_pretty(pg_relation_size(schemaname||'.'||relname)) AS table_size,
              pg_size_pretty(pg_indexes_size(schemaname||'.'||relname)) AS index_size,
              pg_size_pretty(pg_total_relation_size(schemaname||'.'||relname)) AS total_size
       FROM pg_stat_user_tables
       ORDER BY pg_total_relation_size(schemaname||'.'||relname) DESC
       LIMIT 10;

3. Look at live vs dead tuple ratios (a sign of bloat):
       SELECT relname,
              n_live_tup,
              n_dead_tup,
              CASE WHEN n_live_tup + n_dead_tup > 0
                   THEN round(100.0 * n_dead_tup / (n_live_tup + n_dead_tup), 2)
                   ELSE 0
              END AS dead_pct
       FROM pg_stat_user_tables
       ORDER BY dead_pct DESC;

4. Check index sizes and look for bloated indexes:
       SELECT indexname,
              pg_size_pretty(pg_relation_size(indexname::regclass)) AS index_size
       FROM pg_indexes
       WHERE schemaname NOT IN ('pg_catalog','information_schema')
       ORDER BY pg_relation_size(indexname::regclass) DESC
       LIMIT 10;

5. Check the pg_freespace extension if available (shows free space per page):
       -- Note: pgstattuple extension needed for deep bloat analysis
       -- Check if it is installed:
       SELECT * FROM pg_available_extensions WHERE name = 'pgstattuple';

SAFETY
Risk: None
Read-only catalog queries.

TASK TITLE: Understand Checksums and Data Integrity Verification
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Data checksums detect silent data corruption (bit rot, storage controller
failures) before corrupted data is read by an application. A DBA must know
whether checksums are enabled and what tools exist for consistency checking.

STEPS
1. Check if data checksums are enabled on this cluster:
       sudo -u postgres psql -c "SHOW data_checksums;"
   Or check the control file:
       sudo -u postgres pg_controldata /var/lib/postgresql/XX/main/ \
       | grep checksum

2. Understand what checksums protect against:
       - Checksums are written on each 8KB data page when data is written
       - When the page is read, the checksum is verified
       - If it does not match, PostgreSQL raises a checksum failure error
       - Without checksums, silent corruption goes undetected

3. Check if pg_checksums is available (PostgreSQL 12+ tool):
       pg_checksums --help | head -20
   (This tool can verify or enable checksums offline)

4. Check the pg_stat_database view for checksum failures:
       sudo -u postgres psql -c \
       "SELECT datname, checksum_failures, checksum_last_failure
        FROM pg_stat_database
        WHERE checksum_failures > 0;"
   (No output = no detected failures, which is expected)

5. Understand the consistency checking approach for PostgreSQL:
       - pg_checksums   — offline integrity check of all data files
       - amcheck extension — online B-tree index corruption detection
       - pg_dump        — a successful dump is an indirect consistency check

6. Check if the amcheck extension is available:
       sudo -u postgres psql -c \
       "SELECT * FROM pg_available_extensions WHERE name = 'amcheck';"

WHY THIS MATTERS

must know what each view reveals before being able to diagnose a performance
problem. These views are your cockpit instruments.

STEPS

2. List all available pg_stat_* and pg_statio_* views:
       SELECT viewname
       FROM pg_views
       WHERE viewname LIKE 'pg_stat%' OR viewname LIKE 'pg_statio%'
       ORDER BY viewname;

3. Query each of these key performance views and read the output:

   -- Active sessions and their state:
   SELECT pid, usename, state, wait_event_type, wait_event, query_start,
          left(query, 60) AS query_snippet
   FROM pg_stat_activity
   WHERE state != 'idle'
   ORDER BY query_start;

   -- Database-level statistics:
   SELECT datname, numbackends, xact_commit, xact_rollback,
          blks_read, blks_hit,
          round(100.0 * blks_hit / NULLIF(blks_hit + blks_read, 0), 2)
          AS cache_hit_ratio
   FROM pg_stat_database
   WHERE datname NOT LIKE 'template%';

   SELECT relname, seq_scan, seq_tup_read,
          idx_scan, idx_tup_fetch,
          n_tup_ins, n_tup_upd, n_tup_del
   FROM pg_stat_user_tables
   ORDER BY seq_scan DESC;

   SELECT indexrelname, idx_scan, idx_tup_read, idx_tup_fetch
   FROM pg_stat_user_indexes
   ORDER BY idx_scan DESC;

WHY THIS MATTERS

incidents. Each connection consumes memory. A DBA must understand connection
limits, current usage, connection states, and why connection poolers exist.

STEPS

       sudo -u postgres psql -c \
       "SELECT max_conn, used, res_for_super,
               max_conn - used - res_for_super AS available
        FROM
          (SELECT setting::int AS max_conn FROM pg_settings
           WHERE name = 'max_connections') m,
          (SELECT count(*) AS used FROM pg_stat_activity) u,
          (SELECT setting::int AS res_for_super FROM pg_settings

       sudo -u postgres psql -c \
       "SELECT state, count(*)
        FROM pg_stat_activity
        GROUP BY state
        ORDER BY count DESC;"

       idle             — connected but not doing anything
       idle in transaction — in a BEGIN block, waiting (dangerous if old)

       fastpath function call — executing a fast-path function
       disabled         — session is disabled

       sudo -u postgres psql -c \
       "SELECT pid, usename, state,
               now() - state_change AS idle_duration,
               left(query, 60) AS last_query
        FROM pg_stat_activity
        WHERE state = 'idle in transaction'
           OR (state = 'idle' AND state_change < now() - interval '1 hour')
        ORDER BY idle_duration DESC;"

       sudo -u postgres psql -c \

TASK TITLE: Identify Locks and Lock Contention Using System Views
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Lock contention is a major cause of PostgreSQL performance degradation and
application timeouts. A DBA must be able to identify what is locked, who is
waiting, and who is blocking whom — even before knowing how to resolve it.

STEPS
1. View all current locks in the system:
       sudo -u postgres psql -c \
       "SELECT pid, relation::regclass, locktype, mode, granted
        FROM pg_locks
        WHERE relation IS NOT NULL
        ORDER BY relation, granted DESC;"

2. Find blocking and waiting sessions (the most important lock query):
       sudo -u postgres psql -c \
       "SELECT
          blocked.pid AS blocked_pid,
          blocked.usename AS blocked_user,
          blocked.query AS blocked_query,
          blocking.pid AS blocking_pid,
          blocking.usename AS blocking_user,
          blocking.query AS blocking_query
        FROM pg_stat_activity blocked
        JOIN pg_stat_activity blocking
          ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
        WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;"

3. Understand PostgreSQL lock types:
       AccessShareLock     — SELECT holds this; blocks nothing except AccessExclusiveLock
       RowShareLock        — SELECT FOR UPDATE
       RowExclusiveLock    — INSERT/UPDATE/DELETE
       ShareLock           — CREATE INDEX (non-concurrent)
       AccessExclusiveLock — ALTER TABLE, DROP, TRUNCATE; blocks everything

4. Check the lock_timeout and deadlock_timeout settings:
       sudo -u postgres psql -c "SHOW lock_timeout;"
       sudo -u postgres psql -c "SHOW deadlock_timeout;"

5. Look in the server log for any recent deadlock messages:
       sudo grep -i deadlock /var/log/postgresql/postgresql-XX-main.log \
       | tail -10

TASK TITLE: Understand I/O Metrics Using pg_statio and OS Tools
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Disk I/O is often the true bottleneck for database performance. A DBA must
be able to identify which tables and indexes are generating the most I/O,
and correlate that with OS-level disk activity.

STEPS
1. Connect to psql and check I/O statistics per table:
       sudo -u postgres psql -c \
       "SELECT relname,
               heap_blks_read  AS heap_disk_reads,
               heap_blks_hit   AS heap_cache_hits,
               idx_blks_read   AS idx_disk_reads,
               idx_blks_hit    AS idx_cache_hits
        FROM pg_statio_user_tables
        ORDER BY heap_blks_read + idx_blks_read DESC
        LIMIT 10;"

2. Understand what the metrics mean:
       *_blks_read  — blocks that had to be fetched from disk (slow)
       *_blks_hit   — blocks found in shared_buffers cache (fast)
   High blks_read / low blks_hit = cache miss = disk pressure

3. Calculate per-table cache hit ratio:
       sudo -u postgres psql -c \
       "SELECT relname,
               round(100.0 * heap_blks_hit
                     / NULLIF(heap_blks_hit + heap_blks_read, 0), 2)
               AS cache_hit_pct
        FROM pg_statio_user_tables
        WHERE heap_blks_hit + heap_blks_read > 0
        ORDER BY cache_hit_pct;"

4. From the OS, check real-time disk I/O:
       iostat -x 2 3
   (If iostat is not available: sudo apt-get install sysstat)

5. Check which PostgreSQL files are largest (most I/O candidates):
       sudo du -sh /var/lib/postgresql/XX/main/base/*/ 2>/dev/null \
       | sort -h | tail -10

6. Check the current shared_buffers size (main cache):
       sudo -u postgres psql -c "SHOW shared_buffers;"

               calls,

TASK TITLE: Understand Checkpoint Behaviour and Its Performance Impact
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Checkpoints are the periodic events where PostgreSQL flushes dirty data pages
to disk. Frequent or poorly-timed checkpoints cause I/O spikes that affect
query latency. A DBA must be able to see checkpoint activity and understand
what it tells them about the write load.

STEPS
1. Check current checkpoint configuration:
       sudo -u postgres psql -c "SHOW checkpoint_timeout;"
       sudo -u postgres psql -c "SHOW max_wal_size;"
       sudo -u postgres psql -c "SHOW min_wal_size;"
       sudo -u postgres psql -c "SHOW checkpoint_completion_target;"

2. Query checkpoint statistics:
       sudo -u postgres psql -c \
       "SELECT checkpoints_timed,
               checkpoints_req,
               checkpoint_write_time,
               checkpoint_sync_time,
               buffers_checkpoint,
               buffers_clean,
               buffers_backend,
               buffers_alloc
        FROM pg_stat_bgwriter;"

3. Understand the metrics:
       checkpoints_timed — triggered by checkpoint_timeout (expected)
       checkpoints_req   — triggered by WAL size (too frequent = concern)
       buffers_backend   — pages written directly by backends (bad — means
                           checkpoint is not keeping up with writes)

4. Check if checkpoints are being logged:
       grep "log_checkpoints" /etc/postgresql/XX/main/postgresql.conf
       sudo -u postgres psql -c "SHOW log_checkpoints;"

5. If log_checkpoints = on, look for checkpoint log entries:
       sudo grep "checkpoint" /var/log/postgresql/postgresql-XX-main.log \
       | tail -10

6. Understand checkpoint_completion_target:
       - This spreads the checkpoint I/O across a fraction of the
         checkpoint interval to avoid a burst of I/O at the end
       - Default is 0.9 (spread across 90% of the interval)
       - Lower values = more bursty I/O

TASK TITLE: Locate and Inventory All Existing Backup Files
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Before testing DR or PITR, a DBA must know what backups actually exist,
how old they are, and whether they are complete. Many outages are worsened
because backup files assumed to exist are missing, corrupted, or outdated.

STEPS
1. Search common backup locations on the system:
       sudo find /var/backups/ -name "*.dump" -o -name "*.sql" \
       -o -name "*.tar" 2>/dev/null | head -20

       sudo find /home/ -name "*.dump" -o -name "*.sql" 2>/dev/null | head -10

       sudo find /tmp/ -name "*.dump" -o -name "*.sql" 2>/dev/null | head -10

2. Check if there is a dedicated backup directory for PostgreSQL:
       ls -lah /var/lib/postgresql/backup/ 2>/dev/null || \
       echo "No /var/lib/postgresql/backup/ directory"

       ls -lah /opt/pgbackup/ 2>/dev/null || \
       echo "No /opt/pgbackup/ directory"

3. Check for any scheduled backup jobs (cron):
       sudo crontab -l 2>/dev/null | grep -i "pg_dump\|pgbackup\|backup"
       sudo crontab -u postgres -l 2>/dev/null | grep -i backup
       ls /etc/cron.d/ | xargs -I{} grep -li "postgres\|pg_dump" /etc/cron.d/{} \
       2>/dev/null

4. Check systemd timers (modern Debian uses these instead of cron):
       systemctl list-timers | grep -i "pg\|backup\|postgres"

5. For each backup file found, record:
       - Location
       - Size
       - Last modified date
       - Type (dump/sql/basebackup)
       - Whether it is inside or outside the data directory

SAFETY
Risk: None
Read-only file system search. No backup operations executed.

TASK TITLE: Understand and Check the pg_controldata State of the Cluster
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
pg_controldata reads the cluster's control file, which contains the most
critical metadata: last checkpoint, WAL position, instance state, and data
format version. A DBA needs this for backup validation, DR readiness checks,
and post-crash assessment.

STEPS
1. Run pg_controldata and capture its output:
       sudo -u postgres pg_controldata /var/lib/postgresql/XX/main/

2. Locate and understand each of these key fields in the output:
       pg_control version number    — internal format version
       Catalog version number       — system catalog version
       Database system identifier   — unique ID of this cluster
       Database cluster state       — should be "in production"
       Latest checkpoint location   — WAL LSN of last checkpoint
       Prior checkpoint location    — WAL LSN of the prior checkpoint
       Latest checkpoint's REDO location — where replay starts from
       Database block size          — page size (usually 8192)
       WAL block size               — WAL page size
       Bytes per WAL segment        — WAL segment size
       Maximum length of identifiers
       Data page checksum version   — 0 = no checksums, 1 = checksums on

3. Note the "Database cluster state". Valid values are:
       in production              — running normally
       in crash recovery          — recovering from crash
       shut down                  — cleanly shut down (good for backup)
       shut down in recovery      — was a standby when shut down

4. Note the "Data page checksum version":
       0 means checksums are OFF (no corruption detection)
       1 means checksums are ON (recommended)

5. Save the output to a file for your records:
       sudo -u postgres pg_controldata /var/lib/postgresql/XX/main/ \
       > /tmp/controldata_snapshot.txt
       cat /tmp/controldata_snapshot.txt | wc -l

SAFETY
Risk: None
pg_controldata is a read-only tool that does not modify the cluster.

TASK TITLE: Identify Installed Extensions and Version Compliance
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Extensions can lag behind the major PostgreSQL version, break during upgrades,
or introduce security vulnerabilities. A DBA must maintain an inventory of
all installed extensions, their versions, and where they are deployed.

STEPS
1. Connect to psql and list all available extensions:
       sudo -u postgres psql -c \
       "SELECT name, default_version, installed_version, comment
        FROM pg_available_extensions
        ORDER BY installed_version DESC NULLS LAST, name;"

2. List only INSTALLED extensions (installed_version is not null):
       sudo -u postgres psql -c \
       "SELECT name, default_version, installed_version,
               CASE WHEN installed_version != default_version
                    THEN 'UPDATE AVAILABLE'
                    ELSE 'current'
               END AS status
        FROM pg_available_extensions
        WHERE installed_version IS NOT NULL
        ORDER BY name;"

3. Check across all databases (must connect to each one):
   For each database in your cluster:
       sudo -u postgres psql -d yourdatabase -c \
       "SELECT extname, extversion, n.nspname AS schema
        FROM pg_extension e
        JOIN pg_namespace n ON e.extnamespace = n.oid
        ORDER BY extname;"

4. Note any extensions with an update available
   (installed_version != default_version).

5. Check the PostgreSQL server version vs installed package version:
       sudo -u postgres psql -c "SELECT version();"
       dpkg -l | grep postgresql-XX

6. Check if there are any extension script files for upgrades:
       ls /usr/share/postgresql/XX/extension/ | grep "\.sql" | head -20

Risk: None
Read-only catalog queries and file listing.

TASK TITLE: Survey the PostgreSQL Activity Log for Maintenance Events
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
The server log is the audit trail for maintenance activities — when were
backups taken, when did autovacuum run, when did checkpoints occur, when
were connections refused? A DBA must be able to extract maintenance-relevant
events from the log as part of compliance and DR readiness reporting.

STEPS
1. View the last 100 lines of the PostgreSQL log:
       sudo tail -100 /var/log/postgresql/postgresql-XX-main.log

2. Search for checkpoint events in the log:
       sudo grep -i "checkpoint" \
       /var/log/postgresql/postgresql-XX-main.log | tail -20

3. Search for autovacuum events:
       sudo grep -i "autovacuum" \
       /var/log/postgresql/postgresql-XX-main.log | tail -20

4. Search for connection events (logins/logouts):
       sudo grep -E "connection received|connection authorized|disconnection" \
       /var/log/postgresql/postgresql-XX-main.log | tail -20

5. Search for any error or fatal events in the last 24 hours:
       sudo grep -E "ERROR|FATAL|PANIC" \
       /var/log/postgresql/postgresql-XX-main.log | tail -30

6. Determine the log rotation policy:
       ls -lh /var/log/postgresql/
       grep "log_filename\|log_rotation" \
       /etc/postgresql/XX/main/postgresql.conf

7. Note: For compliance, how long are logs being retained? Is there
   any log shipping to a central syslog or SIEM?
       grep "syslog" /etc/postgresql/XX/main/postgresql.conf

Risk: None
Read-only log file inspection.

TASK TITLE: Understand Replication Setup Awareness for DR Readiness
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY THIS MATTERS
Disaster Recovery depends on either a hot standby replica or a reliable
PITR-capable backup chain. A DBA must know whether replication is configured,
what type it is, and whether it is healthy — before an incident, not during one.

STEPS
1. Check if this instance is a primary (has standbys):
       sudo -u postgres psql -c "SELECT * FROM pg_stat_replication;"
   Empty result = no standbys currently connected.

2. Check if this instance is a standby (replica):
       sudo -u postgres psql -c "SELECT pg_is_in_recovery();"
   TRUE = this is a standby/replica
   FALSE = this is a primary

3. If this is a standby, check replication status:
       sudo -u postgres psql -c "SELECT * FROM pg_stat_wal_receiver;"

4. Check replication-related configuration parameters:
       sudo -u postgres psql -c \
       "SELECT name, setting
        FROM pg_settings
        WHERE name IN (
          'wal_level','max_wal_senders','wal_keep_size',
          'hot_standby','primary_conninfo','recovery_target_timeline'
        );"

5. Check for standby signal or recovery files:
       sudo ls -la /var/lib/postgresql/XX/main/standby.signal 2>/dev/null || \
       echo "No standby.signal — this is not configured as a standby"

       sudo ls -la /var/lib/postgresql/XX/main/recovery.signal 2>/dev/null || \
       echo "No recovery.signal"

6. Understand the two main replication types:
       Streaming replication — WAL is streamed in real-time to standby
       Logical replication  — only specific table changes are replicated
