SECTION 1: FIRST PRINCIPLES
================================================================================

Before we discuss configurations, we must understand WHY these layers exist.

1.1 THE FUNDAMENTAL PROBLEM: ISOLATION AND RESOURCE PROTECTION
================================================================================

In a shared Linux system, multiple processes compete for finite resources:
  - CPU scheduling time
  - Memory (physical RAM)
  - Disk I/O capacity
  - Open file descriptors
  - Process count per user
  - Virtual memory mappings

Without boundaries, a single misbehaving or resource-hungry process could
consume all system resources, destroying the entire system—including other
processes running on it (like web applications, monitoring agents, etc.).

QUESTION FOR YOU:
  If PostgreSQL crashes or enters an infinite loop consuming memory, what should
  happen to other services on that same machine? Should the kernel OOM-kill
  PostgreSQL, or should it destroy the web application instead?

The answer to this question drives the entire design of OS-level resource
isolation.


1.2 THE UNIX PERMISSION MODEL: WHY A SEPARATE USER?
================================================================================

PostgreSQL runs as the "postgres" OS user (not root). This is NOT primarily
for convenience—it's a security boundary.

THINK ABOUT:
  - PostgreSQL's codebase is ~500k lines. What if a vulnerability exists?
  - If PostgreSQL runs as root and is exploited, the attacker becomes root.
  - If PostgreSQL runs as "postgres" user, the attacker has only "postgres"
    permissions.

This is **privilege separation** or **principle of least privilege**.

But there's a deeper layer: the OS kernel enforces this isolation using:
  - User ID (UID) tables in the kernel
  - File system permissions (rwx bits)
  - Process accounting per UID
  - Resource limits per UID (this is where ulimits come in)

CRITICAL INSIGHT:
  The "postgres" user is NOT just a label in /etc/passwd. It's a UID that the
  kernel itself knows about. Every process has a UID baked into its task_struct.
  The kernel checks this UID on EVERY system call.


1.3 RESOURCE LIMITS (ULIMITS): WHY THEY EXIST
================================================================================

Even with a separate user, PostgreSQL could still exhaust system resources.
Ulimits are a SECOND LAYER of protection—per-process limits.

Two mechanisms:
  a) Hard limits (ceiling): Process cannot exceed this
  b) Soft limits (warning): Process can temporarily exceed, but kernel may
     enforce or warn

Why two limits?
  - Soft limits allow graceful degradation
  - Hard limits prevent catastrophic failure
  - A process can lower its own soft limit, but not raise its hard limit
    (permission model again)

Examples of what ulimits control:
  - max open files (nofile): How many file descriptors can one process open?
  - max processes (nproc): How many child processes can fork?
  - max locked memory (memlock): How much memory can be locked to RAM?
  - max virtual memory (as): Total address space a process can allocate

THINK ABOUT EACH ONE:
  
  Why would PostgreSQL need to open files?
    - Each table file descriptor
    - Each index
    - WAL files (Write-Ahead Log)
    - Temporary files for sorts, hash joins
    - Connections to shared memory
    
  If the limit is too low, what happens?
    - New connections fail with "too many open files"
    - Queries fail mid-execution
    - The database becomes degraded without crashing

  Why would PostgreSQL care about nproc (max processes)?
    - PostgreSQL spawns background workers
    - Each client connection is a backend process
    - Autovacuum needs processes
    - Logical replication needs processes


1.4 SYSTEMD SERVICE ENCAPSULATION
================================================================================

Systemd is NOT just a process manager. It's a resource and lifecycle manager.

When you define a systemd service, you're creating:
  1. A logical grouping of processes (cgroup)
  2. A resource allocation contract
  3. A lifecycle (start/stop/restart behavior)
  4. Dependencies and ordering
  5. Isolation boundaries

The key insight: ulimits set on the postgres shell are INHERITED by child
processes. Systemd can also enforce limits at the cgroup level (Linux control
groups), which is STRONGER than ulimits because:
  - Applies to all processes in the service, even if they try to raise limits
  - Can be enforced by the kernel even if the process is privileged
  - Survives across process spawning


SECTION 2: SYSTEM-LEVEL MENTAL MODEL
================================================================================

Let's map these concepts onto Linux architecture.

2.1 THE LAYERED ISOLATION MODEL
================================================================================

┌─────────────────────────────────────────────────────────────────┐
│ APPLICATION LAYER: PostgreSQL code runs here                    │
│ (Reads/writes data, processes queries, manages connections)     │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ PROCESS LAYER: PostgreSQL is a Linux process (PID, memory, etc) │
│ UID = 26 (postgres)                                              │
│ PPID = parent process (systemd service manager)                 │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ LIMIT LAYER: Soft/Hard limits from ulimit (and cgroups)        │
│ Max open files, max processes, max virtual memory, etc.         │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ KERNEL LAYER: Enforces limits via permission checks             │
│ When a process tries to open a file, kernel checks UID perms    │
│ When a process tries to allocate memory, kernel checks limits   │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ HARDWARE LAYER: Physical CPU, RAM, storage                      │
└─────────────────────────────────────────────────────────────────┘


2.2 PROCESS CREATION AND INHERITANCE
================================================================================

When systemd starts PostgreSQL:

  systemd (PID 1, UID=0/root)
      ↓
  [systemd spawns postgres postmaster]
      ↓
  postgres (postmaster, PID=4782, UID=26)
      ↓
  [postmaster forks backend processes]
      ↓
  postgres (backend 1, PID=4783, UID=26) — inherited limits from parent
  postgres (backend 2, PID=4784, UID=26) — inherited limits from parent
  postgres (backend N, PID=4785, UID=26) — inherited limits from parent


KEY INSIGHT: When a process is created (fork/exec), it inherits:
  - The parent's UID
  - The parent's ulimits (soft limits can be raised up to hard limits)
  - The parent's cgroup membership

This is why setting limits on the parent process matters.


2.3 FILE DESCRIPTORS: A CONCRETE EXAMPLE
================================================================================

Let's trace what happens when a query needs to read a table:

  PostgreSQL backend process (PID 4783, UID 26)
      ↓
  Query execution engine calls: open("/var/lib/postgresql/base/16384/16385")
      ↓
  Kernel receives syscall, checks:
    a) Is UID 26 allowed to read this file?
       → Check inode permissions: -rw------- postgres postgres
       → YES (UID 26 owns the file)
    b) Does UID 26 have an available file descriptor slot?
       → Check: current FDs used < limit?
       → If FDs used == limit, EMFILE error (errno 24)
    c) Is there kernel memory to allocate the file descriptor?
       → Check global fd limit and slab allocation
  ↓
  If all checks pass, kernel allocates an fd number (e.g., fd 47)
  and returns it to the process.


The ulimit -n (max open files) is the per-process check in step (b).


2.4 MEMORY AND VIRTUAL ADDRESS SPACE
================================================================================

When PostgreSQL allocates memory (e.g., buffer cache, work_mem):

  PostgreSQL calls: malloc(buffer_size)
      ↓
  Glibc's malloc calls: brk() or mmap()
      ↓
  Kernel receives syscall, checks:
    a) Is this process's total virtual memory < limit (ulimit -v)?
    b) Is there physical RAM available? (or swap space?)
    c) Is this process's RSS (resident set size) < limit (ulimit -m)?
  ↓
  If all pass, kernel allocates virtual address space and possibly
  physical pages (depending on lazy allocation strategy)


CRITICAL SUBTLETY:
  Virtual memory ≠ Physical memory
  
  A process can have 10GB of virtual address space allocated but only use
  100MB of physical RAM. The kernel uses lazy allocation (copy-on-write,
  demand paging).
  
  This means:
    - ulimit -v (virtual memory) can be higher than system RAM
    - ulimit -m (resident set size) limits physical memory, but is less
      commonly used because it's hard to set correctly
    - Swap space affects how the kernel handles memory pressure


2.5 THE RELATIONSHIP BETWEEN UID, CGROUPS, AND ULIMITS
================================================================================

These are THREE DIFFERENT isolation mechanisms:

UID-based isolation:
  - Enforced by kernel at permission level
  - Applies to all processes with that UID system-wide
  - Permanent (user exists until deleted)
  - Granularity: per user

Ulimits:
  - Enforced by kernel at process/session level
  - Applied per-process or per-shell-session
  - Inherited by child processes
  - Can be modified by the process itself (within constraints)
  - Granularity: per process or per login session

Cgroups (Linux control groups):
  - Enforced by kernel at process hierarchy level
  - Applied to groups of processes
  - Survives across process spawning
  - Cannot be modified by the process itself (must be set by systemd/root)
  - Granularity: per service/container

MODERN SYSTEMS TREND: Systemd + cgroups is gradually replacing ulimits
because:
  - Cgroups are more predictable (process can't bypass them)
  - Cgroups apply consistently across process hierarchies
  - But ulimits still matter for backward compatibility and specific limits


SECTION 3: DEEP DIVE PER COMPONENT
================================================================================

3.1 THE POSTGRES OS USER: CREATION AND PERMISSION MODEL
================================================================================

3.1.1 PURPOSE
┈┈┈┈┈┈┈┈┈┈┈┈

The postgres user is a security boundary that implements:
  1. Privilege separation: PostgreSQL doesn't need root privileges
  2. Ownership model: Database files belong to "postgres" user
  3. Process accounting: The kernel tracks resource usage per UID
  4. Permission enforcement: Only postgres user (and root) can access
     database files


3.1.2 INTERNAL WORKING
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

When you run `id postgres`, the kernel looks up:

  /etc/passwd entry:
    postgres:x:26:26:PostgreSQL:/var/lib/postgresql:/bin/bash

  Kernel's user table (in memory):
    UID 26 → "postgres"

Every process has a UID in its task_struct (kernel's representation of the
process). The kernel checks this on every system call:

  syscall: open(path, flags)
    kernel_open_syscall():
      current_task = get_current_process()
      uid = current_task->uid
      inode = lookup_inode(path)
      
      if inode->uid == uid:          # Owner can read/write/execute
        allow based on inode->mode & 0700
      elif inode->gid == current_gid:  # Group can read/write/execute
        allow based on inode->mode & 0070
      else:                           # Others
        allow based on inode->mode & 0007
      
      if not allowed:
        return EACCES (Permission denied)

The key: The kernel ENFORCES this. No amount of code in PostgreSQL can
bypass UID checks—they're baked into the VFS (Virtual File System) layer.


3.1.3 DEPENDENCIES AND INTERACTIONS
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

The postgres user depends on:
  a) /var/lib/postgresql directory ownership (must be postgres:postgres)
  b) /var/log/postgresql directory ownership
  c) /var/run/postgresql directory ownership
  d) No other users having permissions to these directories
  e) Root privilege to create the user (useradd only works as root)

If any of these are wrong:
  - PostgreSQL can't read config files
  - PostgreSQL can't write to data directory
  - PostgreSQL can't create PID file
  - Systemd can't switch to postgres user

The postgres user interacts with:
  - Systemd's User/Group= directive (systemd switches to this user)
  - File system ACLs (if using extended permissions)
  - SELinux contexts (if SELinux is enabled)
  - sudo/sudoers (if you want non-root users to control PostgreSQL)


3.1.4 FAILURE MODES
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Misconfiguration examples:

  WRONG: postgres user doesn't exist
    → systemd start fails with "User not found"
    → PostgreSQL never starts
  
  WRONG: /var/lib/postgresql owned by root
    → PostgreSQL starts but can't read WAL files
    → Database becomes inconsistent
  
  WRONG: /var/lib/postgresql permissions 755 (world-readable)
    → Other users can read database files
    → Data breach
  
  WRONG: postgres user given sudo privileges
    → Any vulnerability in PostgreSQL becomes a privilege escalation
    → Attacker can become root
  
  WRONG: /etc/passwd removed postgres entry but UID 26 still owns files
    → Orphaned files (UID exists, but no name)
    → Hard to troubleshoot, files are still owned by UID 26
    → System shows "26" instead of "postgres" in ls -l


3.1.5 TRADE-OFFS
┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Using a separate user:
  + Limits blast radius of a compromise
  + Prevents accidental permission issues
  + Enforced by the kernel, can't be bypassed by application code
  - One more user to manage in production
  - Adds slight complexity to installation/deployment
  - Requires root privilege to create/delete


3.2 ULIMITS: THE PER-PROCESS RESOURCE CEILING
================================================================================

3.2.1 PURPOSE
┈┈┈┈┈┈┈┈┈┈┈

Ulimits prevent a single process from monopolizing system resources through
hard limits (cannot be exceeded) and soft limits (can be temporarily exceeded
but signal the process).

Each limit is actually a PAIR: (soft, hard)
  - Soft limit: process receives SIGXCPU or SIGXFSZ when exceeded
  - Hard limit: kernel refuses the operation with an error
  - A process can lower soft limit (not raise)
  - A process can't change hard limit (even with root privilege,
    must be set at startup)


3.2.2 KEY ULIMITS FOR POSTGRESQL
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Let's reason about each one:

┌─────────────────────────────────────────────────────────────────┐
│ ulimit -n (RLIMIT_NOFILE): Max open file descriptors           │
├─────────────────────────────────────────────────────────────────┤
│ WHY PostgreSQL needs this:                                      │
│   - Each connection is a backend process                        │
│   - Each backend may open: table files, index files, WAL files │
│   - Temporary files for large sorts, hash joins                │
│   - Shared memory segments (not directly FDs, but related)      │
│                                                                 │
│ What happens if too low:                                        │
│   - "too many open files" errors in PostgreSQL logs            │
│   - New connections rejected mid-query                          │
│   - Autovacuum fails to open table files                       │
│   - Checkpoint process stalls                                   │
│                                                                 │
│ Estimation approach:                                            │
│   Max backends * avg FDs per backend + system overhead         │
│   = (max_connections) * (5-10) + 1000                          │
│   + 1000 for safety margin                                     │
│                                                                 │
│   If max_connections=200, reasonable estimate:                 │
│   200 * 8 + 1000 = 2600 (minimum)                             │
│   Use 4096 or higher to be safe                               │
│                                                                 │
│ System-wide context:                                            │
│   - Global FD limit is in /proc/sys/fs/file-max               │
│   - Default is often 32k on modern systems                     │
│   - Each open file also uses kernel memory (struct file_struct)│
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ ulimit -u (RLIMIT_NPROC): Max number of processes              │
├─────────────────────────────────────────────────────────────────┤
│ WHY PostgreSQL needs this:                                      │
│   - Each client connection = one backend process                │
│   - Autovacuum worker processes                                │
│   - Background writer process                                   │
│   - Checkpoint process                                          │
│   - Logical replication launcher                               │
│   - Parallel query workers (might be separate processes)       │
│                                                                 │
│ What happens if too low:                                        │
│   - "Resource temporarily unavailable" when accepting connections
│   - fork() syscalls fail                                        │
│   - Autovacuum stops working                                    │
│   - Database becomes read-only                                 │
│                                                                 │
│ Estimation approach:                                            │
│   max_connections + background workers + buffer (20%)          │
│   = (max_connections + 20) * 1.2                              │
│                                                                 │
│   If max_connections=200:                                      │
│   (200 + 20) * 1.2 = 264                                      │
│   Use 512 or 1024 to be safe                                  │
│                                                                 │
│ System-wide context:                                            │
│   - Global limit in /proc/sys/kernel/pid_max                  │
│   - Each process has a PID, which is a 32-bit integer          │
│   - Default pid_max = 32768, can be increased                 │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ ulimit -v (RLIMIT_AS): Max virtual address space               │
├─────────────────────────────────────────────────────────────────┤
│ WHY PostgreSQL might need this:                                 │
│   - Limits total memory a process can allocate                 │
│   - Includes: heap, stack, memory-mapped files, shared libs   │
│                                                                 │
│ What happens if too low:                                        │
│   - malloc() fails                                              │
│   - PostgreSQL crashes with "Out of memory"                    │
│   - Queries fail when temp memory is needed                    │
│                                                                 │
│ IMPORTANT SUBTLETY:                                             │
│   Setting -v is TRICKY because:                                │
│   - PostgreSQL needs work_mem * max_connections available     │
│   - Plus buffer cache (shared_buffers)                         │
│   - Plus system libraries (libc, libpq, etc.)                 │
│   - Plus mmap'd files                                          │
│                                                                 │
│   If you set -v to exactly your server RAM, processes will    │
│   OOM when they try to allocate beyond physical RAM.          │
│                                                                 │
│ Better approach:                                                │
│   DON'T use -v at all, OR                                      │
│   Set it to 1.5x-2x system RAM to allow for overcommit        │
│   Let cgroups or the OOM killer handle memory pressure         │
│                                                                 │
│ Modern best practice:                                           │
│   Use systemd MemoryMax= or MemoryHigh= instead of ulimit -v  │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ ulimit -m (RLIMIT_MEMLOCK): Max locked memory                  │
├─────────────────────────────────────────────────────────────────┤
│ WHY relevant for PostgreSQL:                                    │
│   - If you use MADV_DONTDUMP or mlockall() (rare)            │
│   - Prevents memory from being swapped to disk                 │
│   - Useful for latency-critical systems                        │
│                                                                 │
│ What happens if too low:                                        │
│   - mlock() syscalls fail with EAGAIN                          │
│   - Pages get swapped to disk (if using mlockall)             │
│   - Unpredictable latency spikes                               │
│                                                                 │
│ Typical setting:                                                │
│   Set to "unlimited" if you want to lock memory                │
│   Most PostgreSQL instances don't use this                     │
│   Memory locking is a performance optimization, not required   │
│                                                                 │
│ Trade-off:                                                      │
│   + Predictable latency (no page faults)                       │
│   - Reduces available RAM for other processes                  │
│   - Requires CAP_IPC_LOCK capability or root                   │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ ulimit -s (RLIMIT_STACK): Max stack size                       │
├─────────────────────────────────────────────────────────────────┤
│ WHY PostgreSQL cares:                                           │
│   - Stack is used for recursive functions, local variables     │
│   - PostgreSQL has recursive query planning (complex plans)    │
│   - Very deeply nested CTEs (Common Table Expressions)         │
│                                                                 │
│ What happens if too low:                                        │
│   - Segmentation fault (SIGSEGV)                               │
│   - PostgreSQL process dies                                    │
│   - No error message, just disappears                          │
│   - Mistaken for a crash                                       │
│                                                                 │
│ Typical value:                                                  │
│   Default on most systems: 8MB                                 │
│   For PostgreSQL: 8MB is usually fine                          │
│   Only increase if you have specific deeply nested queries     │
│                                                                 │
│ Note:                                                           │
│   Stack is per-thread, not per-process                         │
│   Each PostgreSQL backend is single-threaded (one process)    │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ ulimit -c (RLIMIT_CORE): Max core dump size                    │
├─────────────────────────────────────────────────────────────────┤
│ WHY relevant for PostgreSQL:                                    │
│   - Debugging: core dumps help diagnose crashes                │
│   - Core dump = memory snapshot of process at crash time       │
│                                                                 │
│ What happens if too low (e.g., 0):                             │
│   - PostgreSQL crashes, no core dump created                   │
│   - Lost opportunity to debug                                  │
│                                                                 │
│ Typical setting:                                                │
│   Development: unlimited (allows core dumps)                   │
│   Production: 0 or limited (core dumps are huge, disk pressure)│
│   OR: unlimited, but rotate cores like logs                    │
│                                                                 │
│ Modern context:                                                 │
│   Many modern systems use systemd-coredump                     │
│   Automatically captures core dumps to /var/lib/systemd/coredump/
│   Don't rely on ulimit -c anymore                              │
└─────────────────────────────────────────────────────────────────┘


3.2.3 INTERNAL WORKING: HOW KERNEL ENFORCES ULIMITS
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Every process has a resource limits table in the kernel (rlimit structure):

  struct rlimit {
    rlim_t rlim_cur;  // soft limit
    rlim_t rlim_max;  // hard limit
  };

When a syscall tries to consume a resource, the kernel checks:

  Example: open(path)
    → kernel_open_syscall()
    → Get current task's file_count
    → Check: current_task->rlim[RLIMIT_NOFILE].rlim_cur
    → if file_count >= rlim_cur:
        if HARD_LIMIT:
          return EMFILE error (errno 24)
        else:
          send SIGXFSZ to process (optional)
          allow but signal

The key insight: The kernel checks BEFORE the operation succeeds.
The limit is enforced in the syscall handler itself, not in userspace.


3.2.4 DEPENDENCIES AND INTERACTIONS
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Ulimits depend on:
  a) Being set before process starts (via login shell, PAM, or systemd)
  b) Being inherited by child processes
  c) Not being overridden by the process itself (hard limit)

Ulimits interact with:
  a) Cgroups: cgroups can impose STRICTER limits
  b) System-wide limits: kernel limits in /proc/sys/
  c) Swap space: affects how memory limits behave
  d) Systemd: applies limits to entire service

Example interaction: If you set ulimit -n 10000 but cgroups limit
open files to 1000, the cgroups limit wins (smaller).


3.2.5 FAILURE MODES
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

  WRONG: Set ulimit -n too low (e.g., 256)
    + Symptom: "too many open files" errors
    + Affects: Any high-concurrency workload
    + Debug: Check PostgreSQL logs, check current limits with ps -o
    
  WRONG: Set ulimit -u too low (e.g., 64)
    + Symptom: Connection pool can't accept new connections
    + Affects: All clients, not just some
    + Debug: ps aux | grep postgres | wc -l
    
  WRONG: Set ulimit -v (virtual memory) too strict
    + Symptom: Queries fail with "Out of memory" in valid scenarios
    + Affects: Large queries, complex joins
    + Debug: Hard to debug because error looks legitimate
    
  WRONG: Set ulimit -c 0 and then crash
    + Symptom: No core dump available for post-mortem analysis
    + Affects: Debugging production issues
    + Recovery: None, data is lost
    
  WRONG: Set ulimit as superuser, but systemd runs as non-root
    + Symptom: Limits don't apply (systemd's limits override)
    + Affects: Only applies if using systemd
    + Debug: Check systemd service file vs ulimit output


3.2.6 TRADE-OFFS
┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Using ulimits:
  + Prevents runaway processes from consuming all system resources
  + Enforced by kernel (can't be bypassed)
  + Simple to set
  - Process gets killed/fails without graceful shutdown
  - Hard limits are binary (no gradual enforcement)
  - Soft limits require handling signals in application code
  - Settings can be inherited from parent process (confusing)


Using cgroups instead of ulimits:
  + More flexible (can set per-service)
  + Can be changed without restarting process
  + Kernel enforces, can't be bypassed
  - More complex to understand
  - Newer (systemd 215+)
  - Requires understanding of cgroup hierarchies


RECOMMENDATION FOR MODERN SYSTEMS:
  Use systemd service directives instead of ulimit:
    - LimitNOFILE= (instead of ulimit -n)
    - LimitNPROC= (instead of ulimit -u)
    - MemoryMax= (instead of ulimit -v)
  
  These are clearer, more maintainable, and enforced via cgroups.


3.3 SYSTEMD SERVICE CONFIGURATION
================================================================================

3.3.1 PURPOSE
┈┈┈┈┈┈┈┈┈┈┈

Systemd service files are NOT just "how to start a process."
They define:
  1. Process lifecycle (start/stop/restart behavior)
  2. Dependency ordering (when to start relative to other services)
  3. Resource allocation (cgroups, ulimits, memory)
  4. Isolation boundaries (namespace isolation, device access)
  5. Recovery strategies (restart policy, watchdog)
  6. Privilege model (which user/group to run as)

A good systemd service file is a contract between the service and the system.


3.3.2 KEY DIRECTIVES FOR POSTGRESQL
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Let me break down what each directive does and why it matters:

┌─────────────────────────────────────────────────────────────────┐
│ [Unit] Section: Metadata and dependencies                       │
├─────────────────────────────────────────────────────────────────┤
│ Description=PostgreSQL Database Server                          │
│   - Human-readable description (shows in systemctl status)      │
│   - No functional impact, purely informational                  │
│                                                                 │
│ After=network.target                                            │
│   - Ordering: Don't start PostgreSQL until network is ready    │
│   - Why? PostgreSQL might need to resolve DNS or connect to    │
│     shared storage, which requires network                     │
│   - If you have replication over network, this is critical     │
│   - If PostgreSQL is local-only, less critical                 │
│                                                                 │
│ Before=any-service-that-depends-on-postgresql.target            │
│   - Ordering: Stop this service before dependent services      │
│   - Example: web app needs to stop after PostgreSQL stops      │
│   - Prevents data corruption from ungraceful shutdown          │
│   - Systemd uses this to create a correct shutdown order       │
│                                                                 │
│ Wants=postgresql-startup.target                                │
│   - Soft dependency: Start the target, but if it fails,        │
│     still start this service                                   │
│   - If you have custom startup tasks, use this                │
│   - Don't block PostgreSQL on them                            │
│                                                                 │
│ PartOf=postgresql.target                                       │
│   - When the target stops, stop this service too              │
│   - Allows grouping multiple PostgreSQL instances under target │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ [Service] Section: Runtime behavior                             │
├─────────────────────────────────────────────────────────────────┤
│ Type=notify                                                     │
│   - Service sends READY=1 notification when it's ready         │
│   - Systemd waits for this notification before considering     │
│     the service "started"                                      │
│   - Why? PostgreSQL startup takes time (recovery, warming caches)
│   - If Type=simple, systemd considers service "up" when        │
│     postmaster process starts, but DB not ready yet            │
│   - Type=notify ensures systemd knows DB is ready for queries  │
│   - PostgreSQL 9.6+ supports sd_notify()                       │
│                                                                 │
│ User=postgres                                                   │
│   - Systemd switches to this UID before exec'ing PostgreSQL   │
│   - Kernel enforces: no matter what code in PostgreSQL,        │
│     it runs as UID 26                                          │
│   - If missing: PostgreSQL runs as root (DANGEROUS!)           │
│                                                                 │
│ Group=postgres                                                  │
│   - Primary group for the process                              │
│   - File ownership/permissions checked against this group      │
│   - Usually same as User                                       │
│                                                                 │
│ PIDFile=/var/run/postgresql/postgresql.pid                     │
│   - Location of file containing PostgreSQL's PID              │
│   - Systemd monitors this for process death                   │
│   - Used for systemctl status and restart                     │
│                                                                 │
│ ExecStartPre=...                                                │
│   - Commands to run BEFORE starting the main process          │
│   - Example: Check data directory, create runtime directory   │
│   - If these fail, the service doesn't start                  │
│   - Exit code checked: 0 = success, non-zero = failure        │
│                                                                 │
│ ExecStart=/usr/lib/postgresql/...                             │
│   - The actual command to run                                  │
│   - Must be absolute path (no $PATH lookup)                   │
│   - Systemd replaces the systemd process with this executable │
│   - No shell processing (unless wrapped in /bin/sh -c)        │
│                                                                 │
│ ExecReload=...                                                  │
│   - Command to reload config without restarting               │
│   - Example: pg_ctl reload                                     │
│   - Systemd runs this on `systemctl reload postgresql`        │
│                                                                 │
│ ExecStop=/usr/lib/postgresql/...                              │
│   - Command to gracefully stop the service                    │
│   - Example: pg_ctl stop -D /var/lib/postgresql/main -w       │
│   - The -w flag waits for process to exit                     │
│   - Systemd uses this before sending SIGTERM/SIGKILL          │
│                                                                 │
│ TimeoutStartSec=300                                             │
│   - Max time allowed for service to start                      │
│   - If ExecStart doesn't finish in 300s, systemd gives up      │
│   - PostgreSQL recovery can take a long time on large DBs     │
│   - Set this higher if you have slow recovery                 │
│   - If too low: Service fails even though DB is starting      │
│                                                                 │
│ TimeoutStopSec=120                                              │
│   - Max time allowed for graceful shutdown                     │
│   - After this, systemd sends SIGKILL (force kill)            │
│   - PostgreSQL then performs crash recovery on next start     │
│   - Set to time needed for active txns to complete            │
│   - Too low = forced shutdowns = recovery overhead            │
│   - Too high = slow restarts                                   │
│                                                                 │
│ Restart=on-failure                                              │
│   - Automatically restart service if it exits unexpectedly    │
│   - on-failure: Only restart on non-zero exit                 │
│   - always: Restart even if it exited cleanly                 │
│   - no: Never restart                                          │
│   - What is "failure" for PostgreSQL? Exit code != 0          │
│   - Prevents silent downtime, but can mask issues             │
│                                                                 │
│ RestartSec=5s                                                   │
│   - Wait 5 seconds before restarting after failure            │
│   - Why? Give time for dependent resources to settle          │
│   - If restart loops too fast, systemd might give up          │
│   - Use RestartForceExitStatus= to fine-tune restart behavior │
│                                                                 │
│ StandardOutput=journal                                          │
│ StandardError=journal                                           │
│   - Send stdout/stderr to systemd journal                      │
│   - Alternative: file (write to log file)                      │
│   - Journal advantages: structured logging, automatic rotation │
│   - File advantages: simple, readable with tail -f             │
│   - Best practice: Use journal with -l / rsyslog integration  │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ Resource Limits Section: Cgroups v2 directives                 │
├─────────────────────────────────────────────────────────────────┤
│ LimitNOFILE=65536                                               │
│   - Max open file descriptors (replaces ulimit -n)            │
│   - Systemd enforces this via cgroups                         │
│   - Process cannot exceed this, even if it tries              │
│   - Why higher than ulimit defaults? See ulimit section       │
│   - Recommendation: max_connections * 8 + 1000                │
│                                                                 │
│ LimitNPROC=4096                                                │
│   - Max processes (replaces ulimit -u)                         │
│   - Each backend is a separate process                         │
│   - Recommendation: max_connections + 100                     │
│                                                                 │
│ MemoryMax=16G                                                   │
│   - Maximum memory cgroup can use (hard limit)                │
│   - Process OOM-killed if exceeds this                        │
│   - Set to: shared_buffers + (max_connections * work_mem)    │
│            + buffer for OS/shared libraries                    │
│   - Be generous, OOM kill is destructive                      │
│   - Alternative: MemoryLimit= (soft limit, allows overcommit) │
│                                                                 │
│ TasksMax=4096                                                   │
│   - Max threads + processes in cgroup                         │
│   - PostgreSQL is mostly single-threaded (per process)        │
│   - Set to: LimitNPROC= + safety margin                       │
└─────────────────────────────────────────────────────────────────┘


3.3.3 INTERNAL WORKING: SYSTEMD STARTUP SEQUENCE
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

When you run `systemctl start postgresql`:

  1. Systemd reads postgresql.service file
  2. Systemd resolves dependencies (After=, Wants=)
  3. Systemd waits for dependent services to be ready
  4. Systemd creates cgroup for the service
  5. Systemd applies cgroup limits (MemoryMax=, LimitNOFILE=, etc.)
  6. For each ExecStartPre= command:
     a. Systemd creates a new process
     b. Systemd sets UID/GID to User=/Group= from service file
     c. Systemd applies cgroup limits to this process
     d. Systemd exec's the command (no shell)
     e. Waits for it to exit
     f. If exit code != 0, start fails (unless IgnoreErrors=yes)
  7. For ExecStart= command:
     a. Systemd creates a new process (called the "main process")
     b. Systemd sets UID/GID = postgres:postgres
     c. Systemd applies cgroup limits
     d. Systemd exec's the PostgreSQL binary (no shell)
     e. Systemd replaces itself with the exec'd process (same PID)
  8. If Type=notify, systemd waits for sd_notify("READY=1")
     a. If not received within TimeoutStartSec, service marked failed
     b. Once received, systemd considers service "active"
  9. Systemd monitors the PIDFile for process exit
  10. If process exits and Restart=on-failure, systemd restarts


3.3.4 DEPENDENCIES AND INTERACTIONS
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Systemd services depend on:
  a) Systemd version (directives added over time)
  b) System configuration (/etc/security/limits.conf, PAM)
  c) cgroups kernel support (v1 vs v2)
  d) Binary availability (ExecStart path must exist)

Systemd interacts with:
  a) Other services (ordering, dependencies)
  b) Cgroups (resource allocation)
  c) Kernel (systemd-cgroups delegation)
  d) PAM (User= directive uses PAM login process)
  e) Namespace isolation (can restrict /dev, /proc, etc.)


3.3.5 FAILURE MODES
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

  WRONG: User=postgres not set
    + PostgreSQL runs as root
    + Any vulnerability becomes root exploit
    + System is fully compromised
  
  WRONG: ExecStart path doesn't exist
    + systemctl start postgresql fails immediately
    + Check: systemctl status postgresql | grep ExecStart
  
  WRONG: TimeoutStartSec too low
    + Service marked failed even though recovery is happening
    + Systemd gives up waiting
    + DB comes up but systemd thinks it failed
  
  WRONG: ExecStop doesn't wait for process
    + Systemd sends SIGKILL immediately after ExecStop returns
    + Crash recovery needed on next start
    + Use pg_ctl ... -w (wait flag)
  
  WRONG: Restart=always with infinite restart loop
    + Service crashes immediately on start (e.g., config issue)
    + Systemd keeps restarting every 5 seconds
    + Log spam, high CPU, confusing debugging
    + Use systemctl stop postgresql to stop the loop
  
  WRONG: MemoryMax set to < actual memory needed
    + Process gets OOM-killed randomly
    + PostgreSQL crashes, data appears corrupt
    + Only recoverable via crash recovery
  
  WRONG: LimitNOFILE set too low
    + Queries fail with "too many open files"
    + Intermittent failures under load
    + Users see random errors


3.3.6 TRADE-OFFS
┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Using systemd:
  + Standardized, declarative service management
  + Resource limits enforced by cgroups (stronger than ulimits)
  + Automatic restart/recovery
  + Journal integration
  + Dependency ordering handled automatically
  - Complexity (lots of options, easy to misconfigure)
  - Systemd not available on older systems (EL6, Ubuntu 14.04)
  - Debugging failures can be cryptic
  - Some options conflict with each other


SECTION 4: PRACTICAL REASONING
================================================================================

4.1 ESTIMATING VALUES: A FRAMEWORK
================================================================================

Instead of giving you numbers, here's how to REASON about the right values:

4.1.1 Estimating max_connections and LimitNOFILE
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Step 1: How many concurrent connections do you expect?
  - Peak hour traffic? (e.g., during report generation)
  - Connection pooling? (if using pgBouncer, many fewer backend connections)
  - Batch jobs? (number running in parallel)
  
  Example reasoning:
    "We have a web app. Peak traffic is 1000 HTTP requests/minute.
     Each request opens 1 connection. Request takes 100ms to process.
     Peak concurrent = (1000 req/min) * (100ms/1000ms/s) / (60 s/min)
                     ≈ 1.67 connections"
    
    This is typically FAR lower than max_connections default (100).

Step 2: Add background processes
  - Autovacuum workers: 1-3 (default 3)
  - Background writer: 1
  - Checkpoint process: 1
  - Logical replication launcher: 1 (if replication enabled)
  - Custom background workers: ? (your extensions)
  
  Total to add: ~10 processes minimum

Step 3: Add safety margin
  - Why? Peaks exceed estimates
  - Spikes from unexpected queries
  - Data warehouse queries that open many files
  
  Multiplier: 1.5x-2x

Formula:
  max_connections = (expected_concurrent * 2) + background_processes + margin
  LimitNOFILE = (max_connections * 8) + 1000

Example:
  Expected: 50 concurrent
  Background: 10
  Margin: 50
  max_connections = (50 * 2) + 10 + 50 = 160 (reasonable)
  LimitNOFILE = (160 * 8) + 1000 = 2280 (round up to 4096)


4.1.2 Estimating MemoryMax for cgroups
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Formula (conservative):
  MemoryMax = (shared_buffers) 
            + (max_connections * work_mem)
            + (max_worker_processes * work_mem)
            + 1GB (OS overhead)
            + 1GB (libraries and misc)

Example with moderate settings:
  shared_buffers = 4GB (typical: 25% of system RAM for 16GB machine)
  max_connections = 200
  work_mem = 64MB (per connection, for sorting/joining)
  max_worker_processes = 8
  
  MemoryMax = 4GB + (200 * 64MB) + (8 * 64MB) + 1GB + 1GB
            = 4GB + 12.8GB + 0.5GB + 1GB + 1GB
            = 19.3GB
  
  If system has 32GB, this fits with room to spare.

Important: This is a WORST-CASE estimate (all connections use full work_mem).
In practice, most connections use far less.
Setting MemoryMax too conservatively will cause OOM kills.
Setting it too loose defeats the purpose of limits.

RECOMMENDATION:
  MemoryMax = (shared_buffers) + (max_connections * avg_expected_work_mem) + 2GB
  
  Start conservative, monitor, adjust based on actual usage.


4.1.3 Estimating LimitNPROC
┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈

Simple formula:
  LimitNPROC = max_connections + 100

Why +100?
  - Background processes: ~10
  - Parallel query workers: up to max_parallel_workers (~8)
  - Safety margin: 80
  
This is rarely the bottleneck, but set it to be safe.


4.2 DECIDING BETWEEN ULIMITS VS CGROUPS
================================================================================

SCENARIO 1: Modern systemd system (18.04+, CentOS 7+, Debian 8+)
  CHOOSE: Cgroups (via systemd directives)
  REASON:
    - LimitNOFILE= is simpler and clearer than ulimit -n
    - Enforced by kernel, can't be bypassed
    - Can be changed without full restart
    - Survives process spawning
  
  Keep ulimits as backup/documentation, but primary enforcement is cgroups.


SCENARIO 2: Old system without proper systemd
  CHOOSE: Traditional ulimits (via /etc/security/limits.conf)
  REASON:
    - Systemd directives unavailable
    - Cgroups v1 might be too fragmented
    - Ulimits still better than nothing
  
  Set in /etc/security/limits.conf:
    postgres soft nofile 65536
    postgres hard nofile 65536


SCENARIO 3: Container/Kubernetes
  CHOOSE: Init system defaults + resource requests/limits
  REASON:
    - Kubernetes sets memory/CPU via container runtime
    - Container runtime enforces, not need ulimits
    - systemd might not exist in container
    - But still set ulimits for safety (defense in depth)


4.3 WHEN TO OVERRIDE LIMITS: RED FLAGS AND REASONING
================================================================================

RED FLAG 1: "I need more than LimitNOFILE=65536"
  Question: Why?
    - Are you opening files directly (unusual for PostgreSQL)?
    - Do you have extreme connection count (>1000s)?
    - Is your estimate of FDs per connection correct?
  
  Action: Before increasing, profile actual FD usage:
    lsof -p <postgres_pid> | wc -l
  
  If actually high, increase incrementally (65536 → 100000 → 150000).


RED FLAG 2: "MemoryMax keeps killing queries"
  Question: Why?
    - Is work_mem set per the MemoryMax estimate?
    - Are you running large analytical queries?
    - Is system running other memory hogs?
  
  Action: Measure actual memory usage:
    ps aux | grep postgres (RSS column)
    systemd-cgtop (cgroup memory usage)
  
  Adjust MemoryMax to actual + 50% buffer.


RED FLAG 3: "I can't increase LimitNOFILE beyond system maximum"
  Question: What's the system max?
    /proc/sys/fs/file-max (global max)
  
  If hitting this, either:
    a) Increase /proc/sys/fs/file-max
    b) Reduce max_connections
    c) Add connection pooling


4.4 DECISION TREE: WHAT TO CONFIGURE
================================================================================

Question 1: Are you running on systemd?
  YES → Use systemd service directives (LimitNOFILE=, etc.)
       Backup with /etc/security/limits.conf for documentation
  NO → Use /etc/security/limits.conf (traditional method)

Question 2: Do you know your connection load?
  YES → Estimate based on actual traffic (see 4.1.1)
  NO → Start conservative (max_connections=100, LimitNOFILE=4096)
       Monitor and adjust after 1 week of production

Question 3: Are you running large analytical queries?
  YES → Set MemoryMax higher (see 4.1.2)
       Monitor with systemd-cgtop
  NO → Set MemoryMax to shared_buffers * 1.5

Question 4: Do you need memory locking (for ultra-low latency)?
  YES → Set LimitMEMLOCK=unlimited (rare)
  NO → Leave at default (usually 64K)

Question 5: Do you have monitoring?
  YES → Set Restart=on-failure (auto-recovery)
       Set up alerts for restart loops
  NO → Set Restart=no (manual intervention forced, safer)


SECTION 5: PRODUCTION SCENARIOS
================================================================================

5.1 SCALING TO LARGE NUMBERS OF CONNECTIONS
================================================================================

SCENARIO: "We're growing from 10 connections to 1000 connections"

What changes at each scale:

At 10-100 connections:
  - Default PostgreSQL settings work
  - LimitNOFILE=4096 is plenty
  - LimitNPROC=512 is plenty
  - Ulimits are not usually a bottleneck

At 100-500 connections:
  - start hitting default ulimits on some systems
  - Consider connection pooling to avoid process explosion
  - LimitNOFILE=16384 recommended
  - Profile FD usage to confirm

At 500-2000 connections:
  - MUST use connection pooling (pgBouncer, pgpool)
  - PostgreSQL backend processes ≤ 200, clients connect to pool
  - LimitNOFILE=65536
  - System file-max might need increasing
  - Kernel tuning for TCP connections becomes important

At 2000+ connections:
  - Multiple pgBouncer instances with load balancing
  - PostgreSQL stays at reasonable backend count
  - Focus shifts from PostgreSQL limits to:
    - Network stack tuning
    - Connection pool tuning
    - Clustering/sharding


QUESTION: At what point does connection pooling become necessary?
  ANSWER: When the number of backend processes × expected memory per
          backend approaches available system RAM.
          
          Typical: 200+ simultaneous connections, start pooling.


5.2 MEMORY PRESSURE AND OOM BEHAVIOR
================================================================================

SCENARIO: "PostgreSQL keeps getting OOM-killed randomly"

Diagnosis:

Step 1: Is it actually OOM?
  Check dmesg:
    grep -i oom /var/log/kern.log
    grep -i killed /var/log/kern.log
  
  Look for: "Out of memory: Kill process postgres ... score 812"
  This confirms OOM killer, not application error.

Step 2: Why is it happening?
  a) MemoryMax is too low?
     systemd-cgtop (check memory.max vs memory.current)
  
  b) work_mem is too high?
     Each connection doing a sort/join/hash-agg uses work_mem
     If work_mem=256MB and you have 100 connections, that's 25GB just
     for potential work_mem allocations.
  
  c) Other processes consuming memory?
     free -h (check available memory)
     ps aux --sort -%mem (top memory consumers)
  
  d) Memory leak in PostgreSQL?
     Unlikely if using stable version, but check PostgreSQL logs
     for MEMORY messages

Step 3: What to fix?
  Option A: Increase MemoryMax (if system has more RAM available)
  Option B: Reduce work_mem (slightly slower queries, but stable)
  Option C: Reduce max_connections or enable connection pooling
  Option D: Investigate why specific query uses so much memory


Preventive measures:

  Set MemoryHigh before MemoryMax:
    MemoryHigh=15G (soft limit, starts reclaim)
    MemoryMax=16G (hard limit, OOM kill)
  
  The soft limit triggers memory pressure, allowing the kernel to
  reclaim memory gracefully before hard limit.


5.3 FAILOVER AND RESTARTS
================================================================================

SCENARIO: "We're adding WAL replication and need safe failover"

Considerations:

Question 1: How long can your database be down?
  - RTO (Recovery Time Objective): How fast must it be back?
  - RPO (Recovery Point Objective): How much data loss is acceptable?
  
These affect:
  - TimeoutStopSec (grace period for clean shutdown)
  - Restart=on-failure (auto-recovery vs manual intervention)
  - ExecStop=pg_ctl stop vs SIGKILL

Question 2: What causes PostgreSQL restarts in your environment?
  - Kernel updates (planned downtime)
  - Application bugs (PostgreSQL crashes)
  - Resource exhaustion (OOM, disk full)
  
For each:
  - Planned: Use ExecStop with long TimeoutStopSec
  - Crashes: Use Restart=on-failure with RestartSec=10s
  - Resource: Set up monitoring to prevent, but have recovery plan


Recommended systemd settings for production:

  [Service]
  Type=notify
  User=postgres
  Group=postgres
  
  ExecStartPre=/usr/lib/postgresql/check-datadir
  ExecStart=/usr/lib/postgresql/start-postgres
  ExecStop=/usr/lib/postgresql/stop-postgres
  ExecStopPost=/usr/lib/postgresql/cleanup-runtime
  
  # Graceful shutdown (5 minutes)
  TimeoutStopSec=300
  
  # Allow 5 minutes for recovery/startup
  TimeoutStartSec=300
  
  # Auto-restart only on failure, not success
  Restart=on-failure
  RestartSec=10s
  
  # Watchdog: if PostgreSQL hangs, systemd kills it
  WatchdogSec=0 (disabled by default, enable if using systemd watchdog)


5.4 MULTI-INSTANCE DEPLOYMENTS
================================================================================

SCENARIO: "We're running multiple PostgreSQL versions on same server"

Resource allocation becomes critical:

Example: PostgreSQL 12 and PostgreSQL 14 on same 32GB machine

Instance 1 (PostgreSQL 12):
  max_connections = 200
  shared_buffers = 4GB
  work_mem = 32MB
  Estimated MemoryMax = 4GB + (200 * 32MB) + 2GB = 10GB
  LimitNOFILE = 65536
  LimitNPROC = 512

Instance 2 (PostgreSQL 14):
  max_connections = 200
  shared_buffers = 6GB (can use more due to better efficiency)
  work_mem = 32MB
  Estimated MemoryMax = 6GB + (200 * 32MB) + 2GB = 12GB
  LimitNOFILE = 65536
  LimitNPROC = 512

Total memory allocation: 10GB + 12GB = 22GB (leaves 10GB for OS/other)

QUESTION: What happens if both instances try to use their full MemoryMax?
  ANSWER: Kernel memory overcommit might kick in, or one gets OOM-killed.
          To prevent: Set MemoryMax for each instance such that their sum
          is ≤ system RAM with 20% buffer for OS.


5.5 KERNEL PARAMETER TUNING FOR LARGE WORKLOADS
================================================================================

As PostgreSQL scales, kernel parameters matter:

/proc/sys/net/ipv4/tcp_max_syn_backlog
  - SYN queue for new connections
  - If too small: connection refused errors
  - Recommendation: 4096+ for high-traffic servers

/proc/sys/net/core/somaxconn
  - Max queue of connections waiting to be accepted
  - If too small: connections dropped
  - Recommendation: 4096+ for high-traffic servers

/proc/sys/net/ipv4/tcp_tw_reuse
  - Reuse TIME_WAIT sockets (for connection pooling)
  - Recommendation: 1 (enable for pooling setups)

/proc/sys/net/ipv4/tcp_fin_timeout
  - How long to keep connections in TIME_WAIT
  - Recommendation: 30-60s (reduce if connection pooling)

/proc/sys/fs/file-max
  - Global file descriptor limit
  - Recommendation: 1M+ for servers with many connections

These are SYSTEM-WIDE limits, not per-process.
They affect whether the kernel can even accept connections.


SECTION 6: ANTI-PATTERNS
================================================================================

6.1 ANTI-PATTERN: "Just set everything to unlimited"
================================================================================

I've seen this in production:

  [Service]
  LimitNOFILE=infinity
  LimitNPROC=infinity
  MemoryMax=infinity
  LimitMEMLOCK=infinity

PROBLEM:
  If PostgreSQL has a bug that leaks file descriptors, it will consume
  every available FD on the system, causing ALL processes to fail.
  
  Example: Query planner bug opens 1000x the expected files.
  - With limits: Query fails, logs error, others continue
  - Without limits: Entire system becomes unable to open files
                    SSH stops working, systemd can't run services
                    You can't even recover!

This is exactly what limits exist to prevent.

PRINCIPLE: Limits should be high enough for normal operation,
but low enough to catch bugs before they destroy the system.


6.2 ANTI-PATTERN: "ulimit will protect me from runaway queries"
================================================================================

MISCONCEPTION: Setting ulimit -v will prevent memory explosion queries.

REALITY:
  A query that allocates 100MB per second will hit the limit in seconds.
  When it does, the kernel sends SIGKILL (hard limit).
  PostgreSQL crashes, no graceful cleanup, crash recovery needed.

BETTER APPROACH:
  - Set query_cost_limit (PostgreSQL 13+) to abort runaway queries
  - Set statement_timeout to kill hanging queries
  - Monitor memory usage and set MemoryHigh before MemoryMax
  - Ulimits are a LAST RESORT, not primary control


6.3 ANTI-PATTERN: "Let systemd auto-restart PostgreSQL constantly"
================================================================================

CONFIGURATION:
  Restart=always (not just on-failure)
  RestartSec=1s (restart immediately)

WHAT HAPPENS:
  PostgreSQL crashes (e.g., stack overflow in complex query)
  Systemd restarts it immediately
  Same query comes in → same crash → restart loop
  
  Result: High CPU, log spam, system becomes unresponsive

BETTER APPROACH:
  - Restart=on-failure (only restart on crashes)
  - RestartSec=10s (wait before restarting)
  - Set up monitoring that ALERTS on restarts
  - Investigate root cause (don't just auto-recover)
  - Implement RestartForceExitStatus for nuanced behavior


6.4 ANTI-PATTERN: "I'll set TimeoutStopSec=0 for instant shutdown"
================================================================================

CONFIGURATION:
  ExecStop=/usr/lib/postgresql/stop-postgres
  TimeoutStopSec=0 (skip waiting, go straight to SIGKILL)

WHAT HAPPENS:
  pg_ctl stop called
  Before it completes, systemd sends SIGKILL
  Crash recovery on next start
  Repeated: performance degrades, WAL bloat

BETTER APPROACH:
  TimeoutStopSec=300 (5 minutes is reasonable)
  ExecStop=/usr/lib/postgresql/stop-postgres (waits for clean exit)
  
  pg_ctl stop waits for active transactions
  If a txn takes too long, SIGTERM sent after timeout
  If still running, SIGKILL sent
  Clean shutdown in 99% of cases


6.5 ANTI-PATTERN: "We'll use swap as if it's RAM"
================================================================================

SCENARIO:
  System has 16GB RAM, 32GB swap
  Set MemoryMax=32GB (total swap + RAM)
  Think: "Effectively, we have 48GB"

WHAT ACTUALLY HAPPENS:
  Database works fine until RAM is exhausted
  Kernel starts swapping memory to disk
  Disk I/O explodes (100x slower than RAM)
  Queries that took 100ms now take 10 seconds
  Users see timeouts, performance plummets
  Swap thrashing causes further slowdown

This is a DEATH SPIRAL.

BETTER APPROACH:
  Set MemoryMax = actual available RAM - margin
  Use MemoryHigh before MemoryMax to trigger gradual memory reclaim
  If you need more memory, buy more RAM or reduce load
  Swap is for emergency, not expected operations


SECTION 7: DECISION FRAMEWORK
================================================================================

7.1 HOW TO THINK ABOUT CONFIGURATION
================================================================================

Step 1: GATHER DATA
  - What is the application?
  - What workload? (OLTP, analytics, mixed)
  - How many users/connections?
  - What is the hardware? (CPU, RAM, storage)
  - What is the version of PostgreSQL?

Step 2: ESTIMATE RESOURCE NEEDS
  Use the frameworks from Section 4.1
  - max_connections based on traffic
  - shared_buffers based on RAM available
  - work_mem based on query types
  - MemoryMax based on all above

Step 3: SELECT ENFORCEMENT MECHANISM
  - Modern systemd? → Use LimitNOFILE=, MemoryMax=
  - Old system? → Use /etc/security/limits.conf

Step 4: SET LIMITS CONSERVATIVELY
  - Start with limits slightly above estimates
  - NEVER set to "unlimited" without reason
  - Leave room for peaks and unexpected queries

Step 5: DEPLOY AND MONITOR
  - Watch systemctl status postgresql
  - Monitor with systemd-cgtop
  - Check for OOM kills: grep oom /var/log/kern.log
  - Check for limit hits: check PostgreSQL logs

Step 6: ADJUST BASED ON METRICS
  - Too many "too many open files"? Increase LimitNOFILE
  - OOM kills? Increase MemoryMax or reduce work_mem
  - Frequent restarts? Increase TimeoutStartSec or fix root cause

Step 7: DOCUMENT
  - Why each limit was set to its value
  - Expected memory/connection usage
  - Limits are a contract between you and the system


7.2 SIGNALS AND METRICS TO MONITOR
================================================================================

METRIC: Current open files per PostgreSQL process
  Tool: lsof -p <pid> | wc -l
  Signal: If near LimitNOFILE, you're running out
  Action: Increase limit or reduce max_connections

METRIC: Process count per PostgreSQL instance
  Tool: ps aux | grep postgres | wc -l
  Signal: If near LimitNPROC, connection pooling needed
  Action: Enable pgBouncer or increase limit

METRIC: Memory usage
  Tool: systemd-cgtop (cgroup view) or ps aux (process view)
  Signal: If memory.current near memory.max, pressure exists
  Action: Increase MemoryMax, reduce work_mem, or reduce load

METRIC: Restart frequency
  Tool: systemctl status postgresql (shows restart count)
  Signal: If Restart= count increasing, crashes happening
  Action: Check logs, find root cause, fix it

METRIC: Timeout hit count
  Tool: journalctl -u postgresql (search for timeout messages)
  Signal: If startup/stop timeouts exceeded, performance issue exists
  Action: Increase TimeoutStartSec/StopSec or optimize startup

METRIC: File descriptor limit hits
  Tool: grep "too many open files" /var/log/postgresql/*.log
  Signal: Limit exceeded, errors occurring
  Action: Increase LimitNOFILE

METRIC: Memory limit hits
  Tool: grep oom /var/log/kern.log or journalctl -xe
  Signal: Process got OOM-killed, lost work
  Action: Increase MemoryMax or reduce load


7.3 BEFORE/AFTER ANALYSIS
================================================================================

When you make a configuration change:

BEFORE:
  1. Measure current state (metrics above)
  2. Document current settings
  3. Note any issues or complaints

CHANGE:
  1. Update systemd file (or limits.conf)
  2. systemctl daemon-reload (reload systemd config)
  3. systemctl restart postgresql
  4. Verify service is up: systemctl status postgresql

AFTER:
  1. Run same measurements (use same tools)
  2. Compare before/after
  3. Did the change fix the issue?
  4. Did it introduce new issues?
  5. Document the change and result


Example workflow:

Before: LimitNOFILE=4096
  lsof -p $(pgrep -f postgres | head -1) | wc -l
  # Output: 412 (using 412 of 4096 FDs)
  No errors, but want headroom

Change:
  Edit /etc/systemd/system/postgresql.service
  LimitNOFILE=65536
  systemctl daemon-reload
  systemctl restart postgresql

After:
  lsof -p $(pgrep -f postgres | head -1) | wc -l
  # Output: 412 (still using 412 FDs, limit change not needed)
  # But now have headroom for growth


SECTION 8: COMMON MISTAKES
================================================================================

MISTAKE 1: Not checking current limits before troubleshooting
  
  User reports: "Getting 'too many open files' errors"
  
  Wrong approach:
    - Immediately increase LimitNOFILE in systemd file
    - Restart PostgreSQL
    - Hope it works
  
  Right approach:
    - Check current limit: systemctl show -p LimitNOFILE postgresql
    - Check actual FDs used: lsof -p <pid> | wc -l
    - Compare: Are we actually hitting the limit?
    - If yes, increase; if no, investigate why errors occur


MISTAKE 2: Confusing soft and hard limits

  Soft limit: process receives signal, but can often continue
  Hard limit: kernel refuses the operation
  
  Setting only soft limit:
    LimitNOFILE=65536 (systemd)
    This sets BOTH soft and hard to 65536 by default
    
  To set them separately (rare):
    Use PAM or init scripts, systemd doesn't differentiate


MISTAKE 3: Not accounting for parent process limits

  Postgres postmaster started by systemd with LimitNOFILE=65536
  Postgres starts with those limits
  Postgres can't exceed them, even if it wanted to
  
  But if you SSH to the server as postgres user and run a shell:
    ulimit -n (shows system default, maybe 4096)
    Not the same as systemd limits!


MISTAKE 4: Setting memory limits incorrectly

  Wrong: MemoryMax=8GB for a system with 32GB RAM
    Seems conservative, but:
    shared_buffers=2GB + work_mem=64MB*200 + overhead
    = 2GB + 12.8GB + 2GB = 16.8GB needed
    Process gets OOM-killed at 8GB usage
  
  Right: Estimate actual memory needs, add 50%, check against system RAM


MISTAKE 5: Not testing restart behavior

  Set Restart=on-failure, then crash PostgreSQL intentionally
  Does it restart? Does service become healthy?
  
  Test before relying on auto-restart in production


MISTAKE 6: Ignoring systemd journal logs

  systemctl status postgresql shows last status
  journalctl -u postgresql shows full history
  
  Many clues in the logs:
    - Why it failed to start
    - Why it exited
    - Resource limits hit
    
  Check logs FIRST when troubleshooting
