No solutions are provided anywhere in this document, by design. Every item is
a problem, a drill, or a scenario for YOU to solve, instrument, break, and
fix. That repetition is the point.

--------------------------------------------------------------------------------
HOW THIS DOCUMENT IS BUILT
--------------------------------------------------------------------------------
The original spec calls for 900+ assignments, 100+ incident simulations, and
30+ end-to-end projects across 6 career phases. Generating all of that in one
pass would force a choice between truncating it or padding it with repetitive
filler — neither serves you. So this is being built phase-by-phase, in full
depth, starting now with PHASE 1: FOUNDATION.

This file currently contains:
  - The full 6-phase roadmap and target/delivered tracker (below)
  - The assignment structure template
  - PHASE 1 — FOUNDATION: 63 full assignments (3 per domain x 21 domains)
  - A daily/weekly/monthly drill bank (muscle-memory layer)
  - 15 foundation-level incident simulations
  - 2 foundation-tier end-to-end projects

To get PHASE 2 (Professional DBA) appended to this same file in the same
format, just say so. Each phase will be appended in turn — 2, 3, 4, 5, 6 —
until the full target counts in the tracker below are met.

--------------------------------------------------------------------------------
LEARNING ROADMAP — 6 PHASES
--------------------------------------------------------------------------------
PHASE 1 — FOUNDATION          Correct usage of fundamentals under no pressure.
PHASE 2 — PROFESSIONAL DBA    Independent ownership of routine production work.
PHASE 3 — SENIOR DBA          Designs solutions; handles ambiguous incidents.
PHASE 4 — LEAD DBA            Owns architecture decisions across a fleet.
PHASE 5 — PRINCIPAL DBA       Sets standards; handles novel, cross-system failure.
PHASE 6 — ENTERPRISE ARCHITECT  Designs platforms; plans multi-year strategy.

Difficulty and ambiguity increase every phase. Time pressure increases every
phase. Solution scaffolding (hints, given configs, known-good baselines)
decreases every phase. By Phase 5-6, assignments stop telling you what's
broken — only what was observed.

[F1-PGA-01] Cluster Initialization and Directory Layout Audit
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Entry
Estimated Completion Time: 1-2 hours

Objective: Build correct, repeatable instincts for what a healthy PostgreSQL
data directory looks like and why each piece exists.

Business Scenario: You've inherited a server with PostgreSQL already running
and no documentation. Before you touch anything, you need to know what you're
looking at.

Technical Requirements:
- A running PostgreSQL instance (any supported version 13+)
- Shell access with permission to read PGDATA

Environment Setup:
- Install PostgreSQL on a throwaway VM or container
- Initialize a cluster with initdb using non-default data and WAL locations

Tasks:
1. Produce a written map of every top-level item in PGDATA and its purpose
2. Identify where WAL currently lives and confirm it is (or isn't) on a
   separate filesystem/mount
3. Locate and read postgresql.conf, postgresql.auto.conf, and pg_hba.conf;
   note which settings are active and from which file they're sourced
4. Determine the PostgreSQL version, cluster encoding, and locale without
   connecting to the database (filesystem/binary inspection only)
5. Identify the current WAL mode and checkpoint configuration

Deliverables:
- A one-page "cluster fact sheet" documenting findings from tasks 1-5

Validation Criteria:
- Every claim in the fact sheet is independently verifiable by another
  engineer using only the commands you documented

Success Metrics:
- Fact sheet completed with zero reliance on guesswork or assumption

Expected Learning Outcomes:
- Instant orientation on any unfamiliar PostgreSQL host within minutes

--------------------------------------------------------------------------------
[F1-PGA-02] Role and Privilege Baseline Setup
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Core
Estimated Completion Time: 2-3 hours

Objective: Establish a correct least-privilege role hierarchy from scratch.

Business Scenario: A new application is being onboarded. Security review
requires that the app cannot use superuser or owner-level access, and that
read-only reporting users cannot write.

Technical Requirements:
- A database with at least 3 schemas and 5 tables of sample data
- No existing roles besides the default superuser

Environment Setup:
- Create a fresh database; populate with sample schema/tables

Tasks:
1. Design a role hierarchy: an owner role, an app read-write role, a
   reporting read-only role, and a migrations role
2. Implement the hierarchy using GRANT/REVOKE and role membership (not
   superuser shortcuts)
3. Set default privileges so future tables automatically inherit the
   intended grants
4. Verify each role can only do what it should by attempting prohibited
   actions and confirming they fail
5. Document the hierarchy as a diagram or table

Deliverables:
- SQL script implementing the roles
- A test log showing each prohibited action failing as expected

Validation Criteria:
- Reporting role cannot INSERT/UPDATE/DELETE on any table
- App role cannot ALTER schema objects or grant privileges to others
- New tables created later automatically pick up correct default grants

Success Metrics:
- Zero successful privilege escalations during adversarial testing

Expected Learning Outcomes:
- Fluency in PostgreSQL's privilege model without reaching for superuser

--------------------------------------------------------------------------------
[F1-PGA-03] Routine Maintenance Schedule Implementation
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Capstone
Estimated Completion Time: 2-4 hours

Objective: Build a defensible, observable autovacuum/maintenance baseline.

Business Scenario: An inherited database has autovacuum left at out-of-the-box
defaults on tables receiving heavy churn. You're asked to propose and
implement a maintenance baseline before bloat becomes a problem.

Technical Requirements:
- A database with at least one high-churn table (simulate with a script
  that does continuous INSERT/UPDATE/DELETE)
- Ability to query pg_stat_user_tables and pg_stat_activity

Environment Setup:
- Write a small load generator that updates/deletes rows continuously
  against one table for the duration of the exercise

Tasks:
1. Observe default autovacuum behavior on the churning table over time
2. Identify whether autovacuum is keeping pace using dead tuple counts
   and last_autovacuum timestamps
3. Tune per-table autovacuum settings (thresholds/scale factors, cost
   limits) for this specific table's workload
4. Validate the new settings produce measurably tighter dead-tuple control
5. Document the reasoning for each parameter change

Deliverables:
- Before/after dead-tuple and vacuum-frequency measurements
- A written rationale for each setting changed

Validation Criteria:
- Dead tuple ratio on the target table stabilizes rather than growing
  unbounded over a sustained test run

Success Metrics:
- Measurable reduction in table/index bloat growth rate vs. the
  default-configuration baseline

Expected Learning Outcomes:
- Ability to read vacuum health from stats views and tune with intent
  rather than copy-pasted values

[F1-PGP-01] Baseline Configuration Tuning From Defaults
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Entry
Estimated Completion Time: 1-2 hours

Objective: Move a default-configured instance to a sane baseline for its
hardware, with documented reasoning per parameter.

Business Scenario: A new database server was provisioned by infrastructure
and handed to you with stock postgresql.conf. It needs a real baseline
before any application traffic hits it.

Technical Requirements:
- A PostgreSQL instance with default/out-of-the-box configuration
- Known hardware specs (CPU cores, RAM, storage type)

Environment Setup:
- Provision or simulate a VM with specific, known CPU/RAM/disk specs

Tasks:
1. Calculate appropriate shared_buffers, effective_cache_size, work_mem,
   and maintenance_work_mem for the given hardware
2. Set max_connections based on expected workload, not arbitrary defaults
3. Configure WAL-related settings (wal_buffers, min/max_wal_size,
   checkpoint_completion_target) appropriately for the storage type
4. Apply changes and restart/reload as appropriate per parameter
5. Document why each value was chosen, tied to the actual hardware specs

Deliverables:
- Annotated postgresql.conf diff with rationale comments

Validation Criteria:
- Every changed value is traceable to a specific hardware constraint or
  workload assumption, not a generic "best practice number"

Success Metrics:
- Configuration survives a peer review challenge of "why this number?"
  for every changed parameter

Expected Learning Outcomes:
- Tuning from first principles instead of memorized magic numbers

--------------------------------------------------------------------------------
[F1-PGP-02] shared_buffers / work_mem Sizing Exercise
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Core
Estimated Completion Time: 2-3 hours

Objective: Directly observe the performance impact of memory parameter
sizing instead of trusting rules of thumb blindly.

Business Scenario: A report query is slow and someone on the team suggests
"just increase work_mem." You're asked to prove or disprove that this is
the right lever before changing production.

Technical Requirements:
- A dataset large enough to force sorts/hashes to spill to disk at low
  work_mem settings
- A reproducible query that sorts or hash-joins a large result set

Environment Setup:
- Load a table with several million rows of synthetic data

Tasks:
1. Run the target query with EXPLAIN (ANALYZE, BUFFERS) at a low work_mem
   and capture the plan, noting any disk-based sort/hash operations
2. Incrementally raise work_mem and re-run, recording plan and timing
   changes at each step
3. Identify the point of diminishing returns
4. Separately test shared_buffers changes in isolation to distinguish its
   effect from work_mem's effect
5. Summarize which parameter actually mattered for this workload and why

Deliverables:
- A table of work_mem values vs. query time and disk-spill behavior

Validation Criteria:
- Conclusions are backed by EXPLAIN ANALYZE evidence, not assumption

Success Metrics:
- Correctly identifies the point past which raising work_mem stops helping

Expected Learning Outcomes:
- Evidence-based tuning habit; resistance to cargo-cult configuration advice

--------------------------------------------------------------------------------
[F1-PGP-03] pg_stat_statements-Based Hotspot Identification
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Capstone
Estimated Completion Time: 2-3 hours

Objective: Use pg_stat_statements to find the actual top resource
consumers on an instance, not the ones that "feel" slow.

Business Scenario: The application team insists "everything is slow," which
isn't actionable. You're asked to produce a ranked, evidence-backed list of
what to actually fix first.

Technical Requirements:
- pg_stat_statements extension enabled
- A workload generator running a mix of queries with varying cost

Environment Setup:
- Enable pg_stat_statements; run a mixed synthetic workload for 15+ minutes

Tasks:
1. Query pg_stat_statements ranked by total_exec_time and separately by
   calls, and explain why these rankings differ
2. Identify the single query contributing the most cumulative load
3. Identify a query that is individually slow but called rarely, and
   explain why it may not be a priority despite its per-call cost
4. Reset pg_stat_statements and confirm counters return to a clean state
5. Produce a prioritized remediation list with reasoning per item

Deliverables:
- Ranked hotspot report with both per-call and cumulative-cost views

Validation Criteria:
- Prioritization correctly distinguishes "high total cost" from
  "high per-call cost" and justifies the ranking

Success Metrics:
- Report would change at least one wrong assumption a non-data-driven
  reviewer might make about "what's slow"

Expected Learning Outcomes:
- Default instinct to measure before optimizing

[F1-PGI-01] MVCC and Tuple Visibility Exploration
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Entry
Estimated Completion Time: 2 hours

Objective: Build a concrete, observable mental model of how MVCC actually
stores and hides row versions, rather than a textbook abstraction of it.

Business Scenario: A developer asks "why does my UPDATE make the table
bigger instead of changing the row in place?" You need an answer backed by
direct observation, not a copied explanation.

Technical Requirements:
- A test table with a handful of rows
- Ability to inspect system columns (xmin, xmax, ctid)

Environment Setup:
- Create a small table; enable viewing of hidden system columns

Tasks:
1. Insert a row and record its xmin, xmax, and ctid
2. Update the row in one session while observing pg_stat_activity and
   the row's old and new ctid/xmin/xmax from another session
3. Open a transaction in one session, update a row, and from a second
   session observe what that transaction sees vs. what a committed
   reader sees
4. Run VACUUM and observe what happens to the old tuple version
5. Summarize, in your own words, what "row versioning" actually means at
   the storage level

Deliverables:
- A timeline diagram or table showing tuple states across the transaction

Validation Criteria:
- Explanation correctly accounts for visibility differences between
  concurrent sessions

Success Metrics:
- Can correctly predict tuple visibility outcomes for a new scenario not
  in this assignment

Expected Learning Outcomes:
- Intuition for why bloat, vacuum, and long transactions are all the same
  underlying phenomenon

--------------------------------------------------------------------------------
[F1-PGI-02] WAL Record Walkthrough with pg_waldump
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Core
Estimated Completion Time: 2-3 hours

Objective: Connect SQL-level actions to the physical WAL records they
generate.

Business Scenario: You need to explain to a junior engineer, with evidence,
why "just turning off WAL" is not an option, and what's actually inside it.

Technical Requirements:
- pg_waldump (ships with PostgreSQL)
- A test cluster where you can identify current WAL position

Environment Setup:
- Fresh test database; note the current WAL LSN before each task

Tasks:
1. Perform a single INSERT, note the LSN before and after, and use
   pg_waldump to inspect the generated WAL record(s)
2. Repeat for an UPDATE and a DELETE, comparing record types/sizes
3. Perform a transaction with multiple statements and identify the
   commit record in the WAL stream
4. Force a checkpoint and locate the checkpoint record
5. Summarize the relationship between WAL volume and write-heavy workloads

Deliverables:
- Annotated pg_waldump output for each operation type

Validation Criteria:
- Correctly identifies record types (heap insert/update/delete, commit,
  checkpoint) without relying on guesswork

Success Metrics:
- Can predict, before running it, roughly what record types a given SQL
  statement will produce

Expected Learning Outcomes:
- WAL stops being a black box; replication and PITR become mechanically
  obvious rather than memorized

--------------------------------------------------------------------------------
[F1-PGI-03] Catalog Tables Deep Dive (pg_class, pg_stat_*, pg_locks)
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Capstone
Estimated Completion Time: 2-3 hours

Objective: Build fluency querying the system catalogs directly instead of
relying on third-party GUIs or memorized one-liners.

Business Scenario: Monitoring tooling is down during an incident. You need
to answer "what is running, what is it blocking, and how big is it" using
nothing but psql and catalog knowledge.

Technical Requirements:
- A workload generating some lock contention (simulate with overlapping
  transactions)

Environment Setup:
- Two or more sessions intentionally contending for the same rows

Tasks:
1. From pg_class and pg_stat_user_tables, determine table and index sizes
   without using a third-party tool
2. From pg_stat_activity, identify currently running queries and their
   wait states
3. From pg_locks, identify which session is blocking which, joining
   against pg_stat_activity for readable output
4. Write a single query that surfaces "who is blocking whom" in
   human-readable form
5. Document the catalog relationships you relied on

Deliverables:
- A working "blocking sessions" query you wrote yourself
- A short catalog relationship diagram

Validation Criteria:
- The blocking-sessions query correctly identifies blocker/blocked pairs
  in a live contention scenario

Success Metrics:
- Can answer "what's blocking what" in under 2 minutes using only psql

Expected Learning Outcomes:
- Tool-independence during incidents when dashboards aren't available

[F1-QO-01] EXPLAIN / EXPLAIN ANALYZE Fundamentals
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Entry
Estimated Completion Time: 1-2 hours

Objective: Read a query plan accurately, including the difference between
estimated and actual costs.

Business Scenario: A teammate pastes you a query plan and asks "is this
fine?" You need to be able to answer correctly from the plan alone.

Technical Requirements:
- A moderately sized table (100k+ rows) with at least one index

Environment Setup:
- Load sample data; ensure statistics are up to date (ANALYZE)

Tasks:
1. Run EXPLAIN (without ANALYZE) on a simple filtered query and explain
   each line of the plan in your own words
2. Run EXPLAIN ANALYZE on the same query and identify where estimated
   rows diverge from actual rows
3. Deliberately cause a sequential scan (disable an index or query a
   non-indexed column) and compare the plan
4. Identify which plan node is the most expensive by execution time, not
   by visual position in the plan
5. Explain what "Buffers" output adds that timing alone does not

Deliverables:
- Three annotated query plans with your own line-by-line explanation

Validation Criteria:
- Annotations correctly distinguish planning estimates from runtime
  reality

Success Metrics:
- Can identify the most expensive node in an unfamiliar plan within 60
  seconds

Expected Learning Outcomes:
- Reading plans becomes routine, not intimidating

--------------------------------------------------------------------------------
[F1-QO-02] Index Selection Exercise (B-tree vs. Others)
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Core
Estimated Completion Time: 2-3 hours

Objective: Choose an index type based on the query pattern, not habit.

Business Scenario: A table needs indexing but the access patterns vary —
equality lookups, range queries, and a full-text-ish search are all in play.
You're asked to justify, not just pick, the index types.

Technical Requirements:
- A table supporting at least 3 different query patterns (equality, range,
  pattern-match)

Environment Setup:
- Create a table with a numeric range column, a low-cardinality column,
  and a text column

Tasks:
1. Benchmark each query pattern with no index, recording plan and timing
2. Add a B-tree index where appropriate and re-benchmark
3. For the low-cardinality column, evaluate whether a B-tree index is
   actually helpful, and test an alternative if not
4. For the text-search-like pattern, evaluate a GIN/trigram approach and
   compare against the unindexed and B-tree-indexed cases
5. Summarize which index type fit which access pattern and why

Deliverables:
- A before/after benchmark table per query pattern and index type tested

Validation Criteria:
- Each index choice is justified by the access pattern, with benchmark
  evidence, not by default habit

Success Metrics:
- At least one case in the exercise correctly identifies that an index
  would NOT help, with evidence

Expected Learning Outcomes:
- Index selection becomes pattern-driven rather than reflexive

--------------------------------------------------------------------------------
[F1-QO-03] Join Strategy and Statistics Investigation
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Capstone
Estimated Completion Time: 2-3 hours

Objective: Understand why the planner picks nested loop vs. hash vs. merge
join, and how statistics drive that choice.

Business Scenario: A join that was fast last month is now slow, and nobody
changed the query. You're asked to investigate whether the data, not the
query, is the actual cause.

Technical Requirements:
- Two tables with a foreign-key-like relationship and at least 500k rows
  combined

Environment Setup:
- Load both tables; intentionally let statistics go stale on one of them
  (skip ANALYZE after a bulk load)

Tasks:
1. Run the join with stale statistics and capture the plan and estimated
   vs. actual row counts
2. Run ANALYZE on the affected table and re-run the join, comparing plans
3. Identify which join strategy the planner chose in each case and why,
   referencing estimated row counts and cost parameters
4. Force a different join strategy using planner settings and compare
   actual performance against the planner's own choice
5. Summarize how stale statistics caused (or didn't cause) a suboptimal
   plan

Deliverables:
- Before/after plans with row-count estimate deltas clearly highlighted

Validation Criteria:
- Correctly attributes any plan change to the statistics update, with
  evidence from estimated-vs-actual row counts

Success Metrics:
- Forced alternate plan is correctly shown to be equal to or worse than
  the planner's own choice (validating planner trust) or better (justifying
  an override) — either conclusion is acceptable if backed by evidence

Expected Learning Outcomes:
- Statistics-first instinct before blaming the query or the planner

[F1-REP-01] Build a Streaming Replica From Scratch
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Entry
Estimated Completion Time: 2-3 hours

Objective: Stand up physical streaming replication manually, end to end,
without relying on a tool that hides the steps.

Business Scenario: A read replica is needed for reporting load offload, and
you've been asked to build it yourself rather than wait on a platform team.

Technical Requirements:
- Two hosts (or VMs/containers) that can reach each other on the network
- A primary with WAL archiving or replication-ready settings

Environment Setup:
- Provision a primary instance with sample data and a dedicated
  replication role

Tasks:
1. Configure the primary for replication (wal_level, max_wal_senders,
   a replication role with appropriate privileges)
2. Take a base backup of the primary onto the replica host
3. Configure the replica for standby mode and start it
4. Confirm streaming is active and measure initial replication lag
5. Write data on the primary and confirm it appears on the replica,
   noting the lag observed

Deliverables:
- Step-by-step log of commands used and their output
- Lag measurement before and after a write burst

Validation Criteria:
- Replica correctly reflects primary state with measurable, bounded lag

Success Metrics:
- Replica built without consulting a copy-paste tutorial mid-task

Expected Learning Outcomes:
- Replication stops being "a thing Patroni does" and becomes a mechanism
  you understand directly

--------------------------------------------------------------------------------
[F1-REP-02] Replication Slot Management
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Core
Estimated Completion Time: 1-2 hours

Objective: Understand what replication slots actually guarantee, and what
they cost if mismanaged.

Business Scenario: A replica was decommissioned without dropping its slot.
Three weeks later, the primary's disk is filling up and nobody knows why.

Technical Requirements:
- A primary with replication slots enabled
- A replica that can be stopped and started on demand

Environment Setup:
- Create a physical replication slot tied to a live replica

Tasks:
1. Confirm the slot is active and note its WAL retention behavior while
   the replica is connected
2. Stop the replica without dropping the slot and generate write traffic
   on the primary
3. Observe and measure WAL accumulation on the primary caused by the
   inactive slot
4. Decide and justify a remediation: restart the replica vs. drop the
   slot, considering data loss implications
5. Implement the remediation and confirm disk pressure resolves

Deliverables:
- Disk usage measurements before, during, and after the orphaned-slot
  condition

Validation Criteria:
- Correctly identifies the orphaned slot as the root cause using pg_stat
  views, not guesswork

Success Metrics:
- Time from "disk is filling up" to "identified orphaned slot as cause"
  under 15 minutes

Expected Learning Outcomes:
- Recognizing this specific failure signature instantly in production

--------------------------------------------------------------------------------
[F1-REP-03] Monitor and Measure Replication Lag
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Capstone
Estimated Completion Time: 2 hours

Objective: Distinguish between the different ways "lag" can be measured and
why they sometimes disagree.

Business Scenario: A dashboard shows replication lag in bytes, another shows
it in seconds, and they disagree about whether there's a problem. You need
to explain which one is right and why.

Technical Requirements:
- A working streaming replication setup
- Ability to throttle network or simulate slow disk on the replica

Environment Setup:
- Use the replica from F1-REP-01, or build a new primary/replica pair

Tasks:
1. Measure lag using byte-based LSN difference between primary and replica
2. Measure lag using time-based metrics (replay lag)
3. Artificially slow down WAL replay on the replica (e.g. via disk I/O
   throttling) and observe how byte-lag and time-lag diverge
4. Explain, with your measurements as evidence, a scenario where byte-lag
   is low but time-lag is high (or vice versa)
5. Propose which metric should drive alerting and justify the choice

Deliverables:
- Lag measurements under normal and degraded conditions, both metrics

Validation Criteria:
- Correctly explains the divergence using actual measured data, not
  theory alone

Success Metrics:
- Alerting recommendation is defensible against a "why not just use
  bytes" challenge

Expected Learning Outcomes:
- Refusal to trust a single lag number without knowing what it measures

[F1-HA-01] Manual Failover Walkthrough
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Entry
Estimated Completion Time: 2-3 hours

Objective: Perform a clean, manual failover without automation, to
understand exactly what automation tools are doing on your behalf later.

Business Scenario: Patroni/automation isn't deployed yet, but you've been

Technical Requirements:
- A working primary/replica streaming setup

Environment Setup:
- Use or rebuild the F1-REP-01 primary/replica pair

Tasks:
1. Confirm the replica is caught up before proceeding
2. Stop the primary cleanly
3. Promote the replica using the appropriate promotion mechanism for your
   PostgreSQL version
4. Verify the promoted node now accepts writes
5. Document every step as a runbook a teammate could follow without you

Deliverables:
- A written failover runbook produced from your own hands-on steps

Validation Criteria:
- Promoted node correctly accepts both reads and writes post-promotion
- Runbook is followable by someone who didn't do the exercise

Success Metrics:
- Total failover time measured and recorded

Expected Learning Outcomes:
- Concrete understanding of what "promotion" actually changes

--------------------------------------------------------------------------------
[F1-HA-02] Patroni Single-Cluster Bring-Up
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Core
Estimated Completion Time: 3-4 hours

Objective: Stand up a minimal Patroni-managed cluster and understand its
moving parts (DCS, REST API, bootstrap config).

Business Scenario: Leadership wants automated failover. Before rolling it
out broadly, you need a working proof of concept you can explain
component-by-component.

Technical Requirements:
- A distributed configuration store (etcd, Consul, or equivalent)
- 2+ nodes for PostgreSQL, managed by Patroni

Environment Setup:
- Install Patroni and a DCS on a small set of VMs/containers

Tasks:
1. Configure and bootstrap a Patroni-managed primary
2. Add a second node as a Patroni-managed replica
3. Confirm cluster state via the Patroni REST API and DCS directly (not
   just the patronictl CLI)
4. Trigger a manual switchover via patronictl and observe the sequence

[F1-CTR-03] Container Resource Limits and OOM Behavior Exploration
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Capstone
Estimated Completion Time: 2 hours

Objective: Observe directly what happens when a containerized PostgreSQL
instance hits configured memory limits, and how that differs from an
unconstrained host.

Business Scenario: A containerized database was OOM-killed in a shared
environment, and you're asked to understand and prevent recurrence.

Technical Requirements:
- Docker with the ability to set memory limits on a container

Environment Setup:
- A PostgreSQL container, plus a way to generate memory pressure
  (e.g. a workload with high work_mem and many concurrent sorts)

Tasks:
1. Run the container with no memory limit and observe baseline memory
   usage under a moderate workload
2. Apply a deliberately tight memory limit and re-run the same workload
3. Observe and document what happens when the limit is hit (OOM kill,
   degraded performance, etc.)
4. Adjust PostgreSQL-internal memory settings (shared_buffers, work_mem,
   max_connections) to fit safely within the container limit, accounting
   for per-connection overhead
5. Re-test and confirm the workload now completes without hitting the
   limit

Deliverables:
- Before/after behavior under the same workload at the same container
  memory limit

Validation Criteria:
- Tuned configuration completes the workload without triggering an OOM
  event at the same memory limit that previously caused one

Success Metrics:
- Final configuration leaves a documented, deliberate safety margin, not
  a value tuned to the exact edge of failure

Expected Learning Outcomes:
- Treating container memory limits as a hard constraint that database
  configuration must respect, not an afterthought

[F1-IT-01] Disk Space Emergency Triage Drill
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Entry

Objective: Practice the specific triage sequence for an out-of-disk-space
emergency on a database host.

Business Scenario: An alert fires: the volume hosting PGDATA is at 97%
and climbing.

Technical Requirements:
- A test host/container where you can simulate disk pressure (e.g. write

Environment Setup:

1. Identify what's actually consuming space (data files, WAL, logs, an

2. Distinguish between space consumed by live data/WAL (cannot just be

3. Take a safe remediation action and confirm space is reclaimed
4. If the underlying cause is WAL accumulation, trace it back to a root

5. Document the full triage sequence as a quick-reference runbook entry

Deliverables:
- Triage runbook entry
- Before/after disk usage with remediation steps taken

Validation Criteria:
- No data-loss-causing deletion occurs during remediation
- Root cause (not just symptom) is correctly identified when applicable

Success Metrics:
- Time from alert to space reclaimed, measured

Expected Learning Outcomes:
- A safe, fast, repeatable response to one of the most common production
  emergencies

[F1-IT-02] Network Connectivity-to-DB Troubleshooting Tree
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Core
Estimated Completion Time: 2 hours

Objective: Build a systematic troubleshooting tree for "the app can't
connect to the database," covering each layer in order.

Business Scenario: An application team reports connection failures and
immediately assumes the database is down, when the database is, in fact,
healthy.

Technical Requirements:
- A test instance and app-like client on separate hosts/containers
- Ability to introduce connectivity faults (firewall rule, wrong
  pg_hba.conf entry, DNS issue, etc.)

Environment Setup:
- Working app-to-database connectivity as a baseline

Tasks:
1. Document a layered troubleshooting order: DNS/hostname resolution,
   network reachability (port-level), TLS/auth negotiation, pg_hba.conf

2. Introduce one fault at a time (e.g. block the port, then fix it and
   misconfigure pg_hba.conf instead) and confirm your tree correctly
   isolates each one
3. For each fault, record the specific symptom/error message it produces
4. Build a lookup table mapping common error messages to likely layer
5. Test the tree against a fault you did not pre-plan, to confirm it
   generalizes

Deliverables:
- The troubleshooting tree document
- Symptom-to-cause lookup table built from actual reproduced faults

Validation Criteria:
- Tree correctly isolates the injected fault's actual layer in each test,
  including the unplanned one

Success Metrics:
- Time to correctly isolate the fault layer decreases across successive

Expected Learning Outcomes:
- A reusable mental model that prevents wrongly blaming the database for
  network or client-side issues

[F1-IT-03] CPU/Memory Saturation Diagnosis Walkthrough
--------------------------------------------------------------------------------
Difficulty Level: Foundation - Capstone
Estimated Completion Time: 2-3 hours

Objective: Correctly diagnose whether a performance problem is CPU-bound,
memory-bound, or something else entirely, using OS and database evidence
together.

Business Scenario: The host is reported as "at 100% CPU" and everyone
assumes a runaway query, but the actual cause turns out to be something
else.

Technical Requirements:
- A test instance and OS-level tools (top/htop, vmstat, or equivalent)
- A way to generate both a genuinely CPU-bound query load and a
  misleading non-database CPU consumer

Environment Setup:
- Prepare two separate load scenarios: one with a deliberately expensive
  query running heavily, and one with an unrelated OS process consuming
  CPU while the database is actually idle

Tasks:
1. Using OS tools, determine actual per-process CPU/memory consumption
   during each scenario, not just the aggregate host-level number
2. For the database-load scenario, correlate the OS-level finding with
   pg_stat_activity to identify the specific responsible query
3. For the misleading scenario, correctly conclude the database is not
   the cause, with OS-level evidence to back the conclusion
4. Document the specific commands and the exact signal that
   distinguished the two cases
5. Write a short decision guide for the next person who gets a "CPU is
   high" alert

Deliverables:
- Decision guide
- Evidence captured for both scenarios proving the correct diagnosis in
  each

Validation Criteria:
- Misleading scenario is correctly NOT attributed to the database, using
  specific evidence

Success Metrics:
- Decision guide would prevent a wrong first assumption in both tested
  scenarios

Expected Learning Outcomes:
- Diagnosing from process-level evidence instead of host-level
  aggregates, and resisting the obvious-but-wrong first guess

PHASE 1 — MUSCLE MEMORY DRILL BANK
================================================================================
Drills are short, repeatable, and meant to be run many times until they
stop requiring conscious thought. Unlike the assignments above, they are
not one-time projects — log your time on each rep and watch it drop.

--------------------------------------------------------------------------------
DAILY DRILLS (5-15 minutes each, run every working day for at least 2 weeks)
--------------------------------------------------------------------------------
D-01  From a cold terminal, connect to a test instance and produce: current
      connection count, longest-running query, and any blocked sessions —
      using only psql, no saved scripts. Time yourself.
D-02  Given a table name, produce its size, index sizes, and last
      vacuum/analyze timestamps from the catalogs, from memory of the
      relevant views (no lookup).
D-03  Write, from memory, the EXPLAIN ANALYZE incantation that also shows
      buffer usage. Run it against any query.
D-04  Tail and correctly interpret the last 50 lines of the PostgreSQL log
      on a test instance; identify any WARNING/ERROR and explain it.
D-05  Write a one-line psql command to list all roles and their key
      attributes (superuser, login, replication) from memory.
D-06  Check current replication lag (if a replica is available) using both
      a byte-based and a time-based method, from memory.
D-07  Identify the current top 3 queries by total execution time from
      pg_stat_statements, from memory of the column names.

--------------------------------------------------------------------------------
WEEKLY DRILLS (30-60 minutes each, run once per week for at least 6 weeks)
--------------------------------------------------------------------------------
W-01  Take a full backup and restore it to a scratch instance, start to
      finish, without referring to notes. Time the full cycle.
W-02  Trigger a manual failover on a non-prod HA pair and document the
      timeline as if writing a real incident update.
W-03  Pick one table and fully diagnose its bloat level, vacuum health, and
      index efficiency; decide and justify whether action is needed.
W-04  Write a new, small shell script solving a task you haven't scripted
      before, applying the lock/validation/logging conventions from the
      LS domain assignments.
W-05  Review the past week's slow-query or error log entries (real or
      simulated) and produce a one-paragraph summary of any pattern.
W-06  Re-run the F1-IT-02 troubleshooting tree against a fault you didn't
      use last time, and time how long isolation takes.

--------------------------------------------------------------------------------
MONTHLY DRILLS (Half-day, run once per month)
--------------------------------------------------------------------------------
M-01  Full DR drill: simulate a primary loss and execute the F1-DR-01
      runbook exactly as written, timing every step and noting any
      ambiguity discovered under simulated pressure.
M-02  Capacity review: re-run the growth trend analysis (F1-CAP-01) with a
      fresh month of data and compare the new projection against the
      previous month's.
M-03  Security review: re-audit pg_hba.conf, role grants, and network rules
      against the baselines from the SEC/CLD domains; document any drift.
M-04  Cold-start incident simulation: have someone else (or a delayed
      version of yourself) inject an unannounced fault into a test
      environment and respond to it with no prior knowledge of what it is.

--------------------------------------------------------------------------------
SPEED-BUILDING DRILLS (repeat until time targets are consistently met)
--------------------------------------------------------------------------------
SB-01  Identify the single blocking session in a contended test scenario:
       target under 90 seconds from a cold terminal.
SB-02  Restore a known-good backup to a fresh instance and confirm it's
       serving correct data: target under 15 minutes for a small dataset.
SB-03  Diagnose "disk is almost full" down to root cause (not just
       symptom): target under 10 minutes.
SB-04  Write a correct, safe one-off diagnostic query against
       pg_stat_activity joined to pg_locks, from a blank editor: target
       under 3 minutes.

PHASE 1 — REAL-WORLD INCIDENT SIMULATIONS (Foundation Tier)
================================================================================
Each simulation below should be run against a real or realistic test
environment, not solved on paper. Inject the fault, then respond to it as
if it were live. No solutions are given — only the symptom set.

--------------------------------------------------------------------------------
[F1-SIM-01] The Mysterious Connection Exhaustion
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: Application logs show "too many connections" errors. The
database itself appears otherwise healthy.
Symptoms: max_connections nearly saturated; many connections idle in
transaction.
Constraints: You cannot simply restart the application (assume it would
cause customer-visible disruption).
Tasks: Identify the source of the idle-in-transaction connections; decide
whether to terminate sessions and which ones; determine the underlying
application behavior pattern causing it; propose a longer-term fix.
Deliverables: Incident timeline; list of terminated sessions (if any) with
justification; root-cause hypothesis.
Validation Criteria: Connection count returns to a healthy range without
terminating any session still doing legitimate work.
Success Metrics: Correct sessions identified before any termination
action taken.
Expected Learning Outcomes: Distinguishing "idle in transaction" from
healthy connection pooling behavior.

--------------------------------------------------------------------------------
[F1-SIM-02] The Replica That Silently Stopped Catching Up
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: A dashboard shows the replica "connected" but reports from it
are increasingly stale.
Symptoms: Replication connection state shows streaming; lag metric
climbing steadily.
Constraints: The replica must not be taken offline during business hours
without justification.
Tasks: Confirm whether this is a network, disk I/O, or replay-conflict
issue on the replica; quantify the actual lag in both bytes and time;
decide whether the replica is safe to use for reads right now.
Deliverables: Root-cause finding; current safe-use recommendation.
Validation Criteria: Correct identification of the bottleneck layer
(network/disk/replay), backed by evidence.
Success Metrics: Recommendation correctly reflects actual data freshness
risk to anyone querying the replica.
Expected Learning Outcomes: Treating "connected" as necessary but not
sufficient evidence of replica health.

--------------------------------------------------------------------------------
[F1-SIM-03] The Backup Job That's Been "Succeeding" for Months
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: The nightly backup cron job has reported success every night for
months. You're asked to actually verify a backup can be restored.
Symptoms: None visible from logs alone — that's the point.
Constraints: You may not assume the backup is good just because the exit
code was 0.
Tasks: Attempt a full restore of the most recent backup to a clean
instance; verify data integrity and completeness; identify any gap between
"the job exited 0" and "the backup is actually restorable."
Deliverables: Restore validation report.
Validation Criteria: Restore is attempted, not just inspected; integrity
is checked against real expectations (row counts, specific known records).
Success Metrics: Either a confirmed-good restore with evidence, or a
genuine gap identified and documented.
Expected Learning Outcomes: Zero trust in unverified "successful" backup
jobs.

--------------------------------------------------------------------------------
[F1-SIM-04] The Index That Made Things Worse
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: An index was added to "speed up" a query last week. Since then,
write latency on that table has increased and a different read query has
slowed down.
Symptoms: Higher write latency; an unrelated query plan changed
unexpectedly.
Constraints: The original index cannot simply be dropped without
confirming it isn't load-bearing for something else first.
Tasks: Quantify the write-latency impact of the new index; determine why
an unrelated query's plan changed; decide whether to keep, modify, or drop
the index, with evidence.
Deliverables: Before/after performance comparison; final recommendation.
Validation Criteria: Recommendation backed by EXPLAIN ANALYZE and write
latency measurements, not intuition.
Success Metrics: Correctly explains the mechanism behind the unrelated
query's plan change.
Expected Learning Outcomes: Every index is a trade-off, not a free win.

--------------------------------------------------------------------------------
[F1-SIM-05] The Failover That Didn't Fail Over
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: The primary in your HA pair went down. Automated failover was
supposed to promote the replica, but the application is still failing to
connect 5 minutes later.
Symptoms: Replica is healthy and could serve writes; something in the
automation or routing layer didn't complete the handoff.
Constraints: You need to restore service quickly, but also need to know
why automation didn't work before fully trusting it again.
Tasks: Manually complete the failover if automation hasn't; investigate
why the automated path stalled; distinguish between an HA-tool failure and
a connection-routing (pooler/DNS) failure.
Deliverables: Incident timeline; root-cause finding distinguishing HA-tool
vs. routing-layer failure.
Validation Criteria: Service is restored, and the actual failed component
is correctly identified, not just "failover didn't work."
Success Metrics: Time to manual restoration of service.
Expected Learning Outcomes: HA automation has multiple components, any of
which can be the actual point of failure.

--------------------------------------------------------------------------------
[F1-SIM-06] The Slow Query That Only Happens at 9 AM
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: A specific report query is reported as "randomly slow," but
closer inspection shows it correlates with a specific time window.
Symptoms: Query performs fine in isolation; degrades specifically during a
known concurrent batch process.
Constraints: You cannot just move the report off-hours without
understanding the actual contention first (it may recur elsewhere).
Tasks: Reproduce the slowdown by running the query concurrently with the
suspected batch process; identify the specific resource contention (lock,
I/O, CPU, cache eviction); confirm the correlation isn't coincidental.
Deliverables: Reproduction evidence; identified contention mechanism.
Validation Criteria: Slowdown is actually reproduced under controlled
conditions, not inferred from timing alone.
Success Metrics: Correctly identifies the specific shared resource causing
contention.
Expected Learning Outcomes: "Random" performance issues are usually
periodic once you find the right correlated variable.

--------------------------------------------------------------------------------
[F1-SIM-07] The Permission Change That Broke One Thing
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1 hour
Scenario: Following a security hardening pass (similar to F1-SEC-02), one
specific scheduled job starts failing with a permissions error.
Symptoms: Most application functionality works; one specific job/role
fails.
Constraints: You should fix the actual missing grant, not revert the
entire hardening change.
Tasks: Identify exactly which permission is missing for the failing job;
grant only what's needed; confirm no other functionality was broken by the
original hardening pass.
Deliverables: Identified missing grant; minimal-scope fix applied.
Validation Criteria: Fix resolves the specific job without re-opening
unrelated access that was correctly removed.
Success Metrics: Grant added is the minimum necessary, verified by testing
the job afterward.
Expected Learning Outcomes: Security fixes should be surgical, not a
rollback of the whole change.

--------------------------------------------------------------------------------
[F1-SIM-08] The Vacuum That Never Finishes
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: A manual VACUUM on a large table has been running far longer than
expected, and a teammate wants to know if it's stuck or just slow.
Symptoms: Vacuum process visible in pg_stat_activity; unclear if making
progress.
Constraints: Killing it prematurely wastes the progress already made;
letting a genuinely stuck process run wastes time and may be blocking
other operations.
Tasks: Use progress-reporting views to determine if the vacuum is actually
progressing; identify if it's blocked waiting on a lock held by another
session; decide whether to let it continue or intervene.
Deliverables: Progress evidence; decision with justification.
Validation Criteria: Decision is based on actual progress data, not
elapsed time alone.
Success Metrics: Correctly distinguishes "slow but progressing" from
"blocked and stalled."
Expected Learning Outcomes: Long-running maintenance operations are
diagnosable, not just something to wait out blindly.

--------------------------------------------------------------------------------
[F1-SIM-09] The Container That Keeps Restarting
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: A containerized PostgreSQL instance is stuck in a restart loop
after a deployment.
Symptoms: Container starts, runs briefly, then exits; systemd/orchestrator
restarts it; repeat.
Constraints: Each restart attempt briefly drops connections, so rapid
trial-and-error against production-like traffic isn't acceptable.
Tasks: Capture logs from the briefly-running container before it exits;
identify the actual startup failure (config error, permission issue,
corrupted state); fix the root cause rather than just increasing the
restart delay.
Deliverables: Identified root cause; applied fix; confirmation of stable
startup.
Validation Criteria: Container runs stably for a sustained period after
the fix, not just one successful start.
Success Metrics: Root cause identified from logs without needing to guess
and check multiple unrelated changes.
Expected Learning Outcomes: Restart loops are a symptom, not a problem;
the logs from the brief "up" window are the real evidence.

--------------------------------------------------------------------------------
[F1-SIM-10] The Migration That Locked Everything
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: A schema migration deployed during a maintenance window is taking
far longer than estimated, and application errors are starting to appear.
Symptoms: Migration statement still running; growing queue of blocked
queries behind it.
Constraints: The maintenance window is closing and customer impact is
starting.
Tasks: Determine what lock the migration is holding and what it's blocking
behind it; decide whether to let it finish, cancel it, or take another
action; estimate remaining time if letting it finish is viable.
Deliverables: Lock/blocking analysis; decision and outcome.
Validation Criteria: Decision is based on actual lock mode and blocking
evidence, not panic.
Success Metrics: Service impact duration from the moment you started
investigating to resolution.
Expected Learning Outcomes: Locking risk should be assessed before
deployment (per F1-PS-03), but also diagnosable live when it wasn't.

--------------------------------------------------------------------------------
[F1-SIM-11] The Monitoring Gap That Hid a Real Problem
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: A genuine problem (e.g. a slowly growing table due to a missing
cleanup job) existed for weeks before anyone noticed, because nothing was
watching for it.
Symptoms: Discovered only incidentally; no alert ever fired.
Constraints: You need to fix the immediate issue and prevent this class of
gap from recurring, not just patch this one instance.
Tasks: Diagnose and remediate the immediate issue; identify why existing
monitoring (from F1-MON-01/02) didn't catch it; add the missing
check/alert.
Deliverables: Remediation summary; new monitoring check added with
threshold justification.
Validation Criteria: New check would have caught this specific issue
earlier, demonstrated by backtesting against historical data if available.
Success Metrics: Time-to-detection for this class of issue is
meaningfully reduced going forward.
Expected Learning Outcomes: Every undetected incident is also a
monitoring-coverage bug.

--------------------------------------------------------------------------------
[F1-SIM-12] The Credential That Was Still in the Script
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1 hour
Scenario: A routine review of a maintenance script (similar to one built in
the AUTO domain) reveals a hardcoded password.
Symptoms: Script works fine; the problem is entirely latent risk.
Constraints: The fix must not break the automation that currently depends
on this script.
Tasks: Identify every place the credential is exposed (script, logs,
version control history if applicable); remove it in favor of a proper
secrets-handling approach (environment variable, .pgpass, secrets
manager); rotate the exposed credential.
Deliverables: Remediated script; confirmation the old credential no longer
works.
Validation Criteria: No plaintext credential remains in the script, its
logs, or its history going forward; automation continues to function.
Success Metrics: Credential rotation completed with zero automation
downtime.
Expected Learning Outcomes: Treating a credential leak as needing
rotation, not just deletion of the visible copy.

--------------------------------------------------------------------------------
[F1-SIM-13] The "Fixed" Bug That Came Back
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1 hour
Scenario: An issue resolved two weeks ago (e.g. connection exhaustion from
F1-SIM-01) has recurred, identically.
Symptoms: Same symptom signature as a previously closed incident.
Constraints: You must determine whether the original fix was incomplete,
not re-apply the same fix blindly.
Tasks: Review the previous postmortem/fix; determine whether this
recurrence has the same root cause or a different one producing the same
symptom; apply a fix that addresses whichever is actually true.
Deliverables: Comparison between original and current incident; updated
remediation.
Validation Criteria: Conclusion about same-vs-different root cause is
evidence-based, not assumed from symptom match alone.
Success Metrics: If the original fix was incomplete, the gap is
specifically identified.
Expected Learning Outcomes: Recurrence is information, not just
annoyance — it tells you something about the original postmortem's
accuracy.

--------------------------------------------------------------------------------
[F1-SIM-14] The Report That Disagreed With Itself
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1-2 hours
Scenario: Two reports that should show the same underlying number (e.g.
total active users) disagree, and both teams insist their number is right.
Symptoms: No error, no crash — just disagreeing, plausible-looking
numbers.
Constraints: You must determine the actual ground truth, not just defer to
whichever team is more senior or insistent.
Tasks: Trace both reports back to their underlying queries; identify
exactly where the logic, timing, or filtering diverges (e.g. different
point-in-time snapshots, different definition of "active," replica lag
causing one to read stale data); determine which (if either) is correct.
Deliverables: Root-cause explanation of the divergence; recommendation for
which number to trust going forward, or how to reconcile both.
Validation Criteria: Explanation is traced to actual query logic or data
timing, not guessed.
Success Metrics: Both teams' stakeholders would accept the explanation as
sufficient once shown the evidence.
Expected Learning Outcomes: Data disagreements are usually definitional or
timing issues, not corruption — but you have to prove which.

--------------------------------------------------------------------------------
[F1-SIM-15] The Health Check That Lied
--------------------------------------------------------------------------------
Difficulty Level: Foundation | Estimated Time: 1 hour
Scenario: The health-check script from F1-LS-03 reported "healthy"
throughout an incident where the database was, in practice, unusable for
the application.
Symptoms: Health check green; real users experiencing failures.
Constraints: You need to fix the gap in the check without making it
unreliable or excessively heavy for frequent polling.
Tasks: Reproduce the application's actual failure condition; identify
which specific real-world symptom the current health check fails to
detect; extend the check to cover it without significantly increasing its
runtime or risk of false negatives elsewhere.
Deliverables: Updated health-check script; reproduction evidence of the
original gap and the fix closing it.
Validation Criteria: Updated check correctly reports unhealthy under the
reproduced failure condition.
Success Metrics: Check runtime remains within its original performance
budget after the fix.
Expected Learning Outcomes: A health check is only as good as the failure
modes it was actually tested against.
